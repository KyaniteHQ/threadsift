# Threadsift update
Install only the release the Threadsift Instance expects, never a branch or another tag. The owner's request is the yes, so this also installs when automatic install is off.
1. Installed version: `~/threadsift/VERSION`. Then check your memories: when none holds the Instance URL, or the memory is a note that says where the address is stored, ask the owner once in plain text: "What is the public web address of your Threadsift instance? It isn’t a secret, so type it in chat. Start with https:// and include only the host, plus a port if it has one, with no slash or path after it. The instance must be reachable from the internet because the bot runs in Grok’s cloud." When the answer is not an address that starts with https and holds only the host, and a port when it has one, with nothing after it, no slash included, ask again in the same turn. Save the answer as the Instance URL memory, in place of the note and never as a second memory. When the owner does not answer, go on with step 2; the skill asks again at the next link it saves.
2. Run `~/threadsift/threadsift.sh update`. It asks the Instance which release it expects, fetches only that release from raw.githubusercontent.com, checks every file against the hashes in the release's `RELEASE.sha256`, whose own hash the Instance names, and installs the script, `setup.md`, `update.md`, `CHANGELOG.md` and the two routine texts. It keeps the release's skill in `~/threadsift/skill/SKILL.md` for step 3. This also moves the bot back when the Instance expects an older release, but never below bot-v14.
   - `current <tag>` or `installed <tag>`: go on with step 3.
   - `refused <tag>`: the files of that release did not match the hashes the Instance expects, and nothing changed. Say so in one line and stop.
   - `waits <tag>`: that release is not published yet, and nothing changed. Say so in one line and stop.
   - Any other word: say which and stop. `failed` also means the release could not be fetched, the Instance expects a release before bot-v14, or the Instance has no bot install route because it runs an older Threadsift, which the owner updates first; nothing changed.
3. Never in a routine run, a webhook task or a bookmark sync: run `~/threadsift/threadsift.sh skill-staged`. On `staged <tag>`, rewrite the live `threadsift` skill with the skill tool from `~/threadsift/skill/SKILL.md`, read in pages when large: its frontmatter name and description, its body unchanged. Then run `~/threadsift/threadsift.sh skill-saved <tag>` with the tag it printed.
4. Read the live prompt of each routine, then compare it with the text after `Prompt:` in `~/threadsift/routines/threadsift-webhook.md` and `~/threadsift/routines/threadsift-bookmarks.md`. When one differs, update that routine's prompt only. Keep the trigger, schedule, and paused state: an update never changes the schedule of a routine the owner already has, and only a new install gets the 3-hour schedule from `setup.md`.
5. Delete `~/threadsift/state/bookmarks.json` if it exists: a bot-v2 install left it, and the bot has not read it since bot-v3, because the Threadsift Instance keeps the bookmark cursor.
6. When the tag differs from the version memory, read `~/threadsift/CHANGELOG.md`, which step 2 installed and checked, and tell the owner in plain words what changed since the version in the memory. Then write the tag to the version memory.
7. Reply in one line: updated to <tag>, up to date, or what failed.
