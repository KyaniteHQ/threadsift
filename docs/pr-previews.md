# Operate PR previews

`.github/workflows/bundle.yml` builds same-repository PRs without secrets and uploads only the Worker bundle, web assets and SQL migrations. `.github/workflows/pr-preview.yml` runs on `main` after that workflow succeeds. It deploys the matching artifact using tools, configuration and dependencies checked out from `main`. Artifact JavaScript is uploaded with Wrangler's `no_bundle` mode and additional-module discovery disabled; it is never executed on the runner. Artifact config, scripts and package manifests are not consumed. Fork PRs are excluded.

Restrict the GitHub environment `preview` to the branch `main`. Store `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_SETUP_CODE` and `DEMO_OWNER_PASSWORD` there. The setup code needs at least sixteen characters; the demo password needs at least fifteen. Impeccable Reviews must hold that same demo password. The deployed PR Worker receives its own encryption secret and setup code, and the demo password is sent to its setup or sign-in endpoint. It receives no Cloudflare API token or live credentials. Keep live and post-merge credentials in their own environments.

To change the demo password, set the new value in the `preview` environment and in Impeccable Reviews' saved test account, then reset the owner of each open preview. A redeploy keeps an existing owner, so its sign-in with the new value answers 401 and the deploy stops with "Preview owner sign-in failed". `wrangler d1 list` shows each open preview as `threadsift-pr-<n>-db`. For each one, put a one-time `PASSWORD_RESET_CODE` Worker secret of at least 32 characters on `threadsift-pr-<n>` (`wrangler secret put`, reading the value from stdin), send that code and the new password to `POST /api/password/reset` on the preview (204), delete the secret, check that `POST /api/login` with the new password answers 204, and rerun the PR's preview deploy (`gh run rerun <run id> --failed`).

The Cloudflare token needs Worker script edit, D1 edit, R2 storage edit and Queues edit, with the account reads those operations require. It also needs KV read: Wrangler 4.158.0 `wrangler delete` lists legacy Workers Sites asset namespaces after deleting the Worker, even when this config uses no KV (`deleteSiteNamespaceIfExisting` in the installed Wrangler source). Without it, the command can report `10000` after the Worker is already gone; rerunning close resumes the remaining cleanup. Worker secrets are initialized only when absent. Updates preserve the encryption key and setup code, so saved Provider credentials stay readable. Do not remove the encryption secret while retaining the preview database.

`tools/pr-preview.ts` derives the resource manifest from the PR number. Its stable identity is the repository plus PR number; head changes and branch renames retain the Instance. Closing deletes it; reopening creates a fresh one. No arbitrary Worker, database, bucket or Queue name is accepted. GitHub deployment records use `pr-N` as the environment and the built PR head SHA as the revision. They remain as history after the resources are deleted.

Inspect a manifest without a Cloudflare login:

```sh
node tools/pr-preview.ts deploy 222 --plan
node tools/pr-preview.ts close 222 --plan
```

Compile a downloaded artifact without remote mutations:

```sh
node tools/pr-preview.ts deploy 222 --dry-run /path/to/artifact
```

The trusted workflow runs `--apply`. Wrangler 4.158.0 provisions the named D1, R2 and Queue resources. The tool initializes missing secrets, applies the artifact migrations, provisions the demo owner and Pastes the demo links in `tools/preview-owner.ts`. Existing owners and Items are retained. The API's normalized URL filter finds each existing demo Item even beyond the first list page, so provisioning neither duplicates nor refreshes it, except a placeholder Item that holds no Digest, which it Pastes again. Fetching happens asynchronously through the preview Queue. Provisioning logs out its session and runs no deployed check suite. A first deploy can briefly answer errors before migrations finish.

Provisioning saves no Provider, and the preview Worker has no Workers AI binding, because Workers AI is billed per call. A preview holds these demo Items:

- The four demo links in `tools/preview-owner.ts` are fetched and listed with no Digest, Topic or Related Item.
- Twelve placeholder Items, `Demo item 1` to `Demo item 12` at `https://example.com/demo/<n>`, are Pasted with a caller-sent `page` and Digest (`docs/spec.md`, Interfaces, `POST /api/items`), so they publish with a Summary and Key points without a Provider. Items 1 to 6 carry the Topic `Demo topic` and two Tags each; each pair of Tags in `demoTagMerges` (`tools/preview-demo.ts`) is one near-duplicate spelling, such as `nodejs` and `node.js`. Items 7 to 12 carry no Tags and two Items per pair of Topics in `demoTopicMerges`, one Item for each Topic of the pair, such as `ML` and `Machine learning`, so each Topic of a pair has an Item. The placeholders hold no text from the owner's library. Provisioning reads each Item every 5 seconds until its Digest shows, for at most 120 seconds from the first read (`DIGEST_WAIT_MS`, a choice of this repository, shared by all twelve Items). It fails the deploy when the time ends or an Item's `status` is `failed`. A read that answers 404 or 5xx counts as "not yet", and a read has the 30-second request timeout, so the wait ends within 155 seconds: a read that returns just before the 120 seconds end is followed by the 5-second pause and one more read of up to 30 seconds. An Item that exists without a Digest is Pasted again, so a rerun after a failed deploy repairs it. A run against a local Worker and Queue (`wrangler dev`) published all twelve Items and finished provisioning in 12 seconds; no run on Cloudflare has timed twelve Items, and the 120 seconds are a choice of this repository.
- Open Proposals, one for each pair, when the preview's database has a `proposals` table: six `tag-merge` rows for the Tag pairs, and three `topic-merge` rows for the Topic pairs when `proposals` also has the column `from_topic_id`. `seedDemoProposals` in `tools/preview-demo.ts` makes three `wrangler d1 execute DB --remote` calls. The first reads the columns of `proposals` and `pins` with `pragma_table_info`, in one query over a `VALUES` list of probes, because six `SELECT ... UNION ALL` terms fail on D1 with `too many terms in compound SELECT` (local D1, Wrangler 4.158.0). The second runs one `INSERT ... SELECT ... ON CONFLICT DO NOTHING` for each kind, and the Highlight inserts (the next item), in a single command. The third reads the pairs and the demo Highlights back. The pair inserts join the Tags or Topics by their `catalogKey`, so a redeploy adds nothing and a Rejected pair stays Rejected. A build before the `proposals` table deploys without the step, and a build whose `proposals` table is still the one of `main` deploys with the Tag and Topic pairs and no lost-Highlight row; a redeploy after a PR's migration adds the rows that its new column allows. The read-back lists each pair of either kind that has no row, in any state and in either direction, and fails the deploy with the pairs' names, for example when a Digest never published a Tag or a Topic. A pair that has a `tag-merge` Pin whose `from_key` is either Tag of the pair is an accepted pair and does not count as missing, because Accept deletes the merged-away Tag and its row and keeps the Pin; the check reads Tag Pins when `pins` exists. A Topic pair counts the same way through a `topic-merge` Pin, and the check reads Topic Pins only when `pins` has the column `into_topic_id`, which the migration that adds Topic Pins creates. The Tag reasons are the text a real Claude Code run stored for these Tags (container, Claude Code 2.1.319, 2026-11-11). No Provider ran on the Topics, so the Topic reasons come from `tools/copy/write-copy.sh`, asked for the agent's one-line reason in the style of the Tag reasons.
- Three demo Highlights and three open `highlight-lost` Proposals, one for each Highlight, when `proposals` has the column `highlight_id`, which the migration that adds the lost-Highlight Proposals creates (`highlightProposals` in `SCHEMA_PROBES`, `tools/preview-demo.ts`). The Highlights sit on `Demo item 1` to `Demo item 3` and are marked as no longer found. Each quote is a sentence that the Item's text does not hold, and the sentences come from `tools/copy/write-copy.sh`. `demoLostHighlights` in `tools/preview-demo.ts` lists them, and `tools/preview-demo-highlights.ts` holds the other column values and the SQL. The placeholders hold no text from the owner's library, and no Item is added, so the Digest wait and the sum of deadlines below do not change. Provisioning inserts the Highlights, then the rows, in the same `d1 execute` command as the Tag and Topic rows. A Highlight is inserted only when its Item has no Highlight with the same quote, and a row only when its Highlight has none, so a redeploy adds nothing and a Rejected row stays Rejected, with its Highlight in place. A preview whose `proposals` table lacks `highlight_id` gets neither, and a redeploy after the PR's migration adds both. The preview Worker keeps the Cron Trigger of `wrangler.jsonc` (`tools/pr-preview.ts` copies `triggers`), so the sweep runs every minute on a preview and its search stage gives each demo Highlight a search part. The Highlights page lists the Highlight, and Remove deletes it. The read-back lists each demo Highlight whose Item is missing and each demo Highlight that exists with no `highlight-lost` row, in any state, and fails the deploy with the quote and the Item's address. A demo Highlight that Accept removed does not count as missing. Accept removes the Highlight and its row, and nothing records the removal, so the next redeploy puts the Highlight and an open row back.

- Three open `overview-gap` Proposals, one for each of the Topics `Demo topic`, `Machine learning` and `Games`, when `proposals` has the column `topic_id`, which the migration that adds the overview-gap Proposals creates (`overviewProposals` in `SCHEMA_PROBES`, `tools/preview-demo.ts`). `Demo topic` holds Items 1 to 6, and `Machine learning` and `Games` are the `into` Topics of two pairs in `demoTopicMerges`. Every demo Item has a Digest and no Topic page overview, because a preview has no Provider, so each of these Topics has Items that its overview does not cover and the row's counts are true. The `reason` is the fixed code `plain-check`, not text. `tools/preview-demo-overviews.ts` holds the SQL. The rows go in the same `d1 execute` command as the other inserts, each as an `INSERT ... SELECT ... ON CONFLICT DO NOTHING` joined to `topics` by `catalogKey`, so a redeploy adds nothing and a Rejected row stays Rejected. A preview whose `proposals` table lacks `topic_id` gets none, and a redeploy after the PR's migration adds them. Reject works on these rows. Accept answers 409 `no-provider` and leaves the row, because the overview is written by a Provider; a reviewer sees that answer as the preview's limit, not as a defect. The read-back lists each of the three Topics that exists and has no `overview-gap` row in any state, and fails the deploy with the Topic's name. A Topic that an accepted Topic merge deleted does not exist and is not listed. No Item is added, so the Digest wait and the sum of deadlines below do not change.

A screen that needs more than that gets it from a Paste made outside the preview. A Topic page overview and a Related Items section cannot appear on a preview: both jobs open only when a Provider is saved (`providerSet` in `src/core/ai-tasks.ts`), and no route takes a caller-sent overview or pick. Neither weekly Proposals run (the Tag run and the Topic run) opens anything on a preview: the Cron Trigger fires every minute, but each claim needs a saved Provider, which a preview has none of. A Proposal on a preview exists only where provisioning inserted it, and the owner can accept or reject it, except an `overview-gap` row, whose Accept needs a Provider. An HTTP Provider that someone saves by hand on a preview still runs on that key. An open preview keeps the binding and its saved `workers-ai` Provider until its PR's next `bundle` run redeploys it with the tools on `main`; after that, its AI tasks fail with `provider-unavailable`. A change to `tools/preview-owner.ts` reaches a preview only when its provisioning runs after the change lands on `main`, because provisioning runs the tools checked out from `main`. That run adds the Items and Proposals the preview lacks and leaves the Items it has unchanged. `https://example.com/` has no article text, and it stays in the demo because it shows a design reviewer an Item whose fetch found no article.

The read that provisioning makes, `GET /api/items?url=`, retries on 404 and 5xx up to 11 times, 5 seconds apart, as the live deploy waits for `/api/session` in `.github/workflows/gate.yml`. That window is a repository choice and not a Cloudflare figure; Cloudflare's docs state no propagation time for a new Worker. Run 42932873349 got a 404 from `GET /api/items` right after setup and sign-in had answered, on a Worker that was seconds old, and its rerun passed. The app has no 404 for that route, so the response came from the edge before the new Worker was fully routed. A fresh scratch Worker with the same asset and `run_worker_first` settings answered 26 of 26 polls without a 404, so the cause stays inferred. The Paste is a single call and is never retried.

Before it deploys, the tool compares the migration names that the existing preview D1 has applied (`d1_migrations`, read with `wrangler d1 execute`) with the `.sql` files in the artifact's `migrations/`. A rebase that renumbers a migration leaves a name in the database that the artifact lacks, and `wrangler d1 migrations apply` then fails with code `7500`. In that case the tool logs one line and resets the preview with the operations that `close` runs: it detaches the Queue consumer and deletes the Worker, waits, then deletes the Queue, empties and deletes the R2 bucket, and deletes the D1. The deploy that follows creates every resource as it does for a new PR, with fresh secrets, so the owner, Items, Provider and files start empty. Recreating only the D1 does not work: the deployed Worker still names the deleted database, and the deploy fails with code `7404` (reproduced with Wrangler 4.158.0).

The wait lets in-flight work of the deleted Worker end before R2 and the D1 are touched, because a fetch job that writes an image after the bucket is emptied could leave bytes under a key that the new database reuses (`items/<id>/`). It lasts `FETCH_DEADLINE_MS` (120 s, `src/core/fetch-link.ts`) plus 30 s, the time `waitUntil()` can extend a request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Cloudflare's docs do not say how long an invocation of a deleted Worker can continue, so this bound is ours, and no run has held a fetch across a reset. The D1 is deleted last. A run that stops before that finds the foreign name again and repeats the reset; a run that stops after it finds no database and deploys as a new preview. A database with only names the artifact also has, or with no migration table, is migrated as before. The GitHub deployment carries the preview URL on the PR head SHA for Impeccable Reviews.

`tools/preview-selection.ts` rejects fork, failed, obsolete and closed bundle runs. A job rechecks the PR immediately before applying its manifest. Jobs for one PR serialize without cancellation. A PR that closes during deployment is collected by the next sweep. Cleanup runs on pushes to `main`, on the schedule in the workflow, or by dispatch from `main`:

```sh
gh workflow run pr-preview.yml --ref main -f pr=222
```

An empty dispatch sweeps closed previews. Selection reads the latest GitHub deployment for each `pr-N` environment, checks the PR's state and skips inactive deployments. Successful cleanup marks every deployment for that PR inactive. This also covers unmerged PRs, without `pull_request_target`. Schedules can be delayed by GitHub; the dispatch provides a manual recovery. The workflow must first exist on `main` before `workflow_run` can trigger it ([GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

Cloudflare's [Workers Previews](https://developers.cloudflare.com/workers/previews/resources/) cannot consume Queues or receive Cron triggers, so these previews use separately named Workers. Trusted config copies shared runtime settings from `wrangler.jsonc`, with no live bindings, routes or variables. Cloudflare refuses Worker deletion while it consumes a Queue (code `10064`, reproduced with Wrangler 4.158.0); cleanup removes only the manifest Worker's consumer before deleting it ([Queues commands](https://developers.cloudflare.com/workers/wrangler/commands/queues/)). Wrangler 4.158.0 has no populated-bucket empty command (`pnpm exec wrangler r2 bucket --help`), so `tools/preview-cloudflare.ts` uses the documented [R2 prefix-delete job](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/jobs/methods/create/) before deleting the bucket.

Preview failures do not block the gate. A failed deploy or cleanup stays red in Actions, and a deploy also records a failed GitHub deployment. A failed cleanup leaves its deployment active so a later sweep retries it. Reruns skip absent resources and confirm all manifest resources are gone. Deletion has no data rollback; a later deploy creates an empty preview. The per-command and HTTP deadlines in the tools fit inside the workflow's job deadline. Without a reset, the sum of the deadlines is 2,335 seconds against the job's 2,700 (45 minutes): 360 for the migration history check, 600 for the deploy, 240 for the secrets, 120 for the migrations, 655 for owner provisioning (the setup, sign-in and sign-out calls at 30 each, an inventory read of 11 tries at 30 seconds with 5 between, a Paste of 30 and the 155-second Digest wait) and 360 for the three `d1 execute` calls of the Proposals step, which stay three whatever the number of pairs. This sum is our estimate from the constants in `tools/pr-preview.ts` and `tools/preview-owner.ts`, and it leaves out checkout and install. A failure stops the sequence and leaves later resources for a rerun. Once the consumer is detached, the Worker is removed before bucket cleanup so it cannot create new objects. No failure path deletes beyond the printed manifest.
