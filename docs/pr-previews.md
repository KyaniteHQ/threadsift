# Operate PR previews

`.github/workflows/bundle.yml` builds same-repository PRs without secrets and uploads only the Worker bundle, web assets and SQL migrations. `.github/workflows/pr-preview.yml` runs on `main` after that workflow succeeds. It deploys the matching artifact using tools, configuration and dependencies checked out from `main`. Artifact JavaScript is uploaded with Wrangler's `no_bundle` mode and additional-module discovery disabled; it is never executed on the runner. Artifact config, scripts and package manifests are not consumed. Fork PRs are excluded.

Restrict the GitHub environment `preview` to the branch `main`. Store `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`, `PREVIEW_SETUP_CODE` and `DEMO_OWNER_PASSWORD` there. The setup code needs at least sixteen characters; the demo password needs at least fifteen. Impeccable Reviews must hold that same demo password. The deployed PR Worker receives its own encryption secret and setup code, and the demo password is sent to its setup or sign-in endpoint. It receives no Cloudflare API token or live credentials. Keep live and post-merge credentials in their own environments.

To change the demo password, set the new value in the `preview` environment and in Impeccable Reviews' saved test account, then reset the owner of each open preview. A redeploy keeps an existing owner, so its sign-in with the new value answers 401 and the deploy stops with "Preview owner sign-in failed". `wrangler d1 list` shows each open preview as `threadsift-pr-<n>-db`. For each one, put a one-time `PASSWORD_RESET_CODE` Worker secret of at least 32 characters on `threadsift-pr-<n>` (`wrangler secret put`, reading the value from stdin), send that code and the new password to `POST /api/password/reset` on the preview (204), delete the secret, check that `POST /api/login` with the new password answers 204, and rerun the PR's preview deploy (`gh run rerun <run id> --failed`).

The Cloudflare token needs Worker script edit, D1 edit, R2 storage edit and Queues edit, with the account reads those operations require. It also needs KV read: Wrangler 4.158.0 `wrangler delete` lists legacy Workers Sites asset namespaces after deleting the Worker, even when this config uses no KV (`deleteSiteNamespaceIfExisting` in the installed Wrangler source). Without it, the command can report `10000` after the Worker is already gone; rerunning close resumes the remaining cleanup. Worker secrets are uploaded only when absent. Updates preserve the encryption key and setup code, so saved Provider credentials stay readable. Do not remove the encryption secret while retaining the preview database.

`tools/pr-preview.ts` derives the resource manifest from the PR number. Its stable identity is the repository plus PR number; head changes and branch renames retain the Instance. Closing deletes it; reopening creates a fresh one. GitHub deployment records use `pr-N` as the environment and remain as history after the resources are deleted.

Inspect a manifest without a Cloudflare login:

```sh
node tools/pr-preview.ts deploy 222 --plan
node tools/pr-preview.ts close 222 --plan
```

Compile a downloaded artifact without remote mutations:

```sh
node tools/pr-preview.ts deploy 222 --dry-run /path/to/artifact
```

The trusted workflow runs `--apply`. `deployWithSecrets` in `tools/preview-secrets.ts` uploads the Worker with the secrets it lacks, the tool applies the artifact migrations, and `tools/preview-owner.ts` provisions the demo owner and Pastes the demo links. Existing owners and Items are retained, and provisioning refreshes no demo Item except a placeholder that holds no Digest. It runs no deployed check suite.

Provisioning saves no Provider, and the preview Worker has no Workers AI binding, because Workers AI is billed per call. A preview holds these demo Items and Proposals:

- The four demo links in `tools/preview-owner.ts`, fetched and listed with no Digest, Topic or Related Item.
- Twelve placeholder Items, `Demo item 1` to `Demo item 12` at `https://example.com/demo/<n>`, Pasted with a caller-sent `page` and Digest (`docs/spec.md`, Interfaces, `POST /api/items`), so they publish without a Provider and hold no text from the owner's library. `demoTagMerges` and `demoTopicMerges` in `tools/preview-demo.ts` set their Tags and Topics as near-duplicate pairs. Provisioning waits for each Digest for at most 120 seconds (`DIGEST_WAIT_MS`, a choice of this repository, shared by all twelve Items), counts a 404 or 5xx read as "not yet", and fails the deploy when the time ends or an Item's `status` is `failed`. With the 30-second request timeout, the wait ends within 155 seconds. A run against a local Worker and Queue (`wrangler dev`) published all twelve Items and finished provisioning in 12 seconds; no run on Cloudflare has timed twelve Items.
- Open Proposals of five kinds: `tag-merge` and `topic-merge` pairs, three `highlight-lost` rows with their demo Highlights, three `overview-gap` rows and three `items-disagree` rows. `seedDemoProposals` in `tools/preview-demo.ts` seeds each kind only when the preview's `proposals` table has the column that kind needs (`SCHEMA_PROBES` in `tools/preview-demo-schema.ts`), so a build before a kind's migration deploys without it and a redeploy after the migration adds it. A redeploy adds only what is missing, so a Rejected row stays Rejected. The read-back fails the deploy with the names of any seeded pair that has no row in any state, unless a Pin shows that Accept merged it. Accept of a `highlight-lost` row removes the Highlight and its row, and nothing records the removal, so the next redeploy puts both back.
  - The Tag reasons are the text a real Claude Code run stored for these Tags (container, Claude Code 2.1.319, 2026-11-11). The Topic, Highlight and disagreement texts come from `tools/copy/write-copy.sh`.
  - A preview has no Provider, so no overview run has completed and the counts of an `overview-gap` row are true; they stop being true once a Provider writes an overview. On a preview with no Provider, Accept of an `overview-gap` row is expected to answer 409 `no-provider` and leave the row, which a reviewer sees as the preview's limit, not as a defect. That answer is unverified, because the app code that serves it is not part of the change that seeds these rows.
  - `seedDemoProposals` makes three `wrangler d1 execute DB --remote` calls. The first reads the columns of `proposals` and `pins` with `pragma_table_info` in one query over a `VALUES` list, because the workerd that Wrangler 4.158.0 runs allows at most 5 terms in a compound `SELECT` (`sqlite3_limit(db, SQLITE_LIMIT_COMPOUND_SELECT, 5)` at [`src/workerd/util/sqlite.c++:1490`](https://github.com/cloudflare/workerd/blob/v1.20261104.1/src/workerd/util/sqlite.c%2B%2B#L1490), workerd v1.20261104.1; SQLite's own default is [500](https://www.sqlite.org/limits.html#max_compound_select)). `pnpm exec wrangler d1 execute DB --local --persist-to <dir> --command "SELECT 1 UNION ALL SELECT 2 UNION ALL SELECT 3 UNION ALL SELECT 4 UNION ALL SELECT 5 UNION ALL SELECT 6"` answers `too many terms in compound SELECT: SQLITE_ERROR`, and the same command with five terms returns five rows. Whether remote D1 has the same limit is not confirmed.

A screen that needs more than that gets it from a Paste made outside the preview. A Topic page overview and a Related Items section cannot appear on a preview: both jobs open only when a Provider is saved (`providerSet` in `src/core/provider-saved.ts`), and no route takes a caller-sent overview or pick. For the same reason no weekly model run opens anything there, although the Cron Trigger fires every minute. A Proposal exists on a preview only where provisioning inserted it. The owner can accept or reject it, except an `overview-gap` row, whose Accept needs a Provider. Accept of an `items-disagree` row needs no Provider and writes its Pin (`src/core/disagreement-accept.ts`), and answers 409 `not-current` once either Item has a new Digest. If an Item gets a new Digest on a preview, the Proposals page hides its `items-disagree` row, because the row's token no longer matches. An HTTP Provider that someone saves by hand on a preview still runs on that key. An open preview keeps the binding and its saved `workers-ai` Provider until its PR's next `bundle` run redeploys it with the tools on `main`; after that, its AI tasks fail with `provider-unavailable`. A change to `tools/preview-owner.ts` reaches a preview only when its provisioning runs after the change lands on `main`, because provisioning runs the tools checked out from `main`. `https://example.com/` has no article text, and it stays in the demo because it shows a design reviewer an Item whose fetch found no article.

The Worker never serves a version without its secrets. `deployWithSecrets` passes the secrets it lacks to `wrangler deploy --secrets-file`, so a new Worker gets `THREADSIFT_SECRET_KEY` and `SETUP_CODE` in its first upload and no value reaches an argument or a log. The flag "Applies additively with secrets from previous deployments - omitted secrets will not be deleted" (`--help` of Wrangler 4.158.0), so an existing Worker keeps its stored values. The generated config lists both under `secrets.required`, so Wrangler refuses to upload a new Worker without them (`addRequiredSecretsInheritBindings` in the installed Wrangler source). Cloudflare documents the upload path under ["Upload secrets alongside code"](https://developers.cloudflare.com/workers/configuration/secrets/).

Setting the secrets with `wrangler secret bulk` after `wrangler deploy` would make a second Worker version, which the upload above avoids. Cloudflare says that "deployment changes take time to reach every location on Cloudflare's network" and that "locations can use different versions" ([versions and deployments](https://developers.cloudflare.com/workers/configuration/versions-and-deployments/)). With two versions, a location can still serve the first one, and the app answers `POST /api/setup` with 503 and `setup-missing` when its version holds no `SETUP_CODE` (`refuse` in `src/http/refusals.ts`). The failed first attempt of run 43271127249 printed a 503 for the setup call 39 seconds after the tool started, when the tool still set the secrets in a second version. That run's log held no response body, so the link between the two is inferred from the status, the call and a local Worker without `SETUP_CODE` that answers the same way. It is not observed on Cloudflare. Run 42932873349, which got a 404 right after setup, shows that a new `workers.dev` route can also answer before it serves the Worker.

Before provisioning sends its first write, `awaitRoute` in `tools/preview-owner.ts` waits until `GET /api/session` answers 200. A 200 shows that the new route serves the Worker and that the owner and session tables exist. It shows nothing about secrets, which are already in the first version. The window is a repository choice and not a Cloudflare figure.

The read of the demo Items, `GET /api/items?url=`, retries the same way through `untilAnswered`, as the live deploy waits for `/api/session` in `.github/workflows/gate.yml`. Run 42932873349 got a 404 from `GET /api/items` right after setup and sign-in had answered, on a Worker that was seconds old, and its rerun passed. The app has no 404 for that route, so the response came from the edge before the new Worker was fully routed. A fresh scratch Worker with the same asset and `run_worker_first` settings answered 26 of 26 polls without a 404, so the cause stays inferred. The setup call and the Paste are never retried.

Before it deploys, the tool compares the migration names that the existing preview D1 has applied (`d1_migrations`, read with `wrangler d1 execute`) with the `.sql` files in the artifact's `migrations/`. A rebase that renumbers a migration leaves a name in the database that the artifact lacks, and `wrangler d1 migrations apply` then fails with code `7500`. In that case the tool resets the preview with the operations that `close` runs, and the deploy that follows creates every resource as for a new PR, so the owner, Items, Provider and files start empty. Recreating only the D1 does not work: the deployed Worker still names the deleted database, and the deploy fails with code `7404` (reproduced with Wrangler 4.158.0).

The wait lets in-flight work of the deleted Worker end before R2 and the D1 are touched, because a fetch job that writes an image after the bucket is emptied could leave bytes under a key that the new database reuses (`items/<id>/`). It lasts `FETCH_DEADLINE_MS` (120 s, `src/core/request-waits.ts`) plus 30 s, the time `waitUntil()` can extend a request ([Workers limits](https://developers.cloudflare.com/workers/platform/limits/)). Cloudflare's docs do not say how long an invocation of a deleted Worker can continue, so this bound is ours, and no run has held a fetch across a reset. The D1 is deleted last, so a run that stops earlier finds the foreign name again and repeats the reset.

`tools/preview-selection.ts` rejects fork, failed, obsolete and closed bundle runs, and a job rechecks the PR before it applies its manifest. A PR that closes during deployment is collected by the next sweep. Cleanup runs on pushes to `main`, on the schedule in the workflow, or by dispatch from `main`:

```sh
gh workflow run pr-preview.yml --ref main -f pr=222
```

An empty dispatch sweeps closed previews, unmerged PRs included, without `pull_request_target`. Schedules can be delayed by GitHub; the dispatch provides a manual recovery. The workflow must first exist on `main` before `workflow_run` can trigger it ([GitHub events](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows)).

Cloudflare's [Workers Previews](https://developers.cloudflare.com/workers/previews/resources/) cannot consume Queues or receive Cron triggers, so these previews use separately named Workers. Trusted config copies only shared runtime settings from `wrangler.jsonc`. Cloudflare refuses Worker deletion while it consumes a Queue (code `10064`, reproduced with Wrangler 4.158.0); cleanup removes only the manifest Worker's consumer before deleting it ([Queues commands](https://developers.cloudflare.com/workers/wrangler/commands/queues/)). Wrangler 4.158.0 has no populated-bucket empty command (`pnpm exec wrangler r2 bucket --help`), so `tools/preview-cloudflare.ts` uses the documented [R2 prefix-delete job](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/jobs/methods/create/) before deleting the bucket.

Preview failures do not block the gate. A failed deploy or cleanup stays red in Actions, and a failed cleanup leaves its deployment active so a later sweep retries it. Deletion has no data rollback; a later deploy creates an empty preview. The per-command and HTTP deadlines in the tools fit inside the workflow's job deadline: without a reset their sum is 2,405 seconds against the job's 2,700 (45 minutes). That sum is our estimate from the constants in `tools/pr-preview.ts`, `tools/preview-secrets.ts` and `tools/preview-owner.ts`, and it leaves out checkout and install. A failure stops the sequence and leaves later resources for a rerun. No failure path deletes beyond the printed manifest.
