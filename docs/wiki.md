## Topic pages

The page for one Topic (slice 22). The server side is `src/core/topic-page.ts` (the read), `src/core/topic-retry.ts` (Try again), `src/core/topic-overview-contract.ts` (the schemas), `src/core/topic-path.ts` (the address) and `src/http/topic-routes.ts`. The run that writes the overview is the `topic_overview` job (`src/core/topic-overview-job.ts`; see `docs/architecture/jobs-leases-and-the-schedule.md`, and `docs/architecture/ai-tasks-and-providers.md`, The `topic_overview` task).

**Identity.** The address of a Topic page is `/topics/<key>`, where `<key>` is the Topic's `catalogKey` (`docs/architecture/data-model-outline.md`, Catalog keys) written with `encodeURIComponent` and with `.` written as `%2E` (`topicPath` in `src/core/topic-path.ts`). A key made only of dots, or of `~` characters followed only by dots, gets one more leading `~` (`topicSegment`: `.` is `~.`, `..` is `~..`, `~..` is `~~..`), because a path segment of dots is a directory step that a browser, a proxy or the server collapses before the route sees it, and percent-encoding does not stop that. Every other key, `~node` included, is written as it is, and `topicKeyOfSegment` undoes the prefix. The API takes the same segment (`topicApiPath`). A Topic written `İstanbul` and one written `istanbul` have the same key and so one page. A key may contain a dot (`node.js`), and the static fallback answers `index.html` only when the last path segment has no `.` (`docs/architecture/web-app.md`), so the dot is escaped. `GET /api/topics/{key}` runs the key it receives, after `topicKeyOfSegment`, through `catalogKey` again, so the page answers for the Topic's name in any spelling. `topic_pages` and `topic_leases` are keyed by the `topics` row id, which is generated and never reused. `built_from` names Items by their id and Digests by the id of the AI task that wrote them. The Digest id is a version token: the only use is the comparison with `digests.task_id`, so the AI task it names need not survive. Nothing else points at a Topic page.

| Event | What happens to the reference |
|---|---|
| Rename of the Topic's first spelling | The key and the ids stay. The address and `built_from` keep working. |
| Refresh or new Digest of an Item | The Item id stays. The Digest's AI task id changes, so the next overview run counts that Item as not yet built from and reads its new Digest. |
| Re-import, export and restore | Items keep their ids. An export carries `topic_pages` with the `topics` rows and Items it points at, so the Item ids in `built_from` still resolve. The Digest ids are version tokens: the export drops the `ai_tasks` row of a Digest that a newer Digest replaced, and the token still compares right after a restore, because the restore keeps every id and `digests.task_id` is restored unchanged. `topic_leases` is a working table and stays out of the export. Not built. |
| Deleting an Item | `deleteItem` removes no `topic_pages` row, because the page holds the Item id only inside JSON. The Item leaves the Topic's list at once. The next run finds the ids in `built_from` that no longer belong to the Topic (`removedItemIds` in `src/core/topic-coverage.ts`), sends them to the model as removed and stores an overview without them. |
| An accepted disagreement of two Items | The `items-disagree` Pin names the two Items (`pins.from_item_id`, `pins.into_item_id`) and the Digest task ids they carried, so the Topic read lists the entry only while both Items sit under the Topic and still carry those Digests. A Topic merge leaves it listed under the survivor, because the Pin names no Topic. A new Digest of either Item or a move out of the Topic hides it, and deleting either Item deletes the Pin (`docs/proposals.md`, Identity). |
| Moving an Item to another Topic | The same as a delete for the old Topic. |
| Merge of two Topics | Breaks the reference. The `topic-keys` step (`docs/architecture/data-model-outline.md`, Catalog keys) deletes the losing Topic's page and lease with the losing row and moves its Items to the kept Topic, which has no run queued and counts them as uncovered at its next run. A `topic-keys` merge also repoints the Topic Proposals and Topic Pins that name the losing Topic, and rewrites the stored Digests of the moved Items to the kept Topic's name (the shared Topic rewrite, `docs/architecture/data-model-outline.md`, Catalog keys). `pin-keys` merges a Topic that holds a pinned key the same way and, in its last unit, makes one attempt to open an overview run for the kept Topic. Accept of a Topic merge does the same rewrite in units of 500 Items, keeps the Topic page's address working (the merged-away key is answered from its Topic Pin, so the old address opens the kept Topic), and moves the Log lines with the Items. It moves no `built_from`, so the kept Topic counts the moved Items as uncovered, and the last unit makes one attempt to open an overview run for it (`docs/proposals.md`, Accept). |

**The read.** `GET /api/topics/{key}?cursor=` answers `{ topic: { key, name, itemCount }, overview, items, next }` to the owner's session and to an agent token. `items` holds at most 50 Items (`ITEMS_PAGE_SIZE`), newest saved first, with the cursor of `GET /api/items`; each has its title, Source, Summary, saved date, Read state and `inOverview` (the Item and its current Digest are in `built_from`). An Item with no Digest is not listed. `disagreements` is the Known disagreements section: the `items-disagree` Pins whose two Items both sit under this Topic now and still carry the Digest tokens in the Pin (`currentDisagreementPin` in `src/core/disagreement-pins.ts` and `readDisagreements` in `src/core/known-disagreements.ts`), the last accepted first (`created_at`, then `id`, because Accept replaces a stale Pin in place and keeps its id), at most 20 (`DISAGREEMENTS_SHOWN`, chosen), each `{ id, reason, items: [{ id, title }, { id, title }] }` with the titles read live from the two Digests. A Pin whose Item got a new Digest or left the Topic is not shown and not deleted, and it shows again when both Items carry the Pin's Digests again. Every page of the cursor carries the list. `overview` is `{ state, text, cited, builtFrom, provider, failure }`: `state` is `pending` while a `topic_overview` job for the Topic is open, `failed` when the failure marker is set and `idle` otherwise; `cited` holds the id and Digest title of each Item the text names as `[id]`; `provider` is whether a Provider is saved. A key that no Topic has and no `topic-merge` Pin holds answers 404, a key held only by a Pin opens the Topic the Pin points to, and an empty key answers 400.

**Try again.** `POST /api/topics/{key}/overview` clears the failure marker and opens a `topic_overview` job owned by the Topic's newest Item with a Digest. It answers 202 with the overview, 404 for an unknown Topic, and 409 when no Provider is saved or the Topic has no Item with a Digest. A job already open for that Item is not duplicated (the open-job index), so a second press adds nothing. Try again and Accept of an overview-gap Proposal share one start (`startOverview`, `src/core/overview-start.ts`): one guarded batch (`docs/architecture/database-and-search.md`, Guarded batches) whose guard holds while a Provider is saved, the Topic has an Item with a Digest, and no `topic_overview` job that is not `done` is owned by any Item of the Topic. The owner of the new job is chosen inside that batch as one SQL subquery (`newestOwner`: the Topic's Item with a Digest, newest `saved_at`, then `id`) that the guard and the job insert both use, so they name one Item in one transaction; an owner picked before the batch could have left the Topic, or the Topic's last uncovered Item could have gone, in between. After the guard the batch inserts the job, then clears the failure marker. Accept adds a guard condition (its row is `open` and the Topic still has an Item the overview was not built from) and one write right after the job insert, the delete of its row with `WHERE changes() > 0`, so the row and the marker change only when a job was inserted. When the guard fails, `startOverview` reads the Provider, the owner and the open run once and returns one answer: `no-provider`, `no-items`, `open`, or `stale` when all three read as fine again (the state changed between the guard and that read) and when the batch itself failed a guard check. Try again maps `no-provider` and `no-items` to 409, retries on `stale`, and on `open` answers 202 without a second job after it clears the failure marker, as it did before this start was shared. Accept reads its own row after a refusal and answers 404 or 409 `not-open` when the row is gone or decided, 409 `no-provider`, and 409 `not-current` for `open`, `no-items` and a `stale` Topic whose gap closed; it retries on `stale` while the gap holds. Neither takes a Topic lease, because the job takes it when it runs.

**The page.** `/topics/<key>` is the `topic` screen (`web/src/screens.ts`), drawn by `web/src/TopicPage.tsx`. It is reached from the Topic in the Reader (`TopicLink`) and from the Topic choice in the filters pane (`TopicPageLink`), which shows only while a Topic is chosen. `PagesScope` (`web/src/pages-scope.ts`) gives those two links the router's `topic` function. While the overview is `pending`, the page reads the same address every 3 seconds (`usePolling` in `web/src/use-polling.ts`, which the Proposals page also uses) and stops when it is not. A poll reads the first page and then the pages after it until it passes the last Item the page had loaded (`readThrough` in `web/src/use-topic-page.ts`), and replaces the rows, the count, the flags and the cursor, so an Item deleted or moved meanwhile leaves, a new Item appears, and rows keyed by Item id keep the owner's place. A poll that lands after Load more or a reload began is dropped, and the next poll reads again. On a phone, a citation takes its own row at least `--target` (44px) tall, and the Topic link in the Reader is at least `--target` wide, because both sit outside rendered post text, where `DESIGN.md` allows no smaller target. A failed overview shows its note and Try again above the Items, and the Items still list. With no Provider the page shows a note and the Items only. `KnownDisagreements` (`web/src/KnownDisagreements.tsx`) draws the Known disagreements section in the overview's box between the overview and the Items, only when the read holds at least one entry. Each entry is the agent's reason and a list of the two Items as links to the Reader, which grow to `--target` (44px) under 480px and wrap a long title instead of scrolling sideways.

## The Index

The page that lists every Topic with its Item count and overview line (slice 23). The read is `src/core/topic-index.ts`, its schema is `src/core/topic-index-contract.ts`, the route is `src/http/topic-index-route.ts`, and the rule for the overview line is `overviewLine` in `src/core/topic-overview-contract.ts`, next to `citedIds`. It is a read of `topics` and `topic_pages`. It adds no table, no job and no AI task, so it works with no Provider saved.

**Identity.** A row is a Topic, and its identity is the Topic's catalog key (`topics.key`, `docs/architecture/data-model-outline.md`, Catalog keys), the same key that addresses its Topic page (`topicPath`). `İstanbul` and `istanbul` are one row. The cursor is a key, which is unique, so it needs no second column. The key survives a rename of the Topic's first spelling and a refresh of any Item. A merge of two Topics removes the merged-away key as a Topic; its old address still opens the kept Topic through the Topic Pin, and no other record keeps that key.

**The read.** `GET /api/topics?cursor=` answers `{ topics, total, next }` to the owner's session and to an agent token; the MCP endpoint gets no tool, because the spec fixes three. Each topic holds `key`, `name` (the first spelling), `itemCount` and `overviewLine` (a string or null). `itemCount` counts the Items whose `topic_id` is the Topic, the number the Topic page shows as `itemCount`; a Topic whose Items were all deleted stays in the list with 0, because the lists outlive their last Item (`docs/architecture/data-model-outline.md`, Deleting an Item, What stays). `overviewLine` is the first non-blank line of the stored `topic_pages.overview` with every `[12]`-style mark removed, inside the line as well as at its end, because the Topic page turns a mark into the cited Item's title or drops it and never shows it as raw text; a bracketed phrase that is not an id stays (`[the docs] [12]` gives `[the docs]`). It reads the stored text whatever the failure marker says, so a failed run does not hide an earlier overview. A Topic with no `topic_pages` row or no text has a null line. The Topic page splits the same text into lines with `overviewLines`, so both screens use one rule.

**Order and paging.** Rows come ascending by `topics.key`, so a row does not move when a count changes. SQLite compares the keys byte by byte, which for UTF-8 text is code point order: `éclair` sorts after `zebra`, and no locale rule applies, so the order is not a sort for any one language. A page holds 50 rows (`ITEMS_PAGE_SIZE`) and `next` is the last key on the page, or null on the last page. A `cursor` over `CATALOG_KEY_MAX` characters (`docs/architecture/data-model-outline.md`, Catalog keys, Length; the length `GET /api/topics/{key}` allows) answers 400, so the `next` of any page is a cursor the next request accepts. The read is one batch of two statements, the page (with the count as a subquery per returned row) and `count(*)` of `topics`, and the session lookup before it. Measured on 2026-11-11 with 1,000 seeded Topics of one Item each: a page took 4.1 to 5.7 ms on the container target (5 requests each for the first page, the second page and the page after the key `seeded topic 0900`) and 40.0 to 64.9 ms on `wrangler dev --local`. A page issued 3 SQL statements on the container (1 session lookup and 1 batch of 2) and 2 D1 round trips on the Worker (the session lookup and one `batch` of 2 statements), the same for each of the three pages.

**The page.** `/topics` and `/topics/` are the `index` screen (`web/src/screens.ts`), drawn by `web/src/IndexPage.tsx`. It is reached from the Index link in the settings panel, beside Highlights (`PageLinks` in `web/src/PageLinks.tsx`), or by its address; Back returns to the library. The link sits in the panel and not in the masthead row, for the reason given in `docs/architecture/data-model-outline.md`, The Highlights page. A row (`web/src/IndexRow.tsx`) is a link to the Topic page whose whole row is the target; it opens the page in place through the router's `topic` function and leaves modified clicks to the browser. The Index, the Log and Proposals share one page, `ListPage` (`web/src/ListPage.tsx`): the bar, the skeleton, the failed notice, the empty state, the list head, the list and Load more, driven by each page's `Listing` (its texts, head, empty line and rows). `usePagedRead` (`web/src/use-paged-read.ts`) holds loading, failed, and ready with the rows read so far for all three, through `useIndexPage`, `useLogPage` and `useProposalsPage`; Load more keeps the rows when it fails, and a read that returns after a newer one began is dropped. The Topic page and the Index share one row list: its classes carry the `rl-` prefix and live in `web/src/row-list.css`, and `LoadMore` (`web/src/LoadMore.tsx`) is their Load more button. `web/src/topic-page.css` keeps the `tp-` classes of the overview only, and `web/src/index-page.css` adds the Index row's name-and-count grid.

## Related Items

The agent's links from one Item to up to 5 others (slice 24). The code is `src/core/related-job.ts` (the `related_pick` job), `related-candidates.ts` (the ranking query), `related-input.ts` (the prompt), `related-task.ts` (instructions, schema, budgets), `related-write.ts` (the guarded batches), `related-read.ts` (the read for `GET /api/items/{id}` and the MCP `read` tool), `related-contract.ts` (the response schema) and `related-tables.ts` (the table). A pick belongs to the Item that made it. The other Item's Reader does not list it, because showing both directions would need a ranking and a reason policy to keep the cap of 5.

`related_items` has the primary key (`item_id`, `related_id`), so a pair is unique. Checks refuse a pair of one Item with itself, a `position` outside 0 to 4 and an empty `reason`. A unique index on (`item_id`, `position`) keeps the order total, and an index on `related_id` keeps the delete of an Item from scanning every pair. Both Item ids cascade on delete. A set is replaced as a whole, a delete leaves a gap in `position`, and a read orders by `position` and renumbers nothing.

| Record or reference | Identity | Survives | Breaks |
|---|---|---|---|
| A `related_items` row | the pair of two generated Item ids that are never reused; it has no id of its own, because nothing points at a pair and the set of one Item is replaced as a whole | a refresh or re-Paste of either Item, a Topic or Tag change, a rename, an export and restore that keeps Item ids (the export carries the pairs with the Items they name; not built) | deleting either Item |
| The set of one source Item | replaced in one batch by the next stored pick | the other Item's new Digest (its reason may be out of date until this Item's next pick) | this Item's next pick |
| `position` | 0 to 4 within one source Item | a read | a replacement; a delete leaves a gap |
| The `related_pick` job | the job row's generated id, never reused; its open-work lifetime ends when it closes, and the row stays | a restart, a lost queue message, a stale requeue | its close |
| The pick's AI task | its generated id, owned by the source Item (`ai_tasks.item_id`, cascade), with `input_revision` set to the source Item's Digest task id | a restart | the source Item's deletion. The export leaves it out, because no Digest names it |
| Digest versions | the Digest task ids of the source and of the sent candidates | held for one attempt and never stored; the source's is recorded as `input_revision` | the Item's next Digest |

**When it starts.** `publishing` in `src/core/digest-publish.ts`, the batch that publishes a Digest from a model result or a caller-sent Digest, holds `openingPick` (`src/core/digest-source.ts`) as the statement right after the Digest upsert, before the Kept comment and search part writes, the AI task completion and the Item's pending Digest and failure writes. It opens one `related_pick` job for the Item, and only while a Provider is saved (`providerSet`). `linkOlderDigests` publishes no Digest, so linking an older Digest opens none, and there is no backfill: it would cost one model call for each stored Digest and needs the owner's approval of the spend. The job is not an Item job kind, so the Item stays `ready` while it runs, and it waits for the Item's own `digest` job (`blockedBy`). The unique open-job index keeps one open pick for each Item. A Digest that lands while a pick runs opens no second job, and the running pick's writes are guarded on the Digest versions it read, so it is discarded and runs again. `0037_related-items.sql` replaces both `jobs_values` triggers to accept `related_pick`.

**The candidates.** `candidateIds` ranks the other Items that have a stored Digest by FTS5 `bm25()` over the `digest-title`, `summary` and `tags` parts, a lower score being a better match. The terms are the words of the source Digest's clean title and then of its Tags, each through `searchTerms`, with repeats dropped and the first 12 kept (a chosen limit, unsupported). Each term is a quoted exact token, and the terms are joined with ` OR `, because an AND would match almost nothing. The query takes each Item's lowest score and orders by score and then by Item id, and the first 20 Items are the candidates (a chosen limit, unsupported). Post text, comments, the fetched title, Highlights and Notes neither match nor reach the Provider. With no term or no candidate the job stores an empty set in its guarded batch and makes no AI task.

The obvious `min(bm25(...))` over a `GROUP BY` fails on both targets with `unable to use function bm25 in the requested context` (`node:sqlite` on Node 26.12.1 with SQLite 3.53.3, and local D1 under wrangler 4.158.0, 2026-11-11), because `bm25()` works only where the FTS5 table is the row source. The query scores the rows in a `with scored as materialized (...)` subquery, and the outer query takes the minimum for each Item. The same query, compiled by Drizzle and run with literals on both targets over identical seeded rows with ties, an Item that matches in several parts, an Item with no Digest and a non-matching Item, gave the same order with scores equal to the last digit.

**The input and the result.** The input is one JSON text: the source Item's id, title, Topic, Tags and Summary, then the candidates in rank order, each with its id, title, Topic and Summary. The cap counts the whole serialized text in UTF-8 bytes (`utf8Length`): 14,000, this task's own budget, which equals the Topic overview's only by choice. A candidate is added whole in rank order, and one that does not fit is skipped and the next is tried. When candidates exist and none fits, or the source Item alone is over the cap, the job makes no AI task, writes one `related-input-refused` log line with the Item id and the counts, closes, and leaves the earlier picks. A stored Digest that does not parse closes the job the same way with `related-digest-unreadable` when it is the source's, and is skipped with `related-candidate-unreadable` when it is a candidate's. The result is `{ picks }`, at most 5, each `{ item, reason }`, where `item` is a candidate that was sent, once each, and `reason` is one line of 1 to 160 characters under the same punctuation rule as an overview line (`plainText` in `src/core/plain-text.ts`). Zero picks is valid.

**Storing.** One batch holds the version guard, the delete of the Item's old set, the insert of the new set, the completion of the AI task and the closing of the job. The guard holds only while the source Item's Digest is the one the attempt read, every candidate that was sent still has the Digest it had, and the AI task is still running. The empty-set path and the refusal path are guarded the same way. When the guard fails, nothing is written, the AI task fails as `stale` and the job returns to the runner's stale backoff without spending an attempt. A retriable refusal that is not stale throws and retries after 30 seconds and 2 minutes. A terminal refusal or the last retry closes the job and leaves the stored set as it was. The Item is not marked and the Reader shows nothing, so "not run", "failed" and "picked none" look the same there; a later Digest of the Item runs the pick again, and there is no Try again. A candidate that is refreshed after a pick is not re-picked, so a reason may be out of date until the source Item's next pick.

**The read.** `GET /api/items/{id}` and the MCP `read` tool answer `related`: up to 5 entries in position order, each `{ id, title, source, reason }`, where the title is the other Item's Digest title or, with none, its fetched title (null when neither exists). `detailReads` in `src/core/detail-reads.ts` reads them in the same batch as the rest of the detail. The Reader reads the Item when it opens, so a pick that lands while it is open shows on the next open.

**The Reader.** `web/src/Related.tsx` draws the section with the `rd-h` heading, after the post text and the Kept comments and before the Highlights list and the Note, and draws nothing, heading included, when the list is empty. Each entry shows the other Item's Source, its title (or "Untitled") and the reason, and opens that Item at `/items/<id>` through the router (`pages.item`). Under 480 px each entry is at least 44 px tall.

**Cost.** Each claimed run makes at most one model call, with SDK retries off and the handler's deadline `AI_DEADLINE_MS`. An Item with no candidate or no term makes none. Error retries (up to 3 attempts) and stale reruns add calls. An Import of 100 links can add up to 100 pick calls plus retries, and the CLI Providers run 2 tasks at a time.

## The Log

The Log lists the committed changes the agent made to the library (slice 23, second part). It is the `log_entries` table, one row for each change, read by `src/core/log-page.ts`, with its schema in `src/core/log-contract.ts`, its tables in `src/core/log-tables.ts`, its writers in `src/core/log-writes.ts` and its route in `src/http/log-route.ts`.

**Recording.** An entry is a statement in the guarded batch that commits the change it records, so a stale result, a lost claim, a failed guard or a rolled-back write appends nothing, and a committed change never lacks its entry. Logging adds no model call, no job and no retry. A statement that writes an entry stays in the Drizzle `batch`, and a list it needs is bound as one JSON value, because D1 limits a statement to 100 bound parameters.

| Action | Written by | When | Holds |
|---|---|---|---|
| `ingest` | `loggedDigest`, in `publishedLinks` (`src/core/catalog.ts`), which `publishing` in `src/core/digest-publish.ts` runs before the `digests` upsert | the Item has no `digests` row yet | the Item, its Digest title, the Topic, the Tag names |
| `digest` | the same statement | the Item already has a `digests` row (Try again, a refresh, a new caller-sent Digest) | the same |
| `topic` | `loggedTopic`, in `linkingDigest` (`src/core/catalog.ts`) right after the Topic's `bumpVersion`, which a published Digest and the older-Digest linking both run | the Topic insert inserted a row (`changes() > 0`) | the Topic |
| `overview` | `loggedOverview`, in `storedPage` (`src/core/topic-page-store.ts`), which `revisedOutcome` and `keptOutcome` in `src/core/topic-overview-write.ts` both batch | every stored revision, changed, unchanged or prune-only | the Topic, `added` (the Items whose current Digest the revision was built from) and `removed` (the removed Item ids it dropped) |
| `related` | `loggedRelated`, in `pickedOutcome` (`src/core/related-write.ts`) after the pair rows and before the AI task closes | the stored set has at least one pick | the source Item, its Digest title, the number of picks |
| `merge` | `loggedMerge`, in the last unit of an accepted Tag merge (`src/core/proposal-accept.ts`) | the unit left no `item_tags` row for the merged-away Tag | the two Tag names as written and the number of Items that carried the Tag; no Tag and no Item reference |
| `merge-topic` | `loggedMerge` with the action `merge-topic`, in the last unit of an accepted Topic merge (`src/core/topic-merge-unit.ts`) | no Item and no Log entry names the merged-away Topic any more | the two Topic names as written and the number of Items that carried the Topic; no Topic and no Item reference |

- **`changes()` placement.** `bumpVersion` reads `changes()` right after the Topic insert, and SQLite defines `changes()` as the count of the most recent completed insert, update or delete. The `topic` entry therefore sits after `bumpVersion` and before the Tag insert, conditioned on `changes() > 0`, so no statement comes between a catalog insert and the one that reads its count. After `bumpVersion` the count is 1 when the Topic row was inserted and 0 when `ON CONFLICT DO NOTHING` skipped it (`node:sqlite`, Node 26, and local D1, 2026-11-11). A second publication that reuses an existing Topic writes no `topic` entry.
- **`ingest` or `digest`.** The statement reads whether a `digests` row exists, so it runs before the upsert. Entries of one batch keep their insertion order, so a first Digest in a new Topic shows `ingest` above `topic`, because the newest id comes first.
- **No failure entries.** A failed Digest, overview or pick, the Verify task and an Item's deletion are not entries. An empty set of picks records nothing, and neither does a set that clears an older one.
- **The action list.** `LOG_ACTIONS` in `src/core/kinds.ts` is the list, and `log_entries_action_insert` and `log_entries_action_update` (`BEFORE INSERT` and `BEFORE UPDATE OF action` triggers, as `jobs_values` does for jobs) abort a row with another action. A `CHECK` would need the table rebuilt for each action a later slice adds. `test/consistency-triggers.test.ts` walks the list through the real database.
- **No backfill.** The records that exist before the migration cannot give a faithful history: `digests` keeps only the latest Digest of an Item, so nothing tells an ingest from a regeneration; `ai_tasks` has no creation time; `topic_pages` keeps only the latest overview; and `topics` and `tags` have no creation time. The migration inserts the start time into `log_start` from the database clock, and an upgraded library starts with an empty Log. An export carries `log_entries` and `log_start`; the export is not built.
- **The read.** `GET /api/log?cursor=` answers `{ startedAt, entries, next }` to the owner's session and to an agent token, and the MCP endpoint gets no tool. Rows come newest first by `id`, so a clock that steps back cannot reorder them, 50 to a page (`ITEMS_PAGE_SIZE`). `cursor` is the last `id` of the page before, a string of 1 to 16 digits that is a safe integer, and anything else answers 400. The route does not check that an entry with that `id` exists, so a cursor stays valid after its entry is deleted with an Item. `next` is the cursor of the following page or null. The page and the start time are read in one `batch`. Each entry is one of seven shapes, tagged by `action` (`LogEntrySchema`), and the read parses every row with it. The read selects only rows whose `action` is in this release's `LOG_ACTIONS` (`readLog` in `src/core/log-page.ts`), with the paging by `id` unchanged: the cursor names a position, so a skipped row moves no boundary. When a later release adds an action and is rolled back to this one, `GET /api/log` still answers instead of failing on a row it cannot parse. A release before the one that added this filter answered 500 for such a row, because `entryOf` parsed `undefined`. The triggers refuse an unknown action in each release, so a row with a newer action reaches this reader only after such a rollback.
- **The page.** `/log` is the `log` screen (`web/src/screens.ts`), drawn by `web/src/LogPage.tsx` through `ListPage`, with `LogRow.tsx` for a line, `use-log-page.ts` for the read and `log-page.css` for the line's own styles (the list, rows, head and states are the Index's `rl-` classes), reached from a link in the settings panel (`PageLinks`) beside the Index. A line reads `[date] action | title | topic: X | tags: a, b`. The date is the browser's local `YYYY-MM-DD` in a `<time>` element whose `datetime` and `title` hold the full local time (`web/src/log-date.ts`). The title opens the Item in the Reader and the Topic name opens its Topic page, through the router. The states are loading, empty (the text names the start date), failed with Try again, and Load more that keeps the rows when a later page fails. The path has no `.`, so neither target needs a document-routing change.

**Identity.**

| Record or reference | Identity | Survives | Breaks |
|---|---|---|---|
| A `log_entries` row | a generated id, never reused (`AUTOINCREMENT`) | a Paste (it writes none; a Digest it leads to writes its own), a refresh, a rename, a Tag or Topic merge (the snapshot stays; the `topic_id` moves to the kept Topic), an export and restore that keep the ids and the Item and Topic ids the rows name (not built) | deleting the Item it names |
| `item_id` of an entry | the Item's id, `ON DELETE cascade` | everything an Item id survives | the Item's deletion, which removes the entry, because it holds that Item's title and Tags |
| `topic_id` of an entry | the Topic row's id, no delete action | a refresh, an export and restore | a Topic merge: the `topic-keys` step and Accept of a Topic merge move it to the kept Topic (`docs/architecture/data-model-outline.md`, Catalog keys) |
| The snapshot text | stored as written: the Digest title, the Topic's first spelling and the Tag names in the catalog's spelling at the time of the batch | everything | nothing |
| A `merge` entry | a generated id and the two Tag names as written when the merge finished; it holds no Tag and no Item reference | everything, an Item delete and a later merge of either Tag included | nothing |
| A `merge-topic` entry | a generated id and the two Topic names as written when the merge finished; it holds no Topic and no Item reference | everything, an Item delete and a later merge of either Topic included | nothing |
| The start row | `id = 1`, set once by the migration | a restart, a deploy | nothing |

A later rename, merge or regeneration does not change an old line. The line shows the snapshot, and the link goes through the reference.
