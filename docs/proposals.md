# Proposals

The agent's weekly suggestions to merge two Tags or two Topics, the page that lists them, Reject, Accept of a Tag merge and the Pin it leaves. Accept of a Topic merge and the other Proposal kinds are not built. `docs/architecture.md` holds the run, its input and its freshness rule under Jobs, leases and the schedule and AI tasks and Providers; this file holds the rest.

## Code map

- `src/core/proposal-week.ts`: the two weekly claims (`proposals` and `topic_proposals`) and the job each opens.
- `src/core/proposal-candidates.ts`: the plain check, for Tags and for Topics.
- `src/core/proposal-input.ts`: the reads of both runs and the input fill rule.
- `src/core/proposal-task.ts`: instructions of both tasks, the result schema and budgets.
- `src/core/proposal-job.ts`: the run (`proposalsHandler` for Tags, `topicProposalsHandler` for Topics) and its guarded batches.
- `src/core/proposal-tables.ts`: the table, re-exported by `schema.ts`.
- `src/core/proposal-relink.ts`: what a Tag or Topic key merge does to the rows, and the collision priority.
- `src/core/proposal-page.ts`: the read and Reject for `src/http/proposal-routes.ts`.
- `src/core/proposal-accept.ts`: Accept, the merge units and the sweep stage that continues them.
- `src/core/tag-rewrite.ts`: the bounded rewrite of one Tag into another, shared by Accept and `pin-keys`.
- `src/core/pin-tables.ts`, `src/core/pins.ts`: the `pins` table, the Pin read that Digest publication and the older-Digest linking share, and the Pin repoint.
- `src/core/pin-key-step.ts`: the `pin-keys` data step.
- `src/core/older-digests.ts`: the older-Digest linking, which reads the Pins.
- `src/core/proposal-contract.ts`: the schemas the core, the routes and the page share.

## The value guard

`proposals.kind` and `proposals.state` have no `CHECK`. `proposals_values_insert` and `proposals_values_update` refuse a kind or state outside `PROPOSAL_KINDS` and `PROPOSAL_STATES`, as `jobs_values` does (`docs/architecture.md`, Database and search, Consistency triggers), so a later kind is a replaced trigger pair and no table rebuild. `proposals_subject_insert` and `proposals_subject_update` hold which columns a kind uses: `tag-merge` needs both Tag ids and no Topic id, `topic-merge` the reverse. They check only the kinds they know, so an unknown kind is refused by the values pair alone, and the subject rule is no `CHECK` that names kinds, so a kind with other subjects (slice 27) is a replaced trigger pair too. The columns themselves are nullable because one table holds both kinds; `migrations/0041_topic-merge-proposals.sql` rebuilt the table for that (`docs/architecture.md`, Database and search, Migrations). `pins.kind` has the same pair, `pins_values_insert` and `pins_values_update`, from `PIN_KINDS`. `test/consistency-triggers.test.ts` stores and updates each listed value and refuses an unlisted one.

## The read

`GET /api/proposals?cursor=` answers `{ proposals, checkedAt, provider, next }` to the owner's session and to an agent token, and the MCP endpoint gets no tool. It lists `open` and `accepting` rows of both kinds, 50 to a page, newest first by `id`, with the Log's cursor rule (the last `id`, a decimal integer of 1 to 16 digits, 400 otherwise). Each row holds `id`, `kind` (`tag-merge` or `topic-merge`), `state` (`open` or `accepting`), `reason` and `from` and `into`, each `{ id, name, items }` with `items` counted when the call is made: the `item_tags` rows of a Tag, or the Items under a Topic (`items.topic_id`). `pageQuery` joins each kind's two sides on its own columns (`from_tag_id` and `into_tag_id`, or the Topic pair) with left joins and `coalesce`, and names each repeated column. `checkedAt` is the larger `last_run_at` of the two weekly claims, the Tag claim and the Topic claim, in milliseconds, or null when neither exists, and `provider` is whether a Provider is saved.

## Reject

`POST /api/proposals/{id}/reject` is owner-only (Access). It runs one `UPDATE ... WHERE state = 'open' RETURNING` that moves the row to `rejected`, answers 200 `{ state: "rejected" }`, and reads the row again only when nothing changed: 404 for an unknown id and 409 `not-open` for a row in another state. A rejected row never reaches a later run's input, because the plain check skips every pair that has a row, in either order. There is no undo and no flip of direction. It treats a Topic row like a Tag row.

## Accept

`POST /api/proposals/{id}/accept` is owner-only (Access). It answers 409 `not-supported` for a `topic-merge` row in any state (a Topic merge can be rejected and cannot be accepted until a later slice), 404 for an unknown id, 409 `not-open` for a row in any state but `open`, 409 `merge-busy` while another row is `accepting`, 200 `{ state: "done" }` when the merge finished inside the request and 202 `{ state: "accepting" }` when units remain. The MCP endpoint has no tool for it. There is no confirmation and no undo, and no screen removes a Pin. One merge runs at a time instead of leases, so no two merges touch one Tag.

Call the Tag that goes `from` and the Tag that stays `into`. The merge runs in units (`runUnit` in `src/core/proposal-accept.ts`), and each unit is one guarded batch (`guardedBatch`, Database and search in `docs/architecture.md`):

1. The guard. The first unit holds while the row is `open` and no row is `accepting`. A later unit holds while the row is `accepting` at the unit revision it read, so two runners never move the same Items twice or count them twice, even after the cursor goes back to 0. Every unit also holds the row's `from_tag_id` and `into_tag_id` equal to the ids it read, and each of the two Tags' stored `key` equal to the key it read, because a `tag-keys` merge can repoint the ids and its rename can change a key. A unit that loses the guard writes nothing, and the next run reads the row again.
2. The state change to `accepting`, the count, the Pin insert (`ON CONFLICT DO NOTHING`, so every unit can carry it; its `from_key` is `catalogKey` of `from`'s name, which is what `pin-keys` computes, so a `from` Tag whose stored key a key step has not yet recomputed still gets the final key) and the repoint of every Pin that targets `from` to `into`. The Pin commits with the first Items, so a Digest that publishes during the merge already lands on `into`.
3. For the next 100 Items that link to `from` (`REWRITE_UNIT_ITEMS`), by ascending Item id after the cursor: the stored Digest of each is rewritten so every Tag name whose `catalogKey` equals `from`'s key becomes `into`'s name, repeats dropped by key with the first place kept, guarded per Digest on `digests.task_id` and the Digest's `tags` still being the ones read (a rewrite keeps the task id, so the Tags are the part of the Digest that a second rewrite changes); the link moves to `into` or is deleted when the Item already has `into` (`tagMoves` in `src/core/catalog-key-links.ts`, which `tag-keys` also uses and which rebuilds the `tags` search part). The links move before the Digests are rewritten, because the link guard reads the Digests as they were read. An Item whose Digest changed between the read and the batch keeps its link and its Digest for a later unit, so a stored Digest never names `from` beside a link to `into`. A stored Digest that does not parse keeps its text, its link still moves, and one `merge-digest-unreadable` line names the Item id; it never stops the merge, because one merge at a time blocks every other accept.
4. The count of Items (`moved`), computed before the link writes from the `item_tags` rows of `from` among the unit's Items whose Digest still matched the read, so an Item deleted or republished between the read and the batch is not counted. Then the cursor and the unit revision plus one.
5. Only when no `item_tags` row for `from` remains: the `merge` Log entry, one bump of `catalog_version` (so a Digest that read the old Tag list asks again), the delete of the `tag-keys` rows that staged `from` (`data_step_renames`, so a staged survivor never points at a deleted Tag) and the delete of the Tag `from`. The cascade deletes the row and any other Proposal that names `from`. If a link is left, the cursor goes back to 0 and the units continue.

A Tag on 100 Items or fewer therefore merges in one batch that holds the links, the `tags` search part, the stored Digest names, the Pin and the Log entry. `moved` and the Log's count are the Items that carried `from`, including those that already had `into`.

**Who runs the units.** The accept request runs up to 50 units (`UNITS_PER_ACCEPT`). The `merges` sweep stage (`continueMerges`, after `proposals` in `src/core/sweep.ts`) continues every `accepting` row with the same bound on each tick, so a closed tab, a crash or an ended Worker invocation finishes by itself. The route and the stage call one function (`continueMerge`). A unit that throws a database error ends the call, the stage is logged as `sweep-stage-failed`, and the next tick starts again from the stored row.

**A unit that keeps failing.** A unit that fails on every run leaves the row `accepting`. The page keeps showing "Applying…" with Reject disabled, `merge-busy` refuses every other Accept, and only the server log (`sweep-stage-failed`) shows it. The row has no failure marker, and this risk is accepted: a failed unit writes nothing, so a repair of its cause lets the next tick continue.

**Key steps during a merge.** `tick` runs `migrateData` beside the sweep, so a `tag-keys` or `pin-keys` unit can run between two units, and neither waits for the other. A key merge repoints the `accepting` row's Tag ids (`proposalRelinks`), the next unit reads the new ids and continues onto the survivor. When two rows reach one pair, `accepting` outranks `rejected`, which outranks `open` and `declined`, and the smaller id decides inside a class, so a merge that has moved Items never loses its row to an older Reject. The `pin-keys` step skips the `from` Tag of an `accepting` row, because the Accept's Pin already makes that Tag look like one that holds a Pin's key and the Accept finishes it with its own Log entry. A key merge that makes `from` and `into` one Tag deletes the row: the key step already joined the two Tags, the first unit's Pin already points at the survivor, and no `merge` entry is written. A link that a unit moves onto a Tag that a key step is about to delete is caught by that step's restage check (Catalog keys). An accepted merge changes no Topic, takes no Topic lease and queues no overview run. A stored Digest's own AI task (`ai_tasks.result`) keeps the names it returned, as provenance.

**Bounds.** A unit runs 3 reads and 1 batch (`readRow`, the two reads of `readRewrite` and the batch), which D1 counts as 4 queries because a `db.batch()` counts as one query ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), read 2026-11-12). An accept request runs at most 50 units, so about 200 queries, and `migrateData` stops after 100 units at about 4 queries each, so about 400. Both fit under the 1,000 queries a Workers Paid invocation may make; the queries of the other sweep stages are not counted here. The batch holds a fixed set of statements and one more for each stored Digest it rewrites, so its size follows the unit size. The same page sets no limit on statements per batch, limits each statement to 100,000 bytes and a bound string to 2,000,000 bytes, and gives a batch call 30 seconds. The largest bound string is the JSON of a unit's read state: for each of 100 Items an id, a task id and the Digest's Tags, which are at most 3 names of at most 240 characters (`SHORT_TEXT_MAX`), so at most 3 × 240 × 7 × 100 = 504,000 bytes even when every character is a control character that both JSON layers escape. The unit size of 100 and the unit bound of 50 are chosen numbers, not limits.

## Pins

A Pin records an accepted Tag merge: the merged-away Tag's `from_key` and `from_name` as they were and the target Tag's id (`into_tag_id`, no delete action). One Pin exists for a name (a unique index on `kind` and `from_key`). Every path that turns a Digest's names into links reads the Pins for the Digest's Tag keys: `publishing` in `src/core/digest-publish.ts` (a model result, a caller-sent Digest and the Digest `items.pending_digest` holds alike) and `linkOlderDigest` in `src/core/older-digests.ts`. A name whose key is pinned becomes the target Tag's name before `catalogEntries` runs, so the Item links to the target, the stored Digest names the target and no `tags` row with the pinned key is inserted. The AI task's own result keeps the names the model returned.

Both paths guard their batch on the exact resolution they used: for each of the Digest's Tag keys, the Pin they found and its target, or that no Pin existed (`pinnedDigest` in `src/core/pins.ts`). The guard is separate from the catalog guard, so it holds on every path and at every stale count: the model path drops its catalog guard after `MAX_STALE_REQUEUES` and the caller path has none, and the Pin guard inherits neither gap. A publication that loses it is stale and requeues under the existing stale rules, and the next attempt reads the Pins again. `linkOlderDigest` that loses it writes nothing, and the Item stays unlinked for its next pass. It also writes the rewritten Digest, because it links Items whose stored Digest the accept's units did not reach.

**Catalog key steps.** `TAG_KIND.relink` repoints every Pin that targets the losing Tag to the survivor in the unit that deletes it. The `pin-keys` step runs after `tag-keys` with `CATALOG_KEY_VERSION` as its version. Its phases are named in its cursor: `keys` recomputes every Pin's `from_key` from `from_name` in one unit (a Pin holds a key of at most `CATALOG_KEY_MAX`, 4,320 code points, and a name of at most 240; the weekly check adds at most 20 rows, so the read of every Pin stays far under D1's result limit; the deletes, the two key updates and the finish guard each take 100 Pins at a time (`PINS_PER_STATEMENT`), so one bound string stays under 100 × 4,320 × 3 bytes = 1,296,000 bytes, below D1's 2,000,000-byte limit; the first update gives each Pin a temporary key that is longer than any key `catalogKey` can return, so no Pin holds it), keeping the smaller id when two Pins reach one key and deleting the other first, because the unique index would refuse it; `merge:<tag>:<item>` merges a Tag whose key equals a Pin's key into the Pin's target with the same bounded rewrite as Accept (`readRewrite`), and leaves the Pin's own target alone; `finish` records the version only in a batch whose guard checks that every Pin key still equals its recomputed key and that no Tag other than a Pin's target holds a Pin's key. When the guard fails, the next run stages again. The merge unit also repoints the Pins and the Proposals of the Tag it deletes.

**Rollback and roll forward.** The release before this one ignores Pins, so a Digest it publishes can create the merged-away Tag again. Upgrading again does not repair that by itself: `pin-keys` already recorded its version, and the older-Digest linking reads only Items with no Topic. Delete the step's row (`DELETE FROM data_steps WHERE name = 'pin-keys'`, through `wrangler d1 execute` or the container's database). The next start, tick or Paste runs the step again and merges every Tag that holds a Pin's key into the Pin's target, with its links and stored Digests. The same procedure covers Digests an older Worker still in flight writes after a deploy. Rollback is one release back, to the release that has the Proposals tables and the known-action filter in the Log read. `docs/architecture.md` (CI, releases and rollback) holds the caveat beside the catalog-key one.

## The weekly Topic check

The Topic check runs beside the Tag check and shares its code (`proposal-week.ts`, `proposal-input.ts`, `proposal-task.ts`, `proposal-job.ts`). The `topic-proposals` sweep stage, after `proposals`, claims the `scheduled_runs` row `topic_proposals` on the same rule and opens one `topic_proposals` job in its own batch, owned by the same newest Item with a Digest. The two claims are independent: a failing stage or job in one does not skip the other, and the Tag run's batch does not change. `docs/architecture.md` holds the claim, the plain check, the input, the task and its caps under Jobs, leases and the schedule and AI tasks and Providers. A Topic row names no Item, and a Topic with no Item is not sent.

**Topic key step.** `TOPIC_KIND.relink` repoints every row that names the losing Topic to the survivor before the Topic is deleted, by the rule `proposalRelinks` applies to Tags: a row that would pair the survivor with itself is deleted, one of two rows that reach one pair is kept by the priority above, and the rest are repointed. Without this the cascade would delete a Reject and the pair would be proposed again.

## The Log entry

A `merge` entry (`loggedMerge` in `src/core/log-writes.ts`) holds the two Tag names as written when the merge finishes (`merged_from`, `merged_into`) and the Items that carried the Tag (`moved`). It names no Tag and no Item, so it blocks no delete and survives an Item delete. A line reads `[2026-11-04] merge | tag: <from> into <into> | <n> Items`. A failed unit writes nothing, and the Log has no failure entries.

## The page

`/proposals` is the `proposals` screen (`web/src/screens.ts`), reached from a link in the settings panel beside the Log (`PageLinks`), drawn by `ProposalsPage` through `ListPage` with `ProposalRow` for a row and `proposals-page.css` for the row's own styles (the list, rows, head and states are the Index's `rl-` classes).

- **Row.** A row says the effect in one sentence ("Merge X into Y", "Merge topic X into Y" for a Topic), shows each side's live Item count and the agent's reason, and has Accept, the primary action, beside Reject. A Topic row has Reject only, and nothing on it hints at an Accept. There is no confirmation: the sentence states the effect before the press, and the head text says an Accept of a Tag merge cannot be undone in this release and a Reject is final for that pair of Tags or Topics. Each button's accessible name is "Accept merging X into Y" or "Reject merging X into Y" ("Reject merging topic X into Y" for a Topic), and "Try again to accept merging X into Y" (or reject) after a failure, so it begins with the visible label. An `accepting` row shows "Applying…" with both buttons off. A 409 `merge-busy` shows a note on the row and keeps it with its buttons on.
- **States.** Loading, failed with Try again, Load more, and an empty state with three lines read from `provider` and `checkedAt`: no Provider saved, not checked yet, and "The last check started on {date}. No proposals are open now." The date is the most recent claim time of the two weekly runs, which does not say that a check finished, so the last line says no more than the page knows: the list is empty because the check found nothing, is still running or failed, or because the owner rejected every row. The page shows no failure of the weekly run.
- **Shared hook.** `usePagedRead` (`web/src/use-paged-read.ts`) offers `edit` (replace the loaded page, which also drops any read in flight, so a late answer cannot bring a rejected row back) and `reread(through)` (read from the first page until `through` is true for a page, so a row that moved to a later page when newer rows arrived is still read). A reread that a newer edit or read overtakes starts again, at most 3 times, and a reread that fails ends a stuck Load more with its failed state.
- **Reject and Accept flow.** Each row has its own pending state, so a press on one row does not enable another row's button. A rejected or accepted row leaves the list; focus moves to the next row's Reject button, else to the previous row's, else to the heading, and a live region says what happened. When the rejected row was the only one loaded and more pages exist, the page reads again from the first page instead of showing the empty state. When the outcome is unknown (a network failure, or a 404 or 409, which a Reject whose answer was lost also gets when it is sent again), the page reads again through the last loaded row and shows the row as the server has it: a row that is gone leaves with a note, a row that is `accepting` shows "Applying…", and a row that is still open stays with an error and Try again. An Accept that answers 202 marks the row `accepting` at once. While any loaded row is `accepting`, `useAcceptingPoll` (`web/src/use-accepting-poll.ts`) reads every loaded page again each 3 seconds (`usePolling` in `web/src/use-polling.ts`, which the Topic page also uses), so the poll keeps the pages Load more added, and a row that left during the poll is announced and moves focus by the same rule.
- **Routing.** The path has no `.`, so neither target needs a document-routing change. A pull request preview has no Provider and no Cron Trigger, so its weekly run never starts; provisioning inserts demo `open` rows instead, only when the preview's database has the `proposals` table, and a redeploy adds none and keeps a Rejected row Rejected. The demo rows can be accepted, because Accept needs no Provider (`docs/pr-previews.md`).

## The reads of the run

`usedTags` and `usedTopics` read the Tags, or the Topics, that have an Item in pages of 1,000 by id, as a recursion that asks for the page after the last id, because D1 caps one result at 50 MB. `knownPairs` reads every `proposals` row of the run's kind in one query: a row is under 100 bytes and at most 20 rows are added a week, so 50 MB takes about 480 years of weeks (guess).

|---|---|---|---|

| A `merge` Log entry | a generated id, snapshot names, no reference | everything, an Item delete included | nothing |

An Item delete changes no Pin and no row, because a Pin, a `merge` entry and a Proposal name no Item. The two weekly runs open two jobs on the same owner Item, and deleting that Item while they are open loses that week's check for both.

## Probes

The unordered-pair index and the claim's `changes()` placement were run on `node:sqlite` (Node 26.12.1) and on local D1 (`wrangler d1 execute --local`, wrangler 4.158.0) on 2026-11-11, with the migration applied: a row for the pair `(2, 1)` after `(1, 2)` was ignored by `INSERT OR IGNORE` and by `ON CONFLICT DO NOTHING` on both, a pair of one Tag with itself failed `proposals_distinct`, and a claim followed by `INSERT ... SELECT ... WHERE changes() > 0` opened one job, a second claim in the same week opened none, and a claim of a row 7 days old opened one, with identical rows on both.

Accept ran on the same seed on both (thousands of Items with stored Digests, 30 of them naming `ml`, and two `open` Proposals, one of them `ml` into `machine learning`, which the run accepted): the Tags, the links, the stored Digest names, the Pin, the `merge` Log entry, the remaining Proposal row, `catalog_version` and the `tags` search part came out equal in every dumped table (links, Digests, Pins, the Log, `catalog_version` and the `tags` search part), on `node:sqlite` and on local D1 (`wrangler` 4.158.0, 2026-11-11), which ran each unit's batch without error. The seed and the two runners are not in the repository, so the run cannot be repeated from it.

The rebuilt `proposals` table was run on `node:sqlite` and on local D1 on 2026-11-12 with the same results: a Tag pair `(2, 1)` after `(1, 2)` failed `proposals_pair`, a Topic pair `(2, 1)` after `(1, 2)` failed `proposals_topic_pair`, Topic pairs `(1, 2)` and `(1, 3)` coexisted, a Topic pair of one Topic with itself failed `proposals_topic_distinct`, a row whose columns did not match its kind failed a `proposals_subject_*` trigger, an unknown job kind failed `jobs_values_*`, and after ids 1 to 5 with 5 deleted the next insert took id 6, so the id high-water mark survives the rebuild.
