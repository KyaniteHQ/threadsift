# Proposals

The agent's weekly suggestions and the owner's Reject and Accept of them. A Proposal is one of five kinds: `tag-merge`, `topic-merge`, `highlight-lost`, `overview-gap` and `items-disagree`. The three plain checks (lost Highlights, overview gaps, and the Tag and Topic candidate pairs) call no model, the Tag, Topic and disagreement checks run a model, and a merge leaves a Pin. `docs/architecture/jobs-leases-and-the-schedule.md` and `docs/architecture/ai-tasks-and-providers.md` (The `proposals` task) hold the run, its input and its freshness rule. This file holds the rest.

Start from `src/core/proposal-lifecycle.ts` (the states), `src/core/proposal-decision.ts` (Accept's dispatch and Reject), `src/core/proposal-week.ts` (the weekly stages) and `src/core/weekly-model-run.ts` (the job every weekly model check shares). With Grok Bot as the Provider, the Tag, Topic and disagreement runs run as bot tasks through `weeklyBotKind` (`src/core/weekly-bot.ts`), which keeps each run's `current` guard, so a guard that moved fails the task `stale` and requeues the job.

## The lifecycle

`LIFECYCLE` in `src/core/proposal-lifecycle.ts` declares, for each kind, the states a row holds and the states an insert may start in. A merge kind holds `open`, `accepting`, `rejected` and `declined`, and the other kinds hold only `open` and `rejected`. Only that module moves or removes a row between states, and a statement that moves a row names the state it moves from, so a row in another state is left alone. The one other way a row goes is the foreign-key cascade on its subject columns. The preview seeds in `tools/` insert with plain SQL.

- **Reject.** `open` to `rejected`, for every kind.
- **Apply.** `open` to `accepting` in the claim that starts an Accept (`claimed`), before any unit runs. A first unit that finds a Topic lease taken, or throws, hands the row back to `open` (`handedBack`), which only matches a row with no `cursor`, `moved` or `unit_revision`. `cursor`, `moved`, `unit_revision` and `failed_runs` mean something only while the row is `accepting`. The row leaves with the Tag or Topic it names, in the last unit's batch, by the cascade.
- **Remove.** An `open` row is deleted when Accept of an overview update or a disagreement commits and when a weekly stage finds that it no longer holds. The row of a lost Highlight goes with the Highlight. `goneWithItem` deletes the rows of any state that name a deleted Item or its Highlights, and the key steps delete a row that two Tags or two Topics collapse into (`proposalRelinks`).
- **`declined`.** The weekly merge run inserts a row in this state for each pair the model refused, and it never changes.
- **Merge lock.** `anyAccepting` lets one merge run at a time: a row is `accepting`, whatever its kind.

The database refuses a state a kind cannot hold and the `accepting` columns on a row that is not `accepting` (The value guard). `test/consistency-triggers-proposals.test.ts` and `test/consistency-triggers-lifecycle.test.ts` check that. They do not hold the transitions.

## The value guard

`proposals.kind` and `proposals.state` have no `CHECK`. The trigger pairs `proposals_values_*`, `proposals_subject_*`, `proposals_state_*` and `proposals_accepting_*` refuse a kind or state outside `PROPOSAL_KINDS` and `PROPOSAL_STATES`, a kind with the wrong subject columns, `accepting` and `declined` on a non-merge kind, and a `cursor`, `moved`, `unit_revision` or `failed_runs` on a row that is not `accepting`. `pins_values_*` and `pins_subject_*` do the same for `pins`. The reasons for the shape:

- A kind check in a `CHECK` needs a table rebuild for each new kind, and a rebuild resets the id sequence unless the migration carries it. A replaced trigger pair needs neither, so a later kind is a migration that replaces triggers and adds columns with `ALTER TABLE ... ADD COLUMN` (`docs/architecture/database-and-search.md`, Migrations, Consistency triggers). `proposals_state_*` names the merge kinds and `proposals_accepting_*` names no kind, so a later kind that holds only `open` and `rejected` needs no new trigger.
- The subject columns are nullable because one table holds every kind. `migrations/0041_topic-merge-proposals.sql` rebuilt the table for that, and `migrations/0042_topic-merge-pins.sql` rebuilt `pins` for `into_tag_id`.
- Foreign keys to `items` are written by hand as `REFERENCES items(id) ON DELETE cascade`, because `drizzle-kit` drops the delete action. Each Item column has an index, because an Item delete looks up the child rows through it and SQLite scans the whole child table for a foreign key with no index (https://www.sqlite.org/foreignkeys.html#fk_indexes).
- An `overview-gap` row has its own `topic_id` column and not `from_topic_id`, because `proposalRelinks` repoints every row whose `from_topic_id` or `into_topic_id` names a merged Topic with no filter on the kind, and a row repointed onto a survivor that already has one would fail the unique index on every key-step run.
- `proposals_item_pair` is a unique index on the unordered pair (`min` and `max` of the two Item ids), which keeps one disagreement row per pair in any state and either order.
- `from_digest` and `into_digest` hold the task ids of the Digests the model judged and have no foreign key, because a Digest row is replaced when an Item is refreshed.
- `migrations/0050_proposal-lifecycle.sql` adds trigger pairs with no change to a table or a column, so the previous release still runs on it.

## The read

`GET /api/proposals/{id}` answers `{ state }` for one row of any state, `rejected` and `declined` rows (which the list hides) included, and 404 once the row is gone. It answers the owner's session and an agent token, like the list, because it holds only the state, and the MCP endpoint gets no tool. The Proposals page reads it when an Accept or Reject ends with no answer.

`GET /api/proposals?cursor=` answers the owner's session and an agent token, and the MCP endpoint gets no tool. It lists `open` and `accepting` rows of every kind, 50 to a page, newest first by `id`, with the Log's cursor rule. The shapes are in `src/core/proposal-contract.ts`, and the fields that need a reason are these:

- A merge row's `items` counts are read when the call is made. A disagreement row shows the title and `summary` of the stored Digest whose task id the row holds, so the page shows the text the model judged and not a later one.
- `pageQuery` is one statement, and its `WHERE` holds what makes a row listable (`LISTED_WHILE`), before the page limit: a merge row always, a `highlight-lost` row while its Highlight is not `attached`, an `overview-gap` row while `overviewGap` holds for its Topic, and an `items-disagree` row while `DISAGREEMENT.listed` holds. A hidden row therefore leaves the page full and not short. The eligibility, the quote, the Item and the title come from one snapshot, because the Node adapter runs each batch in its own transaction and a later read could pair a row with a subject it was not chosen for.
- The `WHERE` names no kind outside `PROPOSAL_KINDS`, so a row of a kind a later release stored never fills a page, never ends it early and never breaks it.
- `checkedAt` is the largest `last_run_at` of the weekly claims in `WEEKLY_TASK`, and `provider` is whether a Provider is saved.

## Reject

`POST /api/proposals/{id}/reject` is owner-only (Access). It runs one `UPDATE ... WHERE state = 'open' RETURNING`, and reads the row again only when nothing changed: 404 for an unknown id or a kind this release does not know, 409 `not-open` for another state. A rejected row never reaches a later run's input, because the plain check skips every pair that has a row, in either order. There is no undo and no flip of direction. Reject is final: the weekly overview check never inserts a row for a Topic that has one in any state, and a lost-Highlight row stays so that Highlight is not proposed again. Reject changes no Highlight and no Topic page. A rejected disagreement row stays, so the pair is never stored again in either order (`proposals_item_pair`) and is sent to the model as decided. An accepted disagreement row is deleted, and its Pin keeps the pair decided while both Items carry the Digests it was accepted on.

## Accept

`POST /api/proposals/{id}/accept` is owner-only, an agent token gets 403 (`OWNER_ONLY_PATH` in `src/http/access-rules.ts`), the MCP endpoint has no tool, and there is no confirmation and no undo. `acceptProposal` reads the row's `kind` first (`knownProposal`) and calls the entry of a table keyed by kind (`ACCEPT`). A row of a kind the release does not know answers 404 before anything runs, and `readRow` answers only for a merge kind. A release that rolled back from one that stores a later kind therefore never runs a row it cannot read.

The answers common to every kind: 404 for an unknown id (also after a successful Accept of a kind whose row is deleted), 409 `not-open` for a row in another state, and 409 `not-current` when the row's subject changed since the row was made (the row stays and the list hides it, and the weekly stage deletes it once the subject no longer holds). Each kind adds its own:

**Lost Highlight.** `acceptLostHighlight` (`src/core/highlight-proposals.ts`) removes the Highlight by the two statements of Remove in the Reader (`removalWrites` in `src/core/highlights.ts`), and the cascade deletes the row. They run in one guarded batch that holds only while the row is `open` and its Highlight is not `attached`, so a publication that anchors the Highlight again between the read and the batch makes the batch write nothing and the next read answers `not-current`. It takes no lease and ignores `merge-busy`. Accept leaves no Pin, because a Pin keeps a correction from being undone by a regeneration and nothing regenerates a Highlight.

**Disagreement.** `acceptDisagreement` (`src/core/disagreement-accept.ts`) needs no Provider, takes no lease and never meets `merge-busy`. `not-current` means either Item no longer has the Digest the pair was judged on or the two Items no longer sit under one Topic (`DISAGREEMENT.accepts`). One guarded batch holds while the row is `open` and `DISAGREEMENT.accepts` holds, and it inserts the Pin and deletes the row. The Pin insert is an upsert on `(kind, from_key)` with `DO UPDATE ... WHERE NOT currentDisagreementPin`, so a stale Pin of the same pair is replaced in place and keeps its id, and a current one stays. That `WHERE` also covers an `open` row whose pair already has a current Pin, which an older release can store (Rollback and roll forward): the batch deletes the row, the Pin stays and the call answers 200. Accept changes no Item, Summary or overview.

**Overview update.** `acceptOverviewGap` (`src/core/overview-accept.ts`) answers 409 `no-provider` when no Provider is saved (the row stays open). `not-current` also covers a Topic that has no Item with a Digest outside `built_from` or already has an overview run open. It uses `startOverview` and its guard, owner choice and answers, which `docs/wiki.md` (Topic pages, Try again) owns, and adds to the guard that the row is `open` for this Topic and the Topic still has an Item the overview was not built from. It adds one statement right after the job insert, the delete of the row with `WHERE changes() > 0`. The batch inserts the job first, then deletes the row, then clears the failure marker, so neither changes unless a job was inserted. The guard makes the insert certain: an open job owned by the chosen owner is an open job owned by an Item of the Topic, which the guard refuses, so the open-job index suppresses nothing, also for an Item that moved in with a run still open for its old Topic. There is no Topic lease (the job takes it when it runs), no `accepting` state and no `merge-busy`.

**Cost of an overview update.** One run reads at most 40 uncovered Items (`ADDED_READ_LIMIT`), fewer when the 14,000-byte cap or an unparsable stored Digest leaves some out, and starts the next run itself after a success until every Item is covered (`continuingOverview`). When all 40 newest are unparsable, the run reads every remaining uncovered Item and keeps the first 40 that parse (`addedFrom` in `src/core/topic-overview-input.ts`). A failed run takes the refusal path (`reviseOverview` in `src/core/topic-overview-job.ts`) and does not continue, and a Provider removed mid-chain stops the chain. Covering N uncovered Items therefore needs at least ceil(N / 40) successful model calls. Three numbers stay apart: calls attempted, calls that succeeded, and whether coverage completed. The row shows N, so the owner sees the size before pressing. A Topic whose uncovered Items have only unparsable Digests is never covered, so its row, once accepted, is proposed again next week unless the owner rejects it, and that is accepted.

**Merge.** The answers are 409 `merge-busy` while another row of either kind is `accepting`, 409 `topic-busy` for a Topic row whose first unit finds a Topic lease taken (the claim is handed back and the row is `open` again), 200 `{ state: "done" }` when the merge finished inside the request and 202 `{ state: "accepting" }` when units remain. An unknown row left `accepting` still makes Accept of a known merge row answer `merge-busy`, because that row may be a merge of a later release that is still running. One merge runs at a time, so no two merges touch one Tag or one Topic, and a Topic merge also takes the Topic leases, because an overview run writes a Topic page apart from any merge.

Call the Tag or Topic that goes `from` and the one that stays `into`. The merge runs in units (`runUnit` in `src/core/merge-accept.ts`), each one guarded batch (`guardedResults`, `docs/architecture/database-and-search.md`). The two kinds share the guard, the state change, `moved`, the unit revision and the answers, and differ in what a unit plans (`MERGES` in `src/core/merge-kinds.ts`).

The Tag unit (`planTagUnit`):

1. Accept starts with one statement that moves the row from `open` to `accepting` when no row is `accepting` (`claimed`); a claim that matches nothing answers `merge-busy`, or `not-open` when the row is no longer `open`. Every unit, the first included, holds while the row is `accepting` at the unit revision it read, so two runners never move the same Items twice or count them twice, even after the cursor goes back to 0. Every unit also holds both Tag ids and both stored keys as it read them, because a `tag-keys` merge can repoint the ids and its rename can change a key. A unit that loses the guard writes nothing, and the next run reads the row again.
2. The Pin insert is an upsert on `(kind, from_key)`, so every unit can carry it, and the Pin commits with the first Items, so a Digest that publishes during the merge already lands on `into`. `from_key` is `catalogKey` of `from`'s name, which is what `pin-keys` computes, so a `from` Tag whose stored key a key step has not yet recomputed still gets the final key. The unit also repoints every Pin that targets `from` to `into`.
3. Each unit takes the next 100 Items that link to `from` by ascending Item id after the cursor (`REWRITE_UNIT_ITEMS`) and rewrites each stored Digest's `tags` (repeats dropped by key, first place kept). The rewrite is guarded per Digest on `digests.task_id` and on the Digest's `tags` still being the ones read, and writes `$.tags` alone with `json_set`, so a Topic rewrite of the same Digest by `pin-keys` between the read and the batch is not undone. The links move (`tagMoves` in `src/core/catalog-key-links.ts`) before the Digests are rewritten, because the link guard reads the Digests as they were read. An Item whose Digest changed in between keeps its link and Digest for a later unit, so a stored Digest never names `from` beside a link to `into`. A stored Digest that does not parse keeps its text, its link still moves, and one `merge-digest-unreadable` line names the Item id. It never stops the merge, because one merge at a time blocks every other merge Accept.
4. `moved` counts the `item_tags` rows of `from` among the unit's Items whose Digest still matched the read, computed before the link writes, so an Item deleted or republished in between is not counted.
5. Only when no `item_tags` row for `from` remains: the `merge` Log entry and the closing writes (`closingWrites`): one bump of `catalog_version` (so a Digest that read the old Tag list asks again), the delete of the `tag-keys` rows that staged `from`, and the delete of the Tag `from`, whose cascade deletes the row and any other Proposal that names `from`.

A Tag on 100 Items or fewer therefore merges in one batch. `moved` and the Log's count are the Items that carried `from`, including those that already had `into`.

The Topic unit (`planTopicUnit` in `src/core/topic-merge-unit.ts`) has the same steps with these differences:

1. It claims both Topic leases before it reads anything, in ascending Topic id (`claimBoth`, holder `topic_merge:<id>:<unit revision>`), so an overview run cannot write either Topic page while a unit reads or writes it, and two jobs that need the same pair claim in one order. A unit holds its leases for its own batch only, so an overview run can write a page between two units, and the next unit reads the Topic again. The guard also holds both leases (`leaseHolds`).
2. The Pin is a `topic-merge` Pin and the repoint covers the Topic Pins that target `from`.
3. The moves are the shared Topic rewrite (`docs/architecture/data-model-outline.md`, Catalog keys, `topicMoves`): the next 500 Items under `from` (`MERGE_ITEMS`) and the next 500 Log entries that name it, so a Topic merges in one unit only when both collections fit. The cursor stays null, because the next read takes the first Items still linked.
4. When no Item and no Log entry names `from`: the `merge-topic` Log entry, then the closing writes (`topicClosingWrites`) in this order: one attempt to open an overview run for `into`, one bump of `catalog_version`, the delete of the `topic-keys` rows that staged `from`, and the delete of `from`. The row stays until that last statement, because it holds the count the Log entry reads.

**Lease exits.** A claim commits before the batch, so every way out of a unit releases what it took: a second claim that fails or throws releases the first, a unit that throws while it reads releases both, a unit whose guard fails releases both in a separate batch (because the batch rolled back with its releases), and a successful unit releases inside its batch. `releasedAfterFailure` (`src/core/merge-failure.ts`) runs every release outside a batch. A release that fails is logged as `merge-unit-leases-not-released` and never replaces the error that ended the unit or the answer the call would have given. An unreleased lease blocks the Topic's overview run and every merge that names it for `TOPIC_LEASE_MS` (12 minutes). A first unit that finds a lease taken changes nothing but the claim, which `handedBack` undoes, so the row is `open` again and the call answers `topic-busy`. A first unit that throws, in the request or in the stage, hands the claim back in the same way (`recordingFailure`), so a unit that fails for good does not keep the row `accepting` and `merge-busy` on every other merge. A request that ends after the claim and before the first unit commits (a closed tab, an ended Worker invocation, a crash) leaves the row `accepting` at revision 0, and the `merges` stage runs the first unit on the next tick. The unit's lease holder names the row and the revision (`topic_merge:<id>:<unit revision>`) and `claimTopicLease` takes a lease again for the same holder, so the stage takes the leases the ended request left and the Topic stays blocked for no more than the tick. Two runners of one revision do not exclude each other through the lease: the unit's guard holds the revision and, for a Topic unit, the lease generation that each new claim raises, so the runner that claimed first loses its batch. A later unit that finds one ends that call and leaves the row `accepting`, and the `merges` stage continues it on the next tick. A run that finds a lease held neither adds to the count nor clears it, so a merge that only waits for a lease shows "Applying…" and no failure note.

**The overview run after a Topic merge.** The closing writes try to open one `topic_overview` job for `into` (`continuingOverview`). It inserts a job only when a Provider is saved, `into` has Items its page does not cover, and its owner Item has no open job of that kind. It can insert nothing while a job for that owner Item (the Item of `into` with the lowest id) already waits, and that job then runs for `into`, because a job takes its Topic from its owner Item when it starts. The cost is the lower bound of Cost of an overview update, and the row shows both Item counts so the owner sees the size before pressing Accept. A survivor page that has overview text marks the moved Items "Not in overview yet", and a survivor with no overview text shows no marker, because the page flags an Item only when the overview has text.

**Who runs the units.** The accept request claims the row, then runs up to 50 units (`UNITS_PER_ACCEPT`). The `merges` sweep stage (`continueMerges`, in `src/core/sweep.ts`) continues every `accepting` row of either kind with the same bound on each tick, so a closed tab, a crash or an ended Worker invocation finishes by itself. The route and the stage call one function (`continueMerge`) with the job ports (`JobPorts`), because a Topic unit that opens an overview job wakes the runner with `enqueueRows`, and a queued row that is not woken is found by the next sweep. A unit that throws a database error ends the call, the stage is logged as `sweep-stage-failed`, and the next tick starts again from the stored row.

**A unit that keeps failing.** A unit that fails writes nothing, so the row stays `accepting` (a first unit hands the row back to `open` instead, so a failure there leaves the row as it was), `merge-busy` refuses every other merge Accept and Reject of the row stays refused, until a later run commits the unit. No `failed` state exists: a merge that started cannot go back to `open`, because the Pin commits in the first unit, and the one-merge rule keeps two merges off one Tag or Topic. Instead the row counts its failed runs in `failed_runs`. `runUnit` runs planning and applying through `recordingFailure` (`src/core/merge-failure.ts`). When either throws, it logs `merge-unit-failed` with the proposal id, the error class and, for a database error, its code (`databaseCodeOf`, no SQL and no parameters), runs `unitFailed` in a write of its own, and throws the original error. A cleanup write that fails is logged as `merge-unit-failure-not-counted` and does not replace the original error. `unitFailed` matches only a row that is still `accepting` at the unit revision the run read, so a run that lost the row to another writer counts nothing, and the first unit's failure count is cleared when the row is handed back. A unit that commits clears the count (`unitAdvanced`). The read returns the count as `failedRuns`, and the page points the owner to the log line.

**Key steps during a merge.** `tick` runs `migrateData` beside the sweep, so a `tag-keys` or `pin-keys` unit can run between two units, and neither waits for the other. A key merge repoints the `accepting` row's ids (`proposalRelinks`), and the next unit reads the new ids and continues onto the survivor. When two rows reach one pair, an `accepting` row with a committed unit (`unitCommitted`: `unit_revision` is not null) outranks `rejected`, which outranks every other row, a claimed `accepting` row with no committed unit included, and the smaller id decides inside a class, so a merge that has moved Items never loses its row to an older Reject, and a claim that is handed back leaves an older Reject in place. The `pin-keys` step skips the `from` Tag or Topic of a row with a committed unit, because that unit's Pin already makes it look like one that holds a Pin's key and the Accept finishes it with its own Log entry. A claimed row has no Pin yet, so the step treats its `from` as any other. The skip is in the step's read, and the step's batch carries the same check as a guard, so an Accept whose first unit commits between the read and the batch makes the batch write nothing, and the next run reads again. A key merge that makes `from` and `into` one deletes the row: the first unit's Pin already points at the survivor, and no `merge` entry is written. A link that a unit moves onto a Tag that a key step is about to delete is caught by that step's restage check (Catalog keys). An accepted Tag merge changes no Topic, takes no Topic lease and queues no overview run. A stored Digest's own AI task (`ai_tasks.result`) keeps the names it returned, as provenance. `TOPIC_KIND.relink` repoints every row that names the losing Topic before the Topic is deleted, by the same rule, because without it the cascade would delete a Reject and the pair would be proposed again.

**Bounds of a Tag unit.** A unit runs 3 reads and 1 batch (`readRow`, the two reads of `readRewrite` and the batch), which D1 counts as 4 queries, because a `db.batch()` counts as one query ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), read 2026-11-12). An accept request runs at most 50 units, so about 200 queries, and `migrateData` stops after 100 units at about 4 queries each, so about 400. Both fit under the 1,000 queries a Workers Paid invocation may make (the queries of the other sweep stages are not counted). The same page limits each statement to 100,000 bytes and a bound string to 2,000,000 bytes, and gives a batch call 30 seconds. The largest bound string is the JSON of a unit's read state: for each of 100 Items an id, a task id and at most 3 Tag names of at most 240 characters (`SHORT_TEXT_MAX`), so the names take at most 3 × 240 × 7 × 100 = 504,000 bytes when every character is a control character that both JSON layers escape. The worst case with 6-digit ids and task ids measured 509,401 bytes (`JSON.stringify` of 100 objects `{id, task, tags}`, 2026-11-15). The unit size of 100 and the unit bound of 50 are chosen numbers, not limits.

**Bounds of a Topic unit.** A Topic unit runs 5 reads (`readRow`, the two lease claims, the two reads of `TOPIC_KIND.linked`) and 1 guarded batch, so 6 queries on D1. An accept request runs at most 50 units, 25,000 Items at `MERGE_ITEMS` = 500. A counting shim around `node:sqlite` (not D1) measured 304 queries for such a request (254 single, 50 batches) and 3,033 ms, with the 202 answer. One tick that runs 50 units of the `merges` stage and a `topic-keys` step with 150 stale keys measured 367 queries and 4,902 ms with the same shim, below the 1,000 queries of a Workers Paid invocation. No query count of a whole tick was taken on D1, and the other stages of the tick are not in that number. The size 500 and the bound 50 are chosen numbers. Local D1 ran a Topic of 25,101 Items as 50 units of 500 in the request and the other 101 Items in one scheduled event, without error. A deployed D1 was not run, so its CPU time per unit is not measured.

## Pins

A Pin records an accepted merge: the merged-away name's `from_key` and `from_name` and the target's id (`into_tag_id` or `into_topic_id`, no delete action on either, so no target can be deleted while pinned). One Pin exists for a name in each kind (a unique index on `kind` and `from_key`), so a Tag and a Topic can share a key. Every path that turns a Digest's names into links reads the Pins for the Digest's Tag keys and its Topic key: `publishing` in `src/core/digest-publish.ts` (a model result, a caller-sent Digest and `items.pending_digest` alike) and `linkOlderDigest` in `src/core/older-digests.ts`. A name whose key is pinned becomes the target's name before `catalogEntries` runs, so the Item links to the target, the stored Digest names the target, and no `tags` or `topics` row with the pinned key is inserted. The AI task's own result keeps the names the model returned.

Both paths guard their batch on the exact resolution they used: for each key, the Pin they found and its target (the token `id:target`), or that no Pin existed (`pinnedDigest` in `src/core/pins.ts`). The guard is separate from the catalog guard, because the model path drops its catalog guard after `MAX_STALE_REQUEUES` and the caller path has none, and the Pin guard inherits neither gap. `test/topic-pins-wiring.test.ts` shows each path refusing its batch when a Pin appears after the read. A publication that loses the guard is stale and requeues under the existing stale rules. `linkOlderDigest` that loses it writes nothing, and the Item stays unlinked for its next pass. It also writes the rewritten Digest, because it links Items whose stored Digest the accept's units did not reach.

**The address of a merged-away Topic.** `topicOfKey` (`src/core/topic-page.ts`) looks a key up in `topics` first, and when no Topic has it, in the `topic-merge` Pins, and answers the Pin's target. A Topic with the key always wins over a Pin. A Pin is repointed when its target is merged away, so a chain of merges resolves the first address to the last Topic. The Topic page replaces the address with the survivor's path when `topic.key` differs from the requested key (`use-survivor-address.ts` calls `history.replaceState`), so a reload and the Back button land on a key that exists. The `topic=` filter of `GET /api/items` and the Index do not follow a Pin, because a filter is built from live lists and an address is stored by the owner. A Tag Pin is not read for an address.

**Catalog key steps.** `TAG_KIND.relink` and `TOPIC_KIND.relink` repoint every Pin that targets the losing Tag or Topic to the survivor in the unit that deletes it. The `pin-keys` step runs after `tag-keys` with `CATALOG_KEY_VERSION` as its version, and its phases are named in its cursor:

- `keys` recomputes every Pin's `from_key` from `from_name` in one unit, keeping the smaller id when two Pins reach one key and deleting the other first, because the unique index would refuse it. A Pin holds a key of at most `CATALOG_KEY_MAX` (4,320 code points). The deletes, the two key updates and the finish guard take 100 Pins at a time (`PINS_PER_STATEMENT`), so one bound string stays under 100 × 4,320 × 3 bytes = 1,296,000 bytes, below D1's 2,000,000-byte limit. The first update gives each Pin a temporary key longer than any key `catalogKey` can return, so no Pin holds it.
- `merge:<tag>:<item>` merges a Tag whose key equals a Pin's key into the Pin's target with the same bounded rewrite as Accept (`readRewrite`), and leaves the Pin's own target alone.
- `topics` is the Topic case below.
- `finish` records the version only in a batch whose guard checks that every Pin key still equals its recomputed key and that no Tag other than a Pin's target holds a Pin's key. When the guard fails, the next run stages again.

**The Topic case of `pin-keys`.** The cursor `topics` merges a Topic whose key equals a `topic-merge` Pin's key into the Pin's target, one unit at a time, through the shared Topic rewrite (`topicMoves`). It repoints the Proposals and Topic Pins of the loser first (`proposalRelinks`, `repointedTopicPins`), and a unit adds the closing writes (`topicClosingWrites`), each only when no Item and no Log entry names the loser. The step writes no Log entry and no Proposal state and takes no Topic lease. It leaves the Pin's own target alone and skips the merged-away Topic of an `accepting` Topic row, for the reason and with the guard that the Tag case has. The case exists for two causes: a change of `CATALOG_KEY_VERSION` can leave a Topic under a pinned key, and a Digest from an older Worker still in flight after a deploy can create the merged-away Topic again. Without it those Topics stay until someone merges them by hand. It is the riskiest and least used part of the Topic Pin.

**The Pin of a disagreement.** Accept of a disagreement writes an `items-disagree` Pin. It names a pair of Items and not a name, so it reuses two columns that every Pin has and that the table cannot make nullable without a second rebuild of `pins`: `from_key` holds the pair key `<lowItemId>:<highItemId>` (`pairKey`), which the unique index turns into one Pin per pair, and `from_name` holds the agent's reason as the owner accepted it. Both Item columns are `ON DELETE cascade`, because the Pin is a statement about those two Items.

The Pin is weaker than a merge Pin, and `docs/spec.md` and the **Pin** entry of `GLOSSARY.md` say so. It binds the pair to the two Digest versions it was judged on. It survives a regenerated overview, a Topic merge (it names Items and no Topic), a refresh that leaves both Digests alone and a restart. It does not survive a new Digest of either Item, even one with the same Summary text, because the version token changes. The Pin is then stale: the Topic page no longer lists the entry, the weekly check judges the pair again, and a later Accept replaces the Pin in place. A pair is current when `currentDisagreementPin` holds. Four readers use that one condition: the Topic page (`readDisagreements`), the `decided` list of the weekly check (`decidedPairs`, which reads the rows first and then the Pins, because an Accept deletes the row in the batch that writes the Pin, so one read order cannot miss both), the store of the weekly check (a returned pair with a current Pin inserts no row), and the rule that keeps a row listed (`DISAGREEMENT.listed`).

**The `pin-keys` kind filter.** The step recomputes every Pin's `from_key` from `catalogKey(from_name)`, which for an `items-disagree` Pin would rewrite the pair key to the key of the reason and could delete the Pin as a duplicate of another Pin with the same reason. Every read of `pins` in `src/core/pin-key-step.ts` therefore names `MERGE_KINDS`, and the reads in `src/core/pin-merge.ts` name the kind they read. `pinsFor` in `src/core/pins.ts` already filters by kind. `test/disagreement-pin-steps.test.ts` shows both disagreement Pins unchanged, also with the same reason.

**Rollback and roll forward.** `docs/architecture/ci-releases-and-rollback.md` holds the rollback of each migration. The Proposal-specific parts:

- The release before Tag Pins (780bb87) ignores Pins, so a Digest it publishes can create the merged-away Tag again. For a Topic Pin the release before `0042_topic-merge-pins.sql` reads only `tag-merge` Pins, so a Digest it publishes can create the merged-away Topic again. Upgrading again does not repair that, because `pin-keys` already recorded its version and the older-Digest linking reads only Items with no Topic. Delete the step's row (`DELETE FROM data_steps WHERE name = 'pin-keys'`, through `wrangler d1 execute` or the container's database). The next start, tick or Paste runs the step again and merges every Tag and Topic that holds a Pin's key into the Pin's target, with its links and stored Digests. The same procedure covers Digests an older Worker still in flight writes after a deploy.
- After an accepted Topic merge, `0043_merge-topic-log-action.sql` stays in the database. The release before it serves the Items and the Log without the `merge-topic` line, publishes a Digest that names a pinned Topic onto the survivor, answers 404 for the old Topic address, and refuses Accept of a Topic row with 409 `not-supported`. A Topic row left `accepting` shows "Applying…" there, continues nothing, and blocks Accept of a Tag row with 409 `merge-busy`. Rolling forward lets the `merges` stage finish it.
- The disagreement Pins stay in the database. That holds once the `pin-keys` step is recorded complete in `data_steps`, as it is for every database that has run a release with the step. On a database where the step never finished, the older step has no kind filter and rewrites the pair keys of two Pins to the one key of their reasons, which deletes one of them. So do not change `CATALOG_KEY_VERSION` in a release that predates the filter. The release before the disagreement Pins reads Pins only through `pinsFor`, its `GET /api/topics/{key}` has no `disagreements` field, its values triggers do not know the kind so it never writes one, and its `deleteItem` deletes an Item that a Pin names through the cascade. After an Accept the row is gone and only the Pin remembers the pair, and nothing in that release reads the Pin, so a Topic that is touched again can get an `open` row for a pair the owner accepted. Rolling forward reconciles that: the list hides the row at once, the next weekly stage deletes it, an Accept pressed on it answers 200 and deletes it with the Pin kept, and a `rejected` row for any pair stays.
- The release before `0046_disagreement-proposals.sql` opens the migrated database. Its list read keeps an `items-disagree` row out before the page limit, so it lists the earlier kinds in the same order with a full page and a correct `next`, and its Reject and Accept answer 404 for such a row (`knownProposal`) before any merge dispatch. Its `isDue` claims only the kinds in its `JOB_KINDS`, so a queued `disagreement_proposals` job stays queued, and the claim row and `topic_checks` stay untouched. Rolling forward lists the rows again and the queued job runs.

## The weekly Tag and Topic checks

The `proposals` and `topic-proposals` sweep stages claim the `scheduled_runs` rows `proposals` and `topic_proposals` with `claimingWeek` (no row, a `last_run_at` at least 7 days old, or more than 7 days ahead of the clock) and open one job each in their own batch, owned by the newest Item with a Digest. The two claims are independent, so a failing stage or job in one does not skip the other. A Topic row names no Item, and a Topic with no Item is not sent.

## The weekly Highlight check

The `highlight-proposals` sweep stage claims `highlight_proposals` on the same rule and under the same conditions as the other stages: a Provider saved and at least one Item with a Digest. The condition is shared so that the page's empty state, which says the weekly check needs a Provider, stays true. The stage calls no model, makes no `ai_tasks` row and opens no job. It is one `db.batch`:

1. The claim.
2. The insert, with `WHERE changes() > 0` after the claim, so a second tick in the week inserts nothing and a batch that fails spends no week. It takes the 20 newest Highlights (`PROPOSALS_MAX`) whose status is not `attached` and that have no `proposals` row in any state, in ascending id order so the newest Highlight lists first, as `open` rows with the fixed reason `plain-check` (the `proposals_open_reason` check needs a reason on an open row). `ON CONFLICT DO NOTHING` keeps the unique index `proposals_highlight` from failing the batch.
3. The delete of `open` rows whose Highlight is `attached` again, after the insert so that `changes()` in the insert still reads the claim's row. It runs only when the `scheduled_runs` row holds this tick's time (`claimedAt` in `src/core/scheduled-claim.ts`), because a tick that lost the claim must delete nothing. A rejected row stays, so Reject is final for that Highlight.

Nothing in the check updates `highlights`; `src/core/highlight-publish.ts` stays the one writer of `status` and `start`, so a Highlight whose text comes back is `attached` again with no help from a Proposal.

**Unattended path.** A stage that throws before its batch commits logs `sweep-stage-failed`, and the next tick tries again, because the claim did not commit. A batch that commits and whose answer is lost (`docs/architecture/database-and-search.md`, Guarded batches) leaves the rows stored and the week claimed, so nothing is lost. The page shows nothing about either. The overview check works the same way.

## The weekly overview check

The `overview-proposals` sweep stage claims `overview_proposals` on the same rule and under the same conditions. The Provider condition is real here, because with no Provider every Item is outside an overview and Accept needs one. The stage calls no model, makes no `ai_tasks` row and opens no job. It is one `db.batch`:

1. The claim.
2. The insert, with `WHERE changes() > 0` after the claim. It takes up to 20 Topics (`PROPOSALS_MAX`) for which `overviewGap` holds and that have no `proposals` row of this kind in any state, so a Reject is final for the Topic. `overviewGap` is an Item with a Digest that `built_from` does not list with that Digest's task id (the predicate the Topic page uses, and not `coverageGaps`, because `coverageGaps` also counts removed Items), and no `topic_overview` job that is not `done` owned by an Item of the Topic, because that run and the chain it starts are the cure. They are chosen by the number of uncovered Items, most first, then by Topic id, and inserted in the reverse order so the Topic furthest behind lists first, with the fixed reason `plain-check`. `ON CONFLICT DO NOTHING` keeps the unique index `proposals_overview_topic` from failing the batch.
3. The delete of `open` rows whose Topic no longer has a gap, only in the tick that won the claim and after the insert. Between claims the page hides such a row and the row stays, so a row whose Topic has a run open lists again if that run ends and leaves a gap. A Topic that falls behind again after its row was deleted is proposed again.

An overview run that failed leaves a failure marker and uncovered Items with no open job, which is exactly a Topic this stage finds. So do Items that arrived, or that a Topic merge moved, while no Provider was saved.

## The weekly disagreement check

The `disagreement-proposals` sweep stage claims `disagreement_proposals` on the same rule and under the same conditions, and opens one job in the same batch, owned by the newest Item with a Digest (`openModelRun` in `src/core/proposal-week.ts`). The batch holds a second statement, `staleDisagreements`, which deletes the `open` rows whose Items no longer both have the Digest the row names and the `open` rows whose pair has a current Pin (so a duplicate that an older release stored for an accepted pair goes at once). It runs only when the claim row holds this tick's time, so a tick that lost the claim deletes nothing, except that two ticks with the same millisecond both delete, which is harmless because the rows they delete are stale for both. A `rejected` row is never deleted by it, and neither is an `open` row whose Items merely sit in two Topics.

**Which Topics are read.** A Topic is touched when it has at least 2 Items with a Digest and the text of its membership differs from the text stored for it in `topic_checks`. The membership text (`membersOf`) is `itemId:digestTaskId` for each of the Topic's newest 12 Items with a Digest, joined by commas in ascending Item id, built by one `group_concat(... ORDER BY ...)` in SQL. That needs SQLite 3.44 or later (`node:sqlite` is 3.53.3 and local D1 parsed the same text; `sqlite_version()` is not allowed on D1). So a new Item, a deleted Item, an Item that moved Topic and a refreshed Digest inside the newest 12 each make the Topic touched, and a Digest replaced on an older Item does not. The read takes the touched Topics in pages of 20 (`TOPICS_PAGE`), the Topic with the newest Digest `created_at` first, and goes on until the input has no room for another Topic or none is left, so Topics that cannot fit never keep the later ones out. A Digest with no JSON, no title or no Summary leaves its Item out and logs `topic-digest-unreadable`. `fillDisagreementInput` adds each Topic whole in that order while the input stays within 14,000 UTF-8 bytes. A Topic that does not fit loses its oldest Items down to 2, and a Topic that cannot fit 2 Items is skipped and stays touched. The model gets each Item's id, title and Summary and a list `decided` of the Item pairs that already have a row in any state or a current Pin, lower id first. It gets no post text, comment or author.

**The run.** The result is at most 10 pairs (`DISAGREEMENTS_MAX`), each two different Items that were sent in one Topic, with a `reason` of 1 to 160 characters under `plainText`. Zero is valid. One guarded batch stores it. Its guard holds while the AI task is running and the membership text of every sent Topic, computed again inside the batch, is still the text the run read. It first deletes the `open` rows that no longer match the stored Digests or whose pair has a current Pin (`clearedStaleDisagreements`), so a hidden row of a pair that the run judged again cannot keep the pair's slot in `proposals_item_pair`. It then inserts an `open` row for each pair with `ON CONFLICT DO NOTHING` and a `NOT EXISTS` on the pair's current Pin, so a row that still matches, open or rejected, is kept and a returned pair the owner already accepted stores no row. It then upserts `topic_checks` for every sent Topic, including a Topic that produced no pair, and completes the AI task. When the guard fails nothing is written, the task fails as `stale` and the job runs again without spending an attempt. A Topic that was touched but not sent stays touched for next week.

**What hides and deletes a row.** An `open` row stays listed while both Items still have the Digest the row names, are still in one Topic, and the pair has no current Pin (`DISAGREEMENT.listed`). The variants of that condition differ in one place each: `accepts` leaves the Pin out, so Accept answers 200 for an open row whose pair already has a current Pin, and `stale` leaves the Topic out, so the weekly delete keeps a row while its Items sit in two Topics. A refreshed Summary hides a row at once and the next weekly stage, or the next store of the same pair, deletes it. Two Items in different Topics hide it too, but nothing deletes it, because a Topic merge of more than 500 Items commits in units (`MERGE_ITEMS`), so a pair can sit in two Topics between two units, and the row is listed again when the merge ends. A Topic merge leaves the row alone, because the row names no Topic column.

**Cost and budget.** Each attempt makes at most one model call, with SDK retries off. The week opens one job, and error retries and stale reruns add calls. A Topic is judged again only after its membership changed, so a library with no new Items costs no call. The output allowance is 4,096 tokens (`DISAGREEMENT_OUTPUT_TOKENS`, chosen), passed to the executors that take one (Claude Code takes none). A valid answer of 10 pairs with 6-digit ids and 160-character ASCII reasons is 1,979 bytes of JSON, under the allowance at one token per byte. With 160 CJK characters in each reason it is 5,179 bytes, which can pass it at one token per byte, and a cut-off answer is a refusal that is not retried. The token count of CJK text was not measured. Static bound at one token per byte against the 24,000-token context of the model of Measured Digest input budget (`docs/architecture/ai-tasks-and-providers.md`): for five inputs filled to within 14,000 bytes (plain English, escape-heavy, CJK, emoji, Turkish) the input was 12,806 to 13,838 bytes, the instructions 1,098 bytes and the schema 559 bytes, so input, instructions, schema and allowance came to at most 19,591, at least 4,409 under the context (measured by building each input with `fillDisagreementInput` and `disagreementTask` and counting bytes; the script is not kept). Observed on 2026-11-12 with `claude -p --output-format json --json-schema` and the executor's other flags (Claude Code, `claude-sonnet-5-5`, `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`) on the same five inputs, the input-side usage was 6,490 (plain), 9,975 (escape), 6,830 (CJK), 12,121 (emoji) and 8,649 (Turkish) tokens and `output_tokens` was 55 for each, because the inputs repeat one text and the model found no pair. Those numbers hold for Claude Code only, include its own system prompt, and the output side of a full answer of 10 pairs is not measured.

**Unattended path.** A stage that throws before its batch commits logs `sweep-stage-failed` and tries again on the next tick. A refusal retries after 30 seconds and 2 minutes, and the last retry closes the job with nothing stored and every `topic_checks` row unchanged, so the Topics that changed are read again next week. The handler takes no Topic lease and no `blockedBy`, because it writes only `proposals` and `topic_checks` rows. When the job fails before a task row exists, one `disagreement-proposals-run-failed` line names the refusal.

## The Log entry

A `merge` entry (`loggedMerge` in `src/core/log-writes.ts`) holds the two Tag names as written when the merge finishes and the Items that carried the Tag. It names no Tag and no Item, so it blocks no delete and survives an Item delete. A failed unit writes nothing, and the Log has no failure entries. A `merge-topic` entry is the same row for a Topic merge, and `moved` is the number of Items the units of this Accept moved, so the Items a `topic-keys` merge moved between two units are not counted. It is a separate action and not a kind column on `merge`, because the release before it skips an action it does not know, while it would print a Topic merge as `tag:`.

## The page

`/proposals` is the `proposals` screen (`web/src/screens.ts`), drawn by `ProposalsPage` through `ListPage`, with a body for each kind chosen by an exhaustive `switch` on `kind` (`ProposalBody` in `web/src/ProposalRow.tsx`). The words of each kind come from one table (`WORDS` in `web/src/proposals-text.ts`), and the texts came from `tools/copy/write-copy.sh`. Decisions that the code does not state:

- **No confirmation.** The row's sentence states the effect before the press, and the head text covers every kind: an Accept of a merge cannot be undone, an Accept of a lost-Highlight row removes the Highlight for good, an Accept of an overview row starts a model run, an Accept of a disagreement row keeps the pair on the Topic page, and a Reject is final.
- **Accessible names** begin with the visible label and name the subject, and the disagreement row's names also carry the first 40 characters of each Summary (`textCut`), because Items often share a title and two rows would otherwise read the same.
- **The failed-merge note** ("Applying this merge failed once…", `applyFailedNote`) has no live role, because the count rises about once a minute and each rise would be announced again. `useAnnouncingReread` says the text once, when a reread shows a count above 0 on an `accepting` row that had none.
- **Empty state.** The date is the most recent claim time of the weekly runs, which does not say that a check finished, so the last line says no more than the page knows: the list is empty because the check found nothing, is still running or failed, or because the owner rejected every row. The page shows no failure of the weekly run.
- **A disagreement or overview row has no "applying" state**, because Accept answers 200 (and the overview run belongs to the Topic page). A 409 `no-provider` or `merge-busy` or `topic-busy` shows a note beside the buttons and keeps the row with its buttons on (`BUSY_NOTES` in `web/src/ProposalActions.tsx`). A 409 `not-current` reads the list again, where the row is gone, and shows a page notice that nothing was done.
- **Reread.** `usePagedRead` (`web/src/use-paged-read.ts`) offers `edit`, which also drops any read in flight so a late answer cannot bring a rejected row back, and `reread(through)`, which reads from the first page until `through` is true so a row that moved to a later page is still read. While any loaded row is `accepting`, `useProposalsPage` reads every loaded page again each 3 seconds. When the outcome of a press is unknown (a network failure, or a 404 or 409, which a Reject whose answer was lost also gets when sent again), the page reads again and shows the row as the Instance has it.
- **A pull request preview** has no Provider, so its weekly runs claim nothing, although its Cron Trigger fires every minute (`docs/pr-previews.md`). Provisioning inserts demo `open` rows instead, only when the preview's database has the `proposals` table, and a redeploy adds none and keeps a Rejected row Rejected. An overview-gap row answers 409 `no-provider` there.

## The reads of the run

`usedSubjects` reads the Tags, or the Topics, that have an Item in pages of 1,000 by id, as a recursion that asks for the page after the last id, because D1 caps one result at 50 MB. `knownPairs` reads every `proposals` row of the run's kind in one query: a row is under 100 bytes and at most 20 rows are added a week, so 50 MB takes about 480 years of weeks (guess).

## Identity

Every `proposals`, `pins` and `topic_checks` row has a generated id that is never reused (`AUTOINCREMENT`, and the migrations keep the sequence). The weekly claims in `scheduled_runs` are keyed by the task name, survive a restart and a deploy, and stay out of the export as working tables. The rows below break only where the table says.

| Record | Identity | Breaks |
|---|---|---|
| A merge row | a generated id, and the unordered pair of two generated Tag or Topic ids, one row in any state | deleting either side outside a key merge (the accepted merge's last unit removes the row by cascade), or a key merge that makes the two one or brings the row onto a pair that already has a row it loses to |
| A `highlight-lost` row | a generated id, and `highlight_id` | removing the Highlight, deleting its Item, a Highlight that becomes `attached` (the weekly stage deletes the open row) |
| An `overview-gap` row | a generated id, and `topic_id` | deleting the Topic (a Topic merge, by cascade), Accept (the row is deleted with the run it starts), a gap that closes (the weekly stage deletes the open row) |
| An `items-disagree` row | a generated id, and the unordered pair of two Item ids (`proposals_item_pair`), with the two Digest task ids as version tokens | deleting either Item (cascade), a refreshed Digest of either Item (the row is hidden at once and the weekly stage deletes it while it is `open`, and a `rejected` row stays), and a row whose Items sit in two Topics is kept and listed again when they sit in one |
| A disagreement Pin | the kind and the pair key `<low>:<high>`, with the two Digest task ids | deleting either Item (cascade), a new Digest of either Item (hidden, and a later Accept replaces the Pin), and the Items leaving one Topic (hidden) |
| A Tag or Topic Pin | the kind and the merged-away `from_key`, kept in step with `catalogKey` by `pin-keys` | a rule change that brings two Pins to one key (`pin-keys` keeps the smaller id, so the older correction survives), a Pin removed by hand, and a rollback to a release that ignores Pins until the recovery above. A target delete is refused until the Pin is repointed. |
| `topic_checks` row | the Topic id, the membership text the last run read, the time | deleting the Topic (cascade). A run that stores nothing keeps the text of the last run that stored. |
| A Topic lease taken by a Topic unit | the Topic id, holder `topic_merge:<id>:<unit revision>`, a generation | a crash between the claim and the release, which expires after `TOPIC_LEASE_MS` |
| The `accepting` state and its counters | the row's own id | the last unit's delete of the Tag or Topic, which removes the row, or a key merge that makes the two one. A restart, a deploy, a closed tab (the sweep continues it) and a key merge of either side (repointed) do not break it. |
| A `merge` or `merge-topic` Log entry | a generated id, snapshot names, no reference | nothing |

An Item delete changes no merge Pin and no merge row, because a Pin of a merge, a `merge` or `merge-topic` entry and a merge Proposal name no Item. A disagreement Pin and an `items-disagree` row name two Items and go with either of them: `deleteItem` deletes them before the Item, and the cascade on both columns is the second line. The `highlight-lost` rows that name a Highlight of the Item go in any state in the same way, because the quote the row showed is the owner's own text, kept nowhere else. The reason on a disagreement Pin is the agent's own sentence and cites no Item text beyond what the agent wrote (not verified, see Open items and unverified claims). The Summaries a disagreement row showed stay in the Digests and in no row, but the AI task's `inputs` keep the Item titles and Summaries of the Topics that were sent, until the owner Item or the task goes. The weekly model runs open their jobs on the same owner Item, and deleting that Item while they are open loses that week's check for all of them.

## Probes

Each probe ran on `node:sqlite` (Node 26.12.1, SQLite 3.53.3) and on local D1 (`wrangler d1 execute --local`, wrangler 4.158.0) with the migration applied, and the output was identical unless a line says otherwise. The scripts are not in the repository, so the probes cannot be repeated from it. What each shows that the migration files and tests do not:

- **Unordered pair index and claim (2026-11-11).** A row for the pair `(2, 1)` after `(1, 2)` was ignored by `INSERT OR IGNORE` and by `ON CONFLICT DO NOTHING`, and a pair of one Tag with itself failed `proposals_distinct`. A claim followed by `INSERT ... SELECT ... WHERE changes() > 0` opened one job, a second claim in the same week opened none, and a claim of a row 7 days old opened one. That is why the claim must be the statement right before the insert that reads `changes()`.
- **Accept of a Tag merge (2026-11-11).** On one seed (thousands of Items with stored Digests, 30 of them naming `ml`, two `open` Proposals, one of them `ml` into `machine learning`), the Tags, links, stored Digest names, Pin, `merge` Log entry, remaining Proposal row, `catalog_version` and `tags` search part came out equal in every dumped table. Local D1 ran each unit's batch without error.
- **Rebuilt `proposals` table (2026-11-12).** Pair `(2, 1)` after `(1, 2)` failed `proposals_pair`, the same for Topics failed `proposals_topic_pair`, Topic pairs `(1, 2)` and `(1, 3)` coexisted, and a Topic with itself failed `proposals_topic_distinct`. After ids 1 to 5 with 5 deleted the next insert took id 6, so the id high-water mark survives the rebuild.
- **Rebuilt `pins` table and the Digest rewrite (2026-11-12).** With foreign keys on (the file's `PRAGMA foreign_keys` lines were skipped on `node:sqlite`, because D1 ignores them), 0042 kept both Pins with `into_topic_id` null, `sqlite_sequence` held 3 (after a Pin 3 was inserted and deleted) and the next insert took id 4, `foreign_key_list` named `tags` and `topics` with `NO ACTION`, and `foreign_key_check` found 0 violations. `json_set(digest, '$.topic', name)` behind `json_valid` gave the same text on both for 6 rows: a valid Digest changed in place with the key order kept and quotes, a backslash and an accent escaped as before, an object with no `topic` key gained one at the end, `not json` kept its text, a JSON array and a JSON string stayed as they were, and the numbers `1.50` and `12345678901234567890` kept their text.
- **Lease guard, `merge-topic` triggers and address lookup (2026-11-12).** A batch that starts with the two-lease guard released both leases when the guard held and was refused with `CHECK constraint failed` when a lease generation had moved. A release placed before a failing guard rolled back with the batch, so both leases kept their expiry. A Topic with the key was found before a `topic-merge` Pin, and a Tag Pin of the same key was not read.
- **Lost-Highlight claim (2026-11-12).** `foreign_key_list` named `highlights` with `ON DELETE CASCADE` for `highlight_id`, deleting a Highlight deleted its row, and the next insert took an id above the old high-water mark. A claim inserted one row for each of three `gone` or `ambiguous` Highlights and none for an `attached` one, a claim 8 days later inserted for a Highlight lost since, an `open` row whose Highlight was `attached` again went with the next claim, and a rejected row was never inserted again.
- **Overview-gap stage (2026-11-12).** The stage's three statements, run in order on a seed of 5 Topics, stored rows for the Topics with uncovered Items and none for a Topic whose open `topic_overview` job closes its gap. A second run in the same week stored nothing because the claim's `changes()` was 0, and after the claim moved back 7 days the run deleted the row of a Topic that was covered and stored the one whose job was gone. ## Runs

The Proposal kinds and Pins were run on 2026-11-11 to 2026-11-13 on both targets: the container (Claude Code 2.1.319, `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`) and `wrangler dev --local --test-scheduled` (wrangler 4.158.0, no model on the Worker). Each migration was run on `node:sqlite` (Node 26.12.1) and on local D1 with identical output once the suffix D1 adds to an error message is removed (Probes). The runs covered the weekly claim, Reject and Accept in the browser, the forward upgrade from the previous release's volume, the rollback to the previous release on the migrated container volume, and the roll forward. The Worker's rollback ran only for the overview-gap Proposals. The runs are scratch runs that are not in the repository, so they cannot be rerun from it.

Findings that shaped the code:

- The overview-gap rollback ran with the release 9817fca (the lost-Highlight Proposals) on a migrated container volume and on a migrated `wrangler dev --local` database. It listed a full page of 50 with the correct `next`, answered 404 for Accept and Reject of an overview row in any state, deleted a Topic with its overview row through the cascade, and rolling forward listed the rows again with no constraint error. A build of a release without `knownProposal` listed the lost rows with no subjects, answered 500 to Accept of one and showed "Couldn’t load proposals". That is the failure `knownProposal` prevents.
- A model run that returned a pair with a current Pin did not happen in three weekly runs, so the store clause that ignores such a pair has no real-model run. `test/disagreement-pin-store.test.ts` covers it and fails when the clause is removed.
- On the container on 2026-11-11, a Tag with 5,100 Items showed "Applying…" after the press, and with the tab closed the sweep finished the merge 35 seconds after the press (the request had moved 5,000 Items). On the container on 2026-11-12, a Topic of 25,001 Items answered 202 after 2,671 ms with 25,000 Items moved, and with the tab closed the sweep finished it 30.4 s after the request. On the Worker (`wrangler dev --local --test-scheduled`, 2026-11-11), a Tag with 5,100 Items answered 202 in 646 ms and finished at the last of 6 scheduled events sent 2 seconds apart (the sweep runs at most once every 30 seconds, `TICK_SPACING_MS` in `src/core/tick.ts`).
- The recovery after `DELETE FROM data_steps WHERE name = 'pin-keys'` merged a recreated Topic of 1,100 Items and 3 Log lines 1.85 s after the container's start command, and a recreated Topic of 600 Items in 341 ms by the Paste that found the step pending (2026-11-12). Its one opening attempt started a chain of 16 `topic_overview` jobs, because one run covers at most 40 Items. On the Worker, one scheduled event merged a Topic of 1,100 Items in 264 ms, and a Topic of 25,101 Items took 221 ms in its scheduled event after 25,000 Items moved in the request (2026-11-12).
- Accept of an overview update on a Topic of 45 Items ran 2 `topic_overview` tasks (executor `cli`, Claude Code 2.1.319), which equals ceil(45 / 40), and left 0 Items out of the overview (2026-11-12).
- With `fillDisagreementInput` and every pair of every Topic decided (60 Topics of 12 Items), the input stayed within the 14,000-byte bound: 47 Items of 4 Topics and 253 pairs in 13,743 bytes with short Items, and 10 Items of 1 Topic and 45 pairs in 13,860 bytes with long Items.

Not run: the Worker's rollback for the weekly Tag check, Accept and Pins, the Topic Pin and Accept of a Topic merge, a Try again button on the old address of a merged-away Topic (the survivor's page had an overview), a deployed Worker, a real Cron Trigger, a Provider other than Claude Code, the first scheduled weekly run on a live Instance, a real phone, the Worker's model path, the Worker's rollback in the browser, the CPU time of a unit on a deployed D1, the quality and cost of the suggestions on a real library (the real runs used planted contradictions in libraries of 8 to 715 Items), Grok Bot, a refusal by the vendor, and the stale and lost-claim orderings of a store batch in a live run (`test/disagreement-store.test.ts` and `test/topic-pins-guard.test.ts` run those conditions against a real database).
