# Proposals

The agent's weekly suggestions to merge two Tags or two Topics, the weekly plain check for Highlights that are no longer found, the weekly plain check for Topics whose overview leaves out Items, the weekly model check for two Items of one Topic whose Summaries disagree, the page that lists every kind, Reject, Accept of either merge and the Pin it leaves, Accept of a lost Highlight, Accept of an overview update, and Accept of a disagreement with the Pin it leaves. The other Proposal kinds are not built. `docs/architecture.md` holds the run, its input and its freshness rule under Jobs, leases and the schedule and AI tasks and Providers; this file holds the rest.

## Code map

A stage's name is its claim name with `-` for `_`.

## The value guard

`proposals.kind` and `proposals.state` have no `CHECK`. `proposals_values_insert` and `proposals_values_update` refuse a kind or state outside `PROPOSAL_KINDS` and `PROPOSAL_STATES`, as `jobs_values` does (`docs/architecture.md`, Database and search, Consistency triggers), so a later kind is a replaced trigger pair and no table rebuild. `proposals_subject_insert` and `proposals_subject_update` hold which columns a kind uses: `tag-merge` needs both Tag ids and no Topic id, `topic-merge` the reverse, `highlight-lost` needs `highlight_id` and no other subject column, and `overview-gap` needs `topic_id` and no other subject column; each earlier kind also refuses `topic_id`, and each merge kind also refuses `highlight_id`. They check only the kinds they know, so an unknown kind is refused by the values pair alone, and the subject rule is no `CHECK` that names kinds, so a kind with other subjects is a replaced trigger pair too, as `migrations/0044_lost-highlight-proposals.sql` did for the third kind and `migrations/0045_overview-gap-proposals.sql` did for the fourth, which also added `topic_id` (`ALTER TABLE ... ADD COLUMN`, `ON DELETE cascade`, a unique index `proposals_overview_topic`). `migrations/0046_disagreement-proposals.sql` did it for the fifth kind, `items-disagree`: `proposals_values_*` and `jobs_values_*` list the new kind and the new job kind `disagreement_proposals`, `proposals_subject_*` hold that the kind needs `from_item_id`, `into_item_id`, `from_digest` and `into_digest` with two different Items and no other subject column, and each earlier kind refuses the four new columns. The migration adds the columns with `ALTER TABLE ... ADD COLUMN` (no rebuild, so the id sequence stays), the Item columns `REFERENCES items(id) ON DELETE cascade` (written by hand, because `drizzle-kit` drops the delete action), the indexes `proposals_from_item` and `proposals_into_item`, the unique index `proposals_item_pair` on the unordered pair (`min` and `max` of the two Item ids), which keeps one row per pair in any state and either order, and the table `topic_checks`. The two `*_digest` columns hold the task ids of the Digests the model judged and have no foreign key, because a Digest row is replaced when an Item is refreshed. The subject of an `overview-gap` row has a column of its own and not `from_topic_id`, because `proposalRelinks` repoints every row whose `from_topic_id` or `into_topic_id` names a merged Topic with no filter on the kind, and a row repointed onto a survivor that already has one would fail the unique index on every key-step run. The columns themselves are nullable because one table holds every kind; `migrations/0041_topic-merge-proposals.sql` rebuilt the table for that, and `0044` added `highlight_id` with `ALTER TABLE ... ADD COLUMN` and a unique index `proposals_highlight`, with no rebuild, so the id sequence stayed (`docs/architecture.md`, Database and search, Migrations). `pins.kind` has the same pair, `pins_values_insert` and `pins_values_update`, from `PIN_KINDS`, and the same subject rule as `proposals`: `pins_subject_insert` and `pins_subject_update` refuse a `tag-merge` Pin without `into_tag_id` or with `into_topic_id`, and the reverse for `topic-merge`, and each of those two kinds also refuses the four columns `0047_disagreement-pins.sql` added. An `items-disagree` Pin needs `from_item_id`, `into_item_id`, `from_digest` and `into_digest` with two different Items and neither `into_tag_id` nor `into_topic_id`. `0047` added the Item columns with `ALTER TABLE ... ADD` (`REFERENCES items(id) ON DELETE cascade`, by hand because `drizzle-kit` drops the action), the plain integers, an index on each Item column (`pins_from_item`, `pins_into_item`; an Item delete looks up the child rows through them, and SQLite scans the whole child table for a foreign key with no index, https://www.sqlite.org/foreignkeys.html#fk_indexes) and replaced the two trigger pairs, with no rebuild, so the id sequence stays. `into_tag_id` is nullable for the same reason as the Proposal columns, and `migrations/0042_topic-merge-pins.sql` rebuilt `pins` for it (`docs/architecture.md`, Data model outline). `test/consistency-triggers-proposals.test.ts` stores and updates each listed value and refuses an unlisted one.

## The read

`GET /api/proposals?cursor=` answers `{ proposals, checkedAt, provider, next }` to the owner's session and to an agent token, and the MCP endpoint gets no tool. It lists `open` and `accepting` rows of every kind, 50 to a page, newest first by `id`, with the Log's cursor rule (the last `id`, a decimal integer of 1 to 16 digits, 400 otherwise). Each row holds `id`, `kind` (`tag-merge`, `topic-merge`, `highlight-lost`, `overview-gap` or `items-disagree`) and `state` (`open` or `accepting`). A merge row has `reason` and `from` and `into`, each `{ id, name, items }` with `items` counted when the call is made: the `item_tags` rows of a Tag, or the Items under a Topic (`items.topic_id`). A `highlight-lost` row has no `reason` and holds `highlight`, `{ id, quote, item: { id, source, title } }`, with `title` read by `itemTitle` as the Highlights page reads it. An `overview-gap` row has no `reason` and holds `topic`, `{ key, name, uncovered, items }`: the Topic's key and name, `uncovered` (its Items with a Digest that `built_from` does not list with that Digest's task id, `uncoveredCount` in `src/core/topic-coverage.ts`) and `items` (its Items with a Digest, `digestedCount`), counted by correlated subqueries of the same statement. An `items-disagree` row has `reason`, `topic`, `{ key, name }` (the Topic of the first Item, read live), and `first` and `second`, each `{ id, title, summary }`: the Item's id, the title and the `summary` of the stored Digest whose task id the row holds (`from_digest`, `into_digest`), so the page shows the text the model judged and not a later one. `pageQuery` is one statement: it joins each merge kind's two sides on its own columns with left joins and `coalesce`, joins `highlights`, `items` and `digests` for a lost row, `topics` for an overview row, and for a disagreement row the two Items, the two Digests by Item id and task id, and the Topic, and names each repeated column. Its `WHERE` holds what makes a row listable, before the page limit, as one table keyed by kind (`LISTED_WHILE`): a merge row is always listed (its two subjects cannot be missing, because the subject triggers require them and the columns cascade on delete), a `highlight-lost` row is listed while its Highlight has a status other than `attached`, an `overview-gap` row is listed while `overviewGap` holds for its Topic (an Item with a Digest outside `built_from` and no `topic_overview` job that is not `done` owned by an Item of the Topic), and an `items-disagree` row is listed while `disagreementHolds` holds: both Items still have the Digest the row names, the two Items are in one Topic and the pair has no current Pin. A hidden row therefore leaves the page full, not short, and the eligibility, the quote, the Item and the title come from one snapshot, because the Node adapter runs each batch in its own transaction and a later read could pair a row with a subject it was not chosen for. The table has an entry for each kind in `PROPOSAL_KINDS` and the `WHERE` names no other, so a row of a kind a later release stored never fills a page, never ends it early and never breaks it. Each row becomes its shape through a second table keyed by kind (`PROPOSAL_OF`), so a new kind adds one entry to each. `checkedAt` is the largest `last_run_at` of the weekly claims in `WEEKLY_TASK` (the Tag, Topic, Highlight, overview and disagreement claims), in milliseconds, or null when none exists, and `provider` is whether a Provider is saved.

## Reject

`POST /api/proposals/{id}/reject` is owner-only (Access). It runs one `UPDATE ... WHERE state = 'open' RETURNING` that moves the row to `rejected`, answers 200 `{ state: "rejected" }`, and reads the row again only when nothing changed: 404 for an unknown id, or for a row of a kind this release does not know, and 409 `not-open` for a row in another state. A rejected row never reaches a later run's input, because the plain check skips every pair that has a row, in either order. There is no undo and no flip of direction. It treats a Topic row, a lost-Highlight row and an overview row like a Tag row, leaves the Highlight of a lost-Highlight row as it is in every column, and leaves the Topic page of an overview row alone. The weekly overview check never inserts a row for a Topic that has one in any state, so a Reject is final for the Topic. A disagreement row is rejected the same way and stays, so the pair is never stored again in either order (`proposals_item_pair`) and is sent to the model as decided. An accepted disagreement row is deleted, and its Pin keeps the pair decided while both Items carry the Digests it was accepted on.

## Accept

`acceptProposal` reads the row's `kind` first, with `knownProposal` in the query, and calls the entry of a table keyed by kind (`ACCEPT`): the merge kinds go to the merge state machine, a `highlight-lost` row to the removal below and an `overview-gap` row to the overview start below, and an `items-disagree` row to the Pin write below. A row of a kind the release does not know is answered 404, checked before anything runs. `readRow` also answers only for a merge kind (`knownProposal` in its query, then `MERGE_KINDS`), so a row of another kind never reaches `MERGES`. A release that rolled back from one that stores a later kind therefore never runs a row it cannot read. The rest of this section is about merges.

**Accept of a lost Highlight.** `acceptLostHighlight` (`src/core/highlight-proposals.ts`) answers 404 for an unknown id (which is also the answer after a successful removal, because the row went with the Highlight), 409 `not-open` for a row in another state, 409 `not-current` when the Highlight exists and is `attached` (the row stays and the list stops showing it), and 200 `{ state: "done" }` once the removal committed. The removal is the two statements of Remove in the Reader (`removalWrites` in `src/core/highlights.ts`, which `removeHighlight` also runs): delete the Highlight's `search_parts` row, then the Highlight, whose cascade deletes the Proposal. They run in one guarded batch (`guardedResults`) that holds only while the row is `open` and its Highlight exists with a status other than `attached`, so a publication that anchors the Highlight again between the read and the batch makes the batch write nothing and the next read answers `not-current`. It takes no lease, ignores `merge-busy` (no kind but the merges uses the `accepting` state), and leaves `continueMerges` alone. An agent token gets 403 (`OWNER_ONLY_PATH` in `src/http/access-rules.ts`). Accept leaves no Pin, because a Pin keeps a correction from being undone by a regeneration and nothing regenerates a Highlight.

**Accept of a disagreement.** `acceptDisagreement` (`src/core/disagreement-accept.ts`) answers 404 for an unknown id (which is also the answer after a successful Accept, because the row is deleted), 409 `not-open` for a row in another state, 409 `not-current` when either Item no longer has the Digest the pair was judged on (`from_digest` and `into_digest` against `digests.task_id`) or the two Items no longer sit under one Topic (`disagreementCurrent`; the row stays, the list hides it and the next weekly stage deletes it when a Digest changed, and keeps it while only the Topics differ), and 200 `{ state: "done" }` once the Pin is stored. It needs no Provider, takes no lease, makes no model call, does not use the `accepting` state and so never meets `merge-busy`. The write is one guarded batch (`guardedResults`) that holds while the row is `open` and `disagreementCurrent` holds, and it holds two statements: the insert of the Pin, and the delete of the row. The Pin insert is an upsert on `(kind, from_key)` with `DO UPDATE ... WHERE NOT currentDisagreementPin`, so a stale Pin of the same pair (its tokens no longer match the Items' Digests) is replaced in place, keeping its id, and a current one stays as it is. That `WHERE` also answers an `open` row whose pair already has a current Pin, which an older release can store (Rollback and roll forward): the batch deletes the row, the Pin stays unchanged and the call answers 200. A guard that fails between the read and the batch makes the call read the row again. The Pin's `from_key` is the pair key `<lowItemId>:<highItemId>` (`pairKey`), its `from_name` the reason as accepted, `from_item_id` and `into_item_id` the lower and the higher Item id, and `from_digest` and `into_digest` the tokens in the same order. An agent token gets 403 (`OWNER_ONLY_PATH` in `src/http/access-rules.ts`). Accept changes neither Item, no Summary and no overview, so the Highlights, Notes and Digests stay as they are.

**Accept of an overview update.** `acceptOverviewGap` (`src/core/overview-accept.ts`) answers 404 for an unknown id (which is also the answer after a successful Accept, because the row is deleted with the run it starts), 409 `not-open` for a row in another state, 409 `no-provider` when no Provider is saved (the row stays open), 409 `not-current` when the Topic has no Item with a Digest outside `built_from` or already has an overview run open (the row stays, the list hides it and the next weekly claim deletes it), and 200 `{ state: "done" }` once the run is started. The start is `startOverview` (`src/core/overview-start.ts`), which Try again on the Topic page also runs: one guarded batch (`guardedWrite`) whose guard holds while a Provider is saved, the Topic has an Item with a Digest and no `topic_overview` job that is not `done` is owned by any Item of the Topic (`hasOpenOverview`). The owner of the new job is chosen inside the batch, as one subquery (`newestOwner`: the Topic's Item with a Digest, newest `saved_at`, then `id`) that the guard and the job insert both use, so they name one Item in one transaction, where a pick before the batch could name an Item that moved to another Topic in between. Accept adds two things to the guard (the row is `open` for this Topic, and the Topic still has an Item the overview was not built from) and one statement right after the job insert: the delete of the row with `WHERE changes() > 0`, which reads the job insert's count. The batch inserts the job first, then deletes the row, then clears the failure marker, so neither changes unless a job was inserted, and the guard makes the insert certain: an open job owned by the chosen owner is an open job owned by an Item of the Topic, which the guard refuses, so the open-job index suppresses nothing. That covers an Item that moved in with a run still open for its old Topic. A failed guard writes nothing. `startOverview` returns one answer (`no-provider`, `no-items`, `open` or `stale`), and Accept adds one read of its row: unknown 404, `not-open`, `no-provider`, and `not-current` for `open`, `no-items` and a `stale` Topic whose gap closed. A `stale` answer with the gap still open starts the call over, which also covers a guard check that failed inside the batch after the Provider came back. The run then wakes the runner (`enqueueRows`). There is no Topic lease (the job takes it when it runs), no `accepting` state and no `merge-busy`. An agent token gets 403.

**Cost of an overview update.** One run reads at most 40 uncovered Items (`ADDED_READ_LIMIT`), fewer when the 14,000-byte cap or an unparsable stored Digest leaves some out, and starts the next run itself after a success until every Item is covered (`continuingOverview`). A failed run takes the refusal path (`src/core/topic-overview-refusal.ts`), writes the failure marker and does not continue, and a Provider removed mid-chain stops the chain. Covering a fixed set of N uncovered Items therefore needs at least ceil(N / 40) successful model calls. Three numbers stay apart: calls attempted, calls that succeeded, and whether coverage completed. The row shows N, so the owner sees the size before pressing. A Topic whose uncovered Items have only unparsable Digests is never covered: its row, once accepted, is proposed again next week unless the owner rejects it, and that is accepted.

`POST /api/proposals/{id}/accept` is owner-only (Access). For a merge it answers 404 for an unknown id, 409 `not-open` for a row in any state but `open`, 409 `merge-busy` while another row of either kind is `accepting`, 409 `topic-busy` for a Topic row whose first unit finds a Topic lease taken (the row stays `open` and nothing changed), 200 `{ state: "done" }` when the merge finished inside the request and 202 `{ state: "accepting" }` when units remain. The sweep ignores a row of an unknown kind, but an unknown row left `accepting` still makes Accept of a known merge row answer `merge-busy`, because that row may be a merge of a later release that is still running. The MCP endpoint has no tool for it. There is no confirmation and no undo, and no screen removes a Pin. One merge of either kind runs at a time, so no two merges touch one Tag or one Topic; a Topic merge also takes the Topic leases (below), because an overview run writes a Topic page apart from any merge.

Call the Tag or Topic that goes `from` and the one that stays `into`. The merge runs in units (`runUnit` in `src/core/merge-accept.ts`), and each unit is one guarded batch (`guardedResults`, which `guardedBatch` wraps, Database and search in `docs/architecture.md`). The two kinds share the guard, the state change, `moved`, the unit revision and the answers, and differ in what a unit plans (`MERGES` in `src/core/merge-kinds.ts`). The Tag unit is described first and the Topic unit after it.

1. The guard. The first unit holds while the row is `open` and no row is `accepting`. A later unit holds while the row is `accepting` at the unit revision it read, so two runners never move the same Items twice or count them twice, even after the cursor goes back to 0. Every unit also holds the row's `from_tag_id` and `into_tag_id` equal to the ids it read, and each of the two Tags' stored `key` equal to the key it read, because a `tag-keys` merge can repoint the ids and its rename can change a key. A unit that loses the guard writes nothing, and the next run reads the row again.
2. The state change to `accepting`, the count, the Pin insert (`ON CONFLICT DO UPDATE` on the unique `(kind, from_key)`, so every unit can carry it and a Pin that already holds the key ends up pointing at `into`; its `from_key` is `catalogKey` of `from`'s name, which is what `pin-keys` computes, so a `from` Tag whose stored key a key step has not yet recomputed still gets the final key) and the repoint of every Pin that targets `from` to `into`. The Pin commits with the first Items, so a Digest that publishes during the merge already lands on `into`.
3. For the next 100 Items that link to `from` (`REWRITE_UNIT_ITEMS`), by ascending Item id after the cursor: the stored Digest of each is rewritten so every Tag name whose `catalogKey` equals `from`'s key becomes `into`'s name, repeats dropped by key with the first place kept, guarded per Digest on `digests.task_id` and the Digest's `tags` still being the ones read (a rewrite keeps the task id, so the Tags are the part of the Digest that a second rewrite changes), and written with `json_set` on `$.tags` alone, so a Topic rewrite of the same Digest between the read and the batch (`pin-keys`) is not undone; the link moves to `into` or is deleted when the Item already has `into` (`tagMoves` in `src/core/catalog-key-links.ts`, which `tag-keys` also uses and which rebuilds the `tags` search part). The links move before the Digests are rewritten, because the link guard reads the Digests as they were read. An Item whose Digest changed between the read and the batch keeps its link and its Digest for a later unit, so a stored Digest never names `from` beside a link to `into`. A stored Digest that does not parse keeps its text, its link still moves, and one `merge-digest-unreadable` line names the Item id; it never stops the merge, because one merge at a time blocks every other accept.
4. The count of Items (`moved`), computed before the link writes from the `item_tags` rows of `from` among the unit's Items whose Digest still matched the read, so an Item deleted or republished between the read and the batch is not counted. Then the cursor and the unit revision plus one.
5. Only when no `item_tags` row for `from` remains: the `merge` Log entry and then the closing writes (`closingWrites` in `src/core/catalog-key-links.ts`, which a Topic merge also uses): one bump of `catalog_version` (so a Digest that read the old Tag list asks again), the delete of the `tag-keys` rows that staged `from` (`data_step_renames`, so a staged survivor never points at a deleted Tag) and the delete of the Tag `from`. The cascade deletes the row and any other Proposal that names `from`. If a link is left, the cursor goes back to 0 and the units continue.

A Tag on 100 Items or fewer therefore merges in one batch that holds the links, the `tags` search part, the stored Digest names, the Pin and the Log entry. `moved` and the Log's count are the Items that carried `from`, including those that already had `into`.

**The Topic unit.** `planTopicUnit` in `src/core/topic-merge-unit.ts` claims both Topic leases before it reads anything, in ascending Topic id (`claimBoth`, holder `topic_merge:<id>:<unit revision>`), so an overview run cannot write either Topic page while a unit reads or writes it, and two jobs that need the same pair claim in one order. A unit holds its leases for its own batch only, and the batch releases them, so an overview run can write a page between two units; the next unit reads the Topic again. The unit is one guarded batch with the same steps as the Tag unit, with these differences:

1. The guard holds the row's `from_topic_id` and `into_topic_id` and each Topic's stored `key` as read, and both leases (`leaseHolds`).
2. The Pin is a `topic-merge` Pin (`into_topic_id`, `from_key` from `catalogKey` of `from`'s name; a Pin that already holds the key is repointed to `into`, as for a Tag), and the repoint covers the Topic Pins that target `from`. It commits with the first Items, so a Digest published during the merge already lands on `into`.
3. The moves are the shared Topic rewrite of `docs/architecture.md` (Catalog keys, `topicMoves`): the next 500 Items under `from` (`MERGE_ITEMS`) and the next 500 Log entries that name it, so a Topic merges in one unit only when both collections fit. The stored Digest's `digests.topic` and the `topic` field of its JSON change by `json_set`, the Items and Log entries move to `into`, and the page and lease of `from` go when nothing names it. `moved` counts the unit's Items that still carried `from` when the batch ran. The cursor stays null, because the next read takes the first Items still linked.
4. The unit revision grows by one, and the batch releases both leases.
5. When no Item and no Log entry names `from`: the `merge-topic` Log entry, then the closing writes (`topicClosingWrites`, `docs/architecture.md`, Catalog keys) in this order: one attempt to open an overview run for `into`, one bump of `catalog_version`, the delete of the `topic-keys` rows that staged `from`, and the delete of `from`, whose cascade removes the row and any other Proposal that names `from`. The row stays until that last statement, because it holds the count the Log entry reads.

**Lease exits.** A claim commits before the batch, so every way out of a unit releases what it took: a second claim that fails or throws releases the first; a unit that throws while it reads releases both; a unit whose guard fails releases both in a separate batch, because the batch rolled back with its releases; and a successful unit releases inside its batch. An unreleased lease blocks the Topic's overview run and every merge that names it for `TOPIC_LEASE_MS` (12 minutes). A first unit that finds a lease taken changes nothing: the row stays `open` and the call answers `topic-busy`, which the page shows as a note beside the row's buttons. A later unit that finds one ends that call and leaves the row `accepting`, and the `merges` stage continues it on the next tick.

**The overview run.** The closing writes try to open one `topic_overview` job for `into` (`continuingOverview`). The attempt inserts a job only when a Provider is saved, `into` has Items its page does not cover, and its owner Item has no open job of that kind, so it can insert nothing while a job for an Item of either Topic already waits; that job then runs for `into`, because a job takes its Topic from its owner Item when it starts. The attempt is not a promise of one job. The cost is a lower bound: one run reads at most 40 Items it was not built from, and the run continues itself until every Item is covered, so N uncovered Items with valid Digests take at least ceil(N / 40) model calls while a Provider stays available. The row shows both Item counts so the owner sees the size before pressing Accept. With no Provider nothing is opened. A survivor page that has overview text marks the moved Items "Not in overview yet"; a survivor with no overview text shows no marker, because the page flags an Item only when the overview has text (`flagged` in `web/src/TopicPage.tsx`). The row's note that the overview is written again later shows only when a Provider is saved.

**Who runs the units.** The accept request runs up to 50 units (`UNITS_PER_ACCEPT`). The `merges` sweep stage (`continueMerges`, after `proposals` in `src/core/sweep.ts`) continues every `accepting` row of either kind with the same bound on each tick, so a closed tab, a crash or an ended Worker invocation finishes by itself. The route and the stage call one function (`continueMerge`), and both pass the job ports (`JobPorts`), because a Topic unit that opens an overview job wakes the runner with `enqueueRows`; a queued row that is not woken is found by the next sweep. A unit that throws a database error ends the call, the stage is logged as `sweep-stage-failed`, and the next tick starts again from the stored row.

**A unit that keeps failing.** A unit that fails on every run leaves the row `accepting`. The page keeps showing "Applying…" with Reject disabled, `merge-busy` refuses every other Accept, and only the server log (`sweep-stage-failed`) shows it. The row has no failure marker, and this risk is accepted: a failed unit writes nothing, so a repair of its cause lets the next tick continue.

**Key steps during a merge.** `tick` runs `migrateData` beside the sweep, so a `tag-keys` or `pin-keys` unit can run between two units, and neither waits for the other. A key merge repoints the `accepting` row's Tag ids (`proposalRelinks`), the next unit reads the new ids and continues onto the survivor. When two rows reach one pair, `accepting` outranks `rejected`, which outranks `open` and `declined`, and the smaller id decides inside a class, so a merge that has moved Items never loses its row to an older Reject. The `pin-keys` step skips the `from` Tag of an `accepting` row, because the Accept's Pin already makes that Tag look like one that holds a Pin's key and the Accept finishes it with its own Log entry. A key merge that makes `from` and `into` one Tag deletes the row: the key step already joined the two Tags, the first unit's Pin already points at the survivor, and no `merge` entry is written. A link that a unit moves onto a Tag that a key step is about to delete is caught by that step's restage check (Catalog keys). An accepted Tag merge changes no Topic, takes no Topic lease and queues no overview run. A stored Digest's own AI task (`ai_tasks.result`) keeps the names it returned, as provenance.

**Bounds.** A unit runs 3 reads and 1 batch (`readRow`, the two reads of `readRewrite` and the batch), which D1 counts as 4 queries because a `db.batch()` counts as one query ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), read 2026-11-12). An accept request runs at most 50 units, so about 200 queries, and `migrateData` stops after 100 units at about 4 queries each, so about 400. Both fit under the 1,000 queries a Workers Paid invocation may make; the queries of the other sweep stages are not counted here. The batch holds a fixed set of statements and one more for each stored Digest it rewrites, so its size follows the unit size. The same page sets no limit on statements per batch, limits each statement to 100,000 bytes and a bound string to 2,000,000 bytes, and gives a batch call 30 seconds. The largest bound string is the JSON of a unit's read state: for each of 100 Items an id, a task id and the Digest's Tags, which are at most 3 names of at most 240 characters (`SHORT_TEXT_MAX`), so at most 3 × 240 × 7 × 100 = 504,000 bytes even when every character is a control character that both JSON layers escape. The unit size of 100 and the unit bound of 50 are chosen numbers, not limits.

**Bounds of a Topic unit.** A Topic unit runs 5 reads (`readRow`, the two lease claims and the two reads of `TOPIC_KIND.linked`) and 1 guarded batch, so 6 queries on D1. An accept request runs at most 50 units, 25,000 Items at `MERGE_ITEMS` = 500, and a counting shim around `node:sqlite` (not D1) measured 304 queries for such a request (254 single, 50 batches; the 4 above 300 are the request's own reads), 3,033 ms, with the 202 answer; a request that ran one unit measured 9 queries, of which 6 are the unit. One tick that runs 50 units of the `merges` stage and a `topic-keys` step with 150 stale keys measured 367 queries and 4,902 ms with the same shim, below the 1,000 queries of a Workers Paid invocation ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/), read 2026-11-12); no query count of a tick was taken on D1, so the whole-tick count is unmeasured there, the other stages of the tick are not in that number, and a tick that finished a one-unit merge ran 50 queries in all. The size 500 and the bound 50 are chosen numbers. Local D1 ran a Topic of 25,101 Items as 50 units of 500 in the request and the other 101 Items in one scheduled event, without error; a deployed D1 was not run, so its CPU time per unit is not measured.

## Pins

A Pin records an accepted merge: the merged-away name's `from_key` and `from_name` as they were and the target's id (`into_tag_id` for a Tag, `into_topic_id` for a Topic, no delete action on either). One Pin exists for a name in each kind (a unique index on `kind` and `from_key`), so a Tag and a Topic can share a key. Accept of a Tag merge writes a Tag Pin and Accept of a Topic merge writes a Topic Pin. A Topic Pin also answers the old address of its Topic (below). Every path that turns a Digest's names into links reads the Pins for the Digest's Tag keys and its Topic key: `publishing` in `src/core/digest-publish.ts` (a model result, a caller-sent Digest and the Digest `items.pending_digest` holds alike) and `linkOlderDigest` in `src/core/older-digests.ts`. A name whose key is pinned becomes the target's name before `catalogEntries` runs, so the Item links to the target, the stored Digest names the target (for a Topic, in `digests.topic` and in the `topic` field of the Digest JSON), the Log entry of the Digest names the target and no `tags` or `topics` row with the pinned key is inserted. The AI task's own result keeps the names the model returned.

Both paths guard their batch on the exact resolution they used: for the Topic key and for each of the Digest's Tag keys, the Pin they found and its target (the token `id:target`), or that no Pin existed (`pinnedDigest` in `src/core/pins.ts`). The guard is separate from the catalog guard, so it holds on every path and at every stale count by construction (`test/topic-pins-wiring.test.ts` shows each path refusing its batch when a Pin appears after the read, and no test runs a model path past `MAX_STALE_REQUEUES`): the model path drops its catalog guard after `MAX_STALE_REQUEUES` and the caller path has none, and the Pin guard inherits neither gap. A publication that loses it is stale and requeues under the existing stale rules, and the next attempt reads the Pins again. `linkOlderDigest` that loses it writes nothing, and the Item stays unlinked for its next pass. It also writes the rewritten Digest, because it links Items whose stored Digest the accept's units did not reach.

**The address of a merged-away Topic.** `topicOfKey` (`src/core/topic-page.ts`) looks a key up in `topics` first, and when no Topic has it, in the `topic-merge` Pins (`from_key` equal to the key), and answers the Pin's target. A Topic with the key always wins over a Pin. `GET /api/topics/{key}` then answers the survivor's page with the survivor's `topic.key`, `POST /api/topics/{key}/overview` acts on the survivor, and a key with no Topic and no Pin answers 404. A Pin is repointed when its target is merged away, so a chain of merges resolves the first address to the last Topic. The Topic page replaces the address with the survivor's path when `topic.key` differs from the requested key (`use-survivor-address.ts` calls `replace`, which calls `history.replaceState`), so a reload and the Back button land on a key that exists and the old address leaves no history entry. The `topic=` filter of `GET /api/items` and the Index do not follow a Pin, because a filter is built from live lists and an address is stored by the owner. A Tag Pin is not read for an address.

**Catalog key steps.** `TAG_KIND.relink` repoints every Pin that targets the losing Tag to the survivor in the unit that deletes it, and `TOPIC_KIND.relink` does the same for the Topic Pins that target the losing Topic. The `pin-keys` step runs after `tag-keys` with `CATALOG_KEY_VERSION` as its version. Its phases are named in its cursor: `keys` recomputes every Pin's `from_key` from `from_name` in one unit (a Pin holds a key of at most `CATALOG_KEY_MAX`, 4,320 code points, and a name of at most 240; the weekly check adds at most 20 rows, so the read of every Pin stays far under D1's result limit; the deletes, the two key updates and the finish guard each take 100 Pins at a time (`PINS_PER_STATEMENT`), so one bound string stays under 100 × 4,320 × 3 bytes = 1,296,000 bytes, below D1's 2,000,000-byte limit; the first update gives each Pin a temporary key that is longer than any key `catalogKey` can return, so no Pin holds it), keeping the smaller id when two Pins reach one key and deleting the other first, because the unique index would refuse it; `merge:<tag>:<item>` merges a Tag whose key equals a Pin's key into the Pin's target with the same bounded rewrite as Accept (`readRewrite`), and leaves the Pin's own target alone; `finish` records the version only in a batch whose guard checks that every Pin key still equals its recomputed key and that no Tag other than a Pin's target holds a Pin's key. When the guard fails, the next run stages again. The merge unit also repoints the Pins and the Proposals of the Tag it deletes.

**The Topic case of `pin-keys`.** After the Tag phase, the cursor `topics` merges a Topic whose key equals a `topic-merge` Pin's key into the Pin's target, one unit at a time, through the shared Topic rewrite (`topicMoves`, `docs/architecture.md`, Catalog keys). It repoints the Proposals and the Topic Pins of the loser first (`proposalRelinks` with the collision priority above, `repointedTopicPins`), and a unit adds the closing writes (`topicClosingWrites`): one bump of `catalog_version`, the delete of the `topic-keys` rows that staged the loser, one attempt to open an overview run for the target and the delete of the loser, each only when no Item and no Log entry names the loser. The step writes no Log entry, no Proposal state and no Topic lease. It leaves the Topic that is the Pin's own target alone and skips the merged-away Topic of an `accepting` Topic row, because the Accept's Pin already makes that Topic look like one that holds a Pin's key and the Accept finishes it with its own Log entry. `finish` checks that no Topic other than a Pin's target holds a Pin's key and goes back to the Topic phase when one does, and the completion batch carries the same check as a guard. The case exists for two causes: a change of `CATALOG_KEY_VERSION` can leave a Topic under a pinned key, and a Digest from an older Worker still in flight after a deploy can create the merged-away Topic again. It is the riskiest and least used part of the Topic Pin, and without it those Topics stay until someone merges them by hand.

**The Pin of a disagreement.** Accept of a disagreement writes an `items-disagree` Pin. It names a pair of Items and not a name, so it reuses two columns that every Pin has and that the table cannot make nullable without a third rebuild of `pins` (`0040` and `0042` rebuilt it): `from_key` holds the pair key `<lowItemId>:<highItemId>`, which the unique index on `(kind, from_key)` turns into one Pin for a pair, and `from_name` holds the agent's reason as the owner accepted it. `from_item_id` and `into_item_id` hold the two Items, and `from_digest` and `into_digest` the task ids of the two Digests the pair was accepted on. Both Item columns are `ON DELETE cascade`, because the Pin is a statement about those two Items, while the two merge kinds name their target with no delete action so that no target can be deleted while pinned.

The Pin is weaker than a merge Pin, and `docs/spec.md` and the **Pin** entry of `GLOSSARY.md` say so. A merge Pin keeps the merged-away key from coming back. This Pin binds the pair to the two Digest versions it was judged on. It survives a regenerated overview, a Topic merge (it names Items and no Topic), a refresh that leaves both Digests alone and a restart. It does not survive a new Digest of either Item, even one with the same Summary text, because the version token changes. The Pin is then *stale*: the Topic page no longer lists the entry, the weekly check judges the pair again (a stale Pin is not in `decided`), and a later Accept replaces the Pin in place. The stale Pin stays in the database until then or until an Item delete removes it, and it hides itself. A pair is *current* when `currentDisagreementPin` holds: a Pin of the kind whose two tokens equal the two Items' stored Digests. Four readers use that one condition: the Topic page (`readDisagreements`), the `decided` list of the weekly check (`decidedPairs`, which reads the rows first and then the Pins, because an Accept deletes the row in the batch that writes the Pin, so one read order cannot miss both), the store of the weekly check (a returned pair with a current Pin inserts no row) and the rule that keeps a row listed (`disagreementHolds` adds that the pair has no current Pin, so the list hides an `open` row of an accepted pair before the page limit and the weekly stage deletes it; a `rejected` row is never touched by it).

**The `pin-keys` kind filter.** The step recomputes every Pin's `from_key` from `catalogKey(from_name)`, which for an `items-disagree` Pin would rewrite the pair key to the key of the reason and could delete the Pin as a duplicate of another Pin with the same reason. Every read of `pins` in `src/core/pin-key-step.ts` (the key recompute, the finish read and the count of the finish guard) names `MERGE_KINDS`, and the reads in `src/core/pin-merge.ts` name the kind they read. `pinsFor` in `src/core/pins.ts` already filters by kind, so a Digest whose Topic or Tag key equals a pair key is not rewritten. `CATALOG_KEY_VERSION` does not change in this release, so the step does not run again on an upgraded database. `test/disagreement-pin-steps.test.ts` clears the stored `data_steps` row, as `test/pins-steps.test.ts` does, and shows both disagreement Pins unchanged, also with the same reason, and the step complete.

**Rollback and roll forward of the disagreement Pin.** The Pins stay in the database. That holds once the `pin-keys` step is recorded complete in `data_steps`, as it is for every database that has run a release with the step. On a database where the step never finished, the older step has no kind filter, reads every Pin and rewrites the pair keys of two Pins to the one key of their reasons, which deletes one of them. The release before this one reads Pins only through `pinsFor`, which filters by kind, so its Digest paths ignore them; its `pin-keys` has no kind filter, so a bump of `CATALOG_KEY_VERSION` in that release would corrupt them, and the version does not change here, so do not change `CATALOG_KEY_VERSION` in a release that predates the filter. Its `GET /api/topics/{key}` has no `disagreements` field, so its client shows no section, and its `deleteItem` deletes an Item that a Pin names through the foreign key's cascade. Its values triggers do not know the kind, so it never writes one. After an Accept the row is gone and only the Pin remembers the pair, and nothing in that release reads the Pin: a Topic that is touched again (an Item arrives) is sent with a `decided` list that lacks the pair, so the model may return it and that release inserts a new `open` row for a pair the owner accepted. Rolling forward needs the reconciliation above and not nothing: the list hides the row at once, the next weekly stage deletes it, an Accept pressed on it answers 200 and deletes it with the Pin kept, and a `rejected` row for any pair stays. Rollback is one release back.

**Rollback and roll forward.** The release before Tag Pins (780bb87) ignores Pins, so a Digest it publishes can create the merged-away Tag again. For a Topic Pin the release before `0042_topic-merge-pins.sql` reads only `tag-merge` Pins, so a seeded Topic Pin does no harm there and a Digest it publishes can create the merged-away Topic again; the same procedure repairs it. Upgrading again does not repair that by itself: `pin-keys` already recorded its version, and the older-Digest linking reads only Items with no Topic. Delete the step's row (`DELETE FROM data_steps WHERE name = 'pin-keys'`, through `wrangler d1 execute` or the container's database). The next start, tick or Paste runs the step again and merges every Tag that holds a Pin's key into the Pin's target, with its links and stored Digests. The same procedure covers Digests an older Worker still in flight writes after a deploy, for Tags and for Topics. Rollback is one release back, to the release that has the Proposals tables and the known-action filter in the Log read. `docs/architecture.md` (CI, releases and rollback) holds the caveat beside the catalog-key one.

**Rollback after an accepted Topic merge.** `0043_merge-topic-log-action.sql` stays in the database. The release before it (the Topic Pin) opens the volume: it serves the Items and the Log without the `merge-topic` line (its Log read selects only the actions it knows), publishes a Digest that names a pinned Topic onto the survivor, deletes an Item, answers 404 for the old Topic address, and refuses Accept of a Topic row with 409 `not-supported`. A Topic row left `accepting` shows "Applying…" there, continues nothing, and blocks Accept of a Tag row with 409 `merge-busy`, with no error line. Rolling forward again lets the `merges` stage finish it.

## The weekly Topic check

The Topic check runs beside the Tag check and shares its code (`proposal-week.ts`, `proposal-input.ts`, `proposal-task.ts`, `proposal-job.ts`). The `topic-proposals` sweep stage, after `proposals`, claims the `scheduled_runs` row `topic_proposals` on the same rule and opens one `topic_proposals` job in its own batch, owned by the same newest Item with a Digest. The two claims are independent: a failing stage or job in one does not skip the other, and the Tag run's batch does not change. `docs/architecture.md` holds the claim, the plain check, the input, the task and its caps under Jobs, leases and the schedule and AI tasks and Providers. A Topic row names no Item, and a Topic with no Item is not sent.

**Topic key step.** `TOPIC_KIND.relink` repoints every row that names the losing Topic to the survivor before the Topic is deleted, by the rule `proposalRelinks` applies to Tags: a row that would pair the survivor with itself is deleted, one of two rows that reach one pair is kept by the priority above, and the rest are repointed. Without this the cascade would delete a Reject and the pair would be proposed again.

## The weekly Highlight check

The `highlight-proposals` sweep stage, after `topic-proposals`, claims the `scheduled_runs` row `highlight_proposals` on the rule of the Tag and Topic claims (no row, a `last_run_at` at least 7 days old, or more than 7 days ahead of the clock) and under the same conditions: a Provider saved and at least one Item with a Digest. The condition is shared so that the page's empty state, which says the weekly check needs a Provider, stays true; the stage needs no Provider for anything else, because it calls no model, makes no `ai_tasks` row and opens no job. `claimingWeek` is the one claim every weekly stage shares. The stage is one `db.batch`:

1. The claim.
2. The insert, with `WHERE changes() > 0` after the claim, so a second tick in the week inserts nothing and a batch that fails spends no week. It takes the 20 newest Highlights (`PROPOSALS_MAX`, by `highlights.id` descending) whose status is not `attached` and that have no `proposals` row in any state, in ascending id order so that the newest Highlight gets the highest row id and lists first, as `open` rows with the fixed reason `plain-check` (the `proposals_open_reason` check needs a reason on an open row, and the API shows none for this kind). `ON CONFLICT DO NOTHING` keeps the unique index `proposals_highlight` from failing the batch.
3. The delete of `open` rows of this kind whose Highlight is `attached` again, after the insert so that `changes()` in the insert still reads the claim's row. It runs only when the `scheduled_runs` row holds this tick's time, because `changes()` there counts the insert, and a tick that lost the claim must delete nothing. A rejected row stays, so Reject is final for that Highlight, even if it is lost a second time.

The check writes only `proposals` rows. Nothing in it updates `highlights.exact`, `prefix`, `suffix`, `hint` or `status`; `src/core/highlight-publish.ts` stays the one writer of `status` and `start`, so a Highlight whose text comes back is `attached` again with no help from a Proposal.

**Unattended path.** A stage that throws before its batch commits logs `sweep-stage-failed`, and the next tick tries again, because the claim did not commit. A batch that commits and whose answer is lost (`docs/architecture.md`, Database and search, Guarded batches) leaves the rows stored and the week claimed, so nothing is lost. The page shows nothing about either.

## The weekly overview check

The `overview-proposals` sweep stage, after `highlight-proposals`, claims the `scheduled_runs` row `overview_proposals` with `claimingWeek` on the rule of the other claims and under the same conditions, a Provider saved and at least one Item with a Digest. The Provider condition is real here, because with no Provider every Item is outside an overview and Accept needs one. The stage calls no model, makes no `ai_tasks` row and opens no job. It is one `db.batch`:

1. The claim.
2. The insert, with `WHERE changes() > 0` after the claim. It takes up to 20 Topics (`PROPOSALS_MAX`) for which `overviewGap` holds (an Item with a Digest that `built_from` does not list with that Digest's task id, which is the predicate the Topic page uses and not `coverageGaps`, because `coverageGaps` also counts removed Items, and no `topic_overview` job that is not `done` owned by an Item of the Topic, because that run and the chain it starts are the cure) and that have no `proposals` row of this kind in any state, so a Reject is final for the Topic. They are chosen by the number of uncovered Items, most first, then by Topic id, and inserted in the reverse order so that the Topic furthest behind gets the highest row id and lists first, as `open` rows with the fixed reason `plain-check`. `ON CONFLICT DO NOTHING` keeps the unique index `proposals_overview_topic` from failing the batch.
3. The delete of `open` rows whose Topic no longer has a gap, only in the tick that won the claim (`claimedAt` in `src/core/weekly-claim.ts`, the condition the lost-Highlight delete uses too), and after the insert so that the insert's `changes()` still reads the claim's row. Between claims the page hides such a row (`overviewGap` in its read) and the row stays, so a row whose Topic has a run open lists again if that run ends and leaves a gap. A rejected row stays. A Topic that falls behind again after its row was deleted is proposed again.

An overview run that failed leaves a failure marker and uncovered Items with no open job, which is exactly a Topic this stage finds. So do Items that arrived while no Provider was saved and Items that a Topic merge moved while no Provider was saved.

**Unattended path.** The same as the Highlight check: a stage that throws before its batch commits logs `sweep-stage-failed` and tries again on the next tick, and a batch that commits with a lost answer leaves the rows stored and the week claimed.

## The weekly disagreement check

The `disagreement-proposals` sweep stage, after `overview-proposals`, claims the `scheduled_runs` row `disagreement_proposals` with `claimingWeek` on the rule of the other claims and under the same conditions (a Provider saved and at least one Item with a Digest), and opens one `disagreement_proposals` job in the same batch, owned by the newest Item with a Digest (`openModelRun` in `src/core/proposal-week.ts`). The same batch holds a second statement after the opening: `staleDisagreements` deletes the `open` rows whose Items no longer both have the Digest the row names and the `open` rows whose pair has a current Pin (a duplicate that an older release stored for an accepted pair goes at once), and it runs only when the claim row holds this tick's time (`claimedAt`), so a tick that lost the claim deletes nothing, except that two ticks with the same millisecond both delete, which is harmless because the rows they delete are stale for both. A `rejected` row is never deleted by it, and neither is an `open` row whose Items merely sit in two Topics. The week ends in the job, `weeklyModelHandler` (`src/core/weekly-model-run.ts`), which the two merge checks also use. This section holds the input, the task, its caps and the freshness rule; `docs/architecture.md` (Jobs, leases and the schedule, and AI tasks and Providers) names the stage and the task.

**Which Topics are read.** A Topic is touched when it has at least 2 Items with a Digest and the text of its membership differs from the text stored for it in `topic_checks`. The membership text (`membersOf`) is `itemId:digestTaskId` for each of the Topic's newest 12 Items with a Digest (newest `saved_at`, then `id`), joined by commas in ascending Item id, built by one `group_concat(... ORDER BY ...)` in SQL (SQLite 3.44 or later: `node:sqlite` is 3.53.3 and local D1 parsed the same text; `sqlite_version()` is not allowed on D1). So a new Item, a deleted Item, an Item that moved Topic and a refreshed Digest inside the newest 12 each make the Topic touched, and a Digest replaced on an older Item does not. The read takes the touched Topics in pages of 20 (`TOPICS_PAGE`), the Topic with the newest Digest `created_at` first, then the lower id, and goes on to the next page until the input has no room for another Topic (`hasNoRoomForAnother`) or no touched Topic is left, so Topics that cannot fit never keep the later ones out. For each Topic it selects only the `title` and `summary` of each Digest (`json_extract`, guarded by `json_valid`), and a Digest with no JSON, no title or no Summary leaves its Item out and logs `topic-digest-unreadable`. `fillDisagreementInput` adds each Topic whole in that order while the whole input stays within 14,000 UTF-8 bytes (`utf8Length`); a Topic that does not fit loses its oldest Items down to 2, and a Topic that cannot fit 2 Items is skipped and stays touched. The model gets each Item's id, title and Summary and a list `decided` of the Item pairs that already have a row in any state or a current Pin (the Pins whose two tokens still equal both Items' Digests; a pair whose Pin is stale is judged again), lower id first, read for the Topics that were read (`decidedPairs`) and printed only for the sent ones. It gets no post text, comment or author.

**The run.** The result is `{ disagreements }`, at most 10 (`DISAGREEMENTS_MAX`), each `{ a, b, reason }`: two different Items that were sent in one Topic, in either order, with no pair twice, and a `reason` of 1 to 160 characters under `plainText`. Zero is valid. One guarded batch stores the result. Its guard holds while the AI task is running and the membership text of every sent Topic, computed again inside the batch, is still the text the run read. It first deletes the `open` rows that no longer match the stored Digests or whose pair has a current Pin (`clearedStaleDisagreements`), so a hidden row of a pair that the run judged again cannot keep the pair's slot in `proposals_item_pair`. It then inserts an `open` row for each pair (`from_item_id` the lower id, with the Digest task ids the run read in `from_digest` and `into_digest`) with `ON CONFLICT DO NOTHING` and a `NOT EXISTS` on the pair's current Pin, so a row that still matches, open or rejected, is kept and a returned pair the owner already accepted stores no row, then upserts `topic_checks` for every sent Topic, including a Topic that produced no pair, and completes the AI task. When the guard fails nothing is written, the task fails as `stale` and the job runs again without spending an attempt. A Topic that was touched but not sent stays touched for next week.

**What hides and deletes a row.** An `open` row stays listed while both Items still have the Digest the row names and are still in one Topic and the pair has no current Pin (`disagreementHolds`, which is `disagreementCurrent` and no `pairPinned`). A refreshed Summary or an Accept that an older release's duplicate row meets hides it at once and the next weekly stage, or the next store of the same pair, deletes it. Two Items in different Topics hide it too, but nothing deletes it: a Topic merge of more than 500 Items commits in units (`MERGE_ITEMS`), so a pair can sit in two Topics between two units, and the row is listed again when the merge ends. A deleted Item takes its rows through `deleteItem` and the cascade on both Item columns. A Topic merge moves both Items to one survivor and leaves the row alone, because the row names no Topic column.

**Cost and budget.** Each attempt makes at most one model call, with SDK retries off. The week opens one job, and error retries and stale reruns add calls. A Topic is judged again only after its membership changed, so a library with no new Items costs no call. The output allowance is 4,096 tokens (`DISAGREEMENT_OUTPUT_TOKENS`, chosen), passed to the executors that take one; Claude Code takes none. A valid answer of 10 pairs with 6-digit ids and 160-character ASCII reasons is 1,979 bytes of JSON (counted with `JSON.stringify`), under the allowance at one token per byte; with 160 CJK characters in each reason it is 5,179 bytes, which can pass it at one token per byte, and a cut-off answer is a refusal that is not retried. The token count of CJK text was not measured. Static bound, at one token per byte against the 24,000-token context of the model of Measured Digest input budget (`docs/architecture.md`): for five inputs filled to within 14,000 bytes (plain English, escape-heavy, CJK, emoji and Turkish; 1 to 3 Topics and 8 to 29 Items, titles of up to 100 characters, Summaries of up to 1,200 characters, the longest the Digest schema allows) the input was 12,806 to 13,838 bytes, the instructions 1,098 bytes and the schema 559 bytes, so input, instructions, schema and allowance came to 18,559 to 19,591, at most 4,409 under the context (measured by building each input with `fillDisagreementInput` and `disagreementTask` and counting the bytes of what they produce; the script is not kept in the repository). Observed on 2026-11-12 with `claude -p --output-format json --json-schema` and the executor's other flags (Claude Code, `claude-sonnet-5-5`, `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token`) on the same five inputs: the usage fields `input_tokens` plus `cache_creation_input_tokens` plus `cache_read_input_tokens` were 6,490 (plain), 9,975 (escape), 6,830 (CJK), 12,121 (emoji) and 8,649 (Turkish), and `output_tokens` was 55 for each, because the inputs repeat one text and the model found no pair. These numbers hold for Claude Code only. They include Claude Code's own system prompt, and the output side of a full answer of 10 pairs is not measured.

**Unattended path.** The same as the other model checks: a stage that throws before its batch commits logs `sweep-stage-failed` and tries again on the next tick, a refusal retries after 30 seconds and 2 minutes, and the last retry closes the job with nothing stored and every `topic_checks` row unchanged, so the Topics that changed are read again next week. The handler takes no Topic lease and no `blockedBy`, because it writes only `proposals` and `topic_checks` rows. When the job fails before a task row exists, one `disagreement-proposals-run-failed` line names the refusal and no `ai_tasks` row is made; a refusal after the task was created leaves the line and the task row with its refusal.

**Rollback.** The release before `0046_disagreement-proposals.sql` opens the migrated database. Its `knownProposal` keeps an `items-disagree` row out of its list read before the page limit, so it lists the earlier kinds in the same order with a full page and a correct `next`, and its Reject and Accept answer 404 for such a row before any merge dispatch. Its `isDue` claims only the kinds in its `JOB_KINDS`, so a queued `disagreement_proposals` job stays queued, and the claim row and `topic_checks` stay untouched. An Item delete there removes the disagreement rows that name the Item through the cascade on both Item columns, which `0046` created. Rolling forward lists the rows again and the queued job runs.

## The Log entry

A `merge` entry (`loggedMerge` in `src/core/log-writes.ts`) holds the two Tag names as written when the merge finishes (`merged_from`, `merged_into`) and the Items that carried the Tag (`moved`). It names no Tag and no Item, so it blocks no delete and survives an Item delete. A line reads `[2026-11-04] merge | tag: <from> into <into> | <n> Items`. A failed unit writes nothing, and the Log has no failure entries.

A `merge-topic` entry, the Log's seventh action, is the same row for a Topic merge (`loggedMerge` takes the action, and `LogEntrySchema`, `entryOf` in `src/core/log-page.ts` and `mergeParts` in `web/src/LogRow.tsx` read both through one `merged` shape). `moved` is the number of Items the units of this Accept moved. A `topic-keys` merge that runs between two units and moves Items of the merged-away Topic first repoints the row to its own survivor, and the Items it moved are not counted in this entry. It names no Topic and no Item, so it blocks no delete and survives a later merge of either Topic. A line reads `[2026-11-04] merge | topic: <from> into <into> | <n> Items`. It is a separate action, not a kind column on `merge`, because the release before it skips an action it does not know, while it would print a Topic merge as `tag:`. Migration `0043_merge-topic-log-action.sql` replaces `log_entries_action_insert` and `log_entries_action_update` with the seven actions and adds no column.

## The reads of the run

`usedSubjects` reads the Tags, or the Topics, that have an Item in pages of 1,000 by id, as a recursion that asks for the page after the last id, because D1 caps one result at 50 MB. `knownPairs` reads every `proposals` row of the run's kind in one query: a row is under 100 bytes and at most 20 rows are added a week, so 50 MB takes about 480 years of weeks (guess).
