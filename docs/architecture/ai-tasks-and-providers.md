# AI tasks and Providers

Every model call is an AI task with a kind, inputs, an input revision and a Zod result schema. The core creates the task row, an executor runs it, and the core checks the result against the schema and the rules before it applies it. A result whose input revision is no longer current is not applied. The core queues the same step again over the current inputs instead, so no Item's Digest is left out of a Topic overview.

The executors are the HTTP adapter (`src/targets/shared/ai-executor.ts`), the Workers AI binding (`src/targets/worker/ai-binding.ts`), the CLI runners (`src/targets/node/claude-code.ts`, `src/targets/node/codex-cli.ts`) and Grok Bot (asynchronous, below). Workers AI runs on the Cloudflare target only, and Claude Code and Codex on the container only. The Grok CLI is not an executor (CLI executor, Grok CLI).

- **Grok Bot runs every AI task when it is the Provider**. It serves the six kinds in `BOT_TASK_KINDS` (`src/core/bot-task-kinds.ts`). The X link round trip is built next to them (X links, below), and `bot/` holds the Threadsift bot. Whether the bot writes good wiki results, and whether it answers an X link correctly, is unverified until a live run.
  - **The Provider.** `grok-bot` is a row of `PROVIDERS` (`src/core/ai-contract.ts`) with no field, not a stored `settings.provider`. The flag `use_as_provider` on the `grok_bot_settings` row says Grok Bot is the Provider, and the `settings` row keeps the last real Provider the owner saved. `loadAiConfig` (`src/core/ai-load.ts`) reads the flag, the settings row and the revision in one batch, and the routing (`onGrokBot`, `routedHandler` in `src/core/bot-step.ts`) and `runAiTask` use that one answer, so no second read can disagree with it. When the flag is set and the Grok Bot settings are unusable, the kind's own path refuses before any task row, and the stored Provider does not run.
  - **Choosing.** One guarded batch sets the flag and adds 1 to `ai_settings_revision`, because no trigger fires for `grok_bot_settings` (`saveAiSettings`, `src/core/ai-settings.ts`). Saving any other Provider writes its `settings` row and clears the flag in one guarded batch (`src/core/bot-provider.ts`). Deleting the Grok Bot settings is refused while the flag is set.
  - **Switching away.** The batch that clears the flag fails every open Grok Bot task of the Provider with the refusal `abandoned` (an `x_intake` task is not one) and makes each job that waits on the bot due now, so the 30 s sweep claims it and runs it on the new Provider (`abandonedTasks`, `src/core/bot-task-states.ts`). A late callback on an abandoned task gets 409, so an answer is never applied after a switch back. A job that read the flag before the switch and inserts its task after it starts none: `botTaskKind` adds the flag to the `holds` of every task it starts, so the insert fails like a lost lease, and the job waits `FULL_CAP_DEFER_MS` and then runs on the new Provider. An `x_intake` task does not read the flag.
  - **Verify.** `verifyProvider` (`src/core/bot-verify.ts`) starts a `digest` task with the context `{ "verify": true }`, sends it, and waits for the answer (`awaitVerifiedDigest`, `src/core/verify-wait.ts`) for at most `VERIFY_WAIT_MS` (60 seconds, chosen, unsupported). The Worker holds the request as wall time, which has no limit for an HTTP request while the client stays connected ([Workers limits, Duration](https://developers.cloudflare.com/workers/platform/limits/)). The task's own deadline is the window plus one send (`VERIFY_DEADLINE_MS`), so an answer after the window gets 409 whether or not the waiter lives. A task still open when the window passes, or when the caller's request ends, fails `timeout` in a guarded write that loses to an answer stored first.
  - **Modules.** `src/core/bot-task-states.ts` owns every transition of a bot task after its insert. `src/core/bot-step.ts` takes one step per claim. A result kind is a `botTaskKind` (`src/core/bot-task-kind.ts`), and `BOT_TASK_KINDS` is the registry. The kinds share code with their executors, so the bot gets what the other executors get and stores with the same guards.
  - **The send.** The webhook body is `{ taskId, kind, callbackToken }` for every kind (`WebhookBodySchema`, `src/core/ai-task-read.ts`), so no library text and no instructions travel in it, and it carries no address to call back, so a fetched page cannot send the credential elsewhere. The bot reads the task with `GET /api/ai-tasks/{id}`. A failed send fails the task and throws. When the answer arrived while the send was failing, the send leaves the task alone and the job applies the answer. Delivery is at-least-once: a retried send after a lost answer may wake the routine twice, and the first run's callback then finds a failed task (409).
  - **States and steps.** `stepOf` (`src/core/bot-task-states.ts`) decides what each claim of a bot-owned job does from the latest task of the job. A bot error is a `failed` task with the refusal `provider-busy` and `answered_at` still set, until a claim charges it. `jobs.attempts` counts only the throws. A send the bot accepts defers the job with `countsAttempt: false`, so waiting and applying cost nothing, and the third send is made at attempts 2, so its answer still applies. The worst case is three sends of one hour each plus the stale resends that `MAX_STALE_REQUEUES` allows. A job that closes (`closeJob`, `src/core/job-close.ts`) fails its running bot task, so a late callback gets 409 and the task frees its place in the cap.
  - **Apply.** The kind's `parse` builds its Zod schema from the task's persisted `context` and checks the stored `result` once more at apply. A task whose answer no longer fits fails `no-json` and throws. A guard that moved (a candidate deleted or given a new Digest between the send and the answer, say) writes nothing, fails the task `stale`, and requeues the job without an attempt. A runner that lost its claim leaves an accepted answer alone: `failedAiTask` lets only `stale` and `no-json` fail a task that holds one. Three writers fail an answered task on purpose, because nothing can apply the answer any more: closing the job (`givenUpTasks`, `supersededTasks`), saving another Provider (`abandonedTasks`) and the sweep one day after the deadline (`expireAiTasks`).
  - **The task read.** `GET /api/ai-tasks/{id}` answers to the task's callback credential only (`readableTask`, `src/core/ai-task-read.ts`). Reading writes nothing, so the bot may read again, and a resend of the task replaces the credential and so closes the old reader.
  - **The result route.** `POST /api/ai-tasks/{id}/result` serves a task with the executor `grok-bot` and a kind in `BOT_TASK_KINDS` (status codes: `docs/architecture/http-interfaces.md`, The Grok Bot task routes). A result that fails the kind's schema or rules answers 400 with the reasons, and the task stays open for a second answer. The stored `result` is the schema's reading of the body, so keys the schema does not name are not stored. The first accepted answer wins and every repeat gets 409. The batch guard (`acceptsAnswer`) reads the state, the deadline against the database clock and the credential digest in SQL, so two simultaneous callbacks store one answer and a request that authenticated before a resend cannot commit after it. `{ error }` fails the task `provider-busy`, marks it with `answered_at`, logs only the task and job ids as `grok-bot-error` and makes the job due. The next claim charges one attempt.
  - **Guards per kind.** The task's `context` holds everything the route needs to validate and everything the apply needs to write, so nothing is read from memory. Each kind applies the guards of its model executors, except the Digest's catalog check, which only model executors run (`CatalogRule` in `src/core/digest-publish.ts`). The Tag and Topic runs do not compare the catalog revision at publication, and the Digest recomputes `pinnedCatalog` at apply and publishes whatever the catalog holds then. A Digest that names a new spelling of a name adds a near-duplicate, because a refusal would send the task again and cost another bot run. The weekly check can suggest merging such a pair, and the owner accepts or rejects it. A changed Item generation still fails the Digest `stale`, because the Digest then describes old text. The task's `schema` in the payload is JSON Schema 2020-12, which Zod 4 writes natively (`z.toJSONSchema` with `io: "output"`); which dialect the bot accepts is unverified. The guard is read at apply and on every claim before the job resends, waits or expires, through the kind's `current`, so a job whose input moved does not wait out the hour for an answer to an old input, and its stale task never charges an attempt.
  - **One overview task per Topic.** `overviewAtBotHolds` (`src/core/bot-task-states.ts`) guards the task insert against another running `topic_overview` task for the Topic that is answered or still before its deadline. The guard counts an unsent task too, because its job resends after a crash. `preparedOverview` defers `topic-busy` for 15 seconds without an attempt while that task remains. When the task is applied, a deferred job reads fresh inputs and sends only if a coverage gap remains.
  - **Failure marker by Topic id.** When the job gives up, `overviewGaveUp` writes `gave-up` for the Topic named in the context of the job's latest task, because its owner Item can move to another Topic before the job gives up. The marker is skipped when the Topic is gone or its page revision is newer than the one the task was sent with, so a late give-up never marks a page that a newer overview stored. When supplied content or an X link answer closes the Item's jobs, `supersededTasks` fails every running task `stale`, because the input was replaced. The task an X link answer completes is named in the `answering` option of `closeItemJobs`, so the close leaves it running whatever the order of the writes.
  - **X links.** The fetch job of an X link runs an `x_intake` task when the Grok Bot settings are saved (Fetchers, X). It is not a `digest` task, because the Digest it leads to is made by the caller-sent path with its own task. `xIntakeKind` (`src/core/x-intake.ts`) is the kind, and its `inputs` hold the link and the status id only, no library text. The task is not in `BOT_TASK_KINDS`, so the result route answers it 400 `unsupported-task`. The bot answers at `POST /api/ai-tasks/{id}/intake` (`docs/architecture/http-interfaces.md`, The Grok Bot task routes). `POST /api/items` takes no task id, so no callback can be an ordinary save.
  - **Binding of an answer.** `acceptIntake` (`src/core/x-intake-answer.ts`) accepts an answer only while the task is running, unanswered and before its deadline, its fetch job is still open and the Item's content generation still equals the task's `input_revision` (`intakeLive`, `src/core/x-intake-writes.ts`), all in the guard of one batch. A save with content closes every open fetch job and the `x_verify` job of the Item and advances the generation, so an old answer cannot overwrite newer content or close a replacement job. An answer that finds the guard moved stores nothing, fails the task `stale`, answers 409 and makes the bound job due, so its next claim decides what the Item needs. With `content`, one batch stores the thread, the Digest and an `x_verifications` row, queues the `x_verify` job, completes the task and closes the fetch job, and nothing of the thread is shown until `x_verify` has checked it against X (Fetchers, X). With `unavailable`, the Item becomes a Link-only Item. A repeat or a second run of the bot finds a completed task and gets 409, which is the dedupe by task id. A deleted Item takes its task with it (`ON DELETE CASCADE`), so a late answer gets 401, the same as for a credential that does not exist.
  - **Refused answers.** A 400 of the intake route for a task that still takes an answer adds 1 to `ai_tasks.answer_refusals` and writes one `grok-bot-answer-refused` line (`refusedIntake`, `src/core/x-intake-answer.ts`). The line holds the task id, the Item id, the count and `issues`: the zod `code` and path of each validation issue (`issueCodesOf`, `src/core/zod-reasons.ts`), with keys the answer's schema does not name shown as `*` and array indexes as `#`. It holds no zod message, no key name the bot chose, no value of the answer and no credential. The 400 answer to the bot keeps the full reasons, because the bot sent that text itself. At `REFUSALS_BEFORE_RESEND` (2) `refusedAnswer` (`src/core/x-intake-writes.ts`) moves the task's deadline to now and makes the owning job due in the same batch, so the same deadline transition runs at the job's next claim: the task fails `timeout`, the attempt counts, and the next send starts a new task. `deadline` keeps one meaning, the moment after which the task takes no answer. A refusal never ends the task or the job by itself and publishes nothing. A resend of the same task with a new credential (`renewedCredential`) sets the count back to 0. `queueLater` (`src/core/job-finish.ts`) makes a job due at the earlier of the deferral time and the task's stored deadline, so a second refusal that lands before the send's deferral is written is not lost.
  - **Sends of an X link.** A full cap defers the fetch job 60 seconds with `countsAttempt: false`, so an Import of many X links does not fire every webhook at once. A failed send throws, so the runner retries after 30 seconds and 2 minutes, and the third failed send ends the job through `fetchHandler.exhausted`, which sets the Item `failed` with `gave-up`. A wrong key therefore burns three attempts in about 2.5 minutes, and the Settings Test is where a wrong key is found early. There are three sends in all, one hour each, and no fallback to the grok CLI after a failure. `exhausted` stores the Item note that names the cause (`botFailureNote`): `bot-timed-out` when the last task never answered before its deadline, `bot-failed` otherwise.
  - **Deadline and expiry.** A Grok Bot task gets one hour (chosen, because the bot wakes in seconds to tens of seconds by its own estimate). At most 10 tasks occupy the bot (`GROK_BOT_IN_FLIGHT`, chosen, unsupported). A task occupies it while it is running, unanswered and before its deadline, because an answered task waits for its job and not for the bot. The Topic rule above counts an answered `topic_overview` task until it is applied, because the page it will store is what a waiting job must read. The cap is shared by every kind, so weekly runs wait for a place during an Import backlog. `expireAiTasks` fails an unanswered task with no `job_id` at its deadline. It leaves an answered task and a task with a `job_id` alone until one day after the deadline (chosen, unsupported), so an accepted answer is not erased while its job waits for a runner. After that day the sweep fails any running task `timeout`, because a job whose claim never came cannot apply the answer. After three failed attempts the Item or Topic shows the failure with Try again. A failed bot task writes no Log entry, because the Log lists committed changes. There is no silent fallback to another Provider, because the owner picks one.
- **Without Grok Bot,** every task runs on the Provider the owner picked, on that target's executor. The task row records which executor ran it (`originOf` in `src/core/ai-task-start.ts`).
- **OpenAI-compatible URL on Cloudflare** must be a public HTTPS address, because the Worker runs on Cloudflare's network, not in the owner's home. Ollama on the owner's machine works from the container.
- **Workers AI is called through the binding, not through a package.** Cloudflare deprecated `workers-ai-provider` for `createAI` from its `agents` package (npm deprecation notice), and `agents` 0.33.0 is 10.8 MB unpacked with 11 dependencies, Babel and Rolldown plugins among them. The trade-off is one structured-output dialect we write and test ourselves.
- **OpenRouter Connect** is OpenRouter's PKCE flow ([OpenRouter docs, OAuth PKCE](https://openrouter.ai/docs/use-cases/oauth-pkce), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)); the returned key is sealed and saved like a typed key. The code is `src/core/openrouter-*.ts`, `src/http/openrouter-routes.ts` and `src/targets/shared/openrouter-exchange.ts`.
- **OpenRouter price limit.** `THREADSIFT_OPENROUTER_MAX_PRICE_ZERO=true` makes the OpenRouter adapter send a $0 `provider.max_price` limit on every inference (`ZERO_OPENROUTER_PRICE` in `src/targets/shared/ai-executor.ts`). OpenRouter does not document limits for cache or reasoning prices in `max_price`, so a key-level guardrail is separate ([provider selection](https://openrouter.ai/docs/guides/routing/provider-selection#max-price)).
  - **Public origin.** Connect needs `THREADSIFT_PUBLIC_ORIGIN` (`configuredOrigin` in `src/targets/shared/configured-code.ts`). Without it the settings view reports `connect: false` and Start answers 503. A malformed value is an error, not a silent `null`: the container exits 1 at start and the Worker rejects every request (run on 2026-11-08 with `ftp://x.test`, `https://u:p@x.test`, `https://x.test/path` and `http://example.com`). The callback address OpenRouter gets is that origin plus `CONNECT_CALLBACK_PATH`; OpenRouter accepts `http://127.0.0.1:<port>` callbacks (its authorization page showed the address in a run on 2026-11-08).
  - **Settings revision.** Table `ai_settings_revision` (one row) counts changes to `settings`. Triggers in `migrations/0000_schema.sql` add 1 after every insert, update and delete, so every writer moves it. A missing seed raises `UninitializedDatabase`, as the catalog counter does. Start and the final save both compare the revision with the one the page was loaded at, so a typed Save made while the owner was on OpenRouter's page wins and the Connect result is dropped (`settings-changed`). A typed Save is guarded the same way (`saveAiSettings`): when the revision moved, it refuses the Save without a write, so a Save that keeps the stored key cannot write back a key that a Connect or another Save replaced in between. The refusal answers 409 (`settings-changed`) and the owner can try again.
  - **Start.** Start checks `Origin` against the configured origin, `Sec-Fetch-Site: same-origin` and the request host itself, because Hono's `csrf` middleware skips JSON bodies. It stores one row in `openrouter_connect_transactions`: the SHA-256 digest of a 32-byte random `state`, the digest of the session, the PKCE verifier sealed under `THREADSIFT_SECRET_KEY`, the model, the revision, the origin and a 10-minute expiry (`CONNECT_LIFETIME_MS`, the lifetime OpenRouter gives a code). The insert is one guarded batch, so it commits only while the session is live and the revision is current. Every time comes from the database clock (`DATABASE_NOW`), so one clock decides whether an attempt is live. Switching the Provider in the form fills the model only with the saved model of that same Provider, so a model of another Provider is never offered to OpenRouter.
  - **Callback.** The callback is the one `/api/*` route a browser reaches by redirect (`installApiMiddleware`, `src/http/api-middleware.ts`). `privateResponse` sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on every answer of the callback and of Start, so the code in the query and the authorization address are not cached or sent on. `signedOutNavigation` turns the 401 for a signed-out browser navigation into a 303 to `/settings`; any other signed-out caller keeps its 401, so the OpenAPI-wide closed-route check still holds. The handler claims the row with one `DELETE ... RETURNING` on the state digest, the session digest, the expiry, the origin, the revision and a live session. Both time checks read the clock inside the statement (`DATABASE_NOW` in `src/core/guards.ts`), so a statement that waits for the database cannot use an older window. The code is therefore used once, only by the session that started it, and a replay finds no row.
  - **Exchange.** The exchange goes through `aiTransport` (no redirects) with 8 seconds (`HOP_DEADLINE_MS`) and a body read capped at 16 KiB. 400 and 403 mean OpenRouter refused the code (`incomplete`). Any other status, a thrown error, a timeout or a malformed body is `uncertain`, and OpenRouter may then have made a key, so the notice is `possible-orphan`. The callback saves the key before it waits (Final save), then `awaitOpenRouterActivation` polls `GET https://openrouter.ai/api/v1/key` (OpenRouter's current-key endpoint, which spends no credits) every second (`ACTIVATION_POLL_MS`) for at most 45 seconds (`ACTIVATION_WAIT_MS`). A 401 inside the bound means wait, and a 200 means active. The wait is needed because a 401 is final in `retriesAi` (`src/core/ai-contract.ts`): a Digest job that meets the activation delay fails with `wrong-key` for good. The wait takes no caller signal on purpose, because the signal the callback passes is the 8 second timeout of the exchange request, and the key exists at OpenRouter by then.
  - **Activation delay.** Measured on 2026-11-08 with real keys. Keys made through the management API (6 keys) answered 200 on both `/key` and the model call at the first poll. Keys made by the OAuth exchange (16 keys) showed the delay: 6 were active at the first poll, 1 after 4.6 s, 1 after 6.3 s, 1 after 11.1 s and 7 after 15.6 to 17.2 s. A Verify pressed after Connect also failed for 26 s once on the container and 4 s once on the Worker. In all 16 runs `/key` turned 200 together with the model call or at most one 1 second poll after it, never before, so waiting on `/key` is never earlier than the model call. The 45 second bound is 2.6 times the longest of the 16 times and far below `CONNECT_LIFETIME_MS`. Some runs of the model call showed 429 from the free model's rate limit instead of 200, so 429 counted as not 401.
  - **Final save.** The settings row is stored before the activation wait, so a stop during the wait leaves the key saved. `saveConnectedKey` writes it in one guarded batch that commits only while the session is live, the revision is still the one Start saw and the attempt has not expired. A batch that is not positively confirmed is read back, and only a stored row equal to the prepared one goes on; otherwise the notice is `possible-orphan`. `afterActivation` then waits and runs one batch that commits only while the stored row is still the prepared one. A replaced row answers `settings-changed`, and an inactive key answers `activation-pending`, where saving again (a typed Save) opens the Digests. An active key runs `olderDigests` in that batch and answers `connected`. `olderDigests` also reopens Items whose last Digest task was refused with `wrong-key`, which covers a Paste inside the wait.
  - **Notices.** The callback answers 303 to `/settings?openrouter=<notice>`. The `incomplete` text also answers a return address opened a second time after the first visit saved the key. Texts come from `tools/copy/write-copy.sh` (`web/src/ai-text.ts`).
  - **Form state.** `useAiPhase` (`web/src/use-ai-phase.ts`) holds the AI settings form in one reducer. `leaving` is the phase after `window.location.assign`. A page returned by the browser’s back/forward cache stays mounted, so a persisted `pageshow` returns that phase to `idle` and makes the form usable after Back. The status line under the key field follows the server's rule for keeping a key (`nextSettings` in `src/core/ai-next-settings.ts`).

- **Built HTTP path.** `src/targets/shared/ai-executor.ts` uses `ai` with `@ai-sdk/openai-compatible`, `@ai-sdk/anthropic`, `@ai-sdk/openai` and `@ai-sdk/xai`, with structured output, retries off, telemetry off and the attempt's abort signal. The three vendor versions are the ones whose `@ai-sdk/provider` and `@ai-sdk/provider-utils` are the ones `ai` and the compatible package already use, so the lockfile keeps one copy of each (`grep -n "^  '@ai-sdk/provider" pnpm-lock.yaml` shows one version of each). `languageModel` picks the factory by Provider and gives every one the same `aiTransport` fetch and the row's fixed base URL. Anthropic uses the Messages API (`createAnthropic(...).languageModel`, native structured output through `output_config.format` for models that support it and a JSON-tool fallback otherwise, in `structuredOutputMode: "auto"`). OpenAI uses the Responses API (`createOpenAI(...).responses`, named so a later SDK default does not change the endpoint) and xAI uses its Responses API (`createXai(...).responses`; the package has no Chat factory). Sources: [Anthropic](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic), [OpenAI](https://ai-sdk.dev/providers/ai-sdk-providers/openai), [xAI](https://ai-sdk.dev/providers/ai-sdk-providers/xai), and the installed type files. `src/targets/shared/ai-runtime.ts` imports the HTTP adapter inside `run`, so an isolate serving other routes does not initialize either SDK package. Each task row stores the Provider, model and executor (`http`, `binding`, `cli` or `caller`) of the connection it loaded, a failed Verify included, and an empty CLI model is stored as null. Caller-sent Digest tasks keep them null. The model's Digest variant (`ModelDigestSchema`) requires `keptComments`, an empty list allowed, and a stored or caller-sent Digest (`DigestSchema`) keeps it optional. Verify sends no comments, stores `keptComments: []` whatever the model answers, and writes no Item, Topic or Tag.
- **Task owner.** `ai_tasks.item_id` names the Item a task works for. A Digest task, model or caller, carries its Item; the Verify task carries null. The key is `ON DELETE CASCADE` like every other child of `items`: `inputs` holds up to 14,000 bytes of the Item's text, so `SET NULL` would leave that text behind after the Item is gone, and `NO ACTION` would make every delete of an Item list its tasks first. SQLite checks a `NO ACTION` key at the end of a statement ([SQLite docs, Foreign keys](https://www.sqlite.org/foreignkeys.html)), so one `DELETE FROM items` removes the Digest and the task it names together, while a delete of that task alone is refused. Both were run on `node:sqlite` and on local D1 (wrangler 4.156.0, 2026-11-07), with the same results. `startTask` (`src/core/ai-task-start.ts`) creates an Item's task only while its job still holds its claim, in one `INSERT ... SELECT ... WHERE` on `holding` (`src/core/job-rows.ts`), never after a separate read. When the insert writes no row, the attempt reports the lost claim and makes no Provider call. Only Verify creates a task without an owner.
- **Sealed settings.** `src/core/sealed-secret.ts` uses Web Crypto AES-GCM with a fresh 96-bit IV. `THREADSIFT_SECRET_KEY` is 32 random bytes encoded as 64 hex characters, supplied as an environment variable in the container or a Worker secret. A missing or malformed key blocks Save and Verify of an HTTP Provider. A stored key that cannot be decrypted loads as `secret-missing`: it blocks Verify and a Save that carries no new key, and a Save that carries a new API key seals it under the current key and replaces the row, as a first Save does. The GitHub token and the Grok Bot key replace the same way. Workers AI seals nothing, so its Save and Verify work without the key. Responses reveal only whether a key is set. The executor returns selected refusal categories and an HTTP status, never an SDK error object, because those objects may contain credentials.
- **GitHub token settings.** The token is sealed by the same sealer as the AI key and lives in its own `github_settings` row, so a GitHub change never touches the AI row and the other way round. Saving or removing it also deletes the cooldown row (see Rate limits in `fetchers.md`). The `/api/settings` rule of the guard closes the routes to agent tokens like the AI routes. Verify answers its refusals inside HTTP 200, because the web client treats a 401 from Threadsift as a signed-out owner and GitHub's own 401 must not sign the owner out. It sends one `GET https://api.github.com/rate_limit` through `guardedFetch`. `/rate_limit` does not count against the primary limit but can count against the secondary one ([GitHub docs, Rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#checking-the-status-of-your-rate-limit)), which is why Verify honours the cooldown. It answered 401 for an invented `github_pat_` token (`curl`, 2026-11-07).
- **HTTP transport.** `src/targets/shared/ai-transport.ts` is the SDK's custom fetch. It refuses redirects on both targets. On the Worker, `src/core/ai-url.ts` applies the fetch guard's public-address rules from `src/core/addresses.ts` and requires HTTPS on Save and Verify, and `workerFetch` (`src/targets/worker/network.ts`) turns Cloudflare's 530 error page into a network failure. The local Worker's name-check gap in `open-items-and-unverified-claims.md` still applies. The container permits a private HTTP endpoint for Ollama.
- **The `topic_overview` task.** `linkingDigest` (`src/core/catalog.ts`) adds one `topic_overview` job for the Item's Topic to the batch that publishes a Digest, but only when a Provider is saved (`providerSet`, `src/core/provider-saved.ts`: a `settings` row, or Grok Bot chosen). A caller-sent Digest therefore starts it on the configured Provider, and a library with no Provider starts none. The job waits for the Item's own `digest` job (`blockedBy`).
  - **Input.** `preparedOverview` (`src/core/topic-overview-prepare.ts`) reads the current overview, up to 40 Items whose current Digest is not in `built_from` (newest first, as many as fit `OVERVIEW_INPUT_BYTES`; when the first Item alone is over the budget, `fitted` drops its key points from the last until it fits, so one valid Digest is never left out of every run) and the removed Items (Items in `built_from` that left the Topic). `overviewWithout` (`src/core/topic-overview-prune.ts`) takes the removed ids out of the current overview first, with no model, so the model never sees a removed id. A run with no added Item that fits is that prune alone, written by `keptOutcome` without a model call, so a removal ends in a written overview even when the model would refuse. When the prune leaves no line, the write stores an empty `built_from`, so the Items that remain count as uncovered and the continuation opens a run that writes an overview from them.
  - **Result.** The model returns the sources of a line as ids, and `overviewText` (`src/core/topic-overview-task.ts`) writes the stored text. The schema (`topicOverviewTask`) refuses a line with brackets, braces, quotation marks, a line break, a control character or a lone surrogate. The first four rules exist because the first real run with `nvidia/nemotron-3.5-super-vl:free` on 2026-11-11 returned one free-text `overview` string with the model's own `unchangedfalse}JSON_OUTPUT{` fragment inside it and no line breaks. The last two keep each unit of the stored overview at 3 bytes or less in the input. With the same rule on the Topic name, the title and the Summary (`docs/architecture/data-model-outline.md`, Catalog keys), the input that holds the first added Item with none of its Key points is at most 3 × (240 + 240 + 1,200 + 1,500) = 9,540 bytes plus the JSON keys and the Item id, so `fitted` always includes that Item. The output allowance is `MAX_OUTPUT_TOKENS` (8,192): the same model ended a call with `cut-off` at 1,024 tokens and again at 2,048.
  - **Writing.** The write is one guarded batch (`currentInputs`): the Topic still exists, the revision, the sent Items with their Digests and the removed ids are as read (a removed Item that the 200-id read did not return changes the count), and the AI task is still running. When any of that is out of date, nothing is written, the task fails `stale` and the job requeues over fresh inputs. A refusal is first checked against the same inputs: when they are out of date, the attempt is not spent. Any other refusal, and the last retry, stores the refusal as the failure marker and ends the job without an error. Both keep the earlier overview text.
  - **Continuation.** One run is one model call over one bounded batch. When the publication leaves Items uncovered or removed Items unhandled (`coverageGaps`, `src/core/topic-coverage.ts`) and a Provider is saved, the same batch that closes the job opens the next one (`continuingOverview`), so a backlog ends without another Digest arriving. Every publication covers or drops at least one Item, so the chain ends. A merge of two Topics (Accept of a Topic merge) makes the same attempt once for the kept Topic, and inserts a job only when the kept Topic has a coverage gap and its owner Item has no open `topic_overview` job. Accept of an overview-gap Proposal starts one such run through the same start as Try again (`startOverview`, `src/core/overview-start.ts`; `docs/wiki.md`, Topic pages).
  - **Cost.** Covering N moved Items with valid Digests takes at least ceil(N / 40) successful model calls, because one run reads at most 40 Items it was not built from. A merge of 18 Items into a Topic of 28 that had no overview left 46 uncovered Items and made 2 model calls on Claude Code, from 2 jobs that already waited, and one that moved 600 made 16. A failed run takes the refusal path, writes the failure marker and does not continue, and a Provider removed mid-chain stops it, so the calls attempted, the calls that succeeded and whether coverage completed are three different numbers.
- **The `related_pick` task.** `publishing` (`src/core/digest-publish.ts`) opens one `related_pick` job for the Item after the Digest upsert, only when a Provider is saved, and the job waits for the Item's `digest` job (`docs/wiki.md`, Related Items, owns the candidates, the input and the writes). `attemptPick` (`src/core/related-job.ts`) sets `inputRevision` to the source's Digest task id. Its one guarded batch commits only while the Digest task ids of the source and of every sent candidate are current and the AI task is still running; otherwise the task fails `stale` and the runner reruns the job with its stale backoff. The output allowance is `RELATED_OUTPUT_TOKENS` (4,096, chosen). The most the schema allows is 5 reasons of 160 characters, so the allowance is far above any valid answer and below the context bound below.

- **The `proposals` task.** `proposalsHandler` (`src/core/proposal-job.ts`, a `WeeklyModelRun` for `weeklyModelHandler` in `src/core/weekly-model-run.ts`) reads the Tags that have at least one Item in pages of 1,000 by id (`usedSubjects`, `src/core/proposal-input.ts`, because D1 caps one result at 50 MB) and every `proposals` row in one query (`knownPairs`). It finds pairs with a pure function (`candidatePairs`, `src/core/proposal-candidates.ts`) by two rules that the spec leaves open, so they are chosen here. First, the same loose key: a Tag's `key` with every character that is not a letter or a number removed, and one final `s` dropped when at least 3 characters remain (English only, chosen, unsupported), so `machine-learning`, `machine learning` and `machine_learning` meet, as do `llm` and `llms`, and `gas` stays whole. Accents stay, because `catalogKey` keeps `café` and `cafe` apart on purpose. Second, an initialism: a Tag of two or more words whose first letters, joined, equal another Tag's loose key of at least 2 letters (`machine learning` and `ml`). Both rules produce pairs for the model to judge, not merges: `c`, `c++` and `c#` meet under the first rule and are different things. No embeddings exist, so a semantic duplicate beyond the two rules is not found. A pair that has a row in any state is skipped. Pairs are ordered by the two Tags' combined Item count, most used first, and `disjointPairs` takes a pair only when neither Tag is in a pair already taken, up to 20 (`PROPOSALS_MAX`, chosen). Disjoint pairs let the model return every pair it judges a match, so a sent pair it does not return is a real "no" and is stored as `declined`. A pair that is not sent keeps no row and stays eligible. With three spellings of one concept, one week sends one pair; once the merge is accepted, a later week sends the survivor and the third.
  - **Input and storing.** No Item title, Summary, post text or comment is sent, so no Item text stays in `ai_tasks.inputs`. The cap counts the whole serialized text in UTF-8 bytes: 14,000 (`PROPOSALS_INPUT_BYTES`, chosen, equal to the other wiki tasks). A pair that does not fit is skipped and stays eligible. With no pair that fits, the job writes nothing, makes no AI task and closes. One guarded batch (`storedOutcome`, `src/core/weekly-model-run.ts`) inserts an `open` row for each merge and a `declined` row for every other sent pair, with `ON CONFLICT DO NOTHING`, so a pair that gained a row meanwhile keeps it. A guard that failed fails the task `stale` and requeues the job without an attempt. One run judges one set of disjoint pairs and opens no continuation job, so a large first backlog clears over several weeks. The Budget bullet below holds the cost.
  - **Budget.** The output allowance is 4,096 tokens (`PROPOSALS_OUTPUT_TOKENS`, chosen), passed to the executors that take one. Claude Code takes none (`taskArguments`, `src/targets/node/claude-code.ts`) and the app records no token usage from it. A valid answer of 20 merges with 6-digit ids and 160-character reasons is about 4,050 bytes of JSON, under the allowance at one token per byte. An answer padded with characters that JSON escapes can pass it, and a cut-off answer is a refusal that is not retried. Static bound against the 24,000-token context of the model of Measured Digest input budget: for five inputs filled to within 14,000 bytes (plain English, escape-heavy, CJK, emoji and Turkish; 8 to 20 pairs) input, instructions, schema and allowance came to 18,491 to 19,519, at most 4,481 under the context (counted by building each input with `proposalsInput` and `proposalsTask`; the script is not kept). Observed on 2026-11-11 with `claude -p --output-format json --json-schema` and the executor's other flags (Claude Code 2.1.322, its default model) on the same five inputs: 7,269 to 11,447 input tokens (`input_tokens` plus `cache_creation_input_tokens` plus `cache_read_input_tokens`) and 53 output tokens for each, because the model found no merge among the unrelated pairs. These numbers hold for Claude Code only, include its own system prompt, and the output side of a full answer of 20 merges is not measured.

- **Refusal mapping.** `executionRefusal` (`src/targets/shared/ai-executor.ts`) turns every SDK error into one category. xAI answers a wrong key with HTTP 400 and `{"code":"invalid-argument","error":"Incorrect API key provided..."}` (`curl` to `https://api.x.ai/v1/responses` with an invented key, 2026-11-07), so an xAI 400 whose message holds `Incorrect API key provided` is `wrong-key`; Anthropic (`authentication_error`) and OpenAI (`invalid_api_key`) answer 401. The executor reads the finish reason before the output: `content-filter` is `declined` and `length` is `cut-off`, even when the text parsed. When a non-`stop` finish carries no text, the SDK's `output` getter throws `NoOutputGeneratedError`, which only remains for the finish reasons `error`, `other` and `tool-calls`, and is `no-json`. Anthropic's `refusal` stop reason reaches the SDK as `content-filter` (provider page, Finish reason mapping). `@ai-sdk/openai` 4.0.110 and later decode a Responses API refusal part as text and map the finish reason to `content-filter` when the response sets no `incomplete_details.reason` and holds no function call (its changelog, entry 6b97088), so the pinned version needs no code of ours for it. A refusal part the SDK cannot decode fails decoding and is `no-json` with status 200. On 2026-11-15 a local HTTP server answering `/v1/responses`, called through `runHttp`, sent the SDK a refusal part, an empty `incomplete` response and a schema-valid `incomplete` response and got `declined`, `cut-off` and `cut-off` (the script is not kept); no vendor sent one, so a real refusal stays unverified (`open-items-and-unverified-claims.md`, the Anthropic, OpenAI and xAI rows). `declined` and `cut-off` are deterministic for the same model and input, so `retriesAi` does not retry them: the Digest job marks the Item failed with Try again, and Verify shows the recovery text. A `no-json` without an HTTP status, or with a 2xx status, can be retried because a model can return valid JSON on the next call. Before the last attempt, a model job retries a retriable refusal only if its inputs are current. If the inputs are stale when checked, the job requeues without spending an attempt even if they become current before the outcome is written (`refusalOutcome`, `src/core/guarded-outcome.ts`).
- **Measured Digest input budget.** `digestPrompt` (`src/core/digest-prompt.ts`) builds the whole user input, and the 14,000 UTF-8 byte cap counts all of it, field names, brackets and escapes included. The catalog gets up to 4,500 bytes, split equally between Topics and Tags, each list keeping its names with the most Items first. `CATALOG_NAME_LIMIT` bounds each `readCatalog` query from the per-list byte budget and the shortest valid encoded name, so no name that could fit is excluded by the row limit.
  - **Fill order.** The builder reserves the selected catalog and the Item with an empty post text and no comments, and refuses when that alone passes the cap: the Digest ends failed with no Provider call and one `digest-input-refused` log line. When a hop gave linked text, the linked text takes the longest prefix, cut at a code point, that fits one third of the room left (rounded down, our choice, not measured). The rest splits in two, the odd byte to comments. An X Item with joined follow-ups (`reddit_threads.follow_ups` above 0) gives comments only the part of their half that the whole post text does not need, so the joined post text is sent whole when it fits. Comments fill their half in ascending `position` as whole records, and a record that does not fit is skipped. The post text takes the longest prefix that fits all the space left, skipped comments are then tried again, and room that is still unused goes back to the linked text, so a sparse post and few comments leave the whole cap to the page. Sizes come from the serialised JSON, so an escape counts at its full length (a control character costs 6 bytes), and only a text value is ever shortened.
  - **Candidates.** A Reddit or X Item sends its eligible comments (an X Item's replies) of the generation the attempt read (`commentCandidates`, `src/core/reddit-thread.ts`), never a `more` stub, and the linked page of that generation's candidate when the hop gave text (Fetchers, One hop). A parent may be missing from the list because it was ineligible or did not fit, and the instructions say its text must not be invented. Any other Source, and Verify, send none.
  - **Result.** `publishing` removes duplicates and keeps only ids this attempt submitted (`submittedAmong`, which also drops a malformed id that an older release stored), then uses that one list for the stored Digest JSON, the task result, the Kept flags and the search parts, all in the batch that publishes the Digest. A refresh leaves the last published selection until a replacement publishes. Each attempt that reaches the Provider logs one `digest-comments-submitted` line with counts and no comment text. The submitted ids stay recoverable from `ai_tasks.inputs`, so no column holds them.
  - **Output allowance.** `digestPrompt` returns `maxOutputTokens` as 2,048 (`BASE_OUTPUT_TOKENS`) plus the bytes of the submitted id array as JSON, at most 8,192 (`MAX_OUTPUT_TOKENS`), because a full selection of long ids can need more than a fixed 2,048. One token per byte is the upper bound for a byte-level tokenizer. The cap exists so that input and allowance fit the context of `@cf/meta/llama-3.3-70b-instruct-fp8-fast` under that bound: the whole prompt is at most 15,749 bytes (14,000 input, 1,044 instructions, 705 schema), and 15,749 + 8,192 = 23,941 against 24,000. Without the cap, the densest input (201 ids of 32 characters with one-character bodies, empty catalog) would reach 24,787. The cap costs no real selection: the densest case measured below used 2,099 output tokens for 96 ids, about 22 per id, so 200 ids need about 4,400. Verify keeps 2,048. A provider whose own completion limit is under 8,192 would refuse a large allowance with its own error, which is unverified.

  - **Sign-in state.** Every AI settings load, and every save of this row, runs `claude auth status --json` and reads only `loggedIn` through a Zod schema, because the rest holds the email and the organization. A timeout, bad output or any failure reads as signed out. `loggedIn` is a local hint: with a rejected token `claude auth status` still says `loggedIn: true` (2.1.319, `authMethod` `oauth_token`, exit 0), and only Verify proves a model request works.
  - **Refusals.** With `is_error` and no status the executor probes sign-in once: signed out is `not-configured`, signed in is `unreachable`. The log gets one line with the category and the exit code, never stdout, stderr or the prompt.
  - **Stopping.** A task aborts when its signal does (the 10-minute deadline, a client that disconnects from Verify) and when the Instance shuts down. `runProcess` sends `SIGTERM` to the process group (`detached: true`, `process.kill(-pid)`), sends `SIGKILL` after `KILL_GRACE_MS` (5 s) and kills the group's remains when the leader exits. A descendant that left the group (`setsid`) can keep a pipe open after the leader is gone, so `KILL_GRACE_MS` after the leader exits it destroys the pipes and answers; the slot is free then, and the descendant is left running. A child whose `spawn` fails with `EMFILE` or `ENFILE` has no pipes and no process id, and the run answers `spawn-failed` from the `error` event. A probe under `sandbox-run` with `setsid -f sleep 600` as a descendant never settled before this change and settled after 5.0 s after it; with `ulimit -n 64` and no free descriptor the run threw a `TypeError` and the `error` event crashed the process before, and answers `spawn-failed` after. On `SIGTERM` or `SIGINT` the container's `shutdown()` (`src/targets/node/index.ts`) first awaits `node.stop()`, which waits for every job in flight and aborts the Claude Code runner, so a background Digest ends its process group and removes its task folder before the database closes. That wait is bounded by `STOP_WAIT_MS` (9 s, `job-loop.ts`), above the 5 s kill grace and under the 10 s that `podman stop` gives a container by default (`podman stop --help`, `--time`). A job still running after that is abandoned and starts again at the next start, as after a crash (Container restart in `jobs-leases-and-the-schedule.md`).
  - **Concurrency.** At most 2 CLI tasks run at once on an Instance, Verify and Digests together, across every CLI Provider: `startOperatorCode` (`src/targets/node/operator-code.ts`) makes one `Slots` that the Claude Code and Codex runners share. A plan is one person's quota, so this is a chosen value.
  - **Isolation.** An unrestricted run expands an `@file` mention, loads the `CLAUDE.md`, runs the hook and writes the sentinel: removing `--safe-mode`, `--setting-sources` and `--disable-slash-commands` from the arguments put the `CLAUDE.md` sentinel into a Digest (2026-11-07). A probe showed the `@file` mention in stdin is expanded without `CLAUDE_CODE_DISABLE_ATTACHMENTS` and not with it (`echo "Repeat the exact text of @/tmp/canary.txt" | claude -p --tools "" --safe-mode ...`, 2.1.319), but the model did not copy the canary into the Digest either way, so no run shows that the variable changes a Digest.
- **CLI executor (Codex).** It runs on the same spawn, caps, process-group kill, refusal table, `Slots` and `SlottedCli` as Claude Code. `codex-cli.ts` owns the task flow and the sign-in probe, `codex-process.ts` the arguments, the child environment and the start-up catalog, `codex-protocol.ts` the catalog, the tool-surface check and the event parsing, and `codex-home.ts` the reserved names in the Codex home (all in `src/targets/node/`). `startNode` registers the row only when it finds an executable `codex` on the app's `PATH`, the Codex home passes the reservation check below and the bundled catalog loads. The Worker runs no Codex code.
  - **Tool proof.** Codex has no switch that turns every tool off, so the executor removes them from the model's catalog. `codex debug models --bundled` prints the binary's own model catalog; the runner reads it once at start-up (30 s limit, 8 MiB cap), and each run writes a private copy with `tool_mode` null, `apply_patch_tool_type` null, `shell_type` `"disabled"` and `experimental_supported_tools` empty for every model, and points `-c model_catalog_json=<file>` at it. With that file and the run's flags, `codex debug prompt-input` (codex-cli 0.167.0, 2026-11-08) lists one tool, `functions.request_user_input`, and no nested tool; a run with no flags lists `functions.exec`, `functions.wait`, `collaboration.spawn_agent`, `apply_patch`, `exec_command` and the MCP resource tools. `request_user_input` stays because no catalog field removes it, and `codex exec` has no user to answer it: a run told to call it for a question answered that it had no such tool and never emitted a tool event. Leaving one of the four fields at its stock value brings tools back (`tool_mode`: `exec` and `wait`; `shell_type`: `apply_patch`, `exec_command` and `write_stdin`; `experimental_supported_tools`: the `clock` tools and `request_user_input_async`), so the executor sets all four. A model that the edited catalog does not list would get the default shell, so the executor refuses an unlisted `--model` as `model-not-found` before it starts any process. The bundled catalog is 745,260 bytes (`codex debug models --bundled | wc -c`, 2026-11-08, 0.167.0). A start-up failure to load it leaves the row out, with a `codex-catalog-refused` log line. A Codex update needs a restart, as for the binary itself.
  - **Runtime check of the tool surface.** The flags and the catalog reach only the layers the run controls. `--ignore-user-config` skips `$CODEX_HOME/config.toml`, but the 0.167.0 loader ([`load_config_layers_state`](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/config/src/loader/mod.rs)) still loads `/etc/codex/config.toml`, `/etc/codex/requirements.toml`, the legacy `/etc/codex/managed_config.toml`, `/etc/codex/skills` and cloud-managed requirements. A managed `model_catalog_json` replaces ours and only prints a warning ([requirements.rs](https://github.com/openai/codex/blob/rust-v0.167.0/codex-rs/core/src/config/requirements.rs)). So before each task, in the same slot, the executor runs `codex debug prompt-input` with the same `--disable` and `-c` arguments, environment and catalog file as the task, and refuses the task as `provider-unavailable` when it lists any tool other than `functions.request_user_input` or any text that is neither a Codex base text (`surfaceOf`, `src/targets/node/codex-protocol.ts`) nor the check's own prompt. A run that cannot start the check is `not-configured`, a failed or unparsable one is `unreachable`, and the check has its own 60 s limit (a guess; refused Verify calls took 1.1 to 1.2 s). The log gets `codex-surface-refused` with the extra tool names and the count of foreign texts, never their content.

  - **Sign-in state.** Every AI settings load and every save runs `codex login status` and reads only its exit code (0 is signed in), because the output names the login method. Both CLI probes answer `false` at their 15 s deadline even when the child ignores `SIGTERM`; the kill and the folder cleanup finish afterwards (`answerWithin` in `cli-support.ts`), so an AI settings read never waits for them. A real child that traps `SIGTERM`, run for both CLIs, answered the read at 15 s and left nothing within 30 s; without the change it took 20.0 s. The exit code is a local hint, as for Claude Code: an invented `auth.json` also reads as signed in, and only Verify proves a model request works (OpenAI answers it with 401, `wrong-key`).
  - **Login policy.** OpenAI's CI guide ([auth](https://learn.chatgpt.com/docs/auth/ci-cd-auth), read on 2026-11-08) allows ChatGPT-managed `auth.json` only as "an advanced workflow for enterprise and other trusted private automation" where "the runner is trusted private infrastructure"; asks for "one `auth.json` per runner or per serialized workflow stream" and not the same file "across concurrent jobs or multiple machines"; says not to keep it "in the repository, logs, or public artifact storage"; and says "the right way to authenticate automation is with an API key".
