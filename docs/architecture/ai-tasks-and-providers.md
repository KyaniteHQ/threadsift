# AI tasks and Providers

Every model call is an AI task with a kind, inputs, an input revision and a Zod result schema. The kinds are `digest`, `topic_overview`, `related_pick`, `proposals`, `topic_proposals` and `disagreement_proposals`. The core creates the task row, an executor runs it, and the core checks the result against the schema and the rules before it applies it. A result whose input revision is no longer current is not applied; instead the core queues the same step again over the current inputs, so no Item's Digest is left out of a Topic overview.

| Executor | Provider rows it serves | Targets | How it runs a task |
|---|---|---|---|
| HTTP | OpenRouter (key or Connect), Anthropic, OpenAI and xAI keys, an OpenAI-compatible URL | both | AI SDK `generateText` with `output: Output.object({ schema })`; the vendor's own AI SDK package (`@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/xai`) maps the schema to that vendor's structured-output dialect, and `@ai-sdk/openai-compatible` serves OpenRouter and the URL row |
| Workers AI | Workers AI | Cloudflare | `env.AI.run(model, { messages, stream: false, max_tokens: <the task's output allowance>, response_format: { type: "json_schema", json_schema } }, { signal })` in `src/targets/worker/ai-binding.ts`; the model list is the JSON-mode list on Cloudflare's Workers AI docs |
| CLI | Claude Code and Codex on the server | container | Claude Code: `claude -p --output-format json --json-schema` in an empty folder with its tools off, read from `structured_output`. Codex: `codex exec --json --output-schema` with a per-run catalog that has no tools, read from the last `agent_message` event (CLI executor, below). The Grok CLI is not an executor (CLI executor, Grok CLI) |
| Grok Bot | Grok Bot | both | asynchronous, below |

- **Grok Bot runs every AI task when it is the Provider** (owner's decision, 2026-11-04). The Provider row, Save, Verify, the task lifecycle, the send, the in-flight cap, the per-task callback credential and `POST /api/ai-tasks/{id}/result` exist for every kind that calls a model: `digest`, `topic_overview`, `related_pick`, `proposals`, `topic_proposals` and `disagreement_proposals`, the six entries of `BOT_TASK_KINDS` (`src/core/bot-task-kinds.ts`). The X link round trip is built next to them (X links, below), and `bot/` holds the skills (Extension and Threadsift bot). Whether the bot writes good wiki results, and whether it answers an X link correctly, is unverified until a live run.
  - **The Provider.** `grok-bot` is a row of `PROVIDERS` (`src/core/ai-contract.ts`) that both targets list, with no field. It is not a stored `settings.provider`. The flag `use_as_provider` on the `grok_bot_settings` row (`src/core/grok-bot-tables.ts`) says Grok Bot is the Provider, and the `settings` row keeps the last Provider the owner saved. `loadAiConfig` (`src/core/ai-load.ts`) reads the flag, the settings row and the revision in one batch and answers which Provider runs now. The routing and `runAiTask` use that one answer (`onGrokBot` and `routedHandler`, `src/core/bot-step.ts`), so no second read can disagree with it. When the flag is set and the Grok Bot settings are unusable, the kind's own path refuses `not-configured` or `secret-missing` before any task row, and the stored Provider does not run.
  - **Choosing.** `saveAiSettings` (`src/core/ai-settings.ts`) answers 400 `{ error, code }` with `not-configured` or `secret-missing` and writes nothing when the Grok Bot settings are missing or their key cannot be opened. Otherwise one guarded batch sets the flag and adds 1 to `ai_settings_revision`, because no trigger fires for `grok_bot_settings`. Saving any other Provider writes its `settings` row and clears the flag in one guarded batch (`src/core/bot-provider.ts`). `DELETE /api/settings/grok-bot` answers 409 with the code `in-use` while the flag is set.
  - **Switching away.** The batch that clears the flag also fails every open Grok Bot task of the Provider with the refusal `abandoned` (an `x_intake` task is not one) and makes each job that waits on the bot due now, so the 30 s sweep claims it and it runs on the new Provider (`abandonedTasks`, `src/core/bot-task-states.ts`). A late callback on an abandoned task answers 409, so an answer is never applied after a switch back. An abandoned task leaves the in-flight count at once. A job that read the flag before the switch and inserts its task after it starts none: `botTaskKind` (`src/core/bot-task-kind.ts`) adds the flag to the `holds` of every task it starts, so the insert fails like a lost lease, and the job waits the deferral of a full bot (`FULL_CAP_DEFER_MS`) and then runs on the new Provider. An `x_intake` task does not read the flag.
  - **Verify.** `verifyProvider` (`src/core/bot-verify.ts`) starts a `digest` task through the same capped insert with no job and the context `{ "verify": true }`, sends it, and waits for the answer (`awaitVerifiedDigest`, `src/core/verify-wait.ts`) for at most `VERIFY_WAIT_MS` (60 seconds, chosen, unsupported; `src/core/grok-bot-contract.ts`). The Worker holds the request as wall time, which has no limit for an HTTP request while the client stays connected ([Workers limits, Duration](https://developers.cloudflare.com/workers/platform/limits/)). The task's own deadline is the window plus one send (`VERIFY_DEADLINE_MS`), so an answer after the window answers 409 whether or not the waiter lives. A task still open when the window passes, or when the caller's request ends, fails `timeout` in a guarded write that loses to an answer stored first. A failed send answers `refused` with the send's reason. A bot error and a full bot both answer `refused` with `provider-busy`. The bot reads and answers a Verify task like any other (`botKindOf`, `src/core/bot-task-kinds.ts`, picks the Verify definition from the context).
  - **Storage.** Migration `0053_grok-bot-provider.sql` (made by [`drizzle-kit generate`](https://orm.drizzle.team/docs/drizzle-kit-generate)) adds `use_as_provider` to `grok_bot_settings` with the default 0. The previous release ignores the column, so after a rollback it reads the `settings` row and runs on the last real Provider, and no step is needed. `docs/architecture/ci-releases-and-rollback.md` has the run.
  - **Modules.** `src/core/bot-task-states.ts` owns every transition of a bot task after its insert: the state and step rules, the guards that `completedAiTask`, `failedAiTask` and `expireAiTasks` (`src/core/ai-tasks.ts`) call, and the writes for send, resend, answer, bot error, charge, timeout and give-up. The writes that only an X link task makes (its answer, its stale end and its refusal count) are in `src/core/x-intake-writes.ts`. `src/core/bot-step.ts` takes one step per claim. A result kind is a `botTaskKind` (`src/core/bot-task-kind.ts`): the context schema, the task (`task(context)` rebuilds the Zod schema with its refinements and the instructions from the stored context alone), `current` (the kind's guard over the stored context), `release` (the write that frees the kind's lease, none for most kinds), `prepare` (reads the library, returns the task to start or an outcome that settles the job) and `apply` (writes the answer under the kind's guard). `BOT_TASK_KINDS` (`src/core/bot-task-kinds.ts`) is the registry. `botStep` and `sendBotTask` take any `SentTaskKind` (`prepare`, `release`, `current`, `describe`, `apply`). A `BotTaskKind` adds `parse`, and the result route answers it. `xIntakeKind` is a `SentTaskKind` without `parse`: the intake route answers it and closes the task in the same batch, so no job applies its answer. The kinds share code with their executors, so the bot sends what the other executors send and stores with the same guards.
  - **The send.** `sendBotTask` posts the webhook body of the task to the saved address (`WebhookBodySchema` in `src/core/ai-task-read.ts`: `{ taskId, kind, callbackToken }` for every kind, so no library text and no instructions travel in it) through `Network.post` (public `https`, no redirect, one 8-second signal over connect and body, the answer read to 16 KiB and dropped) with the key in the two headers of the settings (`postToGrokBot`, `src/core/grok-bot.ts`, shared with the Test ping). The body carries no address to call back, so a fetched page cannot send the credential elsewhere; the bot reads the task with `GET /api/ai-tasks/{id}` (The task read). HTTP 200 sets `sent_at`. A failed send fails the task and throws. 401 or 403 is `wrong-key`, the 8-second bound is `timeout`, a refused address, or a task whose stored context its kind cannot describe, is `refused`, a Provider that is not configured or whose key cannot be unsealed keeps those two reasons, and every other status or network error is `unreachable`. A send writes only while its job still holds the claim and only to a task that holds no answer. When the answer arrived while the send was failing, the send leaves the task alone and the job applies the answer. Delivery is at-least-once: a retried send after a lost answer may wake the routine twice, and the first run's callback then finds a failed task (409).
  - **States and steps.** A task is `unsent`, `sent`, `answered`, `applied` or `failed` (`stateOf`, from `state`, `sent_at` and `answered_at`). A bot error is a `failed` task with the refusal `provider-busy` and `answered_at` still set, until a claim charges it. On every claim of a bot-owned job `botStep` reads the latest task with that `job_id` and takes the step that `stepOf` names:

    | Latest task of the job | Step | Attempt |
    |---|---|---|
    | none, `applied`, or `failed` for any reason except a bot error not yet charged (`stale` and `no-json` included, whatever `answered_at` holds) | start a task and send it | a failed send throws and counts one |
    | `failed` `provider-busy` with `answered_at` set, whether or not the guard of the stored context has moved | charge it: clear the mark, free the kind's lease and throw | counts one |
    | `running` with `answered_at` | apply the answer | none |
    | `running`, unanswered, deadline passed | fail it `timeout` in one guarded batch and throw, or read the task again when the batch found an answer | counts one, or none after a re-read |
    | `running`, unanswered, `sent_at` null (a crash fell between the insert and the 2xx) | send again with the same task id and a new credential | none; a failed send counts one |
    | `running`, unanswered, deadline ahead | defer to the deadline, no send | none |
    | `running` and unanswered, and the guard of the stored context has moved | fail it `stale`, free the kind's lease, requeue | none |

    `jobs.attempts` counts only the throws. A send that the bot accepts defers the job with `countsAttempt: false`, so waiting and applying cost nothing, a stray wake lands in the wait row, and the third send is made at attempts 2, so its answer still applies. The worst case is three sends of one hour each plus the stale resends that `MAX_STALE_REQUEUES` allows. A job that closes (`closeJob`, `src/core/job-close.ts`) fails its running bot task, so a late callback gets 409 and the task frees its place in the cap. `test/grok-bot-provider-runner.test.ts` follows one job per kind through three claims (the 30 s and 2 minute delays, the third failure exhausting) and the answered third send applying at attempts 2.
  - **Apply.** The kind's `parse` builds its Zod schema from the task's persisted `context` and checks the stored `result` once more at apply, and the kind's apply half writes in the guarded batch that completes the task. A task whose answer no longer fits fails `no-json` and throws. The Related pick persists the source Item's id, the sent candidate ids and the Digest task ids with their stored tags. A candidate deleted or given a new Digest between the send and the answer moves a guard, so the apply writes nothing, the task fails `stale`, and the job requeues through the existing stale rule without an attempt. Its next claim starts a new task. A runner that lost its claim leaves an accepted answer alone: `failedAiTask` lets only `stale` and `no-json` fail a task that holds one. Three writers fail an answered task on purpose, because nothing can apply the answer any more: closing the job (`givenUpTasks`, `stale`), saving another Provider (`abandonedTasks`, `abandoned`) and the sweep one day after the deadline (`expireAiTasks`, `timeout`).
  - **The task read.** `GET /api/ai-tasks/{id}` answers `{ taskId, kind, instructions, input, schema }` (`TaskReadSchema`, `readableTask` in `src/core/ai-task-read.ts`) to the task's callback credential only: `instructions` and `schema` come from the kind's `describe`, `input` is the stored `inputs` text. It answers 409 once the task is not running, is past its deadline or holds an answer (`acceptsAnswer`, read in SQL), 401 and 403 as for the result route, and 400 for a task that is not a Grok Bot task. Reading writes nothing, so the bot may read again, and a resend of the task replaces the credential and so closes the old reader.
  - **The result route.** `POST /api/ai-tasks/{id}/result` takes `{ result }` (any JSON) or `{ error }` (1 to 200 characters), at most 256 KiB. The task's callback credential is the only credential it accepts (Access, below). It serves a task with the executor `grok-bot` and a kind in `BOT_TASK_KINDS`. Any other task answers 400 `unsupported-task`. 400 also means a body of neither shape or a result that fails the kind's schema or rules, with the reasons, and the task stays open for a second answer. A result nested deeper than the schema allows is a failed schema, so 400 as well. The stored `result` is the schema's reading of the body: keys the schema does not name are not stored. 409 means the task is not `running`, is past its deadline or already holds an answer, and nothing changes, so the first accepted answer wins and every repeat gets 409. 204 stores the answer (`result`, `answered_at`) and sets the owning job's due time to now in one guarded batch, then sends one advisory wake. The batch guard (`acceptsAnswer`) reads the state, the unanswered mark, the deadline against the database clock and the credential digest in SQL, so two simultaneous callbacks store one answer and a request that authenticated before a resend cannot commit after it. `{ error }` fails the task `provider-busy`, marks it with `answered_at`, logs the bot's text through `report` as `grok-bot-error` and makes the job due. The next claim charges one attempt.
  - **Kinds and their stored context.** The task's `context` holds everything the route needs to validate and everything the apply needs to write, so nothing is read from memory.

    | Kind | `context` | Guard the apply keeps |
    |---|---|---|
    | `digest` | Item id, its generation (`inputRevision`), the comment ids sent (`submitted`) | generation and task still current, and Pins (`publishing`, `src/core/digest-publish.ts`); the catalog version is not compared |
    | `topic_overview` | Topic id, page revision, the page's `builtFrom`, each added Item with its Digest task id, removed ids, citable ids, `mustChange` and the current overview text | the Topic lease and `inputsHold` over the stored values, and the running task |
    | `proposals`, `topic_proposals` | the sent pairs with the counts shown to the model (the catalog revision is the task's `input_revision`) | every sent pair still exists, and the running task |
    | `disagreement_proposals` | the sent Topics: id, name, `members` text and the Items with their Digest task ids | every sent Topic's membership text is still the one sent, and the running task |

    Each kind applies the guards of its model executors, except the Digest's catalog check, which only model executors run (`CatalogRule` in `src/core/digest-publish.ts`: `digestBotKind` builds `unchecked`, the model path builds `checked`). The Tag and Topic runs do not compare the catalog revision at publication, and the Digest recomputes `pinnedCatalog` at apply and publishes whatever the catalog holds then: a Digest that names a new Topic or Tag another Digest created meanwhile reuses it by key, and one that names a new spelling of a name adds a near-duplicate, because a refusal would send the task again and cost another bot run. The weekly check can suggest merging such a pair, and the owner accepts or rejects the suggestion. A changed Item generation still fails the Digest `stale`, because the Digest then describes old text. A Digest result that keeps a comment that was not sent publishes without that comment, as for the other executors. The task's `schema` in the payload is JSON Schema 2020-12, which Zod 4 writes natively (`z.toJSONSchema` with `io: "output"`); which dialect the bot accepts is unverified. A guard that moved fails the task `stale` and the job requeues without an attempt. The guard is read at apply, and also on every claim before the job waits, resends, expires or charges, through the kind's `current`, which holds what can be read before an answer (the Digest's generation, the overview's `inputsHold`, the sent pairs, Topics or versions) and leaves out the lease and the running task. So a job whose input moved does not wait out the hour for an answer to an old input, and its stale task never charges an attempt.
  - **The Topic lease around the wait.** The overview step holds the Topic's lease for the read and the send only. The kind's `release` is a prefix recovery over the leases whose holder starts with `topic_overview:<job id>:` (`recoverPrefixLeases`). `botStep` puts it in `DeferredOutcome.writes` of every deferral the step returns, which frees the lease in the same guarded batch that records the deferral: after an accepted send, on a wait, on a resend, and on a full cap. It also frees the lease on a failed send, when the claim was lost, and when the guard moved. While the bot works the Topic is free. The apply claims the lease again under the current attempt's holder name, and writes the page, completes the task and frees the lease in one guarded batch. A busy lease defers `topic-busy` for 15 seconds with no attempt, and the answered task stays (expiry skips it). The Grok Bot start also defers `topic-busy`, with the lease freed in the same batch, while `overviewAtBot` (`src/core/bot-task-states.ts`) finds a `topic_overview` Grok Bot task whose context names the Topic and that is `running` and either answered, or unanswered with its deadline ahead. It counts a row whose `sent_at` is still null: a crash between the insert and the 2xx leaves one, its job sends it again, and a second task for the Topic would double the bot run. A failed send fails the row, so it does not count. The model executors never run this check. The check runs under the lease and the task insert holds the lease too (`holds` of `BotTaskStart`, `leaseHolds`), so two starts cannot both insert, even when a runner stalls past `TOPIC_LEASE_MS`; a start whose lease expired inserts nothing and defers 60 seconds like a full bot. An unanswered task past its deadline and a task failed or discarded for any reason no longer count, so a lost task blocks the Topic for at most its hour. Once the open task is applied, a deferred job reads the Topic again: it sends when `hasUncovered` finds Items the stored overview was not built from, and it closes with no send when none remain (`idleOutcome`). A Topic that no longer exists, including one deleted between the check and the claim, fails the task `stale`. A runner that dies between the send and the deferral keeps the lease for at most `TOPIC_LEASE_MS` (12 minutes), and the next claim of its job frees it at its wait or resend step. The tag, Topic and disagreement runs and the Digest hold no lease.
  - **Failure marker by Topic id.** When the job gives up, `overviewGaveUp` writes `gave-up` for the Topic named in the context of the job's latest task (`markTopicOverviewFailed`, `src/core/topic-overview-run.ts`), because the lease holder name carries the attempt and another claimer may hold the released lease. The marker is skipped when the Topic is gone or its page revision is newer than the one the task was sent with, so a late give-up never marks a page that a newer overview stored. The marker by the owner Item's current Topic stays for a job that has no bot task. `closeJob` and `closeItemJobs` (a supplied page or thread, or an X link answer, closes the Item's fetch and x_verify jobs) end the running tasks of the jobs they close through one statement (`givenUpTasks`, `src/core/job-close.ts`), whether the job gave up, published a caller-sent Digest, refused on the model path or was closed by supplied content: `timeout` for an unanswered one and `stale` for one that holds an answer, because nothing can apply that answer once the job has closed.
  - **X links.** The fetch job of an X link runs an `x_intake` task (not a `digest` task, because the Digest it leads to is made by the caller-sent path with its own task) when the Grok Bot settings are saved (Fetchers, X). `xIntakeKind` (`src/core/x-intake.ts`) is the kind; its stored `context` is the Item id, the Item's content generation (also the task's `input_revision`), the status id and the link, and its `inputs` hold the link and the status id only, no library text. The task is not in `BOT_TASK_KINDS`, so the result route answers it 400 `unsupported-task`. The bot reads the task at `GET /api/ai-tasks/{id}` (`kind` `x_intake`, `input` `{ url, statusId }`, `IntakeInputSchema`) and answers at `POST /api/ai-tasks/{id}/intake` with the task's credential: `{ content, digest? }` or `{ unavailable: true }`, at most 8 MiB, 204 for an accepted answer, 400 for a task of another kind or a body or X thread that does not fit (the task stays open and the refusal is counted, Refused answers below), 401 and 403 as for the result route, and 409 for a task that is closed, past its deadline (read in SQL, so an answer after the deadline but before any sweep fails) or already answered. `POST /api/items` takes no task id, so no callback can be an ordinary save.
  - **Binding of an answer.** `acceptIntake` (`src/core/x-intake-answer.ts`) accepts an answer only while the task is running, unanswered and before its deadline, its fetch job (`job_id`) is still open and the Item's content generation still equals the task's `input_revision` (`intakeLive`, `src/core/x-intake-writes.ts`), all in the guard of one batch. A save with content closes every open fetch job and the `x_verify` job of the Item, deletes its stored thread and advances the generation, so an old answer or a waiting check cannot overwrite newer content or close a replacement job. An answer that finds the guard moved stores nothing, leaves the open fetch job open, fails the task `stale` in its own statement, answers 409 and makes the bound job due when it is still open, so its next claim decides what the Item needs. With `content`, `stored` (`src/core/x-intake-answer.ts`) writes the thread, the answer's Digest (or the Item's pending one) and an `x_verifications` row (`queuedVerification`, `src/core/x-verify-store.ts`), queues the `x_verify` job, sets `answered_at`, completes the task (`completedAiTask`) and closes the fetch job, all in the one guarded batch, and answers 204; nothing of the thread is shown until the `x_verify` job has checked it against X and publishes it as for a Paste (Fetchers, X). With `unavailable`, the same guard covers closing the job, settling the Item with the fetch result `status` and completing the task, so the Item is a Link-only Item. A repeat or a second run of the bot finds a completed task and gets 409: that is the dedupe by task id. A deleted Item takes its task with it (`ON DELETE CASCADE`), so a late answer finds no task and gets 401, the same answer as for a credential that does not exist.
  - **Refused answers.** A 400 of the intake route for an `x_intake` task that still takes an answer (`intakeLive`: running, unanswered, credential current, deadline ahead, job open, Item content unchanged) adds 1 to `ai_tasks.answer_refusals` and writes one `grok-bot-answer-refused` line (`refusedIntake`, `src/core/x-intake-answer.ts`, run by the middleware of `registerAiTaskRoutes`, so a body that fails the schema, one that is not JSON and an X thread that the parser refuses count alike). A 400 for a task that no longer takes an answer, and one for a task of another kind, is not counted and writes no line. A failure of the count is logged as `grok-bot-answer-refusal-not-counted` and the bot still gets its 400. The line holds the task id, the Item id, the count and `issues`, cut to 1,000 characters: for each validation issue the zod `code` and its path, with every key that is not a field name of the answer's or the thread's schema shown as `*` and an array index as `#` (`issueCodesOf`, `src/core/zod-reasons.ts`), `not-json` for content that is not JSON, and `thread-rule` with the fixed wording of the rule and its digits shown as `#` for a thread rule. It holds no zod message, no key name the bot chose, no value of the answer and no credential. The 400 answer to the bot keeps the full reasons, because the bot sent that text itself, and `reasonsOf` names every alternative of a union there, so a Digest field that does not fit reads as `digest.summary: ...` and not as `body: Invalid input`. The write is `refusedAnswer` (`src/core/x-intake-writes.ts`). At `REFUSALS_BEFORE_RESEND` (2) it moves the task's deadline to now and sets the owning job's due time to now in the same batch, so the second refusal makes the deadline pass and the same deadline transition runs at the job's next claim: the expire step of the table above fails the task `timeout`, the attempt counts, the retry waits the 30 s or 2 minutes of the job, and the next send starts a new task. `deadline` keeps one meaning, the moment after which the task takes no answer, so a task whose deadline moved to now leaves the in-flight count at once. A refusal never ends the task or the job by itself and publishes nothing, and the third send is the last, as before. A resend of the same task with a new credential (`renewedCredential`) sets the count back to 0, and a new send is a new task with 0. `queueLater` (`src/core/job-finish.ts`) makes a job due at the earlier of the deferral time and the task's stored deadline, or now when the task is no longer running or holds an answer, and queues its wake for the stored due time, so a second refusal that lands before the send's deferral is written is not lost.
  - **Sends of an X link.** The send, the wait, the cap and the retries are the lifecycle above. A full cap defers the fetch job 60 seconds, with `countsAttempt: false`, so an Import of many X links does not fire every webhook at once. A send that fails throws, so the runner retries after 30 seconds and 2 minutes, and the third failed send ends the job through `fetchHandler.exhausted`, which sets the Item `failed` with `gave-up`, and closing the job fails the running tasks (a wrong key therefore burns three attempts in about 2.5 minutes; the Settings Test is where a wrong key is found early). Three sends in all, one hour each, and no fallback to the grok CLI after a failure. `exhausted` stores the Item note that names the cause (`botFailureNote`, `src/core/bot-task-states.ts`): `bot-timed-out` when the last task never answered before its deadline, `bot-failed` otherwise.
  - **Deadline and expiry.** A Grok Bot task gets one hour (a chosen value, because the bot wakes in seconds to tens of seconds by its own estimate). At most 10 tasks occupy the bot (`GROK_BOT_IN_FLIGHT`, chosen, unsupported). A task occupies it while it is running, unanswered and before its deadline, because an answered task waits for its job and not for the bot, and the job may wait for a Digest that needs a place. The Topic rule above counts an answered `topic_overview` task until it is applied, because the page it will store is what a waiting job must read. The last 3 places (`GROK_BOT_WEEKLY_RESERVE`, chosen, unsupported) start only the three weekly runs, so a backlog of Digests after an Import cannot keep them waiting. `expireAiTasks` fails an unanswered task with no `job_id` at its deadline. It leaves an answered task and a task with a `job_id` alone until one day after the deadline (chosen, unsupported), so an accepted answer is not erased while its job waits for a runner, and the owning job fails its unanswered task at its claim and counts the attempt. After that day the sweep fails any running task `timeout`, answered or not, because a job whose claim never came cannot apply the answer. After three failed attempts the Item or Topic shows the failure with Try again. A failed bot task writes no Log entry, because the Log lists committed changes. There is no silent fallback to another Provider, because the owner picks one.
- **Without Grok Bot,** every task runs on the Provider the owner picked, on that target's executor. Nothing in the core knows which executor ran a task.
- **OpenAI-compatible URL on Cloudflare** must be a public HTTPS address, because the Worker runs on Cloudflare's network, not in the owner's home. Ollama on the owner's machine works from the container.
- **Workers AI is called through the binding, not through a package.** Cloudflare deprecated `workers-ai-provider` for `createAI` from its `agents` package (npm deprecation notice), and `agents` 0.33.0 is 10.8 MB unpacked with 11 dependencies, Babel and Rolldown plugins among them. The trade-off is one structured-output dialect we write and test ourselves.
- **OpenRouter Connect** is OpenRouter's PKCE flow ([OpenRouter docs, OAuth PKCE](https://openrouter.ai/docs/use-cases/oauth-pkce), [RFC 7636](https://www.rfc-editor.org/rfc/rfc7636)); the returned key is sealed and saved like a typed key. Files: `src/core/openrouter-connect.ts` (Start and the cleanup), `openrouter-callback.ts`, `openrouter-claim.ts` and `openrouter-save.ts` (the callback), `openrouter-contract.ts` (paths, notices, schemas), `openrouter-tables.ts`; the routes are in `src/http/openrouter-routes.ts` and the exchange adapter is `src/targets/shared/openrouter-exchange.ts`.
- **OpenRouter price limit.** With `THREADSIFT_OPENROUTER_MAX_PRICE_ZERO=true` the OpenRouter adapter sends a $0 `provider.max_price` limit for prompt, completion, request, image and audio on every inference (`ZERO_OPENROUTER_PRICE` in `src/targets/shared/ai-executor.ts`). An unset or `false` variable leaves the Instance unchanged; another value fails startup. OpenRouter does not document limits for cache or reasoning prices in `max_price`, so a key-level guardrail is separate ([provider selection](https://openrouter.ai/docs/guides/routing/provider-selection#max-price)). No test setup sets the variable.
  - **Public origin.** Connect needs `THREADSIFT_PUBLIC_ORIGIN` (`configuredOrigin` in `src/targets/shared/configured-code.ts`): an `https` origin, or `http` on `localhost` or `127.0.0.1`, with no credentials, path, query or fragment. `Ports.publicOrigin` is `null` when it is absent or empty, and the settings view then reports `connect: false`, the button is replaced by a note, and Start answers 503. A malformed value is an error, not a silent `null`: the container exits 1 at start (run on 2026-11-08 with `ftp://x.test`, `https://u:p@x.test`, `https://x.test/path` and `http://example.com`), and the Worker rejects every request. The callback address OpenRouter gets is that origin plus `CONNECT_CALLBACK_PATH`; OpenRouter accepts `http://127.0.0.1:<port>` callbacks (its authorization page showed the address in a run on 2026-11-08).
  - **Settings revision.** Table `ai_settings_revision` (one row, `CHECK` on `id = 1`) counts changes to `settings`. Triggers from migration `0023` (created after `0021_codex-provider` rebuilt `settings`, because a table rebuild drops its triggers) add 1 after every insert, update and delete, so any writer, including one that predates the table, moves it. `aiView` returns it, and Start and the final save both compare it with the revision the page was loaded at, so a typed Save made while the owner was on OpenRouter's page wins and the Connect result is dropped (`settings-changed`). Selecting Grok Bot adds 1 in the same batch, because no trigger fires for the flag. A typed Save is guarded the same way (`saveAiSettings` in `src/core/ai-settings.ts`): it reads the row and the revision together, builds the new row from them (a Save without a key keeps the stored key only when Provider, base URL and model match), and writes in one guarded batch that checks the revision is still the one it read. When it moved, the Save reads again and builds the row again, up to 5 times, so a Save that keeps the key cannot write back a key that a Connect or another Save replaced in between. After 5 misses it throws and answers 500.
  - **Start.** `POST /api/settings/ai/openrouter/start` takes `{ model, revision }` as JSON and is owner-only. It checks `Origin` against the configured origin, `Sec-Fetch-Site: same-origin` and the request host itself, because Hono's `csrf` middleware skips JSON bodies. It stores one row in `openrouter_connect_transactions`: the SHA-256 digest of a 32-byte random `state`, the digest of the session, the verifier (another 32 random bytes) sealed under `THREADSIFT_SECRET_KEY`, the model, the revision, the origin and a 10-minute expiry (`CONNECT_LIFETIME_MS`, the lifetime OpenRouter gives a code). The insert is one guarded batch, so it commits only while the session is live and the revision is current. The creation and expiry times come from the database clock (`DATABASE_NOW`), the clock that the claim, the final save and the sweep also read, so one clock decides whether an attempt is live. The answer is the authorization URL (`code_challenge_method=S256`, `key_label=Threadsift`); the page leaves for it. It answers 201, 400, 403 (not from the owner's page), 409 (stale revision) or 503 (no origin or no sealing key). Switching the Provider in the form fills the model only with the saved model of that same Provider, so a model of another Provider is never offered to OpenRouter.
  - **Callback.** `GET /api/settings/ai/openrouter/callback` is the one `/api/*` route a browser reaches by redirect. `installApiMiddleware` in `src/http/api-middleware.ts` registers two middleware before the guard. `privateResponse` sets `Cache-Control: no-store` and `Referrer-Policy: no-referrer` on every answer of the callback and of Start, refusals included, so the code in the query and the authorization address are not cached or sent on. `signedOutNavigation`, on the callback only, turns the 401 for a signed-out browser navigation (a `GET` with `Sec-Fetch-Mode: navigate` and no `Authorization` header) into a 303 to `/settings`. Any other signed-out caller, and any request with an `Authorization` header, keeps its 401, so the OpenAPI-wide closed-route check still holds; a non-GET answers 405 (Hono routes HEAD to the GET handler, so the handler checks the method). The handler parses exactly one `code` and one 43-character `state` and no `error`; anything else, a denial included, is `incomplete`. It then claims the row with one `DELETE ... RETURNING` on the state digest, the session digest, the expiry, the origin, the revision and a live session, where both time checks read the clock inside the statement (`DATABASE_NOW` in `src/core/openrouter-tables.ts`, `julianday('now')` scaled to milliseconds), not a time the code captured earlier, so a statement that waits for the database cannot use an older window (SQLite date and time functions); so the code is used once, only by the session that started it, and a replay finds no row. A refused claim answers `settings-changed` when the row exists with another revision, else `incomplete`.
  - **Exchange.** `POST https://openrouter.ai/api/v1/auth/keys` with `{ code, code_verifier, code_challenge_method: "S256" }` through `aiTransport` (no redirects), 8 seconds (`HOP_DEADLINE_MS`), and a body read capped at 16 KiB. A 200 answer with `{ key }` is a key; 400 and 403 mean OpenRouter refused the code (`incomplete`); any other status, a thrown error, a timeout or a malformed body is `uncertain`, and OpenRouter may then have made a key, so the notice is `possible-orphan`. The exchange returns `{ kind: "key", key }`, and the callback saves the key before it waits (Final save). The wait is `awaitOpenRouterActivation`, which calls `GET https://openrouter.ai/api/v1/key` (OpenRouter's current-key endpoint, which spends no credits) with the new key every second, `ACTIVATION_POLL_MS`, until the answer is 200 or a 45 second bound, `ACTIVATION_WAIT_MS`, runs out. A 401 inside the bound means wait; a 200 means active; any other status, a thrown error or a timeout stops the wait with the key marked not active. The wait takes no caller signal on purpose: the signal the callback passes is the 8 second timeout of the exchange request, so reusing it would cut the wait to a few seconds, and the callback holds no signal for a client that disconnects. The key exists at OpenRouter by then and the attempt row is already claimed, so the key is saved before the wait starts, and a stop during the wait leaves the saved row and no notice. The wait is needed because a 401 is final in `retriesAi` (`src/core/ai-contract.ts`): a Digest job that meets the activation delay fails with `wrong-key` for good, and saving again does not reopen it.
  - **Activation delay.** Measured on 2026-11-08 with real keys. Keys made through the management API (`POST /api/v1/keys`, 6 keys) answered 200 on both `/key` and the model call at the first poll, after 1 to 2 ms. Keys made by the OAuth exchange (16 keys: 9 authorized in the box browser and saved by Connect, 7 from a direct exchange of the code) showed the delay: 6 were active at the first poll, 1 after 4.6 s, 1 after 6.3 s, 1 after 11.1 s and 7 after 15.6 to 17.2 s; a Verify pressed after Connect also failed for 26 s once on the container and 4 s once on the Worker. In every one of the 16 runs `/key` turned 200 together with the model call or at most one 1 second poll after it, never before, so waiting on `/key` is never earlier than the model call. The 45 second bound is 2.6 times the longest of the 16 measured times (17.2 s), is above the 26 s seen once, and is far below `CONNECT_LIFETIME_MS` (10 minutes), which the final save checks after the wait. The model-call column of some runs shows 429 from the free model's rate limit instead of 200, so 429 counted as not 401.
  - **Final save.** `saveConnectedKey` runs `prepareAiSettings` (the same validation and sealing as a typed Save), then one guarded batch that commits only while the session is live, the revision is still the one Start saw and the attempt has not expired, with the same in-statement clock as the claim. The batch writes the settings row only, and it runs before the activation wait, so the key is stored while the wait runs. A throw while preparing the row is `possible-orphan`. When the batch is not positively confirmed, whether it returned `false` or threw, the code reads the stored row back and goes on only if it holds exactly the prepared row (same sealed key, Provider and model); otherwise the notice is `possible-orphan`. After the wait it reads the stored row again. When a typed Save has replaced it the notice is `settings-changed`. When the key is not active the notice is `activation-pending`, and saving again (a typed Save) opens the Digests. When the key is active, the older-Digest writes open Digests for older Items exactly as a typed Save does and the notice is `connected`; a failure of that batch is logged and answers `activation-pending`.
  - **Notices.** The callback answers 303 to `/settings?openrouter=<notice>` with `connected`, `incomplete`, `settings-changed`, `possible-orphan` or `activation-pending`; the page shows the text once and removes the parameter. `connected` and `activation-pending` show only while the saved settings are OpenRouter with a key set; `activation-pending` otherwise shows the `incomplete` text. `activation-pending` says the key is saved, OpenRouter has not activated it, no Digests for older Items started, and the owner should wait a minute, press Verify and then Save. The `incomplete` text says Threadsift could not confirm the Connect and points to the key shown and to Verify, because it also answers a return address opened a second time after the first visit saved the key. A page that the browser restores from its back/forward cache after the owner left for OpenRouter (`pageshow` with `persisted`) leaves the "Connecting..." state and reads the settings again (`usePageRestore` in `web/src/use-connect.ts`). The notice is part of the form state (below) and goes away on the first Save, Verify or Connect, so a later change of the saved settings cannot turn it into the `incomplete` text. Texts come from `tools/copy/write-copy.sh` (`web/src/ai-text.ts`).
  - **Form state.** `useAiPhase` (`web/src/use-ai-phase.ts`) holds the AI settings form in one reducer: a phase (`idle`, `saving`, `verifying`, `waiting`, `connecting`, `leaving`; Verify with Grok Bot runs in `waiting` while the one request holds for the bot's answer), the outcome shown under the form (a Connect failure is an outcome like a Save failure) and the arrival notice. Save, Verify and Connect each start with one event that clears the outcome and the notice, and `useGuard` rejects a second start in the same frame. In `connecting` and `leaving` Save, Verify, Connect and the Provider picker are blocked, and a press on an unavailable button (a `refuse` event) changes nothing while the phase is not `idle`, and the failed settings read after a persisted `pageshow` goes through the same event, so it never ends a Save, Verify or Connect that started meanwhile; the text fields stay editable, because nothing reads them after Connect has sent the model. Connect, Save and Verify with nothing to act on show the reason in the result line instead of ignoring the press: with `secretReady` false they show the secret-key text, and with a Provider that is signed out they show its sign-in line with the command. `leaving` is the phase after `window.location.assign`; a navigation that is stopped, answered with no content or aborted fires no event on the page (probed on 2026-11-09 in Playwright's headless Chromium with a route answering 204: `beforeunload` fired, `pageshow`, `visibilitychange` and `pagehide` did not), so the phase ends on a persisted `pageshow` or after `LEAVE_WAIT_MS` (10 s, unsupported: a chosen bound), back to `idle` with no error. If the navigation was only slow and the owner presses Connect again, that press makes a second attempt and the first expires with its 10 minutes. The status line under the key field follows the server's rule for keeping a key (`nextSettings` in `src/core/ai-settings.ts`): "API key saved" only while the form's Provider, base URL (trailing slashes ignored) and model equal the saved ones, and "Enter an API key to save this Provider, URL and model." when a key is saved for something else, in which case the key field is required. When the saved key cannot be opened (`keyReadable` is false and `secretReady` is true), the line says so and offers both ways back, the key field is required whatever the form holds, Verify is blocked, and Save and Connect stay available. When the server lists no Providers the picker offers `openai-compatible`; no real run reaches that, because the container and the Worker always list the five HTTP Providers.
  - **Cleanup.** The tick deletes attempts that are expired or whose session is gone or expired (`sweepConnectTransactions`); logout and a password change delete the session, and the foreign key on the session cascades to its attempts.

- **Task owner.** `ai_tasks.item_id` names the Item a task works for. A Digest task, model or caller, carries its Item; the Verify task carries null. The key is `ON DELETE CASCADE` like every other child of `items`: `inputs` holds up to 14,000 bytes of the Item's text, so `SET NULL` would leave that text behind after the Item is gone, and `NO ACTION` would make every delete of an Item list its tasks first. SQLite checks a `NO ACTION` key at the end of a statement ([SQLite docs, Foreign keys](https://www.sqlite.org/foreignkeys.html)), so one `DELETE FROM items` removes the Digest and the task it names together, while a delete of that task alone is refused. Both were run on `node:sqlite` and on local D1 (wrangler 4.156.0, 2026-11-07), with the same results. Foreign keys are on in both targets, and a task for an Item that is gone is refused by the key. `startTask` in `src/core/ai-task-start.ts` creates an Item's task only while its job still holds its claim, in one `INSERT ... SELECT ... WHERE` on `holding` (`src/core/job-rows.ts`, the condition the finishing guard checks), never after a separate read. When the insert writes no row, `runAiTask` and `startCallerTask` report the lost claim and the Digest attempt returns `lostClaim`, a write batch whose guard never passes. `finish` then rejects the batch because the claim is gone, logs one `job-claim-lost` line, and the attempt makes no Provider call. FROM digests` (SQLite 3.33 or later, which D1 must run because the code already uses `RETURNING`, added in 3.35; D1 does not document its version), which scans `digests` once and finds each task by primary key; the earlier correlated subquery took 17.5 s for 10,000 Digests on `node:sqlite` (slice review) against D1's 30 s query limit; a task made before migration `0014` that no stored Digest names (a failed attempt, a replaced Digest) carries no link to its Item, which neither the task nor any other row records, so no run can set its owner; the `ai-task-owners` data step (`src/core/ai-task-owner-step.ts`, 500 ids a unit) deletes those tasks, because `inputs` holds the Item's text and nothing reads an old task, and keeps the Verify task (its `inputs` is `cutDigestInput(VERIFY_INPUT)`) and every task a Digest names. Since `0014` only Verify creates a task without an owner, so the rule holds for new rows.

- **The `topic_overview` task.** `linkingDigest` (`src/core/catalog.ts`) adds one `topic_overview` job for the Item's Topic to the batch that publishes a Digest or links an older one, but only when a Provider is saved (`providerSet` in `src/core/provider-saved.ts`: a `settings` row, or Grok Bot chosen as the Provider; `loadAiConfig` reads the same two facts, and `test/provider-saved.test.ts` compares the two across the states). The model sees that text and the added Items, never a removed id. A run with no added Item that fits the input is that prune alone, written by `keptOutcome` without a model call, so a removal ends in a written overview or an unchanged one even when the model would refuse. When the prune leaves no line, the write stores an empty `built_from`, so the Items that remain count as uncovered and the continuation opens a run that writes an overview from them. Otherwise `reviseOverview` calls `runAiTask` for `{ lines, unchanged }`, where each line is `{ text, items }`. The model returns the sources of a line as ids, and `overviewText` (`src/core/topic-overview-task.ts`) writes the stored text, one line per row, each ending in `[id]` marks. The first real run with `nvidia/nemotron-3.5-super-vl:free` on 2026-11-11 returned one free-text `overview` string with the model's own `unchangedfalse}JSON_OUTPUT{` fragment inside it and no line breaks, so the schema refuses a line with brackets, braces, quotation marks or a line break. The schema (`topicOverviewTask`) accepts at most 5 lines of at most 300 characters, at most 1,500 characters in the stored text, ids only of Items that stay in the overview or were sent, and refuses `unchanged: true` when the pruned overview is null. The output allowance is `MAX_OUTPUT_TOKENS` (8,192): the same model ended a call with `cut-off` at 1,024 tokens and again at 2,048. When the model answers `unchanged`, the stored text is the pruned overview and `built_from` and the revision change. The write is one guarded batch (`currentInputs`): the lease still holds, the revision, the sent Items with their Digests and the removed ids are as read, every Item the overview was built from and not removed is still in the Topic (`retainedStay`), and the AI task is still running. When any of that is out of date, nothing is written, the AI task fails as `stale`, the lease is released and the job requeues over fresh inputs. A refusal is first checked against the same inputs: when they are out of date, the attempt is not spent and the job requeues like any stale result. A refusal that `retriesAi` accepts then fails the attempt until the last one. Any other refusal, and the last retry, stores the refusal as the failure marker and ends the job without an error. `exhausted` stores `gave-up`. Both keep the earlier overview text. One run is one model call over one bounded batch: the Items that fit the input, not every uncovered Item. When the publication leaves Items uncovered or removed Items unhandled (`coverageGaps` in `src/core/topic-coverage.ts`) and a Provider is saved, the same batch that closes the job opens the next one (`continuingOverview`, the `continuation` of the outcome), for the Topic's lowest Item id, so a backlog ends without another Digest arriving. Every publication covers or drops at least one Item, so the chain ends. A merge of two Topics (`pin-keys` and Accept of a Topic merge) makes the same attempt once for the kept Topic in its last unit (Catalog keys, the shared Topic rewrite). It inserts a job only when a Provider is saved, the kept Topic has Items its overview was not built from and its owner Item has no open `topic_overview` job, so it is not a promise of exactly one job. The cost of covering N moved Items with valid Digests is at least ceil(N / 40) model calls, because one run reads at most 40 Items it was not built from: a merge of 18 Items into a Topic of 28 that had no overview left 46 uncovered Items and made 2 model calls on Claude Code, from 2 jobs that already waited, and one that moved 600 made 16. Accept of an overview-gap Proposal starts one such run through the same start as Try again (`startOverview` in `src/core/overview-start.ts`; see `docs/wiki.md`, Topic pages), and the same lower bound holds: covering N uncovered Items takes at least ceil(N / 40) successful model calls, a failed run takes the refusal path, writes the failure marker and does not continue, and a Provider removed mid-chain stops it, so the calls attempted, the calls that succeeded and whether coverage completed are three different numbers.

- **The `proposals` task.** `proposalsHandler` (`src/core/proposal-job.ts`, a `WeeklyModelRun` for `weeklyModelHandler` in `src/core/weekly-model-run.ts`) reads the Tags that have at least one Item, in pages of 1,000 by id (`usedSubjects` in `src/core/proposal-input.ts`, a recursion that asks for the page after the last id, because D1 caps one result at 50 MB), and every `proposals` row in one query (`knownPairs`; a row is under 100 bytes and at most 20 rows are added a week, so 50 MB takes about 480 years of weeks, guess), and finds pairs with a pure function (`candidatePairs` in `src/core/proposal-candidates.ts`) by two rules that the spec leaves open, so they are chosen here. First, the same loose key: a Tag's `key` with every character that is not a letter or a number removed, and one final `s` dropped when at least 3 characters remain after the drop (English only, chosen, unsupported), so `machine-learning`, `machine learning` and `machine_learning` meet, as do `llm` and `llms`, and `gas` stays whole. Accents stay, because `catalogKey` keeps `café` and `cafe` apart on purpose. Second, an initialism: a Tag of two or more words whose first letters, joined, equal another Tag's loose key of at least 2 letters (`machine learning` and `ml`). Both rules produce pairs for the model to judge, not merges: `c`, `c++` and `c#` meet under the first rule and are different things. No embeddings exist, so a semantic duplicate beyond the two rules is not found. A pair that has a row in any state is skipped. Pairs are ordered by the two Tags' combined Item count, most used first, then by the two ids, and `disjointPairs` takes a pair only when neither Tag is in a pair already taken, up to 20 (`PROPOSALS_MAX`, chosen). Disjoint pairs let the model return every pair it judges a match, so a sent pair it does not return is a real "no" and is stored as `declined`. A pair that is not sent keeps no row and stays eligible. With three spellings of one concept, one week sends one pair; once the merge is accepted, a later week sends the survivor and the third.
  - **Input.** One JSON text of `{ pairs }`, each pair two Tags of `{ id, name, items, topics }`, where `topics` holds up to 3 Topic names, the Topic with most of the Tag's Items first and ties by Topic key (`topicsOf`). No Item title, Summary, post text or comment is sent, so no Item text stays in `ai_tasks.inputs`. The cap counts the whole serialized text in UTF-8 bytes (`utf8Length`): 14,000 (`PROPOSALS_INPUT_BYTES`, chosen, equal to the other wiki tasks by choice). `proposalsInput` adds each pair whole in order and skips one that does not fit; a skipped pair stays eligible. With no pair, or none that fits, the job writes nothing, makes no AI task and closes.
  - **Result.** `{ merges }`, at most 20, each `{ from, into, reason }`. `from` and `into` are two different Tag ids of one sent pair, either way round, and a Tag appears in at most one merge. `reason` is 1 to 160 characters under `plainText`. Zero merges is valid.
  - **Freshness and storing.** The attempt keeps the ids of the Tags it sent and passes the `catalog_version` it read as `inputRevision`. One guarded batch (`storedOutcome` in `src/core/proposal-job.ts`) holds while the AI task is still running and every sent Tag still exists. It inserts an `open` row for each merge and a `declined` row with no reason for every other sent pair, with `ON CONFLICT DO NOTHING`, so a pair that gained a row meanwhile keeps it, then completes the AI task and closes the job. When the guard fails nothing is written, the task fails as `stale` and the runner requeues the job without spending an attempt. A retriable refusal retries after 30 seconds and 2 minutes; a terminal refusal or the last retry closes the job and stores nothing. One run judges one set of disjoint pairs and opens no continuation job, so a large first backlog clears over several weeks.
  - **Cost.** Each attempt makes at most one model call, with SDK retries off. The week opens one job; error retries and stale reruns add calls.

- **Refusal mapping.** `executionRefusal` in `src/targets/shared/ai-executor.ts` turns every SDK error into one category. An HTTP 401 or 403 is `wrong-key`, 404 `model-not-found`, 429 and 5xx `provider-busy`, 400 and 422 `no-json`, a redirect or a refused address `refused`. xAI answers a wrong key with HTTP 400 and `{"code":"invalid-argument","error":"Incorrect API key provided..."}` (`curl` to `https://api.x.ai/v1/responses` with an invented key, 2026-11-07), so an xAI 400 whose message holds `Incorrect API key provided` is `wrong-key` too; Anthropic (`authentication_error`) and OpenAI (`invalid_api_key`) answer 401. The executor reads the finish reason before the output: `content-filter` is `declined` and `length` (the task's output allowance, below) is `cut-off`, even when the text parsed, and a `NoObjectGeneratedError` is classified by the same finish reason. When a non-`stop` finish carries no text, the SDK's `output` getter throws `NoOutputGeneratedError`; the finish reason is read first, so that error only remains for the finish reasons `error` and `other`, and it is `no-json`. Anthropic's `refusal` stop reason reaches the SDK as `content-filter` (provider page, Finish reason mapping). `@ai-sdk/openai` 4.0.107 does not do this for the Responses API: its response schema accepts only `output_text` content parts (`openai-responses-api.ts` in the package), so a refusal part (`{"type":"refusal"}`, OpenAI's structured-output refusal shape) fails decoding as an `APICallError` with status 200 and a `TypeValidationError` whose `value` is the response. `holdsRefusalPart` recognises that shape with a Zod schema (an `output[].content[]` part of type `refusal`) and returns `declined`. `@ai-sdk/openai` 4.0.110 decodes refusal parts (its changelog, entry 6b97088), but it needs `@ai-sdk/provider` 4.0.36 and `@ai-sdk/provider-utils` 5.0.75, which would add a second copy of each, and it was published 2026-11-06, inside the repository's 3-day `minimumReleaseAge` (`pnpm-workspace.yaml`); when `ai` and the other packages move to those versions, drop `holdsRefusalPart`. - **Measured Digest input budget.** `digestPrompt` in `src/core/digest-prompt.ts` builds the whole user input, and the 14,000 UTF-8 byte cap counts all of it: the catalog line, the line break, and the Item JSON `{title, source, postText, comments}`, followed by `linked` when there is linked text, with its field names, brackets, commas and escapes. The catalog gets up to 4,500 bytes, split equally between Topics and Tags with JSON overhead reserved; each list retains its names with the most Items first, breaking ties by id. `CATALOG_NAME_LIMIT` bounds each `readCatalog` query from the per-list byte budget and the shortest valid encoded name, so no name that could fit is excluded by the row limit.
  - **Fill order.** The builder reserves the selected catalog and the Item with an empty post text and no comments, and refuses when that alone passes the cap: the Digest ends failed with no Provider call and one `digest-input-refused` log line, the same recovery as any failed Digest. When a hop gave linked text, the builder also reserves the `linked` object with its URL, its title and an empty `text`; when that alone passes the cap, the prompt has no `linked` field and is the prompt of an Item with no hop. The linked text then takes the longest prefix, cut at a code point, that fits one third of the room left (rounded down, our choice, not measured). The rest splits in two, the odd byte to comments. Comments fill their half in ascending `position`, each as a whole `{id, parentId, body}` record with the stored ids and no author, and a record that does not fit is skipped. The post text takes the longest prefix, cut at a code point, that fits all the space left. Skipped comments are then tried again in position order in what remains, and the selected comments go out in position order. Room that is still unused after all three goes back to the linked text, which extends its prefix by exactly those bytes, so a sparse post and few comments leave the whole cap to the page. A prompt with no linked text has the same bytes as before the hop. Sizes come from the serialised JSON, so an escape counts at its full length (a control character costs 6 bytes), and only a text value is ever shortened. `cutDigestInput` stays as the task's `prepareInput` and leaves a finished input unchanged; it still cuts the Verify sample and a long post text read from the file store.

A parent may be missing from the list because it was ineligible or did not fit, and the instructions say its text must not be invented. Any other Source, and Verify, send none.

A refresh leaves the last published selection until a replacement publishes, and a stale result changes none of it. Each attempt that reaches the Provider logs one `digest-comments-submitted` line with the task id, Item id, generation and the eligible, submitted and omitted counts, and no comment text.
