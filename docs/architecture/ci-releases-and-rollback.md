# CI, releases and rollback

- **Gate.** `.github/workflows/gate.yml` runs on every pull request and on every push to `main`. The `check` job installs once and runs `devenv tasks run ci:gate` (Development environment, `tasks`), within 10 minutes. The static check `impeccable detect --github web` stays in the `check` job. The `smoke` job runs the browser smoke spec on the Worker and on the container image, one runner each, within 15 minutes. The `container:build` task builds the image while `ci:install` runs, because the build reads only the `Containerfile` and the source tree; the first build step began 3.7 s after the tasks started, while `ci:install` still ran, against 6.9 s when the Playwright `webServer` built it behind `ci:install` (`smoke (container)` logs of runs 42902189977 and 42898244547, 2026-11-10). The container start gets 60 s in `playwright.config.ts`, about 12 times the 5 s it took in that run, so Playwright fails before the job's budget ends. A container start timeout leaves no test output. The job log records the failure. That `podman build` passes `--jobs 0`, which builds the Containerfile's stages in parallel instead of one after another; the image build took 28 s against 42 s without it (from `[1/5] STEP 1/1` to `Successfully tagged` in the `smoke (container)` logs of runs 42894300041 and 42883935991, 2026-11-10). Fail-fast is off, so a failed target leaves the other running, and a failed smoke run uploads Playwright's `test-results` as the artifact `smoke-<target>` for 7 days. A newer push cancels the older run of a pull request. Check, build, audit, the design check and the core tests share one job because each separate job pays about 32 seconds of setup (the `setup-devenv` step of each job in run 42894300041, 2026-11-10).
- **Shell setup and package cache.** Unmodified `pkgs.corepack` is available from `cache.nixos.org`, so cold runners avoid its build and install checks. pnpm 12 reads `pnpm_config_store_dir` for the cached store and ignores `npm_config_store_dir`. The action does not cache the Nix store itself, because a restored store was no faster than the binary caches. With `nix-community/cache-nix-action` v7.0.2 added to `.github/actions/setup-devenv` before `nix profile add` and keyed on `devenv.lock`, `devenv.nix` and the action file, a warm job restored 1043 MB in a step of 25 to 29 s, `nix profile add` fell from about 19 s to under 1 s and the shell evaluation from 11.0 to 13.3 s (20.1 s in one slow job) to 2 to 3.5 s, so the setup step plus the shell evaluation took 42 to 49 s per job against 37 to 58 s without the store cache, and saving it took 14.5 to 16.5 s (attempts 2 and 3 of run 42906685884 against runs 42896225092, 42897469087, 42897869989, 42905609594 and attempt 1 of 42906685884, 2026-11-10).
- **Nix input downloads.** `nix profile add` and the first `devenv` command download each locked GitHub input from `https://api.github.com/repos/<owner>/<repo>/tarball/<rev>`. A cold runner makes at most 5 such requests per job: 1 in `nix profile add` (devenv-nixpkgs, which holds the `devenv` package) and 4 in `devenv` (devenv, devenv-nixpkgs, nixpkgs and git-hooks.nix from `devenv.lock`). The `devenv` count comes from the `Downloading https://api.github.com` lines of `devenv -v info` on a runner with Nix 2.35.4 and devenv 2.4.0 (run 42428719602, 2026-11-08). The `nix profile add` count comes from `XDG_CACHE_HOME=<fresh dir> nix --store <fresh dir> build --no-link -v "github:cachix/devenv-nixpkgs/<rev>#devenv" 2>&1 | grep -c "downloading 'https://github.com"`, which printed 1 (Nix 2.34.9 on a workstation, 2026-11-10). That Nix had no `access-tokens` entry and so used `https://github.com/<owner>/<repo>/archive/<rev>.tar.gz` instead of the API URL, and the runner's URL form was not measured. `.github/actions/setup-devenv` caches `~/.cache/nix`, Nix's tarball and fetcher caches (about 108 MB compressed), under a key that hashes `devenv.lock` and the action file, which holds the Nix installer pin. A job that restores it makes 0 requests: the second job of that run, on a fresh runner, logged none. The pull request gate runs 3 jobs that set up devenv (`check`, and `smoke` for the Worker and for the container), so a cold gate makes at most 3 × 5 = 15 requests within the same minutes and a warm gate makes 0. The deploy and each target's live check run the same install and locked evaluation, so each should make at most 5 cold and 0 warm.
  - **The 429 is not the hourly quota.** `GET /rate_limit` with the workflow token read `limit` 5000 (the docs give 1,000 for `GITHUB_TOKEN`), and `core.used` stayed at 54 across two `nix flake prefetch github:...` calls with `access-tokens` set, then rose to 57 after 3 `GET /zen` calls (run 42429313493, 2026-11-08). The 429 body in a failed pull request copy run was `429: Too Many Requests` and a notice about scraping. Another author passed a token to Nix in three ways and still got the same 429 with 0 of 5000 used, and concluded it is GitHub's anti-abuse limit on the egress addresses that runners share ([Chasing a GitHub 429 across my Emacs CI](https://www.d12frosted.io/posts/2026-06-29-chasing-a-github-429)). That cause is an inference: GitHub shows no counter for it. So no per-hour sum limits the gate, and the cache cuts the requests that meet the throttle. One untried alternative: Nix 2.35.4 downloads from `https://github.com/<owner>/<repo>/archive/<rev>.tar.gz` instead of the API when no `access-tokens` entry matches (`GitHubInputScheme::getDownloadUrl` in `src/libfetchers/github.cc`); whether that endpoint throttles the same way needs a cold run with both the installed Nix and devenv's Nix.
  - **When the cache misses.** A change to `devenv.lock` or the Nix installer pin gives a new key. The `restore-keys` prefix then restores the newest cache saved under an older key, so the first run after the change should download only the inputs whose revision changed; that partial restore was not measured, and with no older cache every job is cold. A cache made by a pull request run is visible only to that pull request's merge-ref runs; a run on any branch restores the caches of the default branch (GitHub Actions docs, dependency caching, Restrictions for accessing a cache), so the first gate on `main` after the merge seeds the key for the next pull requests. Nix retries a throttled download 5 times and then fails the job; the action adds no retry, because a retry on the same address hides a throttle instead of avoiding it, and a rerun of the job is the repair. The restore from `main`'s cache by a pull request run was not run.
- **Merging.** `main` requires one aggregate `gate` job that needs `check` and `smoke` and passes when each passed or skipped itself; a workflow-level `paths` filter is not used, because a workflow it skips leaves its required checks pending. Renovate opens dependency updates after a 3-day wait.
- **Secrets and forks.** The build and test jobs for pull requests receive no repository secrets. The live deploy uses the `main`-only environment `live`, and the local-runtime live check uses the `main`-only environment `post-merge`. The review of a change runs on the owner's machine and not in CI: OpenAI's CI guide says "Do not use this workflow for public or open-source repositories" about ChatGPT sign-in (`learn.chatgpt.com/docs/auth/ci-cd-auth`).
- **Contributor licence agreement.** The workflow in `.github/workflows/cla.yml` uses `pull_request_target` and `issue_comment` to write to the base repository for fork PRs. It uses temporary GitHub tokens and performs no checkout. Exemptions use the authenticated PR author. Other PRs require the author's signature, and the action checks the commit authors it sees. A PR author who has no commit attributed to their account must add one to sign. The PR author's signature covers co-authored work they submit under section 7 of `CLA.md`. The action reads at most 100 commits, so squash larger PRs before submitting them.
  - Before the workflow reaches `main`, create the `cla-signatures` branch from `main` and seed the signature file named in the workflow with an empty `signedContributors` array. [Version 2.6.1](https://github.com/contributor-assistant/github-action/blob/ca4a40a7d1004f18d9960b404b97e5f30a505a08/src/setupClaCheck.ts) fails with a missing file. In the repository's Actions Policies, scope a **Restrict events** rule to this workflow and allow `pull_request_target` and `issue_comment`. GitHub enforces its public-repository default block on `pull_request_target` from 2 December 2026. Require the `cla` check on `main` immediately after the merge. Reopen or update older PRs to start their check. [GitHub's default event policy](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target#default-policy-for-pull_request_target)
  - The `version1` folder identifies the version of the agreement each signature covers. Give changes to the agreement a new folder and preserve the old ledger and agreement in Git history. The action records the comment ID and timestamp. If a signer edits or deletes the comment later, the ledger still holds the original record without the comment text.
  - GitHub reports `issue_comment` runs on the head of `main`. Check the `pull_request_target` run for the PR and its current head commit. If two PRs share a head commit, GitHub can show one PR's check result on both. Verify the run named for the PR number before merging, or ask its author to push a distinct head commit. [GitHub required check behavior](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks)
  - The pinned action reads only the first 30 PR comments and may mistake a contributor's comment for its own signing prompt. If the phrase was posted after the first 30 comments or the signing prompt fails to appear, open a fresh PR and sign there before other discussion.
- **Live demo.** The `deploy` job in `gate.yml` runs only on a push to `main`, after `gate` passes, in the environment `live`. After the checkout, its first step compares the run's SHA with the head of `main` and skips every other step when `main` has moved, so two quick merges end on the newer one. It builds the web bundle, runs `wrangler d1 migrations apply DB --remote --env live`, then `wrangler deploy --env live --keep-vars`, and reads the deployed address from the file that `WRANGLER_OUTPUT_FILE_PATH` names and requests its `/api/session` up to 11 times, 5 s apart, until one request answers 200. Migrations run first, so a failed migration never publishes code that needs the new schema; Wrangler rolls the failing migration back and keeps the earlier ones (`wrangler d1 migrations apply --help`, 4.159.0). The same order has a cost: the Worker that is still live runs on the new schema until `wrangler deploy` ends, and a migration that adds a `NOT NULL` column with no default or a foreign key makes that Worker's writes to the table fail with `NOT NULL constraint failed` or `FOREIGN KEY constraint failed`. `0008_thread_source.sql` is one: between the migration and the deploy, every thread write (an Extension save, a `.json` Paste, an X Paste with a thread, the fetch and `x_verify` publish of a thread) fails and its job retries, up to 3 attempts (`MAX_ATTEMPTS`, `src/core/contract/job-contract.ts`), and an Export that the old Worker starts and finishes in that window names the new migration in its manifest but holds records without `source`, so no Restore accepts it. Take no Export while such a deploy runs, and Export again after it. The container applies the migration in the one process that then serves, so it has no window. The concurrency group `live-deploy` never cancels a running deploy and sets `queue: max`, so it holds up to 100 pending runs and replaces none of them; without `queue: max`, the run that arrives later replaces the pending one, whatever its commit; the newest merge could then lose its deploy to a rerun of an older commit (GitHub Actions docs, workflow syntax, `concurrency`, https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax). Every pending run waits its turn, and the first step skips it when `main` has moved. The check is a step of `deploy` and not a job before it, because a job that `deploy` needs finishes before `deploy` waits in the concurrency group: a run that then waited behind another deploy would publish an older commit after `main` moved (GitHub Actions docs, workflow syntax, `jobs.<job_id>.needs` and `jobs.<job_id>.concurrency`). A failed deploy fails the run on `main` and is not retried.
  - **Names.** `env.live` in `wrangler.jsonc` names the Worker `threadsift-live` (the top-level name plus `-live`), the D1 database `threadsift-live`, the Queue `threadsift-live-jobs` as producer and consumer, the bucket `threadsift-live-files` and the `AI` binding, because an environment inherits `main`, `assets`, `triggers`, `limits` and `alias` but not bindings or variables ([Wrangler environments](https://developers.cloudflare.com/workers/wrangler/environments/), [configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), and `notInheritable` in wrangler 4.159.0). It carries no `database_id`: `wrangler d1 migrations apply --remote` looks the database up by `database_name` through the Cloudflare API (`getDatabaseByNameOrBinding` in wrangler 4.159.0). It sets `workers_dev` and inherits the top-level observability settings, including `redact_query_string`. The database and the Queue exist already. For a new Instance in another account, `pnpm run deploy --secrets-file /path/to/secrets.json` creates the missing D1 database before migrations; Wrangler creates the bucket and Queue during deploy (`cloudflare-deploy-button.md`).
  - **Variables and secrets.** The config holds no variable and no secret. `THREADSIFT_PUBLIC_ORIGIN` is a variable of the live Worker, set to its own `https://` origin, and `--keep-vars` stops the deploy from deleting it, because a deploy without the flag deletes every variable the config does not name ([wrangler deploy](https://developers.cloudflare.com/workers/wrangler/commands/workers/)). A deploy never deletes secrets and this one passes no `--secrets-file`, so the Worker keeps `THREADSIFT_SECRET_KEY` and every other secret it holds. Never replace that key against existing encrypted data.
  - **Recovery.** For a missing Worker, restore `threadsift-live` with its original `THREADSIFT_SECRET_KEY` before deploying. For a missing database, restore its data from a backup; for a missing Queue, recreate `threadsift-live-jobs` and its consumer binding. These are manual operations, because a deploy cannot decide which lost data or queued work is recoverable. The deploy no longer seeds a demo owner or demo Items, and it keeps whatever the live database holds.
- **Live check.** `.github/workflows/live-check.yml` runs by manual dispatch on `main` before a release. The workflow runs independently of the gate and deploy, once for each target in the environment `post-merge`; a failure fails the live-check workflow. It runs `smoke/live.spec.ts` against the same Worker and container the smoke spec starts. On both targets the spec sets up the owner, saves the workflow's `GITHUB_TOKEN` as the GitHub token and Pastes `https://www.sqlite.org/whentouse.html` and `https://github.com/KyaniteHQ/threadsift`, which the app fetches from the real internet.
  - **Worker: no model.** Each Paste carries a caller-sent Digest (`docs/spec.md`, Agent output per Item), which waits for the fetched text and publishes without a Provider call. The spec waits until both Items are read with `fetch: ok`, then checks that each Item shows its sent Topic, Summary, Key points and Tags. No Provider is saved, and `wrangler dev --local` runs no `ai` binding call (Local runs, `ai-tasks-and-providers.md`). The Worker run no longer proves the HTTP and Workers AI executors, the scheduled handler, the `topic_overview` task, Try again or Related Items on the Worker; the Worker's AI tasks are proven on the container only.
  - **Container: Claude Code.** The image ships no CLI (`docs/guides/providers.md`, Use Claude Code on the container). `live:container` sets `THREADSIFT_LIVE=1`, and `playwright.config.ts` then starts the image with `--env CLAUDE_CODE_OAUTH_TOKEN` and a command that runs the guide's `npm install --global @anthropic-ai/claude-code` into `/data/cli` before it starts the app, which replaces the guide's `podman exec` install and `podman restart` because Playwright owns the container process and the app finds the CLI at its first start. The install runs without the token, the setup code and the secret key in its environment, prints `claude --version` into the log, and passes `--min-release-age=3`, the 3-day rule of `pnpm-workspace.yaml` (`minimumReleaseAge`) and `renovate.json`, so each run installs the newest Claude Code release that is at least 3 days old and a release that breaks the executor fails the next run after it ages in. The spec saves the `claude-code` Provider with the model `claude-haiku-5-5` (`CLAUDE_MODEL` in the spec), chosen to keep the check's use of the owner's subscription low, and checks that the saved settings keep it; the app passes it to the CLI as `--model`. It presses Verify as the guide does (one real Digest, so a refusal such as `provider-busy` fails the run at once), and waits up to 5 minutes for one Digest, then up to 5 minutes more until `GET /api/topics/<key>` for that Digest's Topic answers a written overview (`overview.text` not null, so the `topic_overview` job ran). It then Pastes `https://www.sqlite.org/wal.html`, waits for its Digest, writes the first article's Digest again (`POST /api/items/<id>/digest`) and waits up to 5 minutes until the first article lists the second as a Related Item. The Digest jobs need no scheduler request, because the container's job loop runs them. The only Provider on the Instance is Claude Code, so a published Digest was written by it.
  - **Token.** `CLAUDE_CODE_OAUTH_TOKEN` comes from `claude setup-token` on the owner's Claude subscription (`docs/spec.md`, AI providers). Locally it comes from the owner's secret store; in CI it is a secret of the `post-merge` environment, and the workflow passes it to the container job only. An empty value fails the `live:image` task, which checks it and then runs the same build script as `container:build`, so the run stops before the image builds, with a message that names the variable and `claude setup-token`. A separate check task ordered before `container:build` with `before` would run in every run that builds the image, `smoke:container` included, because devenv pulls in the tasks that a task runs after, and `wantedBy` does not limit that (devenv 2.4.0, run on 2026-11-11; [devenv tasks](https://devenv.sh/tasks/)). A plan at its usage limit answers the CLI with HTTP 429, which the executor maps to `provider-busy`, so Verify fails with that refusal and the container log holds `cli-refused` with reason `provider-busy`; the Digest wait is never reached.
  - **Job timeout.** `timeout-minutes: 30` is above the 20-minute test timeout in `playwright.config.ts` plus the 3-minute server start, the devenv setup (33 s) and an image build (47.2 s without the registry layer cache, the `container:build` line of gate run 42912994763, attempt 4, 2026-11-10).
- **Image.** `.github/workflows/gate.yml` publishes amd64 images through the `image` job after the gate passes. The release workflow builds both architectures with provenance attestations. The runner is pinned to `ubuntu-26.04` instead of `ubuntu-latest`, so its kernel setting changes only when a Renovate pull request moves the pin and its `image` run passes ([runner image announcement](https://github.com/actions/runner-images/issues/14748)). Podman comes from the devenv shell, so `devenv.lock` sets its version. The shell also sets the storage paths Podman uses (`docs/architecture/development-environment.md`, `env`). The `image:build` task is `container:build` without the smoke label and its prune. A rerun reuses the existing `:sha-<full commit sha>` digest and start-checks it again. The `image-publish` queue holds the whole job, so runs build one after another. The job retains immutable `:sha-<full commit sha>` tags and moves `:main` only to a digest that passes `tools/start-check.sh`, while `.github/actions/main-head` prevents an older commit from moving `:main`. Run the workflow by hand (`workflow_dispatch`) with `publish` left `false` to build and start-check locally without a push; `publish: true` is accepted only on `main`. A new package starts private, and GitHub has no API to change that, so the owner makes `ghcr.io/kyanitehq/threadsift` public once in the package settings.
- **Start check.** `tools/start-check.sh <image>` (`docs/testing.md`) counts its 60 s from the container start, not from the pull. CI uses it on every image it publishes, and it runs on a developer machine the same way, so a host that keeps a new image can call it before the switch. `tools/image-digest.sh <reference>` prints a registry tag's digest, prints nothing when the tag does not exist, and fails when the registry cannot answer, so no step takes an outage for a missing tag.
- **Releases.** `.github/workflows/release.yml` handles version tags separately from `gate.yml`, so an ordinary push to `main` never moves `release`. Both jobs run only in `KyaniteHQ/threadsift`. A tag must name a commit on `main`; the build fails before publication when that ancestry check fails. The `release` concurrency group serializes whole runs; their order is not guaranteed. The publish checkout keeps full history so later releases can advance `release` with a fast-forward push. Before publication it checks that ancestry and validates a dry-run image index. If publication succeeds but the branch push fails, rerun the failed publish job: it reuses the recorded digests, and creating the same index again is idempotent. Each build records its pushed digest before runtime checks; those artifacts also identify untagged versions left by a failed check for manual cleanup. The pre-release proof ran on 2026-11-17 ([first release run](https://github.com/KyaniteHQ/threadsift/actions/runs/44159949236), [second release run](https://github.com/KyaniteHQ/threadsift/actions/runs/44164286715)). The `docker buildx imagetools inspect` output showed both platforms and two attestation manifests in each run. The native arm64 start checks answered 200 after 3 s and 2 s, and each published amd64 image passed the container smoke. The `release` branch advanced from `17cbeb071f78f4713db62adc5fa8edfd0f910420` to its direct child `73f3cc458d4011825d50187f5165abd741b97720`; the intervening [ordinary main run](https://github.com/KyaniteHQ/threadsift/actions/runs/44162780681) left it at the first commit. Cleanup removed both pre-release tags, all 14 package versions the proof created and the temporary `release` branch, with registry and ref read-back. It kept all 638 baseline package versions and the ordinary main image; no proof version or temporary ref remains.
- **Rollback.** The container can run an older image tag. Cloudflare can restore an older Worker version with `wrangler rollback`. Neither undoes a migration. An older build cannot write the rows of a table whose migration added a `NOT NULL` column or a key, so after `0008_thread_source.sql` a rollback to an older Worker needs D1 Time Travel to a minute before the migration (`export-backup-and-restore.md`), and the container needs the database file copied before the upgrade. Writes after that minute are lost. After `0011_items_guarded_in_batch.sql`, which drops the trigger `items_restoring` and the column `restores.writing`, an older Worker refuses no Paste during a Restore and fails every Restore slice, so roll back only while no Restore holds the library, or use Time Travel as above.
