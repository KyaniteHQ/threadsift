# CI, releases and rollback

- **Gate.** `.github/workflows/gate.yml` runs on every pull request and on every push to `main`. The `check` job installs once and runs `devenv tasks run ci:gate` (Development environment, `tasks`), within 10 minutes. The `smoke` job runs the browser smoke spec on the Worker and on the container image, one runner each, within 15 minutes. The `container:build` task builds the image while `ci:install` runs, because the build reads only the `Containerfile` and the source tree; the first build step began 3.7 s after the tasks started, while `ci:install` still ran, against 6.9 s when the Playwright `webServer` built it behind `ci:install` and the Playwright start (`smoke (container)` logs of runs 42902189977 and 42898244547, 2026-11-10). The container start gets 60 s in `playwright.config.ts`, about 12 times the 5 s it took in that run, so Playwright fails before the job's budget ends and the artifact still uploads. That `podman build` passes `--jobs 0`, which builds the Containerfile's stages in parallel instead of one after another; the image build took 28 s against 42 s without it (from `[1/5] STEP 1/1` to `Successfully tagged` in the `smoke (container)` logs of runs 42894300041 and 42883935991, 2026-11-10). Fail-fast is off, so a failed target leaves the other running, and a failed smoke run uploads Playwright's `test-results` for 7 days. When the first test of the container smoke fails, `smoke/container-capture.ts` writes `test-results/container-failure/` while the container still runs, because `--rm` and the `webServer` teardown remove the container before a later workflow step could read it, and the existing failure upload carries the folder. The folder tells a persistent port-forward fault from an app fault; after an app crash the container is already gone, so the events and the container log are what remains. A newer push cancels the older run of a pull request. Check, build, audit, the design check and the core tests share one job because each separate job pays about 32 seconds of setup (the `setup-devenv` step of each job in run 42894300041, 2026-11-10).
- **Shell setup and package cache.** Unmodified `pkgs.corepack` is available from `cache.nixos.org`, so cold runners avoid its build and install checks. pnpm 12 reads `pnpm_config_store_dir` for the cached store and ignores `npm_config_store_dir`. The action does not cache the Nix store itself, because a restored store was no faster than the binary caches. With `nix-community/cache-nix-action` v7.0.2 added to `.github/actions/setup-devenv` before `nix profile add` and keyed on `devenv.lock`, `devenv.nix` and the action file, a warm job restored 1043 MB in a step of 25 to 29 s, `nix profile add` fell from about 19 s to under 1 s and the shell evaluation from 11.0 to 13.3 s (20.1 s in one slow job) to 2 to 3.5 s, so the setup step plus the shell evaluation took 42 to 49 s per job, against 37 to 58 s without the store cache, where the 58 s is that slow job; in the cold run, saving it took 14.5 s in the job that saved it and 16.5 s in a job that lost the race to save it (attempts 2 and 3 of run 42906685884 against runs 42896225092, 42897469087, 42897869989, 42905609594 and attempt 1 of 42906685884, 2026-11-10).
- **Container layer cache.** The container target of `smoke` and `live-check` reuses the image's build steps from the last cache that a push to `main` saved. `container:build` serves the folder that `THREADSIFT_LAYER_CACHE` names through a local registry and builds with `--cache-from` and `--cache-to` on it (`devenv.nix`), because Podman 5.8.9 takes only a registry repository for those flags (`man podman-build`). `gate.yml` and `live-check.yml` restore the folder through `.github/actions/layer-cache-restore`, which holds the key; only the `smoke` job on a push saves it when the key misses. A pull request run only reads the cache, and one with nothing to read builds without the registry, so a pull request never pays for filling or saving the cache. A pull request cache could not reach `main` in any case: "Caches created by a `pull_request` run are already scoped to the merge ref" ([GitHub Actions docs, dependency caching](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching), read 2026-11-11). The key hashes the `Containerfile` and the package and lock files and has no `restore-keys` prefix, so a dependency change starts a new cache of about 457 MB and old dependency layers never pile up. The key holds no date, so the smoke image's `apt-get install ca-certificates` layer is refreshed only when the key changes; no released image is built from this cache.
  - **Measured.** On a pull request that changed one file under `src/`, `container:build` took 28.0 and 28.3 s and the `smoke (container)` job 90 and 91 s with the cache, 15 of the 26 build steps coming from it, against 47.2 and 53.1 s and 107 and 117 s at the same commit after the cache was deleted (attempts 1 to 4 of run 42912994763, 2026-11-11). Filling the cache made a build 16 s longer, 68 s against 52 s on a workstation with empty Podman storage (2026-11-10), and the push that fills it also saves the folder.
  - **Not chosen.** The `registry:3` image in a container: `podman run` began pulling it 11.5 s after the task began, while `podman build` alone printed its first step after 3.7 s (`smoke (container)` logs of runs 42904428239 and 42902189977, 2026-11-10). The nixpkgs `distribution` binary instead adds a 20 MB download (`downloadSize` of `nix path-info --json` on cache.nixos.org) to every job's shell. GHCR written from `main` would need no registry, but it needs `packages: write` and a package visibility setting.
- **Nix input downloads.** `nix profile add` and the first `devenv` command download each locked GitHub input from `https://api.github.com/repos/<owner>/<repo>/tarball/<rev>`. A cold runner makes at most 5 such requests per job: 1 in `nix profile add` (devenv-nixpkgs, which holds the `devenv` package) and 4 in `devenv` (devenv, devenv-nixpkgs, nixpkgs and git-hooks.nix from `devenv.lock`). The `devenv` count comes from the `Downloading https://api.github.com` lines of `devenv -v info` on a runner with Nix 2.35.4 and devenv 2.4.0, when `nix profile add` still installed devenv from `cachix/devenv` (run 42428719602, 2026-11-08). The `nix profile add` count comes from `XDG_CACHE_HOME=<fresh dir> nix --store <fresh dir> build --no-link -v "github:cachix/devenv-nixpkgs/<rev>#devenv" 2>&1 | grep -c "downloading 'https://github.com"`, which printed 1; the same command for `github:cachix/devenv/b904dcb51fe48c30db250038241507f60752f222#devenv`, the old install, printed 5 (Nix 2.34.9 on a workstation, 2026-11-10). That Nix had no `access-tokens` entry and so used `https://github.com/<owner>/<repo>/archive/<rev>.tar.gz` instead of the API URL, and the runner's URL form was not measured. With the fetcher cache restored, each gate job copies 1 source tree from the binary caches, against 6 when the install came from `cachix/devenv` (`grep -c "copying path '/nix/store/[a-z0-9]*-source'"` on each job log of runs 42894300041 and 42883935991, 2026-11-10). `.github/actions/setup-devenv` caches `~/.cache/nix`, Nix's tarball and fetcher caches (about 108 MB compressed), under a key that hashes `devenv.lock` and the action file, which holds the Nix installer pin. A job that restores it makes 0 requests: the second job of that run, on a fresh runner, logged none. The pull request gate runs 3 jobs that set up devenv (`check`, and `smoke` for the Worker and for the container), so a cold gate makes at most 3 × 5 = 15 requests within the same minutes and a warm gate makes 0. The deploy and each target's live check run the same install and locked evaluation, so each should make at most 5 cold and 0 warm. The lock update runs `devenv update`, which resolves moving inputs and downloads each new revision whatever the cache holds; its count was not measured.
  - **The 429 is not the hourly quota.** `GET /rate_limit` with the workflow token read `limit` 5000 (the docs give 1,000 for `GITHUB_TOKEN`), and `core.used` stayed at 54 across two `nix flake prefetch github:...` calls with `access-tokens` set, then rose to 57 after 3 `GET /zen` calls (run 42429313493, 2026-11-08). The 429 body in a failed pull request copy run was `429: Too Many Requests` and a notice about scraping. Another author passed a token to Nix in three ways and still got the same 429 with 0 of 5000 used, and concluded it is GitHub's anti-abuse limit on the egress addresses that runners share ([Chasing a GitHub 429 across my Emacs CI](https://www.d12frosted.io/posts/2026-06-29-chasing-a-github-429)). That cause is an inference: GitHub shows no counter for it. So no per-hour sum limits the gate, and the cache cuts the requests that meet the throttle. One untried alternative: Nix 2.35.4 downloads from `https://github.com/<owner>/<repo>/archive/<rev>.tar.gz` instead of the API when no `access-tokens` entry matches (`GitHubInputScheme::getDownloadUrl` in `src/libfetchers/github.cc`); whether that endpoint throttles the same way needs a cold run with both the installed Nix and devenv's Nix.
  - **When the cache misses.** A change to `devenv.lock` or the Nix installer pin gives a new key. The `restore-keys` prefix then restores the newest cache saved under an older key, so the first run after the change should download only the inputs whose revision changed; that partial restore was not measured, and with no older cache every job is cold. A cache made by a pull request run is visible only to that pull request's merge-ref runs; a run on any branch restores the caches of the default branch (GitHub Actions docs, dependency caching, Restrictions for accessing a cache), so the first gate on `main` after the merge seeds the key for the next pull requests. Nix retries a throttled download 5 times and then fails the job; the action adds no retry, because a retry on the same address hides a throttle instead of avoiding it, and a rerun of the job is the repair. The restore from `main`'s cache by a pull request run was not run.
- **Merging.** `main` requires one aggregate `gate` job that needs `check` and `smoke` and passes when each passed or skipped itself; a workflow-level `paths` filter is not used, because a workflow it skips leaves its required checks pending. Renovate opens dependency updates after a 3-day wait.
- **Secrets and forks.** No pull request job holds a secret, and no job uses `pull_request_target`. The secret-free `bundle` workflow uploads PR build artifacts. The `pr-preview` workflow runs trusted code from `main` and deploys only same-repository artifacts; the `preview` environment permits only `main`. Cleanup runs from `main` on pushes, on a schedule and by dispatch. The live deploy uses the `main`-only environment `live`, and the local-runtime live check uses the `main`-only environment `post-merge`. Read [Operate PR previews](../pr-previews.md) for the artifact trust and cleanup procedure. The review of a change runs on the owner's machine and not in CI: OpenAI's CI guide says "Do not use this workflow for public or open-source repositories" about ChatGPT sign-in (`learn.chatgpt.com/docs/auth/ci-cd-auth`).
- **Live demo.** The `deploy` job in `gate.yml` runs only on a push to `main`, after `gate` passes, in the environment `live`. Its first step compares the run's SHA with the head of `main` and skips every other step when `main` has moved, so two quick merges end on the newer one. It builds the web bundle, runs `wrangler d1 migrations apply DB --remote --env live`, then `wrangler deploy --env live --keep-vars`, and reads the deployed address from the file that `WRANGLER_OUTPUT_FILE_PATH` names and requests its `/api/session` up to 11 times, 5 s apart, until one request answers 200. Migrations run first, so a failed migration never publishes code that needs the new schema; Wrangler rolls the failing migration back and keeps the earlier ones (`wrangler d1 migrations apply --help`, 4.158.0). The concurrency group `live-deploy` never cancels a running deploy and sets `queue: max`, so it holds up to 100 pending runs and replaces none of them; without `queue: max`, the run that arrives later replaces the pending one, whatever its commit; the newest merge could then lose its deploy to a rerun of an older commit (GitHub Actions docs, workflow syntax, `concurrency`, https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax). Every pending run waits its turn, and the first step skips it when `main` has moved. The check is a step of `deploy` and not a job before it, because a job that `deploy` needs finishes before `deploy` waits in the concurrency group: a run that then waited behind another deploy would publish an older commit after `main` moved (GitHub Actions docs, workflow syntax, `jobs.<job_id>.needs` and `jobs.<job_id>.concurrency`). A failed deploy fails the run on `main` and is not retried.
  - **Names.** `env.live` in `wrangler.jsonc` names the Worker `threadsift-live` (the top-level name plus `-live`), the D1 database `threadsift-live`, the Queue `threadsift-live-jobs` as producer and consumer, the bucket `threadsift-live-files` and the `AI` binding, because an environment inherits `main`, `assets`, `triggers`, `limits` and `alias` but not bindings or variables ([Wrangler environments](https://developers.cloudflare.com/workers/wrangler/environments/), [configuration](https://developers.cloudflare.com/workers/wrangler/configuration/), and `notInheritable` in wrangler 4.158.0). It carries no `database_id`: `wrangler d1 migrations apply --remote` looks the database up by `database_name` through the Cloudflare API (`getDatabaseByNameOrBinding` in wrangler 4.158.0). It also sets `workers_dev` and the observability settings that the earlier deploy tool wrote into the live Worker, including `redact_query_string`, so a request URL with a query never reaches the logs. The database and the Queue exist already; a new account makes them with `wrangler d1 create` and `wrangler queues create` before the first deploy, and `wrangler deploy` makes the bucket.
  - **Variables and secrets.** The config holds no variable and no secret. `THREADSIFT_PUBLIC_ORIGIN` is a variable of the live Worker, set to its own `https://` origin, and `--keep-vars` stops the deploy from deleting it, because a deploy without the flag deletes every variable the config does not name ([wrangler deploy](https://developers.cloudflare.com/workers/wrangler/commands/workers/)). A deploy never deletes secrets and this one passes no `--secrets-file`, so the Worker keeps `THREADSIFT_SECRET_KEY` and every other secret it holds. Never replace that key against existing encrypted data.
  - **Recovery.** For a missing Worker, restore `threadsift-live` with its original `THREADSIFT_SECRET_KEY` before deploying. For a missing database, restore its data from a backup; for a missing Queue, recreate `threadsift-live-jobs` and its consumer binding. These are manual operations, because a deploy cannot decide which lost data or queued work is recoverable. The deploy no longer seeds a demo owner or demo Items, and it keeps whatever the live database holds.
- **Live check.** `.github/workflows/live-check.yml` runs daily at 00:17 UTC on `main` and supports manual dispatch on `main`. GitHub can delay or drop a scheduled run during periods of high load ([scheduled workflows](https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows#schedule)). The workflow runs independently of the gate and deploy, once for each target in the environment `post-merge`; a failure fails the live-check workflow. It runs `smoke/live.spec.ts` against the same Worker and container the smoke spec starts. On both targets the spec sets up the owner, saves the workflow's `GITHUB_TOKEN` as the GitHub token and Pastes `https://www.sqlite.org/whentouse.html` and `https://github.com/KyaniteHQ/threadsift`, which the app fetches from the real internet.
  - **Worker: no model.** Each Paste carries a caller-sent Digest (`docs/spec.md`, Agent output per Item), which waits for the fetched text and publishes without a Provider call. The spec waits until both Items are read with `fetch: ok`, then checks that each Item shows its sent Topic, Summary, Key points and Tags. No Provider is saved, and `wrangler dev --local` runs no `ai` binding call (Local runs, `ai-tasks-and-providers.md`). The Worker run no longer proves the HTTP and Workers AI executors, the scheduled handler, the `topic_overview` task, Try again or Related Items on the Worker; the Worker's AI tasks are proven on the container only.
  - **Container: Claude Code.** The image ships no CLI (`docs/guides/providers.md`, Use Claude Code on the container). `live:container` sets `THREADSIFT_LIVE=1`, and `playwright.config.ts` then starts the image with `--env CLAUDE_CODE_OAUTH_TOKEN` and a command that runs the guide's `npm install --global @anthropic-ai/claude-code` into `/data/cli` before it starts the app, which replaces the guide's `podman exec` install and `podman restart` because Playwright owns the container process and the app finds the CLI at its first start. The install runs without the token, the setup code and the secret key in its environment, prints `claude --version` into the log, and passes `--min-release-age=3`, the 3-day rule of `pnpm-workspace.yaml` (`minimumReleaseAge`) and `renovate.json`, so each daily run installs the newest Claude Code release that is at least 3 days old and a release that breaks the executor fails the check once it ages in. The spec saves the `claude-code` Provider with the model `claude-haiku-5-5` (`CLAUDE_MODEL` in the spec), chosen to keep the daily run's use of the owner's subscription low, and checks that the saved settings keep it; the app passes it to the CLI as `--model`. It presses Verify as the guide does (one real Digest, so a refusal such as `provider-busy` fails the run at once), and waits up to 5 minutes for one Digest, then up to 5 minutes more until `GET /api/topics/<key>` for that Digest's Topic answers a written overview (`overview.text` not null, so the `topic_overview` job ran). It then Pastes `https://www.sqlite.org/wal.html`, waits for its Digest, writes the first article's Digest again (`POST /api/items/<id>/digest`) and waits up to 5 minutes until the first article lists the second as a Related Item. The Digest jobs need no scheduler request, because the container's job loop runs them. The only Provider on the Instance is Claude Code, so a published Digest was written by it.
  - **Token.** `CLAUDE_CODE_OAUTH_TOKEN` comes from `claude setup-token` on the owner's Claude subscription (`docs/spec.md`, AI providers, CLIs). Locally it comes from the owner's secret store; in CI it is a secret of the `post-merge` environment, and the workflow passes it to the container job only. An empty value fails the `live:image` task, which checks it and then runs the same build script as `container:build`, so the run stops before the image builds, with a message that names the variable and `claude setup-token`. A separate check task ordered before `container:build` with `before` would run in every run that builds the image, `smoke:container` included, because devenv pulls in the tasks that a task runs after, and `wantedBy` does not limit that (devenv 2.4.0, run on 2026-11-11; [devenv tasks](https://devenv.sh/tasks/)). A plan at its usage limit answers the CLI with HTTP 429, which the executor maps to `provider-busy`, so Verify fails with that refusal and the container log holds `cli-refused` with reason `provider-busy`; the Digest wait is never reached.
  - **Job timeout.** `timeout-minutes: 30` is above the 20-minute test timeout in `playwright.config.ts` plus the 3-minute server start, the devenv setup (33 s) and an image build (56 s with a layer cache, in gate run 43055405118; a cold build is not measured, so the rest of the margin covers it).
- **PR previews and design review.** `.github/workflows/pr-preview.yml` publishes an isolated same-repository PR Instance and a GitHub deployment status with its URL for Impeccable Reviews. Preview failures do not enlarge or block the gate. Read [Operate PR previews](../pr-previews.md) before changing or running that lifecycle. The static check `impeccable detect --github web` stays in the `check` job.
- **Image.** After the `gate` job passes on a push to `main`, `image-head` runs the check that `deploy` makes (`.github/actions/main-head`), and every later job skips its work when `main` has moved past the commit. The `image` job builds the `Containerfile` once per architecture on a native runner, `ubuntu-24.04` for amd64 and `ubuntu-24.04-arm` for arm64, with no QEMU. Both legs pin one Ubuntu release so they share one Podman and one kernel setting, because `ubuntu-latest` moves to 26.04 in November 2026 (runner-images issue 14748). The build is the `image:build` task, which is `container:build` without the smoke label and its prune, so the published image carries no smoke label. The amd64 build reads the layer cache the `smoke` job saves, and arm64 has none. Each leg pushes `ghcr.io/kyanitehq/threadsift:sha-<full commit sha>-<arch>` unless that tag exists, so a `:sha-` tag never moves and a rerun checks the existing digest instead. It then removes its local images, pulls the digest, runs `tools/start-check.sh` on it and uploads the digest. The `image-publish` job runs one at a time and queues. It makes the manifest `:sha-<full commit sha>` from the two digests the legs checked, or takes the existing one, runs the start check on the manifest's digest and attests that digest with `actions/attest-build-provenance` (`push-to-registry: true`). That action reads credentials only from `~/.docker/config.json`, so both jobs log in with `docker login` through `.github/actions/ghcr-login`. It then runs the `main` check again, confirms that `:sha-<sha>` still has the tested digest, copies the manifest to `:main` by digest with `skopeo copy --all --preserve-digests` and reads `:main` back. A failed start check fails the job and leaves `:main` on the previous digest. `:sha-<sha>` tags are never moved or deleted. The jobs use only `GITHUB_TOKEN` with `packages: write`, and `image-publish` also `id-token: write` and `attestations: write`. Run the workflow by hand (`workflow_dispatch`) with `publish` left `false` to build both architectures and run the start check on the locally built image with nothing pushed; `publish: true` is accepted only on `main`. A new package starts private, and GitHub has no API to change that, so the owner makes `ghcr.io/kyanitehq/threadsift` public once in the package settings. `gh attestation verify oci://ghcr.io/kyanitehq/threadsift:sha-<sha> -R KyaniteHQ/threadsift` checks the provenance of a published image.
- **Start check.** `tools/start-check.sh <image>` pulls the image when it is not local, then runs it with `podman run`, a fresh volume at `/data` and `PORT=8080`, and asks `GET /api/session` until it answers 200. The 60 s limit counts from the container start, not from the pull. It removes the container and the volume. It exits 0 on the answer and 1 when the container exits first or the 60 s pass, printing the container's last 40 log lines. CI uses it on every image it publishes, and it runs on a developer machine the same way, so a host that keeps a new image can call it before the switch. `tools/image-digest.sh <reference>` prints a registry tag's digest, prints nothing when the tag does not exist, and fails when the registry cannot answer, so no step takes an outage for a missing tag.
- **Releases.** Not built: no release workflow exists. The plan is that a release tag builds and publishes the image with that tag and moves the `release` branch to it.
- **Rollback.** The container rolls back by running the previous image tag: every `:sha-<sha>` tag stays, so the rollback block of `docs/guides/self-hosting.md` (Go back to an older build), which runs a `:sha-<sha>` tag on the same `/data` volume with the same `THREADSIFT_SECRET_KEY` file, is a rollback target, and `:main` stays on the last image that passed the start check. Version tags come with the releases. Cloudflare rolls back with `wrangler rollback` to the previous Worker version. Both work because a migration only adds and the previous release still runs on the new schema, except that a saved `claude-code` Provider row stops the previous container's AI settings until it is switched or removed (see CLI executor, Storage). Grok Bot as the Provider is the flag `use_as_provider` on `grok_bot_settings`, a column the previous release ignores, so after a rollback it reads the `settings` row, which keeps the last Provider the owner saved, and runs on it with no step to take. Run on 2026-11-13 with release `f2fc4bc` (built from its source) on a volume and on a local D1 that the newer release had migrated, with the flag set and one open bot task: `GET /api/settings/ai` and `PUT /api/settings/ai` answered 200 with the stored Provider, and a Digest job that waited on the bot was claimed by the previous release and ran on the stored Provider. The container run reached an unreachable address and the Worker run reached the Workers AI binding, which the local Worker has no model behind, so both ended the job in a refusal and neither shows an answer. On the Worker, a loopback address is refused by the public-only rule, so the proof saved Workers AI. The open bot task stayed `running` until its deadline. Rolling forward kept Grok Bot selected, so a Provider saved while the previous release ran does not clear the flag; save it again on the newer release.
  - **Identity version.** The `item-identity` step changes values, and its release adds two tables the previous release ignores, so the previous release opens the migrated database and treats `normalized_url` as an opaque key. Reads, opening an Item and deleting it by id keep working. A refresh through an original spelling does not: the previous release computes the old identity from the pasted link, so an X link with a handle or a mixed-case GitHub link makes a second Item, and the retry button on the web app sends `originalUrl`. The place line shows `x.com` for a migrated X post because the handle is not in the identity. A rollback changes no stored identity back.
  - **Catalog key version.** The `topic-keys` and `tag-keys` steps change keys and delete the losing rows, and they add no table. A rollback while a `tag-keys` run is unfinished loses decisions: the previous release's merge of two Tags deletes the losing Tag, and a `proposals` row that names it goes with it by cascade, so a rejected pair of that Tag can be suggested again. The previous release opens the migrated database and keeps every name, link and Digest. It looks a Topic or Tag up by its own key, which differs from the new key for a name with `ß`, a sigma, an `İ` or an accent written in decomposed form: its filter for such a name answers nothing, and a Digest with that name makes a second row with the old key and the same name. Rolling forward again does not merge them, because the recorded version already says the steps are complete. To merge them, delete the two rows (`DELETE FROM data_steps WHERE name IN ('topic-keys', 'tag-keys')`, through `wrangler d1 execute` or the container's database); the next start, tick or Paste runs the steps again and merges by the same rule.
  - **Topic Pin version.** `0042_topic-merge-pins.sql` rebuilds `pins` and stays in the database on a rollback. The release before it (the weekly Topic check) reads only `tag-merge` Pins, and its `pin-keys` recomputes a Topic Pin's key with the same function and changes nothing else, so a seeded Topic Pin does no harm there; a Digest it publishes can create the merged-away Topic again. Rolling forward does not repair that by itself, because `pin-keys` already recorded its version. The recovery is the one below for Tags: `DELETE FROM data_steps WHERE name = 'pin-keys'` makes the next start, tick or Paste merge every Topic that holds a Topic Pin's key into its target, with its Items, stored Digests and Log lines. Accept of a Topic merge writes Topic Pins, so a rollback to the release before `0042_topic-merge-pins.sql` can create a merged-away Topic again through a Digest, and the same recovery repairs it. Rollback is one release back.
  - **Topic merge version.** `0043_merge-topic-log-action.sql` replaces the `log_entries_action` triggers and stays in the database on a rollback. The release before it opens the migrated database: its Log read selects only the actions it knows, so it lists no `merge-topic` line and answers 200, it publishes a Digest that names a pinned Topic onto the survivor, deletes an Item, answers 404 for the merged-away address and refuses Accept of a Topic row (`not-supported`). A Topic row left `accepting` shows "Applying…" there and blocks Accept of a Tag row with `merge-busy`, and nothing continues it until the roll forward, when the `merges` stage finishes it. Accept of a Topic merge cannot be undone, and no rollback restores the merged-away Topic.
  - **Pin version.** The release before the Pins ignores them: a Digest it publishes can create the merged-away Tag again, and it deletes a Tag only by a key merge, which fails on a Tag a Pin targets (the unit rolls back and retries). Rolling forward does not repair a recreated Tag by itself, because `pin-keys` already recorded its version and the older-Digest linking reads only Items with no Topic. To merge it, delete the step's row (`DELETE FROM data_steps WHERE name = 'pin-keys'`, through `wrangler d1 execute` or the container's database); the next start, tick or Paste runs the step again and merges every Tag that holds a Pin's key into the Pin's target.
