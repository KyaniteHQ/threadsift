# Extension and Threadsift bot

`extension/` holds the Extension's page save, Reddit thread save and fill-when-opened. `bot/` holds the Threadsift bot: its profile, one skill, two routine prompts, the setup and update guides and the one script that makes every call. Connect Reddit is not built.

- The Extension is built with WXT for desktop Chrome and Firefox (Manifest V3) and posts to `POST /api/items` with an agent token. It saves one page per click and never crawls.
  - **Reddit.** On Save in a tab on a Reddit post or comment, the background worker asks the tab for `<thread>/.json?limit=500&raw_json=1` through `scripting.executeScript` with a function that calls `fetch`, so the request carries the tab's Reddit session (`extension/lib/reddit-thread.ts`). `hiddenRepliesOf` (`src/core/reddit-tree.ts`, built on the `walk` the server's parser uses, so an answer the parser would refuse yields no ids) lists the comment ids behind each `more` stub of an answer: the stub's `children`, or, for a stub with none ("continue this thread"), its parent comment. The worker requests each id at `/comments/<post>/_/<id>.json?limit=500&raw_json=1`, because `/api/morechildren` answered 403 to the signed-in session (owner's browser, 2026-11-04), reads the stubs of that answer the same way, and posts every answer in one request: `{url, content: [thread, ...permalink answers]}`. The pace is our choice, not Reddit's: 500 ms between the starts of two requests and 150 s per thread (`REQUEST_SPACING_MS`, `FILL_DEADLINE_MS`), against the 67 requests that a 677-comment thread needed in the 2026-11-05 run (`docs/spec.md`, Fetchers). The count is Reddit's: it answers `.json` requests with `x-ratelimit-used`, `x-ratelimit-remaining` and `x-ratelimit-reset`, allows 100 requests per window of about 600 s (owner's browser, 2026-11-13; the window length is inferred from the `reset` values) and refuses the 101st with HTTP 429. The injected function returns `x-ratelimit-remaining` with each answer, even when it fails while reading the body. A `RequestWindow` (`src/core/reddit-window.ts`) counts every request of the fill, the thread's own included, and keeps the last count Reddit reported; an answer without a readable header takes 1 off that count, and the fixed cap of `REDDIT_WINDOW_REQUESTS` applies on its own only while no header was read. `mayAsk` stops the fill before the request that would be refused. The deadline is checked again after the spacing wait: no request starts once the 150 s are used, and the timeout of each request (15 s) is cut to the time left, so the fill never runs past the deadline by a request. The fill still stops at the first HTTP 429, which covers another `.json` request that used the window, such as a second thread saved within 10 minutes. Any other failed request is not retried and leaves its stub. The thread is saved with what the fill read. `unfilledStubsOf` (`src/core/reddit-tree.ts`) merges the answers the way the server does and counts the stubs left in the tree, those with no id to request and those whose permalink answer was empty included; when it finds any, the popup says so (`saved-incomplete` in `extension/lib/state.ts`) instead of "Page saved.", without naming a cause. When the thread's own request fails and the visible page is saved instead, the popup says that (`saved-page`). The fill stops asking once the answers it holds are over 8 MiB in characters, a lower bound of their bytes. The Extension then measures the UTF-8 length of the body it will send, `JSON.stringify({url, content})`, and drops trailing answers until the body is at most 8 MiB; the stubs of the answers left out stay as stubs, which the Reader shows as Context stubs that say they were not saved. A first answer that does not fit alone sends the page fallback instead. The function injected into the tab stops reading an answer at 4 MiB (`Content-Length`, or the stream once it passes the limit) and returns no answer, so an answer over the limit is never transferred to the worker or parsed; the server enforces the same limit in `paste` (413). The save request's refusal for a link that takes no page carries `code: unsupported-link` (`UNSUPPORTED_PAGE_LINK` in `src/core/supplied-page.ts`), which the popup matches instead of the error text. The Extension's own trimming runs only in a signed-in tab. When the thread's own `.json` request fails, or its answer is not a thread of the post in the link, the worker injects `capture.js` and posts `{url, page}`; for a Reddit link the script takes the title from Defuddle's Reddit extractor, because the page's `<title>` ends in the community name.
  - **Connect Reddit (self-hosted builds).** The button reads the `reddit_session` cookie through the `cookies` API, which needs the `cookies` permission and host permission for reddit.com (Chrome Extensions docs, chrome.cookies), and sends its value and `expirationDate` to the Instance with the agent token. Whether the API returns the `HttpOnly` cookie in Chrome and Firefox is checked when the button is built. The Instance side exists: the owner pastes the cookie value in Settings (`PUT /api/settings/reddit-account`), and `connectRedditAccount`, `redditAccountState` and `disconnectRedditAccount` in `src/core/reddit-account.ts` are what the button's own route reuses. The Extension's fill loop is `fillAnswers` in `src/core/thread-fill.ts`, which the server's account fetch calls too.
  - **Fill when opened.** The owner opts in once on the settings page (Fill saved Reddit Items), where Turn on asks the browser for `https://*.reddit.com/*`, one of the optional host permissions the manifest already lists. The opt-in is the grant plus the `fill` flag the background worker stores when the owner presses Turn on or Turn off (a missing flag follows the grant, so an opt-in from an earlier version stays on): the page reads both through the worker, so a revoke in the browser's own settings turns filling off. The background worker registers `fill.js` with `scripting.registerContentScripts` for every page of `reddit.com` and its subdomains (`REDDIT_HOSTS` in `extension/lib/config.ts`, the same pattern as the grant) when the permission is held and removes it when it is not (`syncFillScript`, `extension/lib/fill-script.ts`; run at every worker start and on `permissions.onAdded` and `onRemoved`, because MDN says registered scripts are cleared when the extension updates). `fill.js` is an unlisted script, not a WXT `registration: "runtime"` content script, because WXT 0.21.5 adds the `matches` of such a script to the manifest's `host_permissions` (`wxt/dist/internal/manifest.mjs`), which would grant Reddit at install. The script reads nothing from the page. It opens one `fill` port when the page's address is a Reddit post or comment, at load and again on each `currententrychange` of the Navigation API (Baseline since January 2026, MDN), which fires for History API navigations, so a thread opened from a feed or from another thread without a page load fills too. The match covers the whole site, because a feed does not match a thread pattern and no script would be there to see the navigation. The worker takes the tab id and the tab's address from the port's `sender` (`sender.tab.url`, not `sender.url`, which keeps the address the document loaded with: probe, Chromium under Playwright 1.64.1, 2026-11-10), checks the Instance and Reddit permissions again, asks `GET /api/items?url=<thread link>` (which matches by normalized URL) and goes on only when an Item has `fillable: true`. Then it reads the thread with `fetchThread` and sends `{url, content, fill: true}` with the same `send` as Save (`extension/lib/fill.ts`). The body that `fetchThread` returns is the body that is sent: `fitThreadBody` (`extension/lib/thread-body.ts`) measures it with the `fill` field in it and drops trailing permalink answers until it is within the 8 MiB request cap. When Reddit access is removed (`permissions.onRemoved`), `cancelFills` aborts every running fill; each checks its signal after the Item lookup, before each permalink read and before it sends, so an answer read before the revoke is not sent. There is no page fallback, because a page leaves no thread header and the Item would fill again at every visit. Nothing fills in the background: only a thread the owner opens, in a tab, with the Extension opted in. One fill per link runs at a time in the worker; the server decides the rest.
    - **`fillable`.** Every Item view carries it (`FILL_VIEW_COLUMNS`, `src/core/joined-view.ts`). It is true for a Reddit post or comment that has no `reddit_threads` row for any generation, the same test as `hasNoThread` (`src/core/reddit-thread.ts`). It is false for a thread whose Digest never published, which `commentsTotal` cannot tell from a Link-only Item. The Reader shows `FILL_NOTE` (`web/src/reader-text.ts`) above the empty text of a `fillable` Item that is not `processing`, beside the bar's Open on Reddit link, which opens the saved link.
    - **`fill: true`.** `POST /api/items` takes it with `content` only (400 otherwise). The thread is saved only when `awaitsThread` holds (`src/core/reddit-thread.ts`): an Item with this normalized URL exists and has no thread header. The check is part of the guard of the batch that writes the thread (`commit`, `src/core/thread-save.ts`), so two fills sent together save once, and an Item that is filled or deleted meanwhile is not written; the answer is 409 `fill: no Item with this link is waiting for its thread` and nothing changes. A guard that fails for this reason is not rebuilt and retried, which would never end.
  - **Other pages.** One press of the toolbar action reads the active tab and posts `{url, page}` with the agent token. `page` is `{markdown, title, author?, published?, videos?}` (`SuppliedPageSchema` in `src/core/supplied-page.ts`). The server never fetches such a page.
- **How the Extension saves a page.** Source: `extension/`, built by `wxt build` (Chrome) and `wxt build -b firefox --mv3`, which are `pnpm run build:extension`. Defuddle is pinned in `pnpm-workspace.yaml` (`catalog:`) to the version the server uses, so the browser and the server read a page alike.
  - **Permissions.** The manifest asks for `activeTab`, `scripting` and `storage`, and lists `https` sites and `http` on `localhost` and `127.0.0.1` as optional host permissions, which grant nothing until asked for. The settings page asks for the Instance's host when the owner saves it, so the browser's own prompt names the Instance. A Save has two halves. The page requests the host from the click's user gesture with nothing awaited before the call (Chrome docs, chrome.permissions: permissions are requested from inside a user gesture; MDN, permissions.request), then sends the settings to the background worker, which outlives the page. The worker writes them and then runs `reconcileAccess` (`extension/lib/access.ts`): it reads the stored settings, keeps the Instance's host and, when Fill is on, the Reddit hosts, and removes every other optional host the Extension holds, never one the manifest requires. Only `permissions.request` needs a user gesture, so the worker may call `permissions.remove` (Chrome docs and MDN, permissions.remove). The same reconcile runs after a failed write, after a Fill change, and on `runtime.onStartup` (the profile starts) and `runtime.onInstalled` (install, update, browser update), listeners registered at the top level of the background script (Chrome docs, runtime events and service worker events; MDN, runtime.onStartup and onInstalled). A Save cut short between the grant and the page's message therefore leaves its new host granted until the next browser start or extension update, when the reconcile removes it. The reconcile does not run when the worker is merely woken, and the permission-change listeners only sync the Fill script, because the grant wakes a stopped worker before the page's message arrives and a reconcile in that gap would remove the host just granted. The worker answers with the stored settings after the write and the reconcile, and says whether the write and the removals worked; the page shows that answer, and a removal that fails is named on the page. Saves and Fill changes from several tabs run one after the other in the worker, each from the stored settings read at that moment. A second press in one page while a Save runs is ignored. `activeTab` gives the press access to the current tab only. The Extension holds no `tabs`, `cookies` or all-sites permission. A match pattern holds no port (MDN, match patterns), so the grant covers every port on the Instance's host (Chrome docs, activeTab and chrome.permissions; MDN, host_permissions). The Fill saved Reddit Items setting requests `https://*.reddit.com/*` in the same way, from the click on Turn on, and removes it on Turn off. An open settings page follows the Fill grant through `permissions.onAdded` and `onRemoved`, so a change in the browser's extension settings or in another settings tab shows at once; its address field changes only on its own Save or a reload. The Extension reads nothing on Reddit before that grant.
  - **Capture.** The background worker injects `capture.js`, an unlisted script (WXT, Entrypoints), into the active tab with `scripting.executeScript`. The script runs Defuddle on the live document, so text a page script added is included, replaces `<video>`, `<audio>` and `<iframe>` with links by the server's `replaceMedia` (`src/core/article-media.ts`), and, for each image the tab displays, sets the extracted image's `src` to the `currentSrc` the browser selected and drops its `srcset`, `sizes`, `<picture>` sources and lazy-load attributes, because Defuddle's Markdown otherwise picks the largest `srcset` width (`getBestImageSrc` in Defuddle 0.19.6, `dist/markdown.js`). An extracted image matches a displayed one by any shared candidate address (`src`, `srcset` and `<picture>` sources). Shadow DOM and iframe content are not captured.
  - **Token.** The address and the agent token sit in `storage.local`, and the background worker is the only code that reads the token and sends it; the worker limits the storage area to trusted contexts where the browser has `setAccessLevel`. The popup and the capture script never see it, and the settings page gets only the address and whether a token exists, over a `config` port; its token field stays empty, and a save without a typed token keeps the stored one (`extension/lib/credentials.ts` is the one module that reads the token). The request refuses redirects and ends after 25 s, under the 30 s after which Chrome may stop a worker whose `fetch()` has no response yet (Chrome docs, Extension service worker lifecycle, read 2026-11-09). The address must be `https:`, or `http:` on `localhost` or `127.0.0.1`.
  - **Popup and worker.** The popup connects a `runtime` port and the worker posts the result (`SaveState` in `extension/lib/state.ts`); a port that closes before an answer shows the failed state. The popup shows one line for each state and one button for each state except `saving`, `thread-kept` and `budget-spent`. The Extension saves with an agent token, so its saves draw on the token's daily budget (see Access, Daily budget); a 429 with `code: budget-spent` shows the `budget-spent` state, and saving works again after 00:00 UTC or when the owner raises the budget in Settings. The texts come from `extension/lib/text.ts`, written by `tools/copy/write-copy.sh`.
- **Publishing a sent page.** `POST /api/items` takes `page` as an alternative to `content`; both together answer 400 `page: a link takes content or a page, not both`. An X or GitHub link, a Reddit link that is not a post or comment, and a link `isRefusedLink` refuses, never take a page (400); an X link takes its post and replies as `content` instead (Fetchers, X, Supplied thread). A Reddit post or comment link takes it as the Extension's fallback unless the Item holds a saved thread, and stays a Reddit Item (Fetchers, Supplied page). A `page` whose JSON is over 1,000,000 bytes answers 413 and changes nothing, under the same D1 row limit as Large text. Otherwise the page is stored on the Item's fetch job (`jobs.page`) and the job runs the article publication path with the page in place of a network read: `readSuppliedPage` (`src/core/article.ts`) gives the same `ArticleReading` as `readArticle`, so the Article or Other rule, the 100-word minimum, the images, the Highlight anchoring and the Digest are the ones a fetched page gets. A page is never fetched, so the server's guard and its page-size cap do not apply to it. A save of a link the Item already has refreshes it through the same path. The save closes the Item's open fetch jobs in the same batch (`closeFetchJobs`), so a fetch that was running cannot overwrite the page: its claim is lost and it writes nothing.
- The Threadsift bot's files live in `bot/` and call the same HTTP API and the AI task callbacks. The OpenAPI document from `@hono/zod-openapi` is their contract.
  - **Files.** A template carries skills as text and no other file (the bot's own answer, `docs/spec.md`, Grok Bot), so `bot/` holds one skill, `skills/threadsift/SKILL.md` (the bot loads it on every webhook wake, and for another chat turn only when its description matches, so it stays short), and plain files that the skill's bootstrap line installs into `~/threadsift/` on the bot's computer: `setup.md`, `update.md` and `scripts/threadsift.sh`. `profile.md` is the bot's profile, one description of one or two sentences. A template has one profile field (the bot's own answer), and the host uses it for the marketplace card, the share page and the imported bot's profile. The profile names the boundary (the bot never posts or replies on X, does no coding and no general chat), and the skill holds the full rules: what it never does, its voice and what its memory holds. `routines/threadsift-webhook.md` and `routines/threadsift-bookmarks.md` are the prompts of its two routines, which setup creates (a template carries no routine). `SHA256SUMS` lists those three installed files by bare name, `VERSION` is the number of the release, `CHANGELOG.md` is what `update.md` shows the owner, and `README.md` is for a person. The skill pins the hash of `SHA256SUMS` and the release tag (`TAG=` and `SUMS_SHA256=` in its bootstrap line) and is not listed in `SHA256SUMS`, because each would then depend on the other; an update trusts the new `SKILL.md` through HTTPS and the tag only.
  - **Webhook tasks.** The webhook body is `{ taskId, kind, callbackToken }` (`WebhookBodySchema`, `src/core/ai-task-read.ts`) or, for the Test of the Grok Bot settings, `{ "kind": "ping" }`. The body comes from outside, so no value of it becomes a shell word: the bot has no tool that writes a file without the shell, so the agent runs `mark` (it prints a fresh `TS_` and 32 random hex characters) and writes the body with `write event-<hex1>.json <<'TS_<hex1>'`, a heredoc whose delimiter is that word in single quotes, and `task-open` parses the file it made with `python3 -I`, checks `taskId` against `^[0-9]{1,16}$`, `callbackToken` against `^[A-Za-z0-9_-]{1,64}$` and `kind` against `^[a-z][a-z_]{0,39}$` (a task id has at most 16 digits and a callback token is `tst_` and 43 characters), deletes the file, answers `already-done` for a task done with that credential and `already-open` for a task that has a `task.json` less than an hour old and no `done`, asks `GET /api/ai-tasks/{id}` with the event's credential, and only when the Instance answers ok makes `tasks/<taskId>/`, writes the credential to `token` and the task to `task.json` and prints `ok <taskId> <kind>` built from the checked values, so a refused credential leaves the files of an open task as they were. An `x_intake` task is answered with the thread and a Digest through `task-answer`, which posts to the intake route, and the other kinds with a JSON value that fits `schema`, which `task-answer` posts to the result route; the server refuses an answer that does not fit with 400 and the reasons, which go to `errors.txt`.
  - **The script.** `bot/scripts/threadsift.sh` reads the Instance address from `THREADSIFT_URL` (an `https:` origin, or `http:` on `localhost` or `127.0.0.1` with a port; no path, query, fragment or user information) and the agent token from `THREADSIFT_AGENT_TOKEN`, builds every address from them and sends with `curl --disable` (no `.curlrc`) and `--max-redirs 0`. Its commands are `mark` (prints a delimiter word, `TS_` and 32 hex characters from `/dev/urandom`, and prints `failed` and nothing else when the bytes cannot be read), `write <name>` (stores standard input in `tmp/<name>` through a hidden `.part` file that it moves into place, so a failed write leaves no file, minus the one final newline of its input, which the heredoc adds, for a name that matches `^[a-z][a-z0-9-]{0,31}-[0-9a-f]{32}\.(json|txt)$` (the 32 hex characters are those of a `mark`, so `search.json` and `topics.json` can never be written) and at most 8 MiB in total, which protects the disk, since one heredoc call carries far less; a NUL byte in the text is not supported, a `tmp`, `tasks` or `state` that is a link is refused, files in `tmp` older than a day are deleted, and it prints `ok`), `check` (`GET /api/items` with a fixed `url` filter, so a token with the Read scope is the proof), `topics <hex>` (`GET /api/topics`, the first page, written to `tmp/topics-<hex>.json` for the hex of a fresh `mark`), `search <file>` (written to `tmp/search-<hex>.json` with the hex of the query file's name), `forget <hex>` (deletes `tmp/search-<hex>.json` and `tmp/topics-<hex>.json` for a hex of 32 characters, and prints `ok`), `append <name>` (adds its standard input, minus one final newline, to an existing `tmp/<name>` under the same name rule, staging, link refusal and total cap, and answers `bad-input` and changes nothing for a file that does not exist), `bookmarks-cursor` (`GET /api/imports/x-bookmarks`: prints the post id the Instance keeps as the stop marker of the sync, the top bookmark of the last complete run, or `none` for a 404), `bookmarks-send <file> [cursor [all]]` (a file that holds only `{"ids":[...]}`, 1 to 100 post ids of digits; the script builds `https://x.com/i/status/<id>` for each and posts `POST /api/items/batch`, with `import` only when the word `cursor` follows the file, which stores the first id of the file under `x-bookmarks`, or under `x-bookmarks-all` with the word `all` after it, so the bot types no id into a command; it prints `ok <added> <known> <refused>` only when the answer has one result for each id sent, and a 429 or 503 print `budget-spent` and `updating`; the same `saveItem` as `POST /api/items` runs for each link, so an added X link starts the same bot task), `save <file> [file]` (`POST /api/items`, with the thread as `content` for an X link), `task-open <file>`, `task-answer <taskId> <file>` (it posts to the intake route for an `x_intake` task) and `task-error <taskId> <reason>`, where the reason is one of three fixed words the script maps to a fixed sentence. A link, a query and an answer come from a file that `write` made, and every file argument has to resolve inside `tmp/`; the script deletes each file argument when it ends, whatever it prints. The task credential comes from `tasks/<taskId>/token`, goes to curl through a file descriptor and is in no command line and no output. Each call prints one word (`ok`, `none`, `duplicate`, `ping`, `already-done`, `already-open`, `closed`, `invalid`, `too-large`, `budget-spent`, `updating`, `unauthorized`, `forbidden`, `unreachable`, `failed`, and before any request `not-configured`, `bad-input`), and `word_of` in the script is the one table that maps a status to a word. A 200 whose body is not the JSON the command expects prints `failed`. The reasons of `invalid` go to `errors.txt` of the task folder, or to the error output for `save` and `topics`. After `ok` or `closed` the script writes `done` in the task folder, holding the sha256 of the task's credential, and deletes `token`, so a repeated webhook for the same send stops there while a new send of the same task id, which has a new credential, does not. `task-open` deletes the folder of a task done more than 7 days ago and the credential of a task left without `done` for more than a day. The shell tool of the Grok Bot hands a command to `bash -c` on a file descriptor, so no heredoc body appeared in any process command line there (observed on 2026-11-13: no tty, and `ps -eo args` counted only its own `grep`); a harness that passes the command in argv would expose the event body for the length of the call. One shell call cannot carry a long hand-typed text: a call of about 20,000 characters arrived with no command, twice, and one of about 1,000 characters worked, so the skill limits a `write` or `append` call to 3,000 characters, a size below the smallest failure and not a measured maximum, and the bot reads at most the first 100 replies of an X post, where the intake route takes up to 500. The residual risk is that a heredoc whose delimiter is unquoted or not fresh runs the text as shell before the script starts; the quoting and the fresh word are the only guard. The script checks everything after it: an event, a link, a query or an answer that breaks a check ends `bad-input`. The script needs `python3` and `curl` on the bot's computer, and `setup.md` checks for both. The `failed` word for an Instance that answers 5xx is proven by a run against a real Instance whose database is closed (`test/bot-script-links.test.ts`).
  - **Release.** `tools/bot-release.sh` refreshes `SHA256SUMS` and the hash pinned in `SKILL.md` after an edit of a hashed file (`refresh`, the default), makes a release (`release`: bumps `VERSION`, sets the tag `bot-v<VERSION>`, refreshes, and turns the `## Unreleased` heading of `CHANGELOG.md` into `## bot-v<VERSION>` under a new empty one) or checks both (`check`). Once the tag in `SKILL.md` exists in the repository (`check` and `refresh` fetch it from `origin` when it is not there), `refresh` refuses to run after a change to a hashed file and `check` fails when the pinned hash differs from `SHA256SUMS` at that tag, because the bootstrap line fetches `SHA256SUMS` at the tag and could never match; a change to a hashed file after a release goes through `release`. `test/bot-release.test.ts` runs `check` on the repository, so the gate fails when a change leaves `SHA256SUMS` or the pin out of date. Until the first release tag exists the tag in `SKILL.md` is the placeholder `unreleased`, which `check` accepts by name; it cannot install from the repository until `release` runs and the tag is pushed. `update.md` finds the newest release from the tags that start with `bot-v` (`GET /repos/KyaniteHQ/threadsift/git/matching-refs/tags/bot-v`), so no GitHub Release object is needed.
  - **Keeping the files true.** `test/bot-skills.test.ts` compares files that are kept apart: the script's routes and statuses with the OpenAPI document, the words, commands and reason words of the script with the skill, the commands shown in the bot files (each argument is a task id placeholder, a fixed word of the script or a path under `~/threadsift/`), an example thread or Digest with the production schemas, a routine with the section it names and with `setup.md`. `test/bot-skills-schemas.test.ts` compares the task kinds and the fields of a task read and of a webhook body in the skill with the server's registry and schemas. `test/bot-script-tasks.test.ts`, `test/bot-script-events.test.ts`, `test/bot-script-links.test.ts` and `test/bot-script-write.test.ts` (a real `bash -c` heredoc that holds `$(...)`, backticks, quotes, backslashes and lines that look like delimiters) run the script against a real Instance for every command, for a wrong credential, an answered task, a late task, an answer the server refuses and an event whose fields hold shell syntax, quotes, newlines or `../`; they need `python3` and `curl` on the machine, which `devenv.nix` provides, and the listener on `127.0.0.1` that `docs/testing.md` allows. The format has no typed link between the bot and the API, so these tests are the link.
