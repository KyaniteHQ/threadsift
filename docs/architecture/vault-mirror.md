# Vault mirror

Not built: `src` has no vault code, `JOB_KINDS` in `src/core/kinds.ts` has no vault job kind, and nothing calls GitHub's Git Data API (`git/blobs`, `git/trees`, `git/commits`, `git/refs`), so everything below is the design.

- **Git mode, both targets:** commits through GitHub's REST API (create blobs, a tree and a commit, then move the branch ref), with a fine-grained token that can write the contents of one repository. Workers has no `git` binary, and one code path keeps both targets the same. v1 mirrors only to a vault repository on GitHub.
- **Folder mode, container only:** writes the same files into a mounted vault folder.
- **Note paths.** A note keeps the path of its first write. An Item note's file name holds the Item id, so a later title, Topic or Tag change updates the front matter and `aliases` and never the path, and the wikilinks between notes and the owner's own links keep working. A Topic page note keeps its path through a rename the same way. An accepted merge deletes the merged-away Topic's note and rewrites the wikilinks to it, and deleting an Item deletes its note. `itemNote` in `src/core/item-note.ts` is shared with the export. The export's file name, `note-<slug>.md`, holds the title and not the id, so the mirror's file-name format is chosen in the Vault mirror slice.
- **What triggers it.** Every change to a mirrored file's content adds its vault paths to `mirror_paths` with a new sequence number, in the same batch as the change: a new, refreshed or deleted Item, a new Digest, a Read state change, a Highlight or a Note, a Topic page, a Related Item, a Log entry, the Index whenever a Topic's count or overview line changes, and an accepted Proposal, which rewrites every note whose Topic or Tags it renames or merges. One mirror job drains the table and writes the latest state of each path. It deletes only the rows up to the sequence number it read for each path, so a change that arrived while it ran stays queued.
- **One writer.** The mirror job holds the single `vault` lease and checks its generation again right before it moves the ref or writes the folder. A job that lost the lease stops without writing. It moves the ref without `force`, and when GitHub rejects the update because the branch moved, it rebuilds the commit on the new tip. A writer that loses its lease between that check and GitHub's answer can still land one stale commit, and the next drain rewrites those paths from current state, so the vault converges.
- **GitHub's limits.** Text files go inline as `content` in the tree and only images become blobs. One commit holds at most 500 paths (a chosen value), so a large Import mirrors in several commits. On 403 or 429 the job waits for `Retry-After` and resumes, because GitHub's secondary rate limits restrict content creation (GitHub REST docs, Rate limits). A file over GitHub's 100 MiB file limit (GitHub docs, About large files) is left out of the vault with a line in the Log.
