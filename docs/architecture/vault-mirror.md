# Vault mirror

The first slice is in `src/core/vault-mirror.ts`, `src/core/vault-files.ts`, `src/core/vault-github.ts` and `src/core/vault-request.ts`. Both install targets use the same GitHub Git Data API writer. `src/http/vault-routes.ts` and `web/src/ObsidianPage.tsx` own the owner-only settings routes and screen. GitHub writes have not run against the private test vault because its credential is outside this host's Infisical identity scope.

- **Identity.** Item notes live under `Threadsift/items/<Item id>/note-<Item id>.md`. The Item id survives refresh, title, Topic and Tag changes, Export and Restore. The note's `aliases` carries its current title. `itemNote` in `src/core/item-note.ts` is shared with the Export, which keeps its title-based file name. Images and stored post text keep their existing file keys under `Threadsift/`.
- **Queue and ownership.** `migrations/0002_vault_queue.sql` queues Item inserts and writes to `pending_digest` in the same transaction as the Paste or its publication. `mirror_paths.item_id` is unique, and its autoincrement `sequence` advances on each upsert. It deliberately has no Item foreign key, so a queued deletion survives a Restore undo. It is derived state, excluded from the Export along with `mirror_files`, the list of paths this Instance wrote. `vault_settings` is excluded as a secret.
- **One writer.** `mirrorVault` claims the singleton settings row with one conditional update. The generation and sealed credential identify the lease, including after a disconnect and reconnect. The writer checks its lease, the queued sequences and the absence of an active Restore immediately before the branch update. Queue acknowledgements remove only sequences at or below the ones read. An answer lost after GitHub committed leaves the queue for another write. No ref update uses `force`.
- **Bounds and retry.** `VAULT_NOTE_LIMIT` and `VAULT_DEADLINE_MS` in `src/core/vault-contract.ts` are chosen bounds. Twenty notes leave room for the Reader reads below D1's query limit; this is an arithmetic allowance, not a measured live Worker bound. A batch stops before 500 file paths or 8 MiB of text, and an Item with stored binary files gets a batch of its own. A single Item can exceed the text budget, as in the Export. A failed attempt keeps its queue rows. A moved branch rebuilds on the new tip on the next attempt. Rate limits persist GitHub's retry time, and other failures wait one minute. Requests are serial, with at least one second between mutations, following GitHub's REST best practices. The tick calls the writer after the sweep, rather than creating an Item-owned job for Instance-wide work.
- **Restore.** Starting a Restore invalidates the current lease. Its inserts queue notes but the writer cannot claim while a Restore runs or waits for Resume. Finishing or cancelling queues both current Items and the previously written Items, so paths of removed Items are deleted after undo. No mirror table is restored from a zip.
- **Settings.** `src/core/vault-settings.ts` seals tokens through the Instance's `Sealer`. Verify checks a candidate branch without saving it or writing files; a successful read does not prove Contents write permission or permission to update a protected branch. A missing sealing key prevents Save. Disconnect leaves the repository's files in place.

Not built: triggers for every other Item change, Related Item wikilinks, Topic page notes, the Index, the Log and folder mode. The later slices extend the existing queue and writer.
