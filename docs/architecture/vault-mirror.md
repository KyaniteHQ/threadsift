# Vault mirror

`src/features/vault/core/vault-mirror.ts` drains the queue through `VaultTarget` in `vault-target.ts`. The core renders, sequences and acknowledges notes. `src/features/vault/core/vault-paths.ts` writes every vault path and reads the subjects and files back from a listing, for both targets, and `src/features/item/core/item-files.ts` plans an Item's files for the mirror and the Export alike. The GitHub adapter compares branch blobs and publishes GraphQL commits on both targets. The container also registers the folder adapter, which owns filesystem reads, publication and file ownership. `src/features/vault/http/vault-routes.ts` and `web/src/ObsidianPage.tsx` own the owner-only settings routes and screen.

- **Identity.** `vaultNotePath` uses `Threadsift/items/<Item id>/note-<Item id>.md` and `Threadsift/topics/topic-<Topic id>.md`. Item ids survive refresh, title, Topic and Tag changes. Topic ids keep the first path through a rename, and a merge deletes the losing Topic's path. Both ids survive Export and Restore. The singleton notes are `Index.md` and `Log.md` at the root of the `Threadsift/` folder. Log entries are grouped by UTC month. A month uses `Threadsift/log/<YYYY-MM>.md`, for example the November 2026 note is `2026-11.md` in that folder. A month note's name never changes. Images and stored post text keep their file keys under that folder. The Export keeps its title-based file name and excludes the mirror settings, queue and path inventory.
- **Queue.** `mirror_notes` holds unique `(kind, subject_id)` subjects with advancing sequences. `STALE` in `src/core/kernel/vault-stale.ts` is the one place that says which change makes which notes stale, and every writer joins its batch with the statements of its entry, including the shared Highlight removal path. The only thing that stops a writer from queueing notes outside `STALE` is a lint rule that refuses an import of the queue outside the vault modules (`docs/architecture/lint-and-format.md`); a writer that changes data a note shows and never calls `STALE` is not refused. Digest or fetch publication queues changes to the Topic page and to Item notes that link to a renamed Item. Index changes come from Topic membership, a Topic merge or a changed overview line. An overview revision queues its Topic page if the text changed, and a changed Related Item list queues its source Item. A disagreement queues the Topic page whose list changed. Topic and Tag merge units queue the notes they change, and deletion queues the affected notes while the old references still exist. Each Log append queues only its UTC month immediately after its insert. Deleting an Item queues the months of the entries it deletes. After a month note is added or removed, the writer queues `Log.md`. The root links to the published month notes, newest month first. This keeps its links valid while a month is parked or awaits publication.
- **One writer.** The generation and target identify the singleton lease. `currentVaultNotes` checks the lease and the canonical Restore hold while it selects the current queue sequences immediately before publication. Item notes share one commit, Topic page notes share another, and the Index, Log and each due month note have their own commits. A stale subject leaves its commit group. The writer retries any still-current subjects in that group. Folder mode checks the current queue sequence before each file and uses an abort signal with the same deadline as the lease. Its synchronous filesystem operations keep the check and publication in the same Node turn. Every acknowledgement removes only sequences at or below those read. An answer lost after GitHub committed leaves the queue for another attempt. Each `createCommitOnBranch` carries `expectedHeadOid`, so a moved branch, including a reset, refuses the entire commit. A stale-head refusal reads the new tip and rebuilds from the queue, at most three attempts per lease (a chosen bound). REST remains only for branch, commit and subtree reads; no REST blob, tree, commit or ref mutation remains.
- **Bounds.** `VAULT_NOTE_LIMIT`, `TOPIC_NOTE_LIMIT`, `SHARED_NOTE_LIMIT` and `VAULT_DEADLINE_MS` bound a lease. The writer takes up to 12 Item notes, 4 Topic page notes and 4 other notes. Each Item makes one D1 batch of 11 Reader selects (`detailReads`) plus its file-progress read. `VAULT_FILE_BYTES` limits each commit to 8 MiB of raw file content. One Item can span commits.
- **Files and retry.** `vault-content.ts` reads one file at a time and `vault-github.ts` encodes it into the commit. `mirror_files` checkpoints each confirmed path with its Git blob SHA and queue sequence; a resumed attempt skips matching paths already present on the branch. An answer lost after publication is recovered by comparing the remote file SHA, so it creates no duplicate commit. Each attempt releases its encoded payload after its single commit. The deadline starts at claim time. Missing or changed stored files park only that subject for a minute and log the reason; healthy subjects can drain. `vault-tree.ts` reads only needed nonrecursive subtrees, so an unrelated large vault does not require a complete recursive tree. Only paths whose Git blob SHA differs are sent; an unchanged note creates no commit. Tree reads may overlap, and mutations are at least one second apart. GraphQL rate-limit errors are checked even on HTTP 200. Cooldowns preserve Retry-After and reset headers (`rateLimitWait`, `src/features/github/core/github-rate-limit.ts`, which reads Retry-After with the same `retryAfterMs` as the Paste path), cut to one hour like the Paste path (`MAX_COOLDOWN_MS`; `fetchers.md`, Cooldown and attempts, gives the reason), grow exponentially on repeated rate limits, and survive lease expiry for the same sealed credential. When the cut ends a wait early, the next lease sends one real request after the hour, and if GitHub still limits it `rate_failures` grows, so the next wait is at least an hour again. A 403 or 429 that no limit rule matches is still a rate limit when it carries a `Retry-After` header, whatever its value, and a 429 is one without it; its time is the header's or, with no usable time, a minute, and the lease takes the later of that time and its backoff. Other failures wait a minute ([GraphQL limits](https://docs.github.com/en/graphql/overview/rate-limits-and-query-limits-for-the-graphql-api)). The tick runs sweep and mirror as separate best-effort tasks.
- **Restore and upgrade.** `startRestore` checks for a live vault lease in the same batch that starts the Restore. A live lease gives `409 vault-busy` and keeps the uploaded parts for retry. `HOLDS_LIBRARY` in `src/core/kernel/restore-hold.ts` prevents a new claim while the newest Restore holds the library. Save and a completed or cancelled Restore queue the library in their write batch and request a scan for managed paths written by another Instance. Cancelling an upload, or a Restore that never got past its check, never changed the library and queues nothing. GitHub scans managed branch paths. Folder mode scans its written-file list. The first new writer after an upgrade backfills an already configured vault. No mirror table is restored from a zip.
- **Settings.** `vault-settings.ts` seals tokens through the Instance's `Sealer`. Verify reads a candidate branch without saving or writing files; it does not prove Contents write permission or permission to update a protected branch. A missing sealing key prevents Save. Disconnect and a switch of destination leave the previous target's files in place. Saving the new target queues the full library.

A real GitHub `Retry-After` wait and resume remains unverified on both install targets. The 600-Item Imports, 60 further note updates per target and two bounded 450-request impossible-head probes produced no rate refusal. No further load should be sent to force one. `docs/architecture/open-items-and-unverified-claims.md` records the missing evidence and the run that would establish it.

## Wikilinks

`vault-markdown.ts` uses Obsidian's vault-relative path form, without `.md`, for example `[[Threadsift/topics/topic-12|Build tools]]`. The full path identifies the destination even when two notes have the same title. The text after `|` names the destination in context. Obsidian 1.15.1 renders brackets, pipes and ampersands literally in that text. An invisible word joiner separates consecutive brackets and keeps a final closing bracket inside the label. The Item or Topic note also sets its name in the `aliases` list for lookup in Obsidian. Neither the path nor a link's resolution depends on an alias or a plugin. The Log keeps historical names as text, so a Topic merge can drop its old note without leaving links in the history. [Obsidian internal links](https://help.obsidian.md/links), [Obsidian aliases](https://help.obsidian.md/aliases), [vault-relative link setting](https://help.obsidian.md/settings#Files+and+links).

## File ordering and byte budget

GitHub's [FileAddition and FileChanges](https://docs.github.com/en/graphql/reference/git#fileaddition) require full base64 contents and unique paths; a deletion must name an existing path. The writer reads only needed subtrees, adds an Item's assets in earlier commits, writes its note last, then deletes obsolete assets. Removing an Item reverses that dependency: delete its note before its assets. A missing file parks that Item, leaving others eligible. An Item file above 100 MiB is omitted, and the writer records its path once in the Log. An omitted image's embed is removed from the Item note. Stored images are checked by size before reading them. An Item file that exceeds the writer's 8 MiB budget and fits GitHub's file limit stays queued with `file-too-large`. A wiki note, including one Log month, stops rendering at the writer's budget, retains its last published copy and retries after its parked delay. Each monthly render reads entries from that UTC month alone, newest first. [GitHub large files](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github).

The smaller constraint is memory, not the GitHub request envelope:

- GitHub returned `The request payload cannot be larger than 45MB` for a 55,925,619-byte mutation containing twenty 2 MiB images on 2026-11-17. A 97,779-byte mutation containing 500 small files reached its expected-head guard. These are measured responses, not a published numeric schema guarantee. Repeat the refusal probe with a private repository token read from a file, twenty base64 files, and an impossible `expectedHeadOid`; no commit can land. The command below repeats both refusal probes.
- [Workers limits](https://developers.cloudflare.com/workers/platform/limits/#memory) gives 128 MB per isolate, shared by its invocations. For a raw budget B, base64 is at most 4B/3 plus per-file padding. Allowing UTF-16 base64 strings and a UTF-16 JSON copy plus the UTF-8 network body costs about 20B/3. Reserving another 4B for the raw batch, current file, hashing and text and 32 MiB for other work gives about 117.3 MiB at B = 8 MiB, below 128 MB. This is a conservative allocation model with chosen headroom, not a production memory measurement. The resulting base64 body is about 10.7 MiB plus paths and the envelope, below the measured 45 MB refusal. The twenty-image case therefore needs several commits and never retains all forty MiB of image bytes at once.

Set `VAULT_PROBE_INPUT` to a private JSON file containing `repository`, `branch` and `token` for the disposable test vault, then run:

```sh
node --input-type=module - <<'JS'
import { readFileSync } from 'node:fs';
const { repository, branch, token } = JSON.parse(readFileSync(process.env.VAULT_PROBE_INPUT));
for (const [count, bytes] of [[500, 100], [20, 2 * 1024 * 1024]]) {
  const contents = Buffer.alloc(bytes, 65).toString('base64');
  const body = JSON.stringify({
    query: 'mutation($input: CreateCommitOnBranchInput!) { createCommitOnBranch(input:$input) { commit { oid } } }',
    variables: { input: {
      branch: { repositoryNameWithOwner: repository, branchName: branch },
      expectedHeadOid: '0'.repeat(40), message: { headline: 'Capacity refusal probe' },
      fileChanges: { additions: Array.from({ length: count }, (_, n) => ({ path: `Threadsift/capacity-probe/${n}.bin`, contents })), deletions: [] }
    } }
  });
  const response = await fetch('https://api.github.com/graphql', {
    method: 'POST', headers: { authorization: `Bearer ${token}`, 'content-type': 'application/json', 'user-agent': 'Threadsift/1' }, body
  });
  const result = await response.json();
  console.log(Buffer.byteLength(body), response.status, result.errors?.map(error => error.message));
}
JS
```

[CreateCommitOnBranchInput](https://docs.github.com/en/graphql/reference/commits#createcommitonbranchinput) owns the expected-head contract. [GraphQL authentication](https://docs.github.com/en/graphql/guides/forming-calls-with-graphql#authenticating-with-a-personal-access-token) supports fine-grained tokens; the mirror needs Contents write for its selected repository. Verify proves read access only.

## Folder mode

The folder writer uses the same ordering and byte budget as GitHub. It opens path components without following symlinks and uses Linux directory descriptors. Verify checks write access on the mount or existing `Threadsift/` directory, the note directories and the written-file directories it finds. Verify writes nothing. The folder must support hard links.

The hidden `.written` directory under `Threadsift/` holds one hard-link receipt per published path. The receipt identifies the file across retries, Instance restarts, Restore and a switch away from the folder and back. A file replaced by another program loses that identity. An unowned file in the way parks its subject while the other subjects continue. The settings screen names the conflicting path. The Log keeps one entry per conflict path, even after the subject succeeds. If you point Folder mode at a Git checkout, move the checkout's `Threadsift/` files out of the way before switching. Move a conflicting file to let its note publish on the next retry.

The `.staging` directory under `.written` holds the staged bytes and an interrupted operation's receipt information. On replacement or deletion the writer moves the existing file aside and checks its inode before discarding it. The writer uses a hard link to publish complete bytes at a free destination. If an unowned file moved aside and another file took its name, the writer preserves the displaced file in `.recovered` under `.written`. The next lease reconciles unfinished staging before it reads inventory. A receipt whose destination is gone stays visible to the planner until it is removed. The writer syncs the destination and receipt directories before acknowledging the queue. Deleting an Item removes its empty output and receipt directories.

Keep `.written` in the mounted folder and exclude it from sync. A copy without the hard links cannot identify which files the mirror owns. Switching destinations and disconnecting leave the old target's files and receipts in place.
