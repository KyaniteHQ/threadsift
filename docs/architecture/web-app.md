# Web app

- A React 19 single-page app built by Vite (owner's decision, 2026-11-04). One static build serves Workers static assets and Hono's `serveStatic` on Node, and it is the shape Tauri and Capacitor take for a later desktop or mobile app. No server rendering: one owner behind a login gains nothing from it.
- React-specific libraries stay few, so the app can try Preact 11 through `preact/compat` after the first release if page weight matters: in a small comparable build, React's framework JavaScript was 68.0 KB gzip and Preact's 7.7 KB (measured 2026-11-04 in a scratch build, not on this app).
- The prototype is Claude Design's own template format on React 18 classes, so the app rewrites it. Its behaviour (reader bar fitting, folding by measured height, reading-place restore, the keys) is plain DOM code and becomes plain TypeScript modules that take an element.
- `design/system/tokens.css`, `components.css` and `settings-table.ts` are the one source of values and settings; `settings.ts` builds the defaults, the stored-settings reader and the root attributes from the table's rows. `docs/spec.md` owns what each setting does.
- **Settings storage and the root.** All twelve settings are one JSON object in `localStorage` under `STORAGE_KEY` (`design/system/settings.ts`), and `readStored` checks each key on its own, so one bad value falls back alone. `html` carries the same `data-theme`, `data-style` and `data-layout` as the app root (the rows marked `onPage`), so the page canvas resolves the same `--bg` in every Layout and Theme. `useSettings` takes the stored object supplied at startup. Before the first paint, a blocking classic script (no `defer`, `async` or `type=module`) sets the `onPage` attributes from the stored object, so a stored Dark never draws a Light frame and a stored Grid never draws list greys. `tools/theme-script.ts` emits it as the hashed file `/assets/theme-script-<hash>.js` linked from `index.html`, so the Content-Security-Policy needs no inline-script hash and no `'unsafe-inline'` for scripts; the cost is one request before the first paint, which the immutable cache answers on every later load. A change that brings a font stack the root does not use (Font or Style) reaches the root's attributes only once those faces have loaded, or after 3 s (the font block period, https://drafts.csswg.org/css-fonts-4/#font-display-desc): `useSettledAttributes` (`web/src/look-faces.ts`) holds the old attributes until then, because the panel's controls show the pick at once while the page restyles in two steps otherwise, first in the fallback face and then in the real one, and the bar's Comments button moved three times.
- **Settings panel.** The panel is a `<dialog>` inside the app root, never a portal to `body`, so the `data-*` rules of the root reach it and its own `data-font` keeps it in the default type pair. Each single-choice group is a `radiogroup` of native `<input type="radio">` elements, each inside a `<label>` drawn as the segment or the swatch, with the transparent input covering its label, so the browser gives each group one Tab stop and arrow-key choice and the label shows the focus ring through `:has(:focus-visible)`. At 760px and wider the panel is a non-modal popover (`show()`); under 760px it is a modal sheet (`showModal()`), because the browser then makes the rest of the page inert and puts the panel in the top layer above `::backdrop`. The panel in the Reader bar keeps its open state in `ReaderPane` (`useHeldPanelState`), above the subtree that `ReaderPane` swaps when the Reader place changes (the width crossing 760px, or Open items as changed from the panel), so the panel stays open and the browser shows it again in the other form. The state is dropped when the open Item changes or the bar has no gear (the `pane` place, which a Layout change to List brings, with the open Item cleared). Every `SettingsPanel` gets its `PanelState` from its caller (`usePanelState` in `Brand.tsx`, `useHeldPanelState` in `ReaderPane`). While a panel is open it keeps the focused control, found by its `data-focus-key`, and the scroll position of its body in the state (`focusin` and `scroll` listeners), because the Sheet's dialog closes before the panel's own cleanup runs and a closed dialog reads a scroll position of 0. The new panel restores both in a microtask after the commit, and a panel that opens the ordinary way takes its focus in a microtask too, because the Sheet's `showModal()` has moved focus to its first control by then. The Reader's title does not take focus while the panel holds it (`panelHoldsFocus`). A dismissal listener of a panel that has unmounted does nothing, because its `focusout` for the new panel's focus would otherwise close the shared state.
- Fonts: `tokens.css` imports no font host. Every face comes from a Fontsource package in the build, so a self-hosted Instance makes no third-party request. `web/src/main.tsx` imports only the faces of the default Font (IBM Plex Sans and Plex Mono, also the settings panel's type pair); every other family is a dynamic import named in `design/system/style-faces.ts`. `pnpm run check:faces` (`tools/check-font-faces.ts`, run by the `design:check` task) fails the gate when a stack starts with a family that the faces of its Style or Font do not provide, or when a row loads a face that none of its stacks names, because the page would show the fallback font with no error; it checks no weights or italics. Vite settles a dynamic `import()` after the stylesheet has loaded ([Vite, Features, CSS Code Splitting](https://vite.dev/guide/features#css-code-splitting)), so `main.tsx` waits for the stored Style's faces before React renders, and `useSettledAttributes` waits for a changed look's faces before it applies the look. Both waits end after `FACE_WAIT_MS` (3 s). A face stylesheet that hangs therefore delays the first render by up to 3 s, and the first Item row appears after about 3 s either way: with the stylesheet held on this build and with the font files held on `main`, where the font gate already waits that long. A stored non-default Style asks for its stylesheets after the entry script runs, so a cold load in it needs one more round trip before first paint than the default Style. A face stylesheet that fails is not tried again in the same document (the preload helper keeps the href marked as seen after a failure): when it fails after a change of look, `useSettledAttributes` reloads the page once; when it fails at the start, the page renders with the fallback fonts of the stacks until the next reload. Fontsource's variable packages name their family with a `Variable` suffix (Fontsource docs, Variable fonts), so each font token in `tokens.css` names `'<Family> Variable'` first and the plain family as the fallback; the families that have only static packages register the plain name. Imports keep all package subsets, so saved text can use the supported scripts.
- **Screen chunks.** `web/src/lazy-pages.tsx` loads the Settings, Import, Proposals and Log screens through React `lazy`. One `ModuleBoundary` in `web/src/SignedInScreen.tsx` handles only failed module loads and shows `Unreachable` with Try again for a failed import, which reloads the page. The route and the session view are set only inside a transition (`useScreenState`, and `useFlow` with `inTransition`), so the current screen stays until the next screen's chunk arrives. Any new setter of what the screen shows must run inside a transition, because an update outside a transition hides the screen behind the fallback ([React, Suspense](https://react.dev/reference/react/Suspense)). The `popstate` handler sets the path one task later, because React renders a transition that starts inside a `popstate` event synchronously. A new lazy screen goes into `LOADERS` in `lazy-pages.tsx`, which also lets `main.tsx` start its chunk when the address names it, so a reload does not wait for the session answer first. `vite.config.ts` has two `codeSplitting` groups. `zod` holds Zod and `zod-jitless.ts`, so jitless is set before any schema is built and the page's Content-Security-Policy needs no `'unsafe-eval'`. `shared` holds each module of `web/src` and `design/system` that two chunks share, with its dependencies (`src/core` among them), because Rolldown's automatic splitting makes one common chunk per set of importers ([Rolldown, Automatic code splitting](https://rolldown.rs/in-depth/automatic-code-splitting)) and the entry loads all of them before first paint. After a change to these groups, run `pnpm build` and count the `modulepreload` links in `dist/web/index.html`: each one is a file that the first paint waits for.
- Static files answer the same on both targets: `index.html` for a path whose last segment has no `.`, `404` for any other path that matches no file, so `/favicon.ico` and a missing `/assets/x.js` are not HTML. Workers' `single-page-application` mode cannot do this: it answers every unmatched path with `index.html` and `200` (Workers docs, Static Assets, Single Page Application, Configuration; `wrangler dev` 4.156.0 answered `/favicon.ico` and `/assets/nope.js` with `200 text/html`). The Worker therefore leaves `not_found_handling` unset, gets the `ASSETS` binding, and serves `/` itself for a `GET` or `HEAD` of a path without an extension (`src/targets/worker/index.ts`). `run_worker_first: ["/api/*", "/share", "/mcp"]` makes the Worker answer those paths before any static asset (Workers docs, Static Assets, Routing, Worker script); the setting only decides when the Worker runs, so `isServerPath` (`src/http/document-path.ts`) also sends `/api`, `/api/*`, `/share` and `/mcp` to the Hono app, because `serveDocument` answers a `POST` with 404. The Node entry mounts the Hono app before static files, so `/share` and `/mcp` reach it there without a rule, and serves the page with `isDocumentPath` (`src/http/document-path.ts`) on the pathname of `new URL(context.req.url)`. Hono's `context.req.path` decodes `%2E` to `.` (checked with Hono in `node_modules` on 2026-11-11: `GET /topics/node%2Ejs` gave `/topics/node.js`), which would turn the page of a dotted Topic into a 404.
- Caching: hashed `/assets/*` are `public, max-age=31536000, immutable` and `index.html` is `no-cache`. The Node entry sets them in `src/targets/node/web-routes.ts` and compresses with Hono's `compress` middleware. On Workers the platform compresses, and `tools/worker-headers.ts` writes `dist/web/_headers` at build time from the same constants (Workers docs, Static Assets, Headers), so the two targets cannot drift; that file also reaches `dist/web`, so the Node entry answers `/_headers` with the page and never serves the file. `/index.html` redirects to `/` on both targets (`307`).
- The library, not the paste card, reads `GET /api/items/:id/status` for each `processing` Item (`useItemPolling` in `web/src/item-polling.ts`), once a second for the Item's first 10 reads and then every 5 seconds. Reads of one Item never overlap, also when a change of the processing Items replaces the pollers: a read waits for the Item's read still in flight (`readStatus` in `web/src/item-reads.ts`, which the seek of `web/src/use-seek.ts` and `useLookup` share with the poller). The count belongs to the Item, so a new `processing` Item does not start the others' reads over. An Item whose `wait` names a `retryAt` is read next at `retryAt`, at most 60 seconds ahead (the sweep period, a chosen bound). A 404 means the Item was deleted elsewhere, so the library drops it and never reads that id again. A hidden tab makes no reads, and a read that waited for the slot checks that again when the slot frees. No websocket, so both targets serve it the same way.
- A failed list read shows the existing load error with Try again (`useListRead` in `web/src/list-reads.ts`), including a reload after a write, so the owner can retry instead of silently reading stale rows.
- **Read and write deadlines.** `call()` in `web/src/calls.ts` gives every `GET` an abort deadline of `READ_DEADLINE_MS`, 20 s, so a read that the Instance never answers ends in the screen's failed state with Retry or Try again instead of a loading state with no end. The value is a chosen bound: it sits above the 15 s probe (`PROBE_MS`) that `GET /api/settings/ai` can wait for, the slowest read the Instance has. A write needs a deadline of its own, because headless Chromium 156 kept a `POST` to a server that never answers pending for 420 s, when the measurement stopped. `post()`, `put()`, `patch()` and `del()` in `web/src/calls.ts` take the deadline as a required argument, so the type checker refuses a write that names none, and no write gets a default. The argument is a value from `web/src/write-deadlines.ts`, or `NO_DEADLINE`. Each value there is the bound of what the route handler waits for plus a margin (`MARGIN_MS`, which is `READ_DEADLINE_MS`): a write that only touches the database gets the margin alone (`DATABASE_WRITE_DEADLINE_MS`), and a write that waits for an outside system inside the request gets that wait plus the margin. The server constants come from `src/core/request-waits.ts` (which imports nothing, so the web bundle takes no server code with them), `src/core/ports.ts`, `src/core/ai-contract.ts` and `src/core/grok-bot-contract.ts`, so a change there moves the deadline with it. The Restore part uploads and its start call (`web/src/restore-api.ts`) are the only writes with `NO_DEADLINE`; a part's time depends on the owner's link. The Import batch and Accept have deadlines, and a deadline that runs out is not a failure, because the work may still be running or may have landed. Accept is a database write, so it gets `DATABASE_WRITE_DEADLINE_MS`. When it runs out, `sendAccept` answers `unknown` and `useCheck` (`web/src/use-proposal-check.ts`) reads the Proposal's own state with `GET /api/proposals/{id}` (`fetchProposalState`) up to `UNDECIDED_CHECKS` times, `POLL_MS` (3 s) apart, while the row stays pressed. A state of `accepting` shows the row as applying and the 3 s page reads continue. If such a row then reads `open` (the first unit found a lease taken or failed, and the claim was handed back), `useAnnouncingReread` shows the failed state with Try again. A row that vanishes while it shows applying is announced as accepted only when its own state reads as gone (404); a row that reads `rejected` gets the already-decided note. A Proposal that is gone, `rejected` or `declined` goes through `settle` (`web/src/use-proposals-page.ts`), which reads the page again and shows the already-decided note. A Proposal still `open` after the last read shows the failed state with Try again. Reject uses the same check, and a Proposal that reads `rejected` leaves as rejected. A `not-current` answer goes through `settle` alone, because the page decides it. The Import screen sends `IMPORT_BATCH_LINKS` links per batch (7), so that a batch of short links fits the request deadline. The route takes up to `BATCH_LINKS_MAX` (100), a limit chosen for the Worker's query and subrequest counts (`docs/architecture/data-model-outline.md`, Limit of 100 links), and a routine may send that many. `IMPORT_BATCH_LINKS` is the request deadline minus the margin (140 s - 20 s = 120 s), divided by the time of one short link: 2 fetches (the measured count per new short link, same page) of at most `HOP_DEADLINE_MS` (8 s) each, 16 s, so 7 links (arithmetic from those sources, not a run of 7 slow short links). A short link that needs more hops, or a link that waits on the full `FETCH_DEADLINE_MS`, can still pass the deadline, and the recovery below covers it. Each link of a batch can wait on `FETCH_DEADLINE_MS` for a short link, so the longest legitimate wait is `IMPORT_BATCH_PATIENCE_MS`: `IMPORT_BATCH_LINKS` (7) links times `FETCH_DEADLINE_MS` (120 s) plus the margin, 860 s or about 15 minutes (arithmetic, not a run), and no request deadline can sit above it. The request itself gets `IMPORT_BATCH_DEADLINE_MS`, which is `PASTE_DEADLINE_MS`: the longest one link waits plus the margin. Before each batch the run reads `GET /api/imports/{name}` (`cursor` and `updatedAt`). After its first batch the run expects the cursor it wrote last, and a read that finds another cursor means a second tab or routine moved it, so the run ends as `stopped` at the saved position and Continue resumes from there; the first read of a run may find any cursor, because Import again restarts a finished list over the stored cursor. The request carries the cursor it read as `import.previous`, so `saveImport` (`src/core/import-cursor.ts`) moves the saved cursor only from that value: a batch that is still running when the run ends cannot move the cursor back over a later one. When the request reaches its deadline, `batchLanding` (`web/src/import-landing.ts`) reads the state again, `POLL_MS` after each read ends (a read can last up to `READ_DEADLINE_MS`), until the batch counts as saved: the cursor reaches the batch's end and `updatedAt` is newer than the value read before this attempt, so a cursor that an earlier run left does not count. The wait also ends when the owner presses Stop, an `AbortSignal` that ends the pause and the read together, and one last read then still counts a batch that landed; when `CURSOR_READ_FAILURES_MAX` (3) reads in a row fail, which ends the run as `network`; and when `IMPORT_BATCH_PATIENCE_MS` passes, which ends it as `unconfirmed` (the bound is checked once per loop, so a read that starts just before it, the pause and the last read can run up to about 43 s past 860 s: `READ_DEADLINE_MS` + `POLL_MS` + `READ_DEADLINE_MS`), the failed state that says the batch did not land, with Continue. The screen shows `IMPORT.waiting` meanwhile. A batch that landed after its deadline adds nothing to the counts, because only the answer carries them, so the run keeps the number of its links in `Progress.uncounted` and the screen shows `uncountedLabel` under the counts note. On Cloudflare a request that the browser ended may be canceled before its cursor is saved, and then the screen waits for the whole patience or for Stop. The values hold while the handler meets no race: `saveShortLink` in `src/core/save-link.ts` starts a second resolution when its save loses a race, so a Paste that meets that race can pass its 140 s (`PASTE_DEADLINE_MS`) and still land; the GitHub verify restarts its request when the credential changes meanwhile (`withCurrentCredential`), so its 28 s (`HOP_WRITE_DEADLINE_MS`) holds without a concurrent save. Every other caller treats any rejection as its screen's failed state with the action offered again. A failed state after a write therefore means the Instance may have stored the change, may not have, or may have stopped half way, and what holds depends on the install target. On the container the handler keeps running after the browser ends the request, except on the verify and test routes, which read the request's signal. On Cloudflare the request's work may be canceled when the client disconnects ("When the client disconnects or the response is complete, tasks associated with that request may be canceled", [Workers limits, Duration](https://developers.cloudflare.com/workers/platform/limits/)), and the Worker passes nothing to `ctx.waitUntil()`, so a handler that is still running when the deadline ends can stop before its last write. A read-state write and a token budget save send an absolute value, so one that timed out can still land after a later one and leave the stored value different from the screen until the next read; that needs an Instance that holds one request for more than 20 s and answers the next one first. A repeated Delete of an Item, a Highlight or a token that is gone answers 404, which counts as done. A repeated Note save whose first call stored the text answers 409 and shows the revision conflict panel, even when the texts match (`web/src/note-state.ts`). `leave` in `web/src/routing.ts` waits for the `popstate` of its own Back for at most `TRAVERSAL_WAIT_MS`, 1000 ms, which is unsupported: it was chosen far above the 1 to 60 ms between `back` and `popstate` measured at 1x to 20x CPU throttling. A Back that never lands makes Escape and Close do nothing for up to that long, and a Back that lands later than that leaves a second close free to go back again.
- **Pages of the list.** `GET /api/items` answers at most 50 Items (`ITEMS_PAGE_SIZE` in `src/core/item-page.ts`) and `next`, the cursor of the page after. The cursor is `<saved date>.<Item id>` (`listItems` in `src/core/item-selection.ts`). The id breaks a tie between Items saved in the same millisecond, so a page edge inside such a run neither repeats nor skips an Item. **Identity of the cursor.** It names a position, not a record. The Item id is the generated key that is never reused, and `saved_at` is written once at insert, so a delete, a refresh, a Digest or a Read state change between two reads moves no later page, an Item saved after the first read is newer than every cursor, and a cursor survives the deletion of the Item it names. A restore that renumbered ids or changed `saved_at` would make an old cursor name another position, and a read from the first page gives a fresh one (the round trip of 1200 Items kept every id and `saved_at`, so an old cursor names the same position after a Restore). A cursor the server did not give, whose two numbers are safe integers, is accepted and answers the Items after that position; any other cursor is a 400. The counts (`countQueries`) run in the batch of a read with no cursor only, because each scans the whole `items` table and a page read from a cursor needs none. The counts of the first page cover the whole library, so the filter pane and the header stay true while the rows come in pages.

  The browser keeps the pages it has read in `ListState` (`web/src/list-state.ts`): `items` is always the newest-first start of the library for the filters in `query`. `useNearEnd` starts the next page about ten rows before the owner reaches the end, and the Load more button is the keyboard and screen reader way to it. `useMore` (`web/src/list-more.ts`) appends a page only when the list still holds the same `query` and `next`, so an answer for an old filter or position is dropped. `useReads` (`web/src/list-reads.ts`) invalidates the shared generation when a write asks for a reload; list reads, later pages and Item polls drop answers from an older generation. A reload (after a Paste, a Read state write, a deletion, or any change to a polled Item) reads the first page and then the pages after it until it passes the last row the list had loaded (`readThrough` in `web/src/list-reads.ts`) and replaces the rows, so the owner keeps their place because the rows are keyed by Item id. A new Item is placed by its saved date and id (`placed`), and not at all when it belongs to a page not yet read. A Paste of a link the library already holds, whose row is not loaded, reads the next pages one after another until that Item's row is among the loaded rows (`useSeek` in `web/src/use-seek.ts`), and then scrolls the row into view. A share that arrives at `/?saved=<id>` or `/?refreshed=<id>` seeks the same way. So the rows stay the newest-first start of the library, no Item repeats, none is skipped, and the owner's later scroll continues from the last row. The cost grows with the Item's position (the 2,000th of 3,000 Items is 39 reads), which is the price of keeping one run of rows. The other design, reading only the page that starts at the Item and marking the gap before it, costs one read, but every consumer of `items` (`appended`, `readThrough`, `useNearEnd`, `useStep`, the counts of loaded rows) would then need to know about holes. The seek stops without a row when a filter or search is on (the Item may not match it), when the Item is deleted meanwhile, when the pages end, and when a page read fails. It also ends, without scrolling, as soon as the owner's attention moves on (a later Paste, a change of filter or search, a different open Item, a step with j or k, a deletion, or the owner's own wheel, touch scroll, key press or pointer press, `onOwnerMove`); a page that lands after that is appended and nothing more. An Item opened by its address is never sought, so the Reader opens at once; it is read through `GET /api/items/:id/status` and kept in `known` only (`useLookup` in `web/src/use-lookup.ts`). The header reads "{shown} of {total}" from the loaded rows when every row is loaded, and from the Source counts of the first page otherwise (`matchedCount` in `web/src/list-counts.ts`). A step with j or k, in any Layout, can need a page of Items that is not loaded yet: past the last loaded row, or when the open Item came from its address and the loaded rows do not hold it. The step then waits while the page loads (`useStep` in `web/src/use-step.ts`). When the step starts the read itself, the live region says "Loading saved links…", and when that read fails, the live region shows the load error. A step that finds a read already running waits with no text. A key press, a focus move, a Back, or a change of the open Item cancels the waiting step and removes the loading text.

- Read state writes go one after another for each Item (`useAnnouncement` in `web/src/use-announcement.ts`): a press computes its wanted state from the last wanted state still in flight, and its PUT starts after the Item's earlier PUT has answered. Two presses of `m` before the first answer therefore send `read` and then `unread`, so the older answer cannot be the last one applied.
- `usePaste` closes the card of an Item that the library no longer knows (the status read answers 404), because a card with no face renders nothing yet would keep Escape armed and the 6 second timer would never run.
- Attention is the row that scrolls into view, and takes focus when it asks for it. An attention that only reveals a row is dropped as soon as the ready list does not hold the row, so a Paste of an Item that the filters hide does not scroll to it when the owner clears the filters later (`useOpenItem` in `web/src/use-list-actions.ts`). An attention that asks for focus waits for its row only while the rows on screen were read for other filters than the ones in use, because Escape in the search field sets it while the list may still be reloading for the cleared search, and a dropped attention would leave the focus in the search field. Once the rows are the ones for the filters in use and none is the row, the attention is dropped too, so a row that appears later never takes focus from the owner.
- A row's Try again is queued, not stored as the latest request (`usePasteQueue` in `web/src/use-list-actions.ts`): three presses during one save send three requests after it, in the order pressed.
- When `useItemDetail` fails to read `GET /api/items/:id` again and the Reader still holds an answer for the same Item, it keeps the body and marks it `stale`: the Reader shows `READER_STALE` and Try again above the Summary, so the header (from the list) and a body from an earlier read are never shown as one current Item.
- The Reader restores its reading place once after its text is ready (`web/src/use-reading-place.ts`). A reading place (`web/src/reading-place.ts`, in `sessionStorage`, so each tab keeps its own) holds the block index, the fraction and the offset, and the first 80 characters of the block's text with white space collapsed. Restoring uses the block at that index only when its text still starts with the saved text. Otherwise it scrolls to the first block that does, and when none does the Reader stays at the top. A refresh, a new Digest or a different comment selection that adds or removes blocks therefore never lands the owner on unrelated text.
- The paste box mounts a polite `<output>` and an empty `role="alert"` element before any status arrives and writes every status into one of them, because a live region that is inserted with its text is not reliably announced. The card itself has no live role. The Added, refreshed and failure cards close themselves 6 s after they show, held while the pointer or focus is inside.
- The count lines of the Library list and the Highlights page have no live role because their search text changes on every key; `SettledAnnouncement` (`web/src/SettledAnnouncement.tsx`) reads the settled count instead. Its `ANNOUNCE_SETTLE_MS` delay is a chosen bound, not a measured one. It waits for the answer to the current search and filters so a query is never read with an older answer's count. While the Reader covers the list column, the region follows the count silently so closing the Reader does not replay it. The Reader's announcer (`useAnnouncement` in `web/src/use-announcement.ts`) stays separate because marking an Item read changes the count, and a shared region would replace “Marked as read” with that count.
- `FieldAnnouncer` (`web/src/FieldAnnouncer.tsx`) mounts one polite region for the whole app because forms stand on screens with and without a page announcer. In Grid the paste card floats under the header from 760 px, as `DESIGN.md` (Elevation & Depth) says: it can cover one card for up to 6 s, and the other choice, a card in the page flow, moves every card down and back up on each Paste.
- **Post text renderer.** `react-markdown` with `remark-gfm`, loaded as its own chunk (`PostText`, 36 kB, 13 kB gzip, plus the shared `text-projection` chunk, 135 kB, 40 kB gzip, which holds the Markdown parser that both the renderer and the projection use, measured in `pnpm build`). `postTextModule()` starts the import the first time a Reader renders and caches it, so the sign-in screen and an empty library never download it. - **Post text chunk.** `postTextModule()` (`web/src/post-text-module.ts`) shares one import promise between the Reader's `use()` and its lazy renderer. A rejection reaches the same `ModuleBoundary` as a screen chunk and replaces the screen with the reload action. Try again reloads the page, which is what Vite documents for a failed dynamic import ([Vite, Load Error Handling](https://vite.dev/guide/build#load-error-handling)): in Playwright's headless Chromium (2026-11-09) a second `import()` of a chunk whose first request failed did not send a request again, and after a deploy the old chunk is gone and only new HTML names the new one. The HTML Standard stopped caching HTTP error answers in the module map in July 2026 ([whatwg/html#6768](https://github.com/whatwg/html/issues/6768)), but browsers that ship it, and what they do on a dropped connection, are not checked here. Not verified: Firefox and WebKit, and a chunk that is missing after a deploy.

- **The Import screen.** The browser reads the pasted text or the chosen `.csv` or `.txt` file, so the Instance receives only links. `parseImportList` (`src/core/import-list.ts`) keeps every character of a URL that stands alone in a line or field, so `https://en.wikipedia.org/wiki/SQLite_(database)` stays whole; only a line with other words around its address drops trailing punctuation. `runImport` (`web/src/import-run.ts`) sends batches of at most `IMPORT_BATCH_LINKS` links that also fit the 64 KiB body limit of `POST /api/items/batch` (`nextBatch`), and the cursor counts links done, so a failed call stops at the last saved cursor and Continue sends from there. - **Security headers of the app document.** `DOCUMENT_HEADERS` in `src/http/web-headers.ts` is the one source of the headers on the page. The Node entry sets them on `index.html` in `webRoutes`, and `tools/worker-headers.ts` writes them under `/` in `dist/web/_headers`. The `/` rule covers every page address on Workers, because the Worker answers a path such as `/items/5` with `ASSETS.fetch` of `/`, and the platform applies `_headers` to that response. A rule with a splat would also put the policy on every asset, and the rules of `_headers` add up. `src/http/api-middleware.ts` keeps its own, stricter policy for `/api/files/*`, which the document's never replaces: the Node entry mounts the API before the static files, and `_headers` never touches a Worker response.

  The Worker's `_headers` file has rules for `/assets/*` and `/` alone, so its other static files, including the manifest and icons, get no `nosniff`. The container sends it on those files through `src/http/web-headers.ts`.

  `DOCUMENT_HEADERS` uses `same-origin-allow-popups` for `Cross-Origin-Opener-Policy` because the app opens no window from script and the OpenRouter connect flow navigates the page.

  The app sends no `Strict-Transport-Security`. Both install targets share the headers, and the app cannot know how an Instance is reached, so whoever terminates TLS sets that header.

  `DOCUMENT_POLICY` holds each directive. The reasons the code cannot show:

  - `script-src` needs no `'unsafe-eval'`, because `web/src/zod-jitless.ts` turns off the `new Function` probe that Zod 4 runs for its object parsers (Zod README, `jitless`). It stays the first import of `web/src/main.tsx`, so it runs before any schema is built. Zod catches the blocked probe and falls back, so the only sign of a later import is `eval` violations in the browser console, which fail the smoke spec (`smoke/document-checks.ts`).
  - `style-src` needs no `'unsafe-inline'`, because Vite writes the stylesheet to a file and React sets `style` through the CSSOM, which the directive does not govern.
  - `font-src` carries `data:`, because Vite inlines one JetBrains Mono subset in the stylesheet.
  - `img-src` needs only `'self'`, because `isImageRouteOf` in `Picture` (`web/src/StoredPicture.tsx`) renders an image that is not a stored file as a link, and card images come from `fileRouteOf`.
  - The OpenRouter connect flow leaves the page with `window.location.assign`, which no directive governs.

  `same-origin` sends no `Referer` to another site, such as OpenRouter after the connect flow, and still sends `Origin` on a form posted to this origin, which `no-referrer` would turn into `Origin: null`.

- **Installable app.** There is no service worker. Chromium 156.0.8078.4's installability code (`components/webapps/browser/installable/installable_params.h` and `installable_manager.cc`) has no service-worker requirement, web.dev's Install criteria list none, and a `POST` target that the server handles needs none; a service worker would only add offline handling, which the app does not offer. The installed app needs the share route to run on both targets, so `/share` is in the Worker's `run_worker_first` (see above). `tools/icons/build.ts` draws the icons from `tokens.css` and writes its `--bg` colours into `web/public/manifest.webmanifest` and `web/index.html`, so `tokens.css` stays the one source. The icons are placeholders the owner may replace; `node tools/icons/build.ts` regenerates them and those colours in one run.
- **Share arrivals.** `App` reads the address once (`web/src/share-handoff.ts`) and removes the query with `history.replaceState`, so a reload or Back never repeats it. The arrival (`?link=` with a notice, or `?saved=`) stays until the owner edits the box or a save succeeds, so a wrong password, a sign-out and a second sign-in keep the link and write nothing. A save that starts does not release it, because a save that ends in a sign-in screen unmounts the paste box and the link must come back after sign-in. The address only selects what to show and never saves, so a forged address writes nothing.
