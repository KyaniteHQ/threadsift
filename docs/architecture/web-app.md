# Web app

- A React 19 single-page app built by Vite (owner's decision, 2026-11-04). One static build serves Workers static assets and Hono's `serveStatic` on Node, and it is the shape Tauri and Capacitor take for a later desktop or mobile app. No server rendering: one owner behind a login gains nothing from it.
- React-specific libraries stay few, so the app can try Preact 11 through `preact/compat` after the first release if page weight matters: in a small comparable build, React's framework JavaScript was 68.0 KB gzip and Preact's 7.7 KB (measured 2026-11-04 in a scratch build, not on this app).
- The prototype is Claude Design's own template format on React 18 classes, so the app rewrites it. Its behaviour (reader bar fitting, folding by measured height, reading-place restore, the keys) is plain DOM code and becomes plain TypeScript modules that take an element. Highlights are drawn as `<mark>` elements that React renders inside the Markdown (Highlights in the Reader, under Highlights).
- `design/system/tokens.css`, `components.css` and `settings-table.ts` are the one source of values and settings. `settings-table.ts` owns the rows that `web/` imports; `settings.ts` builds the defaults, stored-settings reader and root attributes from those rows. The table has the Style row (attribute `data-style`, default Library, a Look setting that Reset look covers) and the Text size row (attribute `data-size`, Small, Medium and Large, default Medium, a Look setting in the Reading group), with one `[data-size]` block per option in `tokens.css` that sets only a factor, and its Theme default follows the spec's "with no setting stored, the app draws Light". The Style row offers Library and the 10 Styles in `docs/design/styles.md`. Their `[data-style]` blocks follow the Theme and derived-token rules, with nested `[data-theme]` selectors. Style supplies the fonts and accent; the panel keeps Plex text and inherits the Style accent. Font and Accent keep their stored values while disabled, and Library restores them. The settings table lives in `settings-table.ts`; storage operations and derived values live in `settings.ts`.
- **Settings storage and the root.** All twelve settings are one JSON object in `localStorage` under `STORAGE_KEY` (`design/system/settings.ts`). `readStored` checks each key on its own against the table's option ids with plain code (the settings module imports no Zod), so one bad value falls back alone and a payload that is not an object gives the defaults. Every read and write of `localStorage` is guarded, and a failed write leaves the change applied for the session. The app root carries every attribute the table builds, and `html` carries the same `data-theme`, `data-style` and `data-layout` (the rows marked `onPage`), so the page background and `color-scheme` follow the theme and the page canvas resolves the same `--bg` as the app in every Layout and Theme; while Theme is Match system, a `change` event of `matchMedia("(prefers-color-scheme: dark)")` redraws both without a reload, and a `storage` event for `STORAGE_KEY` from another tab applies that tab's object. Before the first paint, a blocking classic script (no `defer`, `async` or `type=module`) sets the `onPage` attributes on `html` from the stored object, so a stored Dark never draws a Light frame and a stored Grid never draws list greys. The plugin in `tools/theme-script.ts` builds the script from the settings table (key, option ids, the Match system pair) at build time, emits it as the hashed file `/assets/theme-script-<hash>.js` and links it in the built `index.html`'s `head`, so the Content-Security-Policy needs no inline-script hash and no `'unsafe-inline'` for scripts; the cost is one request before the first paint, which the immutable cache answers on every later load. `vite dev` serves the same script at `/theme-script.js`. An unreadable store leaves Light. A change that brings a font stack the root does not use (Font or Style) reaches the root's attributes only once those faces have loaded, or after 3 s (the font block period, https://drafts.csswg.org/css-fonts-4/#font-display-desc): `useSettledAttributes` (`web/src/look-faces.ts`) probes the new attributes on a hidden element, loads the display, interface, mono and reading stacks (`LOOK_FONTS`) and holds the old attributes until then, because the panel's controls show the pick at once while the page restyles in two steps otherwise, first in the fallback face and then in the real one, and the bar's Comments button moved three times. The first paint after a load still uses the stored attributes at once.
- **Settings panel.** The panel is a `<dialog>` inside the app root, never a portal to `body`, so the `data-*` rules of the root reach it and its own `data-font` keeps it in the default type pair. Each single-choice group (Theme, Text size, Text width, Density, Accent) is a `radiogroup` of native `<input type="radio">` elements, one `name` per setting, each inside a `<label>` that is drawn as the segment or the swatch; the input is transparent and covers its label, so it stays focusable and the label shows the focus ring through `:has(:focus-visible)`. The browser gives each group one Tab stop and moves and chooses with the arrow keys; a swatch's accessible name is the `aria-label` on its input. The panel is a container (`container-type: inline-size`), and under `24rem` of its own width each label sits above its control; its width is `--pop-w` in `rem`, so it grows with the browser's text size. At 760px and wider it is a non-modal popover (`show()`) that closes on Escape, when focus leaves it or when a press lands outside. Under 760px it is a modal sheet (`showModal()`): the browser makes the rest of the page inert, puts the panel in the top layer and draws `::backdrop`, which `components.css` fills with `--scrim`; Escape arrives as the `cancel` event, a tap on the backdrop closes it, and a Tab handler wraps from the last control to the first and back. The panel is closed and shown again when the width crosses 760px; if the focused element is gone, as Close is, focus goes to the first checked radio in the panel body (`FIRST_CHOICE` in `web/src/use-panel.ts`). Closing returns focus to the gear.
- Fonts: `tokens.css` imports no font host. Every face comes from a Fontsource package in the build, so a self-hosted Instance makes no third-party request. `web/src/main.tsx` imports only the faces of the default Font, IBM Plex Sans and Plex Mono, which are also the settings panel's type pair. Every other family is a dynamic import named in `design/system/style-faces.ts`, which lists the faces of each Style and of each Font; a Style other than Library sets all four stacks, so its list replaces the Font's. `tools/check-font-faces.ts` (`pnpm run check:faces`, run by the `design:check` task) reads each face's `font-family` from the Fontsource stylesheets that `style-faces.ts` imports (the Plex faces from `web/src/main.tsx`) and the stacks from `tokens.css`, and fails the gate when a Style other than Library or a Font sets no stack, when a stack starts with a family that the faces of its Style or Font do not provide (a generic or system family as the first family fails too), or when a row loads a face that none of its stacks names, because the page would show the fallback font with no error. It models the cascade of equal-specificity rules in file order, where a rule for a Font that follows a rule for a Style would override the Style, and it models only top-level rules selected by `:root`, `[data-font]`, `[data-font="id"]` and `[data-style="id"]` of a Style other than Library: a stack set in an at-rule, a nested rule, a compound selector or a Library rule fails the gate instead of passing unread, and it does not check weights or italics. Vite settles such an `import()` after the stylesheet has loaded ([Vite, Features, CSS Code Splitting](https://vite.dev/guide/features#css-code-splitting)), so `main.tsx` waits for the stored Style's faces before React renders, and `useSettledAttributes` (`web/src/look-faces.ts`) waits for a changed look's faces before it applies the look. Both waits end after `FACE_WAIT_MS` (3 s). A face stylesheet that hangs therefore delays the first render by up to 3 s, and the first Item row appears after about 3 s either way: with the stylesheet held on this build and with the font files held on `main`, where the font gate already waits that long. A stored non-default Style asks for its stylesheets after the entry script runs, so a cold load in it needs one more round trip before first paint than the default Style. A face stylesheet that fails is not tried again in the same document (the preload helper keeps its rejected promise): when it fails after a change of look, `useSettledAttributes` reloads the page once, which loads the stored look from the start; when it fails at the start, the page renders with the fallback fonts of the stacks until the next reload. Fontsource's variable packages name their family with a `Variable` suffix (Fontsource docs, Variable fonts), so each font token in `tokens.css` names `'<Family> Variable'` first and the plain family as the fallback. Instrument Serif, Cal Sans, Spectral, DM Mono, Fira Mono and Space Mono have static Fontsource packages. They register the plain family name and load per-weight files; the catalogue offers no variable face for them. The other Style faces use variable packages. Imports keep all package subsets, as the existing font imports do, so saved text can use the supported scripts. Weights and italics follow the Google Fonts list in `design/prototype/tokens.css`: `opsz.css` for Newsreader, Bricolage Grotesque, Source Serif 4 and DM Sans, which have an optical-size axis in that list, `wght.css` for the rest, and the italic files of Newsreader, Instrument Serif, Spectral and EB Garamond. The document-head script and `use-settings.ts` both apply Theme and Style to `html`, so the page canvas matches the app before and after React mounts. `--acc` is derived only where its inputs change, so the panel inherits the Style accent and each Accent swatch draws its own hue.
- **Screen chunks.** `web/src/lazy-pages.tsx` loads the Settings, Import, Proposals and Log screens through `lazyModule` (`web/src/lazy-module.ts`), each inside `ModuleBoundary` (`web/src/ModuleBoundary.tsx`): a failed import becomes `ModuleUnavailable` and the boundary shows `Unreachable` with Try again, which reloads the page; `PostText` uses the same three. One `Suspense` with no fallback in `App` holds them. The route (`usePath`) and the session view (`useSessionView`) are set only through `useScreenState` (`web/src/use-screen-state.ts`), which starts a transition, so the current screen stays until the next screen's chunk arrives. Any new setter of what the screen shows must use it, because an update outside a transition hides the screen behind the fallback ([React, Suspense](https://react.dev/reference/react/Suspense)). The `popstate` handler sets the path one task later, because React renders a transition that starts inside a `popstate` event synchronously. `navigate` does nothing for the address the page is already on, and `useAutoOpen` waits while the address is ahead of the route. A new lazy screen goes into `LOADERS` in `lazy-pages.tsx`, which also lets `main.tsx` start its chunk when the address names it, so a reload does not wait for the session answer first. `vite.config.ts` has two `codeSplitting` groups. `zod` holds Zod and `zod-jitless.ts`, so jitless is set before any schema is built and the page's Content-Security-Policy needs no `'unsafe-eval'`. `shared` holds each module of `web/src` and `design/system` that two chunks share, with its dependencies (`src/core` among them), because Rolldown's automatic splitting makes one common chunk per set of importers ([Rolldown, Automatic code splitting](https://rolldown.rs/in-depth/automatic-code-splitting)) and the entry loads all of them before first paint. After a change to these groups, run `pnpm build` and count the `modulepreload` links in `dist/web/index.html`: each one is a file that the first paint waits for.
- Static files answer the same on both targets: `index.html` for a path whose last segment has no `.`, `404` for any other path that matches no file, so `/favicon.ico` and a missing `/assets/x.js` are not HTML. Workers' `single-page-application` mode cannot do this: it answers every unmatched path with `index.html` and `200` (Workers docs, Static Assets, Single Page Application, Configuration; `wrangler dev` 4.156.0 answered `/favicon.ico` and `/assets/nope.js` with `200 text/html`). The Worker therefore leaves `not_found_handling` unset, gets the `ASSETS` binding, and serves `/` itself for a `GET` or `HEAD` of a path without an extension (`src/targets/worker/index.ts`). `run_worker_first: ["/api/*", "/share", "/mcp"]` makes the Worker answer those paths before any static asset (Workers docs, Static Assets, Routing, Worker script); the setting only decides when the Worker runs, so `isServerPath` (`src/http/document-path.ts`) also sends `/api`, `/api/*`, `/share` and `/mcp` to the Hono app, because `serveDocument` answers a `POST` with 404. The Node entry mounts the Hono app before static files, so `/share` and `/mcp` reach it there without a rule, and serves the page with `isDocumentPath` (`src/http/document-path.ts`) on the pathname of `new URL(context.req.url)`. Hono's `context.req.path` decodes `%2E` to `.` (checked with Hono in `node_modules` on 2026-11-11: `GET /topics/node%2Ejs` gave `/topics/node.js`), which would turn the page of a dotted Topic into a 404.
- **Topic page.** `web/src/TopicPage.tsx` shows one Topic (`docs/wiki.md`, Topic pages, The page). `useTopicPage` (`web/src/use-topic-page.ts`) holds its state: loading, failed, missing, or ready with the Items read so far, and it reads the next 50 on Load more. `SignedInScreen` (`web/src/SignedInScreen.tsx`) draws the signed-in screens, `PageBar` (`web/src/PageBar.tsx`) is the bar of the Highlights page and the Topic page, and the Topic page is keyed by its address, so a move between two Topics starts from the loading state.
- **Index.** `web/src/IndexPage.tsx` lists every Topic (`docs/wiki.md`, The Index, The page). `/topics` has no `.`, so both targets answer `index.html` for it and for `/topics/` with no routing change. `SignedInScreen` draws it for the `index` screen and passes it the router's `Pages`, whose `topic` function opens a row.
- **Proposals.** `web/src/ProposalsPage.tsx` lists the open and accepting Proposals of every kind through `ListPage`, each row with Accept and Reject (a lost-Highlight row draws `LostHighlightBody`: the effect, the Item's title as a link to the Reader place, the quote and the note that the passage is no longer found), and reads again every 3 seconds while a row is accepting (see `docs/proposals.md`, The page). `/proposals` has no `.`, so both targets answer `index.html` for it with no routing change. A Topic row adds a line on the overview effect and a `topic-busy` note, and the Topic page replaces an old address with the survivor's path when the answer's `topic.key` differs from the requested key (`use-survivor-address.ts`, `history.replaceState`).
- **Log.** `web/src/LogPage.tsx` lists the Log (`docs/wiki.md`, The Log, The page). `/log` has no `.`, so both targets answer `index.html` for it with no routing change. `SignedInScreen` draws it, through `WikiPage`, for the `log` screen and passes it the router's `Pages`, whose `item` and `topic` functions open a line's title and Topic name.
- Caching: hashed `/assets/*` are `public, max-age=31536000, immutable` and `index.html` is `no-cache`. The Node entry sets them in `src/targets/node/web-routes.ts` and compresses with Hono's `compress` middleware. On Workers the platform compresses, and `tools/worker-headers.ts` writes `dist/web/_headers` at build time from the same constants (Workers docs, Static Assets, Headers), so the two targets cannot drift; that file also reaches `dist/web`, so the Node entry answers `/_headers` with the page and never serves the file. `/index.html` redirects to `/` on both targets (`307`).
- The library, not the paste card, reads `GET /api/items/:id/status` (the list's columns, without the post text) once a second for each Item's first 10 polls, then once every 5 seconds while it stays `processing` (`web/src/item-polling.ts`). The count belongs to the Item, so a new `processing` Item does not start the others' reads over. An Item whose `wait` names a `retryAt` is read next at `retryAt`, at most 60 seconds ahead (the sweep period, a chosen bound) and never sooner than the normal pause. A read that answers 404 means the Item was deleted elsewhere: the library drops it from the list, recounts, and never reads that id again. The card shows the state of its Item from those reads, so a dismissed card, a card that a newer Paste replaced and a page load that found a `processing` Item all update their row. A read changes the list only when it succeeded and the Item differs, so an unchanged poll renders nothing, and an Item's next read starts after the last answered, so reads never stack. A hidden tab (`document.hidden`) makes no reads, and the first read after it becomes visible runs at once. No websocket, so both targets serve it the same way.
- A list read that fails shows the load error with Retry only when the rows on screen were not read for the filters it asked for (the first load, or a new filter). A reload for the same filters that fails keeps the rows and the open Reader, because a network blip during a background reload must not replace what the owner is reading; the next change (a poll that ends a `processing` Item, a delete, a Paste) reads the list again, and the failure is not announced (`useListRead` in `web/src/list-reads.ts`).
- **Pages of the list.** `GET /api/items` answers at most 50 Items (`ITEMS_PAGE_SIZE` in `src/core/item-page.ts`) and `next`, the cursor of the page after. The cursor is `<saved date>.<Item id>`, built from the sort columns, and `listItems` (`src/core/item-selection.ts`) reads the rows below it with the row-value comparison `(saved_at, id) < (?, ?)` under `order by saved_at desc, id desc`, which the `items_saved_at_id` index serves. It asks for 51 rows, and a 51st row means `next` is the cursor of the 50th. The id breaks a tie between Items saved in the same millisecond, so a page edge inside such a run neither repeats nor skips an Item. **Identity of the cursor.** It names a position, not a record. The Item id is the generated key that is never reused, and `saved_at` is written once at insert, so a delete, a refresh, a Digest or a Read state change between two reads moves no later page, an Item saved after the first read is newer than every cursor, and a cursor survives the deletion of the Item it names. A restore that renumbered ids or changed `saved_at` would make an old cursor name another position, and a read from the first page gives a fresh one (Export and restore are not built, so no run has checked this). A cursor the server did not give, whose two numbers are safe integers, is accepted and answers the Items after that position; any other cursor is a 400. The counts (`countQueries`) run in the batch of a read with no cursor only, because each scans the whole `items` table and a page read from a cursor needs none. The counts of the first page cover the whole library, so the filter pane and the header stay true while the rows come in pages.

  The browser keeps the pages it has read in `ListState` (`web/src/list-state.ts`). `items` is always the newest-first start of the library for the filters in `query`, `next` is the cursor after its last row, and `more` is `idle`, `loading` or `failed`. `useNearEnd` (`web/src/use-near-end.ts`) watches the row 10 before the last and the last row with an `IntersectionObserver`, in List and in Grid, so the next page starts about ten rows before the owner reaches the end, and also when a jump to the end skips that row. It watches the rows again whenever the list changes, because a filter can leave as many rows as before. An empty list that still has a `next`, such as one whose newest 50 rows the list skips because they fail the list's `ItemSchema` (`shownItems`), keeps reading pages until a row shows or the pages end, and says "No items match" only then. `useMore` (`web/src/list-more.ts`) reads the page, shares one request among its callers, and appends it only when the list still holds the same `query` and `next`, so an answer for an old filter or an old position is dropped. An Item the owner changed or deleted while the page was on its way keeps the owner's value (`appended`, `stamps`). Under the rows, while more pages exist, a Load more button (the `btn` component, in the `noresults` block that the Grid centres) reads the next page like the observer does; it is `aria-disabled` while the page loads, the load rows sit above it, and a failed page replaces it with the load error and Try again, which keep the rows. The button is the keyboard and screen reader way to the next page when no row crosses the viewport. j, k, Previous and Next move through the loaded rows. `useStep` (`web/src/use-step.ts`) holds one pending step: at the last loaded row it asks for pages until the neighbour exists, and from an Item opened by its address, which is not in the loaded rows, it asks for pages until that Item is among them and then steps to its real neighbour. The step is dropped when the owner presses another key, closes the Reader, opens another Item or moves focus before the page lands, and while it waits the Reader's live region says "Loading saved links…", or the load error when the read fails (the Reader's Next or j reads again). A reload (a Paste in a filtered list, a Digest that moves a Topic) reads the first page and then the pages after it until it passes the last row the list had loaded (`readThrough` in `web/src/list-reads.ts`), and replaces the rows, so an Item that stopped matching leaves, an Item that began to match appears at its place, and the owner keeps their place because the rows are keyed by Item id. A new Item is placed by its saved date and id (`placed`): among the loaded rows when it is newer than the last one, and not at all when it belongs to a page not yet read. A Paste of a link the library already holds, whose row is not loaded, leaves the counts alone. It also reads the next pages one after another until that Item's row is among the loaded rows (`useSeek` in `web/src/use-seek.ts`), and then scrolls the row into view, as for a loaded row. A share that arrives at `/?saved=<id>` or `/?refreshed=<id>` seeks the same way: the Item is read through `GET /api/items/:id/status` and kept in `known`, so the Paste card shows even when the Item lies past the loaded pages, and then the row is sought. The reads are the ones `useMore` shares with the observer and Load more, and `usePageReader` in `web/src/list-more.ts` is the one loop that asks for them, for the seek and for j and k (`useStep`): it asks once for the cursor it needs, waits while that read is on its way, and stops on the end of the pages or on a failed read of the cursor it asked for. So the rows stay the newest-first start of the library, no Item repeats, none is skipped, and the owner's later scroll continues from the last row. The cost grows with the Item's position (the 2,000th of 3,000 Items is 39 reads), which is the price of keeping one run of rows. The other design, reading only the page that starts at the Item and marking the gap before it, costs one read, but every consumer of `items` (`appended`, `readThrough`, `useNearEnd`, `useStep`, the counts of loaded rows) would then need to know about holes. The seek stops without a row when a filter or search is on (the Item may not match it, and the reload of a filtered list decides what shows), when the Item is deleted meanwhile, when the pages end, and when a page read fails. It also ends, without scrolling, as soon as the owner's attention moves on: a later Paste, a change of filter or search, a different open Item, a step with j or k, a deletion,, any other move of the list's attention (`attend` in `useListActions`), or the owner's own wheel, touch scroll, key press or pointer press anywhere on the page (`onOwnerMove` in `web/src/use-seek.ts`); a page that lands after that is appended and nothing more. An Item opened by its address is never sought, so the Reader opens at once and the row appears with its page. An Item opened by its address that is not in the loaded rows is read through `GET /api/items/:id/status` and kept in `known` only (`useLookup` in `web/src/use-list-actions.ts`). An address that answers 404 returns to `/`; any other failure keeps the address and shows the load error with Try again. The header reads "{shown} of {total}" from the loaded rows when every row is loaded, and from the Source counts of the first page otherwise (`matchedCount` in `web/src/list-counts.ts`).

  **Measured on 2026-11-10** with a library of 3,000 Items (all five Sources, 2,250 unread, 3 Topics and 2 Tags, a title, an author and a community on each, no Digest and no picture, so a real library answers larger rows). It was seeded into a fresh Instance by SQL and read on the development machine through the HTTP API and a real Chromium at 1440 px, with a harness that is no longer in the repository. The harness recorded 5 reads of `GET /api/items` and the whole walk by cursor, and 5 navigations as `performance.now()` when the first `article.it` exists, in List and in Grid. The "before" rows are the same harness on the parent commit, where `GET /api/items` answered all 3,000 Items.

  | Worker, after | 50 Items | 25,337 bytes | 10 to 14 ms | 46 to 58 ms (50 rows) | 43 to 47 ms (50 rows) |

  The answer was about 503 bytes for each Item, so a library of about 100,000 such Items would have crossed D1's 50 MB result cap (guess: the cap counts D1's rows, which the JSON only approximates). A page is bounded by its 50 Items whatever the library holds. Reading all 60 pages took 476 ms on the Worker and 247 ms on the container. The numbers come from one machine and local D1, so they show the size of the change and not production latency, and no run has read a large library on deployed D1.
- A share arrival (`?link=` with a notice, or `?saved=`) lives in `ShareContext` until it is released, and the paste box reads it when it mounts. Typing, a finished save and closing the card (Dismiss, Escape, or the card closing itself) release it (`usePaste` in `web/src/use-paste.ts`). A save that starts does not, because a save that ends in a sign-in screen unmounts the paste box and the link must come back after sign-in. A prefill the owner dismissed therefore does not fill the field and the notice again when the owner returns from Settings.
- Read state writes go one after another for each Item (`useAnnouncement` in `web/src/use-announcement.ts`). A press computes its wanted state from the last wanted state still in flight, not from the Item on screen, and its PUT starts after the Item's earlier PUT has answered. Two presses of `m` before the first answer therefore send `read` and then `unread`, the older answer cannot be the last one applied, and each answer announces its own state. Writes to different Items do not wait for each other.
- A card for an Item that the library no longer knows (deleted from another tab or by an agent token, found by the status read that answers 404) is closed by `usePaste`, because a card with no face renders nothing yet would keep Escape armed and the 6 second timer would never run. Closing it also releases a share arrival, like any other close.
- Attention is the row that scrolls into view, and takes focus when it asks for it (Try again, leaving the search field for the open Item). An attention that only reveals a row (the one a Paste of a known Item sets) is dropped as soon as the ready list does not hold the row, so a Paste of an Item that the filters hide does not scroll to that row when the owner clears the filters later (`useOpenItem` in `web/src/use-list-actions.ts`). An attention that asks for focus waits for its row, because Escape in the search field sets it while the list may still be reloading for the cleared search, and a dropped attention would leave the focus in the search field.
- A row's Try again is queued, not stored as the latest request: each press adds a Paste (or a Digest retry) to the queue in `usePasteQueue` (`web/src/use-list-actions.ts`), and the paste box takes the first one whenever no save is running (`usePasteRequest` in `web/src/use-paste.ts`). Three presses during one save therefore send three requests after it, in the order pressed.
- `useItemDetail` (`web/src/use-item-detail.ts`) reads `GET /api/items/:id` again whenever `refreshKey` changes. When that read fails and the Reader still holds an answer for the same Item, it keeps the body and marks it `stale`: the Reader shows `READER_STALE` and Try again above the Summary, so the header (from the list) and a body from an earlier read are never shown as one current Item. Try again clears the answer and reads again; a failure then shows the plain failed state.
- A reading place (`web/src/reading-place.ts`, in `sessionStorage` under `threadsift:reading-places`) holds the block index, the fraction and the offset, and the first 80 characters of the block's text with white space collapsed. Restoring uses the block at that index only when its text still starts with the saved text. Otherwise it scrolls to the first block that does, and when none does the Reader stays at the top. A refresh, a new Digest or a different comment selection that adds or removes blocks therefore never lands the owner on unrelated text. A place saved without text (by an earlier build) fails the schema, and `readPlaces` then drops every saved place of the tab.

The address only selects what to show and never saves, so a forged address writes nothing.
