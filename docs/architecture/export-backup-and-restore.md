# Export, backup and restore

- The export zip holds a Markdown note for each Item with its stored images and its post text file beside it, as the spec describes (all built), every library record as JSON Lines files under `records/`, and `threadsift.json`, the manifest that lists those files with their row counts and holds the format, the export time, the highest applied migration, the version of each data step, the `sqlite_sequence` value of each `AUTOINCREMENT` table and the number of Items that had an open fetch or Digest job when the export read them (all built). Every entry sits under one folder named `threadsift-<UTC date>/`. The manifest holds no records, because a CRC-32 needs a whole entry and one file of every record cannot be written in slices. `src/core/backup-tables.ts` names the tables and columns the records hold, and gives a reason for each table they leave out. The records hold every stored comment, Kept or not (`reddit_comments` with its `eligible` and `kept` columns), and the Item notes hold Kept comments only. They leave out secrets (Provider keys and the other sealed values: `settings`, `github_settings`, `reddit_account`, the Grok Bot webhook address and key in `grok_bot_settings`, the vault token), the choices of a Provider or an X reader that may not exist on the target (`ai_settings_revision`, `x_settings`), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `topic_leases`, `data_step_lease`, `x_verifications`, and every `ai_tasks` row no Digest names), because a restored Instance gets a new password and new tokens and starts with no work in flight. It keeps the `ai_tasks` rows that Digests name, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. Every record keeps its id: the restore inserts the ids from the record files unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. A fresh Instance can restore from it (not built). The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** (built, except its Settings screen) is a chain of jobs of the kind `export`. `POST /api/export` inserts the `exports` row (`running`) and the first job in one batch; each slice reads the next rows, closes whole zip entries, writes them as objects of the file store, and returns one checkpoint that the runner commits in the same guarded batch that closes the job and opens the next one (`src/core/export-job.ts`). The checkpoint in `exports` holds the stream the next slice resumes in (`stream`, a table name, or `item-files` after the last table) and the row id it resumes after (`cursor`, the Item id in `item-files`), the entry and byte counts, the number of parts and a JSON tally (the files and rows of each table, the count of open Items, the attempt number of each part, and the list of tables the export started with), so a stopped container, a lost queue message or a dead Worker continues from the last committed slice instead of restarting: the container's start puts `running` jobs back to `queued`, and on Cloudflare the sweep takes over a claim that expired. A job that fails 3 attempts ends the export `failed` with `gave-up`. A slice that finds that the table list differs from the one the export started with (a deploy that added, removed or moved a table in `BACKUP_TABLES` while the export ran), or a stored table name the list no longer has, ends the export `failed` with `list-changed`, because resuming would skip or repeat a table without any error.
  - **Layout in the file store.** Slice `n` of attempt `g` writes `exports/<id>/part-<n>-<g>` (the local headers and the data of its entries), `exports/<id>/dir-<n>-<g>` (their central-directory records) and, on the last slice, `exports/<id>/tail-<g>` (the ZIP64 end records). `g` is the attempt number of the claim that built the slice, and the checkpoint records it for each part. A runner that lost its claim and writes late therefore writes other names than the runner that committed the slice, and cannot overwrite committed bytes; its guarded commit fails and the runner deletes the objects it wrote. A retry after a graceful stop (the job was put back to `queued`) reuses the attempt number and overwrites the dead run's objects, and a retry after a kill takes the next number, so the killed run's objects stay under the old number, unreferenced, until the export is removed. The objects are separate because R2 multipart needs equal parts of at least 5 MiB and the container has no multipart. The download streams every `part`, then every `dir`, then the `tail` the checkpoint names, and the result is one store-mode zip (method 0, UTF-8 names, ZIP64 records when there are 65,535 entries or more or an offset or size reaches 4 GiB; `src/core/zip.ts`). `Content-Length` is the sum of the stored sizes. A temporary file that a killed container left beside an object (`.tmp-<hex>-part-<n>-<g>`) is listed and deleted with the export's other objects. The download stops reading and closes the open object when the client disconnects, also in the gap between two objects.
  - **Records.** The slices read one table after another: `topics` and `tags` first, then the other tables in the order of `BACKUP_TABLES` (the order is not a parent order; a restore derives that from the foreign keys). A table is read in pages of at most 2,000 rows in `rowid` order, and a page also stops when the rows it holds reach the room left in the slice, counted in bytes by one SQL window over the column lengths, so a page of long comments or Topic pages stays inside the budget. A page always holds at least one row. A slice ends when it has 8 MiB of rows or the library ends (`EXPORT_SLICE_BYTES`, `EXPORT_PAGE_ROWS` in `src/core/export-contract.ts`; the figures behind them are in Open items and unverified claims). A table's rows go to `records/<table>.<n>.jsonl`, one JSON object per line with `null` written out, and a file closes at 8 MiB (`EXPORT_ENTRY_BYTES`, chosen, unsupported) so every entry is complete inside one slice and its CRC-32 is known before the next slice starts. A table with no rows gets one empty file, `records/<table>.1.jsonl`, so every included table has a file. The manifest is the last entry.
  - **Item notes, images and post text.** After the last table the slices read the Items by id (the stream `item-files`). A slice takes at most 40 Items (`EXPORT_SLICE_ITEMS`, chosen, unsupported) and stops earlier when the next Item's stored images would take the slice past 8 MiB (`EXPORT_SLICE_BYTES`), so an Item whose images alone pass 8 MiB gets a slice of its own. `takeItems` in `src/core/export-items.ts` reads each Item with `readItem` (`src/core/item-detail.ts`), the read the Reader uses, so the Summary, Key points, Highlights, Note, post text and comments of a note are the Reader's, and adds three kinds of entry under `items/<id>/`: `note-<slug>.md`, the post text file under its stored name (`post-<job>-<attempt>.md`, only when the Item keeps its text in a file) and every `media` row with outcome `stored` under its file key (`img-<job>-<attempt>-<position>.<ext>`). `note-` cannot collide with a stored name, which starts with `post-` or `img-`. `itemNote` and `noteFileName` in `src/core/item-note.ts` are pure functions of the Item's values, written so the Vault mirror can call them. The front matter holds `id`, `source`, `url`, `author`, `community`, `posted`, `saved`, `fetched`, `topic`, `tags` and `read`, with every string written by `JSON.stringify` (and `\uXXXX` for the characters YAML refuses raw), a null written as an empty string, and no `title` key, so a hostile title or author cannot add a key. The body is the title as one line (whitespace runs become one space, `Untitled` when empty), then the Summary, Key points, Highlights (a quote that is no longer found is followed by the Reader's line that says so), Note, post text and comments, each section only when it has content. Comments are the Reader's nodes when a Digest covers the thread and none before, so a note holds Kept comments only (plus a comment an attached Highlight holds, as in the Reader): blockquotes nested by depth, each led by the author's handle, and a Context stub as one italic line with the Reader's text. An image link in the post text that names one of the Item's own files (`/api/files/items/<id>/<name>`) becomes the bare file name, so the folder works wherever it is copied; every other link stays as stored. The slug is the title lower-cased with each run of characters that are not letters or digits turned into `-`, trimmed, and cut at 80 code points and at 240 bytes (the byte cut keeps a file name under the 255-byte limit of common file systems), and `item` when it is empty. The labels are the Reader's own texts, copied into `src/core/item-note.ts` because `src/core` cannot import from `web/`. An Item deleted before its slice reads it is left out. A file that is missing when its Item is read, the post text file or an image, makes the slice read that Item's rows and files again once, because a refresh in between gives the Item new keys; a second miss throws `ExportFileMissing`, the attempt fails and the job retries as for any failed attempt. Each Item costs 11 D1 statements (the Reader's 10 and the list of stored files), which puts a slice of 40 Items near 440 against the 1,000 queries of one invocation (arithmetic, not run on a deployed Worker).
  - **Not a snapshot.** The slices read the live database over minutes, so a row written between two slices can appear in one table's file and not in a related one. The manifest's `openItems` counts the Items that had an open job of the kinds `jobs` holds for an Item (a fetch, a Digest or an X check) when their page was read, because a restore may see their text and Digest from different moments. An Item deleted after its page was read stays in the zip.
  - **One at a time, kept 24 hours.** A partial unique index on `exports` (`exports_one_live`) allows one `running` or `ready` row, so a second start while one runs answers 409. A start while one is `ready` marks the old row `failed` with `replaced` and removes its objects. Removing an export marks the row `removing`, deletes its objects page by page, and then marks it `expired`; the download of a `removing` or `expired` id answers 404 and the status reads `none`, and a failure in the middle leaves a `removing` row that the next sweep finishes. The sweep stage `exports` removes a `removing` export, a `failed` export 12 minutes after its last update (the 10-minute slice deadline plus the 2-minute claim margin, `EXPORT_SLICE_DEADLINE_MS` and `CLAIM_MARGIN_MS`, so a slice that was still running has ended) and a `ready` one whose `finished_at` is 24 hours old (`EXPORT_KEEP_MS`), 5 exports a sweep. `DELETE /api/export` removes a ready or failed export at once. It stops a running export (state `failed`, `cancelled`, its job closed, and `none` in the status from then on) and leaves its objects to the sweep: a slice that is already running fails its guarded commit and deletes what it wrote, and the sweep removes the rest 12 minutes later. A `DELETE` that finds the export `ready` by the time it writes removes it as a ready one.
  - **Limit of the download on the Worker.** The download reads 2 objects per slice and the tail, and each read is a subrequest of the one invocation that streams the zip. The Cloudflare target needs Workers Paid (`cloudflare-deploy-button.md`), and Paid allows 10,000 subrequests (Workers docs, Limits), so 4,999 slices. A slice holds 8 MiB of record rows, or from 1 to 40 Items with their notes, images and post text files: it stops at 40 Items, or when the next Item's images would take it past 8 MiB, and an Item takes a slice to itself when its own files pass 8 MiB. A library therefore needs at least its Items divided by 40 slices and at most one slice for each Item plus the record slices (8 MiB of rows each). Paid covers 199,960 Items when every slice holds 40, and always covers a library of 4,900 Items or fewer when its records fill under 99 slices (792 MiB), whatever the size of its images. The 4,000-Item library the spec plans needs between 100 slices (201 reads) and about 4,010 slices (8,021 reads, guess for the record slices). The 50 subrequests of the Free plan allow 24 slices, so 960 Items at best; the Cloudflare target does not support that plan. The container has no such limit. All of this is arithmetic and not a run on a deployed Worker.
  - **Planned and not built.** The Backup section of Settings. The plan's deletion hold, which would delay a file deletion while an export runs, is replaced by the re-read of a missing file above, because the hold would touch the finish, the cleanup and the delete paths.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`. When the export's version of a data step is lower than the running release's, or the export has none, the restore leaves that step's row out and the step runs after the last batch, so a library exported before a rule change gets the same rewrite as a live one (Database and search, Data steps). Planned and not built.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it holds the records, the manifest, the Item notes and the stored files. D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/backup-tables.ts` names every included table with its scope, the columns a backup exports and the columns it leaves out; `EXCLUDED_TABLES` in the same file names every other table, including the search tables, with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`: their values travel in `threadsift.json`, not as records. `test/backup-tables.test.ts` migrates a fresh database and fails when a table is in neither list or in both, or when a column of an included table, a generated column included, is in neither set. A later migration that adds a table or a column must therefore decide where it belongs. The key order of either list is not an insert order: the restore derives the parent order from the foreign keys of the migrated database. The export reads the list in its order after `topics` and `tags`, and an export that is running when a release changes the list ends `failed` with `list-changed`. The restore is not built.
