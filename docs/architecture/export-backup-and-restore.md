# Export, backup and restore

- The export zip holds a Markdown note for each Item with its stored images and post text file beside it, every library record as JSON Lines files under `records/`, and the manifest `threadsift.json`. The manifest lists those files with their row counts and holds the format, the export time, the highest applied migration, the `sqlite_sequence` value of each `AUTOINCREMENT` table, and the number of Items that had an open job of a kind in `ITEM_JOB_KINDS` (`src/core/contract/job-contract.ts`) when the export read them. Every entry sits under one folder named `threadsift-<UTC date>/`. `src/features/export/core/export-format.ts` owns the root folder, the manifest name, the record file names and the manifest schema, so the writer and Restore's reader share one definition; Restore reads the format, the migration, the tables and the sequences and ignores the export time and the open Item count. The manifest holds no records, because a CRC-32 needs a whole entry and one file of every record cannot be written in slices.
- `src/core/kernel/backup-tables.ts` names the tables and columns the records hold and gives a reason for each table they leave out. Secrets, the owner's password hash, sessions, agent token hashes and the working tables are left out, because a restored Instance gets a new password and new tokens and starts with no work in flight. The `ai_tasks` rows that Digests name stay, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. The records hold every stored comment, Kept or not, and the Item notes hold Kept comments only.
- Every record keeps its id. The restore inserts the ids unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/contract/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. The same Export zip moves a library between the two install targets.
- **Why the app writes its own backup.** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data). D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/kernel/backup-tables.ts` holds one record for every included table: the columns a backup exports, the columns it leaves out, and what a Restore does with the table (`mustBeEmpty` for a table whose rows make the library non-empty, `singleton`, `rewrites` and `rebuiltInto`). `EXCLUDED_TABLES` in `test/backup-tables.test.ts` names every other table with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`. `test/backup-tables.test.ts` fails when a table is in neither list or in both, or when a column of an included table is in neither set, so a migration that adds a table or a column must decide where it belongs. Neither list's key order is an insert order, because the restore derives the parent order from the foreign keys of the migrated database. A Proposal is two records, its `proposals` row (`records/proposals.<n>.jsonl`) and one subject row (`records/tag_merge_proposals.<n>.jsonl`, `topic_merge_proposals`, `highlight_lost_proposals`, `overview_gap_proposals` or `items_disagree_proposals`), and the Export reads the tables in slices, so a row of one may be read without its partner. Restore inserts the `proposals` rows first, drops a subject row whose `proposals` row, Tag, Topic, Highlight or Item is not in the restored library, and its finishing slice deletes each `proposals` row left with no subject row (`proposalsWithoutSubject`, `src/features/restore/core/restore-finish.ts`). A zip from a build before `0009_proposals_subjects.sql` holds no subject files and names an older `migration`, so Restore refuses it with `other-release`.

## Export

An export is a chain of jobs of the kind `export`. `POST /api/export` inserts the `exports` row and the first job in one batch. Each slice reads the next rows, closes whole zip entries, writes them as objects of the file store, and returns one checkpoint that the runner commits in the same guarded batch that closes the job and opens the next one (`src/features/export/core/export-job.ts`). A stopped container, a lost queue message or a dead Worker therefore continues from the last committed slice. On the container the start expires the claim of every `running` job (`abandonRunning`, `src/core/compose/jobs.ts`), and on Cloudflare the sweep takes over a claim that expired. A job that fails 3 attempts ends the export `failed` with `gave-up`. A slice that finds that the table list differs from the one the export started with ends it `failed` with `list-changed`, because resuming would skip or repeat a table without any error. A deploy that changes a table or an exported column in `BACKUP_TABLES` while the export runs causes this.

- **Layout in the file store.** Slice `n` of attempt `g` writes `exports/<id>/part-<n>-<g>`, `exports/<id>/dir-<n>-<g>` and, on the last slice, `exports/<id>/tail-<g>`. Attempt number `g` is in the name so that a runner that lost its claim and writes late writes other names than the runner that committed the slice. It cannot overwrite committed bytes, its guarded commit fails, and it deletes what it wrote. The objects are separate because R2 multipart needs equal parts of at least 5 MiB and the container has no multipart. The download streams every `part`, then every `dir`, then the `tail`, as one store-mode zip with ZIP64 records when needed (`src/features/export/core/zip.ts`). `src/core/contract/file-keys.ts` builds these names beside the pattern that accepts them, and `src/features/export/core/export-zip.ts` uses them, with the zip size, for the slice that writes the objects and for the download that reads them back.
- **Records.** The slices read `topics` and `tags` first, then the other tables in `BACKUP_TABLES` order. A table is read in pages of at most 2,000 rows in `rowid` order, and a page also stops when its rows reach the room left in the slice, so a page of long comments stays inside the budget. A slice ends at 8 MiB of rows (`EXPORT_SLICE_BYTES`, `EXPORT_PAGE_ROWS` in `src/core/contract/export-contract.ts`; the figures behind them are in Open items and unverified claims). A record file closes at 8 MiB (`EXPORT_ENTRY_BYTES`, chosen, unsupported), so every entry is complete inside one slice and its CRC-32 is known before the next slice starts. A table with no rows gets one empty file, so every included table has a file.
- **Item notes, images and post text.** After the last table the slices read the Items by id, at most 40 Items per slice (`EXPORT_SLICE_ITEMS`, chosen, unsupported) and at most 8 MiB of entries, except that a slice's first entry is taken whatever its size. When the next entry does not fit, the slice ends inside the Item and the checkpoint records how many of its entries are written, so an Item of 20 images of 2 MiB spreads over 5 or more slices. `takeItems` in `src/features/export/core/export-items.ts` reads each Item with the Reader's read plus its stored files, its Topic and its Kept comments (`readPlanSource`, `src/features/item/core/plan-source.ts`, over `readDetail` in `src/features/item/core/item-detail.ts`) in one batch that also lists its stored files, so the note and the image list come from the same rows. `itemFilePlan` (`src/features/item/core/item-files.ts`) turns that read into the note's input, the post text file and the stored files, and the Vault mirror plans an Item's files with it too. A stored image whose size differs from the recorded one counts as missing.
- **Note format.** `itemNote` and `noteFileName` in `src/features/item/core/item-note.ts` are pure functions of an Item's values, so the Vault mirror can call them. The entry name `note-<slug>.md` cannot collide with a stored name, which starts with `post-` or `img-`. Every front matter string is written by `JSON.stringify` and the front matter has no `title` key, so a hostile title or author cannot add a key. The title, Summary, Key points, Highlight quotes, Note and comment authors are plain text in the Reader, so the note escapes their Markdown characters, while the post text and comment bodies stay as stored. The comments are Kept comments only, as the Glossary says. A comment that the Reader shows only because an attached Highlight holds it is not in the note, but its Highlight is. A Kept comment's ancestors that are not Kept appear as Context stubs so the nesting reads correctly. The Reader's own headings, stub lines and `handleOf` come from `src/core/contract/reader-text.ts`. An image link in the post text that names one of the Item's own files becomes the bare file name, so the folder works wherever it is copied. The slug is cut at 80 code points and at 240 bytes, which keeps the file name under the 255-byte limit of common file systems.
- **Items that change during the export.** An Item deleted before its slice reads it is left out. A missing post text file or image makes the slice read the Item again once, because a refresh in between gives the Item new keys, and a second miss throws `ExportFileMissing`, so the attempt fails and retries. An Item refreshed between two slices of its own entries can leave entries of the old and the new version in the zip.
- **Not a snapshot.** The slices read the live database over minutes, so a row written between two slices can appear in one table's file and not in a related one. The manifest's `openItems` counts the Items that had an open job when their page was read, because a restore may see their text and Digest from different moments. An Item deleted after its page was read stays in the zip.
- **One at a time, kept 24 hours.** The partial unique index `exports_one_live` allows one `running` or `ready` row, so a second start while one runs answers 409. A start while one is `ready` marks the old row `failed` with `replaced` and removes its objects. The sweep stage `exports` removes a `removing` export, a `failed` export 12 minutes after its last update, and a `ready` one 24 hours after `finished_at` (`EXPORT_KEEP_MS`). The 12 minutes are the 10-minute slice deadline plus the 2-minute claim margin (`EXPORT_SLICE_DEADLINE_MS`, `CLAIM_MARGIN_MS`), so the claim of a slice that was still running has expired and its guarded commit fails. The wait does not stop that slice. `DELETE /api/export` removes a ready or failed export at once. It stops a running export (`failed`, `cancelled`) and leaves its objects to the sweep, because a slice that is already running fails its guarded commit and deletes what it wrote. A runner is never cancelled, so a slice that a host suspend, `podman pause` or a stalled disk held for longer than that can still write its objects after the export is `expired`; if the process then stops before the runner deletes them, the objects stay under the `expired` row. The same sweep stage therefore lists `exports/` on every run and deletes each object whose export row is `expired` (`cleanExports` in `src/features/export/core/export-cleanup.ts` through `deleteMatching` in `src/core/kernel/file-pages.ts`, logged as `export-stray-objects-removed`), so such an object lives until the next sweep that runs the stage `exports`; only the stages in `WHILE_RESTORING` run while a restore holds the library (`restoreHoldsLibrary` in `src/core/kernel/restore-hold.ts`; While it runs). It leaves the objects of a `running`, `ready`, `failed` or `removing` export to the removal above, and the objects of an export with no row (after restoring an older database copy), which nothing removes.
- **Limit of the download on the Worker.** The download reads 2 objects per slice and the tail, and each read is a subrequest of the one invocation that streams the zip. The same invocation also makes up to 3 other calls (the session check, a session renewal, the `exports` row), counted as subrequests here although the Workers docs may not count D1 calls (unverified). The Cloudflare target needs Workers Paid (`cloudflare-deploy-button.md`), which allows 10,000 subrequests (Workers docs, Limits), so 2 x slices + 1 + 3 <= 10,000 gives at most 4,998 slices. A library needs at least its Items divided by 40 slices. The 4,000-Item library the spec plans needs between 100 slices (204 subrequests) and about 4,010 slices (8,024 subrequests, with 10 record slices as a guess) when every Item has files of 4 to 8 MiB. A library of 4,000 Items with 20 images of 2 MiB each would need 20,000 slices or more and would not fit. The Cloudflare target does not support the Free plan. The container has no such limit. The slice counts are arithmetic. The largest download run on a Worker is 6.1 MB in 4 slices (Measured runs).
- **Item cost.** Each Item costs 11 D1 statements (the Reader's 10 and the list of stored files), so a slice of 40 Items runs near 440 against the 1,000 queries of one invocation (arithmetic; the 40-Item slice of the demo export ran under 758 D1 queries, the D1 total of its minute, see Measured runs).
- **Not built.** The plan's deletion hold, which would delay a file deletion while an export runs, is replaced by the re-read of a missing file above, because the hold would touch the finish, the cleanup and the delete paths.

## Restore

Restore is the upload of an export zip into an Instance whose library is empty, and a chain of jobs of the kind `restore` that writes every record with its id. Built: the records, the stored images and post text files, the search parts, the anchors of the Highlights, cancel, resume, the cleanup of parts and the setup page step. Only the owner's session may call its routes (`src/features/restore/http/restore-routes.ts`; an agent token gets 403).

- **Upload.** `POST /api/restore` answers 409 unless the library holds no Item, Topic, Tag, Log entry, Proposal, Pin or Import cursor (`library-not-empty`), or when a restore is already open (`restore-open`, the partial unique index `restores_one_open`): one that waits for its upload, one that runs, and one that `failed` with `gave-up` and so still holds the library, which the owner resumes or cancels first. `createRestore` checks the library first, so a run that already wrote records, which is the usual case for a `gave-up` run, gives `library-not-empty`, and `restore-open` is the answer only while the library is still empty, such as a `gave-up` in the phase `check`. A restore that a refusal of the check ended does not block an upload. The Restore screen offers no file picker while a `gave-up` run holds the library. The client cuts the zip into parts of 32 MiB (`RESTORE_PART_BYTES`). A part upload can be repeated while the restore is `uploading`. After the write, `storePart` bumps `updated_at` of an `uploading` row, which keeps a slow upload from looking abandoned. When the row has left `uploading`, it deletes the part it just wrote only when the restore no longer holds its parts, which means `done`, `cancelled` or a failure that is not resumable, and answers `409 not-uploading` (the part route answers 204 for a late part of a `running` restore). While the restore is `running`, or `failed` with `gave-up` outside the `undoing` phase, a late part stays, because Start required every part, so the key existed before and the restore needs it (a retry of a stalled part can land after Start). The 50 GB limit is `RESTORE_MAX_BYTES`. `GET /api/restore` lists the parts that arrived, so a reloaded page sends only the missing ones.
- **Start and check.** `POST /api/restore/<id>/start` flips the row to `running` and opens the first job in one guarded batch. A restore that is past its upload (`running`, `failed`, `cancelled` or `done`) gives `409 not-uploading`, also when a Cancel ends it between the reads of the start, because the start reads the row again before it answers `library-not-empty` or `incomplete-upload`; `restore-open` belongs to `POST /api/restore` alone. A live Vault mirror lease gives `409 vault-busy`. The uploaded parts stay ready for retry. The upload comes before the job chain, which has the phases `check`, `tables`, `files`, `search`, `highlights` and `finish` (`RESTORE_PHASES` also lists `upload`), and `undoing` while a Cancel runs. The check is a separate phase so that its time per request is bounded and the Worker never reads a whole zip in one request. Each check job (`src/features/restore/core/restore-check-unit.ts`, `src/features/restore/core/restore-check-scan.ts`) reads one region of about 8.25 MiB (`RESTORE_CHECK_BYTES`) and moves a cursor that commits with the next job. A refusal ends the restore `failed` with one code from `RESTORE_REFUSALS` in one guarded write, and the job closing then deletes the parts; it writes nothing to the library. A local header whose extra field puts the data of its entry past the start of the central directory is refused with `not-a-zip` by `spanIn` (`src/features/export/core/zip-read.ts`), as `entrySpan` refuses it, so a check job never stops on an entry without moving its cursor. The zip reader (`src/features/export/core/zip-read.ts`, `src/features/export/core/zip-directory.ts`) imports nothing from Restore: it throws `ZipRefused` with its own fault, and `restoreRefusalOf` (`src/features/restore/core/restore-refusal.ts`) maps each fault to a code, while `readRestoreDirectory` (`src/features/restore/core/restore-source.ts`) passes in the size cap of the directory (`RESTORE_DIRECTORY_BYTES`). The check and the slices read the zip through `partSource` (`src/features/restore/core/restore-source.ts`), which streams the parts in order, so a read holds one region and never a whole part.
- **Schema version.** Restore accepts only an Export of the running migration, because older Export zips are not supported. The manifest's `format` names the zip layout (`EXPORT_FORMAT`, `src/features/export/core/export-format.ts`) and stays 1 while that layout holds. A migration that changes the columns of a record, such as the `source` column of `reddit_threads` and `reddit_comments`, changes `migration` instead, so Restore refuses an older zip with `other-release` before it reads a record. `src/features/restore/core/restore-check-unit.ts` checks the manifest before any library record is written, and `phaseUnit` (`src/features/restore/core/restore-phase.ts`) compares the manifest's `migration` with the running one again before every unit of the `tables`, `files` and `finish` phases (`refusedRelease`). A restore that a deploy or a restart moved to a newer migration between two units therefore ends `failed` with `other-release` before that unit writes, and not `done` with the rows of the changed tables counted as dropped. The rows written before that stay until the owner cancels the restore. Each record must carry exactly the exported columns of its table. Defaults for columns deliberately left out of backups remain in `src/features/restore/core/restore-registry.ts`, which fails to build when a left-out column has no default.
- **Values.** A duplicate member name in a line is read the way `JSON.parse` reads it (the last one) at the check and at the write, because the write binds the re-serialized row. A row larger than the 2,000,000 bytes a bound string may hold on D1 (`RESTORE_BIND_BYTES`, 1.9 MB) is inserted alone, with each column bound separately. A row that repeats a key of an earlier row is left out and counted in `restores.dropped`, like a row whose parent is missing, because the check keeps no per-key state (a staging table would hold every key of a library of millions of rows). A row that a CHECK or trigger refuses fails the slice. `reddit_settings` is emptied by the finishing slice when the zip lacks it. `catalog_version` and `log_start` take the rows the zip holds; a Cancel keeps them so the seeded catalog counter remains present and the Log keeps its start date.
- **Slices.** Each job reads the next window of one record file (at most 500 lines or 1.5 MB, `RESTORE_UNIT_LINES`, `RESTORE_UNIT_BYTES`) in foreign key order (`RESTORE_ORDER`, derived from the Drizzle schema). The window, the new cursor and the counts commit in one guarded batch that also opens the next job, so a slice that dies is read again from the saved cursor and a repeated slice writes nothing twice (`src/features/restore/core/restore-job.ts`). The last slice (`src/features/restore/core/restore-finish.ts`) sets each `AUTOINCREMENT` counter of `sqlite_sequence` to the exported high-water mark, so a new Item continues after the highest restored id even when the exported Items with the top ids were deleted.
- **Files.** The `files` phase walks the file names that rows hold, not the zip: `NAMED_FILES` (`src/features/restore/core/named-files.ts`, the one definition that `cleanFiles` also uses) lists each `media.file_key` and `items.post_text_key` with its Item, and a job reads up to the next 1,000 of them by `(Item id, key)` (`RESTORE_FILE_ENTRIES`, cursor `{ owner, key }`) and restores those that fit one `RESTORE_FILE_BYTES` window (`windowOf`, `src/features/restore/core/restore-files.ts`). It looks each name up in the zip's directory. A name that the zip lacks, a name outside its Item's folder, an image above 2 MiB (`IMAGE_MAX_BYTES`) and a post text file above 8 MiB (`ITEM_REQUEST_BYTES`), the sizes the app stores, are counted as missing and not read, so no unit buffers an entry larger than the app itself writes. The entries found go to the file store through `entriesBytes` (`src/features/export/core/zip-read.ts`), which reads the span of one window with one read (`extentWith` sizes it: at most 8 MiB, `RESTORE_FILE_BYTES`, plus one entry), plus one read of the header and one of the data for an entry whose local header is longer than `LOCAL_HEADER_ROOM`, and checks each CRC-32 and each local header's name against the directory, because a read per file would stream half a part for each one. `readDirectory` refuses a zip that holds one name twice. A put of the same key and bytes can repeat, so a window read again writes the same objects. `restored.files` counts the objects put and `dropped["missing-files"]` the names that no object answered; the status route shows them as `files` and `missingFiles`, so a table named `files` cannot collide with them. A row whose file is missing stays. For an image, the Reader links the image's original web address (`media.source_url`, sent as `sourceUrl` in `images`) in place of the picture; for a post text file, the Item shows no text (`textLost`). The screen names the missing files in their own line, and leaves both counts out of the record totals.
- **Job ids in keys.** A key holds the id of the job that stored it (`items/<id>/post-<job>-<attempt>.md`), and the `jobs` table is not exported, so a new Instance numbers its jobs from 1. The finishing slice moves the `jobs` counter above the highest job id found in the restored names, so a later fetch on this Instance cannot write a key a restored Item names and then delete the restored object as superseded.
- **Search.** The `search` phase rebuilds `search_parts` through `restoredPartWrites` in `src/features/restore/core/restore-search.ts`, which calls `rebuiltPartWrites` in `src/features/item/core/search-parts.ts` for every kind of part, so restored Items are searchable when Restore ends. `RESTORE_INDEX_ITEMS` bounds the commit guard below D1's 100 bound parameters per statement, and `RESTORE_INDEX_BYTES` bounds the post text and Kept comments read in one job. D1's [2,000,000-byte string limit](https://developers.cloudflare.com/d1/platform/limits/) still applies to each bound string. `keptBodies` reads separate comment bodies, and `commentPartWrites` chunks them and groups the parts with `jsonArrays` (`src/features/thread/core/thread-rows.ts`). A Restore whose Kept comments total more than 2,000,000 bytes remains unverified on real D1. File-backed post text is read through `postTextOf`. Each job commits only while every Item still matches its read snapshot (`snapshotHolds`) and the cursor has not moved; otherwise it reads the unit again.
- **Highlights.** The `highlights` phase anchors again the Highlights of each Item that has any, up to 8 Items per job (`RESTORE_INDEX_ITEMS`) and fewer once 4 MiB of text has been read, through `anchoredOutcome` (`src/features/item/core/highlight-publish.ts`), the code a refresh and a Digest publication run, so the status and `start` come from the restored text and not from the exported columns (`src/features/restore/core/restore-highlights.ts`). A post Highlight is anchored in the Item's post text, read only for an Item that has a post Highlight. A comment Highlight is anchored in the body of its comment in the thread the Reader shows, with the readability rule of the Reader (`commentReadable`); an Item with no stored thread has no comment text, so its comment Highlights become no longer found, as after a refresh. The projection of a text (`projectText`) held about 500 MB of heap per MiB in a node run and aborted under a 128 MB heap at 600 KiB (the Worker's limit), so a text above 256 KiB (`RESTORE_ANCHOR_BYTES`), a post text file the zip lacked and a comment above that size keep the exported status of their Highlights, counted in `dropped["highlights-as-exported"]` (`keptHighlights` in the status). An attached post Highlight always has a place, because its revision is the Item's generation, so these Highlights stay readable. Each job commits only while the Highlights of its Items are the ones it read (`anchorsHold`) and the cursor has not moved.
- **No work in flight.** A restored Instance starts with no jobs. A Proposal in state `accepting` is restored as `open` with its counters reset, so the owner can Accept it again and the Items it already moved are safe to move again. An Item that had an open fetch or Digest job when the export read it has no job after the restore, so nothing resumes its work.
- **While it runs.** `POST /api/items` and `POST /api/items/batch` answer 503 with `code: "restoring"`, because a new Item would take an id the zip holds. The refusal does not rely on a check that a write can outrun. The trigger `items_restoring` in `migrations/0000_schema.sql` aborts every insert into `items` while the newest `restores` row is `running`, or is `failed` with `gave-up`, and its `writing` flag is 0, and a slice sets `writing` to 1 as the first statement of its own batch and back to 0 as its last. `sweep` runs only the `enqueue` and `restores` stages while the newest restore is `running` or `failed` with `gave-up` (`restoreHoldsLibrary` in `src/core/kernel/restore-hold.ts`, the one predicate that Paste, the batch, the sweep and the file cleanup use), so no other stage writes a half-restored library, and the stages wait and run after the owner resumes or cancels it. A restore that failed with `gave-up` therefore keeps the library closed to Paste the way a running one does, and a restore that a refusal of the check ended does not. The batch saves its Import cursor in one statement guarded by the same predicate (`saveImport`, `src/features/paste/core/import-cursor.ts`), because the trigger covers only `items`: a batch whose links were all refused hosts adds no Item, so a Restore can start while it runs, and an unguarded cursor write would land in the restored library, where nothing in the zip accounts for it. The batch then answers 503 `restoring` and keeps the old cursor. A restore that a deploy or a crash interrupts resumes on the container at the next start and on the Worker when the sweep takes over the expired claim. A slice that fails 3 times marks the restore `failed` with `gave-up` and leaves the rows written so far, and the owner then resumes or cancels it (next bullet). A new restore needs an empty library, so it can start only after that.
- **Sequences on D1.** The finishing slice writes `sqlite_sequence` with ordinary `UPDATE` and `INSERT` statements, as the SQLite documentation allows. This was probed on the container and on local D1 (`wrangler dev --local`), and it ran on real D1: after a restore of a zip whose `sequences.items` is 178 and whose highest Item id is 143, `sqlite_sequence` held 178 for `items` and the next Paste got id 179 (Measured runs).
- **Cancel and resume.** `DELETE /api/restore/<id>` cancels. An `uploading` restore becomes `cancelled` at once and loses its parts. A `running` or `failed` restore whose `restores.restored` is still `{}` and that is not `undoing` has written no library record, because every written record row is tallied there in the batch that writes it. That is the phase `check`, which covers a refusal of the check (it frees the library, so the owner may save Items before the Cancel) and a `gave-up` in the check (an empty library), and the phase `tables` until its first slice commits. Cancel moves such a restore to `cancelled` in one guarded batch that tests `restored` in the same statement as the update, closes its open `restore` jobs, then deletes its parts, and leaves the library alone. A slice that commits first makes the test fail, so the Cancel takes the undo below; a slice that finishes later finds the row `cancelled` and writes nothing, because its commit is guarded by the state, the phase and the cursor. The undo step itself deletes nothing and settles the row as `cancelled` when `restores.restored` is `{}` (`wroteNothing`, `src/core/kernel/restore-hold.ts`), so an undo job that an earlier release queued for such a restore cannot empty a library that holds Items saved since. The route answers 204, as it does for an upload, because nothing is left to undo, and `GET /api/restore` shows `cancelled` at once; only a cancel that starts an undo answers 202. A cancel of a `done` restore answers 409 `finished`, and a resume that is not allowed answers 409 `not-resumable`. Cancel and Resume act only on the newest restore, and an older id answers 409 `superseded`, so a page that still shows an older failed restore cannot erase a newer library. An older run that is already `cancelled` answers 204 to a Cancel and changes nothing but the deletion of its parts, as every cancelled run does; migration `0010_restores_hold_library.sql` moved each older `gave-up` run to that state, so Cancel of such an id answers 204 where it answered 409 before. Any other `running` or `failed` restore past `check` moves, in one guarded batch, to state `running` with phase `undoing` (`cancelRestore` in `src/features/restore/core/restore-cancel.ts`; `GET /api/restore` shows it as `cancelling`). The same batch closes the open `restore` jobs of that restore and opens a new one, so the unit in flight finds its cursor changed and writes nothing, and the third failure of an older job cannot end the undo. Each undo unit (`src/features/restore/core/restore-undo.ts`) deletes up to 500 rows of the first table that still has rows, starting with the tables that `items` is rebuilt into, which is `search_parts` (their foreign keys point at `highlights` and `topics` without a cascade, so rows that a sweep wrote before the failure would make the delete of those tables fail) and then the restored tables in the reverse of `RESTORE_ORDER`, one query per table because D1 refuses a compound `SELECT` of more than a few terms; a unit looks again at every table, so a row that appears in an earlier table is still found; then it deletes every object under `items/`, up to 1,000 a unit, before it commits; the last unit sets `cancelled` and supersedes the parts. It skips `log_start` and `catalog_version`, resets no sequence, and empties `reddit_settings` only when `restores.restored` shows that the run wrote it. `POST /api/restore/<id>/resume` accepts a restore `failed` with `gave-up` whose phase is not `undoing` and whose parts are all stored (`resumable` in `GET /api/restore`): it moves the row to `running` and opens a job, which continues from the cursor of the last committed unit. A refusal of the check keeps no part and cannot be resumed. A `gave-up` failure keeps its parts for Resume, and the sweep deletes them 24 hours after the failure, like an abandoned upload, after which Resume answers 400 `incomplete-upload` and the owner cancels. A failed cancel (`gave-up` in `undoing`) shows `cancelFailed` and is cancelled again, not resumed. What the `files`, `search` and `highlights` phases wrote needs no undo step of its own: `search_parts` go first with the other dependents, the Highlights go with the restored tables, and the file listing of `items/` removes every stored image and post text file. A `files` unit that was in flight when the cancel started can put an object after the last listing, and `cleanFiles` removes it because no row names it. Resume continues from the phase cursor: `{ owner, key }` in `files` (a put of the same key and bytes can repeat) and `{ after }` in `search` and `highlights` (the next job reads its Items again).
- **Cleanup of parts.** The sweep stage `restores` (`cleanRestoreParts`, `src/features/restore/core/restore-parts.ts`), after `exports`, first sets an `uploading` restore to `cancelled` when its `updated_at` is older than 24 hours (`RESTORE_PARTS_KEEP_MS`), and then deletes every object under `restores/` whose restore is not `uploading`, `running`, or the newest restore with `failed` and `gave-up` outside the `undoing` phase whose `updated_at` is less than 24 hours old. The stage also runs while a restore holds the library, because that is when a failed restore's parts age out.
- **Not restored.** Provider keys, the password, sessions and agent tokens are not in the zip, so the owner enters them again, and the screen says so.
