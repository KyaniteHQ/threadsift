# Export, backup and restore

- The export zip holds a Markdown note for each Item with its stored images and post text file beside it, every library record as JSON Lines files under `records/`, and the manifest `threadsift.json`. The manifest lists those files with their row counts and holds the format, the export time, the highest applied migration, the version of each data step, the `sqlite_sequence` value of each `AUTOINCREMENT` table, and the number of Items that had an open job of a kind in `ITEM_JOB_KINDS` (`src/core/kinds.ts`) when the export read them. Every entry sits under one folder named `threadsift-<UTC date>/`. The manifest holds no records, because a CRC-32 needs a whole entry and one file of every record cannot be written in slices.
- `src/core/backup-tables.ts` names the tables and columns the records hold and gives a reason for each table they leave out. Secrets, the owner's password hash, sessions, agent token hashes and the working tables are left out, because a restored Instance gets a new password and new tokens and starts with no work in flight. The `ai_tasks` rows that Digests name stay, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. The records hold every stored comment, Kept or not, and the Item notes hold Kept comments only.
- Every record keeps its id. The restore inserts the ids unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Why the app writes its own backup.** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data). D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/backup-tables.ts` names every included table with the columns a backup exports and the columns it leaves out, and `EXCLUDED_TABLES` names every other table with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`. `test/backup-tables.test.ts` fails when a table is in neither list or in both, or when a column of an included table is in neither set, so a migration that adds a table or a column must decide where it belongs. Neither list's key order is an insert order, because the restore derives the parent order from the foreign keys of the migrated database.

## Export

An export is a chain of jobs of the kind `export`. `POST /api/export` inserts the `exports` row and the first job in one batch. Each slice reads the next rows, closes whole zip entries, writes them as objects of the file store, and returns one checkpoint that the runner commits in the same guarded batch that closes the job and opens the next one (`src/core/export-job.ts`). A stopped container, a lost queue message or a dead Worker therefore continues from the last committed slice. On the container the start expires the claim of every `running` job (`abandonRunning`, `src/core/jobs.ts`), and on Cloudflare the sweep takes over a claim that expired. A job that fails 3 attempts ends the export `failed` with `gave-up`. A slice that finds that the table list differs from the one the export started with ends it `failed` with `list-changed`, because resuming would skip or repeat a table without any error. A deploy that changes a table or an exported column in `BACKUP_TABLES` while the export runs causes this.

- **Layout in the file store.** Slice `n` of attempt `g` writes `exports/<id>/part-<n>-<g>`, `exports/<id>/dir-<n>-<g>` and, on the last slice, `exports/<id>/tail-<g>`. Attempt number `g` is in the name so that a runner that lost its claim and writes late writes other names than the runner that committed the slice. It cannot overwrite committed bytes, its guarded commit fails, and it deletes what it wrote. The objects are separate because R2 multipart needs equal parts of at least 5 MiB and the container has no multipart. The download streams every `part`, then every `dir`, then the `tail`, as one store-mode zip with ZIP64 records when needed (`src/core/zip.ts`).
- **Records.** The slices read `topics` and `tags` first, then the other tables in `BACKUP_TABLES` order. A table is read in pages of at most 2,000 rows in `rowid` order, and a page also stops when its rows reach the room left in the slice, so a page of long comments stays inside the budget. A slice ends at 8 MiB of rows (`EXPORT_SLICE_BYTES`, `EXPORT_PAGE_ROWS` in `src/core/export-contract.ts`; the figures behind them are in Open items and unverified claims). A record file closes at 8 MiB (`EXPORT_ENTRY_BYTES`, chosen, unsupported), so every entry is complete inside one slice and its CRC-32 is known before the next slice starts. A table with no rows gets one empty file, so every included table has a file.
- **Item notes, images and post text.** After the last table the slices read the Items by id, at most 40 Items per slice (`EXPORT_SLICE_ITEMS`, chosen, unsupported) and at most 8 MiB of entries, except that a slice's first entry is taken whatever its size. When the next entry does not fit, the slice ends inside the Item and the checkpoint records how many of its entries are written, so an Item of 20 images of 2 MiB spreads over 5 or more slices. `takeItems` in `src/core/export-items.ts` reads each Item with the Reader's read (`readItem`, `src/core/item-detail.ts`) in one batch that also lists its stored files, so the note and the image list come from the same rows. A stored image whose size differs from the recorded one counts as missing.
- **Note format.** `itemNote` and `noteFileName` in `src/core/item-note.ts` are pure functions of an Item's values, so the Vault mirror can call them. The entry name `note-<slug>.md` cannot collide with a stored name, which starts with `post-` or `img-`. Every front matter string is written by `JSON.stringify` and the front matter has no `title` key, so a hostile title or author cannot add a key. The title, Summary, Key points, Highlight quotes, Note and comment authors are plain text in the Reader, so the note escapes their Markdown characters, while the post text and comment bodies stay as stored. The comments are Kept comments only, as the Glossary says. A comment that the Reader shows only because an attached Highlight holds it is not in the note, but its Highlight is. A Kept comment's ancestors that are not Kept appear as Context stubs so the nesting reads correctly. The Reader's own headings, stub lines and `handleOf` come from `src/core/reader-text.ts`. An image link in the post text that names one of the Item's own files becomes the bare file name, so the folder works wherever it is copied. The slug is cut at 80 code points and at 240 bytes, which keeps the file name under the 255-byte limit of common file systems.
- **Items that change during the export.** An Item deleted before its slice reads it is left out. A missing post text file or image makes the slice read the Item again once, because a refresh in between gives the Item new keys, and a second miss throws `ExportFileMissing`, so the attempt fails and retries. An Item refreshed between two slices of its own entries can leave entries of the old and the new version in the zip.
- **Not a snapshot.** The slices read the live database over minutes, so a row written between two slices can appear in one table's file and not in a related one. The manifest's `openItems` counts the Items that had an open job when their page was read, because a restore may see their text and Digest from different moments. An Item deleted after its page was read stays in the zip.
- **One at a time, kept 24 hours.** The partial unique index `exports_one_live` allows one `running` or `ready` row, so a second start while one runs answers 409. A start while one is `ready` marks the old row `failed` with `replaced` and removes its objects. The sweep stage `exports` removes a `removing` export, a `failed` export 12 minutes after its last update, and a `ready` one 24 hours after `finished_at` (`EXPORT_KEEP_MS`). The 12 minutes are the 10-minute slice deadline plus the 2-minute claim margin (`EXPORT_SLICE_DEADLINE_MS`, `CLAIM_MARGIN_MS`), so the claim of a slice that was still running has expired and its guarded commit fails. The wait does not stop that slice. `DELETE /api/export` removes a ready or failed export at once. It stops a running export (`failed`, `cancelled`) and leaves its objects to the sweep, because a slice that is already running fails its guarded commit and deletes what it wrote. A runner is never cancelled, so a slice that a host suspend, `podman pause` or a stalled disk held for longer than that can still write its objects after the export is `expired`; if the process then stops before the runner deletes them, the objects stay under the `expired` row. The same sweep stage therefore lists `exports/` on every run and deletes each object whose export row is `expired` (`removeStrays` in `src/core/export-cleanup.ts`, logged as `export-stray-objects-removed`), so such an object lives until the next sweep that runs the stage `exports`; only the stage `enqueue` runs while a Restore runs. It leaves the objects of a `running`, `ready`, `failed` or `removing` export to the removal above, and the objects of an export with no row (after a database rollback), which nothing removes.
- **Limit of the download on the Worker.** The download reads 2 objects per slice and the tail, and each read is a subrequest of the one invocation that streams the zip. The same invocation also makes up to 3 other calls (the session check, a session renewal, the `exports` row), counted as subrequests here although the Workers docs may not count D1 calls (unverified). The Cloudflare target needs Workers Paid (`cloudflare-deploy-button.md`), which allows 10,000 subrequests (Workers docs, Limits), so 2 x slices + 1 + 3 <= 10,000 gives at most 4,998 slices. A library needs at least its Items divided by 40 slices. The 4,000-Item library the spec plans needs between 100 slices (204 subrequests) and about 4,010 slices (8,024 subrequests, with 10 record slices as a guess) when every Item has files of 4 to 8 MiB. A library of 4,000 Items with 20 images of 2 MiB each would need 20,000 slices or more and would not fit. The Free plan's 50 subrequests allow 23 slices, and the Cloudflare target does not support that plan. The container has no such limit. All of this is arithmetic and not a run on a deployed Worker.
- **Item cost.** Each Item costs 11 D1 statements (the Reader's 10 and the list of stored files), so a slice of 40 Items runs near 440 against the 1,000 queries of one invocation (arithmetic, not run on a deployed Worker).
- **Not built.** The plan's deletion hold, which would delay a file deletion while an export runs, is replaced by the re-read of a missing file above, because the hold would touch the finish, the cleanup and the delete paths.

## Restore

Restore is the upload of an export zip into an Instance whose library is empty, and a chain of jobs of the kind `restore` that writes every record with its id. Built: the records. Not built: stored images, the search rebuild, the Highlight checks, cancel, resume, the cleanup of abandoned parts and the setup page step. Only the owner's session may call its routes (`src/http/restore-routes.ts`; an agent token gets 403).

- **Upload.** `POST /api/restore` answers 409 unless the library holds no Item, Topic, Tag, Log entry, Proposal, Pin or Import cursor (`library-not-empty`), or when a restore is already open (`restore-open`, the partial unique index `restores_one_open`). The client cuts the zip into parts of 32 MiB (`RESTORE_PART_BYTES`). A part upload can be repeated while the restore is `uploading`, and after the write the route reads the row again and deletes the part it just wrote when the row has left `uploading`, so a late part never replaces bytes the check has read. The 50 GB limit is `RESTORE_MAX_BYTES`. `GET /api/restore` lists the parts that arrived, so a reloaded page sends only the missing ones.
- **Start and check.** `POST /api/restore/<id>/start` flips the row to `running` and opens the first job in one guarded batch. The job chain has the phases `upload`, `check`, `tables` and `finish` (`RESTORE_PHASES`). The check is a separate phase so that its time per request is bounded and the Worker never reads a whole zip in one request. Each check job (`src/core/restore-check-unit.ts`, `src/core/restore-check-scan.ts`) reads one region of about 8.25 MiB (`RESTORE_CHECK_BYTES`) and moves a cursor that commits with the next job. A refusal ends the restore `failed` with one code from `RESTORE_REFUSALS` in the same guarded write that deletes the parts, and writes nothing to the library. The check and the slices read the zip through `partSource` (`src/core/restore-source.ts`), which streams the parts in order, so a read holds one region and never a whole part.
- **Columns of older exports.** A zip whose manifest migration equals the running migration must carry exactly the exported columns of each table. A zip of an older migration may carry columns this release dropped, which the restore ignores, and may lack columns this release added, which take their default. The registry fails to build when a column that a backup leaves out has no default, so the gate catches that before a restore does.
- **Values.** A duplicate member name in a line is read the way `JSON.parse` reads it (the last one) at the check and at the write, because the write binds the re-serialized row. A row larger than the 2,000,000 bytes a bound string may hold on D1 (`RESTORE_BIND_BYTES`, 1.9 MB) is inserted alone, with each column bound separately. A row that repeats a key of an earlier row is left out and counted in `restores.dropped`, like a row whose parent is missing, because the check keeps no per-key state (a staging table would hold every key of a library of millions of rows). A row that a trigger refuses fails the slice. A singleton table that the zip lacks (`reddit_settings`, `catalog_version`) is emptied by the finishing slice, so a setting the target held before the restore does not survive it, and `log_start` keeps the target's row.
- **Slices.** Each job reads the next window of one record file (at most 500 lines or 1.5 MB, `RESTORE_UNIT_LINES`, `RESTORE_UNIT_BYTES`) in foreign key order (`RESTORE_ORDER`, derived from the Drizzle schema). The window, the new cursor and the counts commit in one guarded batch that also opens the next job, so a slice that dies is read again from the saved cursor and a repeated slice writes nothing twice (`src/core/restore-job.ts`). The last slice sets each `AUTOINCREMENT` counter of `sqlite_sequence` to the exported high-water mark, so a new Item continues after the highest restored id even when the exported Items with the top ids were deleted.
- **No work in flight.** A restored Instance starts with no jobs. A Proposal in state `accepting` is restored as `open` with its counters reset, so the owner can Accept it again and the Items it already moved are safe to move again. An Item that had an open fetch or Digest job when the export read it has no job after the restore, so nothing resumes its work. A `data_steps` row of a step in progress is restored as not started, the same rule as for a step whose exported version is older than the running release (Database and search, Data steps). `migrateData` returns at once while a restore runs, and the finishing slice writes each step's row with the version the manifest holds (0 for a step the manifest lacks) and no cursor.
- **While it runs.** `POST /api/items` and `POST /api/items/batch` answer 503 with `code: "restoring"`, because a new Item would take an id the zip holds. The refusal does not rely on a check that a write can outrun. The trigger `items_restoring` (migration `0063_restore.sql`) aborts every insert into `items` while a `restores` row is `running` and its `writing` flag is 0, and a slice sets `writing` to 1 as the first statement of its own batch and back to 0 as its last. The previous release has no such gate in its code, but it opens the migrated database, so its Paste fails on the trigger instead of taking an id. `sweep` runs only the `enqueue` stage while a restore is `running`, so no other stage writes a half-restored library, and the stages wait and run after it. A restore that a deploy or a crash interrupts resumes on the container at the next start and on the Worker when the sweep takes over the expired claim. A slice that fails 3 times marks the restore `failed` with `gave-up` and leaves the rows written so far, because cancel and resume are not built.
- **Sequences on D1.** The finishing slice writes `sqlite_sequence` with ordinary `UPDATE` and `INSERT` statements, as the SQLite documentation allows. This was probed on the container and on local D1 (`wrangler dev --local`). Whether real D1 accepts the same writes is not verified and stays with the deploy slice.
- **Not restored.** Provider keys, the password, sessions and agent tokens are not in the zip, so the owner enters them again, and the screen says so.
