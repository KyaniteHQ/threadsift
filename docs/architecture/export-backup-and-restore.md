# Export, backup and restore

- The export zip holds one Markdown file per Item with its images, as the spec describes, plus `threadsift.json` with every library record: Items, short-link aliases (`item_aliases`), comments, media (stored images and video URLs), Digests, Topics, Tags and their links to Items, Topic pages, Related Items (each pair with both Items it names, so the restore inserts the pairs after the Items; not built), Proposals (each row with its id, its kind and the two Tags, the two Topics or the Highlight it names, so the restore inserts the rows after the Tags, Topics and Highlights and keeps every reference; the `scheduled_runs` rows of the weekly checks are working tables and stay out; not built), the Log (`log_entries` with their ids and the `log_start` row, so the restore keeps every Item and Topic reference and the date the Log began; not built), Pins (each with its id, its kind and the Tag or Topic it targets, so the restore inserts them after the Tags and Topics; not built), Highlights, Notes, import cursors (`imports`), the server settings and the version of each data step (`data_steps`). It leaves out secrets (Provider keys, the Grok Bot webhook address and key in `grok_bot_settings`, the vault token), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `leases`, `topic_leases`, `mirror_paths`, and every `ai_tasks` row no Digest names), because a restored Instance gets a new password and new tokens and starts with no work in flight. It keeps the `ai_tasks` rows that Digests name, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. Every record keeps its id: the restore inserts the ids from `threadsift.json` unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. A fresh Instance can restore from it. The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** is a chain of jobs. Each slice streams the next Items into a store-mode zip (no compression, so little CPU) as R2 multipart parts of at least 5 MiB, or appends to a file in the container, and saves its checkpoint (the multipart upload id, the parts written, the zip's central-directory entries so far and the last Item id) in `exports` in the same batch as its progress; the next slice resumes from it, so an interrupted export continues instead of restarting. Each Item's records and files are read in the same slice, and while an export runs, file deletions from deleted or refreshed Items wait until it ends, so the zip never lists a file it does not hold. Nothing holds the whole library in memory.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`. When the export's version of a data step is lower than the running release's, or the export has none, the restore leaves that step's row out and the step runs after the last batch, so a library exported before a rule change gets the same rewrite as a live one (Database and search, Data steps). Planned and not built.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it is planned and not built. D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- A backup list names every table the backup includes; a test migrates a database and fails when a table is in neither that list nor its list of excluded tables.
