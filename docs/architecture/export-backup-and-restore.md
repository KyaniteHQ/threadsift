# Export, backup and restore

- The export zip holds one Markdown file per Item with its images, as the spec describes (not built: the Item notes and the images are later slices), every library record as JSON Lines files under `records/`, and `threadsift.json`, the manifest that lists those files with their row counts and holds the format, the export time, the highest applied migration, the version of each data step, the `sqlite_sequence` value of each `AUTOINCREMENT` table and the number of Items that had an open fetch or Digest job when the export read them (all built). Every entry sits under one folder named `threadsift-<UTC date>/`. The manifest holds no records, because a CRC-32 needs a whole entry and one file of every record cannot be written in slices. `src/core/backup-tables.ts` names the tables and columns the records hold, and gives a reason for each table they leave out. The records hold every stored comment, Kept or not (`reddit_comments` with its `eligible` and `kept` columns), and the Item notes hold Kept comments only. They leave out secrets (Provider keys and the other sealed values: `settings`, `github_settings`, `reddit_account`, the Grok Bot webhook address and key in `grok_bot_settings`, the vault token), the choices of a Provider or an X reader that may not exist on the target (`ai_settings_revision`, `x_settings`), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `topic_leases`, `data_step_lease`, `x_verifications`, and every `ai_tasks` row no Digest names), because a restored Instance gets a new password and new tokens and starts with no work in flight. It keeps the `ai_tasks` rows that Digests name, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. Every record keeps its id: the restore inserts the ids from the record files unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. A fresh Instance can restore from it (not built). The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** (built for the records and the manifest) is a chain of jobs of the kind `export`. `POST /api/export` inserts the `exports` row (`running`) and the first job in one batch; each slice reads the next rows, closes whole zip entries, writes them as objects of the file store, and returns one checkpoint that the runner commits in the same guarded batch that closes the job and opens the next one (`src/core/export-job.ts`). A slice that dies leaves its objects as orphans of an attempt that never committed, so the retry builds the same slice again and overwrites them; a slice whose checkpoint lost the guard deletes its objects. The checkpoint in `exports` holds the stream and cursor the next slice resumes from, the entry and byte counts, the number of parts and the row tally, so a stopped container, a lost queue message or a dead Worker continues from the last committed slice instead of restarting: the container's start puts `running` jobs back to `queued`, and on Cloudflare the sweep takes over a claim that expired. A job that fails 3 attempts ends the export `failed` with `gave-up`.
  - **Layout in the file store.** Slice `n` writes `exports/<id>/part-<n>` (the local headers and the data of its entries), `exports/<id>/dir-<n>` (their central-directory records) and, on the last slice, `exports/<id>/tail` (the ZIP64 end records). They are separate objects because R2 multipart needs equal parts of at least 5 MiB and the container has no multipart. The download streams every `part`, then every `dir`, then `tail`, and the result is one store-mode zip (method 0, UTF-8 names, ZIP64 records when there are 65,535 entries or more or an offset or size reaches 4 GiB; `src/core/zip.ts`). `Content-Length` is the sum of the stored sizes, so the object sizes in `exports` are the only state a download needs.
  - **Records.** The slices read the tables that are read whole first (`topics` and `tags` ahead of the rest, so parents come before their children), then the Items in id order in groups of 5 with every per-Item table of those Items, through `BACKUP_TABLES`. A slice ends at 40 Items, at 8 MiB of rows or at the end of the library (`EXPORT_SLICE_ITEMS`, `EXPORT_SLICE_BYTES`, `EXPORT_ITEM_GROUP` in `src/core/export-contract.ts`; the figures behind them are in Open items and unverified claims). A table's rows go to `records/<table>.<n>.jsonl`, one JSON object per line with `null` written out, and a file closes at 8 MiB (`EXPORT_ENTRY_BYTES`, chosen, unsupported) so every entry is complete inside one slice and its CRC-32 is known before the next slice starts. The manifest is the last entry.
  - **Not a snapshot.** The slices read the live database over minutes, so a row written between two slices can appear in one table's file and not in a related one. The manifest's `openItems` counts the Items that had a fetch or Digest job open when their slice read them, because a restore may see their text and Digest from different moments. An Item deleted after its slice stays in the zip.
  - **One at a time, kept 24 hours.** A partial unique index on `exports` (`exports_one_live`) allows one `running` or `ready` row, so a second start while one runs answers 409. A start while one is `ready` marks the old row `failed` with `replaced` and deletes its objects. The sweep stage `exports` deletes the objects of a `failed` export 12 minutes after its last update (`EXPORT_SETTLE_MS`, the 10-minute slice deadline plus the 2-minute claim margin, so a slice that was still running has ended) and of a `ready` one whose `finished_at` is 24 hours old (`EXPORT_KEEP_MS`), 5 exports a sweep, and marks the row `expired`; the download of such an id answers 404. `DELETE /api/export` removes a ready or failed export at once. It stops a running export (state `failed`, `cancelled`, its job closed) and leaves its objects to the sweep, because a slice already running would write its objects after an immediate delete and nothing would remove them; `GET /api/export` answers `none` for a cancelled export from the moment of the delete.
  - **Planned and not built.** The Item notes, the stored images, the re-read of a file that a deleted or refreshed Item removed between two slices, the deletion hold the plan names, and the Backup section of Settings.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`. When the export's version of a data step is lower than the running release's, or the export has none, the restore leaves that step's row out and the step runs after the last batch, so a library exported before a rule change gets the same rewrite as a live one (Database and search, Data steps). Planned and not built.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it holds the records and the manifest today (the Item notes and the images are not built). D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/backup-tables.ts` names every included table with its scope, the columns a backup exports and the columns it leaves out; `EXCLUDED_TABLES` in the same file names every other table, including the search tables, with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`: their values travel in `threadsift.json`, not as records. `test/backup-tables.test.ts` migrates a fresh database and fails when a table is in neither list or in both, or when a column of an included table, a generated column included, is in neither set. A later migration that adds a table or a column must therefore decide where it belongs. The key order of either list carries no meaning and is not an insert order: Export and Restore derive the parent order from the foreign keys of the migrated database. The export reads the list (`BACKUP_TABLES` decides which tables and columns each record file holds); the restore is not built.
