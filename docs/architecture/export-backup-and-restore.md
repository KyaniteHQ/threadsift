# Export, backup and restore

- The export zip holds one Markdown file per Item with its images, as the spec describes, plus every library record as JSON Lines files under `records/`, and `threadsift.json`, the manifest that lists those files with their row counts and holds the highest applied migration, the version of each data step and the `sqlite_sequence` value of each `AUTOINCREMENT` table (not built). `src/core/backup-tables.ts` names the tables and columns the records hold, and gives a reason for each table they leave out. The records hold every stored comment, Kept or not (`reddit_comments` with its `eligible` and `kept` columns), and the Item notes hold Kept comments only. They leave out secrets (Provider keys and the other sealed values: `settings`, `github_settings`, `reddit_account`, the Grok Bot webhook address and key in `grok_bot_settings`, the vault token), the choices of a Provider or an X reader that may not exist on the target (`ai_settings_revision`, `x_settings`), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `topic_leases`, `data_step_lease`, `x_verifications`, and every `ai_tasks` row no Digest names), because a restored Instance gets a new password and new tokens and starts with no work in flight. It keeps the `ai_tasks` rows that Digests name, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. Every record keeps its id: the restore inserts the ids from the record files unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. A fresh Instance can restore from it. The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** is a chain of jobs. Each slice streams the next Items into a store-mode zip (no compression, so little CPU) as R2 multipart parts of at least 5 MiB, or appends to a file in the container, and saves its checkpoint (the multipart upload id, the parts written, the zip's central-directory entries so far and the last Item id) in `exports` in the same batch as its progress; the next slice resumes from it, so an interrupted export continues instead of restarting. Each Item's records and files are read in the same slice, and while an export runs, file deletions from deleted or refreshed Items wait until it ends, so the zip never lists a file it does not hold. Nothing holds the whole library in memory.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`. When the export's version of a data step is lower than the running release's, or the export has none, the restore leaves that step's row out and the step runs after the last batch, so a library exported before a rule change gets the same rewrite as a live one (Database and search, Data steps). Planned and not built.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it is planned and not built. D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/backup-tables.ts` names every included table with its scope, the columns a backup exports and the columns it leaves out; `EXCLUDED_TABLES` in the same file names every other table, including the search tables, with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`: their values travel in `threadsift.json`, not as records. `test/backup-tables.test.ts` migrates a fresh database and fails when a table is in neither list or in both, or when a column of an included table, a generated column included, is in neither set. A later migration that adds a table or a column must therefore decide where it belongs. The key order of either list carries no meaning and is not an insert order: Export and Restore derive the parent order from the foreign keys of the migrated database. The export and the restore read the list; neither is built yet.
