# Export, backup and restore

- The export zip holds a Markdown note for each Item with its stored images and its post text file beside it, as the spec describes (all built), every library record as JSON Lines files under `records/`, and `threadsift.json`, the manifest that lists those files with their row counts and holds the format, the export time, the highest applied migration, the version of each data step, the `sqlite_sequence` value of each `AUTOINCREMENT` table whose records the export holds and the number of Items that had an open job of a kind in `ITEM_JOB_KINDS` (`src/core/kinds.ts`) when the export read them (all built). Every entry sits under one folder named `threadsift-<UTC date>/`. The manifest holds no records, because a CRC-32 needs a whole entry and one file of every record cannot be written in slices. `src/core/backup-tables.ts` names the tables and columns the records hold, and gives a reason for each table they leave out. The records hold every stored comment, Kept or not (`reddit_comments` with its `eligible` and `kept` columns), and the Item notes hold Kept comments only. They leave out secrets (Provider keys and the other sealed values: `settings`, `github_settings`, `reddit_account`, the Grok Bot webhook address and key in `grok_bot_settings`, the vault token), the choices of a Provider or an X reader that may not exist on the target (`ai_settings_revision`, `x_settings`), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `topic_leases`, `data_step_lease`, `x_verifications`, and every `ai_tasks` row no Digest names), because a restored Instance gets a new password and new tokens and starts with no work in flight. It keeps the `ai_tasks` rows that Digests name, because `digests.task_id` is NOT NULL and a task's inputs hold the comment ids the agent was shown. Every record keeps its id: the restore inserts the ids from the record files unchanged into the fresh Instance, so foreign keys, file keys (`items/<id>/…`, `src/core/file-keys.ts`) and `/items/<id>` addresses hold, and new rows continue after the highest restored id. A fresh Instance can restore every record from it (built; see Restore). The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** (built, with the Backup section of Settings) is a chain of jobs of the kind `export`. `POST /api/export` inserts the `exports` row (`running`) and the first job in one batch; each slice reads the next rows, closes whole zip entries, writes them as objects of the file store, and returns one checkpoint that the runner commits in the same guarded batch that closes the job and opens the next one (`src/core/export-job.ts`). The checkpoint in `exports` holds the stream the next slice resumes in (`stream`, a table name, or `item-files` after the last table) and the row id it resumes after (`cursor`, the Item id in `item-files`), the entry and byte counts, the number of parts and a JSON tally (the files and rows of each table, the count of open Items, the attempt number of each part, the list of tables and their columns the export started with, and the Item a slice stopped inside), so a stopped container, a lost queue message or a dead Worker continues from the last committed slice instead of restarting: the container's start expires the claim of every `running` job (`abandonRunning`, `src/core/jobs.ts`) so the next claim takes it again, and on Cloudflare the sweep takes over a claim that expired. A job that fails 3 attempts ends the export `failed` with `gave-up`. A slice that finds that the table list differs from the one the export started with (a deploy that added, removed or moved a table or an exported column in `BACKUP_TABLES` while the export ran), or a stored table name the list no longer has, ends the export `failed` with `list-changed`, because resuming would skip or repeat a table without any error.
  - **Layout in the file store.** Slice `n` of attempt `g` writes `exports/<id>/part-<n>-<g>` (the local headers and the data of its entries), `exports/<id>/dir-<n>-<g>` (their central-directory records) and, on the last slice, `exports/<id>/tail-<g>` (the ZIP64 end records). `g` is the attempt number of the claim that built the slice, and the checkpoint records it for each part. A runner that lost its claim and writes late therefore writes other names than the runner that committed the slice, and cannot overwrite committed bytes; its guarded commit fails and the runner deletes the objects it wrote. A retry after a graceful stop or after a kill takes the next number, because the next claim of a job still `running` adds 1 to `attempts`, so the earlier run's objects stay under the old number, unreferenced, until the export is removed. The objects are separate because R2 multipart needs equal parts of at least 5 MiB and the container has no multipart. The download streams every `part`, then every `dir`, then the `tail` the checkpoint names, and the result is one store-mode zip (method 0, UTF-8 names, ZIP64 records when there are 65,535 entries or more or an offset or size reaches 4 GiB; `src/core/zip.ts`). `Content-Length` is the sum of the stored sizes. A temporary file that a killed container left beside an object (`.tmp-<hex>-part-<n>-<g>`) is listed and deleted with the export's other objects. The download stops reading and closes the open object when the client disconnects, also in the gap between two objects.
  - **Records.** The slices read one table after another: `topics` and `tags` first, then the other tables in the order of `BACKUP_TABLES` (the order is not a parent order; a restore derives that from the foreign keys). A table is read in pages of at most 2,000 rows in `rowid` order, and a page also stops when the rows it holds reach the room left in the slice, counted in bytes by one SQL window over the column lengths, so a page of long comments or Topic pages stays inside the budget. A page always holds at least one row. A slice ends when it has 8 MiB of rows or the library ends (`EXPORT_SLICE_BYTES`, `EXPORT_PAGE_ROWS` in `src/core/export-contract.ts`; the figures behind them are in Open items and unverified claims). A table's rows go to `records/<table>.<n>.jsonl`, one JSON object per line with `null` written out, and a file closes at 8 MiB (`EXPORT_ENTRY_BYTES`, chosen, unsupported) so every entry is complete inside one slice and its CRC-32 is known before the next slice starts. A table with no rows gets one empty file, `records/<table>.1.jsonl`, so every included table has a file. The manifest is the last entry.
  - **Item notes, images and post text.** After the last table the slices read the Items by id (the stream `item-files`). A slice takes at most 40 Items (`EXPORT_SLICE_ITEMS`, chosen, unsupported) and at most 8 MiB (`EXPORT_SLICE_BYTES`) of entries, counted with the record rows already in it, except that its first entry is taken whatever its size. An Item's entries are its note, its post text file when it keeps its text in a file, and its stored images in `position` order. When the next entry does not fit, the slice ends inside the Item, and the checkpoint records the Item and the number of its entries already written (`partial` in the `exports` tally, next to `cursor`, which stays at the last whole Item), so an Item of 20 images of 2 MiB spreads over 5 or more slices and no slice holds more than the 8 MiB budget plus one entry. `takeItems` in `src/core/export-items.ts` reads each Item with `readItem` (`src/core/item-detail.ts`), the read the Reader uses, in one `db.batch` that also lists the Item's stored files with their sizes, so the note and the list of images come from the same rows. A stored image is read one at a time into a buffer of its recorded size, and one that is shorter or longer than that size counts as missing. The names of the entries under `items/<id>/` are `note-<slug>.md`, the post text file's stored name (`post-<job>-<attempt>.md`) and each image's file key (`img-<job>-<attempt>-<position>.<ext>`); `note-` cannot collide with a stored name, which starts with `post-` or `img-`. `itemNote` and `noteFileName` in `src/core/item-note.ts` are pure functions of the Item's values, written so the Vault mirror can call them. The front matter holds `id`, `source`, `url`, `author`, `community`, `posted`, `saved`, `fetched`, `topic`, `tags` and `read`, with every string written by `JSON.stringify` (and `\uXXXX` for the characters YAML refuses raw), a null written as an empty string, and no `title` key, so a hostile title or author cannot add a key. The body is the title as one line (whitespace runs become one space, `Untitled` when empty), then the Summary, Key points, Highlights (a quote that is no longer found is followed by the Reader's line that says so), Note, post text and comments, each section only when it has content. The title, Summary, Key points, Highlight quotes, Note and comment authors are text the Reader shows as plain text, so the note escapes their Markdown characters; the post text and the comment bodies stay as stored. The comments are Kept comments only, as the Glossary says: a comment the Reader shows only because an attached Highlight holds it is not in the note, but its Highlight is in the Highlights section. A comment's ancestors that are not Kept appear as Context stubs so the nesting reads correctly. Comments are blockquotes nested by depth, each led by the author's handle, and a Context stub is one italic line with the Reader's text. The headings, stub lines and `handleOf` are the Reader's own, in `src/core/reader-text.ts`, which `web/src/reader-text.ts` re-exports. An image link in the post text that names one of the Item's own files (`/api/files/items/<id>/<name>`) becomes the bare file name, so the folder works wherever it is copied; every other link stays as stored. The slug is the title lower-cased with each run of characters that are not letters or digits turned into `-`, trimmed, and cut at 80 code points and at 240 bytes (the byte cut keeps a file name under the 255-byte limit of common file systems), and `item` when it is empty. An Item deleted before its slice reads it is left out. A file that is missing when its Item is read, the post text file or an image, makes the slice read the Item's rows and files again once, because a refresh in between gives the Item new keys; a second miss throws `ExportFileMissing`, the attempt fails and the job retries as for any failed attempt. An Item refreshed between two slices of its own entries can leave entries of the old and the new version in the zip (see Not a snapshot). Each Item costs 11 D1 statements, the Reader's 10 and the list of stored files, which puts a slice of 40 Items near 440 against the 1,000 queries of one invocation (arithmetic, not run on a deployed Worker).
  - **Not a snapshot.** The slices read the live database over minutes, so a row written between two slices can appear in one table's file and not in a related one. The manifest's `openItems` counts the Items that had an open job of the kinds `jobs` holds for an Item (a fetch, a Digest or an X check) when their page was read, because a restore may see their text and Digest from different moments. An Item deleted after its page was read stays in the zip.
  - **One at a time, kept 24 hours.** A partial unique index on `exports` (`exports_one_live`) allows one `running` or `ready` row, so a second start while one runs answers 409. A start while one is `ready` marks the old row `failed` with `replaced` and removes its objects. Removing an export marks the row `removing`, deletes its objects page by page, and then marks it `expired`; the download of a `removing` or `expired` id answers 404 and the status reads `none`, and a failure in the middle leaves a `removing` row that the next sweep finishes. The sweep stage `exports` removes a `removing` export, a `failed` export 12 minutes after its last update (the 10-minute slice deadline plus the 2-minute claim margin, `EXPORT_SLICE_DEADLINE_MS` and `CLAIM_MARGIN_MS`, so the claim of a slice that was still running has expired and its guarded commit fails) and a `ready` one whose `finished_at` is 24 hours old (`EXPORT_KEEP_MS`), 5 exports a sweep. `DELETE /api/export` removes a ready or failed export at once. It stops a running export (state `failed`, `cancelled`, its job closed, and `none` in the status from then on) and leaves its objects to the sweep: a slice that is already running fails its guarded commit and deletes what it wrote, and the sweep removes the rest 12 minutes later. A `DELETE` that finds the export `ready` by the time it writes removes it as a ready one.
  - **Limit of the download on the Worker.** The download reads 2 objects per slice and the tail, and each read is a subrequest of the one invocation that streams the zip. The same invocation also checks the owner's session (1 D1 read, and 1 more when the session is renewed) and reads the `exports` row (1 D1 read), so up to 3 other calls, counted as subrequests here although the Workers docs may not count D1 calls (unverified). The Cloudflare target needs Workers Paid (`cloudflare-deploy-button.md`), and Paid allows 10,000 subrequests (Workers docs, Limits), so 2 x slices + 1 + 3 <= 10,000 gives at most 4,998 slices. A slice holds 8 MiB of record rows, or from 1 to 40 Items with their notes, images and post text files, and an Item whose files pass 8 MiB spreads over several slices. A library therefore needs at least its Items divided by 40 slices, and at most one slice for each Item plus the record slices (8 MiB of rows each) plus one slice for each 8 MiB of an Item's files beyond the first. Paid covers 199,920 Items when every slice holds 40, and a library of up to 4,900 Items whose files are under 8 MiB for each Item and whose records fill at most 98 slices (784 MiB). The 4,000-Item library the spec plans needs between 100 slices (204 subrequests) and about 4,010 slices (8,024 subrequests, with 10 record slices as a guess) when every Item has files of 4 to 8 MiB, which leaves about 1,976 spare; an Item with 20 images of 2 MiB takes 5 or more slices, so a library of 4,000 such Items would need 20,000 or more and not fit. The 50 subrequests of the Free plan allow 23 slices, so 920 Items at best; the Cloudflare target does not support that plan. The container has no such limit. All of this is arithmetic and not a run on a deployed Worker.
  - **Not built.** The plan's deletion hold, which would delay a file deletion while an export runs, is replaced by the re-read of a missing file above, because the hold would touch the finish, the cleanup and the delete paths.
- **Restore** (built for the records; stored images, the search rebuild, the Highlight checks, cancel, resume, the cleanup of abandoned parts and the setup page step are not built) is the upload of an export zip into an Instance whose library is empty, and a chain of jobs of the kind `restore` that writes every record with its id. The owner starts it from the Backup section of Settings, and only the owner's session may call its routes (`src/http/restore-routes.ts`; an agent token gets 403).
  - **Upload.** `POST /api/restore` takes `bytes` and `parts`, refuses with 409 unless the library holds no Item, Topic, Tag, Log entry, Proposal, Pin or Import cursor (`library-not-empty`) or when a restore is already open (`restore-open`, the partial unique index `restores_one_open`), and inserts the `restores` row (`uploading`). The client cuts the zip into parts of 32 MiB (`RESTORE_PART_BYTES`) and sends each with `PUT /api/restore/<id>/parts/<n>`, which stores it as `restores/<id>/part-<n>` in the file store and can be repeated while the restore is `uploading`: after the write the route reads the row again and deletes the part it just wrote when the row has left `uploading`, so a late part never replaces bytes the check has read, and the restore then ends `failed` because the part is missing. The 50 GB limit is `RESTORE_MAX_BYTES`. `GET /api/restore` lists the parts that arrived, so a page that reloaded sends only the missing ones. A part is a plain object on both targets, and the upload holds one part in memory at a time.
  - **Start and check.** `POST /api/restore/<id>/start` only looks at the row: the restore must be `uploading`, the library must still be empty, and every part must be in the file store (`incomplete-upload` answers 400 and keeps the parts). It then flips the row to `running`, phase `check`, and opens the first job in one guarded batch, and answers 202. The check is the first phase of the job chain (`upload`, `check`, `tables`, `finish`), so its time per request is bounded and the Worker never reads a whole zip in one request. Each check job (`src/core/restore-check-unit.ts`, `src/core/restore-check-scan.ts`) reads the central directory (ZIP64 included, stored entries only, safe entry names, one root folder), the manifest, and then one region of about 8.25 MiB (`RESTORE_CHECK_BYTES`) of the zip, and moves a cursor (`entry`, `offset`, `line`, running CRC-32 and the rows counted per table) that commits with the next job. Every entry is read once and its CRC-32 must match, the manifest must list every table of the export format (an export of an older migration may lack tables added since), each record file may hold lines of at most 8 MiB (`RESTORE_LINE_BYTES`), each line must be valid UTF-8 and JSON with the shape of its table, and the rows counted per table must equal the manifest. A refusal ends the restore `failed` with one `failure` code (`not-a-zip`, `unsupported-compression`, `bad-entry-name`, `no-manifest`, `format`, `newer-release`, `unknown-table`, `unknown-column`, `missing-column`, `crc`) in the same guarded write that deletes the parts, and writes nothing to the library, so the library stays empty and only the job that holds the row decides when the parts go. The check and the slices read the zip through `partSource` (`src/core/restore-source.ts`), which streams the parts in order and skips to the wanted offset, so a read holds one region and never a whole part.
  - **Columns of older exports.** A zip whose manifest migration equals the running migration must carry exactly the exported columns of each table (`unknown-column` for an extra one, `missing-column` for a lacking one). A zip of an older migration may carry columns this release dropped, which the restore ignores, and may lack columns this release added, which take their default; a lacking column with no default is `missing-column`. The registry fails to build when a column that a backup leaves out has no default, so the gate catches that before a restore does.
  - **Values.** A JSON-valued column must hold valid JSON, an enum column one of its values, and a duplicate member name in a line is read the way `JSON.parse` reads it (the last one) at the check and at the write, because the write binds the re-serialized row. A row larger than the 2,000,000 bytes a bound string may hold on D1 (`RESTORE_BIND_BYTES`, 1.9 MB) is inserted alone, with each column bound separately; a window never holds more than that many bytes of lines. A row that repeats a key (the id or a unique value) of an earlier row is left out and counted in `restores.dropped`, like a row whose parent is missing, because the check keeps no per-key state (a staging table would hold every key of a library of millions of rows); a row that a trigger refuses fails the slice, and the enum checks cover the values those triggers guard. A singleton table that the zip lacks (`reddit_settings`, `catalog_version`) is emptied by the finishing slice, so a setting the target held before the restore does not survive it; `log_start` keeps the target's row.
  - **Slices.** Each job reads the next window of one record file (at most 500 lines or 1.5 MB, `RESTORE_UNIT_LINES`, `RESTORE_UNIT_BYTES`), in foreign key order (`RESTORE_ORDER`, derived from the Drizzle schema), and inserts it with one `INSERT ... SELECT` over `json_each`, so a row whose parent row is not in the zip is left out and counted in `restores.dropped`, and the inserted rows are counted with `changes()` into `restores.restored`. The window, the new cursor and the counts commit in one guarded batch that also opens the next job, so a slice that dies is read again from the saved cursor, and a repeated slice writes nothing twice (`src/core/restore-job.ts`). The last slice sets each `AUTOINCREMENT` counter of `sqlite_sequence` to the exported high-water mark, so a new Item continues after the highest restored id even when the exported Items with the top ids were deleted, writes the `data_steps` rows, marks the restore `done` and supersedes the part keys.
  - **No work in flight.** An export holds no jobs, so a restored Instance starts with none. A Proposal in state `accepting` is restored as `open` with its cursor, moved count, unit revision and failed runs reset, so the owner can Accept it again, and the Items it already moved are safe to move again. An Item that had an open fetch or Digest job when the export read it (the manifest counts them) has no job after the restore, so nothing resumes its work. A `data_steps` row of a step in progress is restored as not started, so the step runs after the last batch, the same rule as for a step whose exported version is older than the running release (Database and search, Data steps). `migrateData` returns at once while a restore runs, so no step reads a half-restored library, and the finishing slice writes each step's row with the version the manifest holds (0 for a step the manifest lacks) and no cursor. A library exported before a rule change gets the same rewrite as a live one.
  - **While it runs.** `POST /api/items` and `POST /api/items/batch` answer 503 with `code: "restoring"` (the batch checks each link, not only its start), the MCP add tool returns an error with the same text, the share target shows its updating notice, and the screen shows a Restore notice, because a new Item would take an id the zip holds. The refusal does not rely on a check that a write can outrun: the trigger `items_restoring` (migration `0063_restore.sql`) aborts every insert into `items` while a `restores` row is `running` and its `writing` flag is 0, and a slice sets `writing` to 1 as the first statement of its own batch and back to 0 as its last, so only the restore writes Items. The previous release has no such gate in its code, but it opens the migrated database, so its Paste fails on the trigger instead of taking an id. `sweep` runs only the `enqueue` stage while a restore is `running`, so the weekly Proposal checks, the Digest sweep, the merges, the search reconciler and the cleanups never write a half-restored library; a Provider saved before the restore is supported, because those stages wait for the restore and run after it. A restore that a deploy or a crash interrupts resumes on the container at the next start and on the Worker when the sweep takes over the expired claim. A slice that fails 3 times marks the restore `failed` with `gave-up` and leaves the rows written so far, because cancel and resume are not built.
  - **Sequences on D1.** The finishing slice writes `sqlite_sequence` with ordinary `UPDATE` and `INSERT` statements, as the SQLite documentation allows; this was probed on the container and on local D1 (`wrangler dev --local`). Whether real D1 accepts the same writes is not verified and stays with the deploy slice (#391).
  - **Not restored.** Provider keys, the password, sessions and agent tokens are not in the zip, so the owner enters them again; the screen says so.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it holds the records, the manifest, the Item notes and the stored files. D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- **The backup list.** `BACKUP_TABLES` in `src/core/backup-tables.ts` names every included table with its scope, the columns a backup exports and the columns it leaves out; `EXCLUDED_TABLES` in the same file names every other table, including the search tables, with its reason. `d1_migrations` and `sqlite_sequence` are excluded as `carried-in-manifest`: their values travel in `threadsift.json`, not as records. `test/backup-tables.test.ts` migrates a fresh database and fails when a table is in neither list or in both, or when a column of an included table, a generated column included, is in neither set. A later migration that adds a table or a column must therefore decide where it belongs. The key order of either list is not an insert order: the restore derives the parent order from the foreign keys of the migrated database. The export reads the list in its order after `topics` and `tags`, and an export that is running when a release changes the tables or their columns ends `failed` with `list-changed`.
