# Database and search

SQLite on both targets, one Drizzle schema, one migration folder.

- **Drivers.** D1 uses `drizzle-orm/d1`. The container uses Node's built-in `node:sqlite` through `drizzle-orm/sqlite-proxy`, an adapter (`src/targets/node/database.ts`), because `sqlite-proxy` wants rows as arrays and `node:sqlite` returns them that way after `setReturnArrays(true)` (Node 26.12.1, run on 2026-11-04). Drizzle 0.45.4 (the stable release) has no `node:sqlite` driver; 1.0 (release candidate 5) ships `drizzle-orm/node-sqlite`, which replaces the adapter once 1.0 is stable and its `batch` is checked. `node:sqlite` needs no native addon in the image, unlike `better-sqlite3`. The adapter opens the file with a 5 s busy timeout, because `DatabaseSync` sets none by default and a write from another connection then failed a read at once with `database is locked` (gate run 42288164651, 2026-11-06).
- **Async and batch only.** Both drivers are async and support `db.batch()`. D1 has no interactive transactions, so every multi-statement write is one `batch`, which commits or rolls back as a unit on both targets.
- **Guarded batches.** A batch that may only commit while a condition holds (a lease is still held at its generation, the catalog is still at the version a job read) starts with an insert into `guards`, a table whose `CHECK (ok = 1)` fails when the condition's `SELECT` returns 0. The failed check aborts the whole batch on D1 and in the container alike, so a guarded write is all or nothing. The helpers are in `src/core/guards.ts`. `guardedResults` and `guardedWrite` report a refusal only for a failed guard check (`GUARD_REFUSED` lists the messages that count) whose condition no longer holds, which is a lost lease with nothing written. Any other error is rethrown, because its outcome is unknown: a D1 batch whose answer is lost can have committed, and the condition then no longer holds because the batch itself changed it. One case therefore reports a committed batch as lost: a driver that sends a write batch again after it committed (`guardedBatch` called twice with a batch that closes its own condition returns `true` and then `false`, 2026-11-10). Neither target sends a write twice: D1 retries read-only queries only ([D1 retry queries](https://developers.cloudflare.com/d1/best-practices/retry-queries/), read 2026-11-10), and `node:sqlite` runs each batch once. A nested guard that refuses while the outer condition holds is rethrown. A nested guard that refuses while the outer condition is lost is reported as lost, which is true, because nothing was written. A `finish` that gets such an error deletes no file, and the cleanup pass settles them. The guard insert is written with Drizzle's `insert(guards).select(...)`, because a raw `db.run(sql)` inside a D1 batch fails in drizzle-orm 0.45.4 (`Cannot read properties of undefined (reading 'bind')`). Run on `node:sqlite` and on local D1 under `wrangler dev` 4.156.0 on 2026-11-04: the batch with the held generation committed, and the one with a stale generation failed with a `CHECK constraint failed` error and left no row.
- **Migrations.** `drizzle-kit generate` writes SQL files into `migrations/`; hand-written files hold what Drizzle cannot express (FTS5 tables, triggers). The deploy script applies them with `wrangler d1 migrations apply`. The container applies the same files at start and records them in a `d1_migrations` table of the same shape (`wrangler d1 migrations apply DB --local` creates that table with the columns that `src/targets/node/database.ts` creates, checked on 2026-11-04 with wrangler 4.156.0). Local runs use `--local --persist-to <dir>`, which needs no Cloudflare login or `database_id`. A migration only adds; a removal waits for a later release, so the previous release still runs on the new schema (see CI, releases and rollback in `ci-releases-and-rollback.md`). The owner made one exception before the first release: `0061_derived-item-status.sql` drops `items.status`, so the release before it does not run on a migrated database (Item status version in the same page).
  - **Rebuild.** SQLite has no `ALTER COLUMN`, so a column that must become nullable needs a rebuild (`PRAGMA foreign_keys=OFF`, a `__new_` table, a copy, a drop and a rename), as `0041_topic-merge-proposals.sql` does for `proposals` and `0060_export-records.sql` does for `jobs` (an export job has no Item). A rebuild works with foreign keys on, as D1 requires, only when no table references the rebuilt table. A rebuild also drops the table's triggers and indexes, so the file recreates them. `DROP TABLE` removes the table's `sqlite_sequence` row, so the copy alone would let the next insert reuse an id that was deleted, and a page that is still open could press Reject on a different row. The file first inserts and deletes a placeholder row at the old high-water id, which sets the new table's sequence without a write to `sqlite_sequence` (probed on `node:sqlite` and on local D1: ids 1 to 5 with 5 deleted, the next insert took 6 on both).
  - **Add a column.** A nullable column with no default goes in with `ALTER TABLE ... ADD`, and a new index with `CREATE INDEX`, so neither needs a rebuild and the id sequence stays. `drizzle-kit` 0.31.11 writes `ALTER TABLE ... ADD ... REFERENCES` without the column's `ON DELETE` action (`SQLiteAlterTableAddColumnConvertor` in `node_modules/drizzle-kit/bin.cjs`) while its snapshot records the action, and it mangles a unique expression index, so such a file carries `ON DELETE cascade` and that index by hand (`0014_ai-task-owner.sql`, `0044_lost-highlight-proposals.sql`, `0046_disagreement-proposals.sql`). The generator's other route, recreating `ai_tasks`, would drop a table that `digests.task_id` names, and D1 enforces foreign keys in migrations ([D1 docs, Foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)). A foreign key column gets an index, because SQLite scans the whole child table for a foreign key with no index ([SQLite foreign keys, section 3](https://www.sqlite.org/foreignkeys.html#fk_indexes)).
  - **Unique index and NULL.** SQLite treats each NULL as distinct in a unique index, so two open `export` jobs with no Item are accepted by `jobs_one_open_per_item_kind`, and the partial unique index `exports_one_live` guards the one-live-export rule instead (probed on `node:sqlite` 3.53.3 and on local D1, wrangler 4.159.0).
  - **Sequences.** A restore writes the high-water mark of each `AUTOINCREMENT` counter into `sqlite_sequence` with one `UPDATE` of `max(seq, mark)` and one `INSERT ... SELECT` for a table with no row yet (the manifest's `sequences`), because `sqlite_sequence` has no unique key on `name`. Both statements ran on `node:sqlite` and on local D1 before the restore used them.
- **Budget trigger.** The trigger `items_token_budget` (`0052_agent-token-budget.sql`, replaced by `0066_budget-slot-day.sql`) is written by hand at the end of the generated file, because `drizzle-kit` cannot express a trigger. It fires after an insert into `items` only when `added_by_token` is set and `budget_slot_day` is not the UTC day of `saved_at`, counts the Item for that day and aborts the batch when the count passes the budget. It covers a single add and any Item of a batch saved on a later day than its reservation; the batch's other Items are counted by the reservation (see Access, Daily budget in `access-owner-login-agent-tokens-mcp.md`). `ON CONFLICT DO NOTHING` inserts no row, so a link the library holds never fires it. Checked on local D1 through `wrangler d1 execute --local` on 2026-11-15: an Item saved on a later day than its `budget_slot_day` was counted and the third one past a budget of 2 aborted, and an Item saved on its `budget_slot_day` was not counted.
- **Consistency triggers.** `0031_consistency-triggers.sql` and the migrations after it add `BEFORE INSERT` and `BEFORE UPDATE` triggers that `RAISE(ABORT)` on a row that contradicts itself (a reason outside `FAILURE_REASONS`, both `post_text` and `post_text_key`, a source that does not fit the Item's kind, a job, Proposal or Pin kind or state outside its list in `src/core/kinds.ts`, subject columns that do not fit the kind). They exist because local D1 refuses `ALTER TABLE ... ADD CONSTRAINT ... CHECK` with `not authorized to use function: sqlite_fail`, while `node:sqlite` (SQLite 3.53.3) accepts and enforces it (run on 2026-11-15). An update trigger fires only when the update names one of its columns, so a row stored before the triggers existed stays readable and writable by every other column. A refused write inside a batch rolls the whole batch back, on D1 and in the container alike. The triggers add to the schema and drop nothing. A writer that stores a value the triggers do not list fails its write, so a new value changes its trigger in the same migration. The `test/consistency-triggers*.test.ts` files enforce that: on the real migrations they store and update a row for every listed value, and for each Proposal kind every state it holds (`LIFECYCLE`, `src/core/proposal-lifecycle.ts`), so the gate fails when a trigger refuses a value the code lists. The Item view derives status and reason when it reads (`STATUS_VIEW_COLUMNS` in `src/core/item-status.ts`), so a row that predates the triggers, or a `ready` Item with an open Digest job (which no trigger can refuse, because it needs a read of another table), is listed and read with 200 and the status its jobs imply. A row whose Source or kind is unknown still fails the list's `ItemSchema`, so `shownItems` in `src/http/item-view.ts` skips it in `GET /api/items` with one `item-not-shown` log line, because the browser rejects the whole list when one Item fails that schema. Rollback run (2026-11-09, `node:sqlite` container): the container specs of the release before `0031` that write Items, jobs, Digests and deletions (31 files) ran against a database with only this migration added. The release's own writers passed every case. Six cases failed, all in `post-text-file.spec.ts` and `delete-item-reader.spec.ts`, because their SQL seeds set `post_text` and `post_text_key` on one row, which no writer does.
- **Data steps.** A change to stored data that needs JavaScript, such as `parseLink`, is a data step, because the SQL migration files on both targets run only SQL. `migrateData` in `src/core/data-steps.ts` runs the steps in `STEPS` (`src/core/data-step-list.ts`) in order. A step's `advance` does one bounded unit of work and returns its writes and the cursor of the next unit, or `null` when the step is complete (`src/core/data-step-contract.ts`). The runner commits a unit's writes and the new cursor in one `db.batch`, and records the version only in the batch of the last unit. The record is monotonic: a runner of an older release cannot lower a version a newer release recorded, and it stops at its next unit because the row it reads is complete. A run stops after `UNITS_PER_RUN` units in all, shared by the steps in order (100; a unit costs two to five queries), so the steps together stay inside the 1,000 queries per invocation that D1 allows on Workers Paid, where a `batch` counts as one query ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)). With 60,000 Items to rename and 3,000 pairs of Topics and of Tags to merge on local D1, one call to `migrateData` made at most 403 queries over 6 calls, resumed from the stored cursors each time; with 100 units for each step it made 1,075 and 1,124 (counted from the D1 binding's statements and batches on 2026-11-08 with a script that is no longer in the repository). A run that fails or is killed loses at most its open unit.
  - **One run at a time.** `migrateData` first claims the one row of `data_step_lease`, and a run that gets no row returns without work. The row expires 30 seconds ahead (`LEASE_MS`, our choice; each unit renews it). Every unit commits in a guarded batch whose guard checks that the run still holds the row, so a run that was slower than the lease and lost it commits neither its writes nor its cursor. A run that is killed leaves the row to expire, so the Paste entries answer `updating` for at most 30 seconds after such a crash. The row is transient state that an export leaves out.
  - **Rules for a step.** A unit must be safe to run again, because a run that fails resumes from the stored cursor, and must name in its writes the value it replaces. A step makes no network call, drops no schema and never uses `UPDATE OR IGNORE` or `REPLACE`, so the unique indexes stay in force. A step needing a view of the whole library, as the Item identity does to find collisions, stages its proposals in `data_step_renames` in bounded pages instead of holding the library in memory. A step whose rule changes gets a higher version, which runs it again.
  - **When steps run.** The container runs `migrateData` when its job loop starts, before it serves, and on each minute tick. The Worker runs it at each Cron tick (`tick` in `src/core/tick.ts`, beside the sweep, so a failing sweep does not skip it). Every Paste entry (`paste` in `src/core/paste.ts`, which `POST /api/items` and `/share` both call) first checks that no step is pending, runs `migrateData` itself when one is, and answers 503 (the paste card and the `/share` arrival show the `updating` notice of `web/src/text.ts` and keep the link in the field) while a step still cannot finish. So a Paste never computes an identity under a new rule while stored Items still carry the old one, on a Worker before its first Cron tick and on a container whose start failed. Reads, deletes and Read state work meanwhile. When another run holds the lease, the Paste checks again every 100 ms for up to 5 seconds before it answers 503, because a fresh database gets several first Pastes at once (the demo seed sends every link of `demoPastes` in `tools/preview-owner.ts` at once) and the steps on an empty library finish in milliseconds.
  - **Restore.** A restore (`export-backup-and-restore.md`) writes each step's row from the manifest's version and no cursor, so a step whose exported version is older than `version`, or is missing, or was in progress when the export read it runs again from the start after the last batch, and a step at the current version does not run. `migrateData` does nothing while a restore runs.
- **Search.** FTS5 external-content tables kept in step by triggers; D1 supports FTS5 (D1 docs, SQL statements). Searchable text lives in `search_parts`, one row per part of an Item. A part longer than 500,000 bytes is split into chunks of at most 125,000 characters at the last whitespace, so no word is split and no search row nears D1's 2 MB row limit; one token longer than a chunk is cut hard, which is accepted. A query matches parts and groups them by Item. Related Items candidates come from the same index, ordered by `bm25()` ascending, because a lower `bm25` score is a better match (SQLite FTS5 docs; `src/core/related-candidates.ts`; the aggregate form that fails and the measured form are in `docs/wiki.md`, Related Items). A Kept comment body is cut like a post text by `chunkPostText`. The Digest job reads the selected bodies before its batch, and the reconciler reads the Kept bodies of the published generation in a separate query (`keptBodies`), so no single value or bound parameter holds all of an Item's comments, which can total 4 MiB against D1's 2,000,000 bytes per string. `commentPartWrites` binds the parts as JSON arrays, so a comment of 600,000 bytes is several parts and a thread of many short comments is few statements. The app rewrites an Item's parts in the same batch as the change to that part (`src/core/search.ts`). The migration that creates the index fills nothing. A reconciler in the job sweep (`src/core/search-reconciler.ts`) pages over 10 Items by id with a wrapping cursor and, through the part writer it shares with the restore's `search` phase (`stalePartWrites` in `src/core/search-item-parts.ts`), rewrites an Item's parts when the hash of its title, post text, stored Digest, Tag names, repository text and Kept comment ids differs from the hash stored beside its parts. This fills the index for an existing library, so search reaches an older Item only as the pass advances, and it repairs a write made by the previous release during a deploy or after a rollback. A stored Digest that does not parse adds no Digest parts, and the Item's titles, post text and Tags stay searchable. A search term is a run of letters and digits (the separators `unicode61` uses), matched as a quoted prefix, and the terms reach SQL as one JSON parameter; the filter counts come from the same batch as the first page of the list, so both describe one state of the library (`src/core/item-filters.ts`). An external-content FTS5 table is checked with `INSERT INTO search_index(search_index, rank) VALUES ('integrity-check', 1)`. `saveFailedResolution` in `src/core/failed-resolution.ts`, the write for a short link that fails to resolve, rewrites no part, because it sets the status, the reason, the fetch result and the X note, never the title or post text.
- **Large text.** A post text over 1,000,000 bytes is stored as an object in the file store, and its row holds the key (see Files in `files.md`); the same rule runs on both targets, so no single value nears the 2 MB limit. A comment body is never stored as a file: a Paste whose thread has a comment body over 1,000,000 UTF-8 bytes is refused with a 400, and so is a post text that long. Two chosen limits keep every value and statement below D1's 2,000,000 bytes per string or row (D1 limits, https://developers.cloudflare.com/d1/platform/limits/): a title, author, subreddit, comment id, comment author or parent id over 4,096 bytes is refused, and so is a comment whose stored row, as JSON with its escapes, is over 1,499,998 bytes, which is the 1,500,000-byte statement budget less the array brackets. Both numbers are chosen, not measured or set by Reddit: 4,096 bytes is meant to sit far above any real username, subreddit or title (unsupported: no Reddit source was checked), and 1,500,000 bytes leaves 500,000 bytes of room under 2,000,000 for the statement's own text. A body of 300,000 control characters is under the body limit and over the row limit, because each escapes to 6 bytes. `GET /api/items` leaves out the post text, because about 50 rows of long text would pass the 50 MB query-result limit; `GET /api/items/:id` returns it.
- **D1 limits that shape queries:** 100 bound parameters per statement, 1,000 queries per invocation on the paid plan, 2 MB per row, 50 MB per query result (D1 docs, Limits). A list whose length the data decides is bound as one JSON parameter and expanded with `json_each`; large reads page by key.
- **Duplicate column names.** A `db.batch` select that joins one table twice must name each repeated column with `sql<T>`...`.as("name")`, as `pageQuery` in `src/core/proposal-rows.ts` does. On `wrangler dev --local` 4.158.0 the unnamed query returned `from.id` as the tag's name and `into` as `{}`, because the D1 driver reads each row as an object and the repeated `id` and `name` keys collapse; `node:sqlite` reads rows by position and returned the right values, so the core tests cannot show this.
- **Numbers.** D1 returns numbers as JavaScript numbers, so an integer above 2^53 loses precision (D1 docs, Import and export data). X post ids are above that, so every id that comes from a Source is `text`.

Evidence, a spike on 2026-11-04 (scratch folder, not in the repo): one schema and one query module ran unchanged on `node:sqlite` (Node 26.11.1, SQLite 3.53.3), on Bun 1.4.3 (SQLite 3.53.4) and on local D1 under `wrangler dev` (wrangler 4.156.0). All gave the same results for an upsert by URL, FTS5 with porter stemming and prefix queries, triggers that follow an update and a delete, a cascade delete, and a `batch` whose second insert broke a unique index and left no row behind. D1 refuses `sqlite_version()`.
