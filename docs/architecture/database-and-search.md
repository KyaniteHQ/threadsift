# Database and search

SQLite on both targets, one Drizzle schema, one migration folder.

- **Drivers.** D1 uses `drizzle-orm/d1`. The container uses Node's built-in `node:sqlite` through `drizzle-orm/sqlite-proxy`, an adapter of about 20 lines (`src/targets/node/database.ts`), because `sqlite-proxy` wants rows as arrays and `node:sqlite` returns them that way after `setReturnArrays(true)` (Node 26.12.1, run on 2026-11-04). The adapter supports `run` and `all`; `get` needs a missing-row convention that no query uses yet, so it throws. Drizzle 0.45.4 (the stable release) has no `node:sqlite` driver; 1.0 (release candidate 5) ships `drizzle-orm/node-sqlite`, which replaces the adapter once 1.0 is stable and its `batch` is checked. `node:sqlite` needs no native addon in the image, unlike `better-sqlite3`. The adapter opens the file with a 5 s busy timeout, because `DatabaseSync` sets none by default and a write from another connection then failed a read at once with `database is locked` (gate run 42288164651, 2026-11-06).
- **Async and batch only.** Both drivers are async and support `db.batch()`. D1 has no interactive transactions, so every multi-statement write is one `batch`, which commits or rolls back as a unit on both targets. The container's batch is to run its statements between `BEGIN` and `COMMIT` on the one connection through the `batchCallback` that `drizzle-orm/sqlite-proxy` accepts; `src/targets/node/database.ts` passes that callback, which rolls the batch back when a statement fails.
- **Guarded batches.** A batch that may only commit while a condition holds (a lease is still held at its generation, the catalog is still at the version a job read) starts with an insert into `guards`, a table whose `CHECK (ok = 1)` fails when the condition's `SELECT` returns 0. The failed check aborts the whole batch, on D1 and in the container alike, so a guarded write is all or nothing. A failed guard rolls the batch back. `guardedBatch` and `insertGuard` in `src/core/schema.ts` own the guard insert, atomic writes and condition re-read. `guardedResults` (which `guardedBatch` wraps and which returns each statement's rows, so Accept of a Topic merge can wake the job its closing writes opened) and `guardedWrite` report a refusal only for a failed guard check (`CHECK constraint failed`, from the guard insert) whose condition no longer holds; that is a lost lease, and nothing was written. Any other error is rethrown, because its outcome is unknown: a D1 batch whose answer is lost can have committed, and the condition then no longer holds because the batch itself changed it. A refusal is reported as lost whenever the condition is false when it is read again, and one case reports a committed batch as lost: a driver that sends a write batch again after it committed, since the second send meets the condition the first one closed (`guardedBatch` called twice with a batch that closes its own condition returns `true` and then `false`, 2026-11-10). Neither target sends a write twice: D1 retries read-only queries only ([D1 retry queries](https://developers.cloudflare.com/d1/best-practices/retry-queries/), read 2026-11-10), and `node:sqlite` runs each batch once. A nested guard (an `insertGuard` inside the writes) that refuses while the outer condition holds is rethrown, and a nested guard that refuses while the outer condition is lost is reported as lost, which is true: nothing was written, and the outer holder no longer owns the row. A `finish` that gets such an error deletes no file, and the cleanup pass settles them. The Digest runner requeues stale content or catalog inputs under its claim without consuming an attempt. The job runner (`writeWhileHolding` in `src/core/job-finish.ts`) guards every result on the row still being `running` at the attempt count its runner claimed. The guard insert is written with Drizzle's `insert(guards).select(...)`, because a raw `db.run(sql)` inside a D1 batch fails in drizzle-orm 0.45.4 (`Cannot read properties of undefined (reading 'bind')`). Both behaviours were run on node:sqlite and on local D1 under `wrangler dev` 4.156.0 on 2026-11-04: the batch with the held generation committed, the one with a stale generation failed with `CHECK constraint failed: ok = 1` and left no row.
- **Migrations.** `drizzle-kit generate` writes SQL files into `migrations/`; hand-written files hold what Drizzle cannot express (FTS5 tables, triggers). The deploy script applies them with `wrangler d1 migrations apply`; the container applies the same files at start and records them in a `d1_migrations` table of the same shape (`wrangler d1 migrations apply DB --local` creates that table with the columns that `src/targets/node/database.ts` creates, checked on 2026-11-04 with wrangler 4.156.0). Local runs use `--local --persist-to <dir>`, which needs no Cloudflare login or `database_id`. A migration only adds; a removal waits for a later release, so the previous release still runs on the new schema (see CI, releases and rollback in `ci-releases-and-rollback.md`). A rebuild is the exception when a column must become nullable, because SQLite has no `ALTER COLUMN`: `0012_workers-ai-settings.sql`, `0018_cli-provider.sql` and `0021_codex-provider.sql` rebuilt `settings`, and `0041_topic-merge-proposals.sql` rebuilt `proposals` (`PRAGMA foreign_keys=OFF`, a `__new_` table, a copy, a drop and a rename). It works with foreign keys on, as D1 requires, because no table references `proposals` and the copy only inserts rows whose Tag ids exist. A rebuild also drops the table's triggers, so the file recreates them. `DROP TABLE` removes the table's `sqlite_sequence` row, so the copy alone would let the next insert reuse an id that was deleted, and a page that is still open could press Reject on a different row. The file first inserts and deletes a placeholder row at the old high-water id, which sets the new table's sequence without a write to `sqlite_sequence` (probed on `node:sqlite` and on local D1: ids 1 to 5 with 5 deleted, the next insert took 6 on both). `drizzle-kit` 0.31.11 writes `ALTER TABLE ... ADD ... REFERENCES` without the column's `ON DELETE` action (`SQLiteAlterTableAddColumnConvertor` in `node_modules/drizzle-kit/bin.cjs`) while its snapshot records the action, so `0014_ai-task-owner.sql` and `0044_lost-highlight-proposals.sql` carry `ON DELETE cascade` by hand. `0044` is the second kind of migration this bullet describes: it adds the nullable column `proposals.highlight_id` and a unique index with `ALTER`, needs no rebuild and so leaves the id sequence alone, and is allowed with foreign keys on because the new column has a `NULL` default. It ran on `node:sqlite` (Node 26.12.1) and on local D1 (`wrangler d1 execute --local`) with the same output: `pragma_foreign_key_list` shows `CASCADE`, the unique index takes one row for a Highlight and refuses a second while rows with a `NULL` column coexist, deleting a Highlight deletes its row, and the sequence keeps its high-water mark. `0045_overview-gap-proposals.sql` is the same kind of migration for `proposals.topic_id` and the unique index `proposals_overview_topic`, with `ON DELETE cascade` written by hand for the same reason. `0046_disagreement-proposals.sql` is the same kind again: it adds `proposals.from_item_id` and `into_item_id` (`REFERENCES items(id) ON DELETE cascade`, by hand, and the unique expression index `proposals_item_pair`, which `drizzle-kit` also mangled and so is written by hand), the plain integers `from_digest` and `into_digest`, two indexes, and the table `topic_checks`, and it replaces the three trigger pairs. `0047_disagreement-pins.sql` does the same for `pins`: `from_item_id` and `into_item_id` (`REFERENCES items(id) ON DELETE cascade`, by hand), the plain integers `from_digest` and `into_digest`, the indexes `pins_from_item` and `pins_into_item` (SQLite scans the whole child table for a foreign key with no index, [SQLite foreign keys, section 3](https://www.sqlite.org/foreignkeys.html#fk_indexes)), and the replaced `pins_values_*` and `pins_subject_*` triggers, with no table rebuild, so the id sequence stays. The generator's other route, recreating `ai_tasks`, would drop a table that `digests.task_id` names, and D1 enforces foreign keys in migrations ([D1 docs, Foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)).
- **Consistency triggers.** `0031_consistency-triggers.sql` adds `BEFORE INSERT` and `BEFORE UPDATE` triggers that `RAISE(ABORT)` on a row that contradicts itself, because SQLite cannot add a CHECK to an existing table without recreating it. `items_status_reason` refuses an unknown status, `failed` without a known reason, and a reason on `processing` or `ready`. `items_post_text` refuses a row with both `post_text` and `post_text_key`. `items_source_kind` refuses a source that is not the one its kind belongs to (`sourceOf` in `src/core/links.ts`). `jobs_values` refuses a job kind or state outside `JOB_KINDS` (`fetch`, `digest`, `topic_overview`, `related_pick`, `proposals`, `topic_proposals`, `disagreement_proposals`) and `JOB_STATES`, `proposals_values` refuses a proposal kind (`tag-merge`, `topic-merge`, `highlight-lost`, `overview-gap`, `items-disagree`) or state outside `PROPOSAL_KINDS` and `PROPOSAL_STATES`, `proposals_subject` refuses a row whose subject columns do not fit its kind (a `tag-merge` row has both Tag ids and no other subject column, a `topic-merge` row the reverse, a `highlight-lost` row a Highlight id and no other subject column, an `overview-gap` row a `topic_id` and no other subject column, an `items-disagree` row two different Item ids and two Digest task ids and no other subject column; `0044_lost-highlight-proposals.sql`, `0045_overview-gap-proposals.sql` and `0046_disagreement-proposals.sql` replaced both pairs, and the update trigger names every subject column), `pins_values` refuses a Pin kind outside `PIN_KINDS`, and `pins_subject` refuses a Pin whose target column does not fit its kind (a `tag-merge` Pin has `into_tag_id` and no `into_topic_id`, a `topic-merge` Pin the reverse, and an `items-disagree` Pin has two different Item ids, both Digest tokens and neither target column, while the two earlier kinds refuse the four Item and digest columns; `0047_disagreement-pins.sql` replaced both pairs with no rebuild); `0036_topic-pages.sql`, `0037_related-items.sql`, `0039_weekly-tag-merge-proposals.sql` and `0041_topic-merge-proposals.sql` each replaced both `jobs_values` triggers to add their kind, and `0040_tag-merge-pins.sql` created both `pins_values` triggers and replaced both `log_entries_action` triggers to add `merge`, and `0043_merge-topic-log-action.sql` replaced them again to add `merge-topic`, and `0042_topic-merge-pins.sql` rebuilt `pins` (dropping the table dropped its two triggers) and created the `pins_values` pair with `topic-merge` and the `pins_subject` pair. An update trigger fires only when the update names one of its columns, so a row stored before the triggers existed stays readable and writable by every other column. A refused write inside a batch rolls the whole batch back, on D1 and in the container alike. The triggers add to the schema and drop nothing. A writer that stores a status, reason, Source, Kind or job value the triggers do not list fails its write, so a new value changes its trigger in the same migration. `test/consistency-triggers.test.ts` and `test/consistency-triggers-proposals.test.ts` (a second file, because the first sits at the 300-line cap) enforce that: on the real migrations they store and update a row for every value in `ITEM_STATUSES`, `FAILURE_REASONS`, `KINDS` (with `sourceOf`), `JOB_KINDS`, `JOB_STATES`, `LOG_ACTIONS`, `PIN_KINDS`, `PROPOSAL_KINDS` and `PROPOSAL_STATES`, so the gate fails when a trigger refuses a value the code lists. The Item view derives status and reason when it reads (`STATUS_VIEW_COLUMNS` in `src/core/item-status.ts`), so a row that predates the triggers, or a `ready` Item with an open Digest job (which no trigger can refuse, because it needs a read of another table), is listed and read with 200 and the status its jobs imply. A row whose Source or kind is unknown still fails the list's `ItemSchema`, so `shownItems` in `src/http/item-view.ts` skips it in `GET /api/items` with one `item-not-shown` log line, because the browser rejects the whole list when one Item fails that schema. Rollback run (2026-11-09, `node:sqlite` container): the container specs of the release before this migration that write Items, jobs, Digests and deletions (ingest, Digest, retry, delete, scenario, Reddit, share, highlights, catalog, post text; 31 files) ran against a database with only this migration added. The release's own writers passed every case. Six cases failed, all in `post-text-file.spec.ts` and `delete-item-reader.spec.ts`, because their SQL seeds set `post_text` and `post_text_key` on one row, which no writer does.
- **Data steps.** A change to stored data that needs JavaScript, such as `parseLink`, is a data step, because the SQL migration files on both targets run only SQL. `migrateData` in `src/core/data-steps.ts` runs the steps in order, and `STEPS` there lists them. A step has a name, a version and `advance`, which does one bounded unit of work and returns its writes and the cursor of the next unit, or `null` when the step is complete (`src/core/data-step-contract.ts`). `data_steps` holds, for each step, the version its last complete run recorded and the cursor of a run in progress. The runner reads that row before every unit, commits the unit's writes and the new cursor in one `db.batch` (all or nothing on both targets), and records the version only in the batch of the last unit. The record is monotonic: a runner of an older release cannot lower a version a newer release recorded, and it stops at its next unit because the row it reads is complete. A run stops after `UNITS_PER_RUN` units in all, shared by the steps in order (100; a unit costs two to five queries, a catalog merge unit four and a Topic unit of `pin-keys` five, Catalog keys, Bounds of a Topic unit), so the steps together stay inside the 1,000 queries per invocation that D1 allows on Workers Paid, where a `batch` counts as one query ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)). With 60,000 Items to rename and 3,000 pairs of Topics and of Tags to merge on local D1, one call to `migrateData` made at most 403 queries over 6 calls, resumed from the stored cursors each time; with 100 units for each step it made 1,075 and 1,124 (counted from the D1 binding's statements and batches on 2026-11-08 with a script that is no longer in the repository), and the next run continues from the stored cursor. A run that fails or is killed loses at most its open unit. One run works at a time. `migrateData` first claims the one row of `data_step_lease` with an insert that takes an expired row and returns no row while another run holds it, and a run that gets no row returns without work. The row holds a random holder id and an expiry 30 seconds ahead (`LEASE_MS`, our choice; each unit renews it). Every unit commits in a guarded batch whose guard checks that the run still holds the row, so a run that was slower than the lease and lost it commits neither its writes nor its cursor and stops. A run deletes its row when it ends. A run that is killed leaves the row to expire, so the Paste entries answer `updating` for at most 30 seconds after such a crash. Identity of the row: its `id` is the constant 1, the holder is a new random UUID for each run and is never reused, and the row is transient state that an export leaves out. A unit must still be safe to run again, because a run that fails resumes from the stored cursor, and must name in its writes the value it replaces. A step makes no network call, drops no schema and never uses `UPDATE OR IGNORE` or `REPLACE`, so the unique indexes stay in force. A step needing a view of the whole library, as the Item identity does to find collisions, stages its proposals in `data_step_renames` (step, subject, old key, new key) in bounded pages instead of holding the library in memory. A step is reached the way the app already runs work: the container runs `migrateData` when its job loop starts, before it serves, and on each minute tick; the Worker runs it at each Cron tick (`tick` in `src/core/tick.ts`, beside the sweep, so a failing sweep does not skip it). Every Paste entry (`paste` in `src/core/paste.ts`, which `POST /api/items` and `/share` both call) first checks that no step is pending, runs `migrateData` itself when one is, and answers 503 (the paste card and the `/share` arrival show the `updating` notice of `web/src/text.ts` and keep the link in the field) while a step still cannot finish. When another run holds the lease, the Paste checks again every 100 ms for up to 5 seconds before it answers 503, because a fresh database gets several first Pastes at once (the demo seed sends 4) and the steps on an empty library finish in milliseconds. Reads, deletes and Read state work meanwhile. So a Paste never computes an identity under a new rule while stored Items still carry the old one, on a Worker before its first Cron tick and on a container whose start failed. A fresh Instance runs the steps on its first Paste or tick, over an empty library. A step whose rule changes gets a higher version, which runs it again. The `item-identity` step (`src/core/item-identity.ts`) is the first; `topic-keys` and `tag-keys` (`src/core/catalog-key-step.ts`) follow it (see Catalog keys in `data-model-outline.md`), then `pin-keys` (see Catalog keys in `data-model-outline.md`, Pins; it merges a Tag and a Topic that hold a Pin's key), then `ai-task-owners` (see AI tasks and Providers in `ai-tasks-and-providers.md`, Task owner).
- **Search.** FTS5 external-content tables kept in step by triggers; D1 supports FTS5 (D1 docs, SQL statements). Searchable text lives in `search_parts`, one row per part of an Item: the title, each post-text chunk, each Kept comment (`comment` parts for each Kept comment of the published Digest's generation, written in the batch that publishes the Digest), the Summary, the Tags, each Highlight and the Note. A part longer than 500,000 bytes is split into chunks, so no search row nears D1's 2 MB row limit. A query matches parts and groups them by Item; the Highlights page queries only Highlight and Note parts. Related Items candidates come from the same index, ordered by `bm25()` ascending, because a lower `bm25` score is a better match (SQLite FTS5 docs): only the `digest-title`, `summary` and `tags` parts of Items that have a Digest are matched, 12 terms at most joined with OR, and each Item's best score ranks it (`src/core/related-candidates.ts`; the aggregate form that fails and the measured form are in `docs/wiki.md`, Related Items). An Item that the reconciler has not yet rebuilt shows as a candidate only after it has. Built so far: the title, the post text, the Digest's clean title, the Summary and the Tags, the `repository` part (a GitHub repository's description and topics, one line each, written by the fetch job in the batch that writes the `github_repos` row), the `comment` parts of a Reddit thread, the `highlight` parts (Highlights) and the `note` part (The Note); the other kinds arrive with their slices. A Kept comment body is cut like a post text by `chunkPostText`: the Digest job reads the selected bodies before its batch (`selectedBodies` in `src/core/reddit-thread.ts`), the reconciler reads the Kept bodies of the published generation in a separate query (`keptBodies`, so no single value or bound parameter holds all of an Item's comments, which can total 4 MiB against D1's 2,000,000 bytes per string), and `commentPartWrites` binds the parts as JSON arrays, so a comment of 600,000 bytes is several parts and a thread of many short comments is few statements. The app rewrites an Item's parts in the same batch as the change to that part (`src/core/search.ts`, called from the fetch, Digest and catalog writes). The migration that creates the index fills nothing. A reconciler in the job sweep (`src/core/search-reconciler.ts`) pages over 10 Items by id with a wrapping cursor, the same pattern as `linkOlderDigests`, and rewrites an Item's parts when the hash of its title, post text, stored Digest, Tag names, repository text and Kept comment ids differs from the hash stored beside its parts. This fills the index for an existing library, so search reaches an older Item only as the pass advances, and it repairs a write made by the previous release during a deploy or after a rollback. A post text over 500,000 bytes is cut into chunks of at most 125,000 characters at the last whitespace, so no word is split; one token longer than a chunk is cut hard, which is accepted. A stored Digest that does not parse adds no Digest parts, and the Item's titles, post text and Tags stay searchable. A search term is a run of letters and digits (the separators `unicode61` uses), matched as a quoted prefix, and the terms reach SQL as one JSON parameter; the filter counts come from the same batch as the first page of the list, so both describe one state of the library (`src/core/item-filters.ts`). An external-content FTS5 table is checked with `INSERT INTO search_index(search_index, rank) VALUES ('integrity-check', 1)`. `saveFailedResolution` in `src/core/failed-resolution.ts`, the write for a short link that fails to resolve, sets only the status, the reason and the fetch result, never the title or post text, so it rewrites no part.
- **Large text.** A post text, comment body or AI task input over 1,000,000 bytes is stored as an object in the file store, and its row holds the key; the same rule runs on both targets, so no single value nears the 2 MB limit. The file store, the read of a post text from it and the fetch job's write of a long post text are built (see Files in `files.md`); no other kind of text uses the store yet. A comment body is never stored as a file: a Paste whose thread has a comment body over 1,000,000 UTF-8 bytes (`utf8Length` of the body) is refused with a 400, and so is a post text that long. Two chosen limits keep every value and statement below D1's 2,000,000 bytes per string or row (D1 limits, https://developers.cloudflare.com/d1/platform/limits/): a title, author, subreddit, comment id, comment author or parent id over 4,096 bytes is refused, and so is a comment whose stored row, as JSON with its escapes, is over 1,499,998 bytes, which is the 1,500,000-byte statement budget less the array brackets. Both numbers are chosen, not measured or set by Reddit: 4,096 bytes is meant to sit far above any real username, subreddit or title (unsupported: no Reddit source was checked) and keeps the title, author and subreddit parameters far below D1's limit, and 1,500,000 bytes leaves 500,000 bytes of room under 2,000,000 for the statement's own text. A body of 300,000 control characters is under the body limit and over the row limit, because each escapes to 6 bytes. `GET /api/items` selects the list's columns and leaves out the post text, because about 50 rows of long text would pass the 50 MB query-result limit; `GET /api/items/:id` returns it.
- **D1 limits that shape queries:** 100 bound parameters per statement, 1,000 queries per invocation on the paid plan, 2 MB per row, 50 MB per query result (D1 docs, Limits). A list whose length the data decides is bound as one JSON parameter and expanded with `json_each`; large reads page by key.
- **Duplicate column names.** A `db.batch` select that joins one table twice must name each repeated column with `sql<T>`...`.as("name")`, as `pageQuery` in `src/core/proposal-page.ts` does. On `wrangler dev --local` 4.158.0 the unnamed query returned `from.id` as the tag's name and `into` as `{}`, because the D1 driver reads each row as an object and the repeated `id` and `name` keys collapse; `node:sqlite` reads rows by position and returned the right values, so the core tests cannot show this.
- **Numbers.** D1 returns numbers as JavaScript numbers, so an integer above 2^53 loses precision (D1 docs, Import and export data). X post ids are above that, so every id that comes from a Source is `text`.

Evidence, a spike on 2026-11-04 (scratch folder, not in the repo): one schema and one query module ran unchanged on `node:sqlite` (Node 26.11.1, SQLite 3.53.3), on Bun 1.4.3 (SQLite 3.53.4) and on local D1 under `wrangler dev` (wrangler 4.156.0). All gave the same results for an upsert by URL, FTS5 with porter stemming and prefix queries, triggers that follow an update and a delete, a cascade delete, and a `batch` whose second insert broke a unique index and left no row behind. D1 refuses `sqlite_version()`.
