# Database and search

SQLite on both targets, one Drizzle schema, one migration folder.

- **Drivers.** D1 uses `drizzle-orm/d1`. The container uses Node's built-in `node:sqlite` through `drizzle-orm/sqlite-proxy`, an adapter (`src/targets/node/database.ts`), because `sqlite-proxy` wants rows as arrays and `node:sqlite` returns them that way after `setReturnArrays(true)` (Node 26.12.1, run on 2026-11-04). Drizzle 0.45.4 (the stable release) has no `node:sqlite` driver; 1.0 (release candidate 5) ships `drizzle-orm/node-sqlite`, which replaces the adapter once 1.0 is stable and its `batch` is checked. `node:sqlite` needs no native addon in the image, unlike `better-sqlite3`. The adapter opens the file with a 5 s busy timeout, because `DatabaseSync` sets none by default and a write from another connection then failed a read at once with `database is locked` (gate run 42288164651, 2026-11-06).
- **Async and batch only.** Both drivers are async and support `db.batch()`. D1 has no interactive transactions, so every multi-statement write is one `batch`, which commits or rolls back as a unit on both targets.
- **Guarded batches.** A batch that may only commit while a condition holds (the Proposal is still at the unit revision the merge read, the catalog is still at the version a job read) starts with an insert into `guards`, a table whose `CHECK (ok = 1)` fails when the condition's `SELECT` returns 0. The failed check aborts the whole batch on D1 and in the container alike, so a guarded write is all or nothing. The helpers are in `src/core/kernel/guards.ts`. `guardedResults` and `guardedWrite` report a refusal only for a failed guard check (`GUARD_REFUSED` lists the messages that count) whose condition no longer holds, which is a lost lease with nothing written. Any other error is rethrown, because its outcome is unknown: a D1 batch whose answer is lost can have committed, and the condition then no longer holds because the batch itself changed it. One case therefore reports a committed batch as lost: a driver that sends a write batch again after it committed (`guardedBatch` called twice with a batch that closes its own condition returns `true` and then `false`, 2026-11-10). Neither target sends a write twice: D1 retries read-only queries only ([D1 retry queries](https://developers.cloudflare.com/d1/best-practices/retry-queries/), read 2026-11-10), and `node:sqlite` runs each batch once. A nested guard that refuses while the outer condition holds is rethrown. A nested guard that refuses while the outer condition is lost is reported as lost, which is true, because nothing was written. A `finish` that gets such an error deletes no file, and the cleanup pass settles them. The guard insert is written with Drizzle's `insert(guards).select(...)`, because a raw `db.run(sql)` inside a D1 batch fails in drizzle-orm 0.45.4 (`Cannot read properties of undefined (reading 'bind')`). Run on `node:sqlite` and on local D1 under `wrangler dev` 4.156.0 on 2026-11-04: the batch with the held generation committed, and the one with a stale generation failed with a `CHECK constraint failed` error and left no row.
- **Migrations.** `migrations/0000_schema.sql` creates a fresh database and `0001_vault.sql` adds the vault tables. `0004_vault_wiki.sql` replaces the vault triggers with explicit write batches, widens the Log and vault checks, and preserves the affected sequence counters. `0010_restores_hold_library.sql` widens the unique index `restores_one_open` to the runs that hold the library. It first moves each older `failed` run with `gave-up` to `cancelled`, with `failure` cleared and `finished_at` set as every other cancel does, because only the newest run can hold the library and an older one that stayed in the index would refuse every later upload. `0011_items_guarded_in_batch.sql` drops the trigger `items_restoring` and the column `restores.writing`, because a guard in every batch that inserts an Item now refuses it while a restore holds the library (`export-backup-and-restore.md`, While it runs). After a change to `HOLDING` or `OPEN_RUNS` in `src/core/kernel/restore-standing.ts`, run `pnpm exec drizzle-kit generate`; it prints a change when the index needs a new migration. Generate the table definitions with `pnpm exec drizzle-kit generate`; custom SQL holds FTS5, its triggers, the restore insert guard, settings revision triggers, unordered-pair expression indexes and singleton seeds. Drizzle Kit 0.31.11 splits commas inside expression indexes into quoted column names, so those indexes stay in custom SQL. The deploy script applies migrations with `wrangler d1 migrations apply`; the container applies the same files at start through `src/targets/node/database.ts`. Local D1 uses `--local --persist-to <dir>` and needs no Cloudflare login. Databases from the unreleased migration chain must be recreated empty. The initial migration has a distinct name so applying it to an old database fails on the existing tables instead of skipping initialization. No build older than the one that migrated a database is supported on it.
  - **Unique index and NULL.** SQLite treats each NULL as distinct in a unique index, so two open `export` jobs with no Item are accepted by `jobs_one_open_per_item_kind`, and the partial unique index `exports_one_live` guards the one-live-export rule instead (probed on `node:sqlite` 3.53.3 and on local D1, wrangler 4.159.0).
  - **Sequences.** A restore writes the high-water mark of each `AUTOINCREMENT` counter into `sqlite_sequence` with one `UPDATE` of `max(seq, mark)` and one `INSERT ... SELECT` for a table with no row yet (the manifest's `sequences`), because `sqlite_sequence` has no unique key on `name`. Both statements ran on `node:sqlite` and on local D1 before the restore used them.
- **Consistency constraints.** The Drizzle table definitions declare row-local value and subject rules as `CHECK` constraints, with value lists built from their constants and subject-column matching in `src/core/kernel/schema-checks.ts`. A failed check rolls back its batch on both targets. `test/consistency-triggers*.test.ts` and `test/proposal-subject-tables.test.ts` exercise these storage contracts. Triggers remain where a rule reads another table or maintains derived data: the FTS5 search triggers and the settings revision triggers in `migrations/0000_schema.sql`, and the five `<kind>_proposals_gone` triggers of `migrations/0009_proposals_subjects.sql`, which delete the `proposals` row of a deleted subject row. Each subject table holds a `kind` column checked to its own kind, in a composite foreign key `(proposal_id, kind)` to `proposals(id, kind)` (the unique index `proposals_id_kind`), so a subject row of another kind and a second subject row for one Proposal fail in the database. That every Proposal has a subject row is an application rule: the batch that adds a Proposal inserts both, and the finishing slice of a Restore deletes a `proposals` row left with none. D1 refuses a statement whose trigger programs nest more than 10 levels, so a table that reaches D1 through a cascade and a trigger needs a run on local D1 (`docs/architecture/decisions-and-evidence.md`, Trigger depth on D1).
- **Search.** FTS5 external-content tables kept in step by triggers; D1 supports FTS5 (D1 docs, SQL statements). Searchable text lives in `search_parts`, one row per part of an Item. A part longer than 500,000 bytes is split into chunks of at most 125,000 characters at the last whitespace, so no word is split and no search row nears D1's 2 MB row limit; one token longer than a chunk is cut hard, which is accepted. A query matches parts and groups them by Item. Related Items candidates come from the same index, ordered by `bm25()` ascending, because a lower `bm25` score is a better match (SQLite FTS5 docs; `src/features/related/core/related-candidates.ts`; the aggregate form that fails and the measured form are in `docs/wiki.md`, Related Items). A Kept comment body is cut like a post text by `chunkPostText`. The Digest job reads the selected bodies before its batch, and Restore reads the Kept bodies of the published generation in a separate query (`keptBodies`), so no single value or bound parameter holds all of an Item's comments, which can total 4 MiB against D1's 2,000,000 bytes per string. `commentPartWrites` binds the parts as JSON arrays, so a comment of 600,000 bytes is several parts and a thread of many short comments is few statements. The app rewrites an Item's parts in the same batch as the change to that part (`src/features/item/core/search.ts`). The migration that creates the index fills nothing. Restore rebuilds the parts in its `search` phase (`src/features/restore/core/restore-search.ts`) through `rebuiltPartWrites` (`src/features/item/core/search-parts.ts`), which calls each rewrite in `src/features/item/core/search.ts`. Every rewrite deletes the kinds it replaces from `PART_GROUPS` (`src/features/item/core/search-part-groups.ts`), and a kind added to `search_parts` fails type-checking until a group holds it. A group does not make its rewrite insert the kind, so the rewrite that reads the new group still needs its insert. A stored Digest that does not parse adds no Digest parts, and the Item's titles, post text and Tags stay searchable. A search term is a run of letters and digits (the separators `unicode61` uses), matched as a quoted prefix, and the terms reach SQL as one JSON parameter; the filter counts come from the same batch as the first page of the list, so both describe one state of the library (`src/features/item/core/item-filters.ts`). An external-content FTS5 table is checked with `INSERT INTO search_index(search_index, rank) VALUES ('integrity-check', 1)`. `saveUnresolved` in `src/features/paste/core/short-link-save.ts`, the write for a short link that fails to resolve, rewrites no part, because it sets the status, the reason, the fetch result and the X note, never the title or post text.
- **Large text.** A post text over 1,000,000 bytes is stored as an object in the file store, and its row holds the key (see Files in `files.md`); the same rule runs on both targets, so no single value nears the 2 MB limit. A comment body is never stored as a file: a Paste whose thread has a comment body over 1,000,000 UTF-8 bytes is refused with a 400, and so is a post text that long. Two chosen limits keep every value and statement below D1's 2,000,000 bytes per string or row (D1 limits, https://developers.cloudflare.com/d1/platform/limits/): a title, author, subreddit, comment id, comment author or parent id over 4,096 bytes is refused, and so is a comment whose stored row, as JSON with its escapes, is over 1,499,998 bytes, which is the 1,500,000-byte statement budget less the array brackets. Both numbers are chosen, not measured or set by Reddit: 4,096 bytes is meant to sit far above any real username, subreddit or title (unsupported: no Reddit source was checked), and 1,500,000 bytes leaves 500,000 bytes of room under 2,000,000 for the statement's own text. A body of 300,000 control characters is under the body limit and over the row limit, because each escapes to 6 bytes. `GET /api/items` leaves out the post text, because about 50 rows of long text would pass the 50 MB query-result limit; `GET /api/items/:id` returns it.
- **D1 limits that shape queries:** 100 bound parameters per statement, 1,000 queries per invocation on the paid plan, 2 MB per row, 50 MB per query result (D1 docs, Limits). A list whose length the data decides is bound as one JSON parameter and expanded with `json_each`; large reads page by key.
- **Duplicate column names.** A `db.batch` select that joins one table twice, or two tables that share a column name, must name each repeated column with `sql<T>`...`.as("name")`, as `lostPage` in `src/features/wiki/core/highlight-proposals.ts` does (`id` of the Proposal, the Highlight and the Item). On `wrangler dev --local` 4.158.0 the unnamed query returned `from.id` as the tag's name and `into` as `{}`, because the D1 driver reads each row as an object and the repeated `id` and `name` keys collapse; `node:sqlite` reads rows by position and returned the right values, so the core tests cannot show this.
- **Numbers.** D1 returns numbers as JavaScript numbers, so an integer above 2^53 loses precision (D1 docs, Import and export data). X post ids are above that, so every id that comes from a Source is `text`.

Evidence, a spike on 2026-11-04 (scratch folder, not in the repo): one schema and one query module ran unchanged on `node:sqlite` (Node 26.11.1, SQLite 3.53.3), on Bun 1.4.3 (SQLite 3.53.4) and on local D1 under `wrangler dev` (wrangler 4.156.0). All gave the same results for an upsert by URL, FTS5 with porter stemming and prefix queries, triggers that follow an update and a delete, a cascade delete, and a `batch` whose second insert broke a unique index and left no row behind. D1 refuses `sqlite_version()`.
