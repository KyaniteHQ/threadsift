- Post text and comments are stored as Markdown, which Defuddle can return directly. The Reader renders Markdown without raw HTML, so other people's posts never reach the page as HTML, and the export and the Vault mirror reuse the stored text.
- **`jobs.page`.** The JSON of a page the Extension sent, owned by one open fetch job: it points to nothing and nothing points to it, and the job's own row is its identity (`id`, never reused). It is set when the save queues the job, read by the job that runs it, and cleared to null when the job ends, is replaced by a newer save, or is closed by `closeItemJobs`, so no page text outlives its job. An export carries no job rows, so it carries no page. A restore starts with no open jobs.
- A refresh re-anchors each Highlight by its quote, prefix and suffix; a Highlight whose quote is gone keeps its text and is marked as no longer found (`docs/spec.md`, Highlights and Notes; the rules are under Highlights below).

## Highlights

The Reader draws a Highlight (slice 15a2) from what the server stores here. The server side is `src/core/highlights.ts` (create, remove, the detail read), `src/core/highlight-anchor.ts` (the matcher), `src/core/text-projection.ts` (the text a quote is taken from) and `src/core/highlight-publish.ts` (publication).

**Identity.** A Highlight's id is generated (`AUTOINCREMENT`, never reused). A post Highlight names its Item. A comment Highlight names the Item and Reddit's comment id (`t1_...`), never the generation-specific row of `reddit_comments`, so it survives a refresh, a re-paste and a new Digest. Remove and deleting the Item end it. A restored library keeps the id, the target, the selector, `createdAt` and `projection`, because the restore inserts ids unchanged (Export, backup and restore). The status, the revision and `start` are derived: the restore recomputes them against the restored text, in the same way a refresh does. The export and restore code belongs to its own slices. A Highlight has no key beyond its id, so a merge of two copies of a library needs its own contract, as the Item merge does (Item identity).

**Authority.** Only the owner's session creates and removes Highlights: `isOwnerOnly` in `src/http/access-rules.ts` answers 403 to an agent token on `POST /api/items/{id}/highlights` and `DELETE /api/items/{id}/highlights/{highlightId}`. An agent token reads Highlights in `GET /api/items/{id}`. A third path removes a Highlight: Accept of a lost-Highlight Proposal, owner-only through the Proposal routes, which runs the same two statements as the DELETE route (`removalWrites` in `src/core/highlights.ts`) and holds only while the Highlight is still not found. The weekly check that proposes it writes only `proposals` rows, so nothing but the owner's Accept or Remove, or the delete of its Item, ends a Highlight, and nothing writes `exact`, `prefix`, `suffix`, `hint` or `status` but publication.

**Projection.** A Highlight quotes the text the owner reads, not Markdown. `projectText` parses the stored Markdown with `remark-parse` and `remark-gfm`, turns the tree into hast with `remark-rehype` (the same parser family `react-markdown` uses in `web/src/PostText.tsx`; the three packages are direct dependencies now, and no parser is new), and reads the text. The browser and the server call the same function. `PROJECTION_VERSION` (now 2) is stored on each Highlight; a change to a rule below changes the version. Version 2 changed how a stored picture with empty alt text projects (see the image rule below). No data step moves version 1 rows. A Highlight made under version 1 that holds a stored picture's file address in its quote, or stands after such a picture in the same body, no longer matches. It becomes `gone`, or stays `attached` at a wrong place until its Item is published again. Nothing in the repository holds such a row: the first release has not shipped, the only deployment is the `threadsift-live` copy of `main` (CI, releases and rollback, Live demo), and the Reader, the one screen that creates a Highlight, landed after the records. A data step also gets only the database (`DataStep.advance` in `src/core/data-step-contract.ts`), and the text it would have to anchor again lives in a file when it is long, so a rule change after the first release needs a step that can read files first.

- A block (paragraph, heading, blockquote, list, list item, thematic break) ends a line, and a Highlight can cross a block boundary. Blocks are joined with one `\n`; the projection has no leading or trailing newline.
- Inside a block, a run of spaces, tabs and line breaks in the source is one space. A hard break (`<br>`) is `\n`. Entities are decoded. Emphasis, strong, strikethrough and a link add no characters, so a quote can cross them; a link is its text, without its address.
- A code block is verbatim, with its whitespace and newlines, minus one trailing newline. Inline code is text.
- A table row is its cells joined by `\t`, one row per line, and the header row counts as a row.
- An image is its alt text. When the alt text is empty, a picture the app stored (an address that is a file route, `keyOfFileRoute` in `src/core/file-keys.ts`) is the single character U+FFFC, the Unicode object replacement character, and any other image is its address, shown only when `readerUrl` (`src/core/reader-url.ts`, shared with `PostText.tsx`) would show it. A stored picture's address holds the fetch attempt (`img-<job id>-<attempt>-<position>`, see Media), so a refresh of an unchanged Article stores the same picture under a new address. The quote of a Highlight that runs across the picture must not hold that address, so `pictureText` in `src/core/reader-url.ts` is the one rule that the server, the marking tree and the DOM adapter all call, through `imageText` in `src/core/text-projection.ts`.
- A task-list checkbox adds nothing. A footnote call, a footnote back-link and the footnotes heading add nothing; the footnote text stays in its place at the end.
- Raw HTML in the Markdown is literal text, because the Reader uses `react-markdown` without `rehype-raw`, so `<b>x</b>` projects as those seven characters. Reader controls and generated text (fold buttons, labels) are not in the projection.

**Selector and matcher.** The selector follows the W3C Web Annotation `TextQuoteSelector` ([section 4.2.4](https://www.w3.org/TR/annotation-model/#text-quote-selector)): `exact` and up to 32 code points of `prefix` and `suffix`, cut at the edges of the target. `hint` is the place of `exact` in the projection of the revision it was made on. Offsets are in code points, so a browser and `node:sqlite` or D1 agree on text with emoji. What I took from Hypothesis's client (`src/annotator/anchoring/` in `hypothesis/client`): the 32-character context, and choosing between several matches by how much of the stored prefix and suffix each one shares. What differs: the quote must match exactly, with no fuzzy search; and `hint` is checked once, when a Highlight is created, and never ranks matches after that, because a position moves with every edit. `anchorIn` finds every occurrence of `exact` in the new projection. None means `gone`. One means `attached`, whatever its context. Several are scored by the number of whole code points of the stored prefix that end where the match starts plus the number of whole code points of the stored suffix that begin where it ends (never UTF-16 units, so two different emoji that share a surrogate half score nothing); the single best score attaches, and a tie for the best score means `ambiguous`, never the first one. A create is checked by `selectorHolds`: `exact` must stand at `hint`, with exactly the stored `prefix` and `suffix` around it.

**Revisions and the create.** `GET /api/items/{id}` returns `highlights`: `revisions.post` (the Item's content generation, which a refresh or a new post text changes), `revisions.comments` (the generation of the thread the Reader shows, which can be older than the newest fetched one while a Digest is pending; null without a thread) and every Highlight with its status and the current revision of its target. `POST` takes the target, the revision the owner read and the selector. It reads the Item, the comment body and the Highlight of the same passage in one batch, then the post text file if the Item has one. One guarded batch (`guardedWrite`) inserts the Highlight with `RETURNING` and adds its search part, and its guard holds only while the target still has that revision and no attached Highlight of the same passage exists, so two identical creates sent at once save one row and the second one is answered again from the start (it finds the saved row). The response names the row that `RETURNING` gave, never a row found by its anchor, which a publication can move. A failed guard that leaves the revision changed answers 409; a selector that does not hold in the text of that revision answers 400; the same passage of the same revision answers 200 with the saved Highlight. `DELETE` removes the Highlight's search part and then the row in one batch, and answers 404 when no row matched both ids.

**Publication.** Every path that changes the displayed text (`attemptFetch` in `src/core/fetch-attempt.ts` when it replaces content, `publishThread` in `src/core/thread-save.ts` for a supplied or stored thread, and `publishing` in `src/core/digest-publish.ts`) gives `anchoredOutcome` (`src/core/highlight-publish.ts`) its plain writes and the text it displays. `anchoredOutcome` reads a snapshot of the Item's Highlights, computes the new places from the new text (`anchorWrites`, which projects each text once per publication), appends them to the writes and sets a precondition on the batch: the Item's ordered list of Highlight ids is the one in the snapshot, and, for a thread save, a published Digest generation still exists or still does not. An Item that does not exist yet is a snapshot too, with no Highlights: its precondition is that no Item has the address, so a Highlight on an Item that another publisher created in the meantime is never overwritten unchecked. Ids are never reused, so an equal list means no Highlight was created or removed. A job's batch also carries its own guards (`holding`, `generationCurrent`). When the precondition fails, the publisher calls `rebuild`, which reads a fresh snapshot and recomputes the places against the same fetched text or the finished Digest. It never fetches again and never calls the Provider again, and the loop costs no job attempt and raises no error: a retry needs a Highlight created or removed since the last snapshot, each retry is one read and one batch, and the loop ends when the owner stops changing Highlights. `publishThread` learns whether it created the Item from the `RETURNING` of its Item insert in the guarded batch that commits. The fetch takes its snapshot after the network work and only when it replaces content. A caller Digest takes it in the same batch as the Digest input, and a model Digest takes it after the model returns. A Highlight created between the snapshot and the commit is therefore checked against the published text.

**Comments.** A comment of the displayed generation that holds an attached Highlight is readable even when the Digest no longer keeps it: `threadRows` in `src/core/thread-read.ts` joins the comment ids of the Item's attached Highlights and marks a row `readable` when it is Kept or holds one, and `commentsViewOf` shows a readable comment with its author, body and ancestors' stubs. `kept` and the Kept count are not changed, and nothing is stored for the retention, so no write can leave it stale. When the comment is not in the new generation, or its body no longer holds the quote, the Highlight is `gone` (or `ambiguous`) and keeps its quote; when a later generation has the quote again, the same id is `attached` again.

**Search.** One `search_parts` row of kind `highlight` per Highlight holds the exact quote and references the Highlight in `search_parts.highlight_id` (nullable, with a unique index, so a Highlight has at most one part and the other kinds have none). The create adds the part in its batch; the remove deletes the part before the row, because the reference has no cascade (a migration cannot add the action to a column with `ALTER TABLE` through `drizzle-kit`, see Migrations in `database-and-search.md`). The parts stay while the Highlight is unattached, so an Item stays findable by a quote its text no longer has, and a publication never rewrites them, because it changes only the Highlight's status and `start`. Two Highlights with the same quote have two parts that differ by `highlight_id`, so a hit maps back to its Highlight. The reconciler's fingerprint does not include Highlights, so a create or a remove never makes it reindex the Item. A separate check compares each Item's Highlights with its `highlight` parts row by row (every Highlight has a part with its quote, and every `highlight` part has a Highlight with that quote), without joining the quotes into one value, because an Item's quotes can total more than D1's 2,000,000 bytes per string, and the check must not fail the page query that all Items of the sweep share. When the check fails it deletes the parts that match no Highlight and adds the missing ones (`highlightPartWrites`).

**Deleting.** `deleteItem` deletes the search parts and then `highlights` in the same batch as the other Item-owned tables (Deleting an Item), in that order because `search_parts.highlight_id` references `highlights`.

**Highlights in the Reader.** The Reader (slice 15a2) selects, draws and lists Highlights with the browser's own selection and no storage of its own: every Highlight is a row from `GET /api/items/{id}`, and the page edits its copy of `highlights` (`editHighlights` in `web/src/use-item-detail.ts`) after the server answers. Every edit counts, and a detail read that started before an edit is dropped and read again, so a slow read cannot undo a Keep or a Remove. `useHighlightWrites` (`web/src/Highlights.tsx`) sends the Keeps and Removes of one Reader one at a time, so a late answer to an earlier Keep cannot bring back a Highlight a later Remove took away.

- **Projection in the page.** `web/src/dom-projection.ts` turns the rendered `.md` element into the hast shape that `projectTree` (exported from `src/core/text-projection.ts`, the function `projectText` is built on) reads, so the page and the server run one projector over three trees: the server's Markdown tree, react-markdown's own tree inside the marking plugin, and the DOM. The pieces of a projection carry the text node and the range of it each piece comes from, which maps a DOM range to code point offsets (`spanOf`) and an offset back to text (`web/src/highlight-marks.ts`). `selectorAt` (`src/core/highlight-anchor.ts`) builds the selector from those offsets with the same 32 code points of context the server checks with `selectorHolds`, and the offset goes along as `hint`. A picture with empty alt text that failed to load is a link labelled with its file address, which the server projects as one placeholder character. `Picture` marks that link with `data-failed-picture`, and the adapter reads it as an image without text, so the page projects it as the server does and a selection that starts or ends outside the label stays eligible; a selection wholly inside the label does not. The renderer drops the last newline of a code block before it draws it (`codePartsOf` in `web/src/PostTextComponents.tsx`), and the server's code text always ends with one that the projector drops again, so the adapter adds that newline back to each `pre`; a block that ends in a blank line then projects as the server's does. Offsets count code points, as the server's do; the parser and the projection load as lazy chunks, and `web/src/highlight-draft.ts` is imported only when the owner selects something.
- **Eligible selections.** One non-empty contiguous passage inside one `.md[data-target]` body (the post text, or one Kept comment, whose key is `post` or the comment id) is eligible. A selection across two bodies, one that touches a control or a Context stub, or one that is only whitespace is not, and the popover stays closed. `useSelectionDraft` (`web/src/use-selection-draft.ts`) reads the selection 150 ms after the last `selectionchange` and not while a pointer is down. 150 ms is a chosen value: it is long enough that dragging a handle on a phone does not reopen the popover on every step and short enough that Tab reaches the button right after a keyboard selection; it is not measured. The selector and the revision of the target are saved in the draft before focus moves, so the save sends what the owner saw even when a refresh lands in between.
- **Marks.** `markPlugins` (`web/src/highlight-marks.ts`) is a rehype plugin that runs inside `react-markdown` before it turns raw nodes into text, splits the text nodes that hold a Highlight, and wraps the parts in a `mark` element with `data-highlights` (the ids, separated by spaces when Highlights overlap). `Mark` (`web/src/Mark.tsx`) renders it with `tabIndex={-1}`, so a script can focus it and the Tab order does not change. A code block gets its parts as children of `code`, and an image that stays a link is drawn as a link to its source whose text is its label (`imageText`, the alt text or the address), so a passage that covers part of the label marks only that part. A stored picture of the open Article (Showing images) stays a picture: the plugin gives the `img` node the ids in `data-highlights` instead of wrapping it, and `Picture` (`web/src/StoredPicture.tsx`) draws the `mark` inside its `.rd-media` wrapper, so two adjacent pictures stay siblings and `.md .rd-media + .rd-media` keeps their gap. The whole picture is marked, whatever part of its alt text the passage covers. `web/src/dom-projection.ts` reads the `alt` and `src` of each `img` it finds, so the page's text matches the server's. The CSS Custom Highlight API is not used: `docs/agents/changing-code.md` asks for Baseline Widely available features and the API is Newly available, and wrapping React-owned text nodes from outside React breaks the next render. `.md mark[data-highlights]` in `design/system/components.css` uses tokens only, with an underline in every mode and, under `forced-colors: active`, the `Mark` and `MarkText` system colours.
- **The popover.** `HighlightAction` (`web/src/HighlightAction.tsx`) renders a `popover="auto"` element right after the body it belongs to, so it sits inside the Grid sheet's dialog and stays interactive there. `popover="auto"` gives light dismiss and Escape through the browser's close watcher, and the element sits in the top layer at fixed coordinates, which `placePopover` (`web/src/place-popover.ts`) sets from the selection's client rects and the visible box (the viewport cut by every scrolling ancestor, the dialog and the Reader bar; the ancestors, the bar, the pointer type and the gaps are read once when the popover opens, and each scroll frame reads only rects), above the first line, or below the last line when the pointer is coarse, because a phone's own selection menu sits above the selection (not checked on a device). The popover holds one native button, Keep, or Remove when the owner clicks a mark with no selection. It has no `role="menu"`; the two buttons carry `aria-label`s from `KEEP_GROUP` and `REMOVE_GROUP`. A selection change never moves focus, and the keyboard path is a selection by keys, then Tab: the browser starts sequential focus at the selection, and the popover follows the body in the DOM. A user-driven selection is needed for that start point; one made by a script does not give it. In the Grid sheet the open dialog holds focus, so the browser starts at the dialog and Tab reaches Keep after the controls that come before the body. Shift with an arrow key extends the selection and is not a library key (`use-library-keys.ts`), so Grid does not open the next Item. Clicking a mark with the primary button and no modifier opens Remove and cancels the click, so a marked link does not open; a click with a modifier, or Enter on the link, follows the link and opens nothing (`use-highlight-panel.ts`). Under 480 px a mark gets padding and an equal negative margin (`.app[data-bp~="phone"] .md mark[data-highlights]`) that make its hit area `--target` high and wide without moving the text, and `background-clip: content-box` keeps the tint on the text. `[popover]` is in `TYPING` in `web/src/use-library-keys.ts`, so a library key typed with the button focused does nothing, and its Escape branch checks any `:popover-open`, so Escape closes the popover and leaves the Reader open.
- **The list.** `HighlightList` (`web/src/HighlightList.tsx`) is the last section of the Reader and lists every Highlight of the Item, attached or not. An attached entry is a button that scrolls to its mark and focuses it. An entry whose quote is gone shows the quote and `NOT_FOUND` and has no such button. Remove is a native button named after the quote (`removeNamed`), and after a successful removal focus moves to the Remove button of a neighbouring entry, or to the Reader title when the list is empty; a failed removal leaves focus on its button. A failed keep or remove shows its message in a `role="alert"` line, and so does a selection module that fails to load (`SELECT_FAILED`, with a Try again button that reloads the page, since a browser keeps a failed module import for the life of the document; while the module is failed, the line carries that button under a keep or remove message too); a keep that meets text changed by a refresh (the server answers 404 or 409) shows `KEEP_STALE` and reloads the Item.
- **Reveal.** Choosing an entry whose passage sits in a folded comment or a folded code block opens it: `useOpenOnReveal` (`web/src/highlights-context.ts`), which `CodeBlock` and the comment fold share, sets the open state while rendering (React's "adjust state during render" pattern), and a layout effect (`useReveal`) then scrolls to the mark and focuses it with `scrollAndFocus` (`web/src/jump-to-comments.ts`), which owns the reduced-motion rule.
- **Announcements.** `KEPT_ANNOUNCEMENT` and `REMOVED_ANNOUNCEMENT` go through the Reader's own announcer (`announce` in `ReaderControls`, the live region `Announcement`, which sits inside the Sheet's dialog while a sheet is open because a modal dialog makes everything outside it inert, and in `Library.tsx` otherwise), after an empty announcement so a repeat is read again; the visible failure line is separate.
- **Not verified.** The phone's own selection menu (iOS Safari, Android Chrome), the reading of the popover by a screen reader, and Firefox and WebKit.

## Media

`media` (`src/core/media-tables.ts`) holds what the fetch job found in an Article besides its text: one row for each image and each video. The Reader draws a stored image from its file route, and the list and status answers carry the first one (Showing images).

**Identity.** A row's id is generated (`AUTOINCREMENT`, never reused). Within an Item a row is matched by its kind and its source URL (`media_item_source` is unique on `(item_id, kind, source_url)`): the address after Defuddle resolved it against the page and its `<base href>`, with the fragment and any credentials removed, the query kept, and no Item URL normalization, because a query can choose the picture. A base64 `data:` image has no address, so its source is `inline:sha256:<hex digest of the whole data URL text>`: the same bytes in the same encoding are one row. A row's file key is unique and belongs to one attempt (`items/<id>/img-<job id>-<attempt>-<position>.<ext>`, where `imagePrefix` of `attemptFileKeys` in `src/core/file-keys.ts` builds the part up to the position), and no key is written twice. The type is the extension.

**Events.**

| Event | What happens to the rows |
|---|---|
| Refresh that still finds the image | The row keeps its id and moves to the attempt's new file key and alt text; the file of the old key goes after the publish. |
| Refresh that no longer finds it | The row is deleted in the publishing batch, and its file goes after the commit. |
| Refresh that finds an image for the first time | A new row with a new id. |
| Failed refresh, or a result that publishes no content | Rows, files and text stay as they were. |
| Refresh with no images, or a change to Other | Every row of the Item is deleted and every file goes. |
| A thread published over the Item (a Paste with `content`, or a fill; `threadPublication`) | Every row of the Item is deleted in the publishing batch, and the cleanup pass removes the files that no row names. |
| Delete of the Item | `deleteItem` deletes the rows (Deleting an Item) and the prefix delete removes the files. |
| Export and restore | Not built. The export carries the ids, the file keys and the video URLs, and rewrites file-route links in the text to relative paths, so a restore keeps every row and link. |
| Merge of two copies | Not built. Two Items never share rows, because the match key holds `item_id`. |

**Alt text.** `alt` is the alt text of the first place the text shows the image, with runs of whitespace collapsed, trimmed and cut to 300 characters (`ALT_MAX` in `src/core/article-images.ts`, a chosen limit). It is `''` for a video, a failed image, and a stored image saved before the column existed: no data step fills it, so such an Item shows its card picture with an empty alt text until the next refresh, the same rule as for short-link aliases.

**Dimensions.** `width` and `height` are the pixel size the browser draws, read from the stored bytes by `imageSize` (`src/core/image-size.ts`) and `NULL` for a video, a failed image, a file whose header the reader does not understand, and a stored image saved before the columns existed (no data step fills them; the next refresh does). The reader covers PNG, GIF, JPEG (the first start-of-frame marker of any kind, progressive included, and an EXIF orientation of 5 to 8 swaps the two), WebP (`VP8 `, `VP8L` and `VP8X`) and AVIF (the `ispe` and `irot` properties that `ipma` associates with the primary item `pitm` names, and an odd `irot` angle swaps the two; `imir` and a `clap` crop change nothing, as in Chromium). It is about 220 lines and adds no dependency. `image-size` 2.0.2 (MIT, no dependencies) covers the same five formats, but its GitHub repository is archived, the repository's release-age policy blocked its newest release when checked, and it reads JPEG frames 0 to 2 only, so a package would be added for a hint. The values only reserve space (see Showing images), so a wrong or missing one costs a layout move, never a wrong picture. The values were checked against the size Chromium decodes for 11 files of the five formats (lossy, lossless and animated WebP, two AVIF files, a JPEG with EXIF orientation 6) and for 11 AVIF files from `avifenc` 1.4.2 (rotations 0 to 3, a mirror with a rotation, an alpha plane, a 2x2 grid with and without a rotation, a `clap` crop, and two grids patched so that the first `ispe` belongs to a tile).

**What a row says.** `kind` is `image` or `video`. `outcome` is `stored` (an image with a file), `failed` (an image with no file and a `reason`) or `linked` (a video, which is never downloaded). Three `CHECK`s hold that: a video is `linked` and only a video is, a `failed` row has a reason and no other row has one, and a `stored` row has a file key, a type and a size and no other row has them. `reason` is one of `MEDIA_FAILURES` in `src/core/kinds.ts`: `timeout`, `network`, `refused` (an address the guard refuses), `unsupported`, `redirect-limit`, `status`, `too-large`, `not-an-image` and `type-mismatch`.

**Extraction.** `readArticle` (`src/core/article.ts`) runs `replaceMedia` (`src/core/article-media.ts`) on the linkedom document first: a `video` element's HTTP(S) `src` and `source` URLs become links in place and video rows, a `iframe` of a provider `embedLinkOf` (`src/core/embed-links.ts`) knows, matched by exact host name, becomes the provider's watch-page link and a video row (YouTube and Vimeo are videos, an X post is a link only), and `audio` and any other `iframe` become plain links with no row. Then Defuddle 0.19.6 runs with `separateMarkdown: true`, which returns the Markdown in `contentMarkdown` and the video list is kept only for the links that survive its cleaning (`retainedVideos`). Defuddle resolves relative URLs, `<base href>`, `srcset` and `picture` and reads the lazy-loading attributes it knows. Defuddle converts to Markdown only inside `Defuddle()`: `node --input-type=module -e 'const m = await import("defuddle/full"); console.log(Object.keys(m).join(), typeof m.createMarkdownContent)'` prints `Defuddle,default,module.exports undefined` at 0.19.6, so no separate converter exists to call on a cleaned DOM, and the job takes `contentMarkdown`.

**Which images.** `readArticle` finds the image nodes of the final Markdown with `remark-parse` and `remark-gfm` (`scanMarkdown` in `src/core/markdown-images.ts`), reference-style images included, never with a regular expression, so a code sample and an ordinary link stay as written, and returns them with their offsets. It does so inside the page reader and not in the job, because parsing the 3.2 MB War and Peace text took 1,098 ms on the event loop (Node 26, 2026-11-09), and another Item's read then took 1,112 ms against a 1,000 ms bound. `prepareMedia` (`src/core/article-images.ts`) takes the first 20 distinct sources in text order, downloads at most 2 at once, and rewrites each stored image's node to the file-route path. A failed image, or an image past the 20, keeps its source address as the image destination. A `blob:`, `file:`, script, fragment-only or empty destination becomes its alt text, and so does an inline image that failed. An embed that Defuddle wrote as an image (`![](youtube...)`) becomes a link before any download.

**Caps.** 20 images for each Item, 2 MiB for each image (decoded for a `data:` URL, whose payload is percent-decoded and stripped of base64 whitespace before the size is checked, and whose raw text is refused above three times the base64 length of 2 MiB before anything is decoded), 2 downloads at once, 4,096 bytes for an address, 20 videos, and the fetch job's one 120 s deadline for the page, the extraction and every image. The per-hop 8 s deadline and the 20-redirect limit of the guard apply to each image. These are chosen product limits, not Cloudflare limits.

**Formats.** JPEG, PNG, GIF, WebP and AVIF, where the declared `Content-Type` and the bytes agree. `sniffImageType` (`src/core/image-type.ts`) checks the signatures of [WHATWG MIME Sniffing](https://mimesniff.spec.whatwg.org/#matching-an-image-type-pattern) section 6.1 and the AVIF brand (`avif` or `avis` in the `ftyp` box). SVG, HTML, XML, PDF, an unknown type and a mismatch stay links (`not-an-image`, `type-mismatch`). `docs/spec.md` (Fetchers, Media) states this raster-only rule; the owner decides whether SVG is worth the script risk.

**Fetching.** `guardedFetchBytes` (`src/core/fetch-guard.ts`) is the guard's byte-level traversal, and `guardedFetch` decodes its result for pages. `src/core/image-download.ts` gives it an image policy: it refuses a Reddit or X link as the first address, before any request, and stops at one in a redirect, follows no meta refresh, sends no owner credential, agent token or GitHub token, and reads at most 2 MiB; an oversized body is cut and reported as `too-large`, and every rejected body is consumed or cancelled.

**Publication.** The files are put before the guarded `db.batch()` that publishes the text, the media set (`mediaWrites` in `src/core/media-writes.ts`: one delete of the rows the attempt did not find and one insert-select from a single JSON parameter, because D1 allows 100 bound parameters per statement), the search parts, the generation and the job's completion. A `put` that fails is a failed attempt (the job retries), not an image failure, and the files it wrote go to the cleanup pass.

- **Reader.** `PostText` (`web/src/PostText.tsx`) draws an `img` for a Markdown image only when `ReaderOriginal` passes it the Item's id, which it does for the post text of every Item whatever its Source (a Reddit page stores pictures like an article), and `isImageRouteOf` (`src/core/file-keys.ts`) says the destination is an image file route of that Item. A comment and an image of another Item stay a link, or the alt text when the destination is not a link. The `img` is `loading="lazy"`, keeps its alt text and title, and sits in `.rd-media` (`design/system/components.css`): the picture treatment, at most `--media-max` tall and never wider than the reading column or stretched past its own width. An `img` that fails to load becomes the same link as a failed image: its alt text, or the address when the alt text is empty. The detail answer carries `images`, the `{ url, width, height }` of each stored image that has dimensions (`sizedImageRows` in `src/core/post-text.ts`), and `PostText` sets `width` and `height` on the matching `img` and an inline width of at most `--media-max` times the aspect ratio, so the browser reserves the box before the bytes arrive and a late image does not move the paragraphs below it. A failed image, one past the 20 and an SVG are links to their source from the fetch job on, so the browser makes no request for them.
- **List and Grid.** `itemView` (`src/http/item-view.ts`) adds `image`, `{ url, alt }` or `null`, to every Item answer. `IMAGE_VIEW_COLUMNS` (`src/core/joined-view.ts`) reads it as the stored image with the lowest `position`, which is the first one in the text, and `fileRouteOf` writes its `url`. `ItemRow` draws it in `.it-media` (`design/system/components.css`: a 40 px thumbnail in List, a 16 / 10 top of the card in Grid, cropped to the top-left corner); the URL comes from a stored file key (`imageOf` in `src/http/item-image.ts`), so the row does not check it again, unlike the Reader, whose post text is untrusted Markdown. ## The Note

The owner's one free-text Note per Item (slice 15b). The server side is `src/core/notes.ts` (save, the detail read), `src/core/note-contract.ts` (the schemas and the cap) and `src/http/note-routes.ts`. The Reader side is `NoteBox` (`web/src/NoteBox.tsx`) and `useNote` (`web/src/use-note.ts`).

**Identity and revision.** A Note has no id of its own. `notes.item_id` is its primary key and a foreign key to `items.id` with `ON DELETE cascade`, so an Item has at most one Note and the Note follows `items.id` through an edit, a clear, a refresh, a re-paste, a new Digest, a change of the Item's `normalized_url` (the `item-identity` step keeps the id) and an export and restore that keeps ids (Export, backup and restore). Deleting the Item ends it. Two copies of a library that both have a Note on one Item need their own merge contract, as the Item merge does.

`revision` counts the Note's writes. No row means revision 0, the first save writes 1, and every accepted write, a replace or a clear, stores the revision it named plus 1. A clear keeps the row with a null `body`. The revision never resets while the Item exists, so a save made before a clear is still stale after it. `created_at` is the first write and `updated_at` the latest.

**Write.** `PUT /api/items/{id}/note` takes `{ body, revision }`. `saveNote` runs one `guardedWrite` batch (Database and search, Guarded batches) whose guard holds while the Item exists and the stored revision, or 0 for no row, equals `revision`. The batch upserts the row, then replaces the Note's search part from the stored row (`notePartWrites` in `src/core/search.ts`), and the route answers the row the batch returned. When the guard fails, a second read answers 404 for a missing Item or 409 with the current Note and revision, and nothing was written. A `body` that is empty after `trim()` clears the Note. Any other body is stored as sent: plain text, never read as Markdown or HTML, up to 10,000 code points and well-formed Unicode (`NOTE_MAX_CODE_POINTS`). The cap is chosen, not measured: 10,000 code points are at most 40,000 bytes in UTF-8, far under D1's 2,000,000 bytes per row (D1 limits, https://developers.cloudflare.com/d1/platform/limits/), and the 64 KiB request cap still holds a body of 10,000 control characters escaped as `\u00XX`.

**Authority.** `isOwnerOnly` covers `PUT /api/items/{id}/note` only, so an agent token gets 403 on it. `GET /api/items/{id}` returns `note: { body, revision }` from the batch that reads the rest of the detail, to the owner and to an agent token alike.

**Search.** One `search_parts` row of kind `note` per nonempty Note, with a null `highlight_id`. The write replaces it in the Note's own batch, so a replace never leaves two parts and a clear leaves none. The reconciler's fingerprint does not include the Note. A separate check per Item (`notePartHolds` in `src/core/search-reconciler.ts`) compares the count and bodies of its `note` parts with the stored Note, and when they differ the reconciler runs `notePartWrites`, which deletes the Item's `note` parts and inserts the one the stored Note needs in a single batch. That batch reads the Note when it runs, so it cannot put an older Note over a save that landed after the check, and it touches no part of another kind.

**Refresh and delete.** A refresh, a Digest and an agent's update name no statement on `notes`, so none rewrites a Note. `deleteItem` deletes the row, a cleared one included, in the batch of the other Item-owned tables (Deleting an Item).

**Later consumers.** The export puts the Note in the Item's Markdown and its row in `threadsift.json`, and the Vault mirror queues the Item's path in the same batch as a Note change. Neither is built.

**The Note box.** `NoteBox` is the section after the Highlights list. `useNote` keeps the Note the page last knew (`saved`, read from `GET /api/items/{id}` when the Reader mounts and replaced only by a save answer or by the owner taking the newer one) apart from the text in the field (`draft`). A later detail read never replaces either, so a refresh of the Item cannot move text under the owner. One save is in flight at a time. The Save button, and Ctrl or Cmd with Enter in the field, send `draft` with `saved.revision`. The answer replaces `saved`, and text typed while the request was in flight stays in the field. A 409 shows the newer Note beside the owner's text with two buttons: Keep mine sends the same text again with the newer revision and may be refused again, and Use newer version replaces the text with the newer Note. A request that fails, or answers anything else, shows a failure line and keeps the text. A draft over 10,000 code points cannot be sent (`Array.from(draft).length`, because a field's `maxLength` counts UTF-16 units). Library keys ignore `textarea` (`TYPING` in `web/src/use-library-keys.ts`), and Escape in the field only leaves it, because a native `dialog` otherwise closes the Grid sheet on Escape and drops the draft.

**The kept draft.** A draft that differs from `saved` is kept in the browser's `localStorage` under `threadsift.note-draft.<items.id>` (`web/src/note-draft.ts`), with the revision it was typed against, so closing the Reader, opening another Item, a reload and a second tab of the same browser all show it again as unsaved text. The key follows `items.id`, so a refresh, a clear and a new Digest keep it, and a save sends the stored revision: a Note that changed elsewhere meanwhile meets the 409 state on that save. The draft is removed when `draft` equals `saved` and no save is in flight (after a save, after Use newer version, or after an edit back to the saved text) and ignored at mount when it equals the Note the detail returned. While a save is in flight the draft stays, even when it equals the old `saved`, because an unmounted Reader never sees the answer: text typed back to the old Note then returns on reopening. The draft also records the text and revision of that save (`sent`). When the Reader opens and the detail's Note holds that text at the next revision, the save committed, so the draft takes the detail's revision and a save from it does not meet the 409 state; a Note that differs in any other way does. Use newer version does nothing while a save is in flight. Deleting the Item from this browser removes its draft (`useDeletion`). The draft is per browser, not per device, and one slot per Item. A tab that sees another tab write the slot (the `storage` event) takes that draft and its revision as its own unsaved text and does not write it back, so two tabs that edit the same Item converge on the text typed last and neither loses the other's words. An Item deleted elsewhere leaves its draft in `localStorage` unused, because ids are never reused.

## The Highlights page

The page that lists every Highlight and Note of the library (slice 16). The server side is `src/core/highlights-page.ts` (the query), `src/core/highlights-page-contract.ts` (the entry schema, the page size and the cursor), `src/http/highlights-page-route.ts` and `src/http/highlights-page-schemas.ts`. The web side is `HighlightsPage` (`web/src/HighlightsPage.tsx`), `useHighlightsPage` (`web/src/use-highlights-page.ts`), `HighlightEntry` and `web/src/place.ts`.

**Stored data and identity.** The page stores nothing: no table, no stored reference, no migration. An entry is a row of `highlights` or of `notes` read with its Item. It is named by its `kind` and its `id`, which is the generated Highlight id (never reused) or the Item id for a Note (the Note's primary key, see The Note). A link to an entry, `/items/<id>?highlight=<highlight id>` or `/items/<id>?note`, therefore survives a refresh, a re-anchor, a new Digest, an edit of a Note and an export that keeps ids, and ends with the Highlight or the Item, when the Reader opens with no place to go to.

**The read.** `GET /api/highlights` answers `{ entries, next, counts }`. `entries` holds at most 50 entries (`HIGHLIGHTS_PAGE_SIZE`), newest first. A Highlight is dated by `highlights.created_at`, a Note by `notes.updated_at`, and a cleared Note (null `body`) has no entry. Each entry carries `kind`, `id`, `text` (the quote, or the Note), `date`, `found` for a Highlight (false when its status is not `attached`, so a refresh that removed its passage shows) and `item`: the Item's id, Source, title (the Digest's clean title, else the fetched one) and saved date. An agent token with the `read` scope may read it: `isOwnerOnly` (`src/http/access-rules.ts`) does not match `/api/highlights`, and `requiredScope` gives every `GET` `read`.

- **Filters.** `source`, `topic` and `tag` mean what they mean in `GET /api/items`: `itemFilters` builds them and `itemConditions` applies them to the entry's Item, with the same `catalogKey` rule for Topics and Tags. `q` is different. Its words, each a prefix as in the Library search, must all be in the entry's own `search_parts` row (`partMatching` in `src/core/search.ts`: the Highlight's part by `highlight_id`, the Note's part by `item_id` and kind `note`), so a word of another Highlight, of the Note of the same Item, or of the Item's title, Summary or Tags finds nothing.
- **Order and cursor.** Two selects, one over `highlights` and one over `notes`, are joined to the Item and combined with `unionAll`, then ordered by `(date desc, kind desc, id desc)` and cut at 51 rows. The cursor is `<date>.<kind>.<id>` (`formatCursor`, `parseCursor`); the next page asks for the rows below it by row-value comparison, `(date, kind, id) < (?, ?, ?)`, so a read depends on the position named and not on a row that still exists. Clearing the Note a cursor names leaves the next page as it was. A Highlight kept between two reads is newer than every cursor, so it shows at the top of a new read and moves no later page: no repeat and no gap. A Note saved again between two reads of one run moves to the top: a run that is already below the top does not see it, and the next read from the first page does. A cursor that is not of that shape, or holds a number above 9007199254740991, is a 400. A well-formed cursor that no page gave is accepted and answers the entries below that position, because the cursor holds the position and no record of the pages that were served.
- **Counts.** `counts.total` is the number of entries in the library (Highlights, and Notes with a body) and ignores every filter. `sources`, `topics` and `tags` give, for each choice, the number of entries it leaves with the search and the other groups applied, and a group ignores its own filter, as in `GET /api/items`. They run the same `facetQueries` as the Library's counts, with a `Unit` that counts an Item's matching entries (two correlated counts) in place of `count()`, and the search terms go into that unit and not into the Item's conditions. The Library's own counts are unchanged.
- **Cost.** There is no index on `highlights.created_at` or `notes.updated_at`, so a page sorts every matching entry; this is not measured.

**The page.** `/highlights` is the `highlights` screen (`web/src/screens.ts`), reached from the Highlights link in the settings panel, beside Instance settings (`PageLinks` in `web/src/PageLinks.tsx`, so from the masthead's gear in List and Grid and from the Reader bar's gear), or by its address; Back returns to `/`. The link is not a control of its own in the masthead row, because a second 44 px control there made the masthead scroll sideways at 1440 px in the mono Font at Small text size and Compact density, and moved the gear. It has the Library's search box, Source, Topic and Tag filters (`SearchField` and `FilterPane` with the Read group left out, because an entry has no read state of its own) and its keys (`j`, `k` and `/` through `useLibraryKeys`; Escape in the search box moves to the first entry). `useHighlightsPage` reads the first page again whenever the filters change and drops an answer that is not the latest request's. Load more sends `next` and appends the entries; the focus moves to the first new one, and a Load more that fails ends that wait, so a later change of the rows never moves focus (`useFocusNewRows`, `web/src/use-focus-new-rows.ts`), the counts of the head are the latest answer's, and a failed Load more keeps the entries and offers Try again. The first read has loading, empty (no entries at all) and failed (Try again) states, and "no match" offers Clear search and filters and hides the filter pane's Clear filters link. A Highlight kept across a stored picture with empty alt text holds `STORED_PICTURE_TEXT` (U+FFFC, `src/core/reader-url.ts`) in its `exact` text where the picture was, so `QuoteText` (`web/src/QuoteText.tsx`, used by `HighlightEntry` and by the Reader's `HighlightList`) draws each one as an inline sunk-surface chip with the picture icon, named `PICTURE_LABEL` ("Image", `web/src/reader-text.ts`) for assistive technology (`role="img"`), and the entry link's description reads that name with the quote. `removeNamed` writes the same name where the Remove button's label holds the character. A Note is plain text and never gets a chip.

**Arrival.** An entry is a link whose whole row is the target (`.hp-open` stretched over its article). It goes to `placePath`: `/items/<id>?highlight=<id>` or `/items/<id>?note`. `usePath` keeps only the path in its state and leaves the query in the address, and `arrivalPlace` (`web/src/place.ts`) reads it. `ReaderPane` holds one `Arrivals` ledger (`web/src/place-arrival.ts`) above the Sheet and page subtrees, which remount each other when the width crosses the narrow breakpoint, and each part takes its arrival from it once for each address and kind. `useReveal` (`web/src/use-reveal.ts`) calls `show` for an attached Highlight, which opens a folded comment or code block and focuses the mark through the reveal above, and focuses the list entry of a Highlight that is not found. `NoteBox` focuses its field. `watchPlace` (`web/src/use-reading-place.ts`) does not restore the saved reading place while the ledger still holds the arrival: the restore set the scroll again after the arrival had scrolled, and a second visit to the same Item stopped at the saved place (scrolled to 11 px in a debug run, with the mark 1,631 px down). After the arrival is taken, a remount restores the place the reader had reached, and does not arrive again. The address keeps its query, so a reload arrives again.

## Item identity

`items.normalized_url` is the only identity of an Item, and `parseLink` in `src/core/links.ts` writes it. `parseLink` gives the identity of an identity as itself, so the data step, a Paste of a stored identity and a Paste of the link it came from reach the same Item. It reads the link once with constant stack and linear time: `canonicalHost` removes every trailing dot, every leading `www.` that leaves a dot in the host and a `mobile.` in front of `x.com` or `twitter.com`, in any order, and `withoutGitSuffix` removes every `.git` from a repository name. `hostOf`, `redditRefOf` and the predicates `isRedditOrXLink` and `isGitHubLink` call the same `canonicalHost`, so a fetch, a supplied page and `parseLink` agree on which Source a spelling belongs to (`www.mobile.x.com` is X and `www.www.github.com` is GitHub for all of them), and a fetch still sends the pasted address. A repository name of 12,000 `.git` suffixes normalizes in a few milliseconds. A generic link keeps its scheme and case, loses its fragment, credentials, a trailing dot on the host, a `www.` prefix and the tracking parameters (`utm_*` and the others in `TRACKING_PARAMS`), so `http` and `https` stay two Items. Four rules are named exceptions, each for a Source whose service gives one thing one id:

- **X.** A post's identity is its status id, written as decimal text without leading zeros: `https://x.com/i/status/<id>`. The hosts `x.com` and `twitter.com` (with `www.` and `mobile.`), any handle spelling, `/i/status/`, `/i/web/status/`, a media or quotes suffix and any query give the same identity. The id stays text because X ids pass 2^53. A reply or a quote post has its own status id and is another Item. The handle is not in the identity; `original_url` keeps the pasted link, and the row's place line reads the handle from it (`spellingOf` and `whereOf` in `src/core/link-place.ts`).
- **GitHub.** A repository-root link (exactly an owner and a repository) lower-cases both, and drops a trailing `/` and a `.git` suffix. GitHub documents `owner` and `repo` as case-insensitive ([Get a repository](https://docs.github.com/en/rest/repos/repos#get-a-repository)). A deep link and a file path keep their pasted case and stay their own Items, and a renamed repository stays an Item under the name it was pasted with. The Reader and the place line show the pasted case, read from `original_url` when it has the same identity.
- **Reddit.** A post id and a comment id must be ASCII letters and digits (base-36) and are lower-cased. A link whose id fails the check is a plain link. A comment is a different Item from its post, and two comments on one post differ. `redd.it` links follow the same rule. A share link (`reddit.com/r/<community>/s/<code>`) holds no id, so it is no identity: the Paste resolves it to the post or comment it leads to and keeps it as an alias (see Short-link aliases).
- **No second key.** There is no Source id column. A new rule for another Source changes `parseLink` and bumps the version of the `item-identity` data step.

The `item-identity` step recomputes every stored `normalized_url` with `parseLink`, with no network call, and keeps an Item's kind: an Item whose new link would have another kind is left as it is, except that a stored Article takes the identity of its link when `parseLink` calls it a plain link, because an Article is a plain link that a fetch found to be an article (`proposedIdentity` in `src/core/item-identity.ts`). The version is 2: version 1 ran `parseLink` once over each link, and a link with a doubled artifact (`www.www.`, a second trailing dot, `repo.git.git`, `www.mobile.x.com`) came out in a form that `parseLink` changed again, so the Item kept a form that no Paste of its link produced again. Version 2 runs the step again over the stored identities. An Item whose new identity no other Item has gets it and keeps its id and every record. Two or more Items whose new identities are equal, and an Item whose new identity another Item already holds, are not merged: each keeps its stored identity, and the run logs one `item-identity-collision` line per group with the identity and the Item ids. The logged identity ends before its first `?` or `#`, because a kept query pair can carry a credential, and is cut to 1,000 characters. A merge needs its own contract for content generations, Digests, Kept comments, Read state, files, catalog links, search parts, jobs and AI tasks.

The units run in four phases, named in the cursor. `stage` reads Items in id order, at most 500 rows and about 4 MB of identity text per unit (`STAGE_ROWS`, `STAGE_BYTES`, far under D1's 50 MB result limit and the Worker's 128 MB, [Workers limits](https://developers.cloudflare.com/workers/platform/limits/)), and stages the Items whose identity changes, 24 rows per insert so a statement stays under D1's 100 bound values. No statement carries more than one identity per value, so the 2 MB string limit of D1 is not reached by the batch size. `apply` renames up to 500 staged Items per unit with one statement that renames an Item only when its stored identity still equals the staged old key, no other staged Item has the same new key, and no Item holds the new key, then deletes the staged rows that are no longer at their old key. Because the statement checks the holder itself, a Paste or an older release that takes a planned identity after the plan cannot make a unit fail on the unique index: that pair is skipped and reported. `report` logs the staged rows that are left, 20 groups per unit, and `finish` logs `item-identity-finished` with the count, clears the staging and records the version. The first unit clears the staging a lost run left. Both sizes are our choice. On `node:sqlite`, 100,000 Items that all needed a rename took 6.7 s and 7 MB more resident memory across 5 runs (Node 26.12.1, drizzle-orm 0.45.4, 2026-11-08). The cost on D1 was not measured (see Open items).

## Short-link aliases

A short link (`isShortLink` in `src/core/links.ts`) or a Reddit share link (`isRedditShareLink` in the same file) is not an Item's identity: the Item's identity is the address it resolves to. This section says "short link" for both, except under Reddit share links. `item_aliases` records which Item a short link made or reached, so a later Paste or Try again of that short link finds the Item without resolving the link again. `original_url` cannot do this, because it holds only the first spelling that made an Item.

**Identity record.**

- **Key.** `item_aliases.normalized_url` is the primary key. It is `parseLink(<short link>).normalizedUrl`, so two spellings of one short link (a tracking parameter, a fragment, a trailing dot on the host) are one alias, and the path keeps its case because short codes are case sensitive. `item_aliases.address` is the address the short link resolved to when the row was written, spelled as the fetch job read it (`www.` and query kept). Every later refresh through the alias fetches that address, because the Item's `normalized_url` drops `www.` and tracking parameters that the site may need. The first row wins, and a later resolution does not change it. `item_aliases.item_id` is the Item's `items.id`, with `ON DELETE cascade` and an index for the delete. An alias holds nothing else.
- **Survives.** A re-paste, a Try again and a refresh keep the row. A rename of the Item's `normalized_url` by a data step keeps it, because the row names the id. An export and a restore keep it with its `address`, because the restore keeps every id (see Export, backup and restore in `export-backup-and-restore.md`).
- **Ends.** Deleting the Item deletes its aliases, in the same batch (see Deleting an Item).
- **Breaks.** A change to the generic rule of `parseLink` can change the key of a short link. The old row is then never found, and the short link resolves anew, which writes a row under the new key. That costs a lookup and never reaches a wrong Item. A merge of two Items, which no code does yet, must repoint the aliases of the Item it removes.
- **Existing libraries.** No data step writes aliases for Items saved before this table existed. Such an Item gets its alias the next time its short link is pasted and resolves to it.

**Rules.** `saveItem` in `src/core/save-link.ts` applies them to a pasted short link, in this order:

1. If an alias exists for the link, the Paste or Try again refreshes that Item and resolves nothing. The refresh queues a fetch job whose address is the alias's `address`, never the short link, so a short link that now points elsewhere cannot bring other content into the Item. A short link whose target moved keeps its Item, and the new target is not saved. A short link that has died still reaches its Item.
2. Otherwise the link is resolved. A resolution that fails saves the failure under the short URL, as before (`saveFailedResolution` in `src/core/failed-resolution.ts`), and writes no alias. Its writes start with a guard that fails while an alias for the link exists, so a failure that ends after another Paste wrote the alias makes no failed Item, and the Paste is applied again from rule 1.
3. A resolution that succeeds gives an address, and one batch does the rest. If an Item exists under the short URL, left by an earlier failed resolution or fetch (its `fetch_result` is set and is not `ok`, and it was never fetched, so `fetched_at` is null; `promoteFailedItem` in `src/core/short-link-aliases.ts` checks both, because a refresh that failed leaves an earlier success's content and date on the Item), and no Item holds the resolved identity, that Item takes the resolved identity, kind and Source and is fetched again: the failed Item becomes the resolved one. If an Item already holds the resolved identity, the Paste reaches that Item, and the failed Item stays as it is for the owner to delete, because merging two Items needs its own contract (see Item identity). The batch then saves or refreshes the Item at the resolved identity, queues its fetch job with the resolved address, and writes the alias with the resolved address. A second short link to the same target ends at the same Item and gets its own alias.
4. Concurrent first saves of one short link end with one Item. The unique index on `items.normalized_url` and the primary key of `item_aliases` allow one row each, and the batch starts with a guard (`insertGuard`, see Database and search in `database-and-search.md`) that holds only while no alias for the link names an Item other than the one at the resolved identity. When another Paste writes such an alias while this one was resolving, the guard fails, the batch rolls back and writes nothing, and the Paste is applied again from rule 1. The failed-Item promotion is one `UPDATE` that renames only when no Item holds the new identity, so two Pastes cannot both take it.

An alias never moves one Item's content to another Item.

**Reddit share links.** `isRedditShareLink` accepts a path of exactly `/r/<community>/s/<code>` (a trailing `/` allowed, `<code>` letters and digits) on the host `reddit.com`, with or without `www.`. Every other form is no share link and stays a plain link with no request: `old.reddit.com`, `m.reddit.com` and the other subdomains (an `old.reddit.com` share link answers a redirect to its login page), `reddit.com/s/<code>` without a community (it answers 200 and holds no redirect), and `/u/` or `/user/` paths (no such link was seen).

`saveItem` sends a share link through the rules above. `resolveShortLink` in `src/core/fetch-link.ts` follows its one redirect with `SHARE_LINK_POLICY`, which stops at the first redirect whatever its host, so no request goes to the destination, reads no body, follows no meta refresh and sends no cookie, and accepts that address only when `redditRefOf` reads a post or a comment from it. A redirect to a community root, a wiki page, a login page or any other address, and an answer that is no redirect, answer `unresolved` (the notice says Threadsift could not find the post or comment). An HTTP error answer such as a 403 stays `status`, which names what happened and logs the code (`fetch-status`), and a transport failure keeps its own result. Rule 2 saves each of them as before: a Link-only Item under the share link, kind `link`, with no alias and no job. The next Paste of that link resolves it again, and if it then resolves, rule 3 turns that Item into the resolved one. A comment destination keeps its comment id, so the Item is the comment's and never its post's.

The alias key is the share link's normalized address: `reddit.com` without `www.`, and the community and code in their pasted case, because a code is case sensitive. Two spellings that differ only in the community's case are two aliases of one Item. The alias `address` is the `www.reddit.com` address Reddit redirected to, with its `share_id` and `utm_*` query kept as it came; the fetch job uses only the post or comment id from it (`fetchLink`).

## The import cursor

`POST /api/items/batch` (`src/http/batch-routes.ts`) saves up to 100 links with `pasteBatch` (`src/core/batch-paste.ts`) and keeps the caller's cursor in `imports` (`src/core/import-cursor.ts`). Both it and `GET /api/imports/{name}` are open to agent tokens, because `isOwnerOnly` does not list them (see Access).

**Identity record.**

- **Key.** `imports.name` is the primary key, chosen by the caller: 1 to 64 letters, digits, `.`, `_` and `-`. The Instance generates nothing, because the caller already has a stable name for its routine, such as `x-bookmarks`. `cursor` is the caller's opaque text of 1 to 256 characters. The Import screen names a row `list-` plus the first 16 hex digits of the SHA-256 of its cleaned links joined by line feeds (`importNameOf`, `src/core/import-list.ts`) and keeps its cursor as the number of links done. The row holds no copy of the list, so the same list is the same row, and a list with one link added, removed or moved is another.
- **Stop marker.** The X bookmark sync keeps the post id of the top bookmark of its last run that stopped cleanly under `x-bookmarks`, and an import of all bookmarks keeps its top id under `x-bookmarks-all` and also stores it under `x-bookmarks`, so the next sync stops on its first page. The sync reads the list from the top and stops at that id, so the cursor marks where to stop and never where to resume, and a missing cursor only makes the next run read further. A run stops cleanly when it sent every page it read and stopped at the stored id, at the end of the list or at the 20-page limit of a sync. A sync that stops at the limit moves the marker to the top, because a marker that stayed would make every later run send the same 2,000 bookmarks again; the bookmarks below those pages wait for the import of all bookmarks.
- **Survives.** A restart, a deploy and a rollback keep the row. An export and a restore carry it (not built: see Export, backup and restore in `export-backup-and-restore.md`), because losing it makes a routine send everything again, which is safe but slow, since every link answers `known`.
- **Breaks.** A caller that renames its routine starts a new row. The old row stays and nothing points to it.
- **Reference.** Nothing points to an `imports` row and it points to no Item, so deleting an Item never touches it.

**One call.**

- **Order.** The links are saved one after the other, in the order given, and the cursor is written after the last one. A call that dies half way leaves the old cursor, and the caller sends the same links again. This is at-least-once delivery, and the repeat is cheap because a link the library holds answers `known`.
- **Known links.** `pasteBatch` calls `saveItem` with `existing: "keep"`, which writes only when the link's final identity has no Item. For a plain link, one guarded batch inserts the Item with its fetch job and pending Digest, and the guard (`holdsNoItem`, checked inside the batch like the other guards in Database and search) fails the whole batch when an Item exists. A short link or a Reddit share link is resolved first, and then the same guard runs on the address it reached. An Item found that way keeps its status, jobs and pending Digest, whether the call lost a race with another save or a new short link reached an Item that was already saved, and the batch only records the new alias (`saveResolved` in `src/core/resolved-save.ts`). A failed resolution of a held short link also keeps the stored Item (`saveFailedResolution`). A short link whose earlier resolution failed and whose address now resolves, with no Item at that address, renames the failed Item to the resolved identity as rule 3 of Short-link aliases says (`promoteFailedItem`), keeps its status and queues no job, so the Import adds no second Item. The link answers `known`, spends no fetch and no Digest, and drops a Digest sent with it. A Paste of that link still refreshes it, because `existing` defaults to `"refresh"`. An Import adds Items (`GLOSSARY.md`), and refreshing the library would cost one model call per link.
- **Updating.** A link meets the data-step check before anything else, held or not, so a library being updated answers 503 as `POST /api/items` does. The links before it stay saved and the cursor does not move.
- **Limit of 100 links.** The number is our choice, not a platform limit, and the counts below justify it against the paid-plan limits (Workers docs, Limits: 10,000 subrequests per invocation, which count `fetch` calls, each hop of a redirect chain, and requests to D1 and other Cloudflare services; D1 docs, Limits: 1,000 queries per invocation, where one `db.batch()` call counts as one query however many statements it holds). Measured on 2026-11-11 on the Worker (`wrangler dev --local`, with a wrapper that counts `env.DB.prepare` and `batch` calls, `fetch` calls and `env.JOBS.sendBatch` calls inside one request), one call of 100 links with an agent token:

| Call | D1 executions | D1 batches | D1 queries | Statements in batches | Redirect fetches | Queue sends |
|---|---|---|---|---|---|---|
| 100 new X, article and Reddit links | 253 | 116 | 369 | 774 | 0 | 100 |
| The same call again, all known | 402 | 100 | 502 | 700 | 0 | 0 |
| 100 new short links of one real shortener, each reaching its own address | 302 | 100 | 402 | 800 | 200 | 100 |
| The same call again, all known | 502 | 100 | 602 | 700 | 0 | 0 |

A new link costs about 4 D1 queries and one queue send, and a short link adds 2 fetches here, so the call stays under 1,000 D1 queries and uses 702 subrequests at most (402 D1 queries, 200 fetches and 100 queue sends), against 10,000. A short link can take up to 20 redirect hops (`resolveShortLink`), which would be 2,100 fetches for 100 links and about 2,800 subrequests in all, still under 10,000. A known link costs 5 to 6 D1 queries, because the guarded batch fails and the Item is read again. The container has none of these limits. The counts are for the paid plan, which this document assumes; the Free plan allows 50 subrequests per invocation and does not fit a call of this size.

## Catalog keys

`catalogKey` in `src/core/catalog-key.ts` is the one key function for Topics and Tags. Digest publication, the older-Digest linking, the `topic` and `tag` filters of `GET /api/items` and the `topic-keys` and `tag-keys` steps all call it. It runs in JavaScript on both targets because SQLite has no case folding. The key of a name is, in this order: NFKC, Unicode full case folding, removal of U+0307 directly after an `i`, NFC, trim, and each run of whitespace collapsed to one space.

- **Dotted I.** Folding `İ` (U+0130) gives `i` and U+0307 (`CaseFolding.txt`, status F). The removal step drops that dot, so `İ`, `I`, `i`, `İ` written as `I` with U+0307, and `i` with U+0307 all give `i`. Dotless `ı` has no entry in the C and F statuses, so it stays apart from `i`, and every other accent stays too: `café` and `cafe`, `ş` and `s`, `ö` and `o` are different keys. The rule is not Turkic folding (status T), which would map `I` to `ı` and split `Istanbul` from `istanbul`, and it uses no locale. The removal covers a run of U+0307, because a key must give itself back when it is folded again.
- **Properties.** `node tools/case-folding/check.ts` calls `catalogKey` on every code point except surrogates and on every two- and three-character string made from 24 characters that matter here (`i`, `İ`, `ı`, U+0307, `ß`, the sigmas, a ligature, two spaces and others), 1,126,464 names in about 3 s (Node 26.12.1, 2026-11-08). It fails when a key is not stable (the key of a key is the key) or when the key of the previous rule's key differs from the key of the name. The second property lets the steps recompute from the visible name, and the first lets them run again.
- **Length.** A key is at most `CATALOG_KEY_MAX` (4,320) UTF-16 units (`src/core/catalog-key-limit.ts`): a Topic or Tag name is at most 240 units (`SHORT_TEXT_MAX`), and the worst single unit, U+FDFA, makes 18 (its NFKC form is 18 characters). Every route that takes a key (`GET /api/topics/{key}` and the Index `cursor`) uses that bound, so a key a Topic can have is never refused. `test/parsers.test.ts` calls `catalogKey` on every code point except surrogates, takes the largest ratio of key length to name length, and fails when it differs from `CATALOG_KEY_EXPANSION_MAX`, so a Unicode update that raises it is noticed (about 3.8 s, Node 26.12.1 with Unicode 17.0, 2026-11-11). A request line that carries a key this long, percent-encoded, can exceed a server's request-line limit before the route sees it; the limit is not measured here.
- **Folding table.** `src/core/case-folding-table.ts` is generated by `node tools/case-folding/build.ts` from `https://www.unicode.org/Public/18.0.0/ucd/CaseFolding.txt` (Unicode 18.0.0, the current release on 2026-11-08) with the C and F statuses: 1,606 mappings as 208 runs and 105 expansions, 7,741 bytes. The generator refuses a file whose SHA-256 is not the pinned one, and the table carries the Unicode license header (`Unicode-3.0`). The generator writes the file in its committed format, so `git diff --exit-code src/core/case-folding-table.ts` after a run shows nothing while the Unicode data is the same. A new Unicode release changes keys only when someone runs the generator again and raises `CATALOG_KEY_VERSION`, which runs both steps again.
- **Why not a package.** Searched on npm on 2026-11-08. `unicode-case-folding` 1.1.2 (MIT, no dependencies, 25 KB, one maintainer, 4 releases, last on 2026-10-01) has a table equal to the C and F statuses of Unicode 18.0.0 for every code point except surrogates, but it states no Unicode version, so a dependency update could change every stored key without a step version. `@unicode/unicode-18.0.0` 2.1.0 pins the version in its name and ships the data, but it decodes it with `node:zlib`, which `src/core` may not import. `fold-case` (last release 2014) and `@ar-nelson/foldcase` (2019) are not maintained. The generated table costs 7,741 bytes of source and a script, and in return the keys change only by a commit.
- **Identity.** A Topic or Tag is identified by its row id, which `items.topic_id` and `item_tags.tag_id` reference. The key is derived from the name, is unique, and survives a refresh, a re-import and an export and restore, because it is recomputed from the name. It does not survive a change of the rule, which is why the steps exist. The name never changes after the row is created.

`topic-keys` and `tag-keys` (`src/core/catalog-key-step.ts`, `src/core/catalog-key-links.ts`) recompute every key from the visible name with the same function. Within Topics and within Tags the row with the smallest id survives with its name unchanged, which is the first spelling saved. The units run in four phases, named in the cursor. `stage` reads rows in id order, 100 per unit, and stages `(id, stored key, new key)` in `data_step_renames`, 24 rows per insert so a statement stays under D1's 100 bound values. A staged key is one bound value of at most `CATALOG_KEY_MAX` (4,320) code points, about 13 KB in UTF-8 at 3 bytes a code point, far under D1's 2 MB per value ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)). `merge` takes the next staged row that has a smaller id with the same new key, a loser, moves up to 500 of its links to the survivor in one batch, and deletes the loser in the batch that finds no link left. A Topic's links are `items.topic_id` and `log_entries.topic_id`, and the batch moves up to 500 of each, so a Log line that named the loser opens the survivor's page. The same batch deletes the loser's `topic_pages` and `topic_leases` rows once no Item and no entry names it, because both reference `topics` with no delete action and foreign keys are enforced on both targets, so a loser with either row would fail its delete and roll the unit back on every run. The survivor's overview is not rebuilt by the step: its `built_from` lacks the moved Items, so the next overview run for the survivor counts them as uncovered, and no run is queued by the merge. A Tag's links are `item_tags` rows: a row moves unless the Item already has the survivor, the rest are deleted, so the unique index on `(item_id, tag_id)` is never asked to decide. The Proposals of a Tag, and of a Topic, are repointed in the same unit and before the loser is deleted (`proposalRelinks` in `src/core/proposal-lifecycle.ts`, one function over the Tag columns or the Topic columns), because a change of spelling rule does not delete a concept and the owner's Reject must survive it. `proposals.from_topic_id` and `into_topic_id` cascade, so without the repoint a Reject on a pair that names the losing Topic would be deleted and the pair proposed again. Two cases come before the update, because the unique pair index would refuse it: a row that would become a pair of one Tag (or Topic) with itself is deleted (the merge already made the two one), and when two rows would reach the same pair one is kept: an `accepting` row over a `rejected` one, a `rejected` row over an `open` or `declined` one, and then the smaller id. An active merge's progress must not lose a collision to an inactive decision, so `accepting` outranks `rejected`; an older rule ranked the two equal, so the smaller id could delete an `accepting` row whose two final sides were still distinct. The cascade then deletes a Proposal only when a Tag or a Topic goes any other way. `TOPIC_KIND.relink` repoints the Topic Pins that target the loser (`repointedTopicPins` in `src/core/pins.ts`) in the same unit, because `pins.into_topic_id` has no delete action and the delete would otherwise fail on every run. The bounded move of a Topic's Items, Digests and Log references is the shared Topic rewrite below, and it stays apart from this repoint. The same batch rebuilds the `tags` search part of the moved Items (`tagPartWrites` in `src/core/search.ts`), so a search finds an Item by the surviving name and no longer by the deleted one. `rename` sets each surviving row's key to its new key in units of 500, only where the stored key is still the staged one and no other row holds the new key, which is why `merge` runs first: a loser can hold the key its survivor is about to take. `finish` clears the staging and records the version. No statement uses `UPDATE OR IGNORE` or `REPLACE`, and every unit is one `db.batch`, so a failed unit moves nothing and the next run repeats it. The Topic step touches no search part, because search parts hold Tag names and not Topic names. The `tag-keys` step leaves the stored Digest JSON with the original Tag names. The `topic-keys` step writes the survivor's name into `digests.topic` and into the `topic` field of the stored Digest JSON of every Item it moves (the shared Topic rewrite below).

A Digest published or linked while a step runs can add a row under a key the step is about to use (the survivor still has its old key, so the new row is a second row for the same name), or a link to a loser after its last unit. `finish` therefore checks that every staged row is resolved: its key is its new key, and no staged row with a smaller id shares that key. When one is not, `finish` logs `catalog-keys-restaged` with the step name and up to 20 row ids and starts `stage` again, which now sees the new row and merges it into the smallest id. The batch that records the version carries the same check as a guard, so a row added between the check and the batch makes the batch fail and the next run restages. A step records its version only when the catalog holds one row for each key. The search reconciler (`src/core/search-reconciler.ts`) fingerprints the Tag names of an Item in key order, so it rewrites the parts of the merged Items once more in its own pass. That is harmless and not needed for correctness.

**The shared Topic rewrite.** `topicMoves` in `src/core/catalog-key-links.ts` is the bounded rewrite of one Topic into another, and `closingWrites` in the same file holds the closing writes that a Tag merge and a Topic merge share, written once over `TAG_KIND` and `TOPIC_KIND`; `topicClosingWrites` adds the overview attempt for a Topic and returns the position of that attempt beside the writes (`{ writes, wakes }`), so Accept of a Topic merge can wake the job the attempt opened. The `topic-keys` step, `pin-keys` and Accept of a Topic merge call them, as Accept, `tag-keys` and `pin-keys` share `tagMoves` and `closingWrites` for Tags. For up to `MERGE_ITEMS` Item ids and, independently, up to `MERGE_ITEMS` Log entry ids that `TOPIC_KIND.linked` read, a unit does three things in this order. First, one `UPDATE` sets `digests.topic` and the `topic` field of the Digest JSON (`json_set`, only when `json_valid`) to the survivor's name for the Digests of those Items that still link to the loser, with no read of the Digest and no JavaScript. This is a storage contract and not a display fix: the Reader shows the linked Topic's name whatever `digests.topic` says, but a stored Digest must not name a Topic that no longer exists, because `linkOlderDigest` re-links from the stored names and the export and the Vault mirror (not built) carry them. A Digest whose JSON is not valid keeps its text, still gets `digests.topic`, and its Item still moves. Second, `items.topic_id` and `log_entries.topic_id` move. Third, the loser's `topic_pages` and `topic_leases` rows go once no Item and no Log entry names the loser. A unit is the last one only when both collections fit (`isLastUnit`), because Digest publication keeps adding Log entries for a Topic, so a Topic with few Items can have more than one unit of Log references. `topicMoves` does not repoint Proposals or Pins: the `topic-keys` step and `pin-keys` do that around it, and Accept keeps its own Proposal row to the last batch, because the row carries the continuation, the count and the unit revision. The closing writes join the last unit of a caller that merges for good (`pin-keys` and Accept of a Topic merge; `topic-keys` keeps its own close and queues nothing). They bump `catalog_version` once, delete the `topic-keys` rows that staged the loser, make one opening attempt for the survivor's overview (`continuingOverview`) and delete the loser, each only when no Item and no Log entry names the loser. The opening attempt is not a promise of exactly one job: the open-job index is on Item and kind, so a job of either Topic's owner Item can already be open, and a job takes its Topic from its owner Item when it starts, so a queued job of the loser's owner follows its Item into the survivor. The chain that one attempt starts is long for a big merge, because a run covers at most 40 Items (`reviseOverview`): the 600 Items a merge moved needed 16 jobs and 16 model calls on Claude Code.

**Bounds of a Topic unit of the key steps.** A unit runs 4 reads (`recordedRow`, the Topic with its Pin, and the two reads of `TOPIC_KIND.linked`) and 1 guarded batch of 19 statements, 5 queries on D1 because a `db.batch` counts as one ([D1 limits](https://developers.cloudflare.com/d1/platform/limits/)). The unit size is `MERGE_ITEMS` (500), the number the `topic-keys` step already moved in one batch. The largest bound string is the JSON of 500 Item ids, 2,002 bytes, the longest statement is 1,499 bytes of SQL and a statement binds at most 10 values, against D1's 100,000 bytes per statement, 2,000,000 bytes per bound string and 100 bound values. Measured with the node adapter's code behind a counter that counts each statement outside a batch and each batch as one query (2026-11-12, Node 26.12.1, the script is not in the repository): one Topic with 1,100 Items took 7 batches and 35 queries in `migrateData`, and 80 queries for the whole `tick`, the sweep included; 150 pinned Topics of 1 Item each stopped the step at `UNITS_PER_RUN` (100 units), 540 queries for the whole `tick` with 52 Topics left for the next one. Both stay under the 1,000 queries of a Workers Paid invocation. On local D1 one scheduled event merged the 1,100-Item Topic in 264 ms.

**Pins.** The `pin-keys` step reads only the two merge kinds (`MERGE_KINDS` in `src/core/kinds.ts`): it recomputes a key from `from_name`, which for an `items-disagree` Pin is the reason and not a name, so a read of every Pin would rewrite the pair key and could delete the Pin as a duplicate. Its reads, the count in its finish guard and the reads in `src/core/pin-merge.ts` all name the kind, and `pinsFor` in `src/core/pins.ts` does too, so the Digest paths ignore the third kind. `TAG_KIND.relink` repoints every Pin that targets the losing Tag to the survivor in the unit that deletes the loser (`repointedPins` in `src/core/pins.ts`), because `pins.into_tag_id` has no delete action and the delete would otherwise fail and roll the unit back on every run, the failure `topic_pages`, `topic_leases` and `log_entries` caused for Topics. The `pin-keys` step (`src/core/pin-key-step.ts`) follows `tag-keys`, shares `CATALOG_KEY_VERSION`, recomputes every Pin's key and merges a Tag that holds a Pin's key into the Pin's target; The step also merges a Topic whose key equals a `topic-merge` Pin's key into the Pin's target through the shared Topic rewrite, and leaves the Topic that is the Pin's own target alone. A change of `CATALOG_KEY_VERSION` can leave a Topic under a pinned key, and a Digest from an older Worker still in flight after a deploy can create the merged-away Topic again. `docs/proposals.md` (Pins) holds its rules and the identity of a Pin.

## Deleting an Item

`deleteItem` in `src/core/delete-item.ts` runs `DELETE /api/items/:id` (`src/http/delete-item-route.ts`) for the owner's session and agent tokens. The route answers 204 when the delete's `RETURNING` names the Item and 404 otherwise.

- **Manifest.** One `batch`, in this order: `reddit_comments`, `reddit_threads`, `github_repos`, `x_verifications`, `search_parts`, `proposals` (the `highlight-lost` rows that name a Highlight of the Item, in any state, then the `items-disagree` rows whose `from_item_id` or `into_item_id` names the Item, in any state), `pins` (the Pins whose `from_item_id` or `into_item_id` names the Item), `highlights`, `media`, `notes`, `related_items` (the rows where either column names the Item), `log_entries` (the rows whose `item_id` names the Item), `search_fingerprints`, `item_tags`, `item_aliases`, `digests`, `ai_tasks`, `jobs`, then `items`. A child goes before its parent, and `digests` goes before the `ai_tasks` row its `task_id` names, because that reference has no `ON DELETE` action. Foreign keys are enforced on `node:sqlite` and on D1. The `search_parts` delete fires the FTS triggers, so the index follows. The `ON DELETE cascade` on each `item_id` column stays as a second line of defence; the list is the contract.
- **Related Items.** Deleting either Item of a pair removes the pair. The other Item's list shrinks by one entry and renumbers nothing (a gap stays in `position`), and no new pick runs. The Summaries of the candidates that a deleted Item's pick sent stay in that Item's `ai_tasks.inputs` until the Item itself is deleted, as the Topic overview's inputs do; the candidate Items' own deletion does not rewrite them.
- **Log entries.** An entry that names the Item (`ingest`, `digest` and `related`) holds that Item's title and Tags, so it goes with the Item. A `topic`, `overview`, `merge` or `merge-topic` entry names no Item and holds no Item text, so it stays, and the Log keeps showing that a Topic was created or its overview revised. The delete itself is not an entry.
- **What stays.** Topics, Tags and `catalog_version`, because the lists outlive their last Item and a filter shows such a name with the count 0. `catalog_linking` and `search_reconciling` keep a cursor that may name the deleted id, which is a checkpoint and not a link. `scheduled_runs`, `file_cleaning` and the id sequences stay too, so an id is never reused.
- **Files after the commit.** After the batch commits, `deleteItem` lists `items/<id>/` through `FileStore.list` until the cursor is `null` and deletes every key it found, so the delete reaches temporary files too. A storage failure is logged as `item-files-not-deleted` and the route still answers 204, because the Item is already gone; the cleanup pass deletes what is left, since no Item names it.
- **Late writers.** Every job write is guarded on its job row (`holding` in `src/core/job-rows.ts`), the AI task insert is guarded the same way, and the search reconciler and catalog linking re-read the Item in their guard, so a runner that finishes after the delete writes nothing and ends as a lost claim. A fetch that put a long post text into the store before it lost its claim deletes that file itself, or the cleanup pass does.
- **Confirm dialog wait.** The Reader's confirm dialog refuses Escape and both buttons while its DELETE is pending, so a DELETE that never answers would hold the owner there. After 20 seconds (`DELETE_WAIT_MS` in `web/src/DeleteItem.tsx`, the same as the read deadline `READ_DEADLINE_MS` in `web/src/calls.ts`, a chosen value) the dialog moves to its failed state with Cancel and Delete enabled. The request is not cancelled: an answer that arrives later still removes the Item from the list and closes the dialog, and it leaves the Reader, moves attention and announces only while the Reader still shows that Item (`opened` in `useDeletion`), and a refusal that arrives later changes the dialog only while that attempt is the latest and the dialog was not cancelled (`reduceDelete` in `web/src/delete-flow.ts`). A second Delete on an Item that is already gone counts as deleted because the route answers 404 (`removeItem` in `web/src/api.ts`).
- **Proposals.** A merge row names no Item (it names two Tags or two Topics, and its Item counts are read live), so a delete never touches one. An `overview-gap` row names a Topic and reads its counts live, so a delete never touches it and the counts shrink at once. A `highlight-lost` row names a Highlight, and a Highlight names its Item, so the manifest deletes the `proposals` rows that name a Highlight of the Item, in any state, before the Item's `highlights`, and `proposals.highlight_id ON DELETE cascade` is the second line. `test/lost-highlight-accept.test.ts` deletes an Item with open and rejected rows through the route and checks that they go. The quote that row showed is the owner's own text and stays nowhere else. The one Item-owned record the two model runs make is their job: the job needs an owner Item, because `jobs.item_id` is `NOT NULL` with `ON DELETE cascade`, and the AI task carries the same owner (`ai_tasks.item_id`). An `items-disagree` row names two Items, so the manifest deletes the `proposals` rows whose `from_item_id` or `into_item_id` is the Item, in any state, before the Item, and the cascade on both columns is the second line (`test/disagreement-page.test.ts` deletes each Item of an open pair through the route). The three weekly model runs (`proposals`, `topic_proposals` and `disagreement_proposals`) open three jobs on the same owner Item, which the open-job index allows because the kinds differ. Deleting that Item while a job is open deletes the job and its task, and that week's run is lost until the next one; deleting it while all are open loses all. The `proposals` task's `inputs` hold Tag and Topic names and the `topic_proposals` task's `inputs` hold Topic and Tag names, and neither holds Item text, so none stays after an Item is deleted. The `disagreement_proposals` task's `inputs` hold the id, title and Summary of each sent Item, so they stay in `ai_tasks.inputs` until the task goes with its owner Item; deleting another sent Item removes its row and its Digest but not those words from a finished task. `topic_checks` names a Topic and no Item, so an Item delete leaves it, and the membership text it holds names an Item id that no longer exists, which makes that Topic touched on the next weekly run.
- **Each slice that adds an Item-owned record extends `deleteItem` and this list in the same change.** Mirror paths are the planned one. A `merge` or `merge-topic` entry and a Pin of a merge name no Item, so `deleteItem` does not change for them. An `items-disagree` Pin names two Items (`pins.from_item_id`, `pins.into_item_id`), so the manifest deletes the Pins that name the Item before the Item's own row, and the cascade on both columns is the second line. Because every `item_id` key has `ON DELETE cascade`, the Item delete removes the rows of a table left out of the batch in `src/core/delete-item.ts`, and nothing notices; only the `digests` line is enforced, because the `ai_tasks` delete fails without it.
