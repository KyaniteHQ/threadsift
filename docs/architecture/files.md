# Files

The `FileStore` port (`src/core/file-store.ts`) has two adapters. The container writes under `<DATA_DIR>/files`, and Cloudflare writes to the R2 bucket `threadsift-files`, bound as `FILES`. `put` takes a byte array because R2 needs a known length for a streamed `put`. An Article's images and the photos of an X post are stored as fetched (see Media in `data-model-outline.md`). There is no resizing: it would need two image paths (an Images binding on Cloudflare, a native library in the container) for a feature the spec does not ask for.

- **Not built.** The byte range of `get` and the multipart upload for a file of unknown length (every multipart part but the last must be at least 5 MiB; R2 docs, Workers API and multipart uploads). The restore needs neither: it stores each 32 MiB part of the zip as its own object and reads a window by skipping to it in the part's stream. Its `files` phase puts the Item files under the `items/` root with the same keys the zip names.
- **Key grammar.** `src/core/file-keys.ts` is the one place that defines a key, and both adapters call it before they touch storage, so nothing decodes or normalizes a key after the check. An Item's key is `items/<id>/<name>`, where `<name>` is 1 to 225 ASCII letters, digits, `.`, `-` and `_`, other than `.` and `..`. The `<id>` is a canonical positive integer of at most 19 digits, the length of the largest SQLite rowid. A prefix ends in a slash, so `items/1/` never matches `items/10/`. A second root, `exports/<id>/<name>`, holds one export's objects, named `part-<n>-<g>`, `dir-<n>-<g>` or `tail-<g>` with the attempt number `g` (`docs/architecture/export-backup-and-restore.md`). A third root, `restores/<id>/part-<n>`, holds the parts of an uploaded restore zip. The restore deletes its parts when it is done, is cancelled or refuses the zip, keeps them for Resume when it fails with `gave-up` and the sweep deletes them 24 hours after the failure, and the sweep stage `restores` (`cleanRestoreParts` in `src/core/restore-parts.ts`) removes the rest (Restore in `export-backup-and-restore.md`). The image route serves `items/` keys only, `cleanFiles` sweeps `items/` only, the sweep stage `exports` removes `exports/` objects, and the sweep stage `restores` removes `restores/` objects. `get`, `delete` and `list` also accept a temporary file name of up to 255 bytes, `.tmp-<hex>-<name>` whose embedded `<name>` is valid (`parseStoredKey`), so a leftover of a 225-byte name (30 + 225 = 255 bytes) can be listed and removed. A key or prefix outside the grammar makes the call throw `FileRefused`, and a delete batch is checked whole before any key is removed.
- **Listing.** Both adapters list in the order of the key strings and return only keys the grammar accepts, so every listed key can go back into `get` and `delete`. The container pages by the last key it returned: `keysAfter` in `src/targets/node/file-store.ts` skips the item folders that end before that key, so a page costs the folders it needs and not every folder. R2 pages by its own cursor, at most 1,000 keys, and its `delete` takes at most 1,000 keys, so the adapter splits a longer batch.
- **Listing cost.** Listing 4,500 files in 1,500 item folders in pages of 100 (the page size of `cleanFiles`) took 3.2 to 3.6 s over 3 runs when every page read all folders, and 0.16 to 0.19 s over 3 runs with `keysAfter` (measured 2026-11-13 on the owner's workstation). Run this from the repository root, on a checkout of each version:

  ```sh
  node --input-type=module - <<'JS'
  import { mkdir, mkdtemp, rm, writeFile } from "node:fs/promises";
  import { tmpdir } from "node:os";
  import { join } from "node:path";
  import { dataFileStore } from "./src/targets/node/file-store.ts";

  const dir = await mkdtemp(join(tmpdir(), "list-bench-"));
  for (let item = 1; item <= 1500; item += 1) {
    const folder = join(dir, "files", "items", String(item));
    await mkdir(folder, { recursive: true });
    await writeFile(join(folder, `post-${item}-1.md`), "x");
    await writeFile(join(folder, `img-${item}-1-1.png`), "x");
    await writeFile(join(folder, `img-${item}-1-2.png`), "x");
  }
  const store = dataFileStore(dir);
  const started = performance.now();
  let cursor = null;
  let keys = 0;
  do {
    const page = await store.list("items/", cursor, 100);
    keys += page.keys.length;
    cursor = page.cursor;
  } while (cursor !== null);
  console.log(`${keys} keys, ${Math.round(performance.now() - started)} ms`);
  await rm(dir, { recursive: true });
  JS
  ```

- **Container folder.** `put` writes a temporary file `.tmp-<random>-<name>` in the key's folder, syncs it and renames it into place, so a reader never sees half a file and two puts never share a temporary path. The temporary prefix takes 30 bytes (12 random bytes as hex), so the grammar allows a name of 255 - 30 = 225 bytes (`FILE_NAME_MAX`) and a temporary name always fits a Linux file name. The name ends with the key's own file name, so `finalKeyOf` maps a temporary file to the key it will become, and the cleanup protects it as it protects that key. The adapter throws `FileRefused` for a symlinked or non-directory path component and for a leaf that is not a regular file (`lstat`, then `O_NOFOLLOW` on open). The trust assumption is that no other local process swaps the store's folders while the app runs: the check and the open are two steps for a parent folder.
- **Reading post text.** `items.post_text_key` names the file that holds an Item's post text. A row holds `post_text` or `post_text_key`, never both, and the `items_post_text_check` CHECK refuses a row that sets both. `getItem` (`src/core/item-detail.ts`) reads the file and drops the key from the answer. A key outside the grammar, a key in another Item's folder, a missing file and a refused file all give `postText: null` with status 200 and one log line, so one bad file does not hide the Item. Any other storage error, such as a permission error or an outage, is not hidden as missing content and ends in a 500. When a refresh deleted the old file after `getItem` read the row, `getItem` reads the Item once more, and a second miss gives `postText: null`. A refresh keeps the old text and file until committed content replaces or clears them, so a failed fetch, an `ok` result with no content and a Paste while a job is open leave the file readable.
- **Writing and publishing a long post text.** The fetch job stores a post text over 1,000,000 UTF-8 bytes (`INLINE_TEXT_BYTES` in `src/core/limits.ts`) in the store, and `readArticle` returns the whole Markdown, so the job and not the reader splits at the limit. The key `items/<item id>/post-<job id>-<attempt>.md` names the job and its attempt. A job id is never reused, and a job gets a new attempt number whenever a runner takes it over, so a key is never written twice. Two requeues keep the attempt number, and neither may follow a file write. A fetch wait counts an attempt when it is `limited` (`countsAttempt: limited` in `waitingOutcome`, `src/core/fetch-outcome.ts`), which a rate limit or an X reread (`readAgain`, `src/core/x-fetcher.ts`) sets, and ends before any file is written: `settledContent` takes `Concluded`, which has no wait member, so `tsc` refuses a `Fetched` there. A stale-result requeue needs a `currency` on the outcome. The Digest outcomes and `guardedOutcome` set one and write no post text file, and a fetch job gets one only from `lostOutcome`, whose guard never holds. A fetch outcome with a `currency`, or a wait after `placePostText`, would write one key twice and replace a file nothing names yet, because the batch that publishes a key also closes the job. One SQL expression builds the key, `postText` of `attemptFileKeys` in `src/core/job-rows.ts`, so the claim, the fetch job and the cleanup share one formatter. The job writes the file first. Only the guarded finishing batch (the job is `running` at the attempt its runner claimed) sets `post_text_key`, so a file that stops being protected never becomes protected again.
  `finish` in `src/core/job-finish.ts` tells three outcomes apart. After a commit it deletes the files the attempt superseded. After a rejected finish (the claim was lost) it deletes only the files its own attempt wrote that no row names, never another attempt's file, because the container runs 4 jobs at once and a runner that was taken over can still be inside its attempt while the new attempt holds the row. A finish that throws deletes nothing, because the batch may have committed and the Item may already name the files, and the cleanup pass settles them. A delete that fails is logged (`file-not-deleted`) and left to the cleanup.
- **Image files and the file route.** An attempt writes its images under `items/<id>/img-<job id>-<attempt>-<position>.<ext>` (see Media in `data-model-outline.md` for the identity). `GET /api/files/items/:id/:name` (`src/http/file-routes.ts`, `servedImage` in `src/core/image-serving.ts`) serves a key only when a `media` row of that Item has exactly that key, kind `image` and outcome `stored`. Every other key answers 404 with the same body. The body carries a generated `Content-Disposition` filename, never the page's. `privateFile` in `src/http/api-middleware.ts` sets the security headers on every answer, the 401 and 404 included. The reasons are in the headers' own specifications: `nosniff` and the stored type keep a browser from reading an image as script ([Fetch, `nosniff`](https://fetch.spec.whatwg.org/#x-content-type-options-header)), `sandbox` and `default-src 'none'` make an image opened as a page inert ([CSP](https://www.w3.org/TR/CSP3/)), and `Content-Disposition` follows [RFC 6266](https://www.rfc-editor.org/rfc/rfc6266).
- **Digest of a long post text.** `readDigestText` in `src/core/digest-post-text.ts` reads the whole file with `readPostText` (`src/core/post-text.ts`) and cuts the text to the 14,000 bytes of the Digest input (`cutDigestInput`), so no AI task input comes near 1,000,000 bytes. A file that is missing, refused or unreadable gets the same input-currency rule as a Provider result. When the Item's generation, pending Digest or open fetch job changed since the attempt read them, the attempt ends in a guarded batch that fails, so the runner requeues the job on the current inputs (`stale`) without counting an attempt. When they still match, the attempt fails before any Provider call and the job retries after 30 seconds and 2 minutes. The third failed read ends in one guarded batch that checks the generation again and sets `failed`, so a refresh that publishes during the read is never failed by the old read.
- **Cleanup.** Every tick runs one page of `cleanFiles` (`src/core/file-cleanup.ts`, 100 keys) at the end of the sweep. It touches only keys of a kind it owns (`isSweptKey` in `src/core/file-keys.ts`: post text files, image files, and the temporary file of either), so a release that stores a new kind of file under `items/` keeps its files while an older release runs. It deletes every owned key that no Item names (`items.post_text_key`, `media.file_key`) and that no job `running` at the attempt in the key owns (the condition the finishing guard checks: `postText` and `imagePrefix` of `attemptFileKeys`). `deleteUnclaimed` re-reads the named keys after the listing and deletes nothing while a restore holds the library (`restoreHoldsLibrary`), so it cannot delete a file that a `files` unit put back between its reads, nor a file a failed restore keeps for Resume. A temporary file is judged by the key it will become (`finalKeyOf`), so the temporary file of an attempt that is still `running` stays. A page that deletes cleanly saves the store's next cursor, and `null` after the last page starts a new pass. A delete that fails throws before the save, so the cursor stays and the next sweep that runs the stage lists from the same cursor again. This retry has no limit. The keys that the delete did remove leave the listing, so later keys move into the page as keys leave it. A page that holds only keys that stay (keys an Item names, keys a running job owns, and keys the store does not delete) stops the pass until the store deletes one of them. The key names its attempt, so no table of pending files exists, and the listing finds a file whose writer crashed before any database write. A write that lands after its attempt was overtaken and after the pass went by is found on the next pass.
