# Files

The `FileStore` port (`src/core/ports.ts`) has four calls. `put(key, bytes)` takes a byte array, whose length is known (R2 needs a known length for a streamed `put`). `get(key)` returns a stream, or `null` when the key is missing, and an adapter knows the file exists before it returns the stream. `delete(keys)` counts a missing key as deleted. `list(prefix, cursor, limit)` returns keys with their upload time and the next cursor, and may return a short page before the end. The container writes under `<DATA_DIR>/files` (`/data/files` in the image); Cloudflare writes to the R2 bucket `threadsift-files`, bound as `FILES`. An Article's images are stored as fetched (see Media in `data-model-outline.md`). No resizing: it would need two image paths (an Images binding on Cloudflare, a native library in the container) for a feature the spec does not ask for.

- **Not built yet.** The byte range of `get` and the multipart upload for a file of unknown length (every multipart part but the last must be at least 5 MiB; R2 docs, Workers API and multipart uploads) wait for the slices that need them, restore.
- **Key grammar.** `src/core/file-keys.ts` is the one place that defines a key, and both adapters call it before they touch storage. A key is `items/<id>/<name>`: `<id>` is a canonical positive integer (no sign, no leading zero, at most 19 digits, the length of the largest SQLite rowid), and `<name>` is 1 to 225 ASCII letters, digits, `.`, `-` and `_`, other than `.` and `..`, with no further path component. Nothing decodes or normalizes a key after the check. A prefix is `items/` or `items/<id>/`, and the trailing slash keeps `items/1/` from matching `items/10/`. `put` and the Item's own keys use that grammar. `get`, `delete` and `list` also accept a temporary file name of up to 255 bytes, `.tmp-<hex>-<name>` whose embedded `<name>` is valid under the grammar (`parseStoredKey`), so a leftover of a 225-byte name (30 + 225 = 255 bytes) can be listed and removed; a 226-byte name that is no such temporary file is outside the grammar and not listed. A key or prefix outside the grammar makes the call throw `FileRefused`, and a delete batch is checked whole before any key is removed. Deleting an Item can therefore delete one prefix.
- **Listing.** Both adapters list in the order of the key strings and return only keys the grammar accepts, so every listed key can go back into `get` and `delete`. The container pages by the last key it returned: `keysAfter` in `src/targets/node/file-store.ts` skips the item folders that end before that key and stops reading folders once the page and one look-ahead key are found, so a page costs the folders it needs and not every folder; a folder that disappears between the directory read and its own read counts as empty. R2 pages by its own cursor, at most 1,000 keys. R2's `delete` takes at most 1,000 keys, so the adapter splits a longer batch.
- **Listing cost.** Listing 4,500 files in 1,500 item folders in pages of 100 (the page size of `cleanFiles`) took 3.2 to 3.6 s over 3 runs when every page read all folders, and 0.16 to 0.19 s over 3 runs with `keysAfter` (measured 2026-11-13 on the owner's workstation). Run this from the repository root, on a checkout of each version:

  ```sh
  node --input-type=module - <<'JS'
  import { mkdir, mkdtemp, rm, writeFile } from "node:fs/promises";
  import { tmpdir } from "node:os";
  import { join } from "node:path";
  import { dataFileStore } from "./src/targets/node/file-store.ts";

  const dir = await mkdtemp(join(tmpdir(), "list-bench-"));
  for (let item = 1; item <= 1500; item += 1) {
    const folder = join(dir, "files", "items", String(item));
    await mkdir(folder, { recursive: true });
    await writeFile(join(folder, `post-${item}-1.md`), "x");
    await writeFile(join(folder, `img-${item}-1-1.png`), "x");
    await writeFile(join(folder, `img-${item}-1-2.png`), "x");
  }
  const store = dataFileStore(dir);
  const started = performance.now();
  let cursor = null;
  let keys = 0;
  do {
    const page = await store.list("items/", cursor, 100);
    keys += page.files.length;
    cursor = page.cursor;
  } while (cursor !== null);
  console.log(`${keys} keys, ${Math.round(performance.now() - started)} ms`);
  await rm(dir, { recursive: true });
  JS
  ```

- **Container folder.** `put` writes a temporary file with an exclusively created name in the key's folder, `.tmp-<random>-<name>`, syncs it and renames it into place, so a reader never sees half a file and two puts never share a temporary path. The temporary name is `.tmp-<random>-` (30 bytes: 12 random bytes as hex) and the whole file name, and the key grammar allows 255 - 30 = 225 bytes for a name (`FILE_NAME_MAX`), so a temporary name always fits the 255 bytes of a Linux file name and never cuts the name. No file the app writes has a name above 50 bytes (`post-<job id>-<attempt>.md`, `img-<job id>-<attempt>-<position>.<ext>` with 19-digit ids). `list` reports a temporary file whose embedded name is valid, whatever its length up to 255 bytes, so the cleanup and the Item's delete can remove one that a crash left. The name ends with the key's own file name, so `finalKeyOf` (`src/core/file-keys.ts`) maps a temporary file to the key it will become, and the cleanup protects it exactly as it protects that key. The adapter refuses a symlinked or non-directory component of the path (the `files` root, the `items` folder and the item folder, checked top down with `lstat` before any `mkdir`, list, open or delete, and by one function for all four calls) and a leaf that is not a regular file, by `lstat` and by opening it with `O_NOFOLLOW` and checking the opened handle; a file that disappears between the checks and the open reads as missing; it throws `FileRefused`, and the post text read turns that into no text and a log line. Every resolved path stays inside the folder. The trust assumption is that no other local process swaps the store's folders while the app runs: the check and the open are two steps for a parent folder.
- **Reading post text.** The `items.post_text_key` column names the file that holds an Item's post text. `getItem` in `src/core/item-detail.ts` reads it for `GET /api/items/:id` through `readPostText` (`src/core/post-text.ts`) and drops the key from the answer. A row holds `post_text` or `post_text_key`, never both; a database trigger refuses a row that sets both. A key outside the grammar, a key that names another Item's folder (`foreign-key` in the log), a missing file or a refused file gives `postText: null`, the Item's other fields, status 200, and one JSON log line with the key escaped. Any other storage error, such as a permission error or an outage, is not hidden as missing content and ends in a 500. When a key's file is gone because a refresh committed a new text and deleted the old file after `getItem` read the row, `getItem` reads the Item once more and answers from the new row; a second miss gives `postText: null`. The list and the status poll select neither column. A refresh keeps the old text and file until committed content replaces or clears them, so a failed fetch, an `ok` result with no content and a Paste while a job is open leave the file readable.
- **Writing and publishing a long post text.** The fetch job stores a post text over 1,000,000 UTF-8 bytes (`INLINE_TEXT_BYTES` in `src/core/limits.ts`) in the store, and `readArticle` returns the whole Markdown, so the job and not the reader splits at the limit. The key names the job and its attempt, `items/<item id>/post-<job id>-<attempt>.md`: a job id is never reused, and a job gets a new attempt number whenever a runner takes it over, so a key is never written twice. The one requeue at the same number is a fetch that waits for the GitHub limit without counting an attempt, and it ends before any file is written: `attemptFetch` returns it from the `waiting` member of `Fetched` (`src/core/details.ts`), and `settledContent`, which calls `placePostText` and `prepareMedia`, takes `Concluded`, which has no such member, so `tsc` refuses a `Fetched` there (TS2345, run on 2026-11-10). The other requeue that keeps the number, a stale Digest, needs a `currency` on the outcome, which only the Digest job sets, and a Digest writes no file. A fetch outcome with a `currency`, or a wait that came after `placePostText`, would write one key twice; the second write would replace a file nothing names yet, because the batch that publishes a key also closes the job. One SQL expression builds the key, `postText` of `attemptFileKeys` in `src/core/file-keys.ts`: the claim returns it with the job row as `attemptKey`, the fetch job writes that file, and the cleanup compares each listed key with it, so no second formatter exists. The job writes the file first. Only the guarded finishing batch (the job is `running` at the attempt its runner claimed) sets `post_text` and `post_text_key` together: a long text stores the key and clears `post_text`, a short text stores the text and clears the key, and Other clears both. Nothing else sets a key, so a file that stops being protected never becomes protected again. `finish` in `src/core/job-finish.ts` tells three outcomes apart. After a commit it deletes the files the attempt superseded: the previous post text file, which the key the Item had when the attempt started names, and every image file of the Item's `media` rows when the attempt replaced the media. After a rejected finish (the claim was lost; the log gets one `job-claim-lost` JSON line with the job id and attempt) it deletes the files its own attempt wrote that no row names, never another attempt's file, because the container runs 4 jobs at once and a runner that was taken over can still be inside its attempt while the new attempt holds the row. A finish that throws, so that its result is unknown, deletes nothing, because the batch may have committed and the Item may already name the files; the cleanup pass settles them. A delete that fails is logged (`file-not-deleted`) and left to the cleanup, and the Item and the job stay committed. A long text is searchable like a short one: the batch writes its search parts, and the search reconciler leaves the post-text parts of an Item that has a key alone, because it reads only the row. The reconciler's fingerprint and its guard hold the key, so a publish between its read and its write rejects the write, and the next pass reads the key and indexes the Item again; without the key, a key published after the read left the parts to be deleted and the fingerprint unchanged.
- **Image files and the file route.** An attempt writes its images under `items/<id>/img-<job id>-<attempt>-<position>.<ext>` (see Media in `data-model-outline.md` for the identity). `GET /api/files/items/:id/:name` (`src/http/file-routes.ts`, `servedImage` in `src/core/image-serving.ts`) answers through the same guard as the rest of the API, so an owner session or an `Authorization` agent token reaches it and nothing else does. It builds the key from the two parameters, checks it with `parseFileKey`, and serves it only when a `media` row of that Item has exactly that key, kind `image` and outcome `stored`; every other key answers 404 with the same body: an unpublished or superseded image, a temporary file, a post text file, a key of another Item and anything the grammar refuses. The body is streamed with the stored type, `Content-Length`, and `Content-Disposition: inline; filename="image-<media id>.<ext>"`, a generated name, never the page's. Every answer, the 401 and the 404 included, carries `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin` and `Content-Security-Policy: default-src 'none'; sandbox; frame-ancestors 'none'` (`privateFile` in `src/http/api-middleware.ts` sets them after the handler, so a refusal from the guard has them too). The reasons are in the headers' own specifications: `nosniff` and the stored type keep a browser from reading an image as script ([Fetch, `nosniff`](https://fetch.spec.whatwg.org/#x-content-type-options-header)), `sandbox` and `default-src 'none'` make an image opened as a page inert ([CSP](https://www.w3.org/TR/CSP3/)), `Content-Disposition` follows [RFC 6266](https://www.rfc-editor.org/rfc/rfc6266). `readerUrl` (`src/core/reader-url.ts`) lets exactly these paths through the Reader's URL check.
- **Digest of a long post text.** A text in the store opens a Digest job like a short one, and the Digest job reads the start of it: `readDigestText` in `src/core/digest-source.ts` reads the file through `readPostText` and cuts it to the 14,000 bytes of the Digest input (`cutDigestInput`), so no AI task input comes near 1,000,000 bytes. A file that is missing, refused or unreadable gets the same input-currency rule as a Provider result. When the Item's generation, pending Digest or open fetch job no longer match the ones the attempt read, the attempt ends in a guarded batch that fails, so the runner requeues the job on the current inputs (`stale`) without counting an attempt. When they still match, the attempt fails before any Provider call and the job retries after 30 seconds and 2 minutes; the third read that fails ends in one guarded batch that checks the generation again and sets `failed` and the third attempt, so a refresh that publishes during the read is never failed by the old read. A retry reads the row again, so a refresh that replaced the file mid-run is picked up.
- **Cleanup.** Every tick runs one page of `cleanFiles` (`src/core/file-cleanup.ts`, 100 keys) at the end of the sweep. It lists `items/` from the cursor in `file_cleaning` and looks only at the keys of a kind it owns, which is a post text file, `items/<id>/post-<job id>-<attempt>.md`, or an image, `items/<id>/img-<job id>-<attempt>-<position>.<ext>` (`isSweptKey` in `src/core/file-keys.ts`), or the temporary file of either; it leaves every other key under `items/` alone, so a release that stores a new kind of file there keeps its files when an older release is running. For the keys it owns it asks one query, with the page's keys bound as one JSON parameter, which keys an Item names (`items.post_text_key` or `media.file_key`) or belong to a job that is `running` at the attempt in the key (the condition the finishing guard checks: `postText` of `attemptFileKeys` for a post text, its `imagePrefix` for an image), and deletes every other one of the page, a temporary file included. A temporary file is judged by the key it will become (`finalKeyOf`), so the temporary file of an attempt that is still `running` stays and the temporary file of an attempt that ended or was overtaken goes. A page that deletes cleanly saves the store's next cursor, and `null` after the last page starts a new pass; a delete that fails throws before the save, so the next tick lists the same page again and the tick log shows the error. The key names its attempt, so no table of pending files exists, and the listing finds a file whose writer crashed before any database write. A write that lands after its attempt was overtaken and after the pass went by is found on the next pass.
