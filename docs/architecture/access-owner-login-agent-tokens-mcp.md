# Access: owner login, agent tokens, MCP

- **Setup.** A new Instance shows a setup page that asks for the one-time `SETUP_CODE` first (unless the Instance has none usable, below), then for a new password and, optionally, an export zip to restore (see Export, backup and restore in `export-backup-and-restore.md`). On Cloudflare the deploy button prompts for `SETUP_CODE` and `THREADSIFT_SECRET_KEY` as secrets; in the container both are environment variables, and a missing `SETUP_CODE` makes the container print a generated one as one `Setup code:` log line at each start while no owner exists. Without the code, anyone who finds a fresh public Instance could claim it. A code shorter than 16 characters is refused with 503 on both setup calls, and so is a Worker with no code. Every refusal of the setup and login calls carries one `code` in the error body (the closed list `REFUSAL_CODES` in `src/http/schemas.ts`: `wrong`, `owner-exists`, `locked`, `setup-missing`, `setup-short`, `password-short`, `password-long`), and the web client reads that field instead of guessing from the status. While no owner exists, `GET /api/session` also answers `code` (`set`, `missing` or `short`, from `checkConfiguredCode` in `src/core/setup-code.ts`), so the setup page opens on the block that names the fix instead of asking for a code first. The field reveals only what the 503 already reveals, and it is absent once an owner exists. The single `owner` row (a `CHECK` on `id = 1`, inserted with `ON CONFLICT DO NOTHING`) makes a second setup a 409.
- **The guard.** One middleware on `/api/*` runs before every handler and answers closed by default. The only routes it lets through unauthenticated are `GET /api/session`, `POST /api/setup/code`, `POST /api/setup`, `POST /api/login` and `POST /api/password/reset`, matched by exact method and path in `src/http/access-rules.ts`. It checks, in order: an owner session cookie or an agent token (`bearer-auth`: 400 for a malformed header, an empty one included, 401 for an unknown or revoked token), then that `/api/tokens`, `/api/logout`, `/api/settings`, `/api/password`, `/api/items/:id/read-state`, `/api/items/:id/note` and `/api/items/:id/highlights` (with its `/:highlightId` delete) are not reached with a token (403), because Read state, Highlights and the Note are the owner's, then Hono's `csrf` (403) for requests without an `Authorization` header only, because a bearer token is no ambient credential a foreign page could make the browser send, then `body-limit` (413). `POST /api/items/batch` and `GET /api/imports/{name}` are not on that list, so an agent token reaches both within its scopes (see The import cursor in `data-model-outline.md`). A token call then needs a scope: `requiredScope` in `src/http/access-rules.ts` gives every `GET` and `HEAD` `read` and lists each other method and path with its scope (`docs/spec.md`, Interfaces, names them), and a token call to a non-`GET` route that the list leaves out answers 403, so a route added later is closed to tokens until someone lists it. The guard sets who calls on the request (`principal` in `src/http/token-scopes.ts`: the owner, a token with its scopes, or nobody), and a check that needs the parsed body reads it there: a `digest` sent with a Paste needs `digest` besides `add` (`requirePasteScopes`, in `POST /api/items` and for each entry of `POST /api/items/batch`). The owner's session is not limited by scopes. The OpenAPI document states the scope and a 403 on each scoped route (`scopeNote` and `scopeRefusal` in `src/http/openapi.ts`, from `requiredScope`).
- **Owner login.** The password is counted in code points after NFKC normalization, must be 15 to 1,024 long (NIST SP 800-63B-4 sets 15 as the minimum for a password alone), and is hashed with scrypt from `node:crypto`, which both targets have, at N=2^15, r=8, p=3, one of OWASP's Password Storage settings, with `maxmem: 64 MiB`. Node's default `maxmem` of 32 MiB rejects those settings (`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`, Node 26.11.1, run on 2026-11-04). The OWASP default N=2^17 needs 128 MiB, the whole memory of one Worker. The stored string is `scrypt$N=…$r=…$p=…$salt$key`, so a later cost change still verifies old hashes. A session is a 32-byte random id in the `__Host-threadsift_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, Max-Age 30 days), stored in `sessions` as a SHA-256 digest with its expiry. A use renews the session once less than 29 days remain, so a session lives 30 days from its last use, and an expired one is deleted and refused. The renewal is one `UPDATE ... RETURNING` that matches only an unexpired row (`checkSession` in `src/core/sessions.ts`), so a session that a password change or a logout deleted after the read gets no row back and is refused, with no cookie. A login commits its session in a guarded batch (see Database and search in `database-and-search.md`) that holds only while the password hash it verified is still the stored one, so a login that raced a password change or a reset gets 409 `password-changed` and starts no session. Setup does the same: it inserts the owner, then commits its session in a guarded batch on the hash it wrote, so a reset that lands between the two leaves no session and setup answers 409 `password-changed`. Chromium keeps the `Secure` `__Host-` cookie over `http://127.0.0.1`, so the local suite runs the real cookie.
- **Throttle.** The `throttles` table holds one row for each of `setup`, `login` and `reset`. One atomic upsert counts each attempt before its code or password is checked, so parallel guesses each count and only ten of them are checked; the tenth counted attempt locks the kind for 60 seconds. A locked kind answers 429 with `Retry-After` without checking anything, even for the right code or password, so an attempt during a lock is not counted and does not extend it. Each attempt counted after a lock ends, before a success, doubles the next lock, up to 1 hour. A success deletes the row only when it is the latest counted attempt, so a success that finishes late cannot clear a lock that newer attempts set. The lock is in the database, so a restart keeps it. It is global, not per address, because behind a proxy the app has no address it can trust; the cost is that anyone who can reach the login can lock the owner out of signing in for up to an hour, while sessions already open and agent tokens keep working.
- **Owner-only Proposal routes.** The same rule covers Accept and Reject of a lost-Highlight row, so only the owner's session removes a Highlight. `OWNER_ONLY_PATH` in `src/http/access-rules.ts` matches `/api/proposals/{id}/accept` and `/api/proposals/{id}/reject`, so an agent token gets 403 and a signed-out caller 401 on them. Both have a route. `GET /api/proposals` is open to agent tokens, as the Log and the Index are.
- **Change and reset the password.** `src/core/owner-password.ts` holds both. They end every session and keep the agent tokens, which the signed-in owner revokes on their own.
  - **Change.** `POST /api/password` is owner-only and closed to tokens. It refuses a new password outside 15 to 1,024 characters (400) before it counts an attempt, then verifies the current password under the `login` throttle kind, so a guess through the login or through the change draws on one budget (OWASP Authentication Cheat Sheet: ask for the current password to change it, and count lockout per account). A wrong current password answers 403 `wrong`, never 401, because the web client treats a 401 as signed out. One guarded batch sets the new hash, deletes every session and inserts the caller's new session, and it holds only while the stored hash is still the one that was verified and the calling session still exists. The new session is prepared without writes, and its cookie is sent only after the commit, replacing the guard's renewal cookie if both are set (OWASP Session Management Cheat Sheet: renew the session id on a password change). A call that loses the race gets 409 `password-changed` and changes nothing. A change runs two scrypt hashes in one request.
  - **Reset.** `POST /api/password/reset` is public and works only while the server holds `PASSWORD_RESET_CODE`: a container environment variable read at start, or a Worker secret read from each request's `env` (`src/targets/worker/index.ts` keeps one app per code value and never reads the code from the cached ports). It is an operator credential on the owner's own server, like `SETUP_CODE`, so it has no expiry. That departs on purpose from the Forgot Password Cheat Sheet's expiry advice, and its single use, the 32-character minimum and the removal after use make up for it. The code is compared by SHA-256 digests with `crypto.equal`, under its own `reset` throttle kind that counts each attempt before the check. The reset reads the stored hash before it hashes the new password. One guarded batch, which holds only while that hash is still the stored one and the code is unspent, inserts the code's digest into `spent_reset_codes`, sets the hash, deletes every session and clears the `login` throttle row, because that lock protected the old password. A spent digest stays refused after later codes are used, so setting an old code again does nothing. When the batch fails, the reset answers `reset-used` if the code is spent and `password-changed` otherwise, so a reset never overwrites a change that committed after it read the hash. The reset starts no session and sets no cookie (Forgot Password Cheat Sheet: do not log the user in automatically).
  - **States the routes reveal.** Wrong current password 403 `wrong`; wrong reset code 403 `wrong`; no reset code 503 `reset-missing`; a code under 32 characters 503 `reset-short`; a spent code 409 `reset-used`; no owner 409 `no-owner`; a lost race 409 `password-changed` (also from setup and reset); a change without a live session 401; locked 429 with `Retry-After`; a new password outside 15 to 1,024 characters 400. Every refusal leaves the password, the sessions and the spent codes as they were. The 503 reveals only whether a code exists, as the setup 503 does.
  - **Rules from outside.** NIST SP 800-63B-4 3.1.1.2 and 3.2.2 are cited as selected guidance (15 characters, no composition rules, no forced rotation, an attempt limit), not as full conformance; its section 4 on recovery was not read. Cloudflare's `wrangler secret put` deploys a secret at once and `wrangler secret delete` removes it (Workers docs, Secrets). A run on a throwaway pull request copy (wrangler 4.156.0, 2026-11-07) agreed: after `put` of a code, a reset with it answered 204; after `put` of a second code, the first answered 403 `wrong` and the second 204; after `delete`, a code never used answered 503 `reset-missing`.
- **Screen states.** `useGuard` (`web/src/use-form.ts`) sets a ref before its first await, so a second press in the same frame does nothing while the first request is on its way, where a `busy` state alone is still false until the next render; the token list, Back to code and the password forms use it, and a button the guard blocks keeps `aria-disabled` instead of `disabled`, so focus stays on it. The Revoke question, the GitHub, Grok Bot and Reddit sections and the Proposals rows keep one state union each in a reducer, run through `useFlow` (`web/src/use-flow.ts`), which also keeps the state in a ref so the reducer refuses a second press in the same frame (`web/src/token-revoke.ts`, `use-settings-action.ts`, `proposal-row-state.ts`). The Revoke failure belongs to the token the owner asked about and clears on Cancel or on asking about another token. Cancel and asking about another token also work while a revoke is on its way; the answer of that revoke then removes the token from the list, and a refusal changes nothing, because only the question still open takes it (`request` in `web/src/token-revoke.ts`). A failed token list load keeps its message after a token is added. The session check (`web/src/use-session-view.ts`) aborts after `CHECK_DEADLINE_MS` (10 s) and ends on the unreachable screen with Retry, and a newer check aborts the older one; an explicit sign-in or sign-out supersedes the check in flight, so that check's late answer changes nothing (`web/src/session-state.ts`). Opening the reset screen again clears the notice that a reset finished.
- **Agent tokens.** One random token per connected agent, `tsa_` and 32 random bytes in base64url, shown once, stored as a SHA-256 hash (the token is high-entropy, so a fast hash is enough), revocable in settings. `last_used_at` updates at most once an hour through a conditional `UPDATE`, so a busy agent does not write on every request. The Extension, Grok Bot and MCP clients use them as bearer tokens. Each token holds scopes in the JSON column `agent_tokens.scopes` (`docs/spec.md`, Token scopes; the routes each scope covers are in Interfaces), which `src/core/tokens.ts` parses with `ScopeListSchema` where it leaves the database: a token whose scopes cannot be read fails every call (fail closed) and the token list shows it with no scopes, so the owner can revoke it. Token creation always writes its scopes, and `0049_agent-token-scopes.sql` adds the column with a default of all four, because SQLite `ADD COLUMN ... NOT NULL` needs a default and a token that exists before the migration must keep every call. A rollback drops the limit (see CI, releases and rollback in `ci-releases-and-rollback.md`, Token scopes version). The Grok Bot settings hold only the routine's address and key and no token; the route that takes AI task results will use a credential made for each task.
- **Secrets at rest.** Provider keys, the GitHub token, the Grok Bot webhook key, the vault token and the owner's Reddit session cookie are sealed with AES-GCM (WebCrypto, on both targets) under `THREADSIFT_SECRET_KEY`, which the app reads from its environment and never shows. The Grok Bot key lives in `grok_bot_settings.sealed_key`; no route returns it, and the address, which the bot's docs call partly secret, is returned only to the owner's session (`/api/settings` is closed to agent tokens). A Save without a key keeps the stored key only when the address is unchanged, so a mistyped address never receives the old key.
- **The share route.** `/share` (`src/http/share-routes.ts`) is the manifest's `share_target` action. It sits outside `/api/*`, so the guard never sees it and an agent token never reaches it. It takes the form `POST` that the manifest declares and a `GET` with the same fields, and it writes only for a `POST` that has all three: an owner session cookie, `Sec-Fetch-Site: same-origin` and an `Origin` whose host equals the request's host (`src/http/share-trust.ts`). Missing metadata, `Origin: null` and a token never authorize a write. The session cookie is `SameSite=Lax`, so a cross-site `POST` carries no cookie, and the two header checks stop a same-site page on another port, whose `POST` does carry it. The pattern is the `csrf()` default of the installed Hono 4.13.16 (`node_modules/hono/dist/middleware/csrf/index.js`), made stricter: Hono lets a request pass on either header, this route needs both. It compares the host of the `Origin` and not its scheme, because the container sees plain HTTP behind the owner's TLS proxy while the browser's `Origin` says `https`, and `Sec-Fetch-Site: same-origin` already covers the scheme. The 64 KiB body limit applies, and a body that cannot be decoded, such as `multipart/form-data` with no boundary, answers the same `no-store` `303` with `notice=invalid` (`src/http/share-fields.ts`). A trusted share calls `paste` (`src/core/paste.ts`), the core function that `POST /api/items` calls, and answers `303` to `/?saved=<id>`, or `/?refreshed=<id>` for a known Item that had been fetched. Every other arrival writes nothing and answers `303` to `/?link=<link>`, with `notice=invalid`, `private` or `empty` when the trusted share had nothing valid to save (`src/core/share-address.ts` owns the address in both directions). The link is the first `http:` or `https:` address in `url`, then `text`, then `title`, without trailing `.,;:!?)]}'"` (`src/core/shared-link.ts`); an address that ends in `)`, such as a Wikipedia title with a bracket, loses it, which is the cost of the rule. The address carries at most 1,000 UTF-16 code units, so the redirect stays under Node's default header limit of 16 KiB even when every unit percent-encodes to 9 bytes, the worst case for a three-byte UTF-8 character (Node docs, `--max-http-header-size`); a longer link is cut to that and carries `notice=invalid`.
- **Request limits.** Hono's `body-limit` middleware caps request bodies on both targets, because Node has no cap of its own and Cloudflare's cap depends on the zone's plan (100 MB on Free and Pro, Workers docs, Limits). Every route takes 64 KiB, `/mcp` included, except `POST /api/items`, which takes 8 MiB (413) because it carries a thread; its `content` field is then limited to 4 MiB (413) and must parse as a thread of the link, a Reddit thread or an X post with its replies (400, with the reason). `GET /api/items/:id` returns the published `comments` view: the reported and received counts, the Kept count and the nodes in tree order.
- **MCP.** `/mcp` serves Streamable HTTP on both targets through `createMcpHandler` from `@modelcontextprotocol/server` 2.4.0 (`src/http/mcp-route.ts`; the SDK's Hono guide mounts `handler.fetch(c.req.raw, ...)` and names Workers as supported). One handler serves every request, but its factory builds and registers a fresh `McpServer` for each, and the app keeps no session registry: the SDK changelog for 2.3.0 records that one server shared by overlapping requests fails them. The handler serves the 2026-07-28 per-request exchange and, statelessly, the 2025 handshake. It checks no token, no Host and no Origin, and it reads up to 4 MiB, so `mcpGate` (`src/http/mcp-gate.ts`) and the `bodyCap` of the guard run in front of it. The tools are not in OpenAPI: `/api/openapi.json` stays the REST contract, and an MCP client finds the tools with `tools/list`.
  - **Gate.** `/mcp` is outside `/api/*`, so the guard never sees it. The gate runs on every HTTP request, after `initialize` as well, and caches nothing, so a token the owner revokes fails on the next request of a client that is still connected. It accepts the Authorization header only: no cookie, query string or body field, and a valid owner cookie never replaces a missing, malformed or revoked token. No credentials, or a cookie alone, answers 401 with `WWW-Authenticate: Bearer`; a malformed header, an empty one included, answers 400; an unknown or revoked token answers 401, the same split as the guard. The check is `verifyToken` in `src/core/tokens.ts`, the function the guard uses, so the hash and the `last_used_at` rule have one copy. The verified token reaches the handler as `authInfo` (`clientId` `agent-token-<id>`). Its `scopes` are the token's scopes. Each tool registers a `scopeChallenge` built with the SDK's `requireScopes` (`src/http/mcp-read-tools.ts`, `src/http/mcp-add-tool.ts`), which the SDK runs before the tool, and a call without the scopes answers 403 with `WWW-Authenticate: Bearer error="insufficient_scope"`. `pasteScopes` (`src/core/scopes.ts`) is the one copy of the Paste rule for HTTP and MCP.
  - **Host and Origin.** The SDK's validators match hostnames without a port, so the gate has its own rules, and none of them reads the allowlist from the request. With `THREADSIFT_PUBLIC_ORIGIN` set, `Host` must equal that origin's host with its port, and a present `Origin` must equal the whole origin: scheme, host and port. Loopback is then refused, so a client on the same machine uses the public address. Without it, `Host` must be `localhost`, `127.0.0.1` or `[::1]` on any port and a present `Origin` must be a loopback origin, so reaching `/mcp` from another machine needs `THREADSIFT_PUBLIC_ORIGIN`. A request without `Origin` passes, because CLI clients send none; `Origin: null`, a malformed one and an unlisted one answer 403, and so does a `Host` header that the rules refuse while the request address passes: the gate checks both. The gate answers 403 before it asks for credentials.
  - **Request size.** The whole request is capped at 64 KiB before any parsing (`BODY_LIMIT_BYTES`, `src/core/limits.ts`, the guard's limit), also without `Content-Length`, and a larger one answers 413 and writes nothing. The SDK's 4 MiB default never applies.
  - **Tools.** `search`, `read` and `add` call the same core code as `GET /api/items`, `GET /api/items/:id` and `POST /api/items`, through the functions those routes call (`readItemPage` and `readItem` in `src/http/item-read.ts`, `paste`), and answer the same JSON as `structuredContent`, which each tool's `outputSchema` describes. `search` and `read` are marked read-only. `read` returns the whole detail view: the Digest, the comment tree with a highlighted comment that is no longer Kept, the Highlights with their revisions and the Note with its revision. No tool writes a Highlight, a Note or a Read state, which stay the owner's. `add` takes `url` and an optional `digest`, not `content`, `page` or `fill`, and keeps the 503 refusal while a data step runs. It answers `{item, url}` and does not say whether the Item was new.
  - **Errors.** A gate refusal is an HTTP status. A malformed JSON-RPC message or an unknown tool is a JSON-RPC error from the SDK. A missing Item, a refused host, the data-step refusal and an argument the input schema rejects (an invalid link, Digest or cursor) are tool results with `isError: true`; the first three carry the REST route's text and the last carries the SDK's validation message. Any other failure is logged by class name and answers the tool result `Internal error`, so no exception text reaches the client.
  - **Disconnect.** A client that goes away releases its request and its stream. An `add` whose Paste committed keeps its Item and its jobs, which finish through the job runner as for any Paste.
  - **Lockout.** Agent tokens take no part in the login throttle, and `/mcp` has no rate limit of its own.
  - OAuth for Grok Bot's catalog comes later (`docs/spec.md`, Grok Bot).
