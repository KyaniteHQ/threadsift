# Access: owner login, agent tokens, MCP

- **Setup.** A new Instance shows a setup page that asks for the one-time `SETUP_CODE` first (unless the Instance has none usable, below), then for a new password, then offers the choice between Start with an empty library and Restore a backup (`StartStep` in `web/src/StartStep.tsx`). The choice shows once, right after the password is created, because the page holds the step in its own state: a reload signs the owner in to the library. Restore a backup opens `/settings#backup`, the Backup section, where the Restore is offered while the library is empty (see Export, backup and restore in `export-backup-and-restore.md`). The Cloudflare deploy button prompts for `SETUP_CODE` and `THREADSIFT_SECRET_KEY` as secrets (see `cloudflare-deploy-button.md`). In the container both are environment variables. If `SETUP_CODE` is missing, the container prints a generated one as one `Setup code:` log line at each start while no owner exists. Without the code, anyone who finds a fresh public Instance could claim it. A code shorter than 16 characters is refused with 503 on both setup calls, and so is a Worker with no code. Every refusal of the setup and login calls carries one `code` in the error body (the closed list `REFUSAL_CODES` in `src/core/kinds.ts`; `src/core/access-refusal.ts` gives each refusal its status, code and text, and `turnedAway` in `src/http/refusals.ts` renders it), and the web client reads that field instead of guessing from the status. While no owner exists, `GET /api/session` also answers `code` (`set`, `missing` or `short`, from `anonymousState` in `src/core/owner.ts`), so the setup page opens on the block that names the fix instead of asking for a code first. The field reveals only what the 503 already reveals, and it is absent once an owner exists. The single `owner` row makes a second setup a 409.
- **Route access.** Each route states who may call it where it is declared, with `access(...)` from `src/http/access.ts`, and the same statement sets its body cap and its cache headers. `createApp` stops at start-up unless `withPorts` is the first registration and the first handler of every route is an `access(...)` gate (`verifyPolicies` in `src/http/policy-check.ts` reads Hono's `app.routes`), so a route added later is closed to everyone until it names its callers. The check knows a gate and `withPorts` by identity, so a function that only carries a `who` property does not pass. It also stops the app when a route names `read` on a method other than `GET` or `HEAD`, another scope on a `GET` or `HEAD`, or any scope on `ALL`, so every read stays under the `read` scope. A mounted app sets no `onError`: Hono wraps its handlers, the check finds no gate in the wrapper and stops the app. The app's one `onError` is `answerFailure`. The classes are:
  - **`owner`.** The owner's session alone. An agent token gets 403, because Read state, Highlights, the Note, Settings, Export, Restore and the Proposal decisions are the owner's.
  - **A scope: `read`, `add`, `digest`, `delete` or `reddit`.** The owner's session, or an agent token that holds the scope (403 otherwise). The owner's session is not limited by scopes. `POST /api/items/batch` and `GET /api/imports/{name}` are not owner-only, so an agent token reaches both within its scopes (see The import cursor in `data-model-outline.md`). `scopeNote` and `scopeRefusal` (`src/http/openapi.ts`) write the scope into the route's description and 403 answer in `GET /api/openapi.json` from the same `access(...)` value.
  - **`anyone`.** The session check, the first-run setup, the sign-in and the password reset.
  - **`callback`.** The three task routes of the Grok Bot (below).
  - **`self`.** `/mcp` and `/share`, which check their own caller; the gate only caps the body. A check of its own goes through `ownCheck(...)` in front of the gate.

  For `owner` and a scope the gate checks, in order: an owner session cookie or an agent token (400 for a malformed header, an empty one included, 401 for an unknown or revoked token or for no credentials), then that a token is allowed on the route (403), then Hono's `csrf` (403) for requests without an `Authorization` header only, because a bearer token is no ambient credential a foreign page could make the browser send, then `body-limit` (413). The credentials come before the cap, so a call with no access and a large body gets 401 and not 413. `anyone` and `callback` routes run `csrf` and then the cap. A `HEAD` request to one of them is checked first as a `read` call, so a `HEAD` is never public. A check that needs the parsed body reads who calls from `principal` (`src/http/token-scopes.ts`): a `digest` sent with a Paste needs `digest` besides `add` (`requirePasteScopes`, in `POST /api/items` and for each entry of `POST /api/items/batch`).

  `refusedBearer` (`src/http/bearer.ts`) returns the bearer refusals as JSON answers, and the refusal that Hono's `csrf` throws as an `HTTPException` becomes a JSON answer in `answerFailure` (`src/http/refusals.ts`, the app's one error handler), so the cache headers and the sign-in redirect of a route cover its refusals. A `callback` route is the exception: it sets its cache headers on the answers of its credential step and of the handler, not on the refusals before it (401 for a `HEAD`, 403 from `csrf`, 413 from the cap).

  A call to `/api/*` that matches no route goes through `unrouted()`: the owner's session, or for `GET` and `HEAD` a token with `read`, then 404; a token on any other method gets 403 and a call with no credentials 401. `UNROUTED_PATHS` in `src/http/unrouted.ts` is the one path table left. It holds the owner-only prefixes (a token gets 403 on every method), the task callback paths (a caller with a session or a token gets the credential refusal of the task routes and not 404) and the paths whose answers carry cache headers. A route that exists never reads this table.
- **The task callback credential.** `GET /api/ai-tasks/{id}`, `POST /api/ai-tasks/{id}/result` and `POST /api/ai-tasks/{id}/intake` are the only routes declared `access("callback")`. They take a per-task credential, and the gate looks for no session or agent token before it. Its credential step (`callbackTask` in `src/http/task-credential.ts`, which calls `callbackTaskOf` in `src/core/callback-credential.ts`) finds the task by the SHA-256 digest of the secret (`ai_tasks.callback_hash`) and answers 401 for a missing, malformed or unknown credential, one of another task's included, because the lookup matches the path's `{id}` and the digest together. An owner session or an agent token without the task's credential gets 403, so no other principal can answer a task. The secret is made when the task is sent and shown once, in the webhook body only, and a resend of the same task replaces it. A task keeps its digest after it closes, so a late answer finds the task and gets 409 and not 401. Hono's `csrf` and the body cap run before the credential step, so `csrf` still refuses a form content type from another origin (403). The credential is a Threadsift secret in the bot's hands: it reads and answers one task and nothing else.
- **Owner login.** The password is counted in code points after NFKC normalization, must be 15 to 1,024 long (NIST SP 800-63B-4 sets 15 as the minimum for a password alone), and is hashed with scrypt from `node:crypto`, which both targets have, at N=2^15, r=8, p=3, one of OWASP's Password Storage settings, with `maxmem: 64 MiB`. Node's default `maxmem` of 32 MiB rejects those settings (`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`, Node 26.11.1, run on 2026-11-04). The OWASP default N=2^17 needs 128 MiB, the whole memory of one Worker. The stored string is `scrypt$N=…$r=…$p=…$salt$key`, so a later cost change still verifies old hashes. A session is a 32-byte random id in the `__Host-threadsift_session` cookie, stored in `sessions` as a SHA-256 digest with its expiry. A use renews the session once less than 29 days remain, so a session lives 30 days from its last use, and an expired one is deleted and refused. The renewal is one `UPDATE ... RETURNING` that matches only an unexpired row (`checkSession` in `src/core/sessions.ts`), so a session that a password change or a logout deleted after the read gets no row back and is refused, with no cookie. A login commits its session in a guarded batch (see Database and search in `database-and-search.md`) that holds only while the password hash it verified is still the stored one, so a login that raced a password change or a reset gets 409 `password-changed` and starts no session. Setup does the same: it inserts the owner, then commits its session in a guarded batch on the hash it wrote, so a reset that lands between the two leaves no session and setup answers 409 `password-changed`. Chromium keeps the `Secure` `__Host-` cookie over `http://127.0.0.1`, so the local suite runs the real cookie.
- **Throttle.** The `throttles` table holds one row for each of `setup`, `login` and `reset`. One atomic upsert counts each attempt before its code or password is checked, so parallel guesses each count and only ten of them are checked; the tenth counted attempt locks the kind for 60 seconds. A locked kind answers 429 with `Retry-After` without checking anything, even for the right code or password, so an attempt during a lock is not counted and does not extend it. Each attempt counted after a lock ends, before a success, doubles the next lock, up to 1 hour. A success deletes the row only when it is the latest counted attempt, so a success that finishes late cannot clear a lock that newer attempts set. The lock is in the database, so a restart keeps it. It is global, not per address, because behind a proxy the app has no address it can trust; the cost is that anyone who can reach the login can lock the owner out of signing in for up to an hour, while sessions already open and agent tokens keep working.
- **Owner-only Restore routes.** Every Restore route is declared `access("owner")`, so an agent token gets 403 and a signed-out caller 401 on them (`src/http/restore-routes.ts`), because a leaked token must not write a whole library. `PUT /api/restore/{id}/parts/{n}` names its own body cap, the part size (`PART_CAP` in `src/http/access.ts`).
- **Owner-only Proposal routes.** `POST /api/proposals/{id}/accept` and `POST /api/proposals/{id}/reject` are declared `access("owner")`, so only the owner's session removes a Highlight through a lost-Highlight row. `GET /api/proposals` is open to agent tokens, as the Log and the Index are.
- **Change and reset the password.** `src/core/owner-password.ts` holds both. They end every session and keep the agent tokens, which the signed-in owner revokes on their own.
  - **Change.** `POST /api/password` is owner-only and closed to tokens. It refuses a new password outside 15 to 1,024 characters (400) before it counts an attempt, then verifies the current password under the `login` throttle kind, so a guess through the login or through the change draws on one budget (OWASP Authentication Cheat Sheet: ask for the current password to change it, and count lockout per account). A wrong current password answers 403 `wrong`, never 401, because the web client treats a 401 as signed out. One guarded batch sets the new hash, deletes every session and inserts the caller's new session, and it holds only while the stored hash is still the one that was verified and the calling session still exists. The new session is prepared without writes, and its cookie is sent only after the commit, replacing the renewal cookie of the route's access gate if both are set (OWASP Session Management Cheat Sheet: renew the session id on a password change). A call that loses the race gets 409 `password-changed` and changes nothing. A change runs two scrypt hashes in one request.
  - **Reset.** `POST /api/password/reset` is public and works only while the server holds `PASSWORD_RESET_CODE`: a container environment variable read at start, or a Worker secret read from each request's `env` (`src/targets/worker/index.ts` keeps one app per code value and never reads the code from the cached ports). It is an operator credential on the owner's own server, like `SETUP_CODE`, so it has no expiry. That departs on purpose from the Forgot Password Cheat Sheet's expiry advice, and its single use, the 32-character minimum and the removal after use make up for it. The code is compared by SHA-256 digests with `crypto.equal`, under its own `reset` throttle kind that counts each attempt before the check. The reset reads the stored hash before it hashes the new password. One guarded batch, which holds only while that hash is still the stored one and the code is unspent, inserts the code's digest into `spent_reset_codes`, sets the hash, deletes every session and clears the `login` throttle row, because that lock protected the old password. A spent digest stays refused after later codes are used, so setting an old code again does nothing. When the batch fails, the reset answers `reset-used` if the code is spent and `password-changed` otherwise, so a reset never overwrites a change that committed after it read the hash. The reset starts no session and sets no cookie (Forgot Password Cheat Sheet: do not log the user in automatically).
  - **States the routes reveal.** Every refusal leaves the password, the sessions and the spent codes as they were. The 503 for a missing or short reset code reveals only whether a code exists, as the setup 503 does.
  - **Rules from outside.** NIST SP 800-63B-4 3.1.1.2 and 3.2.2 are cited as selected guidance (15 characters, no composition rules, no forced rotation, an attempt limit), not as full conformance; its section 4 on recovery was not read. Cloudflare's `wrangler secret put` deploys a secret at once and `wrangler secret delete` removes it (Workers docs, Secrets). A run on a throwaway pull request copy (wrangler 4.156.0, 2026-11-07) agreed: after `put` of a code, a reset with it answered 204; after `put` of a second code, the first answered 403 `wrong` and the second 204; after `delete`, a code never used answered 503 `reset-missing`.
- **Screen states.** `useGuard` (`web/src/use-form.ts`) sets a ref before its first await, so a second press in the same frame does nothing while the first request is on its way, where a `busy` state alone is still false until the next render; a button the guard blocks keeps `aria-disabled` instead of `disabled`, so focus stays on it. The Revoke question, the budget change on a token row and the GitHub, Grok Bot and Reddit sections run through `useFlow` (`web/src/use-flow.ts`), which keeps the state in a ref for the same reason; the sections reach it by way of `web/src/use-settings-action.ts`, and the Proposals page holds one `busyId` ref for all its rows (`web/src/use-proposal-presses.ts`). Cancel and asking about another token work while a revoke is on its way; the answer of that revoke then removes the token from the list and ends any question still open about it, so a second revoke of it that answers 404 shows no failure (`reduceRevoke` in `web/src/token-revoke.ts`, `revokeToken` in `web/src/access-api.ts`). The session check (`web/src/use-session-view.ts`) aborts after `CHECK_DEADLINE_MS` (10 s) and ends on the unreachable screen with Retry, except that an unreachable answer leaves the signed-in view in place (`answeredView` in `web/src/session-state.ts`); an explicit sign-in or sign-out supersedes the check in flight, so that check's late answer changes nothing.
- **Agent tokens.** One random token per connected agent, `tsa_` and 32 random bytes in base64url, shown once, stored as a SHA-256 hash (the token is high-entropy, so a fast hash is enough), revocable in settings. `last_used_at` updates at most once an hour through a conditional `UPDATE`, so a busy agent does not write on every request. The Extension, Grok Bot and MCP clients use them as bearer tokens. Each token holds scopes in the JSON column `agent_tokens.scopes` (see `docs/spec.md`, Access, Token scopes; the routes each scope covers are the ones whose `access(...)` names it), which `src/core/tokens.ts` parses with `ScopeListSchema` where it leaves the database. A token with unreadable scopes fails every call (fail closed), and the token list shows it with no scopes so the owner can revoke it. The Grok Bot settings hold no token; the routes that take AI task results use a credential made for each task (`src/http/task-credential.ts`).
- **Daily budget.** `withinBudget` in `src/core/agent-token-budget.ts` runs for `paste`, `pasteLink` and the batch through `admitted` (`src/core/admission.ts`), which also holds the restore gate; `tokenItemsToday` supplies the same count to Settings. The count comes from the Items a token added in the current UTC day. A deleted Item frees its place, a save that fails after the insert still counts, and a refresh never counts. The owner's session and tokens with no budget have no cap. Known links, including short-link aliases, do not count. A limited request reads the count once before saving and is refused whole when its possibly new Items would cross the cap. Two requests at the same moment can read the same count and both pass, exceeding the limit by one request's links; a batch holds up to `BATCH_LINKS_MAX` links (`src/core/import-contract.ts`, enforced in `src/http/batch-schemas.ts`). A held link deleted during a batch and a batch that crosses midnight are not checked again. This is sufficient for one owner's agents. A refusal answers 429 with `code: budget-spent` and `Retry-After` until the next UTC midnight.
- **Secrets at rest.** Provider keys, the GitHub token, the Grok Bot webhook key and the owner's Reddit session cookie are sealed with AES-GCM (WebCrypto, on both targets) under `THREADSIFT_SECRET_KEY`, which the app reads from its environment and never shows. No route returns the Grok Bot key, and the address, which the bot's docs call partly secret, is returned only to the owner's session (`/api/settings` is closed to agent tokens). A Save without a key keeps the stored key only when the address is unchanged, so a mistyped address never receives the old key. The Reddit session is opened only by `openedSession` in `src/core/reddit-account.ts` and passed to the adapter as an argument, put in one `Cookie` header that goes only to `www.reddit.com`, and never stored in a job row or a task input, put in an error or logged. `GET /api/settings/reddit-account` answers a state and never the value, a state of `unreadable` (the sealing key changed) sends no request, and a request that answers a redirect is never followed with it.
- **The share route.** `/share` (`src/http/share-routes.ts`) is the manifest's `share_target` action. It is declared `access("self")`, so the gate checks no session, token or origin and only caps the body, because the route decides for itself who is trusted; an agent token never writes through it. It writes only for a `POST` that has all three: an owner session cookie, `Sec-Fetch-Site: same-origin` and an `Origin` whose host equals the request's host (`sentByOwnPage` in `src/core/own-origin.ts`, which `src/http/share-trust.ts` and the OpenRouter Start route call). Missing metadata, `Origin: null` and a token never authorize a write. The session cookie is `SameSite=Lax`, so a cross-site `POST` carries no cookie, and the two header checks stop a same-site page on another port, whose `POST` does carry it. The pattern is the `csrf()` default of the installed Hono (`node_modules/hono/dist/middleware/csrf/index.js`), made stricter: Hono lets a request pass on either header, this route needs both. It compares the host of the `Origin` and not its scheme, because the container sees plain HTTP behind the owner's TLS proxy while the browser's `Origin` says `https`, and `Sec-Fetch-Site: same-origin` already covers the scheme. A trusted share calls `pasteLink` (`src/core/paste.ts`) as the owner, which saves a link with no content or page the way `paste` does for `POST /api/items` when the request holds only a link, and answers `303` to `/?saved=<id>`, or `/?refreshed=<id>` for a known Item that had been fetched. Every other arrival writes nothing and answers `303` to `/?link=<link>`, with a `notice` from `PREFILL_NOTICES` when the trusted share saved nothing. The link is the first `http:` or `https:` address in `url`, then `text`, then `title` (`src/core/shared-link.ts`); an address that ends in `)`, such as a Wikipedia title with a bracket, loses it, which is the cost of the rule. The address carries at most 1,000 UTF-16 code units, so the redirect stays under Node's default header limit of 16 KiB even when every unit percent-encodes to 9 bytes, the worst case for a three-byte UTF-8 character (Node docs, `--max-http-header-size`); a longer link is cut to that and carries `notice=invalid`.
- **Request limits.** Hono's `body-limit` middleware caps request bodies on both targets, because Node has no cap of its own and Cloudflare's cap depends on the zone's plan (100 MB on Free and Pro, Workers docs, Limits). Every route takes 64 KiB, `/mcp` included, unless its `access(...)` names another cap (`src/http/access.ts`). `POST /api/items` takes 8 MiB (413) because it carries a thread. The AI task callbacks take 256 KiB (`GET` and `result`) or 8 MiB (`intake`), and a Restore part takes the part size. The cap holds without `Content-Length` too, a larger body answers 413 and writes nothing, and the SDK's 4 MiB default for `/mcp` never applies.
- **MCP.** `/mcp` serves Streamable HTTP on both targets through `createMcpHandler` from `@modelcontextprotocol/server` (`src/http/mcp-route.ts`; the SDK's Hono guide mounts `handler.fetch(c.req.raw, ...)` and names Workers as supported). One handler serves every request, but its factory builds and registers a fresh `McpServer` for each, and the app keeps no session registry: the SDK changelog for 2.3.0 records that one server shared by overlapping requests fails them. The handler serves the 2026-07-28 per-request exchange and, statelessly, the 2025 handshake. It checks no token, no Host and no Origin, and it reads up to 4 MiB, so `mcpGate` (`src/http/mcp-gate.ts`) and the 64 KiB cap of `access("self")` run in front of it. The tools are not in OpenAPI: `/api/openapi.json` stays the REST contract, and an MCP client finds the tools with `tools/list`.
  - **Gate.** `/mcp` is declared `ownCheck(mcpGate(ports))` and then `access("self")`: `ownCheck` (`src/http/access.ts`) names `mcpGate` as the route's own check, so it runs first and the start-up check finds a gate in front, and `access("self")` adds the cap and no check of its own. `mcpGate` runs on every HTTP request, after `initialize` as well, and caches nothing, so a token the owner revokes fails on the next request of a client that is still connected. It accepts the Authorization header only: no cookie, query string or body field, and a valid owner cookie never replaces a missing, malformed or revoked token. The statuses are 401 with `WWW-Authenticate: Bearer` for no Authorization header, 401 with `Bearer error="invalid_token"` for an unknown or revoked token, and 400 with `Bearer error="invalid_request"` for a malformed header or with `Bearer realm=""` for an empty one, which `refusedBearer` (`src/http/bearer.ts`) answers for the REST routes too. The header is read and the token verified by `presentedToken` in `src/core/bearer.ts`, which the REST routes use, and it calls `verifyToken` in `src/core/tokens.ts`, so the parse, the hash and the `last_used_at` rule have one copy. Each tool registers a `scopeChallenge` built with the SDK's `requireScopes`, which the SDK runs before the tool, and a call without the scopes answers 403 with `WWW-Authenticate: Bearer error="insufficient_scope"`. `pasteScopes` (`src/core/scopes.ts`) is the one copy of the Paste rule for HTTP and MCP.
  - **Host and Origin.** The SDK's validators match hostnames without a port, so the gate has its own rules, and none of them reads the allowlist from the request. With `THREADSIFT_PUBLIC_ORIGIN` set, `Host` must equal that origin's host with its port, and a present `Origin` must equal the whole origin: scheme, host and port. Loopback is then refused, so a client on the same machine uses the public address. Without it, `Host` must be `localhost`, `127.0.0.1` or `[::1]` on any port and a present `Origin` must be a loopback origin, so reaching `/mcp` from another machine needs `THREADSIFT_PUBLIC_ORIGIN`. A request without `Origin` passes, because CLI clients send none; `Origin: null`, a malformed one and an unlisted one answer 403, and so does a `Host` header that the rules refuse while the request address passes: the gate checks both. The gate answers 403 before it asks for credentials.
  - **Tools.** `search`, `read` and `add` call the same functions as `GET /api/items`, `GET /api/items/:id` and `POST /api/items` (`readItemPage` and `readItem` in `src/http/item-read.ts`, `paste`) and answer the same JSON as `structuredContent`. No tool writes a Highlight, a Note or a Read state, which stay the owner's. `add` takes `url` and an optional `digest`, not `content`, `page` or `fill`, and keeps the 503 refusal while a restore runs. It answers `{item, url}` and does not say whether the Item was new.
  - **Errors.** A gate refusal is an HTTP status. A missing Item, a refused host, a token that has added its daily budget, the restore refusal and an argument the input schema rejects are tool results with `isError: true`; the first four carry the REST route's text and the last carries the SDK's validation message. Any other failure is logged by class name and answers the tool result `Internal error`, so no exception text reaches the client.
  - **Disconnect.** A client that goes away releases its request and its stream. An `add` whose Paste committed keeps its Item and its jobs, which finish through the job runner as for any Paste.
  - **Lockout.** Agent tokens take no part in the login throttle. `/mcp` has no rate limit of its own, and its `add` tool draws on the token's daily budget (see Daily budget); `search` and `read` have no limit.
  - OAuth for Grok Bot's catalog comes later (`docs/spec.md`, Later (not in the first release)).
