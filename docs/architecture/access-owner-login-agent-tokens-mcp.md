# Access: owner login, agent tokens, MCP

- **Setup.** A new Instance shows a setup page that asks for the one-time `SETUP_CODE` first (unless the Instance has none usable, below), then for a new password, then offers the choice between Start with an empty library and Restore a backup (`StartStep` in `web/src/StartStep.tsx`). The choice shows once, right after the password is created, because the page holds the step in its own state: a reload signs the owner in to the library. Restore a backup opens `/settings#backup`, the Backup section, where the Restore is offered while the library is empty (see Export, backup and restore in `export-backup-and-restore.md`). The Cloudflare deploy button that would prompt for `SETUP_CODE` and `THREADSIFT_SECRET_KEY` as secrets is not built (see `cloudflare-deploy-button.md`); in the container both are environment variables, and a missing `SETUP_CODE` makes the container print a generated one as one `Setup code:` log line at each start while no owner exists. Without the code, anyone who finds a fresh public Instance could claim it. A code shorter than 16 characters is refused with 503 on both setup calls, and so is a Worker with no code. Every refusal of the setup and login calls carries one `code` in the error body (the closed list `REFUSAL_CODES` in `src/http/schemas.ts`), and the web client reads that field instead of guessing from the status. While no owner exists, `GET /api/session` also answers `code` (`set`, `missing` or `short`, from `checkConfiguredCode` in `src/core/setup-code.ts`), so the setup page opens on the block that names the fix instead of asking for a code first. The field reveals only what the 503 already reveals, and it is absent once an owner exists. The single `owner` row makes a second setup a 409.
- **The guard.** One middleware on `/api/*` (`src/http/access-rules.ts`) runs before every handler and answers closed by default. The only routes it lets through unauthenticated are the session, setup, login and password reset calls in `PUBLIC_ROUTES` and the Grok Bot's callbacks on `/api/ai-tasks/{id}` (below). It checks, in order: an owner session cookie or an agent token (400 for a malformed header, an empty one included, 401 for an unknown or revoked token), then that the owner-only routes (`OWNER_ONLY_PATH`) are not reached with a token (403), because Read state, Highlights and the Note are the owner's, then Hono's `csrf` (403) for requests without an `Authorization` header only, because a bearer token is no ambient credential a foreign page could make the browser send, then `body-limit` (413). `POST /api/items/batch` and `GET /api/imports/{name}` are not on the owner-only list, so an agent token reaches both within its scopes (see The import cursor in `data-model-outline.md`). A token call then needs a scope: `requiredScope` gives every `GET` and `HEAD` `read` and lists each other method and path with its scope (`docs/spec.md`, Interfaces, names them), and a token call to a non-`GET` route that the list leaves out answers 403, so a route added later is closed to tokens until someone lists it. A check that needs the parsed body reads who calls from `principal` (`src/http/token-scopes.ts`): a `digest` sent with a Paste needs `digest` besides `add` (`requirePasteScopes`, in `POST /api/items` and for each entry of `POST /api/items/batch`). The owner's session is not limited by scopes.
- **The task callback credential.** `GET /api/ai-tasks/{id}`, `POST /api/ai-tasks/{id}/result` and `POST /api/ai-tasks/{id}/intake` are the only routes that take a per-task credential, and the guard passes them before it looks for a session or an agent token. Its `taskCredential` middleware (`src/http/task-credential.ts`) finds the task by the SHA-256 digest of the secret (`ai_tasks.callback_hash`) and answers 401 for a missing, malformed or unknown credential, one of another task's included, because the lookup matches the path's `{id}` and the digest together. An owner session or an agent token without the task's credential gets 403, so no other principal can answer a task. The secret is made when the task is sent and shown once, in the webhook body only, and a resend of the same task replaces it. A task keeps its digest after it closes, so a late answer finds the task and gets 409 and not 401. The route is public to the guard, so Hono's `csrf` still runs on it and refuses a form content type from another origin (403). The credential is a Threadsift secret in the bot's hands: it reads and answers one task and nothing else.
- **Owner login.** The password is counted in code points after NFKC normalization, must be 15 to 1,024 long (NIST SP 800-63B-4 sets 15 as the minimum for a password alone), and is hashed with scrypt from `node:crypto`, which both targets have, at N=2^15, r=8, p=3, one of OWASP's Password Storage settings, with `maxmem: 64 MiB`. Node's default `maxmem` of 32 MiB rejects those settings (`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`, Node 26.11.1, run on 2026-11-04). The OWASP default N=2^17 needs 128 MiB, the whole memory of one Worker. The stored string is `scrypt$N=…$r=…$p=…$salt$key`, so a later cost change still verifies old hashes. A session is a 32-byte random id in the `__Host-threadsift_session` cookie, stored in `sessions` as a SHA-256 digest with its expiry. A use renews the session once less than 29 days remain, so a session lives 30 days from its last use, and an expired one is deleted and refused. The renewal is one `UPDATE ... RETURNING` that matches only an unexpired row (`checkSession` in `src/core/sessions.ts`), so a session that a password change or a logout deleted after the read gets no row back and is refused, with no cookie. A login commits its session in a guarded batch (see Database and search in `database-and-search.md`) that holds only while the password hash it verified is still the stored one, so a login that raced a password change or a reset gets 409 `password-changed` and starts no session. Setup does the same: it inserts the owner, then commits its session in a guarded batch on the hash it wrote, so a reset that lands between the two leaves no session and setup answers 409 `password-changed`. Chromium keeps the `Secure` `__Host-` cookie over `http://127.0.0.1`, so the local suite runs the real cookie.
- **Throttle.** The `throttles` table holds one row for each of `setup`, `login` and `reset`. One atomic upsert counts each attempt before its code or password is checked, so parallel guesses each count and only ten of them are checked; the tenth counted attempt locks the kind for 60 seconds. A locked kind answers 429 with `Retry-After` without checking anything, even for the right code or password, so an attempt during a lock is not counted and does not extend it. Each attempt counted after a lock ends, before a success, doubles the next lock, up to 1 hour. A success deletes the row only when it is the latest counted attempt, so a success that finishes late cannot clear a lock that newer attempts set. The lock is in the database, so a restart keeps it. It is global, not per address, because behind a proxy the app has no address it can trust; the cost is that anyone who can reach the login can lock the owner out of signing in for up to an hour, while sessions already open and agent tokens keep working.
- **Owner-only Restore routes.** `OWNER_ONLY_PATH` also matches `/api/restore` and everything under it, so an agent token gets 403 and a signed-out caller 401 on the four Restore routes, because a leaked token must not write a whole library. `PUT /api/restore/{id}/parts/{n}` has its own body cap, the part size (`partCap` in `src/http/guard.ts`).
- **Owner-only Proposal routes.** `OWNER_ONLY_PATH` also matches `/api/proposals/{id}/accept` and `/api/proposals/{id}/reject`, so only the owner's session removes a Highlight through a lost-Highlight row. `GET /api/proposals` is open to agent tokens, as the Log and the Index are.
- **Change and reset the password.** `src/core/owner-password.ts` holds both. They end every session and keep the agent tokens, which the signed-in owner revokes on their own.
  - **Change.** `POST /api/password` is owner-only and closed to tokens. It refuses a new password outside 15 to 1,024 characters (400) before it counts an attempt, then verifies the current password under the `login` throttle kind, so a guess through the login or through the change draws on one budget (OWASP Authentication Cheat Sheet: ask for the current password to change it, and count lockout per account). A wrong current password answers 403 `wrong`, never 401, because the web client treats a 401 as signed out. One guarded batch sets the new hash, deletes every session and inserts the caller's new session, and it holds only while the stored hash is still the one that was verified and the calling session still exists. The new session is prepared without writes, and its cookie is sent only after the commit, replacing the guard's renewal cookie if both are set (OWASP Session Management Cheat Sheet: renew the session id on a password change). A call that loses the race gets 409 `password-changed` and changes nothing. A change runs two scrypt hashes in one request.
  - **Reset.** `POST /api/password/reset` is public and works only while the server holds `PASSWORD_RESET_CODE`: a container environment variable read at start, or a Worker secret read from each request's `env` (`src/targets/worker/index.ts` keeps one app per code value and never reads the code from the cached ports). It is an operator credential on the owner's own server, like `SETUP_CODE`, so it has no expiry. That departs on purpose from the Forgot Password Cheat Sheet's expiry advice, and its single use, the 32-character minimum and the removal after use make up for it. The code is compared by SHA-256 digests with `crypto.equal`, under its own `reset` throttle kind that counts each attempt before the check. The reset reads the stored hash before it hashes the new password. One guarded batch, which holds only while that hash is still the stored one and the code is unspent, inserts the code's digest into `spent_reset_codes`, sets the hash, deletes every session and clears the `login` throttle row, because that lock protected the old password. A spent digest stays refused after later codes are used, so setting an old code again does nothing. When the batch fails, the reset answers `reset-used` if the code is spent and `password-changed` otherwise, so a reset never overwrites a change that committed after it read the hash. The reset starts no session and sets no cookie (Forgot Password Cheat Sheet: do not log the user in automatically).
  - **States the routes reveal.** Every refusal leaves the password, the sessions and the spent codes as they were. The 503 for a missing or short reset code reveals only whether a code exists, as the setup 503 does.
  - **Rules from outside.** NIST SP 800-63B-4 3.1.1.2 and 3.2.2 are cited as selected guidance (15 characters, no composition rules, no forced rotation, an attempt limit), not as full conformance; its section 4 on recovery was not read. Cloudflare's `wrangler secret put` deploys a secret at once and `wrangler secret delete` removes it (Workers docs, Secrets). A run on a throwaway pull request copy (wrangler 4.156.0, 2026-11-07) agreed: after `put` of a code, a reset with it answered 204; after `put` of a second code, the first answered 403 `wrong` and the second 204; after `delete`, a code never used answered 503 `reset-missing`.
- **Screen states.** `useGuard` (`web/src/use-form.ts`) sets a ref before its first await, so a second press in the same frame does nothing while the first request is on its way, where a `busy` state alone is still false until the next render; a button the guard blocks keeps `aria-disabled` instead of `disabled`, so focus stays on it. The Revoke question, the budget change on a token row, the GitHub, Grok Bot and Reddit sections and the Proposals rows run through `useFlow` (`web/src/use-flow.ts`), which keeps the state in a ref for the same reason. Cancel and asking about another token work while a revoke is on its way; the answer of that revoke then removes the token from the list and ends any question still open about it, so a second revoke of it that answers 404 shows no failure (`request` in `web/src/token-revoke.ts`). The session check (`web/src/use-session-view.ts`) aborts after `CHECK_DEADLINE_MS` (10 s) and ends on the unreachable screen with Retry, except that an unreachable answer leaves the signed-in view in place (`answeredView` in `web/src/session-state.ts`); an explicit sign-in or sign-out supersedes the check in flight, so that check's late answer changes nothing.
- **Agent tokens.** One random token per connected agent, `tsa_` and 32 random bytes in base64url, shown once, stored as a SHA-256 hash (the token is high-entropy, so a fast hash is enough), revocable in settings. `last_used_at` updates at most once an hour through a conditional `UPDATE`, so a busy agent does not write on every request. The Extension, Grok Bot and MCP clients use them as bearer tokens. Each token holds scopes in the JSON column `agent_tokens.scopes` (see `docs/spec.md`, Token scopes; the routes each scope covers are in Interfaces), which `src/core/tokens.ts` parses with `StoredScopesSchema` where it leaves the database: a scope name this release does not know is dropped, so a token stored by a later release keeps the scopes this one knows, and a token whose scopes are not a list of names fails every call (fail closed) and the token list shows it with no scopes, so the owner can revoke it. `0049_agent-token-scopes.sql` adds the column with a default of the four scopes that existed then (`LEGACY_SCOPES`, so the later `reddit` scope needs no migration and an old token never gets it), because SQLite `ADD COLUMN ... NOT NULL` needs a default and a token that exists before the migration must keep every call. The Grok Bot settings hold no token; the routes that take AI task results use a credential made for each task (`src/http/task-credential.ts`).
- **Daily budget.** Each agent token may add a limited number of new Items for each UTC day, because each new Item costs the Provider one Digest call. `agent_tokens.daily_budget` holds the limit and NULL means no budget. A token made without one gets `DEFAULT_TOKEN_BUDGET` (200, `src/core/limits.ts`, the maintainer's choice and not a measurement), and a token that existed when `0052_agent-token-budget.sql` ran keeps NULL. The owner's session has no budget. Only a new Item counts: a link whose normalized URL the library holds (`200`, or `known` in a batch, a short link found by its alias included), a refused host, a read and a search do not. `agent_token_days` holds one count for each token and UTC date and goes with the token. Each Item counts on the UTC day it was saved on, and `Retry-After` is the seconds to the next UTC midnight.
  - **Two ways to enforce it.** A single add (`POST /api/items`, the Extension, the `add` tool of `/mcp`) saves with `items.added_by_token` set, and the trigger `items_token_budget` counts it in the same batch and aborts the batch when the count passes the limit; `paste` turns the abort into `budget-spent`. A batch must be refused whole, and a D1 batch cannot roll back the batches before it, so `withinBudget` (`src/core/agent-token-budget.ts`) reserves one slot for each link that may be new before anything is saved (a batch of only held links reserves nothing, so it never answers 429, even when the owner lowered the budget below today's count), then saves each Item it creates with `added_by_token` set and `budget_slot_day` set to the day of the reservation, and gives back the slots it did not use when the batch ends or fails (`SaveAs`). The trigger skips an Item whose `budget_slot_day` is the day of its `saved_at`, because the reservation already counts it, and counts any other Item, so an Item a batch saves after 00:00 UTC is counted on its own day and refused at that day's limit, as a single add is. A link that creates an Item when no slot is left saves it with `added_by_token` set and no `budget_slot_day`, so the trigger counts it and aborts at the limit. Both end with the count equal to the Items created that day. Two parallel adds do not both take the last slot, and a refused add counts nothing. The race tests run on one connection, so they prove the order of the awaits and not D1's writers; on D1 the rule rests on Cloudflare's statement that a batch is one transaction.
  - **Bounds.** A held link that another request deletes while a batch runs is saved again by the batch with no slot reserved for it. It takes a slot that another link did not use, or, with none left, the trigger refuses it past the budget: the call answers 429, and the links saved before it stay saved and counted, so the count never passes the budget (`test/token-budget-upkeep.test.ts`). A batch that fails with an error counts the Items it saved before the error and keeps the one slot of the link that failed, because that link's Item may exist, until 00:00 UTC. `settle` is one `UPDATE` of the reservation day's count, so it either ends or does not run. An Item that a batch saves after 00:00 UTC takes no slot of the earlier day, so when the new day's budget is spent the call answers 429 and the links saved before stay saved and counted. A process that stops while the batch still saves links leaves the whole reservation counted until 00:00 UTC, the slots the batch did not use included; the Items it saved keep their `added_by_token`, because the insert sets it. The code cannot tell the reservation of a dead batch from that of a live one, because the reservation is one number in `agent_token_days` that names no batch and has no deadline. The count only goes up, so the token can be refused earlier than its budget says. An Item that another request deletes before `settle` runs is still counted for its day, because `settle` does not read the Items back. A write that creates an Item and does not take the `Caller` that `paste` and `pasteBatch` require would not be counted, so every insert into `items` gets it.
  - **Refusal.** 429 with `code: budget-spent` and `Retry-After` (`BudgetRefusalSchema`); the `add` tool answers a tool error with the same `code` and `retryAfter`. `forgetOldDays` deletes a token's rows older than 2 days when its `last_used_at` renews, so a token keeps at most 3 rows.
- **Secrets at rest.** Provider keys, the GitHub token, the Grok Bot webhook key and the owner's Reddit session cookie are sealed with AES-GCM (WebCrypto, on both targets) under `THREADSIFT_SECRET_KEY`, which the app reads from its environment and never shows. No route returns the Grok Bot key, and the address, which the bot's docs call partly secret, is returned only to the owner's session (`/api/settings` is closed to agent tokens). A Save without a key keeps the stored key only when the address is unchanged, so a mistyped address never receives the old key. The Reddit session is opened only by `openedSession` in `src/core/reddit-account.ts` and passed to the adapter as an argument, put in one `Cookie` header that goes only to `www.reddit.com`, and never stored in a job row or a task input, put in an error or logged. `GET /api/settings/reddit-account` answers a state and never the value, a state of `unreadable` (the sealing key changed) sends no request, and a request that answers a redirect is never followed with it.
- **The share route.** `/share` (`src/http/share-routes.ts`) is the manifest's `share_target` action. It sits outside `/api/*`, so the guard never sees it and an agent token never reaches it. It writes only for a `POST` that has all three: an owner session cookie, `Sec-Fetch-Site: same-origin` and an `Origin` whose host equals the request's host (`src/http/share-trust.ts`). Missing metadata, `Origin: null` and a token never authorize a write. The session cookie is `SameSite=Lax`, so a cross-site `POST` carries no cookie, and the two header checks stop a same-site page on another port, whose `POST` does carry it. The pattern is the `csrf()` default of the installed Hono (`node_modules/hono/dist/middleware/csrf/index.js`), made stricter: Hono lets a request pass on either header, this route needs both. It compares the host of the `Origin` and not its scheme, because the container sees plain HTTP behind the owner's TLS proxy while the browser's `Origin` says `https`, and `Sec-Fetch-Site: same-origin` already covers the scheme. A trusted share calls `paste` (`src/core/paste.ts`), the core function that `POST /api/items` calls, and answers `303` to `/?saved=<id>`, or `/?refreshed=<id>` for a known Item that had been fetched. Every other arrival writes nothing and answers `303` to `/?link=<link>`, with a `notice` from `PREFILL_NOTICES` when the trusted share saved nothing. The link is the first `http:` or `https:` address in `url`, then `text`, then `title` (`src/core/shared-link.ts`); an address that ends in `)`, such as a Wikipedia title with a bracket, loses it, which is the cost of the rule. The address carries at most 1,000 UTF-16 code units, so the redirect stays under Node's default header limit of 16 KiB even when every unit percent-encodes to 9 bytes, the worst case for a three-byte UTF-8 character (Node docs, `--max-http-header-size`); a longer link is cut to that and carries `notice=invalid`.
- **Request limits.** Hono's `body-limit` middleware caps request bodies on both targets, because Node has no cap of its own and Cloudflare's cap depends on the zone's plan (100 MB on Free and Pro, Workers docs, Limits). Every route takes 64 KiB, `/mcp` included, except `POST /api/items`, which takes 8 MiB (413) because it carries a thread, and the AI task callbacks, which `capFor` in `src/http/guard.ts` sizes on their own. The cap holds without `Content-Length` too, a larger body answers 413 and writes nothing, and the SDK's 4 MiB default for `/mcp` never applies.
- **MCP.** `/mcp` serves Streamable HTTP on both targets through `createMcpHandler` from `@modelcontextprotocol/server` (`src/http/mcp-route.ts`; the SDK's Hono guide mounts `handler.fetch(c.req.raw, ...)` and names Workers as supported). One handler serves every request, but its factory builds and registers a fresh `McpServer` for each, and the app keeps no session registry: the SDK changelog for 2.3.0 records that one server shared by overlapping requests fails them. The handler serves the 2026-07-28 per-request exchange and, statelessly, the 2025 handshake. It checks no token, no Host and no Origin, and it reads up to 4 MiB, so `mcpGate` (`src/http/mcp-gate.ts`) and the `bodyCap` of the guard run in front of it. The tools are not in OpenAPI: `/api/openapi.json` stays the REST contract, and an MCP client finds the tools with `tools/list`.
  - **Gate.** `/mcp` is outside `/api/*`, so the guard never sees it. The gate runs on every HTTP request, after `initialize` as well, and caches nothing, so a token the owner revokes fails on the next request of a client that is still connected. It accepts the Authorization header only: no cookie, query string or body field, and a valid owner cookie never replaces a missing, malformed or revoked token. The statuses are the guard's (401 with `WWW-Authenticate: Bearer` for no credentials or an unknown or revoked token, 400 for a malformed header). The check is `verifyToken` in `src/core/tokens.ts`, the function the guard uses, so the hash and the `last_used_at` rule have one copy. Each tool registers a `scopeChallenge` built with the SDK's `requireScopes`, which the SDK runs before the tool, and a call without the scopes answers 403 with `WWW-Authenticate: Bearer error="insufficient_scope"`. `pasteScopes` (`src/core/scopes.ts`) is the one copy of the Paste rule for HTTP and MCP.
  - **Host and Origin.** The SDK's validators match hostnames without a port, so the gate has its own rules, and none of them reads the allowlist from the request. With `THREADSIFT_PUBLIC_ORIGIN` set, `Host` must equal that origin's host with its port, and a present `Origin` must equal the whole origin: scheme, host and port. Loopback is then refused, so a client on the same machine uses the public address. Without it, `Host` must be `localhost`, `127.0.0.1` or `[::1]` on any port and a present `Origin` must be a loopback origin, so reaching `/mcp` from another machine needs `THREADSIFT_PUBLIC_ORIGIN`. A request without `Origin` passes, because CLI clients send none; `Origin: null`, a malformed one and an unlisted one answer 403, and so does a `Host` header that the rules refuse while the request address passes: the gate checks both. The gate answers 403 before it asks for credentials.
  - **Tools.** `search`, `read` and `add` call the same functions as `GET /api/items`, `GET /api/items/:id` and `POST /api/items` (`readItemPage` and `readItem` in `src/http/item-read.ts`, `paste`) and answer the same JSON as `structuredContent`. No tool writes a Highlight, a Note or a Read state, which stay the owner's. `add` takes `url` and an optional `digest`, not `content`, `page` or `fill`, and keeps the 503 refusal while a data step runs. It answers `{item, url}` and does not say whether the Item was new.
  - **Errors.** A gate refusal is an HTTP status. A missing Item, a refused host, a token that has added its daily budget, the data-step refusal and an argument the input schema rejects are tool results with `isError: true`; the first four carry the REST route's text and the last carries the SDK's validation message. Any other failure is logged by class name and answers the tool result `Internal error`, so no exception text reaches the client.
  - **Disconnect.** A client that goes away releases its request and its stream. An `add` whose Paste committed keeps its Item and its jobs, which finish through the job runner as for any Paste.
  - **Lockout.** Agent tokens take no part in the login throttle. `/mcp` has no rate limit of its own, and its `add` tool draws on the token's daily budget (see Daily budget); `search` and `read` have no limit.
  - OAuth for Grok Bot's catalog comes later (`docs/spec.md`, Grok Bot).
