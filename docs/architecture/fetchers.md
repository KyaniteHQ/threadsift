# Fetchers

The built-in fetchers are functions that `fetchedForJob` (`src/core/fetch-source.ts`) calls by the link's kind, not a port: article, GitHub and Reddit below. The one registry is `Ports.fetchers`, the list of plug-ins (Plug-ins below). X has its own two routes below, the Grok Bot and the grok CLI.

- **Article:** a plain `fetch` through `guardedFetch`, then Defuddle 0.19.6 on the linkedom document that also gives the title, with Markdown output (`readArticle` in `src/core/article.ts`). Its CPU cost is why the Cloudflare target needs Workers Paid (see Cloudflare deploy button in `cloudflare-deploy-button.md`). No Browser Rendering: pages that need JavaScript or a login come in through the Extension.
  - **Article or Other.** The page is an Article when it is HTML (`text/html` or `application/xhtml+xml`, compared without case and without parameters), the body was not cut at the cap, the final URL is not a video host (`VIDEO_HOSTS` in `src/core/links.ts`) or a Reddit, X or GitHub link, and Defuddle counts 100 words or more. Any other page is Other with no post text. A page with no `<title>` and no title from Defuddle leaves the Item as it was, with the fetch result `no-title`. The 100 words are our choice, from a probe with Defuddle 0.19.6 and linkedom 0.18.15 on 2026-11-06: `https://example.com/` gave 25 words, `https://stephango.com/saw` 143 and `https://en.wikipedia.org/wiki/Bread` 6642. With `useAsync: false` a YouTube watch page gives 0 words (probe, 2026-11-06), so no YouTube entry of `VIDEO_HOSTS` has a page that can fail on its own; `https://vimeo.com/terms` (8,211 words) is the page that needs the list, so the list is matched against the final URL and not the pasted one. Reddit, X and GitHub links never reach Defuddle.
  - **Defuddle makes no request of its own.** It runs with `useAsync: false`, because 0.19.6 extractors such as `c2-wiki` fetch extra pages with the global `fetch`, outside the guard (`src/extractors/c2-wiki.ts` at tag 0.19.6). `https://wiki.c2.com/?WelcomeVisitors` is the page that shows it: with the option Defuddle reads 9 words from the page and sends nothing, and without it the extractor requests `https://c2.com/wiki/remodel/pages/WelcomeVisitors` and returns 376 words (probe on Node 26.12.1, 2026-11-06). Defuddle also takes a `fetch` option (`node_modules/defuddle/dist/types.d.ts`, `Options.fetch`), and `readArticle` passes one that refuses every request, so an extractor that ran despite `useAsync: false` would fail the job instead of using the global `fetch`. The guarded fetch cannot be passed instead, because the reader runs where no `Network` port exists (a worker thread on the container).
  - **Markdown only.** Defuddle keeps `video`, `audio` and `iframe` elements as raw HTML in its Markdown, and the Reader renders Markdown without raw HTML, so `readArticle` removes those elements from the document before Defuddle runs; a code sample that mentions the tags is text and stays. Media explains how they become links and rows.
  - **A failed refresh keeps the Article.** `settle` (`src/core/settle.ts`) writes no content field for a fetch that failed.
  - **Where it runs.** Parsing, the title read and Defuddle sit behind the `PageReader` port (`src/core/ports.ts`), and the job calls it through `ports.pages`. The container adapter (`src/targets/node/page-reader.ts`) sends each page to one `node:worker_threads` worker (`page-reader-worker.ts`), because Defuddle runs on the thread that calls it: a 4 MB Gutenberg page blocked the container's event loop for about 8 s, and the API answered nothing in that time. Each read takes the fetch job's 120 s deadline signal. When it aborts with a read in flight, the container adapter terminates the worker, fails that read alone with `PageReadTimeout`, and posts the other pending reads again to a new worker, each keeping its own deadline; `fetchLink` turns that error into the fetch result `timeout`, which the job treats like a network timeout. After `stop()` every read, pending or new, fails with an error and no worker starts again, and an answer that does not parse fails only the read it names. A probe with a 4.5 MiB page (68.9 s to read) at a 1 s deadline next to two small reads failed all three with `PageReadTimeout` at 1.0 s before this change, and failed only the large one after it (`WorkerPageReader` imported as the container does). A bad answer from the worker has no real input that makes it, so that path is unverified. The Worker adapter (`src/targets/worker/page-reader.ts`) calls the same functions inline and relies on the Worker's CPU limit. Each adapter also gives `maxHtmlBytes`, the largest HTML page it reads: 5 MiB on the container and 900 KiB on the Worker. The 4,039,247 byte War and Peace page is therefore an Article on the container, whose whole text (3,298,760 bytes of Markdown, measured 2026-11-06) is kept in a file in the store, and an Other Item, cut at the cap, on the Worker.
  - **Worker memory.** A Worker isolate has 128 MB (Workers docs, Limits). Local `wrangler dev` does not enforce that limit, so the memory is estimated from the peak resident memory of the `workerd` processes (`VmHWM` in `/proc/<pid>/status`, sampled every 25 ms during one Paste in a fresh `wrangler dev` 4.156.0, 2026-11-06) minus the same measure for a Paste of `https://example.com/` (214.9 MiB). That is the whole process, so it overstates the isolate. The inspector (`--inspector-port`) returned no heap numbers.

It also makes `https://www.rfc-editor.org/rfc/rfc9110` (4,899,392 bytes) an Other Item on the Worker.
  - **On the Worker.** `defuddle/node` bundles with `nodejs_compat`, but wrangler's bundler follows turndown's `browser` field to a build that needs a global `document`, which workerd lacks: every conversion then fell back to Defuddle's "Partial conversion completed with errors" text, which holds the raw HTML (`ReferenceError: document is not defined`, `wrangler dev` 4.156.0, 2026-11-06). `wrangler.jsonc` `alias` points `turndown` and `@mixmark-io/domino` at their Node builds (Workers docs, Wrangler configuration, Module aliasing: https://developers.cloudflare.com/workers/wrangler/configuration/#module-aliasing). Wrangler resolves an alias value from the project root, so both packages are direct dependencies at the versions `defuddle` resolves (`turndown` 7.2.4, MIT; `@mixmark-io/domino` 2.2.0, BSD-2-Clause, last release 2024-04-08), and a `defuddle` update moves the two pins with it. Without the aliases the stored text holds the fallback HTML.
- **GitHub:** the GitHub REST API on both targets, anonymous or with the owner's optional token (see Token below). `fetchedOfRepository` in `src/core/github-fetch.ts` runs when a pasted link's kind is `github-repo`, in place of the page fetch, and sends two requests through `guardedFetch` with API version `2022-11-28`, GitHub's default version, supported until 2028-03-10 ([API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions), read 2026-11-07).
  - **Requests.** `GET /repos/{owner}/{repo}` gives the description, stars, language, license, topics and last push. Then `GET /repos/{owner}/{repo}/readme` runs on the owner and name that first answer returns, so a renamed repository reads the README of its new name. Owner and name are the first two path segments of the pasted URL with a trailing `.git` removed (`repositoryRef` in `src/core/repository-ref.ts`); the Item's identity stays the name it was pasted with (see Item identity in `data-model-outline.md`), so `KyaniteHQ/commonplace` stays an Item under that name and shows the metadata of `KyaniteHQ/threadsift`, which GitHub redirects it to. A deep link such as an issue URL has the same kind and reads the same repository. GitHub says any request may redirect and the client should follow ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#follow-redirects)), and the guard's chain of 20 does that.
  - **Headers.** Both requests send `Accept: application/vnd.github+json` and `X-GitHub-Api-Version`. The `Network` port takes the extra headers of each hop from the fetch policy (`FetchPolicy.headers`), and the GitHub policy returns them only for an `https` URL on `api.github.com`, so they ride each redirect hop to that host and never reach another host. The global `REQUEST_HEADERS`, which every pasted site receives, did not change. `NetworkResponse` carries three response headers as `rateLimit` (`Retry-After`, `X-RateLimit-Remaining`, `X-RateLimit-Reset`), and the guard reads them only for a 403 or 429 from `https://api.github.com` (see Rate limits below).
  - **Token.** The fetch job reads the saved token when a repository fetch starts (`loadGithubAuth` in `src/core/github-token.ts`: no row is anonymous, a row the sealer opens is the token, any other row is unreadable). The GitHub policy adds `Authorization: Bearer <token>` only on a hop whose URL has the origin `https://api.github.com`, compared as a whole origin so another port of that host gets none (`apiPolicy` in `src/core/github-api.ts`), so a redirect to another host never carries it. An unreadable token ends the fetch as `github-token` without a request. A repository or README answer of 401 while a token was sent also ends it as `github-token`: the fetch writes no content, so the Item keeps its metadata and README, and the Item is not fetched again without the token. Both set the Item's fetch result `github-token`; the paste card, the row and the Reader tell the owner to replace or remove the token in Settings. A 403 or 429 stays `status`. A repository answer marked `private` ends the fetch as `status` before the README request, so a token with access to private repositories stores no private metadata; no run reached that case (see Open items).
  - **Rate limits.** A 403 or 429 from the GitHub API is classified by `rateLimitOf` in `src/core/github-rate-limit.ts` ([Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), read 2026-11-08). It is a primary limit when `x-ratelimit-remaining` is `0` and a secondary limit when the JSON `message` names a "secondary rate limit". The guard classifies from the status and the headers first, so a header-confirmed primary limit never waits on the body and survives a body that stalls, closes or fails to decompress. Only an answer the headers do not confirm gets its message read, and only for those two statuses on that origin (`FetchPolicy.readsLimits`), cut at 8 KiB (`ERROR_BODY_BYTES`, our choice); the guard returns the classification, never the message. Any other 403 or 429 stays `status`. The earliest retry time is the later of `x-ratelimit-reset` (UTC epoch seconds, primary only) and `retry-after` (whole seconds, or an HTTP date in any of the three forms of [RFC 9110, Date/Time Formats](https://www.rfc-editor.org/rfc/rfc9110.html#section-5.6.7): IMF-fixdate, the obsolete RFC 850 form with a two-digit year, and asctime); a value that is malformed, zero or in the past is ignored. `parseHttpDate` in `src/core/http-date.ts` reads dates as UTC, rebuilds each one with `Date.UTC` and compares every field with the input, because `Date.parse` moves `Sun, 31 Feb 2027 13:00:00 GMT` to 3 March (Node 26.12.1) and that would store a wait of months. No existing parser fits: `package.json` lists no date library, and the one correct parser in `node_modules`, `parseHttpDate` in undici 7.30.1's internal `lib/util/date.js`, is a transitive dependency of the AI SDK packages that the package does not export for use. A two-digit year that would land more than 50 years ahead of now is read as the latest earlier year with the same last two digits, as RFC 9110 says. With no usable time the wait is 60 seconds and 120 seconds for the second limited attempt (`FALLBACK_BASE_MS`, from the docs' "at least one minute" and "exponentially increasing", the numbers are ours), so no limit ever gives an immediate retry. `Retry-After` counts for a primary limit too, because the later time is the safe one.
  - **Cooldown and attempts.** A limited answer stores the Instance's cooldown (`github_cooldown`, one row, `startCooldown` in `src/core/github-cooldown.ts`, never moved earlier). The cooldown is at most one hour (`MAX_COOLDOWN_MS` in `src/core/github-rate-limit.ts`), because every primary limit GitHub documents is per hour ([Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), read 2026-11-09) and the page names no longer wait: `limitedUntil` cuts a `Retry-After` or `x-ratelimit-reset` beyond it, and `cooldownUntil` cuts a stored time more than an hour ahead and writes the cut back, so a row from a wrong header or a host clock that ran behind ends within the hour. Saving or removing the GitHub token deletes the row in the same batch, because the token has its own limit. And `requestApi` in `src/core/github-api.ts` checks it before the repository request and before the README request, so a Paste of any GitHub link waits for it too. Requests already in flight finish, but one sent with a credential that was saved over or removed since stores no cooldown: `startCooldown` writes only in a guarded batch that checks `github_settings` still holds the sealed token the request used (or holds no row, for an anonymous request), and otherwise throws `CredentialChanged`. `withCurrentCredential` in `src/core/github-token.ts` catches it, loads the current credential and sends the whole request again, so the obsolete limit is dropped and the new token is not blocked. Saving the same token again seals it with a new random IV, so it also counts as a change. The fetch job turns a limited or cooled answer into a deferred outcome (see Jobs, leases and the schedule in `jobs-leases-and-the-schedule.md`): the retry time is the answer's, or the cooldown's. A limited attempt counts once whichever request was limited: the first two defer, and the third ends the Item `failed` with the reason `rate-limited`, keeping its saved content, and drops a pending caller Digest like `gave-up`. Finding a cooldown counts no attempt. Verify (`verifyGithubToken`) goes through `requestApi` too. During a stored cooldown it sends no request and answers the refusal `rate-limited`, and a limited answer to its own request is stored as the cooldown before the same refusal. GitHub exempts `GET /rate_limit` from the primary limit but says it can count against the secondary limit ([Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#checking-the-status-of-your-rate-limit), read 2026-11-08), so a Verify during a secondary backoff would add to the load that caused it.
  - **README format.** The raw media type (`application/vnd.github.raw+json`) answers no file name, so a fetch could not tell Markdown from another format (response headers of `GET /repos/kepano/defuddle/readme`, `curl`, 2026-11-07). The README request asks for the JSON form instead, which has the `name`, the `encoding` and the base64 `content` in one request. The Item keeps the README as post text only when the name ends in `.md` or `.markdown` (any case); any other name, such as `README.rst`, `README` or `ReadMe`, gives no text, and so does an encoding other than `base64`. The JSON body is larger than the file: GitHub wraps the base64 `content` every 60 characters and JSON escapes each line break, so 45 file bytes take 62 bytes (`GET /repos/kepano/defuddle/readme`, `curl`, 2026-11-07: a 14,146-byte README gave 316 base64 lines in a 20,313-byte answer), and the metadata adds about 0.8 KiB there and, by estimate, under 4 KiB for the longest owner and repository names. The README request therefore has its own cap, `README_ANSWER_BYTES` (768 KiB, `FetchPolicy.dataMaxBytes`), which holds the answer for a README of 512 KiB (about 706 KiB of JSON) with room for the metadata. A README whose answer is still cut is never parsed and never stored, and it is not "no README": the README read fails with `unreadable`, the fetch writes nothing, and a refresh keeps the text and metadata saved earlier. For a new Item that leaves it Link-only. GitHub documents the JSON form for files up to 1 MB ([Get repository content](https://docs.github.com/en/rest/repos/contents#get-repository-content)); a larger README is expected to answer with an HTTP error, which takes the `status` path. Relative links and images are not resolved: the Reader keeps the rule that refuses a relative URL. `NOASSERTION`, GitHub's answer for a license it cannot name, is stored as no license.
  - **Outcomes.** A repository answer of 200 and a README answer of 200 give a ready Item with metadata and README text. A repository 200 with a README 404 gives a ready Item with metadata and no text, and the Reader says the repository has no Markdown README. A repository answer that is not 2xx (404, 451, a 403 or 429 that is not a rate limit as Rate limits below defines it) and a README answer that is neither 200 nor 404 end the fetch with the result `status` and write no metadata: the Item settles `ready` and Link-only with no failure reason, so its row offers no Try again, and the owner pastes the link again to refetch it. The Reader says the repository has no Markdown README only after a repository answer of 200 (`fetch` is `ok`); otherwise it says the Item has no post text. `status` is not retried. A network error or a timeout takes the path it takes for a page, and an answer that does not parse gives `unreadable`.
  - **Publication.** A repository is its own kind of fetched content (`github-repo` in `src/core/details.ts`), never an Article. The guarded finishing batch of the fetch job writes the item fields, the title and post-text search parts, the `github_repos` upsert, the `repository` search part and the generation together (`repositoryWrites` in `src/core/repositories.ts`), so a runner whose claim was taken over writes none of them. A failed fetch writes no repository row, and an Item keeps its earlier row until a fetch that succeeds replaces it. The list, the status route and the save answer carry nullable `stars`; `GET /api/items/:id` carries the whole block as `repository`.
- **Reddit:** oEmbed for the title, author and subreddit, and one `.json` parser (`src/core/reddit-json.ts`) for the `.json` paste, the JSON the Extension sends and the account fetch; the Extension's Defuddle page, sent as a `page`, when its `.json` request failed. A `more` stub whose replies could not be fetched becomes a Context stub. In the self-hosted builds, a link without Extension content goes first to the connected account, when there is one and its session works, and then to the archive fill: Arctic Shift's comment tree passes through a thin adapter (Arctic's top level is `{"data":[t1 nodes]}`, not Reddit's two Listings, while nested `replies` are Listings) into the same parser, so no second parser exists. The fill runs inside the fetch job, started together with the oEmbed request (`fetchedWithThread`, `src/core/reddit-fetch.ts`), only when the setting is on and the Item holds no thread. It asks for the post (`/api/posts/ids?ids=<id>`) and then the whole tree (`/api/comments/tree?link_id=t3_<id>&limit=9999`) through the fetch guard, one request at a time, so Arctic sees two sequential requests while oEmbed runs beside them. Arctic's rate limit is respected: on a 429 the request is sent once more after the seconds in `X-RateLimit-Reset` (seconds until the limit resets, per Arctic's API README), and a reset longer than 10 s or a second 429 leaves the Item Link-only without waiting. An answer larger than 8 MiB (`ITEM_REQUEST_BYTES`, so the Worker holds at most that text and its parse), a timeout, an outage, a post the archive lacks or an answer the parser refuses also leave the Item Link-only, and none of them fails the Item or retries the job. The oEmbed title is kept when it exists; the archive's title is used only when oEmbed failed. A comment the archive marks `_meta.was_deleted_later` is rewritten to the `[deleted]` placeholder before the parser reads it, so the Comment filter drops it and its replies keep their place. The connected account is the first source for a post or comment that holds no saved thread, before the archive fill and whether or not the archive fill is on. `reddit-fetch.ts` takes the turn first (`accountTurn`, `src/core/reddit-account-turn.ts`), so a job that has to wait sends no request, not even oEmbed. `accountThread` (`src/core/reddit-account-fetch.ts`) then requests `/comments/<post>.json?limit=500&raw_json=1` (`/comments/<post>/_/<comment>.json` for a comment link) and the replies behind each `more` stub by permalink, with an address built from `redditRefOf` and never from the pasted text. The loop that asks for the replies is `fillAnswers` (`src/core/thread-fill.ts`), which the Extension calls too: 500 ms between request starts (the account row keeps `last_request_at`, so the 500 ms also holds from one fill to the next), at most 100 requests in all (`mayAsk`, `src/core/reddit-window.ts`), 8 MiB held, a stop at the first 429 and a fill deadline of 90 s on the server (the Extension's is 150 s). Before each request the server asks whether the account row is still `connected` with the same sealed session (`stillConnected`), so Disconnect and `expired` stop the fill within one request. One parser reads the answers (`parseRedditThread`), and a fill that stops early stores the thread with Context stubs, so up to 99 requests of a limited budget are never thrown away. The stored thread has a null `archived_at`, because the thread is current. The port is `Ports.redditSession` (`src/core/ports.ts`), one `get(path, cookie, signal)` to `www.reddit.com`, a host fixed in the adapter, that follows no redirect with the session, and the app's own `Threadsift/1` User-Agent, which Reddit answered with 200 (2026-11-13). The container sends it with the platform `fetch` (`nodeRedditSession`, `src/targets/node/network.ts`); no browser-impersonating client, because plain `fetch` got HTTP 200. The Worker sends it over `connect()` from `cloudflare:sockets` (`src/targets/worker/reddit-session.ts`) with HTTP/1.1 written and read by the app (`src/targets/worker/http1.ts`), because Reddit answers the Workers `fetch` client with 403 even with the cookie, while a raw socket from the same Worker got 200 (3 of 3 runs, 2026-11-05). The Worker opens one connection for each request and asks for `Connection: close`, because the port is stateless and a socket cannot outlive the invocation that made it; Reddit answers an HTTP/1.1 request with `Content-Length` and `Connection: close`, and honours `Accept-Encoding: identity` (2026-11-13, checked over TLS from the development machine), so the reader also handles a chunked body and a body that ends with the connection, and refuses an encoded one. A search on 2026-11-13 found no maintained HTTP client over `connect()` (`@pixel/socket-fetch` is 3 releases old and published on JSR only), so the reader is the app's own. Reddit's request limit is read from its headers: `x-ratelimit-remaining` and `x-ratelimit-reset` (100 requests for about 600 s, seen as `99.0` with a decimal) are stored on the account row, and no job takes the turn while the stored window is used up or `limited_until` is in the future. A 429 stores `window_remaining = 0` and `limited_until` (the largest of that answer's own `x-ratelimit-reset`, its `Retry-After` and 60 s, cut to one hour), on the first request and in the middle of a fill. On the first request the job then waits with `reddit-limit` and counts an attempt, and the third limited attempt uses the archive fill. Every first answer and every `me.json` answer updates the stored window, and the `me.json` check waits 500 ms after the first request and is skipped when the window is used up. A first answer that shows fewer requests left than the hidden replies need drops that answer, waits for the reset and counts no attempt, so a later Paste, which never replaces a saved thread, does not keep a thread with stubs that could have been fetched; a thread that needs 100 requests or more is stored with stubs. A 401 or 403 sends one `me.json` check with the same session (`checkSession`, `src/core/reddit-account.ts`): `ok` is a 200 that names a `t2` account, `logged-out` is a 401 or a 200 that names none, and everything else is `blocked`, because Reddit answers 403 with the same network-security page to an altered session and to no session at all (2026-11-13), so `logged-out` sets the state `expired` at once, and a 403 from both requests counts as one refusal in `refused_count`, once for each job: the third refusal, on 3 different jobs in a row, sets `expired` as well, and any answer that shows the session works clears the count. Any other status, a timeout, a network error or a parse refusal uses the archive fill for that fetch and leaves the state alone. One fill runs at a time, oldest job first (`jobs-leases-and-the-schedule.md`, The Reddit turn). The fill's start rule is unmeasured for a session that Reddit logged out: the first real expiry will show whether Reddit answers `me.json` with 401, with a 200 that names no account, or with 403.
  - **Supplied thread.** `POST /api/items` with `content` is a Paste of a post or comment link with its `.json` (`src/core/paste.ts`); the server sends no request for thread JSON. `content` is one JSON text, or 1 to 101 texts (`MAX_THREAD_ANSWERS`): the thread's `.json` first, then the permalink answers behind its `more` stubs. Each text is capped at 4 MiB and the request at 8 MiB. The parser (`src/core/reddit-json.ts`, with the Zod schemas in `src/core/reddit-wire.ts`) takes a post Listing and a comment Listing, each of `kind` `Listing` as are the reply Listings, checks the post id against the link, every `parent_id` against the tree and every comment id for duplicates and for the id grammar the stored Digest accepts (1 to 29 letters or digits, so `t1_` plus the id is at most 32 characters, `src/core/comment-id.ts`), walks the tree without recursion, and drops a deleted or removed body, `AutoModerator` and a bare agreement from the Kept candidates (`src/core/comment-filter.ts`); a link to one comment stores that comment as the post text and its descendants as the thread, with no reported count. A comment link's tree starts at the response's outermost comment, whose parent may be outside the response (Reddit's `context` is the number of parents returned and may be 0, https://www.reddit.com/dev/api/#GET_comments_{article}); every other `parent_id` must match inside the response. One batch writes the Item's content, the thread rows (each statement binds its rows as one JSON array parameter of at most 1,500,000 bytes counting the brackets and separators (`jsonArrays` in `src/core/thread-rows.ts`), expanded with `json_each`, so no statement nears D1's 100-parameter or 2 MB limits), a content generation increment, marks every open fetch job done so that an older fetch cannot overwrite the thread, and opens the Digest the caller sent. The caller's `keptComments` (at most 2000 ids) are applied only in the batch that publishes that Digest, so a refresh keeps the last published selection readable until its Digest is accepted; a Digest from the Provider chooses its own Kept comments from the comments its prompt carried (AI tasks and Providers, Measured Digest input budget) and keeps only ids it was shown. A Paste of the link alone refreshes the Item through oEmbed and keeps the stored thread.
  - **Several answers.** The first text sets the Item's post, its title and its `reported` count. Each later text is read by the same parser, must be a thread of the same post, and must hold exactly one comment at its top, as a permalink answer does (an answer with no comment changes nothing). `graft` (`src/core/reddit-tree.ts`) places it in tree order, before any check of the whole tree runs: when the comment's id is in the `children` of a `more` stub with the same `parent_id`, the comment and its replies take the stub's place at the stub's depth, and the stub stays, listing only the ids not yet answered; when the comment is the parent of a stub with no children, the answer's replies replace that stub. Answers apply in order, so a stub inside one answer is filled by a later answer. Then the whole tree is checked as for one text, so a comment id that two answers hold answers 400 `appears twice`. An answer that fills no stub answers 400 and changes nothing. A stub that stays is stored as a `more` row, which the Reader shows as a Context stub that says its replies were not saved.
  - **Supplied page.** A Reddit post or comment link takes `page` as the Extension's fallback (`saveThreadPage`, `src/core/thread-page.ts`). When the Item already has a thread header (`reddit_threads`, so also a thread with no comments or with no published Digest), the page is refused with 409 `page: the saved thread stays` and nothing changes, because the page holds fewer comments than the saved `.json` and would drop them at the next Digest. The check is the guard of the batch that queues the page (`hasNoThread`, `src/core/reddit-thread.ts`), so a `.json` save that lands while the page is being queued is never replaced; a `.json` save that lands after it closes the page's fetch job, as any save does. The CPU limit of the Free plan (10 ms, the reason the Free plan is not supported, `docs/architecture/cloudflare-deploy-button.md`) is not measured for 40 `linkedom` parses and a large `JSON.parse` in one slice. The job owns the requests; the CLI route's one lookup after a `found: false` answer (`shownOnX`) is the only other caller. The first 429 or other unavailable answer stops every later request of the slice, the `t.co` hops of posts already started included. The rules are exact, with no similarity and no length guess (`src/core/x-oembed.ts`). A post must exist on X under that id and that author (the handle in `author_url`, compared without case). A whole post must equal the stored text after one normalisation: every run of white space becomes one space, a `<br>` is one separator, a media link is ignored only when X's answer has the media anchor, and every other link in the stored text must agree with the anchor in the same position, by its `href`, by its display text, or by the address its `t.co` link redirects to (one request that stops at the first redirect). Markup in the paragraph other than text, `<br>` and `<a>`, and a `url` that is not a status address, make the answer unusable and never throw: an unusable answer for the root is unavailable, and for a reply it is a rejected reply. A post that X returns cut is recognised only by its text ending in U+2026, optionally followed by links, with at least 250 characters before the mark, each link counted as 23 characters (X's own length for a `t.co` link: the recorded cut heads of 255 characters with one link and 264 to 276 without fit a cut at about 277; the two numbers are chosen, not documented by X). The stored text must then start with the text before the mark, and the rest is stored unverified and counted. A search for a real post with two links before its cut (one run of the grok CLI's X search on 2026-11-13) returned none, so the two-link case is proven only by the rule and an invented answer. A reply must have an id greater than the root's and a parent with an earlier id, or it is rejected before any request. A reply that fails is dropped and counted, its replies move to the nearest reply that stays (or to the post), and the post's reply count is raised to at least the replies received plus those dropped. At publish, the thread is compared with the highest stored generation that holds comments: one with fewer replies is never published (`fewer-replies`, the Item ends `unreadable`, and the stored thread stays), and a thread with fewer replies than the post reports ends with the Reader's "Further replies were not saved" row. A root post that fails ends the Item `unreadable` on both routes (`x-verify-refused`). A Reddit post or comment is asked only while the Item holds no thread (`noThreadFor`, the check the archive fill uses), and its page publishes through the Reddit page path (Supplied thread and Supplied page above), so the Item keeps its Reddit Source and kind. An Item with a thread skips the plug-ins and takes the built-in route, which keeps the thread. Every other link publishes through `detailsOfSuppliedPage`: 100 words or more become an Article with image storage and Highlight anchoring, and fewer a Link-only Item with the plug-in's title. A video-host link (YouTube, Vimeo) is offered to the plug-ins too, but it keeps the title-only publication every video-host page gets (`detailsOfSuppliedPage` returns a Link-only Item for it before it reads the Markdown). A short link is asked by its resolved address, as the built-in fetchers see it. Before any `matches` runs, `Network.reachable` (`nodeNetwork` in `src/targets/node/network.ts`) resolves the link's host with the classification `globalAddressesOnly` uses; a host that resolves and has no globally reachable address ends the fetch `refused`, as on the built-in route, and no plug-in is asked. A host that does not resolve is still offered, because the plug-in may know it, and the Worker's `reachable` always answers `true`. The check covers the link a plug-in is asked about, not the plug-in's own network calls. The plug-in returns no URL, key or reference, so the Item's identity and the data model do not change.
  - **Order.** `fetchedForJob` asks the plug-ins before the built-in route, in listed order, only for a job with no Extension page. The first `matches` that returns `true` fetches; the later plug-ins and the built-in route do not run for that link. `false` moves on to the next plug-in. A page the Extension sent wins over every plug-in. The answer reaches the Item only through the fetch job's guarded finishing batch (Jobs, leases and the schedule), so an answer that arrives after the job was closed or taken over publishes nothing, and no plug-in callback writes Item state.
  - **Per-call checks and results.** `matches` must return the boolean `true` or `false`. A thrown error, a Promise (its late rejection is ignored) or any other value is a plug-in failure, and so are a thrown or rejected `fetch`, an answer that fails the schema and one over `PAGE_BYTES`. Each ends the fetch `unreadable` without trying later plug-ins or the built-in route, so a broken plug-in shows as a failed fetch and not as quietly different content. `unreadable` settles the Item `ready` and keeps earlier content, Highlights and Note. The methods are called as methods of the default export.
  - **Deadline.** The plug-in gets the fetch job's 120 s signal (`attemptFetch` in `src/core/fetch-job.ts`). `pluginPage` calls no matcher and no `fetch` when the signal has already aborted, so a throwing matcher cannot turn an expired deadline into `unreadable`; otherwise it races the answer against the signal and removes its listener afterwards. Only that signal aborting gives `timeout` (retry rules as for any fetch); an `AbortError` thrown while the signal is open is a plug-in failure. `Promise.race` subscribes to the answer, so a rejection that arrives after the deadline is handled and cannot end the process, and a late answer or rejection is dropped. This stops the app waiting. It does not stop the plug-in: a synchronous loop, a runaway allocation, a timer or `process.exit()` still reach the whole process. Process isolation (a child process or worker thread) is not built, because the spec gives no isolation promise ("at their own risk"). Neither the signal, the schema nor a read-only mount is a sandbox.
  - **Loading** (`src/targets/node/fetcher-modules.ts`, because `src/core` and `src/http` refuse a computed `import()` and a `node:` import). `startNode` takes the raw `THREADSIFT_FETCHERS` text, and the loader runs first in it, before the CLI runners, the job loop and the listener. Unset, empty or blank means none. Otherwise the text is split on `,` and each entry trimmed; an empty entry (a double or trailing comma) fails the start. An entry is an absolute path, or a `file:` URL with an empty or `localhost` host and no query or fragment (`fileURLToPath` converts it, so `#` and `%` in a file name stay safe; a comma in a file name is written `%2C` in the `file:` form). A relative path, a bare package name, another scheme, a missing file or a directory fails the start. The path goes through `realpath` before the import, and two entries with the same real path fail the start. The default export is checked with Zod (an object with callable `matches` and `fetch`; `z.function()` is not used, because it wraps the function and checks nothing at start). Any failure throws one error that names the module as written, a fixed stage word (`specifier`, `file`, `import`, `shape`) and the failure's class name, and drops the original error and its message, so the start stops with a nonzero exit and the module's own error text is not printed. All entries are resolved before any is imported, and each loaded module logs `{"event":"fetcher-loaded","module":...}` once all have loaded. No timeout applies to the import: a module whose top-level `await` never settles keeps the Instance from starting. Supported formats: `.mjs` (recommended) or `.mts`; `.js` and `.ts` follow the nearest `package.json` `type`; `.ts` runs on Node 26's type stripping, so only erasable syntax, explicit import extensions and no `tsconfig.json`. Loading happens at start only: adding or removing a module needs a restart, and removing the variable returns to the built-ins. No screen lists plug-ins; the start-up lines are the record.
  - **Logging.** Each plug-in failure writes one line through `logFailure` with the event `fetcher-failed`, the module as written, a fixed stage word (`matches`, `fetch`, `page`, `size`, `timeout`) and the error's class name. It carries no pasted URL, message, stack, Zod issue or page content. The guarantee covers only what Threadsift writes; plug-in code can call `console` itself.
  - **Trust.** A plug-in runs in the app process with the Instance's environment, its files, the database and `THREADSIFT_SECRET_KEY`. The container runs up to 4 jobs at once (`LOOP_WIDTH`), so one module serves several calls at once, and a retry or lease takeover may call it again for one link, so exactly-once is not promised. Whoever controls the container's environment and mounted folders can add one; no screen or API does. Its own network calls do not pass `guardedFetch` (see Private addresses).
- **URLs:** one normalizer (lower-case host, no `www.`, tracking parameters dropped, short links followed) gives each Item its identity.
- **Private addresses.** A pasted link, a one-hop link or a redirect could point a fetcher at the server's own network, and the page would then be stored, served over MCP and mirrored to GitHub. So every request the server sends to a pasted address goes through one function, `guardedFetch` (`src/core/fetch-guard.ts`), with one exception: a fetcher plug-in's own network calls do not pass it, so a plug-in can reach the server's private network, and what it stores is served over MCP and mirrored to GitHub (the images in its Markdown are still downloaded through the guard). The guard follows redirects by hand and checks each hop before it connects. The `Network` port makes one request per call without following redirects and sends the extra headers the policy gives that hop: the container's adapter is `node:http` and `node:https`, the Worker's is the global `fetch` with `redirect: "manual"`. On Cloudflare, that `fetch` answers a host that does not resolve with Cloudflare's own `530` and the body `error code: 1016`, not an error (measured from a deployed Worker on 2026-11-06), so the Worker's adapter turns that answer into a network failure, which ends a new Item `failed` with "Couldn’t reach the website" as on the container.
  - **Address rules.** `src/core/addresses.ts` allows a literal address only when it is global unicast and outside every block of the IANA special-purpose registries whose Globally Reachable value is not True, plus multicast and the reserved IPv4 block. It also refuses `2002::/16` (6to4), where an IPv4 address is embedded, decodes the IPv4 address embedded in `64:ff9b::/96` (RFC 6052), and refuses `64:ff9b:1::/48` whole, because the registry marks it Globally Reachable False and RFC 8215 leaves its prefix length and layout to the operator. Blocks whose registry rows hold a True sub-block (`192.0.0.0/24`, `2001::/23`) are refused whole, so the PCP, TURN and DNS-SD anycast addresses are refused too. The WHATWG URL parser turns `2130706433` and `0x7f.1` into `127.0.0.1` before the check, and `localhost` and every name under `.localhost` are refused by name (RFC 6761).
  - **Container.** The adapter passes a `lookup` function to `http.request`, so the check runs on the addresses the connection will use and the name is never resolved a second time. A name such as `localtest.me`, which resolves to `127.0.0.1` in public DNS, is refused after it resolves, so the link is saved without a title. A Worker deployed on Cloudflare's network cannot reach the owner's network, so there the check covers literal addresses and `localhost` only. The local Worker under `wrangler dev` runs on the owner's machine and has the same check, so the name check is missing there (see Open items).
  - **Posting to the Grok Bot.** `Network.post(url, body, signal, headers)` makes one POST without following a redirect, so a 3xx answers as a status. The container's adapter is `exchange` in `src/targets/node/network.ts`, which `get` shares: `lookup: globalAddressesOnly` refuses a name that resolves only to non-global addresses at connect time (`localtest.me` answered `refused` in 42 ms, 2026-11-12), and `agent: false`; `post` sends `Accept-Encoding: identity`, so an answer with a `Content-Encoding` the container cannot decode is not turned into `unreachable`. The Worker's is the global `fetch` with `redirect: "manual"`. Both first refuse a literal private address and a name under `.localhost` (`assertPublicHost`, `src/core/public-host.ts`), because Node skips `lookup` for a literal address; `test/grok-bot-network.test.ts` calls both adapters' `post` for that. Save stores the address in its canonical form (`new URL(address).href`, so `HTTPS://Example.com/hook` is stored as `https://example.com/hook`), and the container picks `http` or `https` from `new URL(url).protocol`. The Worker cannot check the address a public name resolves to, because Cloudflare resolves it, so a name that points to a private address is checked on the container only; whether a Worker reaches a private address through a public name is not verified. Three more limits of Worker `fetch` are not enforced, because they depend on the deployed Cloudflare network. Without the compatibility flag `global_fetch_strictly_public` (`wrangler.jsonc` sets only `nodejs_compat`), Cloudflare's compatibility-flags page says a `fetch` to a host in the Worker's own zone goes to that zone's origin server and ignores Workers and Cloudflare security settings, so a saved address in the Instance's own zone would reach the origin with the key in two headers (a deployed Worker is needed to show it, and `wrangler dev --local` has no zone). The same page says, for a site proxied by Cloudflare, that a port Cloudflare's proxy does not support is ignored, so `https://host:12345/` would reach port 443 (`wrangler dev --local` honored the port: `https://httpbin.org:8443/post` answered `timeout` after 8032 ms, 2026-11-12). Cloudflare's known-issues page says a Workers subrequest can only go to a URL, not to an IP address (`wrangler dev --local` sent `https://1.1.1.1/hook` and answered `bot-error` in 98 ms, so a deployed Worker is needed to see whether it fails). Only the owner can set the address, so each stays a limit of the Worker target and is not a refusal rule. The core allows the saved address only as `allowedAiUrl(address, true)` (public `https`, no credentials, query or fragment), not `ports.ai.allowsUrl`, whose container rule (`publicOnly: false`, `src/targets/node/ports.ts`) accepts `http` and private hosts. One signal of `HOP_DEADLINE_MS` (8 s) covers the connection and the reading of the answer; the answer is read to 16 KiB at most and nothing of it is kept. The ping body is `{"kind":"ping"}`, and the key travels only in `Authorization: Bearer` and `X-Automation-Key`. Each ping writes one line, `{"event":"grok-bot-ping","result":…,"status":…}`, with no address and no key. The owner's real bot, on the owner's Instance on 2026-11-12, answered three pings with 200 (`ok`), and its routine ran once per ping. It answered a wrong key with 401 and woke no run, and it answered 401 too for a routine id that does not exist under its `/automations/webhook/` path, so a wrong id shows `wrong-key`. `not-found` was not seen: no other wrong address, such as another host or path prefix, was tried, and no 403 was seen. A public name that resolves to 10.0.0.1 answered `refused` on the container with no request sent. `postToGrokBot` (`src/core/grok-bot.ts`) builds the request from the saved settings for the Test ping and for the task send (AI tasks and Providers, Grok Bot).
  - **Limits.** Every hop has an 8 s deadline from the lookup to the last body byte, 20 redirects are followed (the Fetch standard's own limit) and the body is cut at a cap, after content decoding: the page reader's `maxHtmlBytes` (5 MiB or 900 KiB, see Article) for an HTML page fetched for a pasted link, and `SMALL_BODY_BYTES` (512 KiB, defined once in `src/core/fetch-guard.ts`) for a page of any other media type, for the Reddit oEmbed call and for the HTML of a short link host; the deadline and the caps are our choices, not a source's. The guard returns the final page with its media type and a flag that says the body was cut, and a cut body is never read as an Article. `https://en.wikipedia.org/wiki/Bread` is 619,662 bytes and `https://www.gutenberg.org/files/2600/2600-h/2600-h.htm` 4,039,247 bytes after decoding (measured 2026-11-06), so the old 512 KiB cap cut both; the Gutenberg page downloaded in 2.7 s from the owner's machine, inside the 8 s deadline, and `https://www.gutenberg.org/files/100/100-h/100-h.htm` (7,018,827 bytes) is the page over the cap. The adapter passes `autoSelectFamilyAttemptTimeout: HOP_DEADLINE_MS` to `http.request`, so no connection attempt ends the hop before the deadline (Node 26 docs, `socket.connect(options)`: an attempt gets that time before Node tries the next address, 250 ms by default). Node also cuts the last attempt at that time, so a smaller value ends a host whose addresses all hang early: with 2 s per attempt, `http://example.com:81/` answered `timeout` after 4014 ms on a host without an IPv6 route (2026-11-05). The trade-off is a host whose first address drops packets while a later one works: it uses up the hop and answers `timeout` on the container. A connection that never answers and a body that stalls after the connection is open both run to the 8 s deadline on both targets. `guardedFetch` through `nodeNetwork` to `http://example.com:81/` (4 addresses, Node 26.12.1) answered `timeout` after 1003 ms without the option and after 8041 ms with it.
  - **Status log.** A fetch that ends `status` writes one JSON line with `event: "fetch-status"` and `httpStatus`, the HTTP status of the last hop, and no URL, host or body (`loggedFailureOf` in `src/core/fetch-guard.ts`; the page, Reddit oEmbed, short link and GitHub fetches all end there). The Item keeps the result `status` without the code, so this line is where a failed run shows whether the host answered 404, 429 or 503.
  - **What a hop may reach.** A redirect to a Reddit or X link stops without a request, so the oEmbed-only and X no-request rules (`docs/spec.md`, Decisions, Reddit) hold for a short link or a redirect. A short link (`SHORT_LINK_HOSTS` in `src/core/links.ts`) or a Reddit share link is the only kind of redirect that changes an Item's identity: its final or stopping URL becomes the Item's URL, and a short link that fails, or ends on a status outside 2xx, stays the Item's URL. A short link that already has an alias is not resolved at all (see Short-link aliases in `data-model-outline.md`). The request resolves the short link only to find that URL (`resolveShortLink` in `src/core/fetch-link.ts`), and reads no body on a hop that is not a short link host (the policy's `readsBody`; `requestHop` then returns the page without touching `response.body` and the abort closes the connection), because the fetch job reads the page, so a page that stalls after its headers still resolves; the Item is then stored and queued like any other Paste with the final URL as the job's address, so its content comes from the same fetch job and a short link to an article gets the article's text, and the short link is recorded as an alias of the Item. A short link that fails to resolve is saved under the short URL with that failure, no job and no alias, until a later Paste resolves it. Any other redirect only decides where the title comes from, so a redirect to a Reddit or X link leaves the pasted URL as the identity and the answer is `redirect-stopped`. A hop that is not an `http` or `https` URL answers `unsupported`, and a hop to an address that is not globally reachable answers `refused`. The 21st redirect answers `redirect-limit` even when it points to Reddit or X. A link whose Source allows no request (an X post, a Reddit link that is not a post or a comment) answers `not-requested`. A final dot on a host (`x.com.`) is dropped before any of these rules and before the Item's identity is built.
  - **Reddit share links.** A share link answers a redirect without a login, a cookie or a challenge. Checked on 2026-11-08 from the development machine with `nodeNetwork.get` (`src/targets/node/network.ts`) and `workerNetwork.get` (`src/targets/worker/network.ts`) inside `wrangler dev` (4.156.0, workerd 1.20261023.1), each followed by `resolveShortLink`, one link at a time 2 s apart with the adapters' own request headers: 32 links on each target, every answer a 301, and the same `Location` path on both targets. A post's link goes to `/r/<community>/comments/<post>/<title>/` and a comment's link goes to `/r/<community>/comments/<post>/comment/<comment id>/` (older links: `/<title>/<comment id>/`), on `www.reddit.com`. Links that do not end on a post or comment: an unknown or removed code answers 307 to the community root (`reddit.com/r/gifs/s/ZZZZZZZZZZ`), 2 of 13 older links went to a community root or a wiki page, `old.reddit.com/r/<community>/s/<code>` answers 302 to `old.reddit.com/login/`, and `reddit.com/s/<code>` answers 301 to a page that answers 200. Reddit showed a challenge page to the headless browser used for the check, so no link came from the Share control; the 32 links were collected from public GitHub issues.
  - **Meta refresh.** A page from a short link host that ends the chain as HTML and holds a `<meta http-equiv="refresh">` with a delay of 0 counts as one more redirect (`src/core/meta-refresh.ts`, the HTML standard's [shared declarative refresh steps](https://html.spec.whatwg.org/multipage/document-lifecycle.html#shared-declarative-refresh-steps), read 2026-11-05): the URL resolves against the page's URL, goes through the same address, Reddit and X, `http(s)` and 20-redirect checks, and a page on any other host is never followed this way. tinyurl.com needs it: on 2026-11-04 and 2026-11-05 it answered an old link sometimes with a 301 to the target and sometimes with a 302 to `/preview/deprecated/<id>`, a 200 HTML page whose head holds the refresh (`curl` and a probe through `nodeNetwork.get`).
