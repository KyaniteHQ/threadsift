# Fetchers

The built-in fetchers are functions that `fetchedForJob` (`src/core/fetch-source.ts`) calls by the link's kind, not a port: article, GitHub and Reddit below. The one registry is `Ports.fetchers`, the list of plug-ins (Plug-ins below). X has its own two routes below, the Grok Bot and the grok CLI.

- **Article:** a plain `fetch` through `guardedFetch`, then Defuddle 0.19.6 on the linkedom document that also gives the title, with Markdown output (`readArticle` in `src/core/article.ts`). Its CPU cost is why the Cloudflare target needs Workers Paid (see Cloudflare deploy button in `cloudflare-deploy-button.md`). No Browser Rendering: pages that need JavaScript or a login come in through the Extension.
  - **Article or Other.** The 100-word minimum is our choice, from a probe with Defuddle 0.19.6 and linkedom 0.18.15 on 2026-11-06: `https://example.com/` gave 25 words, `https://stephango.com/saw` 143 and `https://en.wikipedia.org/wiki/Bread` 6642. With `useAsync: false` a YouTube watch page gives 0 words (probe, 2026-11-06), so no YouTube entry of `VIDEO_HOSTS` (`src/core/links.ts`) has a page that can fail on its own; `https://vimeo.com/terms` (8,211 words) is the page that needs the list, so the list is matched against the final URL and not the pasted one.
  - **Defuddle makes no request of its own.** It runs with `useAsync: false`, because 0.19.6 extractors such as `c2-wiki` fetch extra pages with the global `fetch`, outside the guard (`src/extractors/c2-wiki.ts` at tag 0.19.6). `https://wiki.c2.com/?WelcomeVisitors` shows it: with the option Defuddle reads 9 words from the page and sends nothing, and without it the extractor requests `https://c2.com/wiki/remodel/pages/WelcomeVisitors` and returns 376 words (probe on Node 26.12.1, 2026-11-06). `readArticle` also passes Defuddle a `fetch` option that refuses every request (`Options.fetch`, `node_modules/defuddle/dist/types.d.ts`), so an extractor that ran despite `useAsync: false` would fail the job. The guarded fetch cannot be passed instead, because the reader runs where no `Network` port exists (a worker thread on the container).
  - **Markdown only.** Defuddle keeps `video`, `audio` and `iframe` elements as raw HTML in its Markdown, and the Reader renders Markdown without raw HTML, so `readArticle` removes those elements before Defuddle runs. Media explains how they become links and rows.
  - **Where it runs.** Parsing, the title read and Defuddle sit behind the `PageReader` port (`src/core/ports.ts`). The container adapter (`src/targets/node/page-reader.ts`) sends each page to one `node:worker_threads` worker, because Defuddle runs on the thread that calls it: a 4 MB Gutenberg page blocked the container's event loop for about 8 s, and the API answered nothing in that time. When a read's deadline aborts it, the adapter terminates the worker, fails that read alone with `PageReadTimeout`, and posts the other pending reads again to a new worker. A probe with a 4.5 MiB page (68.9 s to read) at a 1 s deadline next to two small reads failed all three with `PageReadTimeout` at 1.0 s before this change, and failed only the large one after it. The Worker adapter (`src/targets/worker/page-reader.ts`) calls the same functions inline and relies on the Worker's CPU limit. Each adapter gives `maxHtmlBytes`, the largest HTML page it reads: 5 MiB on the container and 900 KiB on the Worker. The 4,039,247 byte War and Peace page is therefore an Article on the container, whose whole text (3,298,760 bytes of Markdown, measured 2026-11-06) is kept in a file in the store, and an Other Item, cut at the cap, on the Worker.
  - **Worker memory.** A Worker isolate has 128 MB (Workers docs, Limits). Local `wrangler dev` does not enforce that limit, so the memory is estimated from the peak resident memory of the `workerd` processes (`VmHWM` in `/proc/<pid>/status`, sampled every 25 ms during one Paste in a fresh `wrangler dev` 4.156.0, 2026-11-06) minus the same measure for a Paste of `https://example.com/` (214.9 MiB). That is the whole process, so it overstates the isolate. The inspector (`--inspector-port`) returned no heap numbers.

A text-heavy page just under the cap may still pass 128 MB, so memory stays under Not verified. The cap makes War and Peace and `https://www.rfc-editor.org/rfc/rfc9110` (4,899,392 bytes) Other Items on the Worker.
  - **On the Worker.** `defuddle/node` bundles with `nodejs_compat`, but wrangler's bundler follows turndown's `browser` field to a build that needs a global `document`, which workerd lacks: every conversion then fell back to Defuddle's "Partial conversion completed with errors" text, which holds the raw HTML (`ReferenceError: document is not defined`, `wrangler dev` 4.156.0, 2026-11-06). `wrangler.jsonc` `alias` points `turndown` and `@mixmark-io/domino` at their Node builds ([Module aliasing](https://developers.cloudflare.com/workers/wrangler/configuration/#module-aliasing)). Wrangler resolves an alias value from the project root, so both packages are direct dependencies at the versions `defuddle` resolves (domino's last release was on 2024-04-08), and a `defuddle` update moves the two pins with it.
- **GitHub:** the GitHub REST API on both targets, anonymous or with the owner's optional token (see Token below). `fetchedOfRepository` (`src/core/github-fetch.ts`) runs when a pasted link's kind is `github-repo`, in place of the page fetch, with API version `2022-11-28`, GitHub's default version, supported until 2028-03-10 ([API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions), read 2026-11-07).
  - **Requests.** The README request runs on the owner and name that the repository answer returns, so a renamed repository reads the README of its new name. The Item's identity stays the name it was pasted with (see Item identity in `data-model-outline.md`), so `KyaniteHQ/commonplace` stays an Item under that name and shows the metadata of `KyaniteHQ/threadsift`, which GitHub redirects it to. A deep link such as an issue URL has the same kind and reads the same repository. GitHub says any request may redirect and the client should follow ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#follow-redirects)), and the guard's chain of 20 does that.
  - **Headers.** The GitHub policy (`FetchPolicy.headers`) returns the extra headers only for an `https` URL on `api.github.com`, so they ride each redirect hop to that host and never reach another host. The global `REQUEST_HEADERS`, which every pasted site receives, did not change. The guard reads `NetworkResponse.rateLimit` only for a 403 or 429 from `https://api.github.com` (see Rate limits below).
  - **Token.** `Authorization: Bearer <token>` goes only on a hop whose URL has the origin `https://api.github.com`, compared as a whole origin so another port of that host gets none (`apiPolicy`, `src/core/github-api.ts`), so a redirect to another host never carries it. An unreadable token ends the fetch as `github-token` without a request. A repository or README answer of 401 while a token was sent also ends it as `github-token`: the fetch writes no content, so the Item keeps its metadata and README, and the Item is not fetched again without the token. A 403 or 429 stays `status`. A repository answer marked `private` ends the fetch as `status` before the README request, so a token with access to private repositories stores no private metadata; no run reached that case (see Open items).
  - **Rate limits.** A 403 or 429 from the GitHub API is a primary limit when `x-ratelimit-remaining` is `0` and a secondary limit when the JSON `message` names a "secondary rate limit" (`rateLimitOf`, `src/core/github-rate-limit.ts`; [Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), read 2026-11-08). The guard classifies from the status and the headers first, so a header-confirmed primary limit never waits on the body and survives a body that stalls, closes or fails to decompress. Only an answer the headers do not confirm gets its message read, cut at 8 KiB (`ERROR_BODY_BYTES`, our choice). The earliest retry time is the later of `x-ratelimit-reset` and `retry-after`, and `Retry-After` counts for a primary limit too, because the later time is the safe one. `retry-after` is read as a whole number of seconds, then with `Date.parse` (`retryAfterAt` in `src/core/github-rate-limit.ts`). GitHub documents seconds; the date fallback delegates to the runtime instead of maintaining an HTTP-date parser. With no usable time the wait is 60 seconds and 120 seconds for the second limited attempt (`FALLBACK_BASE_MS`, from the docs' "at least one minute" and "exponentially increasing"; the numbers are ours), so no limit ever gives an immediate retry.
  - **Cooldown and attempts.** A limited answer stores the Instance's cooldown (`github_cooldown`, one row, `startCooldown` in `src/core/github-cooldown.ts`, never moved earlier). It is at most one hour (`MAX_COOLDOWN_MS`), because every primary limit GitHub documents is per hour ([Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api), read 2026-11-09) and the page names no longer wait. A stored time more than an hour ahead is cut and written back, so a row from a wrong header or a host clock that ran behind ends within the hour. Saving or removing the GitHub token deletes the row in the same batch, because the token has its own limit. `requestApi` (`src/core/github-api.ts`) checks the cooldown before each request, so a Paste of any GitHub link waits for it too. A request sent with a credential that was saved over or removed since stores no cooldown: `startCooldown` throws `CredentialChanged`, which `withCurrentCredential` (`src/core/github-token.ts`) catches and sends the whole request again with the current credential. A limited attempt counts once whichever request was limited: the first two defer, and the third ends the Item `failed` with the reason `rate-limited`, keeping its saved content, and drops a pending caller Digest like `gave-up`. Finding a cooldown counts no attempt. Verify (`verifyGithubToken`) goes through `requestApi` too: during a stored cooldown it sends no request and answers the refusal `rate-limited`. GitHub exempts `GET /rate_limit` from the primary limit but says it can count against the secondary limit ([Rate limits for the REST API](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#checking-the-status-of-your-rate-limit), read 2026-11-08), so a Verify during a secondary backoff would add to the load that caused it.
  - **README format.** The raw media type (`application/vnd.github.raw+json`) answers no file name, so a fetch could not tell Markdown from another format (response headers of `GET /repos/kepano/defuddle/readme`, `curl`, 2026-11-07). The README request asks for the JSON form instead, which has the `name`, the `encoding` and the base64 `content` in one request. The Item keeps the README as post text only when the name ends in `.md` or `.markdown` (any case) and the encoding is `base64`; `README.rst`, `README` or `ReadMe` give no text. The JSON body is larger than the file: GitHub wraps the base64 `content` every 60 characters and JSON escapes each line break, so 45 file bytes take 62 bytes (a 14,146-byte README gave 316 base64 lines in a 20,313-byte answer, same `curl`), and the metadata adds about 0.8 KiB there and, by estimate, under 4 KiB for the longest owner and repository names. The README request therefore has its own cap, `README_ANSWER_BYTES` (768 KiB, `FetchPolicy.dataMaxBytes`), which holds the answer for a README of 512 KiB (about 706 KiB of JSON) with room for the metadata. A README whose answer is still cut is never parsed and never stored, and it is not "no README": the README read fails with `unreadable`, the fetch writes nothing, and a refresh keeps the text and metadata saved earlier. GitHub documents the JSON form for files up to 1 MB ([Get repository content](https://docs.github.com/en/rest/repos/contents#get-repository-content)); a larger README is expected to answer with an HTTP error, which takes the `status` path. Relative links and images are not resolved, because the Reader refuses a relative URL. `NOASSERTION`, GitHub's answer for a license it cannot name, is stored as no license.
  - **Outcomes.** A repository 200 with a README 404 gives a ready Item with metadata and no text, and the Reader says the repository has no Markdown README. A repository answer that is not 2xx (404, 451, a 403 or 429 that is not a rate limit) and a README answer that is neither 200 nor 404 end the fetch with the result `status` and write no metadata: the Item settles `ready` and Link-only with no failure reason, so its row offers no Try again, and the owner pastes the link again to refetch it. `status` is not retried. A network error or a timeout takes the path it takes for a page, and an answer that does not parse gives `unreadable`.
  - **Publication.** A repository is its own kind of fetched content (`github-repo` in `src/core/details.ts`), never an Article. The guarded finishing batch writes the item fields, the search parts, the `github_repos` upsert and the generation together (`repositoryWrites`, `src/core/repositories.ts`), so a runner whose claim was taken over writes none of them. A failed fetch writes no repository row, and an Item keeps its earlier row until a fetch that succeeds replaces it.
- **Reddit:** oEmbed for the title, author and subreddit, and one `.json` parser (`src/core/reddit-json.ts`) for the `.json` paste, the JSON the Extension sends and the account fetch; the Extension's Defuddle page, sent as a `page`, when its `.json` request failed. A `more` stub whose replies could not be fetched becomes a Context stub. In the self-hosted builds, a link without Extension content goes first to the connected account, when there is one and its session works, and then to the archive fill.
  - **Archive fill.** Arctic Shift's comment tree passes through a thin adapter into the same parser (Arctic's top level is `{"data":[t1 nodes]}`, not Reddit's two Listings, while nested `replies` are Listings), so no second parser exists. The fill runs inside the fetch job, started together with the oEmbed request (`fetchedWithThread`, `src/core/reddit-fetch.ts`), only when the setting is on and the Item holds no thread. It asks for the post (`/api/posts/ids?ids=<id>`) and then the whole tree (`/api/comments/tree?link_id=t3_<id>&limit=9999`) through the fetch guard, one request at a time. Arctic's rate limit is respected: on a 429 the request is sent once more after the seconds in `X-RateLimit-Reset` (per Arctic's API README), and a reset longer than 10 s or a second 429 leaves the Item Link-only without waiting. An answer larger than 8 MiB (`ITEM_REQUEST_BYTES`, so the Worker holds at most that text and its parse), a timeout, an outage, a post the archive lacks or an answer the parser refuses also leave the Item Link-only, and none of them fails the Item or retries the job. The oEmbed title is kept when it exists; the archive's title is used only when oEmbed failed. A comment the archive marks `_meta.was_deleted_later` is rewritten to the `[deleted]` placeholder before the parser reads it, so the Comment filter drops it and its replies keep their place.
  - **Connected account.** The account is the first source for a post or comment that holds no saved thread, before the archive fill and whether or not the archive fill is on. `reddit-fetch.ts` takes the turn first (`accountTurn`, `src/core/reddit-account-turn.ts`), so a job that has to wait sends no request, not even oEmbed. `accountThread` (`src/core/reddit-account-fetch.ts`) requests the post's `.json` and the replies behind each `more` stub by permalink, with an address built from `redditRefOf` and never from the pasted text. The loop that asks for the replies is `fillAnswers` (`src/core/thread-fill.ts`), which the Extension calls too. Its limits are 500 ms between request starts (the account row keeps `last_request_at`, so the 500 ms also holds from one fill to the next), at most 100 requests in all (`mayAsk`, `src/core/reddit-window.ts`), 8 MiB held, a stop at the first 429 and a fill deadline of 90 s on the server (the Extension's is 150 s). Before each request the server asks whether the fill's run still holds the turn (`holdsTurn`, `src/core/reddit-account-queue.ts`), so Disconnect, `expired`, a closed or deleted job and a takeover run of the same job stop the fill within one request. A fill that stops early stores the thread with Context stubs, so up to 99 requests of a limited budget are never thrown away. The stored thread has a null `archived_at`, because the thread is current. One fill runs at a time, oldest job first (`jobs-leases-and-the-schedule.md`, The Reddit turn).
  - **Transport.** The port is `Ports.redditSession` (`src/core/ports.ts`), one `get(path, cookie, signal)` to `www.reddit.com`, a host fixed in the adapter, that follows no redirect with the session and sends the app's own `Threadsift/1` User-Agent, which Reddit answered with 200 (2026-11-13). The container sends it with the platform `fetch` (`nodeRedditSession`, `src/targets/node/network.ts`); no browser-impersonating client, because plain `fetch` got HTTP 200. The Worker sends it over `connect()` from `cloudflare:sockets` (`src/targets/worker/reddit-session.ts`) with HTTP/1.1 written and read by the app (`src/targets/worker/http1.ts`), because Reddit answers the Workers `fetch` client with 403 even with the cookie, while a raw socket from the same Worker got 200 (3 of 3 runs, 2026-11-05). The Worker opens one connection for each request and asks for `Connection: close`, because the port is stateless and a socket cannot outlive the invocation that made it. Reddit answers an HTTP/1.1 request with `Content-Length` and `Connection: close`, and honours `Accept-Encoding: identity` (2026-11-13, checked over TLS from the development machine), so the reader also handles a chunked body and a body that ends with the connection, and refuses an encoded one. A search on 2026-11-13 found no maintained HTTP client over `connect()` (`@pixel/socket-fetch` is 3 releases old and published on JSR only), so the reader is the app's own.
  - **Request limit and session health.** Reddit's request limit is read from its headers (`x-ratelimit-remaining` and `x-ratelimit-reset`: 100 requests for about 600 s, seen as `99.0` with a decimal) and stored on the account row, and no job takes the turn while the stored window is used up or `limited_until` is in the future. A 429 stores `window_remaining = 0` and `limited_until` (the largest of that answer's `x-ratelimit-reset`, its `Retry-After` and 60 s, cut to one hour). On the first request the job then waits with `reddit-limit` and counts an attempt, and the third limited attempt uses the archive fill. A first answer that shows fewer requests left than the hidden replies need drops that answer, waits for the reset and counts no attempt, so a later Paste, which never replaces a saved thread, does not keep a thread with stubs that could have been fetched; a thread that needs 100 requests or more is stored with stubs. A 401 or 403 sends one `me.json` check with the same session (`checkSession`, `src/core/reddit-account.ts`). `verdictOf` calls a 403 `blocked`, not `logged-out`, because Reddit answers 403 with the same network-security page to an altered session and to no session at all (2026-11-13); a 401 or a 200 that names no account is `logged-out` and sets the state `expired` at once. A fill whose first request and `me.json` check both answer 403 is one refused fill. `refused_threads` keeps the post id of each thread whose fill was refused since the last answer that showed the session works, so a thread counts once however many jobs or retries it takes, and the third distinct thread sets `expired`. Any answer that shows the session works clears the streak. Any other status, a timeout, a network error or a parse refusal uses the archive fill for that fetch and leaves the state alone. The fill's start rule is unmeasured for a session that Reddit logged out: the first real expiry will show whether Reddit answers `me.json` with 401, with a 200 that names no account, or with 403.
  - **Supplied thread.** `POST /api/items` with `content` is a Paste of a post or comment link with its `.json` (`src/core/paste.ts`); the server sends no request for thread JSON. `content` is one JSON text, or 1 to 101 texts (`MAX_THREAD_ANSWERS`): the thread's `.json` first, then the permalink answers behind its `more` stubs. A comment link's tree starts at the response's outermost comment, whose parent may be outside the response (Reddit's `context` is the number of parents returned and may be 0, https://www.reddit.com/dev/api/#GET_comments_{article}); every other `parent_id` must match inside the response. The parser (`src/core/reddit-json.ts`, schemas in `src/core/reddit-wire.ts`) checks ids against the link and the tree and drops a deleted or removed body, `AutoModerator` and a bare agreement from the Kept candidates (`src/core/comment-filter.ts`). The thread rows go in as JSON arrays expanded with `json_each` (`jsonArrays`, `src/core/thread-rows.ts`), so no statement nears D1's 100-parameter or 2 MB limits. One batch writes the content and the rows, increments the content generation, marks every open fetch job done so that an older fetch cannot overwrite the thread, and opens the Digest the caller sent. The caller's `keptComments` are applied only in the batch that publishes that Digest, so a refresh keeps the last published selection readable until its Digest is accepted. A Digest from the Provider chooses its own Kept comments from the comments its prompt carried (AI tasks and Providers, Measured Digest input budget) and keeps only ids it was shown. A Paste of the link alone refreshes the Item through oEmbed and keeps the stored thread.
  - **Several answers.** The first text sets the Item's post, its title and its `reported` count. Each later text must be a thread of the same post and hold exactly one comment at its top, as a permalink answer does. `graft` (`src/core/reddit-tree.ts`) places it in tree order: the comment and its replies take the place of the `more` stub that lists its id, and the stub stays, listing only the ids not yet answered, until none is left. An answer that fills no stub answers 400 and changes nothing. A stub that stays is stored as a `more` row, which the Reader shows as a Context stub that says its replies were not saved.
  - **Supplied page.** A Reddit post or comment link takes `page` as the Extension's fallback (`saveThreadPage`, `src/core/thread-page.ts`). When the Item already has a thread header (`reddit_threads`, so also a thread with no comments or with no published Digest), the page is refused with 409 `page: the saved thread stays`, because the page holds fewer comments than the saved `.json` and would drop them at the next Digest. The check is the guard of the batch that queues the page (`hasNoThread`, `src/core/reddit-thread.ts`), so a `.json` save that lands while the page is being queued is never replaced. Otherwise the page goes through the same path as the page of any other link (Publishing a sent page): the Item keeps its Reddit source and kind, gets the title, author and date of the page and the community from the link's `/r/<community>/` segment, and has no thread header and no comment rows. Two parts of that path differ for a Reddit page. The 100-word minimum decides only whether the Item gets post text and images; below it the Item keeps its title, author and community and stays a Reddit Item, where an article below the minimum becomes a plain link with no author. A refresh by a page below the minimum clears the post text, the date and the stored images and advances the content generation (`empty-page` in `src/core/details.ts`), and the Item's source and kind never change to Article.
- **X:** one reader reads an X link, and the owner chooses it in Settings (`x_settings.reader`, `X_READER_CHOICES` in `src/core/kinds.ts`; no row means `auto`). `routeOf` (`src/core/x-reader.ts`) decides the route from the choice and the two readers' states, and the fetch job follows that route and nothing else. `auto` is the order from before the choice existed: the Grok Bot first, on both targets, when its settings are saved and its key opens; otherwise the grok CLI in the container, when it is installed; otherwise a Link-only Item. `grok-bot` and `grok-cli` use that reader alone. When it cannot be used, the fetch ends a Link-only Item and stores the note that names the cause (`items.x_note`, `X_READ_NOTES`). The other reader is not tried, so one Paste costs one route. A Paste can carry the thread too, and it ignores the choice, because it makes no fetch job. The Worker has no CLI: `offeredReaders` leaves `grok-cli` out, and `chosenXReader` counts a `grok-cli` row that the Worker finds in a database written by the Node target as `auto`, so `GET /api/settings/x` and the route agree. Each reread follows the current reader choice. While the job has an open Grok Bot task (`hasOpenIntakeTask`, `src/core/bot-task-states.ts`), `xRouteOf` keeps the bot route whatever the setting says. A saved Grok Bot is never skipped for the CLI under `auto`, and a failed bot answer is never retried through the CLI.
  - **Grok Bot.** `attemptFetch` (`src/core/fetch-attempt.ts`) asks `xRouteOf` before `fetchedForJob`, so before any plug-in or other fetch. On the bot route it runs `botStep` with `xIntakeKind`, so the task, the send, the wait, the cap and the retries are the Grok Bot task lifecycle (AI tasks and Providers, Grok Bot). There is no fallback to another source after a failure: a bot that never answers ends the Item `failed` with `gave-up`, because closing the job also fails its running tasks. A bot that answers `unavailable` ends the Item Link-only with the note `bot-unavailable`, not as a website error.
  - **Grok CLI, where it runs.** `grokXFetcher` (`src/targets/node/grok-x.ts`) is `Ports.xFetcher` (`null` on the Worker and when no `grok` binary is found on `PATH` at start). The CLI is an agent harness. The status id is the only outside input in its prompt. Posts reach the model only as tool results, from which it writes the thread, so a run can return an incorrect answer (The check against X below). It has its own `Slots` of width 2 (our choice, unsupported: xAI's quota is not Claude's or Codex's). A run waits for a slot for at most `X_SLOT_WAIT_MS` (180 s, `src/core/request-waits.ts`) and then has `X_RUN_DEADLINE_MS` (180 s) from the moment the slot is granted (`inTimedSlot`, `src/targets/node/cli-slots.ts`), so the time spent behind other runs never shortens it. The fetch job's own deadline for the grok CLI route is the sum of the two, and the claim of a fetch job lasts that sum plus `CLAIM_MARGIN_MS` (`fetchHandler`, `src/core/fetch-job.ts`; `jobs-leases-and-the-schedule.md`). The container runs 4 jobs at once and the CLI has 2 slots, so a third X fetch waits for one of the first two. `parseXThreadValue` (`src/core/x-thread.ts`) is the parser a Paste uses, so the stored rows are the same.
  - **The isolation rule.** The run may reach the two X tools (`x_thread_fetch`, and `x_keyword_search` with `conversation_id:<id> filter:replies` and the like bands of Replies kept) and the CLI backend's `web_search` and `open_page`. It may reach no local tool: no shell, file, edit, subagent, MCP or workflow tool. The backend tools are part of the proven surface because grok 1.0.77 cannot turn them off without losing the X tools: `--disable-web-search`, `GROK_BACKEND_SEARCH=0` and `--disallowed-tools` with `web_search` each leave a run in which `x_keyword_search` is unavailable, and `--tools x_thread_fetch,x_keyword_search` restricts nothing (grok warns that the names "name no tool, so other tools stay available"). The backend tools run on xAI's side and touch no resource of the host. What they leave open: a hostile reply can make the model search or open a public page, which sends public post text and the Grok account's saved rules to a page of the attacker's choice and tells the attacker that the thread was fetched, and the page text can reach the model's answer. The stored answer passes the shape checks (`XThreadSchema`, the handle and size limits, `post.id` equal to the asked id) and the check against X's oEmbed answer (next bullet), so a hostile run cannot store a post or reply that X does not show under that id and author. The CLI's own record of a run cannot serve for this check: it holds the tool calls and the model's own answer and never the tool results (grok 1.0.77, every output format, the session folder, both logs, `grok export` and `grok trace`; a probe on 2026-11-13, open items). A dedicated Grok account is the owner's mitigation (`docs/guides/providers.md`).
  - **The check against X.** Both routes store the parsed thread unverified and unpublished and queue one `x_verify` job (`xVerifyHandler`, `src/core/x-verify-job.ts`); the Item shows nothing of the thread until that job publishes it. The stored state is the `x_verifications` table (`src/core/x-verification-tables.ts`): the thread, its Digest, a `revision` that guards every write of the job, and the `judged` map of post id to verdict. An accepted verdict records whether X cut the text and whether the reader supplied extra recipient mentions. Every write of content for the Item (`closeItemJobs`, `src/core/job-close.ts`) closes its `x_verify` job and deletes the row in the same batch, so a waiting check cannot overwrite newer content. A thread whose JSON after reply selection is longer than `MAX_ROW_BYTES` (`src/core/thread-rows.ts`, the repository's statement budget under D1's 2 MB limit) is refused with a 400 that names the limit, because the row is one value. The job asks X's public oEmbed answer for each post (`GET https://publish.x.com/oembed?url=https://x.com/i/status/<id>&omit_script=1`, no login) in slices of at most 40 planned requests, the root alone first (`sliceOf`). A post is planned at 2 requests plus its links, because it may also end in a quote link whose address needs one request (Quoted posts below). The 40 comes from the Cloudflare Workers Limits page, read 2026-11-13: 50 subrequests per invocation on the Free plan (10,000 on Paid), and the queue consumer takes one job per invocation. The CPU limit of the Free plan (10 ms, the reason the Free plan is not supported, `docs/architecture/cloudflare-deploy-button.md`) is not measured for 40 `linkedom` parses and a large `JSON.parse` in one slice. The first 429 or other unavailable answer stops every later request of the slice, the `t.co` hops of posts already started included.

    The rules are exact, with no similarity and no length guess (`src/core/x-oembed.ts`). A post must exist on X under that id and that author (the handle in `author_url`, compared without case). A 404 or 410 means X does not show it, and so does a 403 only when its body is X's own JSON for a protected or suspended post; any other 403 is unavailable. A whole post must equal the stored text after one normalisation (white space runs collapse, `<br>` is one separator). X's answer leaves out the line break before a mention anchor that follows text with no white space (`itemsOf`, `src/core/x-paragraph.ts`; a live post on 2026-11-15 shows it), so that anchor is read as a separator; a mention joined to the word before it, such as `with@name` where X shows `with @name`, stays rejected, and a hashtag or cashtag is not covered, because no live answer showed the same drop for one. A media link is ignored only when X's answer has the media anchor, and every other link in the stored text must agree with the anchor in the same position, by its `href`, by its display text, or by the address its `t.co` link redirects to (one request that stops at the first redirect). A post that X returns cut is recognised only by its text ending in U+2026, optionally followed by links, with a weighted length of at least 250 before the mark after white space runs collapse. `weightedLength` uses NFC and the code point weights from [twitter-text v3](https://github.com/twitter/twitter-text/blob/30e2430d90cff3b46393ea54caf511441983c260/config/v3.json). Most Korean, Japanese and Chinese code points count as 2, and each link counts as 23. Each `RGI_Emoji` match counts as 2, as do keycaps with or without an emoji variation selector, emoji with an emoji variation selector or skin tone modifier, and chains of these sequences or bare emoji joined by zero-width joiners. The sets come from the runtime's Unicode data, so Node and workerd may differ on the newest emoji. [Unicode Emoji](https://www.unicode.org/reports/tr51/#Emoji_Sequences) defines the sequence forms. [X's counting guide](https://docs.x.com/fundamentals/counting-characters) describes these weights. The 250 minimum is a Threadsift choice based on recorded oEmbed cuts. The Latin heads measured 255 characters with one link and 264 to 276 without links. The Korean head recorded on 2026-11-18 had 186 characters, including 91 with weight 2. It weighed 277 before white space collapsed and 273 after. The stored text must then start with the text before the mark, and the rest is stored unverified and counted. A search for a real post with two links before its cut (one run of the grok CLI's X search on 2026-11-13) returned none, so the two-link case is proven only by the rule and an invented answer. The full-text verdicts decide the author thread, including which missing parts to mark. Every other reply, including a separate reply by the post's author, can start with recipient handles that oEmbed omits. After any leading whitespace, each handle must be a whole `@name` followed by whitespace, with 1 to 15 ASCII letters, digits or underscores in the name. The remaining text must be nonempty under the same comparison rules and agree with X. A mention X shows stays in the reply. The verification job saves the reply text without the removed mentions, with its verdict, before the next slice, and publishes that text when the check ends. A reply that fails is dropped and counted, its replies move to the nearest reply that stays (or to the post), and the post's reply count is raised to at least the replies received plus those dropped.

    The author thread is joined after the check (`joinedAuthorThread`, `src/core/x-author-thread.ts`). A follow-up is a reply that passed the check, by the post's author, whose parent is the previous part, or a rejected reply of the author whose own parent leads to the previous part. A rejected middle follow-up therefore does not hide the ones after it, and an author's reply to another person's reply never joins. A reply an earlier CLI reader moved to the post because its parent was missing (`repairedParent` in the stored thread, never accepted from a Paste or the bot) never joins, because its real parent may be another person's reply. Each follow-up that stays is appended to the post text after a blank line while the joined text stays within `INLINE_TEXT_BYTES` (1,000,000 bytes); the follow-ups past that limit are left out like a rejected one. A last line (`NOT_SAVED_NOTE`, written with `tools/copy/write-copy.sh`) says a part was not saved when a reply that would have been a part was rejected or left out. The follow-ups stop being replies, so the reported reply count drops by the number of follow-ups and rejected parts. The count of joined follow-ups is stored as `reddit_threads.follow_ups` (0 for a thread saved before it, whose follow-ups are comment rows), and the fewer-replies comparison counts comments plus `follow_ups` on both sides, so a refresh never holds less than what is stored and an Item saved before the join still publishes. A Paste with `content` is joined the same way with every reply kept, but its text is not checked against X, so a Paste never gets the not-saved line unless the 1,000,000-byte limit leaves a follow-up out. At publish, the thread is compared with the highest stored generation that holds comments: one with fewer replies is never published (`fewer-replies`, the Item ends `unreadable`, and the stored thread stays), and a thread with fewer replies than the post reports ends with the Reader's "Further replies were not saved" row. A refused root logs `x-verify-refused`. For a CLI answer the verification row carries the fetch’s attempt count, so the job discards that answer and queues the next fetch after the existing delay. The bot route and the last CLI attempt end the Item `unreadable` with `x-unconfirmed` and keep any previously published thread. Not checked: a Paste with `content` (the caller's own statement), the tail of a cut post, media, the part of a link address that X does not show, anything oEmbed does not return, and the Digest that comes with an intake answer (the bot's own summary, published with the verified thread). The answers in `test/x-oembed/` keep the markup of answers recorded on 2026-11-13 and 2026-11-18 with invented handles, names, ids and text, because `AGENTS.md` keeps other people's posts out of the repository; `smoke/live.spec.ts` reads real posts from X at run time (their ids are in `smoke/x-live-thread.json`).
  - **When X does not answer.** A timeout, a 429, a 5xx, a redirect or an HTML 403 leaves a post without a verdict. The slice saves its progress and ends with the wait reason `x-verify` and the existing retry delays, and it counts an attempt only when X was unavailable; a slice that made progress and has posts left runs again at once and counts nothing. On the last attempt the job ends as `unreadable` on both routes (`x-verify-refused`), and nothing of the thread is shown. A retry after an unavailable X is a retry of the `x_verify` job only, so the grok CLI and the Grok Bot are not asked again. When the grok CLI answers `found: false`, every attempt asks oEmbed once (`notFoundBy`, `src/core/x-fetcher.ts`). A confirmed absence ends `status`. When X shows the post or gives no verdict, the fetch waits with the reason `x-reread` and reads again within its remaining attempts. An answer the schema refuses waits and reads again the same way and asks X only on the last attempt, because the CLI gave no verdict on the post (the 2026-11-15 run: grok 1.0.77 answered one of three runs for one post with no tool call, author `example` and an empty text, and the next two read it). Probe, 2026-11-13: 150 sequential requests answered with no 429 and no rate-limit header, mean 393 ms; X's documentation says "Requires authentication? No" and "Rate limited No" for the endpoint (https://docs.x.com/x-for-websites/oembed-api), and its developer policy sets duties for pages that display an embed and does not name this use (unverified).
  - **The check at run time.** The proven surface is one constant (`src/targets/node/grok-surface.ts`): the exact `grok --version` string, the argument list and the sorted names of the local tools the run exposes, which are none. `tool_definitions.json` under the run's `GROK_HOME` (not a documented interface) lists the local tools only, so it says nothing of the backend tools. The exact version string pins the client only, and a change of the backend tools on xAI's side is not detected (unverified). A preflight with the same arguments and a fixed prompt that holds no external text reads that file and compares it, before the first real fetch after the process starts and whenever the binary's path, size or modification time differs from the last proven one (`permission`, `src/targets/node/grok-proof.ts`). The binary can still be replaced between the second read of it (after the slot is taken and after the preflight) and the process start; only the tool-list check after the run covers that window, and an extra tool has by then run. Every real run is checked after it ends, also a run that failed: a list with any tool refuses the fetch and bars the binary (`extra-tools`); a list that cannot be read, or is missing after a run that exited 0, discards the answer, drops the proof of a proven binary and proves again on the next fetch (`checkedRun`). No later result replaces a bar of the same binary, also not a preflight that ends after the bar, and a run of a file that was replaced since leaves the proof of the new file alone, because a run that started before a bar or a replacement can end after it (`keptBar`, `afterRun`). A version that is not the proven one bars the binary (`version-changed`). The two bars are kept per binary until the process restarts or the binary changes (`docs/guides/providers.md` says how the owner clears it). A refused fetch logs `x-fetch-refused` with the category `surface-unproven`, and Settings shows `not-proven` with the version. The constant changes only through a code change that records a new probe.
  - **The run.** The arguments and the environment are in `grok-surface.ts` and `grokCli` (`src/targets/node/grok-process.ts`). The environment is built from nothing, so no key, proxy or `THREADSIFT_*` variable reaches the run. The prompt (`fetchPrompt`) is a request to the model, and a hostile post can override it, so the run deadline and the 2 slots are the real bounds (`--max-turns` counts model turns and not calls: a run with `--max-turns 2` took 1 turn, made all its tool calls and returned a complete answer, 2026-11-13). Both readers preserve a missing parent's id so the Reader groups its replies under one Context stub. The schema sent to the CLI stays an object with a nullable `thread`, because the proven argument list is the one probed.
  - **Partial threads.** The run reads a few dozen replies at most (Replies kept below), so a post with many replies comes back partly. Every X thread, from the CLI, from a Paste with `content` and from the Grok Bot intake, follows two rules. When the post's reply count is larger than the replies in the thread, or unknown while replies exist, code (not the model) appends a `more` row, which the Reader shows as "Further replies were not saved" (`withMoreMarked`, `src/core/x-thread.ts`). A thread with fewer replies than the stored one never replaces it, and the database decides at commit time: the write of each route holds `holdsAtLeastStored` (`src/core/x-partial.ts`) in its precondition, so a thread another writer stored with more replies after this one was built is kept. `publishThread` (`src/core/thread-save.ts`) refuses the Paste with 400, and `published` (`src/core/x-verify-publish.ts`) refuses the CLI and the intake with `x-fetch-refused` and `fewer-replies`; the Item keeps its thread. An explicit Paste follows the rule too, so the owner who wants a smaller thread deletes the Item first.
  - **Replies kept.** Both readers keep the most important replies by the 80/20 rule, decided by the owner. `readFetchedThread` (`src/core/x-replies-ranked.ts`) cuts them before the check against X, so the check asks only for replies the Item keeps. The cut ranks the replies by their likes, then by their own reply count (the bot omits it, so it counts as zero), then by the older id, and keeps the smallest set of top replies whose likes reach 80% of the likes of all the fetched replies (`X_REPLIES_LIKES_PERCENT`), never fewer than `X_REPLIES_MIN` (20) and never more than `X_REPLIES_KEPT_MAX` (40; `src/core/limits.ts`). When fewer replies qualify for ranking than the minimum, both readers keep all of them.
    - **What the cut leaves alone.** The replies of the author thread (`authorPartsOf`, `src/core/x-author-thread.ts`) are not ranked: they join the post text after the check, whatever their likes, and are not counted in the likes total or the two limits. The cut runs before the check, so when the first follow-up fails the check, a later direct follow-up of the author that the cut left out because of few likes is not joined. Bot intake also keeps replies eligible for ranking that the stored Digest names in `keptComments`, even when they rank below the cut. It uses the bot's Digest when supplied and otherwise the pending Digest sent with the link. A bot read can therefore keep more replies than a CLI read of the same link. Missing ids add nothing, and verification still checks every selected reply. A kept reply keeps its fetched ancestors, in addition to the limit, so the Reader draws the thread above it. Replies with empty text or the CLI placeholder `(No text content)` do not rank. Neither do replies whose parent id is older than the root or at least as new as the reply, because verification rejects them. These replies also do not count toward the refresh floor, except that a photo-only author part with a possible parent still counts. When the cut drops any fetched reply, the post's reported reply count is raised to at least the number of replies fetched, so the "Further replies were not saved" row appears even when X's own count is lower. A repeated reply id in a CLI answer keeps its first occurrence, because `max_id` is inclusive (The calls below) and one repeat would otherwise refuse the whole answer.
    - **A refresh never holds less.** The cut keeps at least as many posts as the Item holds (`storedReplyCount`, `src/core/x-partial.ts`), because the rule above would otherwise keep a different number on each read and the refusal of a thread with fewer replies than the stored one (Partial threads) would reject a refresh that read the same replies. This is the owner's decision: the floor wins over the maximum, so an Item stored with more than 40 replies, such as one saved with a Paste, keeps that count on every refresh.
    - **The calls.** One `x_thread_fetch` for the post, which also returns its top replies nested under their parents and their reply counts (the one source of `parentId` for them), and one for each quoted post. Then at most 6 `x_keyword_search` calls (`MAX_REPLY_CALLS`), each with `mode: "Latest"` and `limit: 10`, the largest limit the tool takes (the tool's own parameter schema, read from the model, 2026-11-15): one for each band of likes, `min_faves:300`, `min_faves:100 -min_faves:300`, `min_faves:30 -min_faves:100`, `min_faves:10 -min_faves:30` and `-min_faves:10`, and when a call returns 10 posts, one more for the same band with `max_id:<lowest id returned>` (`MAX_CALLS_PER_QUERY` is 2). `max_id` is inclusive, so the next page repeats the post it starts from and a band yields at most 19 distinct replies in 2 calls; the oldest reply of a full band is lost, which costs one low-ranked reply and is accepted until the tool offers an exclusive cursor. The bands exist because the tool returns 10 posts a call and its `Top` mode is not ordered by likes (on 2026-11-15 the first 10 of `Top` for the DeepSeek post held a reply with 11 likes and none of the 6 replies above 100), while `min_faves` filters exactly: the 5 posts of `min_faves:20 -min_faves:100` came back the same in `Top` and `Latest` mode. The steps are 300, 100, 30 and 10 likes, our choice from that one post. On a post with tens of thousands of likes the first bands fill their pages, so they return the latest replies of the band and not the most liked ones, an effect of fixed steps that no run measured against the true top. The 6 calls are our choice: 5 bands and one next page, and runs with 5, 6 and 7 calls allowed took 85, 91 to 93 and 95 to 98 s on a heavy post, so the count moves the time little.
    - **Why 20 and 40.** The minimum 20 is our choice: for the DeepSeek post the rule alone keeps 6 replies (1,170 of 1,456 likes), and the minimum brings in the next replies by likes, down to the 20th, so the Item reads as a discussion and not as its top few. The maximum 40 is our choice too: it bounds the ranked replies of a fresh read, which the run returned at 31 for the DeepSeek post and at 53 to 67 for posts with tens of thousands of replies. The stored thread can pass 40 by the ancestors of kept replies and by the refresh floor, so the maximum does not bound the Reader or the Digest input (`DIGEST_INPUT_BYTES`), which cut the replies they read themselves. Neither number is measured against the Digest.
    - **Measured** on 2026-11-15 with grok 1.0.77 on the Node target. The DeepSeek post `https://x.com/deepseek_ai/status/2121247896918253875` (465 replies reported): 31 replies, 3 of them the author's own thread, in 56, 64 and 61 s (raw runs, 7 calls allowed) and 73, 77 and 78 s in the app (`x-fetch` log, `elapsedMs`); 5,700 to 6,100 output tokens, 17,000 to 35,000 input tokens and 0.30 to 0.33 USD (`total_cost_usd` of the CLI's JSON answer). The run before this rule, on the same post, took 54 s, returned 11 replies and cost 0.12 USD with 4,686 output tokens. Posts that fill the calls, `https://x.com/SteveLovesAmmo/status/2121015586960654831` (20,500 replies) and `https://x.com/MilkTeaSept/status/2120412600790138924` (31,490 replies): 53 to 67 replies, 91 to 98 s raw, 9,300 to 10,400 output tokens and 0.44 to 0.58 USD, and 107 s from the request in the app. That is why a run has `X_RUN_DEADLINE_MS` (180 s) and not the 120 s of the other fetches: the heavy runs leave 14 to 29 s under 120 s, and a run past its deadline ends `timeout` and stores nothing.
    - **Three fetches at once.** A paste of 3 X posts at once (the DeepSeek, MilkTeaSept and SteveLovesAmmo posts, all with the grok CLI reader): the first two ran side by side and ended at 73 and 77 s, the third waited about 70 s for a slot and ran about 113 s, so its Item was ready 189 s after the paste, past the old 120 s that counted the wait. With the run deadline counted from the slot, the same paste ended `ready` for all three Items (at 113, 129 and 350 s; 3 of the 6 answers in that run were `found: false` answers that the retry delays absorbed), with no `timeout`.
  - **Quoted posts.** `post.quoted` (`src/core/x-wire.ts`) holds the chain the post quotes, in order. It defaults to an empty list when absent, and the grok answer schema (`XCliThreadSchema`) requires it, so the run must state the chain, empty or not. The Grok Bot skill (`bot/skills/threadsift/SKILL.md`, Fetch an X thread) asks the bot for the chain with the same cap: it takes the quoted id from `referenced_tweets` of the post, reads that post with `get_posts_by_id`, and goes on one post at a time, so a bot answer and a bot chat save hold it. In a task answer the skill also has the bot leave the `t.co` link of the quoted post out of the text, because the check compares that link with the next listed quoted post only when the stored text leaves it out (`withoutQuoteLink`, `src/core/x-quote-link.ts`); a Paste is not checked, so a chat save keeps the text as X returns it. `x_thread_fetch` shows the post a post quotes inside its own result (`Quoted Post:` with id, author, time, engagement and content; probe, grok 1.0.77, 2026-11-15), so the run reads the next level by calling it again for the last quoted post, and a quoted post that only a reply quotes is never added. The cap is `X_QUOTES_MAX` (5, our choice, not measured): each level costs the run one more `x_thread_fetch` call inside the run deadline, and the check one oEmbed request and one `t.co` request, and a chain deeper than 5 is rare enough that no reader needs it. Measured on 2026-11-15 with grok 1.0.77: `https://x.com/NobleBrown/status/2120566084684353565`, a post that quotes a post that quotes a third, read in 19.5 s with 2 quoted posts (`x-fetch` log), and its check took 2 slices, of 2 and 3 requests.
  - **The quoted posts are checked like the post.** Each one gets an oEmbed request by its own id and the same rules, and its judgement is kept in the same `judged` map (a cut quoted post keeps an unverified tail, counted in `unverifiedTails`). The ids must fall along the chain (each quoted id below the id of the post that quotes it, because a post can only quote an older one) and differ from the post's, every reply's and every other quoted id, or the answer is refused (`checkedQuoted`, `src/core/x-thread.ts`), so a Paste with such a chain answers 400. A post that quotes another ends its oEmbed paragraph with the quote's own `t.co` link, which the stored text does not hold, because the tools return the quoted post separately. When the stored text lacks the last link of the answer, the answer has no cut, and that link's `t.co` address leads to the status address of another post, `checked` (`src/core/x-oembed.ts`) ignores that link and `resolutionsNeeded` asks for its address. A short post that quotes another passes: probe, 2026-11-15, `https://x.com/hernan__cc/status/2120297728961872081` gave `verified` with its quote link ignored.
  - **The chain is compared with the quote link.** For the root and each listed quoted post, `rejectedQuotes` (`src/core/x-quote-link.ts`) compares the status the ignored link leads to with the next listed quoted post. When they differ, the next one is judged `rejected`, so a real post that the quote link does not lead to never shows as the quote. When the link leads to a post that no listed quoted post follows (the run left the quote out, or the chain stopped at the cap), the id the link leads to is judged `rejected` as well, under its own id although it is in no stored thread; `joinedPost` reads any `rejected` id that is in no post of the thread as a quoted post that was not saved. A whole post with no link at all cannot quote, so a quoted post listed after it is rejected. Not compared: a cut post shows no quote link, so the quoted post listed after a cut post is accepted on its own check; and a stored text that holds the quote's `t.co` link itself is compared as text and its address is not asked. A reply gets no such comparison: no quoted post of a reply is kept, and a reply that links a status in its text and loses the link in the stored text passes. The unproven part is the order of a chain whose posts are cut.
  - **Quoted posts in the Item.** After the check, the leading quoted posts, up to the first one judged `rejected`, are appended to the post text right after the post's own text and before the author thread, as nested Markdown block quotes (`joinedPost`, `src/core/x-joined-post.ts`). `leadingQuotes` is the one rule that decides which quoted posts the check still asks for, which are shown and how many are counted, so a quoted post after a rejected one is never asked. When a quoted post failed, did not fit, or was left out, one line (`Quoted posts were not saved.`, written with `tools/copy/write-copy.sh`) stands at the depth where it would stand, and the room for it is kept before the quotes are fitted into the 1,000,000-byte post text limit. The quoted text is part of the post text, so the Digest, search, the Reader, the export's Item note and the Vault mirror read it. The Digest takes the first 14,000 bytes of the post text, so a long post and thread lose the end of the thread before they lose a quoted post. The size limit of a stored thread is measured on the thread as sent (the row of `x_verifications`), not on the joined text, whose line prefixes and escapes make it longer. A refresh whose read lacks a quoted post that the Item held saves the line in its place, and the owner pastes the link again to read it once more; there is no stored count to compare, as there is for replies.
  - **Images.** The post, each quoted post and each reply carry `images`, the addresses of their photos. The run copies them from the `Media` lines of the tool results (probe, grok 1.0.77, 2026-11-15: `- Item 1: photo - URL: https://pbs.twimg.com/media/HXGiOQFWIAA0HeS.jpg`; a video item lists only a `video.twimg.com` `.mp4` address, so a video is not kept). An address is kept only when it equals its parsed form, is an `https://pbs.twimg.com/media/` address and is at most 4,096 bytes (`isXImageUrl`, `src/core/x-images.ts`); any other is dropped and the answer stays valid. The join writes each kept address as a Markdown image, so the rule has to be exact: an address that parsed but differed from its raw text carried Markdown into a post that the check had judged (probe in the commit that fixed it). The download refuses a redirect to any address that fails the same rule, so no other host is fetched. Only the replies that are parts of the author thread keep their `images`.
  - **Photos in the Item.** The join puts each photo after the text it belongs to: after the post, inside the block quote of its quoted post, and after each follow-up; a post with an open code fence or an open HTML comment, `script`, `pre`, `style` or `textarea` block gets it closed first (`closedBlocks`, `src/core/x-blocks.ts`), because such a block would otherwise swallow the photo. `storeMedia` (`src/core/store-media.ts`) stores them at publish like an Article's images (Media in `data-model-outline.md`), inside the `x_verify` publish, which has `PUBLISH_DEADLINE_MS` (90 s) for the downloads; a slice and that publish fit in the claim of 210 s. A Highlight added during the publish rebuilds only the anchors and keeps the downloaded files. A photo that cannot be stored, or one past the 20 of the Item, becomes the line `A photo was not saved.` (written with `tools/copy/write-copy.sh`), and the rest of the Item is saved. A post whose text is only photos has the tool's `(No text content)` placeholder replaced by an empty text when it has photos, so X's answer, which holds only the media link, matches it; its title is the handle when the text has no first line.
  - **What the check says about photos.** oEmbed holds the `pic.x.com` link of a post that has media. A post that has stored photos but whose oEmbed answer has no media link loses its photos, and the check records that under the key `no-photos:<post id>` in `judged` (the `x-verify` log line counts them as `photoless`). Which photo belongs to which post is not checked: the address comes from the run's tool result. The Grok Bot reader sends photos in its intake answer, which `XBotThreadSchema` (`src/core/x-wire.ts`, the shape of `XCliThreadSchema` without the reply counts) takes. The skill asks the bot for them: the `url` of the `photo` items of `includes.media` (it asks for `media.fields` `url`, because X returns only `media_key` and `type` otherwise, https://docs.x.com/x-api/fundamentals/expansions) through each post's `attachments.media_keys`, for the post, each quoted post and the replies of the post's author, and to leave the `t.co` link that X adds for the media out of the text of a post whose photos it sends, so a post that is only photos has an empty text. No run has read them through the bot's own tools yet (Open items and unverified claims). For replies, both readers keep photos only on parts of the author thread (`readFetchedThread`, `src/core/x-replies-ranked.ts`). - **Plug-ins (container only):** a self-hoster's fetcher is an ES module whose default export is a `Fetcher` (`src/core/fetcher.ts`): `matches(url)` returns a boolean and `fetch(url, { signal })` returns a promise of a page. The container loads every module listed in `THREADSIFT_FETCHERS` before it starts any work. The Worker loads none, because its bundle is built from the repository, so a plug-in there means a fork. A plug-in is trusted code of the Instance's owner, and nothing here sandboxes it.
  - **The page.** A plug-in returns page text only: `markdown`, `title` and optional `author` and `published`, the fields of the Extension's page without `videos`. A strict Zod object (`PluginPageSchema`) parses the answer, so an unknown field such as `videos` fails it. The answer must be at most `PAGE_BYTES` (1,000,000) bytes once serialized, with no truncation, and the check runs before any page processing. It limits what the app accepts, not the plug-in's memory, because the plug-in has already allocated its answer. An empty `title` ends the fetch `no-title`, as for any page. The context carries the deadline signal only: no database, file store, sealer, `Network` or `Ports`.
  - **Which links are asked.** The core asks `matches` only for a link that takes a page (`takesPage`, `src/core/links.ts`): never an X or GitHub link, and never a Reddit link that is not a post or comment, because a page there would become an Article and lose the repository or post kind and Source. A Reddit post or comment is asked only while the Item holds no thread (`noThreadFor`), and its page publishes through the Reddit page path (Supplied thread and Supplied page above), so the Item keeps its Reddit Source and kind. Every other link publishes through `detailsOfSuppliedPage`: 100 words or more become an Article with image storage and Highlight anchoring, and fewer a Link-only Item with the plug-in's title. A video-host link is offered to the plug-ins too, but it keeps the title-only publication every video-host page gets. A short link is asked by its resolved address. Before any `matches` runs, the loaded plug-in wrapper in `src/targets/node/fetcher-modules.ts` resolves the link's host with the classification `globalAddressesOnly` uses; a host that resolves and has no globally reachable address ends the fetch `refused`, as on the built-in route, and no plug-in is asked. A host that does not resolve is still offered, because the plug-in may know it. The check covers the link a plug-in is asked about, not the plug-in's own network calls. The plug-in returns no URL, key or reference, so the Item's identity and the data model do not change.
  - **Order.** `fetchedForJob` asks the plug-ins before the built-in route, in listed order, only for a job with no Extension page. The first `matches` that returns `true` fetches; the later plug-ins and the built-in route do not run for that link. A page the Extension sent wins over every plug-in. The answer reaches the Item only through the fetch job's guarded finishing batch (Jobs, leases and the schedule), so an answer that arrives after the job was closed or taken over publishes nothing, and no plug-in callback writes Item state.
  - **Per-call checks and results.** `matches` must return the boolean `true` or `false`. A thrown error, a Promise (its late rejection is ignored) or any other value is a plug-in failure, and so are a thrown or rejected `fetch`, an answer that fails the schema and one over `PAGE_BYTES`. Each ends the fetch `unreadable` without trying later plug-ins or the built-in route, so a broken plug-in shows as a failed fetch and not as quietly different content. `unreadable` settles the Item `ready` and keeps earlier content, Highlights and Note.
  - **Deadline.** The plug-in gets the fetch job's 120 s signal (`attemptFetch`, `src/core/fetch-attempt.ts`). `pluginPage` calls no matcher and no `fetch` when the signal has already aborted, so a throwing matcher cannot turn an expired deadline into `unreadable`; otherwise it races the answer against the signal. Only that signal aborting gives `timeout`; an `AbortError` thrown while the signal is open is a plug-in failure. `Promise.race` subscribes to the answer, so a rejection that arrives after the deadline is handled and cannot end the process. This stops the app waiting. It does not stop the plug-in: a synchronous loop, a runaway allocation, a timer or `process.exit()` still reach the whole process. Process isolation (a child process or worker thread) is not built, because the spec gives no isolation promise ("at their own risk"). Neither the signal, the schema nor a read-only mount is a sandbox.
  - **Loading** (`src/targets/node/fetcher-modules.ts`, because `src/core` and `src/http` refuse a computed `import()` and a `node:` import). The loader runs first in `startNode`, before the CLI runners, the job loop and the listener. An entry is an absolute path, or a `file:` URL with an empty or `localhost` host and no query or fragment. Any other entry, a missing file, a directory, an empty entry or two entries with the same real path fails the start. The default export is checked with Zod (`z.function()` is not used, because it wraps the function and checks nothing at start). Any failure throws one error that names the module as written, a fixed stage word (`specifier`, `file`, `import`, `shape`) and the failure's class name, and drops the original error and its message, so the module's own error text is not printed. The import has a deadline of 30 seconds (`IMPORT_DEADLINE_MS`, our choice: half of the 60 seconds the start check waits, `docs/testing.md`), so a module whose top-level `await` does not settle fails the start with the class name `TimeoutError`, instead of keeping the Instance from starting or ending Node with exit code 13 and no module name. The deadline does not stop the module's code, and the failed start ends the process. Supported formats: `.mjs` (recommended) or `.mts`; `.js` and `.ts` follow the nearest `package.json` `type`; `.ts` runs on Node 26's type stripping, so only erasable syntax, explicit import extensions and no `tsconfig.json`. Loading happens at start only: adding or removing a module needs a restart, and removing the variable returns to the built-ins. No screen lists plug-ins; the start-up lines (`fetcher-loaded`) are the record.
  - **Logging.** Each plug-in failure writes one `fetcher-failed` line through `logFailure` with the module as written, a fixed stage word (`matches`, `fetch`, `page`, `size`, `timeout`) and the error's class name. It carries no pasted URL, message, stack, Zod issue or page content. The guarantee covers only what Threadsift writes; plug-in code can call `console` itself.

The container runs up to 4 jobs at once (`LOOP_WIDTH`), so one module serves several calls at once, and a retry or lease takeover may call it again for one link, so exactly-once is not promised. Whoever controls the container's environment and mounted folders can add one; no screen or API does. Its own network calls do not pass `guardedFetch` (see Private addresses).

- **Private addresses.** A pasted link, a one-hop link or a redirect could point a fetcher at the server's own network, and the page would then be stored, served over MCP and mirrored to GitHub. So every request the server sends to a pasted address goes through one function, `guardedFetch` (`src/core/fetch-guard.ts`), with one exception: a fetcher plug-in's own network calls do not pass it, so a plug-in can reach the server's private network (the images in its Markdown are still downloaded through the guard). The guard follows redirects by hand and checks each hop before it connects. The `Network` port makes one request per call without following redirects: the container's adapter is `node:http` and `node:https`, the Worker's is the global `fetch` with `redirect: "manual"`. On Cloudflare, that `fetch` answers a host that does not resolve with Cloudflare's own `530` and the body `error code: 1016`, not an error (measured from a deployed Worker on 2026-11-06), so the Worker's adapter turns that answer into a network failure, which ends a new Item `failed` as on the container.
  - **Address rules.** `src/core/addresses.ts` allows a literal address only when it is global unicast and outside every block of the IANA special-purpose registries whose Globally Reachable value is not True, plus multicast and the reserved IPv4 block. It also refuses `2002::/16` (6to4), where an IPv4 address is embedded, decodes the IPv4 address embedded in `64:ff9b::/96` (RFC 6052), and refuses `64:ff9b:1::/48` whole, because the registry marks it Globally Reachable False and RFC 8215 leaves its prefix length and layout to the operator. Blocks whose registry rows hold a True sub-block (`192.0.0.0/24`, `2001::/23`) are refused whole, so the PCP, TURN and DNS-SD anycast addresses are refused too. The WHATWG URL parser turns `2130706433` and `0x7f.1` into `127.0.0.1` before the check, and `localhost` and every name under `.localhost` are refused by name (RFC 6761).
