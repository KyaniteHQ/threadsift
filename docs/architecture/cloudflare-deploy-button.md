# Cloudflare deploy button

Not built: `.dev.vars.example`, the `cloudflare` key and the `deploy` script in `package.json`, and `.github/workflows/update-from-upstream.yml` do not exist, and the top level of `wrangler.jsonc` sets no `observability` (only `env.live` does), so a deploy from it keeps Workers Logs off and logs no request URL; an owner who turns logs on also sets `redact_query_string: true`, which wrangler 4.156.0 accepts only beside one of the `enabled` flags. `wrangler.jsonc` binds D1, the `threadsift-jobs` Queue, a Cron Trigger and the `FILES` R2 binding for the bucket name `threadsift-files`, and the `AI` binding for Workers AI, which names no resource of its own and so needs no provisioning on the button. The `FILES` binding serves local runs and the file store; the deploy button creating a bucket for the owner's copy is not built; the live demo's bucket `threadsift-live-files` comes from `wrangler deploy` (CI, releases and rollback, Live demo). The text below is the plan.

- The button is `https://deploy.workers.cloudflare.com/?url=https://github.com/KyaniteHQ/threadsift/tree/release`. It points at the `release` branch, which moves only when a release is cut, so a click never deploys work in progress. Cloudflare provisions the resources `wrangler.jsonc` names, which will be the D1 database, R2 bucket, Queue and Workers AI binding (Workers docs, Deploy buttons).
- `.dev.vars.example` lists the secrets the button prompts for: `THREADSIFT_SECRET_KEY` and `SETUP_CODE`. `cloudflare.bindings` in `package.json` explains each binding on that page.
- `THREADSIFT_PUBLIC_ORIGIN` is a Worker variable, not a secret: the deployed `https://` origin. `wrangler.jsonc` does not hold it, because the origin differs for each deployment and an absent value means no public origin is configured; the deployer sets it as a variable of the Worker. The Worker reads it for OpenRouter Connect (see AI tasks and Providers in `ai-tasks-and-providers.md`).
- `package.json` `deploy` runs `wrangler d1 migrations apply DB --remote` and then `wrangler deploy`. `wrangler deploy` makes the R2 bucket a `r2_buckets` entry names when the account has none, and reuses one that exists (Wrangler automatic provisioning, 4.156.0; proved on the earlier pull request copies, not through the button).
- The Workers Paid plan ($5 a month) is needed: extracting one 362 KB article page with Defuddle took 236 ms on local workerd (spike, 2026-11-04), and the free plan allows 10 ms of CPU per request (Workers docs, Limits). This is the one place that states the reason; the README says so beside the button.
- **Updates.** The button copies the repository into the deployer's own GitHub account, "where they can continue development after deploying", and writes the provisioned resource ids into that copy's `wrangler.jsonc` (Workers docs, Deploy buttons); nothing pulls later releases into the copy. The repository therefore ships `.github/workflows/update-from-upstream.yml`, which runs only outside `KyaniteHQ/threadsift`, weekly or on demand:
  1. It fetches `refs/heads/release` from `https://github.com/KyaniteHQ/threadsift` and lays that tree over the copy's tree, so it needs no shared history.
  2. It writes the copy's own resource ids back into the new `wrangler.jsonc` by binding name, and lists any new binding in the pull request, because Cloudflare has not provisioned it yet.
  3. It opens a pull request with a fine-grained token the deployer adds as `UPDATE_TOKEN` (contents, pull requests and workflows on the copy), because Actions' own `GITHUB_TOKEN` may not change files under `.github/workflows/`. The deployer merges it; Workers Builds deploys the merge, and the deploy script runs the new migrations. Local changes the deployer made show in the pull request's diff.
  4. When a step fails, the run fails and opens an issue in the copy, so a stuck update is visible.

  Every other workflow in the repository runs only when `github.repository == 'KyaniteHQ/threadsift'`, so a copy runs none of the project's gate or release jobs.
