## One codebase, two install targets

The app is one core with ports, and each target supplies an adapter per port. Open Managed Agents ships one Hono app on `@hono/node-server` and on Workers this way; EdgeEver ships one Hono app on Workers and on Bun in Docker.

```
             web app (React SPA), Extension, agents, MCP clients, Grok Bot
                                      |
                 Hono app from createApp(ports): API, MCP, login, setup, static files
                                      |
                 core: ingest pipeline, AI tasks, wiki, export, restore
                                      |
   ports:   Database   FileStore   JobQueue   Scheduler   AiExecutor          Fetchers
             |           |           |          |          |                   |
container:  node:sqlite  folder     loop       timer      HTTP, CLI, Grok Bot  + plug-ins, grok CLI
Cloudflare: D1           R2         Queues     Cron       HTTP, Workers AI, Grok Bot
```

- The core imports no runtime module (`node:*`, `cloudflare:*`). Only the two target entry files and their adapters do, so a core change runs on both targets by construction.
- The `Crypto` port has one adapter, `nodeCrypto` in `src/targets/shared/`, and both targets pass it, because the Worker runs `node:crypto` through `nodejs_compat`. This is the accepted exception to the two-adapter rule. The port exists because the lint bans `node:` imports in `src/core` and `src/http`.
- Ports reach routes through `createApp(ports)`, never through `c.env`, because `c.env` holds Worker bindings on Cloudflare and Node's request and response on Node. `waitUntil` lives in the Worker entry for the same reason: Hono's Node adapter passes no execution context.
- Code that only one target has (CLI Providers, the grok X fetcher, fetcher plug-ins, the local vault folder, Workers AI) is an adapter the other target does not register. The settings screens list only registered adapters, as `docs/spec.md` (AI providers) asks.
- Hono, not Next.js: the container target runs plain Node, and Hono runs on Node and Workers with the same app object. Nitro v3 was the runner-up and was rejected for now: it is a release candidate, its database layer has no `batch`, it has no job queue on Node, and the deploy button's handling of its generated Wrangler config is undocumented. Hono 5 is at its first release candidate; the app moves to it once it is stable.

## Database and search

SQLite on both targets, one Drizzle schema, one migration folder.

- **Drivers.** D1 uses `drizzle-orm/d1`. The container uses Node's built-in `node:sqlite` through `drizzle-orm/sqlite-proxy`, an adapter of about 20 lines (`src/targets/node/database.ts`), because `sqlite-proxy` wants rows as arrays and `node:sqlite` returns them that way after `setReturnArrays(true)` (Node 26.12.1, run on 2026-11-04). The adapter supports `run` and `all`; `get` needs a missing-row convention that no query uses yet, so it throws. Drizzle 0.45.4 (the stable release) has no `node:sqlite` driver; 1.0 (release candidate 5) ships `drizzle-orm/node-sqlite`, which replaces the adapter once 1.0 is stable and its `batch` is checked. `node:sqlite` needs no native addon in the image, unlike `better-sqlite3`.
- **Async and batch only.** Both drivers are async and support `db.batch()`. D1 has no interactive transactions, so every multi-statement write is one `batch`, which commits or rolls back as a unit on both targets. The container's batch is to run its statements between `BEGIN` and `COMMIT` on the one connection through the `batchCallback` that `drizzle-orm/sqlite-proxy` accepts; `src/targets/node/database.ts` passes that callback, which rolls the batch back when a statement fails.
- **Guarded batches.** A batch that may only commit while a condition holds (a lease is still held at its generation, the catalog is still at the version a job read) starts with an insert into `guards`, a table whose `CHECK (ok = 1)` fails when the condition's `SELECT` returns 0. The failed check aborts the whole batch, on D1 and in the container alike, so a guarded write is all or nothing. A job that gets the check error has lost its lease or read a stale catalog, so it reads again instead of writing. The job runner (`writeWhileHolding` in `src/core/jobs.ts`) guards every result on the row still being `running` at the attempt count its runner claimed. The guard insert is written with Drizzle's `insert(guards).select(...)`, because a raw `db.run(sql)` inside a D1 batch fails in drizzle-orm 0.45.4 (`Cannot read properties of undefined (reading 'bind')`). Both behaviours were run on node:sqlite and on local D1 under `wrangler dev` 4.156.0 on 2026-11-04: the batch with the held generation committed, the one with a stale generation failed with `CHECK constraint failed: ok = 1` and left no row.
- **Migrations.** `drizzle-kit generate` writes SQL files into `migrations/`; hand-written files hold what Drizzle cannot express (FTS5 tables, triggers). The deploy script applies them with `wrangler d1 migrations apply`; the container applies the same files at start and records them in a `d1_migrations` table of the same shape (`wrangler d1 migrations apply DB --local` creates that table with the columns that `src/targets/node/database.ts` creates, checked on 2026-11-04 with wrangler 4.156.0). Local runs use `--local --persist-to <dir>`, which needs no Cloudflare login or `database_id`. A migration only adds; a removal waits for a later release, so the previous release still runs on the new schema (see CI, releases and rollback).
- **Search.** FTS5 external-content tables kept in step by triggers; D1 supports FTS5 (D1 docs, SQL statements). Searchable text lives in `search_parts`, one row per part of an Item: the title, each post-text chunk, each Kept comment, the Summary, the Tags, each Highlight and the Note. A part longer than 500,000 bytes is split into chunks, so no search row nears D1's 2 MB row limit. A query matches parts and groups them by Item; the Highlights page queries only Highlight and Note parts. Related Items candidates come from the same index, ordered by `bm25()` ascending, because a lower `bm25` score is a better match (SQLite FTS5 docs). The app rewrites an Item's parts in the same batch as the change to that part.
- **Large text.** A post text, comment body or AI task input over 1,000,000 bytes is stored as an object in the file store, and its row holds the key; the same rule runs on both targets, so no single value nears the 2 MB limit. Until the file store exists, an Article whose Markdown is over 1,000,000 bytes (UTF-8) keeps its title, author and posted date and has no post text (see Open items). `GET /api/items` selects the list's columns and leaves out the post text, because about 50 rows of long text would pass the 50 MB query-result limit; `GET /api/items/:id` returns it.
- **D1 limits that shape queries:** 100 bound parameters per statement, 1,000 queries per invocation on the paid plan, 2 MB per row, 50 MB per query result (D1 docs, Limits). A list whose length the data decides is bound as one JSON parameter and expanded with `json_each`; large reads page by key.
- **Numbers.** D1 returns numbers as JavaScript numbers, so an integer above 2^53 loses precision (D1 docs, Import and export data). X post ids are above that, so every id that comes from a Source is `text`.

Evidence, a spike on 2026-11-04 (scratch folder, not in the repo): one schema and one query module ran unchanged on `node:sqlite` (Node 26.11.1, SQLite 3.53.3), on Bun 1.4.3 (SQLite 3.53.4) and on local D1 under `wrangler dev` (wrangler 4.156.0). All gave the same results for an upsert by URL, FTS5 with porter stemming and prefix queries, triggers that follow an update and a delete, a cascade delete, and a `batch` whose second insert broke a unique index and left no row behind. D1 refuses `sqlite_version()`.

## Data model outline

Names follow `CONTEXT.md`. Columns are settled during the build.

| Table | Holds |
|---|---|
| `items` | Source, Source id (text), normalized URL (unique), original URL, author, community (the subreddit), posted and saved dates, the date the content was last fetched, title, post text as Markdown (`post_text`, up to 1,000,000 bytes in the row until the file store exists), status (`processing`, `ready`, `failed`), the failure reason (`timeout`, `network`, `gave-up`), the last fetch result (`fetch_result`, null until a first fetch ends), Read state |
| `comments` | per Item: Source id (text), parent id, author, date, body as Markdown, Kept flag; dropped parents of Kept comments and Reddit `more` stubs whose replies could not be fetched render as Context stubs |
| `media` | per Item: file key or video URL, kind, size |
| `digests` | per Item: the Digest JSON, Provider and model, created date |
| `topics`, `tags`, `item_tags` | the agent's lists and the links; `catalog_version` counts changes to the Topic and Tag lists |
| `topic_pages` | overview text, its revision, and the ids of the Items it was built from |
| `related_items` | Item pair and one-line reason |
| `log_entries` | every agent action |
| `proposals`, `pins` | weekly Proposals with their state; accepted corrections |
| `highlights`, `notes` | owner text; a Highlight stores its target (post text or a comment id) and a text-quote anchor: the exact text plus a short prefix and suffix, as in the W3C Web Annotation `TextQuoteSelector` |
| `search_parts` | FTS5 source rows and their FTS table |
| `owner`, `sessions`, `agent_tokens` | login and access |
| `settings` | server-side settings; secrets in it are encrypted |
| `jobs`, `leases`, `scheduled_runs`, `guards` | the job runner (a job's kind, Item, `address` (the link a fetch reads, which can differ from the Item's normalized URL), state, attempts, next attempt time and claim expiry; a unique index allows one open job per Item and kind), the leases with their generation, the schedule claims, the guard table of guarded batches |
| `ai_tasks` | one row per AI task: kind, inputs, input revision, executor, attempts, deadline, state, result |
| `imports`, `exports`, `restores` | cursors and checkpoints of long runs |
| `mirror_paths` | vault paths waiting to be written, each with a sequence number |

- Post text and comments are stored as Markdown, which Defuddle can return directly. The Reader renders Markdown without raw HTML, so other people's posts never reach the page as HTML, and the export and the Vault mirror reuse the stored text.
- A refresh re-anchors each Highlight by its quote, prefix and suffix; a Highlight whose quote is gone keeps its text and is marked as no longer found (`docs/spec.md`, Highlights and Notes).

## Files

One `FileStore` port: `put` from a stream of known length, `get` as a stream with an optional byte range, `delete`, `list` by prefix with a cursor, and a multipart upload for a file whose length is not known up front (R2 needs a known length for a streamed `put`, and every multipart part but the last must be at least 5 MiB; R2 docs, Workers API and multipart uploads). The container writes under `/data/files`; Cloudflare writes to an R2 bucket. Keys are `items/<item id>/<file>`, so deleting an Item deletes one prefix. Images are stored as fetched. No resizing: it would need two image paths (an Images binding on Cloudflare, a native library in the container) for a feature the spec does not ask for.

## Jobs, leases and the schedule

- **Jobs.** Each step that waits on the network (fetch, an AI task, a wiki step, a Vault mirror write, a Grok Bot webhook, a slice of an export or restore) is a row in `jobs` with its state, attempts and next attempt time. The same `runJob` code runs on both targets. On Cloudflare a Queues message carries the job id, with `max_batch_size: 1`, so one invocation runs one job; in the container an in-process loop picks due rows. The row, not the message, is the source of truth: a lost message, a discarded retry or a restart loses no work, because the sweep re-queues due rows.
- **One run per job.** A runner starts a job only by claiming its row (`claim` in `src/core/jobs.ts`): `UPDATE jobs SET state = 'running', claim_expires = now + deadline + 2 minutes, attempts = attempts + (state = 'running') WHERE id = ? AND ((state = 'queued' AND next_attempt_at <= now) OR (state = 'running' AND claim_expires < now)) RETURNING *`. A `done` row matches neither branch, so a second message for a finished job, or a sweep that finds it, claims nothing. An attempt whose runner died counts when the next runner takes over its expired claim, so a job that always kills its runner still reaches `gave-up`. The sweep enqueues every due row. A runner writes its result in one guarded batch (see Database and search) that checks the row is still `running` at the attempt count it claimed, so a runner whose claim was taken over writes nothing. The fetch result, the Item's status and the job's `done` state commit in that one batch, so a crash never leaves a `done` job with a `processing` Item.
- **Deadlines.** Each job runs under a deadline below the 15 minutes of wall time a Queues consumer gets (Workers docs, Limits): an AI call gets 10 minutes, a fetch 2 minutes, an export or restore slice 10 minutes. `fetchLink` builds a fetch job's deadline signal (`AbortSignal.timeout`) and passes it to `guardedFetch`, which combines it with each hop's 8 s signal through `AbortSignal.any` and turns an aborted job signal into the `timeout` result, so a fetch past its deadline ends the Item `failed` with `timeout` and is not retried. Every other job kind fails its attempt at the deadline and its row retries it. The consumer sets `limits.cpu_ms` to 300,000, the Workers Paid maximum, because a Queues consumer gets 30 seconds of CPU by default (Workers docs, Limits).
- **Values chosen for fetch jobs** (`src/core/jobs.ts` and `src/targets/node/job-loop.ts`). The deadline is 2 minutes (`FETCH_DEADLINE_MS` in `src/core/fetch-link.ts`) and a claim lasts the claimed kind's deadline plus 2 minutes (`CLAIM_MARGIN_MS`). The runner keeps one record per job kind (`HANDLERS` in `src/core/jobs.ts`: its deadline, how an attempt runs, and what giving up writes), so a new kind adds an entry and no branch. A job gets 3 attempts (`MAX_ATTEMPTS`); a failed attempt is retried after 30 seconds, and a second one after 2 minutes (`RETRY_DELAYS_MS`); after the third the Item is `failed` with `gave-up`. On Cloudflare the retry is a Queues message with `delaySeconds`. The tick sweeps at most once per 30 seconds (`TICK_SPACING_MS`), claimed in `scheduled_runs` so two ticks do not both sweep, and enqueues at most 100 due rows (`SWEEP_LIMIT`) in one `sendBatch` call, which takes up to 100 messages and one `delaySeconds` for the batch (Queues docs, JavaScript APIs: https://developers.cloudflare.com/queues/configuration/javascript-apis/); the container wakes its loop once. The container loop runs 4 jobs at once (`LOOP_WIDTH`), looks for due rows every 5 seconds (`LOOP_POLL_MS`) and calls the tick every 60 seconds (`TICK_MS`).
- **Container restart.** When the container loop starts it marks the claim of every `running` row as expired (`abandonRunning`), because the process that held those claims is gone. The loop then claims the rows again, counts the lost attempt and runs them, so an Item that was `processing` at the restart leaves `processing` without a new Paste.
- **Leases with a generation.** A lease is a row with a holder, an expiry and a generation number that grows on every claim. Its expiry is the job's deadline plus 2 minutes, so a job that runs to its deadline still holds it. A job that writes under a lease commits in a guarded batch (see Database and search) whose guard checks that its generation still holds the lease and that the record it read is still at the revision it read; otherwise nothing is written and the job retries on fresh inputs. Jobs that need two leases, such as merging two Topics, claim them in Topic id order.
- **One update at a time per Topic.** Each wiki step for a Topic holds that Topic's lease while it reads, calls the executor and writes. This is the spec's rule against near-duplicate pages from parallel updates (`docs/spec.md`, The library wiki). With Grok Bot, the call returns later through a callback, so the step releases the lease after sending; applying the result is its own step that takes the lease again (see AI tasks and Providers).
- **New Topics and Tags.** A Digest job reads `catalog_version` with the Topic and Tag lists it gives the model. When its Digest reuses only existing names, it publishes at once, so an Import is not serialized. When it creates a Topic or a Tag, its publishing batch is guarded on `catalog_version` still being the version it read; when the guard fails, the job asks the model again with the new lists. A unique-index conflict on a new name means another job created the same name first, and the job reuses that name. After two retries the job waits with backoff instead of publishing against an old list, because the spec allows no near-duplicates (`docs/spec.md`, Decisions, Tags).
- **Schedule.** One tick, every minute, claims each due task in `scheduled_runs` and enqueues jobs: one per Topic the weekly checks touched, one per import and Grok Bot cursor, and the sweep. The tick calls no model, because a Cron Trigger under an hourly interval gets 30 seconds of CPU (Workers docs, Limits). Cloudflare calls the tick from a Cron Trigger; the container calls it from a timer.

## Fetchers

Each Source has one fetcher behind a `Fetcher` port: `matches(url)` and `fetch(url, ctx)` returning Item content, comments and media.

- **Article:** a plain `fetch` through `guardedFetch`, then Defuddle 0.19.6 on the linkedom document that also gives the title, with Markdown output (`readArticle` in `src/core/article.ts`). Its CPU cost is why the Cloudflare target needs Workers Paid (see Cloudflare deploy button). No Browser Rendering: pages that need JavaScript or a login come in through the Extension.
  - **Article or Other.** The page is an Article when it is HTML (`text/html` or `application/xhtml+xml`, compared without case and without parameters), the body was not cut at the cap, the final URL is not a video host (`VIDEO_HOSTS` in `src/core/links.ts`) or a Reddit, X or GitHub link, and Defuddle counts 100 words or more. Any other page is Other with no post text. A page with no `<title>` and no title from Defuddle leaves the Item as it was, with the fetch result `no-title`. The 100 words are our choice, from a probe with Defuddle 0.19.6 and linkedom 0.18.15 on 2026-11-06: `https://example.com/` gave 25 words, `https://stephango.com/saw` 143 and `https://en.wikipedia.org/wiki/Bread` 6642. With `useAsync: false` a YouTube watch page gives 0 words (probe, 2026-11-06), so no YouTube entry of `VIDEO_HOSTS` has a page that can fail on its own; `https://vimeo.com/terms` (8,211 words) is the page that needs the list, and `e2e/article.spec.ts` pastes it directly and through a redirect, so matching the pasted URL instead of the final one fails. Reddit, X and GitHub links never reach Defuddle.
  - **Defuddle makes no request of its own.** It runs with `useAsync: false`, because 0.19.6 extractors such as `c2-wiki` fetch extra pages with the global `fetch`, outside the guard (`src/extractors/c2-wiki.ts` at tag 0.19.6). `https://wiki.c2.com/?WelcomeVisitors` is the page that shows it: with the option Defuddle reads 9 words from the page and sends nothing, and without it the extractor requests `https://c2.com/wiki/remodel/pages/WelcomeVisitors` and returns 376 words (probe on Node 26.12.1, 2026-11-06). `e2e/article.spec.ts` pastes that page and expects Other, so removing the option fails it. Defuddle also takes a `fetch` option (`node_modules/defuddle/dist/types.d.ts`, `Options.fetch`), and `readArticle` passes one that refuses every request, so an extractor that ran despite `useAsync: false` would fail the job instead of using the global `fetch`. The guarded fetch cannot be passed instead, because the reader runs where no `Network` port exists (a worker thread on the container).
  - **Markdown only.** Defuddle keeps `video`, `audio` and `iframe` elements as raw HTML in its Markdown, and the Reader renders Markdown without raw HTML, so `readArticle` removes those elements from the document before Defuddle runs; a code sample that mentions the tags is text and stays. Slice 7c turns them into links.
  - **A failed refresh keeps the Article.** `settle` (`src/core/settle.ts`) writes no content field for a fetch that failed. `e2e/article-pages.spec.ts` seeds a full Article at a `.invalid` host with `storeItem`, pastes it, and expects the Source, kind, title, author, post text, posted date and fetch time unchanged and the fetch result `network` (2026-11-06, both targets).
  - **Where it runs.** Parsing, the title read and Defuddle sit behind the `PageReader` port (`src/core/ports.ts`), and the job calls it through `ports.pages`. The container adapter (`src/targets/node/page-reader.ts`) sends each page to one `node:worker_threads` worker (`page-reader-worker.ts`), because Defuddle runs on the thread that calls it: a 4 MB Gutenberg page blocked the container's event loop for about 8 s, and the API answered nothing in that time. Each read takes the fetch job's 120 s deadline signal. When it aborts with a read in flight, the container adapter terminates the worker, fails every pending read with `PageReadTimeout`, and starts a new worker on the next read; `fetchLink` turns that error into the fetch result `timeout`, which the job treats like a network timeout. The Worker adapter (`src/targets/worker/page-reader.ts`) calls the same functions inline and relies on the Worker's CPU limit. Each adapter also gives `maxHtmlBytes`, the largest HTML page it reads: 5 MiB on the container and 900 KiB on the Worker. The 4,039,247 byte War and Peace page is therefore an Article with no text on the container and an Other Item, cut at the cap, on the Worker. `e2e/article.spec.ts` reads another Item while the container converts the book and expects an answer within 1 s (measured 6.6 ms slowest over 162 reads on the container, 2026-11-06).
  - **Worker memory.** A Worker isolate has 128 MB (Workers docs, Limits). Local `wrangler dev` does not enforce that limit, so the memory is estimated from the peak resident memory of the `workerd` processes (`VmHWM` in `/proc/<pid>/status`, sampled every 25 ms during one Paste in a fresh `wrangler dev` 4.156.0, 2026-11-06) minus the same measure for a Paste of `https://example.com/` (214.9 MiB). That is the whole process, so it overstates the isolate. The inspector (`--inspector-port`) returned no heap numbers.

    | Page | HTML bytes | Peak above idle |
    |---|---|---|
    | Bread | 619,662 | 39 MiB |
    | Bird vocalization (revision 1380253618) | 866,784 | 58 MiB |
    | Tale of Two Cities (Gutenberg 98) | 944,391 | 194 MiB |
    | Great Expectations (Gutenberg 1400) | 1,098,188 | 249 MiB |
    | Moby Dick (Gutenberg 2701) | 1,450,985 | 287 MiB |
    | Anna Karenina (Gutenberg 1399) | 2,222,084 | 1,012 MiB |
    | War and Peace (Gutenberg 2600) | 4,039,247 | 1,490 MiB |

    The cap of 900 KiB (921,600 bytes) lies between the largest page under 128 MB (Bird vocalization) and the smallest one over it (Tale of Two Cities). A text-heavy page just under the cap may still pass 128 MB, so memory stays under Not verified. The cap changes one acceptance page: War and Peace on the Worker (above). It also makes `https://www.rfc-editor.org/rfc/rfc9110` (4,899,392 bytes) an Other Item on the Worker, and `e2e/library.spec.ts` therefore does not assert its Source.
  - **On the Worker.** `defuddle/node` bundles with `nodejs_compat`, but wrangler's bundler follows turndown's `browser` field to a build that needs a global `document`, which workerd lacks: every conversion then fell back to Defuddle's "Partial conversion completed with errors" text, which holds the raw HTML (`ReferenceError: document is not defined`, `wrangler dev` 4.156.0, 2026-11-06). `wrangler.jsonc` `alias` points `turndown` and `@mixmark-io/domino` at their Node builds (Workers docs, Wrangler configuration, Module aliasing: https://developers.cloudflare.com/workers/wrangler/configuration/#module-aliasing). Wrangler resolves an alias value from the project root, so both packages are direct dependencies at the versions `defuddle` resolves (`turndown` 7.2.4, MIT; `@mixmark-io/domino` 2.2.0, BSD-2-Clause, last release 2024-04-08), and a `defuddle` update moves the two pins with it. `e2e/article.spec.ts` fails when the aliases are removed, because the stored text then holds the fallback HTML (`expectMarkdown` in `e2e/articles.ts`).
- **GitHub:** the GitHub REST API, with an optional token in settings for the higher rate limit.
- **Reddit:** oEmbed for the title, author and subreddit, and one `.json` parser for the `.json` paste, the JSON the Extension sends and the account fetch; the Extension's Defuddle content when its `.json` request failed. A `more` stub whose replies could not be fetched becomes a Context stub. In the self-hosted builds, a link without Extension content goes first to the connected account, when there is one, and then to the archive fill: Arctic Shift's comment tree passes through a thin adapter (Arctic's top level is `{"data":[t1 nodes]}`, not Reddit's two Listings, while nested `replies` are Listings) into the same parser, so no second parser exists. Arctic's rate limit is respected and a 429 is retried once after `X-RateLimit-Reset`, at most 10 s; the Item stays Link-only otherwise. A connected account fetches `<thread>/.json?limit=500&raw_json=1` with the `reddit_session` cookie, then the replies behind each `more` stub by permalink (`docs/spec.md`, Fetchers), spaced and capped per thread, and follows `/s/` redirects. The container sends these requests with the platform `fetch`; no browser-impersonating client, because plain `fetch` got HTTP 200. The Worker sends them over `connect()` from `cloudflare:sockets` with HTTP/1.1, because Reddit answers the Workers `fetch` client with 403 even with the cookie, while a raw socket from the same Worker got 200 (3 of 3 runs, 2026-11-05). Before writing the chunked-body reader for that socket, search for a maintained HTTP client over `connect()`. The hidden-reply fill over the socket is not measured yet (see Open items).
- **X:** the Grok Bot intake webhook on both targets; the grok CLI in the container. `grok --json-schema` returns the parsed result in a `structuredOutput` field (grok 1.0.70, run on 2026-11-04). On Cloudflare without a Grok Bot webhook, an X link becomes a Link-only Item.
- **Other:** a Link-only Item with the page's `<title>` or its oEmbed title (Defuddle's title when the page has none), and no AI task, because there is no text to digest.
- **One hop:** only when the linked URL is an article or a GitHub repository.
- **Plug-ins (container only):** a self-hoster's fetcher is an ES module that exports the same `Fetcher` shape. The container loads every module listed in `THREADSIFT_FETCHERS` at start. The Cloudflare bundle is built from the repository, so a plug-in there means a fork.
- **URLs:** one normalizer (lower-case host, no `www.`, tracking parameters dropped, short links followed) gives each Item its identity.
- **Private addresses.** A pasted link, a one-hop link or a redirect could point a fetcher at the server's own network, and the page would then be stored, served over MCP and mirrored to GitHub. So every request the server sends to a pasted address goes through one function, `guardedFetch` (`src/core/fetch-guard.ts`), which follows redirects by hand and checks each hop before it connects. The `Network` port makes one request per call without following redirects: the container's adapter is `node:http` and `node:https`, the Worker's is the global `fetch` with `redirect: "manual"`. On Cloudflare, that `fetch` answers a host that does not resolve with Cloudflare's own `530` and the body `error code: 1016`, not an error (measured from a deployed Worker on 2026-11-06), so the Worker's adapter turns that answer into a network failure, which ends a new Item `failed` with "Couldn’t reach the website" as on the container.
  - **Address rules.** `src/core/addresses.ts` allows a literal address only when it is global unicast and outside every block of the IANA special-purpose registries whose Globally Reachable value is not True, plus multicast and the reserved IPv4 block. It also refuses `2002::/16` (6to4), where an IPv4 address is embedded, decodes the IPv4 address embedded in `64:ff9b::/96` (RFC 6052), and refuses `64:ff9b:1::/48` whole, because the registry marks it Globally Reachable False and RFC 8215 leaves its prefix length and layout to the operator. Blocks whose registry rows hold a True sub-block (`192.0.0.0/24`, `2001::/23`) are refused whole, so the PCP, TURN and DNS-SD anycast addresses are refused too. The WHATWG URL parser turns `2130706433` and `0x7f.1` into `127.0.0.1` before the check, and `localhost` and every name under `.localhost` are refused by name (RFC 6761).
  - **Container.** The adapter passes a `lookup` function to `http.request`, so the check runs on the addresses the connection will use and the name is never resolved a second time. A name such as `localtest.me`, which resolves to `127.0.0.1` in public DNS, is refused after it resolves, so the link is saved without a title. A Worker deployed on Cloudflare's network cannot reach the owner's network, so there the check covers literal addresses and `localhost` only. The local Worker under `wrangler dev` runs on the owner's machine and has the same check, so the name check is missing there (see Open items).
  - **Limits.** Every hop has an 8 s deadline from the lookup to the last body byte, 20 redirects are followed (the Fetch standard's own limit) and the body is cut at a cap, after content decoding: the page reader's `maxHtmlBytes` (5 MiB or 900 KiB, see Article) for an HTML page fetched for a pasted link, and `SMALL_BODY_BYTES` (512 KiB, defined once in `src/core/fetch-guard.ts`) for a page of any other media type, for the Reddit oEmbed call and for the HTML of a short link host; the deadline and the caps are our choices, not a source's. The guard returns the final page with its media type and a flag that says the body was cut, and a cut body is never read as an Article. `https://en.wikipedia.org/wiki/Bread` is 619,662 bytes and `https://www.gutenberg.org/files/2600/2600-h/2600-h.htm` 4,039,247 bytes after decoding (measured 2026-11-06), so the old 512 KiB cap cut both; the Gutenberg page downloaded in 2.7 s from the owner's machine, inside the 8 s deadline, and `https://www.gutenberg.org/files/100/100-h/100-h.htm` (7,018,827 bytes) is the page over the cap. The adapter passes `autoSelectFamilyAttemptTimeout: HOP_DEADLINE_MS` to `http.request`, so no connection attempt ends the hop before the deadline (Node 26 docs, `socket.connect(options)`: an attempt gets that time before Node tries the next address, 250 ms by default). Node also cuts the last attempt at that time, so a smaller value ends a host whose addresses all hang early: with 2 s per attempt, `http://example.com:81/` answered `timeout` after 4014 ms on a host without an IPv6 route (2026-11-05). The trade-off is a host whose first address drops packets while a later one works: it uses up the hop and answers `timeout` on the container. A connection that never answers and a body that stalls after the connection is open both run to the 8 s deadline on both targets. `guardedFetch` through `nodeNetwork` to `http://example.com:81/` (4 addresses, Node 26.12.1) answered `timeout` after 1003 ms without the option and after 8041 ms with it.
  - **What a hop may reach.** A redirect to a Reddit or X link stops without a request, so the oEmbed-only and X no-request rules (`docs/spec.md`, Decisions, Reddit) hold for a short link or a redirect. A short link (`SHORT_LINK_HOSTS` in `src/core/links.ts`) is the only kind of redirect that changes an Item's identity: its final or stopping URL becomes the Item's URL, and a short link that fails, or ends on a status outside 2xx, stays the Item's URL. The request resolves the short link only to find that URL (`resolveShortLink` in `src/core/fetch-link.ts`), and reads no body on a hop that is not a short link host (the policy's `readsBody`; `requestHop` then returns the page without touching `response.body` and the abort closes the connection), because the fetch job reads the page, so a page that stalls after its headers still resolves (`e2e/article-pages.spec.ts` uses `https://is.gd/3a9eIm`, made once through is.gd's API, to `https://httpbin.org/drip?duration=10&numbytes=5&code=200`); the Item is then stored and queued like any other Paste with the final URL as the job's address, so its content comes from the same fetch job and a short link to an article gets the article's text. A short link that fails to resolve is saved under the short URL with that failure and no job. Any other redirect only decides where the title comes from, so a redirect to a Reddit or X link leaves the pasted URL as the identity and the answer is `redirect-stopped`. A hop that is not an `http` or `https` URL answers `unsupported`, and a hop to an address that is not globally reachable answers `refused`. The 21st redirect answers `redirect-limit` even when it points to Reddit or X. A link whose Source allows no request (an X post, a Reddit link that is not a post or a comment) answers `not-requested`. A final dot on a host (`x.com.`) is dropped before any of these rules and before the Item's identity is built.
  - **Meta refresh.** A page from a short link host that ends the chain as HTML and holds a `<meta http-equiv="refresh">` with a delay of 0 counts as one more redirect (`src/core/meta-refresh.ts`, the HTML standard's [shared declarative refresh steps](https://html.spec.whatwg.org/multipage/document-lifecycle.html#shared-declarative-refresh-steps), read 2026-11-05): the URL resolves against the page's URL, goes through the same address, Reddit and X, `http(s)` and 20-redirect checks, and a page on any other host is never followed this way. tinyurl.com needs it: on 2026-11-04 and 2026-11-05 it answered an old link sometimes with a 301 to the target and sometimes with a 302 to `/preview/deprecated/<id>`, a 200 HTML page whose head holds the refresh (`curl` and a probe through `nodeNetwork.get`).

## AI tasks and Providers

Every model call is an AI task with a kind, inputs, an input revision and a Zod result schema. The kinds are `digest`, `topic_overview`, `related_pick` and `proposals`. The core creates the task row, an executor runs it, and the core checks the result against the schema and the rules before it applies it. A result whose input revision is no longer current is not applied; instead the core queues the same step again over the current inputs, so no Item's Digest is left out of a Topic overview.

| Executor | Provider rows it serves | Targets | How it runs a task |
|---|---|---|---|
| HTTP | OpenRouter (key or Connect), Anthropic, OpenAI and xAI keys, an OpenAI-compatible URL | both | AI SDK `generateText` with `output: Output.object({ schema })`; the AI SDK maps the schema to each vendor's structured-output dialect |
| Workers AI | Workers AI | Cloudflare | `env.AI.run(model, { messages, response_format: { type: "json_schema", json_schema } })`; the model list is the JSON-mode list on Cloudflare's Workers AI docs |
| CLI | Claude Code, Codex, Grok on the server | container | `claude -p --output-format json --json-schema`, `codex exec --output-schema`, `grok --json-schema --output-format json`, in an empty folder with tools off; reads `structured_output`, the last message or `structuredOutput` |
| Grok Bot | Grok Bot | both | asynchronous, below |

- **Grok Bot runs every AI task when it is the Provider** (owner's decision, 2026-11-04). Threadsift posts `{task id, kind, inputs, input revision, result schema}` to the bot's webhook with the stored key; the bot wakes, writes the result and posts it to `POST /api/ai-tasks/:id/result`. The bot's skill files in `bot/` hold the same contract. Whether the bot writes good wiki results is unverified until a live run.
  - **Who may answer.** Only the agent token the owner connected as Grok Bot may post a result; any other token gets 403.
  - **X links.** A `digest` task for an X link closes through `POST /api/items`, which carries the content the bot fetched, its Digest and the task id, as `docs/spec.md` (Grok Bot, flow C) describes. Either route closes the task by its id.
  - **Duplicates and late answers.** A result for a task that is already closed gets 409 and changes nothing. A result for an open task whose input revision has moved is handled like any stale result: the step is queued again.
  - **Deadline.** A Grok Bot task gets one hour (a chosen value, because the bot wakes in seconds to tens of seconds by its own estimate). At the deadline the task is sent again, up to 3 attempts; after that it fails, the Item or Topic shows the failure with Try again, and the Log records it. There is no silent fallback to another Provider, because the owner picks one.
- **Without Grok Bot,** every task runs on the Provider the owner picked, on that target's executor. Nothing in the core knows which executor ran a task.
- **OpenAI-compatible URL on Cloudflare** must be a public HTTPS address, because the Worker runs on Cloudflare's network, not in the owner's home. Ollama on the owner's machine works from the container.
- **Workers AI is called through the binding, not through a package.** Cloudflare deprecated `workers-ai-provider` for `createAI` from its `agents` package (npm deprecation notice), and `agents` 0.33.0 is 10.8 MB unpacked with 11 dependencies, Babel and Rolldown plugins among them. The trade-off is one structured-output dialect we write and test ourselves.
- **OpenRouter Connect** is OpenRouter's PKCE flow; the returned key is stored like any other key.
- **"Verify"** in settings runs one real `digest` task through the same path.

## Access: owner login, agent tokens, MCP

- **Setup.** A new Instance shows a setup page that asks for the one-time `SETUP_CODE` first (unless the Instance has none usable, below), then for a new password and, optionally, an export zip to restore (see Export, backup and restore). On Cloudflare the deploy button prompts for `SETUP_CODE` and `THREADSIFT_SECRET_KEY` as secrets; in the container both are environment variables, and a missing `SETUP_CODE` makes the container print a generated one as one `Setup code:` log line at each start while no owner exists. Without the code, anyone who finds a fresh public Instance could claim it. A code shorter than 16 characters is refused with 503 on both setup calls, and so is a Worker with no code. Every refusal of the setup and login calls carries one `code` in the error body (the closed list `REFUSAL_CODES` in `src/http/schemas.ts`: `wrong`, `owner-exists`, `locked`, `setup-missing`, `setup-short`, `password-short`, `password-long`), and the web client reads that field instead of guessing from the status. While no owner exists, `GET /api/session` also answers `code` (`set`, `missing` or `short`, from `checkConfiguredCode` in `src/core/setup-code.ts`), so the setup page opens on the block that names the fix instead of asking for a code first. The field reveals only what the 503 already reveals, and it is absent once an owner exists. The single `owner` row (a `CHECK` on `id = 1`, inserted with `ON CONFLICT DO NOTHING`) makes a second setup a 409.
- **The guard.** One middleware on `/api/*` runs before every handler and answers closed by default. The only routes it lets through unauthenticated are `GET /api/session`, `POST /api/setup/code`, `POST /api/setup` and `POST /api/login`, matched by exact method and path in `src/http/access-rules.ts`. It checks, in order: an owner session cookie or an agent token (`bearer-auth`: 400 for a malformed header, an empty one included, 401 for an unknown or revoked token), then that `/api/tokens` and `/api/logout` are not reached with a token (403), then Hono's `csrf` (403) for requests without an `Authorization` header only, because a bearer token is no ambient credential a foreign page could make the browser send, then `body-limit` (413). A route added later is therefore closed until someone lists it.
- **Owner login.** The password is counted in code points after NFKC normalization, must be 15 to 1,024 long (NIST SP 800-63B-4 sets 15 as the minimum for a password alone), and is hashed with scrypt from `node:crypto`, which both targets have, at N=2^15, r=8, p=3, one of OWASP's Password Storage settings, with `maxmem: 64 MiB`. Node's default `maxmem` of 32 MiB rejects those settings (`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`, Node 26.11.1, run on 2026-11-04). The OWASP default N=2^17 needs 128 MiB, the whole memory of one Worker. The stored string is `scrypt$N=…$r=…$p=…$salt$key`, so a later cost change still verifies old hashes. A session is a 32-byte random id in the `__Host-threadsift_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, Max-Age 30 days), stored in `sessions` as a SHA-256 digest with its expiry. A use renews the session once less than 29 days remain, so a session lives 30 days from its last use, and an expired one is deleted and refused. Chromium keeps the `Secure` `__Host-` cookie over `http://127.0.0.1`, so the local suite runs the real cookie.
- **Throttle.** The `throttles` table holds one row for `setup` and one for `login`. One atomic upsert counts each attempt before its code or password is checked, so parallel guesses each count and only ten of them are checked; the tenth counted attempt locks the kind for 60 seconds. A locked kind answers 429 with `Retry-After` without checking anything, even for the right code or password, so an attempt during a lock is not counted and does not extend it. Each attempt counted after a lock ends, before a success, doubles the next lock, up to 1 hour. A success deletes the row only when it is the latest counted attempt, so a success that finishes late cannot clear a lock that newer attempts set. The lock is in the database, so a restart keeps it. It is global, not per address, because behind a proxy the app has no address it can trust; the cost is that anyone who can reach the login can lock the owner out of signing in for up to an hour, while sessions already open and agent tokens keep working.
- **Agent tokens.** One random token per connected agent, `tsa_` and 32 random bytes in base64url, shown once, stored as a SHA-256 hash (the token is high-entropy, so a fast hash is enough), revocable in settings. `last_used_at` updates at most once an hour through a conditional `UPDATE`, so a busy agent does not write on every request. The Extension, Grok Bot and MCP clients use them as bearer tokens. The token the owner connects in the Grok Bot settings is marked as Grok Bot's, and only it may post AI task results.
- **Secrets at rest.** Provider keys, the Grok Bot webhook key, the vault token and the owner's Reddit session cookie are sealed with AES-GCM (WebCrypto, on both targets) under `THREADSIFT_SECRET_KEY`, which the app reads from its environment and never shows.
- **Request limits.** Hono's `body-limit` middleware caps request bodies on both targets, because Node has no cap of its own and Cloudflare's cap depends on the zone's plan (100 MB on Free and Pro, Workers docs, Limits).
- **MCP.** `createMcpHandler` from `@modelcontextprotocol/server` serves Streamable HTTP at `/mcp` on both targets; its SDK documents that web-standard handler for Workers. The handler checks no token itself (MCP SDK reference, `createMcpHandler`), so a Hono middleware hashes the bearer token, rejects a miss, checks Host and Origin, and passes the caller as `authInfo` to `handler.fetch`. Each tool calls the same core function as the matching HTTP route. OAuth for Grok Bot's catalog comes later (`docs/spec.md`, Grok Bot).

## Web app

- A React 19 single-page app built by Vite (owner's decision, 2026-11-04). One static build serves Workers static assets and Hono's `serveStatic` on Node, and it is the shape Tauri and Capacitor take for a later desktop or mobile app. No server rendering: one owner behind a login gains nothing from it.
- React-specific libraries stay few, so the app can try Preact 11 through `preact/compat` after the first release if page weight matters: in a small comparable build, React's framework JavaScript was 68.0 KB gzip and Preact's 7.7 KB (measured 2026-11-04 in a scratch build, not on this app).
- The prototype is Claude Design's own template format on React 18 classes, so the app rewrites it. Its behaviour (reader bar fitting, folding by measured height, reading-place restore, the keys) is plain DOM code and becomes plain TypeScript modules that take an element. Highlights are drawn with the CSS Custom Highlight API.
- `design/system/tokens.css`, `components.css` and `settings.ts` are the one source of values and settings. `settings.ts` is a TypeScript module that `web/` and `e2e/` import; the defaults, the Look keys, the stored-settings reader and the root attributes are built from its table. The table has the Style row (attribute `data-style`, default Library, a Look setting that Reset look covers) and the Text size row (attribute `data-size`, Small, Medium and Large, default Medium, a Look setting in the Reading group), with one `[data-size]` block per option in `tokens.css` that sets only a factor, and its Theme default follows the spec's "with no setting stored, the app draws Light". The 10 Style blocks move from `design/prototype/tokens.css` into `design/system/tokens.css`, with their theme selectors rewritten from classes (`.th-dark`) to `[data-theme]`, when the Styles are built; until then Style has the one option Library and the panel shows no Style row. Layout likewise offers only List until Grid is built, so a stored `grid` falls back to List. `checkDefaults()` in `e2e/default-tokens.ts` confirms that the default option of every setting draws the same tokens as an element with no attribute.
- **Settings storage and the root.** All twelve settings are one JSON object in `localStorage` under `STORAGE_KEY` (`design/system/settings.ts`). `readStored` checks each key on its own against the table's option ids with plain code (the settings module imports no Zod), so one bad value falls back alone and a payload that is not an object gives the defaults. Every read and write of `localStorage` is guarded, and a failed write leaves the change applied for the session. The app root carries every attribute the table builds, and `html` carries the same `data-theme`, so the page background and `color-scheme` follow the theme; while Theme is Match system, a `change` event of `matchMedia("(prefers-color-scheme: dark)")` redraws both without a reload, and a `storage` event for `STORAGE_KEY` from another tab applies that tab's object. Before the first paint, a blocking inline script that the plugin in `tools/theme-script.ts` injects into the built `index.html`, after `<meta charset>`, sets `html`'s `data-theme` from the stored object, so a stored Dark never draws a Light frame; the plugin builds the script from the settings table (key, Theme option ids, the Match system pair) at build time, and an unreadable store leaves Light.
- **Settings panel.** The panel is a `<dialog>` inside the app root, never a portal to `body`, so the `data-*` rules of the root reach it and its own `data-font` keeps it in the default type pair. Each single-choice group (Theme, Text size, Text width, Density, Accent) is a `radiogroup` of native `<input type="radio">` elements, one `name` per setting, each inside a `<label>` that is drawn as the segment or the swatch; the input is transparent and covers its label, so it stays focusable and the label shows the focus ring through `:has(:focus-visible)`. The browser gives each group one Tab stop and moves and chooses with the arrow keys; a swatch's accessible name is the `aria-label` on its input. The panel is a container (`container-type: inline-size`), and under `24rem` of its own width each label sits above its control; its width is `--pop-w` in `rem`, so it grows with the browser's text size. At 760px and wider it is a non-modal popover (`show()`) that closes on Escape, when focus leaves it or when a press lands outside. Under 760px it is a modal sheet (`showModal()`): the browser makes the rest of the page inert, puts the panel in the top layer and draws `::backdrop`, which `components.css` fills with `--scrim`; Escape arrives as the `cancel` event, a tap on the backdrop closes it, and a Tab handler wraps from the last control to the first and back. The panel is closed and shown again when the width crosses 760px; if the focused element is gone, as Close is, focus goes to the chosen Theme radio. Closing returns focus to the gear.
- Fonts: `tokens.css` imports no font host. `web/src/main.tsx` imports every face from Fontsource, so a self-hosted Instance makes no third-party request. Fontsource's variable packages name their family with a `Variable` suffix (Fontsource docs, Variable fonts), so each font token in `tokens.css` names `'<Family> Variable'` first and the plain family as the fallback. Instrument Serif has no variable package and uses `@fontsource/instrument-serif`. Weights and italics follow the Google Fonts list in `design/prototype/tokens.css`: `opsz.css` for Newsreader, Bricolage Grotesque and Source Serif 4, which have an optical-size axis in that list, `wght.css` for the rest, and the italic files of Newsreader and Instrument Serif.
- Static files answer the same on both targets: `index.html` for a path whose last segment has no `.`, `404` for any other path that matches no file, so `/favicon.ico` and a missing `/assets/x.js` are not HTML. Workers' `single-page-application` mode cannot do this: it answers every unmatched path with `index.html` and `200` (Workers docs, Static Assets, Single Page Application, Configuration; `wrangler dev` 4.156.0 answered `/favicon.ico` and `/assets/nope.js` with `200 text/html`). The Worker therefore leaves `not_found_handling` unset, gets the `ASSETS` binding, and serves `/` itself for a `GET` or `HEAD` of a path without an extension (`src/targets/worker/index.ts`). `run_worker_first: ["/api/*"]` makes the Worker answer `/api/*` before any static asset (Workers docs, Static Assets, Routing, Worker script), and `isApiPath` (`src/http/document-path.ts`) sends the bare `/api` to the API too. The Node entry does the same with `isDocumentPath` (`src/http/document-path.ts`).
- Caching: hashed `/assets/*` are `public, max-age=31536000, immutable` and `index.html` is `no-cache`. The Node entry sets them in `src/targets/node/index.ts` and compresses with Hono's `compress` middleware. On Workers the platform compresses, and `web/public/_headers` carries the same two rules (Workers docs, Static Assets, Headers); that file also reaches `dist/web`, so the Node entry answers `/_headers` with the page and never serves the file. `/index.html` redirects to `/` on both targets (`307`).
- The library, not the paste card, reads `GET /api/items/:id/status` (the list's columns, without the post text) once a second for each `processing` Item it shows, until the Item leaves `processing` (`web/src/library.ts`). The card shows the state of its Item from those reads, so a dismissed card, a card that a newer Paste replaced and a page load that found a `processing` Item all update their row. A read changes the list only when it succeeded and the Item differs, so an unchanged poll renders nothing, and an Item's next read starts after the last answered, so reads never stack. A hidden tab (`document.hidden`) makes no reads, and the first read after it becomes visible runs at once. No websocket, so both targets serve it the same way.
- The paste box mounts two live regions before any status arrives: a polite `<output>` and an empty `role="alert"` element. Every status, from the card or from a row, is written into one of them as `<title>: <Item name>` plus its note: Reading the link, Added, Already saved, refreshed and a note go to the polite one, and `timeout`, `network`, `gave-up` and the input errors go to the alert one. The card itself has no live role. A row's Try again is a Paste through the same path, so it shows the card and makes the same announcements. The Added, refreshed and failure cards close themselves 6 s after they show, held while the pointer or focus is inside; only Dismiss and Escape move focus to the paste field.
- The PWA is a web manifest with `share_target` and a small service worker, both hand-written.

## Extension and Threadsift bot

Not built: neither `extension/` nor `bot/` exists yet.

- The Extension is built with WXT for desktop Chrome and Firefox (Manifest V3) and posts to `POST /api/items` with an agent token. It saves one page per click and never crawls.
  - **Reddit.** On Save it requests `<thread>/.json?limit=500&raw_json=1` once from the owner's tab and posts the JSON as the content; the server's `.json` paste parser reads it. ## Vault mirror

- **Git mode, both targets:** commits through GitHub's REST API (create blobs, a tree and a commit, then move the branch ref), with a fine-grained token that can write the contents of one repository. Workers has no `git` binary, and one code path keeps both targets the same. The owner chose this on 2026-11-04; v1 mirrors only to a vault repository on GitHub.
- **Folder mode, container only:** writes the same files into a mounted vault folder.
- **What triggers it.** Every change to a mirrored file's content adds its vault paths to `mirror_paths` with a new sequence number, in the same batch as the change: a new, refreshed or deleted Item; a new Digest; a Read state change; a Highlight or a Note; a Topic page; a Related Item; a Log entry; the Index, whenever a Topic's count or overview line changes; and an accepted Proposal, which rewrites every note whose Topic or Tags it renames or merges. One mirror job drains the table and writes the latest state of each path, so later wiki changes reach the vault too. When it is done it deletes only the rows up to the sequence number it read for each path, so a change that arrived while it ran stays queued.
- **One writer.** The mirror job holds the single `vault` lease and checks its generation again right before it moves the ref or writes the folder; a job that lost the lease stops without writing. It moves the ref without `force`; when GitHub rejects the update because the branch moved, it rebuilds the commit on the new tip. A writer that loses its lease between that check and GitHub's answer can still land one stale commit; the next drain rewrites those paths from current state, so the vault converges.
- **GitHub's limits.** Text files go inline as `content` in the tree; only images become blobs. One commit holds at most 500 paths (a chosen value), so a large Import mirrors in several commits. On 403 or 429 the job waits for `Retry-After` and resumes, because GitHub's secondary rate limits restrict content creation (GitHub REST docs, Rate limits). A file over GitHub's 100 MiB file limit (GitHub docs, About large files) is left out of the vault with a line in the Log.

## Export, backup and restore

- The export zip holds one Markdown file per Item with its images, as the spec describes, plus `threadsift.json` with every library record: Items, comments, media (stored images and video URLs), Digests, Topics, Tags and their links to Items, Topic pages, Related Items, Log, Proposals, Pins, Highlights, Notes and the server settings. It leaves out secrets (Provider keys, the Grok Bot webhook key, the vault token), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `leases`, `ai_tasks`, `mirror_paths`), because a restored Instance gets a new password and new tokens and starts with no work in flight. A fresh Instance can restore from it. The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** is a chain of jobs. Each slice streams the next Items into a store-mode zip (no compression, so little CPU) as R2 multipart parts of at least 5 MiB, or appends to a file in the container, and saves its checkpoint (the multipart upload id, the parts written, the zip's central-directory entries so far and the last Item id) in `exports` in the same batch as its progress; the next slice resumes from it, so an interrupted export continues instead of restarting. Each Item's records and files are read in the same slice, and while an export runs, file deletions from deleted or refreshed Items wait until it ends, so the zip never lists a file it does not hold. Nothing holds the whole library in memory.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data). D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- A backup list names every table the backup includes; a test migrates a database and fails when a table is in neither that list nor its list of excluded tables.

## Lint and format

oxlint and oxfmt run directly, not through Vite+. Vite+ 1.5.0 bundles the same oxlint and oxfmt, but its docs advise against `oxlint.config.ts` and `.oxfmtrc.json` and document only `--fix`, `--type-aware` and `-c` for `vp lint` (viteplus.dev/guide/lint, read 2026-11-04). Direct use keeps every oxlint flag and lets oxlint update on its own schedule. `oxlint.config.ts` and `.oxfmtrc.json` hold the rules; what they cannot show:

- **No separate `tsc` step.** `options.typeCheck` makes `oxlint-tsgolint` report TypeScript errors with the lint, and it needs TypeScript 7.
- **Rule plugins in `tools/oxlint/`.** `anti-slop/` is dmmulroy/anti-slop, vendored (its `UPSTREAM.md`). `threadsift/` holds `no-comments` (`docs/agents/changing-code.md`, No comments). Anti-slop's `require-safety-comment-for-type-assertion` and its two assertion rules are off, because `typescript/consistent-type-assertions` set to `never` bans the assertion itself, and the safety rule would ask for a comment.
- **Only safe fixes run unattended.** The commit hook and the agent hook (`.claude/hooks/lint-fix.sh`, after each edit to a file in the project or in one of its git worktrees, linted with that checkout's own `node_modules`) apply safe fixes; suggestion fixes run only through `pnpm lint:fix`, whose diff the agent reads.
- **Markdown is not formatted.** oxfmt pads every table column to its widest cell, so a one-cell change in a doc would rewrite the whole table.
- **`design/` is mostly outside the lint.** `design/prototype/` is reference code, and the CSS in `design/system/` keeps its one-line rule layout, so both stay out of oxlint and oxfmt. `design/system/settings.ts` is app code: oxlint, oxfmt and the TypeScript `include` cover it.

## Dependency updates

Renovate, the GitHub App, is the one update bot; `renovate.json` holds its rules.

- **Schedule.** Every minor and patch npm update arrives in one PR on Monday morning (Istanbul time); each major gets its own PR, except that `oxlint` and `@oxlint/plugins` always move together, because they must share one exact version. Lock file maintenance refreshes the indirect packages on the first day of each month. The Dependency Dashboard issue lists every pending and waiting update, so it is where an update is noticed. Renovate never merges on its own.
- **Release age.** Renovate proposes an npm version only once it is 3 days old, the same wait as pnpm's `minimumReleaseAge` in `pnpm-workspace.yaml`, so a PR never asks for a version pnpm refuses.
- **Security.** GitHub's Dependabot alerts and the OSV database feed Renovate's security PRs, which open at any time and skip the wait (Renovate docs, `vulnerabilityAlerts`, read 2026-11-04). A fix younger than 3 days still fails pnpm's install, so that PR also adds the package to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml`. Dependabot's own version and security PRs stay off, because both bots would open a PR for the same bump.
- **Local check.** `pnpm outdated` lists the npm updates before Renovate's next run. `devenv.lock` moves through `.github/workflows/update-devenv-lock.yml`, weekly or by hand, because Renovate's `nix` manager reads only `flake.nix` and is still in beta (Renovate docs, Nix manager, read 2026-11-04). The workflow runs `devenv update`, opens a pull request and approves the `pull_request` run of `gate` on its head through the REST endpoint for approving a workflow run, because a pull request that `GITHUB_TOKEN` opens holds its `pull_request` runs for approval (GitHub docs, Triggering a workflow from a workflow, read 2026-11-04). A `gate` started with `workflow_dispatch` instead passed but left the pull request blocked on `main`'s required check while the held run waited (a throwaway pull request, 2026-11-04). The approve endpoint needs the Actions write permission, which the job's `actions: write` gives its `GITHUB_TOKEN` (GitHub REST docs, Permissions required for GitHub Apps, read 2026-11-04). It needs the repository setting that lets Actions create pull requests.

## CI, releases and rollback

- **Gate.** `.github/workflows/gate.yml` runs the devenv checks, build, audit, design checks, and 3 end-to-end shards per target on separate runners and Instances with one Playwright worker each. Fail-fast is off so a failed shard leaves the others running, and every shard uploads reports and scenario attachments for 14 days. In run 42213336014, devenv spent about 137 s before the slowest Worker shard's tasks started as its largest fixed cost, while [shell setup optimization](https://github.com/KyaniteHQ/threadsift/issues/37) is separate, and `docs/testing.md` gives the local commands and count rule.
- **Docs-only changes.** When every changed path matches `docs/**` or a root `*.md` file, the end-to-end jobs skip themselves with a job-level `if:`; `ci:check` and the build still run. A path outside that list runs every job, so a file missing from the list costs a longer run, never a skipped check.
- **Merging.** `main` requires one aggregate `gate` job that needs every other job and passes when each passed or skipped itself; a workflow-level `paths` filter is not used, because a workflow it skips leaves its required checks pending. Renovate opens dependency updates after a 3-day wait.
- **Secrets and forks.** A pull request from a fork gets no secrets, and a rerun does not change that (GitHub Actions docs). The AI jobs are skipped on fork pull requests; after reading the change, a maintainer pushes it to a branch in the repository, where the AI jobs run. No job that runs pull request code uses `pull_request_target`, because it would run the fork's code with the secrets; the copy cleanup below uses it and checks out `main` only.
- **Pull request copies.** Each pull request from a branch of this repository against `main` gets its own Worker on Cloudflare with a demo owner and demo data, and its pull request page links it through a GitHub deployment. Worker Previews are not used, because they consume no Queue and run no Cron Trigger (Workers docs, Previews, Resources and isolation, read 2026-11-06), so every Paste would stay `processing`. `tools/pr-copy/cli.ts` does the work and `.github/workflows/pr-copy.yml` runs it; run with no arguments, it prints how to run it from a maintainer's machine.
  - **The token boundary.** The Cloudflare token can write every Worker, D1 database and Queue in an account that also runs other production Workers, so no job that runs pull request code sees it. The token, the account id and the demo password exist only in the GitHub environments `preview` and `live`, whose deployment branch rule allows only `main`. The gate's `build` job holds no secret and uploads the pull request's build, migrations and `wrangler.jsonc` as an artifact. The deploy runs on `workflow_run` of a successful gate, from `main`'s workflow file and `main`'s checkout, and reads the artifact as data: it copies only named regular files that stay inside the artifact. The pull request number and head SHA come from the event, never from the artifact, and the deploy checks them against the pull request before it changes anything. The copy itself runs the pull request's code, so it receives the shared demo password and holds only demo data.
  - **Whose config.** The copy runs the pull request's `wrangler.jsonc`, so a change to the compatibility date, a flag, a limit or the cron shows on its copy. The deploy parses that file against a fixed list of keys and bindings and writes every name itself, so no command can reach the live database or Queue. A new key or binding fails the deploy, before any Cloudflare call, until `tools/pr-copy/stage.ts` maps it to a copy name. Cleanup needs no config from the pull request, so such a change never stops a cleanup.
  - **Names.** A copy is the Worker and D1 database `threadsift-pr-<n>` and the Queue `threadsift-pr-<n>-jobs`, at `https://threadsift-pr-<n>.<subdomain>.workers.dev`. Every Cloudflare call refuses a name outside that pattern before it runs.
  - **Migrations and resets.** Migrations run before the Worker deploys, so a failed migration never publishes code that needs the new schema; a later push keeps the data. `wrangler d1 migrations apply` skips a file whose name is applied even when its SQL changed, so each successful deploy records the database id and a hash of every migration file in its GitHub deployment. When the record no longer matches, or a resource is missing while the Worker exists, the deploy deletes the whole copy and builds it again. It deletes the Worker too, because after `wrangler deploy` returned, the previous Worker version answered requests for some seconds and failed on its deleted database (2026-11-06). The Queue must lose its consumer before the Worker can go, and the Worker before the Queue. `wrangler delete` is not used, because it also lists KV namespaces, which the token may not read (wrangler 4.156.0, 2026-11-06).
  - **Demo owner and data.** The deploy claims an unclaimed copy, or signs in to a claimed one, through the real API with the demo password, then pastes a fixed list of links and waits for each Item's end state. A page that changed fails that deploy only, with the Item's answer in the log. Right after a deploy, workers.dev answered Cloudflare's own 404 or `error code: 1042` instead of the app, even after a run of good answers from the app (2026-11-06). So the deploy waits for the app first and repeats a call that got such an answer; that call never reached the app, and a Paste of a known link only refreshes it.
  - **One run at a time.** Deploy and cleanup for one pull request share one concurrency group with `queue: max`, so runs queue and none is cancelled (the default keeps only the newest pending run). A run for an older head or a closed pull request stops without changes, so two quick pushes end on the newer head, and a close during a deploy is cleaned up after it. The number of copies has a cap, a guess against Cloudflare's 500 Workers and 250 Cron Triggers on Paid (the account had 2 Workers on 2026-11-06); a deploy past it fails and names the open copies.
  - **Cleanup.** The `delete` job runs on `pull_request_target` `closed` and checks out `main` only. It tries every deletion, treats a resource already gone as deleted, marks the pull request's GitHub deployments inactive, and then fails with the list of deletions that failed. A reopened pull request gets a new copy from its next gate run.
- **Releases.** Not built: no release workflow exists. The plan is that a release tag builds and publishes the image with that tag and moves the `release` branch to it.
- **Rollback.** Planned with the releases. The container rolls back by running the previous image tag. Cloudflare rolls back with `wrangler rollback` to the previous Worker version. Both work because a migration only adds and the previous release still runs on the new schema.

## Testing

`docs/testing.md` is the project's testing policy: no fakes and no replayed recordings; each claim is proven through the real app the way the owner or an agent reaches it.
