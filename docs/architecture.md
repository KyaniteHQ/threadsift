The owner chose pnpm with Node 26 over Bun on 2026-11-04: Bun 1.4.3 ran the database spike with the same results, but Vite, oxlint, Playwright and wrangler run on Node anyway, so Bun would be a third runtime to test.

Two words this file uses beyond `CONTEXT.md`: a **port** is an interface the core calls (Database, FileStore, JobQueue, Scheduler, AiExecutor, Fetcher, Network), and an **executor** is the adapter that runs an AI task for one kind of Provider.

## One codebase, two install targets

The app is one core with ports, and each target supplies an adapter per port. Open Managed Agents ships one Hono app on `@hono/node-server` and on Workers this way; EdgeEver ships one Hono app on Workers and on Bun in Docker.

```
             web app (React SPA), Extension, agents, MCP clients, Grok Bot
                                      |
                 Hono app from createApp(ports): API, MCP, login, setup, static files
                                      |
                 core: ingest pipeline, AI tasks, wiki, export, restore
                                      |
   ports:   Database   FileStore   JobQueue   Scheduler   AiExecutor          Fetchers
             |           |           |          |          |                   |
container:  node:sqlite  folder     loop       timer      HTTP, CLI, Grok Bot  + plug-ins, grok CLI
Cloudflare: D1           R2         Queues     Cron       HTTP, Workers AI, Grok Bot
```

- The core imports no runtime module (`node:*`, `cloudflare:*`). Only the two target entry files and their adapters do, so a core change runs on both targets by construction.
- The `Crypto` port has one adapter, `nodeCrypto` in `src/targets/shared/`, and both targets pass it, because the Worker runs `node:crypto` through `nodejs_compat`. This is the accepted exception to the two-adapter rule. The port exists because the lint bans `node:` imports in `src/core` and `src/http`.
- Ports reach routes through `createApp(ports)`, never through `c.env`, because `c.env` holds Worker bindings on Cloudflare and Node's request and response on Node. `waitUntil` lives in the Worker entry for the same reason: Hono's Node adapter passes no execution context.
- Code that only one target has (CLI Providers, the grok X fetcher, fetcher plug-ins, the local vault folder, Workers AI) is an adapter the other target does not register. The settings screens list only registered adapters, as `docs/spec.md` (AI providers) asks.
- Hono, not Next.js: the container target runs plain Node, and Hono runs on Node and Workers with the same app object. Nitro v3 was the runner-up and was rejected for now: it is a release candidate, its database layer has no `batch`, it has no job queue on Node, and the deploy button's handling of its generated Wrangler config is undocumented. Hono 5 is at its first release candidate; the app moves to it once it is stable.

## Database and search

SQLite on both targets, one Drizzle schema, one migration folder.

- **Drivers.** D1 uses `drizzle-orm/d1`. The container uses Node's built-in `node:sqlite` through `drizzle-orm/sqlite-proxy`, an adapter of about 20 lines (`src/targets/node/database.ts`), because `sqlite-proxy` wants rows as arrays and `node:sqlite` returns them that way after `setReturnArrays(true)` (Node 26.12.1, run on 2026-11-04). The adapter supports `run` and `all`; `get` needs a missing-row convention that no query uses yet, so it throws. Drizzle 0.45.4 (the stable release) has no `node:sqlite` driver; 1.0 (release candidate 5) ships `drizzle-orm/node-sqlite`, which replaces the adapter once 1.0 is stable and its `batch` is checked. `node:sqlite` needs no native addon in the image, unlike `better-sqlite3`. The adapter and the end-to-end SQL helpers open the file with a 5 s busy timeout, because `DatabaseSync` sets none by default and a write from another connection then failed a read at once with `database is locked` (gate run 42288164651, 2026-11-06).
- **Async and batch only.** Both drivers are async and support `db.batch()`. D1 has no interactive transactions, so every multi-statement write is one `batch`, which commits or rolls back as a unit on both targets. The container's batch is to run its statements between `BEGIN` and `COMMIT` on the one connection through the `batchCallback` that `drizzle-orm/sqlite-proxy` accepts; `src/targets/node/database.ts` passes that callback, which rolls the batch back when a statement fails.
- **Guarded batches.** A batch that may only commit while a condition holds (a lease is still held at its generation, the catalog is still at the version a job read) starts with an insert into `guards`, a table whose `CHECK (ok = 1)` fails when the condition's `SELECT` returns 0. The failed check aborts the whole batch, on D1 and in the container alike, so a guarded write is all or nothing. A failed guard rolls the batch back. `guardedBatch` and `insertGuard` in `src/core/schema.ts` own the guard insert, atomic writes and condition re-read. A lost lease returns without writing; an error while the lease still holds is rethrown. The Digest runner requeues stale content or catalog inputs under its claim without consuming an attempt. The job runner (`writeWhileHolding` in `src/core/job-finish.ts`) guards every result on the row still being `running` at the attempt count its runner claimed. The guard insert is written with Drizzle's `insert(guards).select(...)`, because a raw `db.run(sql)` inside a D1 batch fails in drizzle-orm 0.45.4 (`Cannot read properties of undefined (reading 'bind')`). Both behaviours were run on node:sqlite and on local D1 under `wrangler dev` 4.156.0 on 2026-11-04: the batch with the held generation committed, the one with a stale generation failed with `CHECK constraint failed: ok = 1` and left no row.
- **Migrations.** `drizzle-kit generate` writes SQL files into `migrations/`; hand-written files hold what Drizzle cannot express (FTS5 tables, triggers). The deploy script applies them with `wrangler d1 migrations apply`; the container applies the same files at start and records them in a `d1_migrations` table of the same shape (`wrangler d1 migrations apply DB --local` creates that table with the columns that `src/targets/node/database.ts` creates, checked on 2026-11-04 with wrangler 4.156.0). Local runs use `--local --persist-to <dir>`, which needs no Cloudflare login or `database_id`. A migration only adds; a removal waits for a later release, so the previous release still runs on the new schema (see CI, releases and rollback). `drizzle-kit` 0.31.11 writes `ALTER TABLE ... ADD ... REFERENCES` without the column's `ON DELETE` action (`SQLiteAlterTableAddColumnConvertor` in `node_modules/drizzle-kit/bin.cjs`) while its snapshot records the action, so `0014_ai-task-owner.sql` carries `ON DELETE cascade` by hand. The generator's other route, recreating `ai_tasks`, would drop a table that `digests.task_id` names, and D1 enforces foreign keys in migrations ([D1 docs, Foreign keys](https://developers.cloudflare.com/d1/sql-api/foreign-keys/)).
- **Search.** FTS5 external-content tables kept in step by triggers; D1 supports FTS5 (D1 docs, SQL statements). Searchable text lives in `search_parts`, one row per part of an Item: the title, each post-text chunk, each Kept comment (`comment` parts for each Kept comment of the published Digest's generation, written in the batch that publishes the Digest), the Summary, the Tags, each Highlight and the Note. A part longer than 500,000 bytes is split into chunks, so no search row nears D1's 2 MB row limit. A query matches parts and groups them by Item; the Highlights page queries only Highlight and Note parts. Related Items candidates come from the same index, ordered by `bm25()` ascending, because a lower `bm25` score is a better match (SQLite FTS5 docs). Built so far: the title, the post text, the Digest's clean title, the Summary and the Tags, the `repository` part (a GitHub repository's description and topics, one line each, written by the fetch job in the batch that writes the `github_repos` row) and the `comment` parts of a Reddit thread; the other kinds arrive with their slices. A Kept comment body is cut like a post text by `chunkPostText`: the Digest job reads the selected bodies before its batch (`selectedBodies` in `src/core/reddit-thread.ts`), the reconciler reads the Kept bodies of the published generation in a separate query (`keptBodies`, so no single value or bound parameter holds all of an Item's comments, which can total 4 MiB against D1's 2,000,000 bytes per string), and `commentPartWrites` binds the parts as JSON arrays, so a comment of 600,000 bytes is several parts and a thread of many short comments is few statements. The app rewrites an Item's parts in the same batch as the change to that part (`src/core/search.ts`, called from the fetch, Digest and catalog writes). The migration that creates the index fills nothing. A reconciler in the job sweep (`src/core/search-reconciler.ts`) pages over 10 Items by id with a wrapping cursor, the same pattern as `linkOlderDigests`, and rewrites an Item's parts when the hash of its title, post text, stored Digest, Tag names, repository text and Kept comment ids differs from the hash stored beside its parts. This fills the index for an existing library, so search reaches an older Item only as the pass advances, and it repairs a write made by the previous release during a deploy or after a rollback. A post text over 500,000 bytes is cut into chunks of at most 125,000 characters at the last whitespace, so no word is split; one token longer than a chunk is cut hard, which is accepted. A stored Digest that does not parse adds no Digest parts, and the Item's titles, post text and Tags stay searchable. A search term is a run of letters and digits (the separators `unicode61` uses), matched as a quoted prefix, and the terms reach SQL as one JSON parameter; the filter counts come from the same batch as the list, so both describe one state of the library (`src/core/item-filters.ts`). An external-content FTS5 table is checked with `INSERT INTO search_index(search_index, rank) VALUES ('integrity-check', 1)`, which `e2e/search.spec.ts` runs after a replacement and a cascade delete. `saveSettled` in `src/core/items.ts`, the write for a short link that fails to resolve, sets only the status, the reason and the fetch result, never the title or post text, so it rewrites no part (`e2e/search-short-link.spec.ts` runs both its branches).
- **Large text.** A post text, comment body or AI task input over 1,000,000 bytes is stored as an object in the file store, and its row holds the key; the same rule runs on both targets, so no single value nears the 2 MB limit. The file store, the read of a post text from it and the fetch job's write of a long post text are built (see Files); no other kind of text uses the store yet. A comment body is never stored as a file: a Paste whose thread has a comment body over 1,000,000 UTF-8 bytes (`utf8Length` of the body) is refused with a 400, and so is a post text that long. Two chosen limits keep every value and statement below D1's 2,000,000 bytes per string or row (D1 limits, https://developers.cloudflare.com/d1/platform/limits/): a title, author, subreddit, comment id, comment author or parent id over 4,096 bytes is refused, and so is a comment whose stored row, as JSON with its escapes, is over 1,499,998 bytes, which is the 1,500,000-byte statement budget less the array brackets. Both numbers are chosen, not measured or set by Reddit: 4,096 bytes is meant to sit far above any real username, subreddit or title (unsupported: no Reddit source was checked) and keeps the title, author and subreddit parameters far below D1's limit, and 1,500,000 bytes leaves 500,000 bytes of room under 2,000,000 for the statement's own text. A body of 300,000 control characters is under the body limit and over the row limit, because each escapes to 6 bytes. `GET /api/items` selects the list's columns and leaves out the post text, because about 50 rows of long text would pass the 50 MB query-result limit; `GET /api/items/:id` returns it.
- **D1 limits that shape queries:** 100 bound parameters per statement, 1,000 queries per invocation on the paid plan, 2 MB per row, 50 MB per query result (D1 docs, Limits). A list whose length the data decides is bound as one JSON parameter and expanded with `json_each`; large reads page by key.
- **Numbers.** D1 returns numbers as JavaScript numbers, so an integer above 2^53 loses precision (D1 docs, Import and export data). X post ids are above that, so every id that comes from a Source is `text`.

Evidence, a spike on 2026-11-04 (scratch folder, not in the repo): one schema and one query module ran unchanged on `node:sqlite` (Node 26.11.1, SQLite 3.53.3), on Bun 1.4.3 (SQLite 3.53.4) and on local D1 under `wrangler dev` (wrangler 4.156.0). All gave the same results for an upsert by URL, FTS5 with porter stemming and prefix queries, triggers that follow an update and a delete, a cascade delete, and a `batch` whose second insert broke a unique index and left no row behind. D1 refuses `sqlite_version()`.

## Data model outline

Names follow `CONTEXT.md`. Columns are settled during the build.

| Table | Holds |
|---|---|
| `items` | Source, Source id (text), normalized URL (unique), original URL, author, community (the subreddit), posted and saved dates, the date the content was last fetched, title, post text as Markdown (`post_text`, up to 1,000,000 bytes in the row), the key of the file that holds a longer post text (`post_text_key`, internal, never set together with `post_text`), content generation, a pending caller-sent Digest, a linked Topic, a Digest failure marker (pending work is derived from open jobs), status (`processing`, `ready`, `failed`), the failure reason (`timeout`, `network`, `gave-up`), the last fetch result (`fetch_result`, null until a first fetch ends), Read state |
| `github_repos` | one row per GitHub repository Item, removed with it: description, stars, primary language, license as an SPDX id, GitHub's topics as a JSON array (not Threadsift Topics or Tags), and the last push in milliseconds. An Item without a row has no stars, so the list shows no stars line for it |
| `reddit_threads` | one row per Item and content generation that has a Reddit thread, removed with the Item: the comment count the thread reported (`reported`, null for a comment link) |
| `reddit_comments` | per Item and content generation, one row per comment or `more` stub in tree order (`position`): Reddit id (text), parent id, depth, kind, author, body as Markdown (null for a dropped comment and for a `more` stub), score, date, `eligible` (false for a deleted or removed body, `AutoModerator` and a bare agreement such as "this" or "thanks") and `kept`. A Digest publication sets `kept` for the ids the caller named, only on eligible rows, and deletes every older generation in the same batch. The Reader shows the Kept comments, the ancestors they need as Context stubs, and a `more` stub under any shown comment or stub or at the top level. An Item whose Digest has not published a thread reads the stored current generation: the reported and received counts and the top-level `more` stubs, and no comment body, because nothing is kept until a Digest publishes |
| `media` | per Item: file key or video URL, kind, size |
| `digests` | one stored Digest per Item: JSON, AI task id, nullable Provider and model, content generation and created date |
| `topics`, `tags`, `item_tags` | the agent's lists and the links; `catalog_version` counts changes to the Topic and Tag lists, and `catalog_linking` checkpoints older-Digest linking |
| `topic_pages` | overview text, its revision, and the ids of the Items it was built from |
| `related_items` | Item pair and one-line reason |
| `log_entries` | every agent action |
| `proposals`, `pins` | weekly Proposals with their state; accepted corrections |
| `highlights`, `notes` | owner text; a Highlight stores its target (post text or a comment id) and a text-quote anchor: the exact text plus a short prefix and suffix, as in the W3C Web Annotation `TextQuoteSelector` |
| `search_parts` | FTS5 source rows and their FTS table |
| `owner`, `sessions`, `agent_tokens`, `spent_reset_codes` | login and access; the last holds the SHA-256 digest and time of each password reset code already used |
| `settings` | server-side settings; secrets in it are encrypted. The AI row holds a Provider and model; an HTTP row also holds a base URL and a sealed key, and a Workers AI row holds neither (a `CHECK` keeps the columns in step) |
| `jobs`, `leases`, `scheduled_runs`, `guards`, `file_cleaning` | the job runner (a job's kind, Item, `address` (the link a fetch reads, which can differ from the Item's normalized URL), state, attempts, stale requeues, next attempt time and claim expiry; a unique index allows one open job per Item and kind), the leases with their generation, the schedule claims, the guard table of guarded batches, the cursor of the file cleanup |
| `ai_tasks` | one row per AI task: kind, inputs, input revision, executor, nullable Provider and model of the connection it ran with, nullable owner Item (`item_id`), attempts, deadline, state, result |
| `imports`, `exports`, `restores` | cursors and checkpoints of long runs |
| `mirror_paths` | vault paths waiting to be written, each with a sequence number |

- Post text and comments are stored as Markdown, which Defuddle can return directly. The Reader renders Markdown without raw HTML, so other people's posts never reach the page as HTML, and the export and the Vault mirror reuse the stored text.
- A refresh re-anchors each Highlight by its quote, prefix and suffix; a Highlight whose quote is gone keeps its text and is marked as no longer found (`docs/spec.md`, Highlights and Notes).

### Deleting an Item

`deleteItem` in `src/core/delete-item.ts` runs `DELETE /api/items/:id` (`src/http/delete-item-route.ts`) for the owner's session and agent tokens. The route answers 204 when the delete's `RETURNING` names the Item and 404 otherwise.

- **Manifest.** One `batch`, in this order: `reddit_comments`, `reddit_threads`, `github_repos`, `search_parts`, `search_fingerprints`, `item_tags`, `digests`, `ai_tasks`, `jobs`, then `items`. A child goes before its parent, and `digests` goes before the `ai_tasks` row its `task_id` names, because that reference has no `ON DELETE` action. Foreign keys are enforced on `node:sqlite` and on D1. The `search_parts` delete fires the FTS triggers, so the index follows. The `ON DELETE cascade` on each `item_id` column stays as a second line of defence; the list is the contract.
- **What stays.** Topics, Tags and `catalog_version`, because the lists outlive their last Item and a filter shows such a name with the count 0. `catalog_linking` and `search_reconciling` keep a cursor that may name the deleted id, which is a checkpoint and not a link. `scheduled_runs`, `file_cleaning` and the id sequences stay too, so an id is never reused.
- **Files after the commit.** After the batch commits, `deleteItem` lists `items/<id>/` through `FileStore.list` until the cursor is `null` and deletes every key it found, so the delete reaches temporary files too. A storage failure is logged as `item-files-not-deleted` and the route still answers 204, because the Item is already gone; the cleanup pass deletes what is left, since no Item names it.
- **Late writers.** Every job write is guarded on its job row (`holding` in `src/core/job-rows.ts`), the AI task insert is guarded the same way, and the search reconciler and catalog linking re-read the Item in their guard, so a runner that finishes after the delete writes nothing and ends as a lost claim. A fetch that put a long post text into the store before it lost its claim deletes that file itself, or the cleanup pass does.
- **Each slice that adds an Item-owned record extends `deleteItem` and this list in the same change.** Comments, images, Highlights, the Note, wiki records and mirror paths are the planned ones. `e2e/deletion.ts` finds every table whose `CREATE TABLE` text names an `item_id` column, in any quoting, and compares the result with its own `MANIFEST`, so the hard-case test fails until a new table is added there and seeded. `MANIFEST` is separate from the batch in `src/core/delete-item.ts`. Because every `item_id` key has `ON DELETE cascade`, the Item delete removes the rows of a table left out of the batch, and no test notices; only the `digests` line is enforced, because the `ai_tasks` delete fails without it.

## Files

The `FileStore` port (`src/core/ports.ts`) has four calls. `put(key, bytes)` takes a byte array, whose length is known (R2 needs a known length for a streamed `put`). `get(key)` returns a stream, or `null` when the key is missing, and an adapter knows the file exists before it returns the stream. `delete(keys)` counts a missing key as deleted. `list(prefix, cursor, limit)` returns keys with their upload time and the next cursor, and may return a short page before the end. The container writes under `<DATA_DIR>/files` (`/data/files` in the image); Cloudflare writes to the R2 bucket `threadsift-files`, bound as `FILES`. Images are stored as fetched. No resizing: it would need two image paths (an Images binding on Cloudflare, a native library in the container) for a feature the spec does not ask for.

- **Not built yet.** The byte range of `get` and the multipart upload for a file of unknown length (every multipart part but the last must be at least 5 MiB; R2 docs, Workers API and multipart uploads) wait for the slices that need them, the file route and restore.
- **Key grammar.** `src/core/file-keys.ts` is the one place that defines a key, and both adapters call it before they touch storage. A key is `items/<id>/<name>`: `<id>` is a canonical positive integer (no sign, no leading zero, at most 19 digits, the length of the largest SQLite rowid), and `<name>` is 1 to 255 ASCII letters, digits, `.`, `-` and `_`, other than `.` and `..`, with no further path component. Nothing decodes or normalizes a key after the check. A prefix is `items/` or `items/<id>/`, and the trailing slash keeps `items/1/` from matching `items/10/`. A key or prefix outside the grammar makes the call throw `FileRefused`, and a delete batch is checked whole before any key is removed. Deleting an Item can therefore delete one prefix.
- **Listing.** Both adapters list in the order of the key strings and return only keys the grammar accepts, so every listed key can go back into `get` and `delete`. The container reads the folders on each call and pages by the last key it returned, which suits the few files a library holds; R2 pages by its own cursor, at most 1,000 keys. R2's `delete` takes at most 1,000 keys, so the adapter splits a longer batch.
- **Container folder.** `put` writes a temporary file with an exclusively created name in the key's folder, `.tmp-<random>-<name>`, syncs it and renames it into place, so a reader never sees half a file and two puts never share a temporary path. The temporary name keeps `.tmp-<random>-` and cuts the file name after it, so it stays within 255 bytes and the key grammar for the longest accepted name. `list` reports temporary files too, so the cleanup can delete one that a crash left. The name ends with the key's own file name, so `finalKeyOf` (`src/core/file-keys.ts`) maps a temporary file to the key it will become, and the cleanup protects it exactly as it protects that key. The adapter refuses a symlinked or non-directory component of the path (the `files` root, the `items` folder and the item folder, checked top down with `lstat` before any `mkdir`, list, open or delete, and by one function for all four calls) and a leaf that is not a regular file, by `lstat` and by opening it with `O_NOFOLLOW` and checking the opened handle; a file that disappears between the checks and the open reads as missing; it throws `FileRefused`, and the post text read turns that into no text and a log line. Every resolved path stays inside the folder. The trust assumption is that no other local process swaps the store's folders while the app runs: the check and the open are two steps for a parent folder.
- **Reading post text.** The `items.post_text_key` column names the file that holds an Item's post text. `getItem` in `src/core/item-selection.ts` reads it for `GET /api/items/:id` through `readPostText` (`src/core/post-text.ts`) and drops the key from the answer. With a key, the file wins over the row's `post_text`. A key outside the grammar, a missing file or a refused file gives `postText: null`, the Item's other fields, status 200, and one JSON log line with the key escaped. Any other storage error, such as a permission error or an outage, is not hidden as missing content and ends in a 500. The list and the status poll select neither column. A refresh keeps the old text and file until committed content replaces or clears them, so a failed fetch, an `ok` result with no content and a Paste while a job is open leave the file readable.
- **Writing and publishing a long post text.** The fetch job stores a post text over 1,000,000 UTF-8 bytes (`INLINE_TEXT_BYTES` in `src/core/post-text-files.ts`) in the store, and `readArticle` returns the whole Markdown, so the job and not the reader splits at the limit. The key names the job and its attempt, `items/<item id>/post-<job id>-<attempt>.md`: a job id is never reused, and a job gets a new attempt number whenever a runner takes it over, so a key is never written twice. One SQL expression builds the key, `ATTEMPT_KEY` in `src/core/schema.ts`: the claim returns it with the job row as `attemptKey`, the fetch job writes that file, and the cleanup compares each listed key with it, so no second formatter exists. The job writes the file first. Only the guarded finishing batch (the job is `running` at the attempt its runner claimed) sets `post_text` and `post_text_key` together: a long text stores the key and clears `post_text`, a short text stores the text and clears the key, and Other clears both. Nothing else sets a key, so a file that stops being protected never becomes protected again. `finish` in `src/core/job-finish.ts` tells three outcomes apart. After a commit it deletes the previous file, which the key the Item had when the attempt started names. After a rejected finish (the claim was lost; the log gets one `job-claim-lost` JSON line with the job id and attempt) and after a finish that failed with an error while the claim was held, it deletes the one file its own attempt wrote, never another attempt's file, because the container runs 4 jobs at once and a runner that was taken over can still be inside its attempt while the new attempt holds the row. A delete that fails is logged and left to the cleanup, and the Item and the job stay committed. A long text is searchable like a short one: the batch writes its search parts, and the search reconciler leaves the post-text parts of an Item that has a key alone, because it reads only the row. The reconciler's fingerprint and its guard hold the key, so a publish between its read and its write rejects the write, and the next pass reads the key and indexes the Item again; without the key, a key published after the read left the parts to be deleted and the fingerprint unchanged.
- **Digest of a long post text.** A text in the store opens a Digest job like a short one, and the Digest job reads the start of it: `readDigestText` in `src/core/digest-source.ts` reads the file through `readPostText` and cuts it to the 14,000 bytes of the Digest input (`cutDigestInput`), so no AI task input comes near 1,000,000 bytes. A file that is missing, refused or unreadable gets the same input-currency rule as a Provider result. When the Item's generation, pending Digest or open fetch job no longer match the ones the attempt read, the attempt ends in a guarded batch that fails, so the runner requeues the job on the current inputs (`stale`) without counting an attempt. When they still match, the attempt fails before any Provider call and the job retries after 30 seconds and 2 minutes; the third read that fails ends in one guarded batch that checks the generation again and sets `failed` and the third attempt, so a refresh that publishes during the read is never failed by the old read. A retry reads the row again, so a refresh that replaced the file mid-run is picked up. `e2e/long-text-digest.spec.ts` proves it on both targets with the Workers AI proof Provider and with no Provider: War and Peace on the container ends with a Digest whose `ai_tasks` input is at most 14,000 bytes and starts with the start of the file; a seeded file of over 28,000 bytes, on both targets, gives an input of exactly 13,998 bytes that holds a marker at the start and one in the middle, holds nothing after the cut and no U+FFFD, because the cut falls inside a 4-byte character and drops it; a seeded Article with a missing file ends `failed` after three attempts with no `ai_tasks` row; and a Digest whose file is missing while a trigger opens a fetch job at its claim is requeued with its attempt count unchanged, `failed` unset and no Provider call.
- **Cleanup.** Every tick runs one page of `cleanFiles` (`src/core/file-cleanup.ts`, 100 keys) at the end of the sweep. It lists `items/` from the cursor in `file_cleaning`, asks one query, with the page's keys bound as one JSON parameter, which keys an Item names or belong to a job that is `running` at the attempt in the key (the condition the finishing guard checks), and deletes every other key of the page, a temporary file included. A temporary file is judged by the key it will become (`finalKeyOf`), so the temporary file of an attempt that is still `running` stays and the temporary file of an attempt that ended or was overtaken goes. A page that deletes cleanly saves the store's next cursor, and `null` after the last page starts a new pass; a delete that fails throws before the save, so the next tick lists the same page again and the tick log shows the error. The key names its attempt, so no table of pending files exists, and the listing finds a file whose writer crashed before any database write. A write that lands after its attempt was overtaken and after the pass went by is found on the next pass.

## Jobs, leases and the schedule

- **Jobs.** Each step that waits on the network (fetch, an AI task, a wiki step, a Vault mirror write, a Grok Bot webhook, a slice of an export or restore) is a row in `jobs` with its state, attempts and next attempt time. The same `runJob` code runs on both targets. On Cloudflare a Queues message carries the job id, with `max_batch_size: 1`, so one invocation runs one job; in the container an in-process loop picks due rows. The row, not the message, is the source of truth: a lost message, a discarded retry or a restart loses no work, because the sweep re-queues due rows.
- **One run per job.** A runner starts a job only by claiming its row (`claim` in `src/core/jobs.ts`): `UPDATE jobs SET state = 'running', claim_expires = now + deadline + 2 minutes, attempts = attempts + (state = 'running') WHERE id = ? AND ((state = 'queued' AND next_attempt_at <= now) OR (state = 'running' AND claim_expires < now)) RETURNING *`. A `done` row matches neither branch, so a second message for a finished job, or a sweep that finds it, claims nothing. An attempt whose runner died counts when the next runner takes over its expired claim, so a job that always kills its runner still reaches `gave-up`. The sweep enqueues every due row. A runner writes its result in one guarded batch (see Database and search) that checks the row is still `running` at the attempt count it claimed, so a runner whose claim was taken over writes nothing. The fetch result, the Item's status and the job's `done` state commit in that one batch, so a crash never leaves a `done` job with a `processing` Item.
- **Deadlines.** Each job runs under a deadline below the 15 minutes of wall time a Queues consumer gets (Workers docs, Limits): an AI call gets 10 minutes, a fetch 2 minutes, an export or restore slice 10 minutes. `fetchLink` builds a fetch job's deadline signal (`AbortSignal.timeout`) and passes it to `guardedFetch`, which combines it with each hop's 8 s signal through `AbortSignal.any` and turns an aborted job signal into the `timeout` result, so a fetch past its deadline ends the Item `failed` with `timeout` and is not retried. Every other job kind fails its attempt at the deadline and its row retries it. The consumer sets `limits.cpu_ms` to 300,000, the Workers Paid maximum, because a Queues consumer gets 30 seconds of CPU by default (Workers docs, Limits).
- **Values chosen for fetch jobs** (`src/core/jobs.ts` and `src/targets/node/job-loop.ts`). The deadline is 2 minutes (`FETCH_DEADLINE_MS` in `src/core/fetch-link.ts`) and a claim lasts the claimed kind's deadline plus 2 minutes (`CLAIM_MARGIN_MS`). The runner keeps one record per job kind (`HANDLERS` in `src/core/jobs.ts`: its deadline, how an attempt runs, and what giving up writes), so a new kind adds an entry and no branch. A job gets 3 attempts (`MAX_ATTEMPTS`); a failed attempt is retried after 30 seconds, and a second one after 2 minutes (`RETRY_DELAYS_MS`); after the third the Item is `failed` with `gave-up`. On Cloudflare the retry is a Queues message with `delaySeconds`. The tick sweeps at most once per 30 seconds (`TICK_SPACING_MS`), claimed in `scheduled_runs` so two ticks do not both sweep, and enqueues at most 100 due rows (`SWEEP_LIMIT`) in one `sendBatch` call, which takes up to 100 messages and one `delaySeconds` for the batch (Queues docs, JavaScript APIs: https://developers.cloudflare.com/queues/configuration/javascript-apis/); the container wakes its loop once. The container loop runs 4 jobs at once (`LOOP_WIDTH`), looks for due rows every 5 seconds (`LOOP_POLL_MS`) and calls the tick every 60 seconds (`TICK_MS`).
- **Fetched Items and Digests.** `src/core/fetch-job.ts` increments the content generation in the same guarded batch whenever a successful fetch replaces the content, and the new text may be none (a repository without a README, an Article that ends without text, a Link-only result): a Digest that started on the old text then fails its generation check instead of publishing over cleared text. The same batch opens a Digest only when text is stored and SQL finds saved settings or a pending caller-sent Digest, and marks a kept Digest "not updated" when no Digest job opens (`markKeptDigest` in `src/core/digest-job.ts`). A Digest job that finds no text left marks it the same way. A Paste alone leaves the generation alone. A supplied Reddit thread increments the generation in its own batch even when it carries no post text, and a retained Digest whose text it cleared is marked as not updated (`src/core/thread-publish.ts`). Link-only Items open no Digest. `providerSet` in `src/core/digest-job.ts` checks only for a saved row. With a saved key that no longer opens, the fetch still opens a Digest job; the run in `e2e/catalog.spec.ts` shows it giving up as `secret-missing` before any Provider call. The runner applies each handler's `blockedBy` list before claiming a job, so a Digest stays queued behind an open fetch. `src/core/digest-job.ts` then calls the task's `prepareInput` on the fetched title, Source and post text (read from the file store when the row holds a key). Its publishing guard checks the generation again. A moved generation discards the result, fails that AI task as `stale` and requeues the job under its held claim at the same attempt count, with the stale-input backoff below. One model call per run keeps the 10-minute AI deadline below Queues' 15-minute consumer limit.
- **One Item status rule.** `finish` in `src/core/job-finish.ts` closes a job and settles its Item in one batch. A failed fetch keeps its status and reason before open jobs are considered. Otherwise any remaining open fetch or Digest keeps the Item `processing` with a null reason; with none it becomes `ready`. Give-up and exhaustion use the same path, so the paste card's Added state and the New marker wait until both jobs end. A Digest failure never discards fetched content or an earlier Digest.
- **Digest refusal policy.** Wrong keys, missing models, `refused`, `not-configured`, `secret-missing`, and HTTP 400 or 422 give up immediately. `unreachable`, `timeout`, `provider-busy` and schema failures after successful HTTP responses retry after the runner's 30 seconds and 2 minutes. The scheduled sweep closes running AI tasks past their deadline as `failed/timeout` through `expireAiTasks` in `src/core/ai-tasks.ts`, covering abandoned calls after a crash or takeover. Each failed call ends its own AI task; only the batch that stores a Digest marks its task `done`. The stored Provider and model come from that call's result, so a settings change during a call cannot change its provenance.
- **Digest state and retry.** The shared Digest projection in `src/core/item-selection.ts`, used by `src/core/items.ts`, carries the stored title and Topic apart from `digestOutcome`, the latest run's outcome. `pending` comes from an open Digest job; only the failure marker is stored. Either outcome can coexist with a stored Digest. The Item view also carries its retry action (`paste`, `digest`, or none), so the UI follows one server rule. `POST /api/items/{id}/digest` opens one job over existing text at attempt 0 and leaves an already-open Digest or a failed Item unchanged; it never fetches. Both the owner's session and agent tokens may use it. `web/src/ItemRow.tsx` uses the Digest title and Topic, shows No Digest only for a failure without a stored Digest, shows Digest not updated when an older Digest is kept, and offers Try again for either failure state. A refresh that stores new text without opening a Digest job marks an older Digest as failed in the same batch. `saveAiSettings` opens older non-failed Items with text but no Digest, failure marker or open Digest job through one `INSERT ... SELECT` in its save batch, which also sets those Items `processing`. The sweep and container loop start the jobs. This costs one model call per eligible Item, at the existing runner concurrency.
- **Container restart.** When the container loop starts it marks the claim of every `running` row as expired (`abandonRunning`), because the process that held those claims is gone. The loop then claims the rows again, counts the lost attempt and runs them, so an Item that was `processing` at the restart leaves `processing` without a new Paste.
- **Leases with a generation.** A lease is a row with a holder, an expiry and a generation number that grows on every claim. Its expiry is the job's deadline plus 2 minutes, so a job that runs to its deadline still holds it. A job that writes under a lease commits in a guarded batch (see Database and search) whose guard checks that its generation still holds the lease and that the record it read is still at the revision it read; otherwise nothing is written and the job retries on fresh inputs. Jobs that need two leases, such as merging two Topics, claim them in Topic id order.
- **One update at a time per Topic.** Each wiki step for a Topic holds that Topic's lease while it reads, calls the executor and writes. This is the spec's rule against near-duplicate pages from parallel updates (`docs/spec.md`, The library wiki). With Grok Bot, the call returns later through a callback, so the step releases the lease after sending; applying the result is its own step that takes the lease again (see AI tasks and Providers).
- **New Topics and Tags.** A Digest job reads `catalog_version` with the Topic and Tag lists it gives the model. When its Digest reuses only existing names, it publishes at once, so an Import is not serialized. When it creates a Topic or a Tag, its publishing batch is guarded on `catalog_version` still being the version it read; when the guard fails, the job asks the model again with the new lists. `src/core/catalog.ts` uses `ON CONFLICT(key) DO NOTHING` and links by key in that same batch, so names another job created are reused. Each inserted name increases `catalog_version` once; reused keys leave it alone. The guard also allows a moved version when every named key already exists. The runner distinguishes lease loss, stale inputs and database errors. Only database errors consume an attempt at publish. `jobs.stale_requeues` counts guarded stale requeues, including generation changes, up to `MAX_STALE_REQUEUES` in `src/core/job-outcome.ts`, and resets on an error retry or publish. Its neighbouring `STALE_DELAYS_MS` makes the first two stale requeues due immediately and the third and later ones due 30 seconds later. After three stale requeues, a model result bypasses the catalog-version guard and publishes by key, accepting possible near-duplicate names to avoid starvation under catalog churn. The Item generation and pending-value guards still apply, so a refreshed Item cannot receive an obsolete Digest. Caller-sent Digests skip the catalog guard because no model can revise them.
- **Catalog identity and linking.** `catalogKey` in `src/core/catalog.ts` writes NFKC, lower-case, trimmed and whitespace-collapsed keys in JavaScript because SQLite lacks that Unicode normalization. Unique keys keep the first spelling. `linkingDigest` replaces an Item's Topic and Tag links in the publish batch. `linkOlderDigests` handles up to 10 unlinked stored Digests per sweep in Item id order with the same function and a guard on the stored Digest. The singleton `catalog_linking.last_item_id` checkpoint advances past failed rows and wraps after the final page, so corrupt rows cannot starve later Items and are retried on later passes. The Topic and Tag usage counts and unlinked scan use the indexes in `src/core/schema.ts`. A corrupt stored Digest is logged with its Item id and error and skipped. The list uses the linked Topic's name with `digests.topic` as its fallback.
- **Caller-sent Digests.** `items.pending_digest` stores the last Paste's validated Digest, or null. The fetch drops it when it stores no text; otherwise the Digest job reads its post-fetch generation and publishes under the generation and pending-value guards, then clears the pending column. `startCallerTask` in `src/core/ai-tasks.ts` first creates its running AI task with executor `caller`, then publication completes it. A failed publish leaves a failed task row, as for a model result, and the sweep expires a stranded running row. Nullable `digests.provider` and `digests.model` preserve its provenance. A later Paste without a Digest and Try again use the model path.

- **Schedule.** One tick, every minute, claims each due task in `scheduled_runs` and enqueues jobs: one per Topic the weekly checks touched, one per import and Grok Bot cursor, and the sweep, which also runs one page of the file cleanup (`src/core/tick.ts`; see Files). The tick calls no model, because a Cron Trigger under an hourly interval gets 30 seconds of CPU (Workers docs, Limits). Cloudflare calls the tick from a Cron Trigger; the container calls it from a timer.

## Fetchers

Each Source has one fetcher behind a `Fetcher` port: `matches(url)` and `fetch(url, ctx)` returning Item content, comments and media.

- **Article:** a plain `fetch` through `guardedFetch`, then Defuddle 0.19.6 on the linkedom document that also gives the title, with Markdown output (`readArticle` in `src/core/article.ts`). Its CPU cost is why the Cloudflare target needs Workers Paid (see Cloudflare deploy button). No Browser Rendering: pages that need JavaScript or a login come in through the Extension.
  - **Article or Other.** The page is an Article when it is HTML (`text/html` or `application/xhtml+xml`, compared without case and without parameters), the body was not cut at the cap, the final URL is not a video host (`VIDEO_HOSTS` in `src/core/links.ts`) or a Reddit, X or GitHub link, and Defuddle counts 100 words or more. Any other page is Other with no post text. A page with no `<title>` and no title from Defuddle leaves the Item as it was, with the fetch result `no-title`. The 100 words are our choice, from a probe with Defuddle 0.19.6 and linkedom 0.18.15 on 2026-11-06: `https://example.com/` gave 25 words, `https://stephango.com/saw` 143 and `https://en.wikipedia.org/wiki/Bread` 6642. With `useAsync: false` a YouTube watch page gives 0 words (probe, 2026-11-06), so no YouTube entry of `VIDEO_HOSTS` has a page that can fail on its own; `https://vimeo.com/terms` (8,211 words) is the page that needs the list, and `e2e/article.spec.ts` pastes it directly and through a redirect, so matching the pasted URL instead of the final one fails. Reddit, X and GitHub links never reach Defuddle.
  - **Defuddle makes no request of its own.** It runs with `useAsync: false`, because 0.19.6 extractors such as `c2-wiki` fetch extra pages with the global `fetch`, outside the guard (`src/extractors/c2-wiki.ts` at tag 0.19.6). `https://wiki.c2.com/?WelcomeVisitors` is the page that shows it: with the option Defuddle reads 9 words from the page and sends nothing, and without it the extractor requests `https://c2.com/wiki/remodel/pages/WelcomeVisitors` and returns 376 words (probe on Node 26.12.1, 2026-11-06). `e2e/article.spec.ts` pastes that page and expects Other, so removing the option fails it. Defuddle also takes a `fetch` option (`node_modules/defuddle/dist/types.d.ts`, `Options.fetch`), and `readArticle` passes one that refuses every request, so an extractor that ran despite `useAsync: false` would fail the job instead of using the global `fetch`. The guarded fetch cannot be passed instead, because the reader runs where no `Network` port exists (a worker thread on the container).
  - **Markdown only.** Defuddle keeps `video`, `audio` and `iframe` elements as raw HTML in its Markdown, and the Reader renders Markdown without raw HTML, so `readArticle` removes those elements from the document before Defuddle runs; a code sample that mentions the tags is text and stays. Slice 7c turns them into links.
  - **A failed refresh keeps the Article.** `settle` (`src/core/settle.ts`) writes no content field for a fetch that failed. `e2e/article-pages.spec.ts` seeds a full Article at a `.invalid` host with `storeItem`, pastes it, and expects the Source, kind, title, author, post text, posted date and fetch time unchanged and the fetch result `network` (2026-11-06, both targets).
  - **Where it runs.** Parsing, the title read and Defuddle sit behind the `PageReader` port (`src/core/ports.ts`), and the job calls it through `ports.pages`. The container adapter (`src/targets/node/page-reader.ts`) sends each page to one `node:worker_threads` worker (`page-reader-worker.ts`), because Defuddle runs on the thread that calls it: a 4 MB Gutenberg page blocked the container's event loop for about 8 s, and the API answered nothing in that time. Each read takes the fetch job's 120 s deadline signal. When it aborts with a read in flight, the container adapter terminates the worker, fails every pending read with `PageReadTimeout`, and starts a new worker on the next read; `fetchLink` turns that error into the fetch result `timeout`, which the job treats like a network timeout. The Worker adapter (`src/targets/worker/page-reader.ts`) calls the same functions inline and relies on the Worker's CPU limit. Each adapter also gives `maxHtmlBytes`, the largest HTML page it reads: 5 MiB on the container and 900 KiB on the Worker. The 4,039,247 byte War and Peace page is therefore an Article on the container, whose whole text (3,298,760 bytes of Markdown, measured 2026-11-06) is kept in a file in the store, and an Other Item, cut at the cap, on the Worker. `e2e/article.spec.ts` reads another Item while the container converts the book and expects an answer within 1 s (measured 6.6 ms slowest over 162 reads on the container, 2026-11-06).
  - **Worker memory.** A Worker isolate has 128 MB (Workers docs, Limits). Local `wrangler dev` does not enforce that limit, so the memory is estimated from the peak resident memory of the `workerd` processes (`VmHWM` in `/proc/<pid>/status`, sampled every 25 ms during one Paste in a fresh `wrangler dev` 4.156.0, 2026-11-06) minus the same measure for a Paste of `https://example.com/` (214.9 MiB). That is the whole process, so it overstates the isolate. The inspector (`--inspector-port`) returned no heap numbers.

It also makes `https://www.rfc-editor.org/rfc/rfc9110` (4,899,392 bytes) an Other Item on the Worker, and `e2e/library.spec.ts` therefore does not assert its Source.
  - **On the Worker.** `defuddle/node` bundles with `nodejs_compat`, but wrangler's bundler follows turndown's `browser` field to a build that needs a global `document`, which workerd lacks: every conversion then fell back to Defuddle's "Partial conversion completed with errors" text, which holds the raw HTML (`ReferenceError: document is not defined`, `wrangler dev` 4.156.0, 2026-11-06). `wrangler.jsonc` `alias` points `turndown` and `@mixmark-io/domino` at their Node builds (Workers docs, Wrangler configuration, Module aliasing: https://developers.cloudflare.com/workers/wrangler/configuration/#module-aliasing). Wrangler resolves an alias value from the project root, so both packages are direct dependencies at the versions `defuddle` resolves (`turndown` 7.2.4, MIT; `@mixmark-io/domino` 2.2.0, BSD-2-Clause, last release 2024-04-08), and a `defuddle` update moves the two pins with it. `e2e/article.spec.ts` fails when the aliases are removed, because the stored text then holds the fallback HTML (`expectMarkdown` in `e2e/articles.ts`).
- **GitHub:** the GitHub REST API on both targets, with no token. An optional token for a higher limit is a later change. `fetchedOfRepository` in `src/core/github-fetch.ts` runs when a pasted link's kind is `github-repo`, in place of the page fetch, and sends two requests through `guardedFetch` with API version `2022-11-28`, GitHub's default version, supported until 2028-03-10 ([API versions](https://docs.github.com/en/rest/about-the-rest-api/api-versions), read 2026-11-07).
  - **Requests.** `GET /repos/{owner}/{repo}` gives the description, stars, language, license, topics and last push. Then `GET /repos/{owner}/{repo}/readme` runs on the owner and name that first answer returns, so a renamed repository reads the README of its new name. Owner and name are the first two path segments of the pasted URL with a trailing `.git` removed (`repositoryRef` in `src/core/repository-ref.ts`); the Item's URL and identity stay as pasted, so `KyaniteHQ/commonplace` stays an Item under that name and shows the metadata of `KyaniteHQ/threadsift`, which GitHub redirects it to. A deep link such as an issue URL has the same kind and reads the same repository. GitHub says any request may redirect and the client should follow ([best practices](https://docs.github.com/en/rest/using-the-rest-api/best-practices-for-using-the-rest-api#follow-redirects)), and the guard's chain of 20 does that.
  - **Headers.** Both requests send `Accept: application/vnd.github+json` and `X-GitHub-Api-Version`. The `Network` port takes the extra headers of each hop from the fetch policy (`FetchPolicy.headers`), and the GitHub policy returns them only for an `https` URL on `api.github.com`, so they ride each redirect hop to that host and never reach another host. The global `REQUEST_HEADERS`, which every pasted site receives, did not change. Nothing reads GitHub's rate-limit response headers yet: the port returns no response headers.
  - **README format.** The raw media type (`application/vnd.github.raw+json`) answers no file name, so a fetch could not tell Markdown from another format (response headers of `GET /repos/kepano/defuddle/readme`, `curl`, 2026-11-07). The README request asks for the JSON form instead, which has the `name`, the `encoding` and the base64 `content` in one request. The Item keeps the README as post text only when the name ends in `.md` or `.markdown` (any case); any other name, such as `README.rst`, `README` or `ReadMe`, gives no text, and so does an encoding other than `base64`. The JSON body is larger than the file: GitHub wraps the base64 `content` every 60 characters and JSON escapes each line break, so 45 file bytes take 62 bytes (`GET /repos/kepano/defuddle/readme`, `curl`, 2026-11-07: a 14,146-byte README gave 316 base64 lines in a 20,313-byte answer), and the metadata adds about 0.8 KiB there and, by estimate, under 4 KiB for the longest owner and repository names. The README request therefore has its own cap, `README_ANSWER_BYTES` (768 KiB, `FetchPolicy.dataMaxBytes`), which holds the answer for a README of 512 KiB (about 706 KiB of JSON) with room for the metadata. A README whose answer is still cut is never parsed and never stored, and it is not "no README": the README read fails with `unreadable`, the fetch writes nothing, and a refresh keeps the text and metadata saved earlier. For a new Item that leaves it Link-only. GitHub documents the JSON form for files up to 1 MB ([Get repository content](https://docs.github.com/en/rest/repos/contents#get-repository-content)); a larger README is expected to answer with an HTTP error, which takes the `status` path. Relative links and images are not resolved: the Reader keeps the rule that refuses a relative URL. `NOASSERTION`, GitHub's answer for a license it cannot name, is stored as no license.
  - **Outcomes.** A repository answer of 200 and a README answer of 200 give a ready Item with metadata and README text. A repository 200 with a README 404 gives a ready Item with metadata and no text, and the Reader says the repository has no Markdown README. A repository answer that is not 2xx (404, 451, a rate-limited 403 or 429) and a README answer that is neither 200 nor 404 end the fetch with the result `status` and write no metadata: the Item settles `ready` and Link-only with no failure reason, so its row offers no Try again, and the owner pastes the link again to refetch it. The Reader says the repository has no Markdown README only after a repository answer of 200 (`fetch` is `ok`); otherwise it says the Item has no post text. `status` is not retried, so a rate-limited answer is not repeated before GitHub's reset time. A network error or a timeout takes the path it takes for a page, and an answer that does not parse gives `unreadable`.
  - **Publication.** A repository is its own kind of fetched content (`github-repo` in `src/core/details.ts`), never an Article. The guarded finishing batch of the fetch job writes the item fields, the title and post-text search parts, the `github_repos` upsert, the `repository` search part and the generation together (`repositoryWrites` in `src/core/repositories.ts`), so a runner whose claim was taken over writes none of them. A failed fetch writes no repository row, and an Item keeps its earlier row until a fetch that succeeds replaces it. The list, the status route and the save answer carry nullable `stars`; `GET /api/items/:id` carries the whole block as `repository`.
- **Reddit:** oEmbed for the title, author and subreddit, and one `.json` parser (`src/core/reddit-json.ts`) for the `.json` paste, the JSON the Extension sends and the account fetch; the Extension's Defuddle content when its `.json` request failed. A `more` stub whose replies could not be fetched becomes a Context stub. In the self-hosted builds, a link without Extension content goes first to the connected account, when there is one, and then to the archive fill: Arctic Shift's comment tree passes through a thin adapter (Arctic's top level is `{"data":[t1 nodes]}`, not Reddit's two Listings, while nested `replies` are Listings) into the same parser, so no second parser exists. Arctic's rate limit is respected and a 429 is retried once after `X-RateLimit-Reset`, at most 10 s; the Item stays Link-only otherwise. A connected account fetches `<thread>/.json?limit=500&raw_json=1` with the `reddit_session` cookie, then the replies behind each `more` stub by permalink (`docs/spec.md`, Fetchers), spaced and capped per thread, and follows `/s/` redirects. The container sends these requests with the platform `fetch`; no browser-impersonating client, because plain `fetch` got HTTP 200. The Worker sends them over `connect()` from `cloudflare:sockets` with HTTP/1.1, because Reddit answers the Workers `fetch` client with 403 even with the cookie, while a raw socket from the same Worker got 200 (3 of 3 runs, 2026-11-05). Before writing the chunked-body reader for that socket, search for a maintained HTTP client over `connect()`. The hidden-reply fill over the socket is not measured yet (see Open items).
  - **Supplied thread.** `POST /api/items` with `content` is a Paste of a post or comment link with its `.json` (`src/core/paste.ts`); the server sends no request for thread JSON. The parser (`src/core/reddit-json.ts`, with the Zod schemas in `src/core/reddit-wire.ts`) takes a post Listing and a comment Listing, each of `kind` `Listing` as are the reply Listings, checks the post id against the link, every `parent_id` against the tree and every comment id for duplicates, walks the tree without recursion, and drops a deleted or removed body, `AutoModerator` and a bare agreement from the Kept candidates (`src/core/comment-filter.ts`); a link to one comment stores that comment as the post text and its descendants as the thread, with no reported count. A comment link's tree starts at the response's outermost comment, whose parent may be outside the response (Reddit's `context` is the number of parents returned and may be 0, https://www.reddit.com/dev/api/#GET_comments_{article}); every other `parent_id` must match inside the response. One batch writes the Item's content, the thread rows (each statement binds its rows as one JSON array parameter of at most 1,500,000 bytes counting the brackets and separators (`jsonArrays` in `src/core/thread-rows.ts`), expanded with `json_each`, so no statement nears D1's 100-parameter or 2 MB limits), a content generation increment, marks every open fetch job done so that an older fetch cannot overwrite the thread, and opens the Digest the caller sent. The caller's `keptComments` (at most 2000 ids) are applied only in the batch that publishes that Digest, so a refresh keeps the last published selection readable until its Digest is accepted; a Digest from the Provider carries no such ids and keeps nothing. A Paste of the link alone refreshes the Item through oEmbed and keeps the stored thread. The model's Digest schema (`ModelDigestSchema`) does not carry `keptComments`; the agent's own keep decision is a later slice.
- **X:** the Grok Bot intake webhook on both targets; the grok CLI in the container. `grok --json-schema` returns the parsed result in a `structuredOutput` field (grok 1.0.70, run on 2026-11-04). On Cloudflare without a Grok Bot webhook, an X link becomes a Link-only Item.
- **Other:** a Link-only Item with the page's `<title>` or its oEmbed title (Defuddle's title when the page has none), and no AI task, because there is no text to digest.
- **One hop:** only when the linked URL is an article or a GitHub repository.
- **Plug-ins (container only):** a self-hoster's fetcher is an ES module that exports the same `Fetcher` shape. The container loads every module listed in `THREADSIFT_FETCHERS` at start. The Cloudflare bundle is built from the repository, so a plug-in there means a fork.
- **URLs:** one normalizer (lower-case host, no `www.`, tracking parameters dropped, short links followed) gives each Item its identity.
- **Private addresses.** A pasted link, a one-hop link or a redirect could point a fetcher at the server's own network, and the page would then be stored, served over MCP and mirrored to GitHub. So every request the server sends to a pasted address goes through one function, `guardedFetch` (`src/core/fetch-guard.ts`), which follows redirects by hand and checks each hop before it connects. The `Network` port makes one request per call without following redirects and sends the extra headers the policy gives that hop: the container's adapter is `node:http` and `node:https`, the Worker's is the global `fetch` with `redirect: "manual"`. On Cloudflare, that `fetch` answers a host that does not resolve with Cloudflare's own `530` and the body `error code: 1016`, not an error (measured from a deployed Worker on 2026-11-06), so the Worker's adapter turns that answer into a network failure, which ends a new Item `failed` with "Couldn’t reach the website" as on the container.
  - **Address rules.** `src/core/addresses.ts` allows a literal address only when it is global unicast and outside every block of the IANA special-purpose registries whose Globally Reachable value is not True, plus multicast and the reserved IPv4 block. It also refuses `2002::/16` (6to4), where an IPv4 address is embedded, decodes the IPv4 address embedded in `64:ff9b::/96` (RFC 6052), and refuses `64:ff9b:1::/48` whole, because the registry marks it Globally Reachable False and RFC 8215 leaves its prefix length and layout to the operator. Blocks whose registry rows hold a True sub-block (`192.0.0.0/24`, `2001::/23`) are refused whole, so the PCP, TURN and DNS-SD anycast addresses are refused too. The WHATWG URL parser turns `2130706433` and `0x7f.1` into `127.0.0.1` before the check, and `localhost` and every name under `.localhost` are refused by name (RFC 6761).
  - **Container.** The adapter passes a `lookup` function to `http.request`, so the check runs on the addresses the connection will use and the name is never resolved a second time. A name such as `localtest.me`, which resolves to `127.0.0.1` in public DNS, is refused after it resolves, so the link is saved without a title. A Worker deployed on Cloudflare's network cannot reach the owner's network, so there the check covers literal addresses and `localhost` only. The local Worker under `wrangler dev` runs on the owner's machine and has the same check, so the name check is missing there (see Open items).
  - **Limits.** Every hop has an 8 s deadline from the lookup to the last body byte, 20 redirects are followed (the Fetch standard's own limit) and the body is cut at a cap, after content decoding: the page reader's `maxHtmlBytes` (5 MiB or 900 KiB, see Article) for an HTML page fetched for a pasted link, and `SMALL_BODY_BYTES` (512 KiB, defined once in `src/core/fetch-guard.ts`) for a page of any other media type, for the Reddit oEmbed call and for the HTML of a short link host; the deadline and the caps are our choices, not a source's. The guard returns the final page with its media type and a flag that says the body was cut, and a cut body is never read as an Article. `https://en.wikipedia.org/wiki/Bread` is 619,662 bytes and `https://www.gutenberg.org/files/2600/2600-h/2600-h.htm` 4,039,247 bytes after decoding (measured 2026-11-06), so the old 512 KiB cap cut both; the Gutenberg page downloaded in 2.7 s from the owner's machine, inside the 8 s deadline, and `https://www.gutenberg.org/files/100/100-h/100-h.htm` (7,018,827 bytes) is the page over the cap. The adapter passes `autoSelectFamilyAttemptTimeout: HOP_DEADLINE_MS` to `http.request`, so no connection attempt ends the hop before the deadline (Node 26 docs, `socket.connect(options)`: an attempt gets that time before Node tries the next address, 250 ms by default). Node also cuts the last attempt at that time, so a smaller value ends a host whose addresses all hang early: with 2 s per attempt, `http://example.com:81/` answered `timeout` after 4014 ms on a host without an IPv6 route (2026-11-05). The trade-off is a host whose first address drops packets while a later one works: it uses up the hop and answers `timeout` on the container. A connection that never answers and a body that stalls after the connection is open both run to the 8 s deadline on both targets. `guardedFetch` through `nodeNetwork` to `http://example.com:81/` (4 addresses, Node 26.12.1) answered `timeout` after 1003 ms without the option and after 8041 ms with it.
  - **Status log.** A fetch that ends `status` writes one JSON line with `event: "fetch-status"` and `httpStatus`, the HTTP status of the last hop, and no URL, host or body (`loggedFailureOf` in `src/core/fetch-guard.ts`; the page, Reddit oEmbed, short link and GitHub fetches all end there). The Item keeps the result `status` without the code, so this line is where a failed run shows whether the host answered 404, 429 or 503. `e2e/fetch-status.spec.ts` reads it from each target's Instance log.
  - **What a hop may reach.** A redirect to a Reddit or X link stops without a request, so the oEmbed-only and X no-request rules (`docs/spec.md`, Decisions, Reddit) hold for a short link or a redirect. A short link (`SHORT_LINK_HOSTS` in `src/core/links.ts`) is the only kind of redirect that changes an Item's identity: its final or stopping URL becomes the Item's URL, and a short link that fails, or ends on a status outside 2xx, stays the Item's URL. The request resolves the short link only to find that URL (`resolveShortLink` in `src/core/fetch-link.ts`), and reads no body on a hop that is not a short link host (the policy's `readsBody`; `requestHop` then returns the page without touching `response.body` and the abort closes the connection), because the fetch job reads the page, so a page that stalls after its headers still resolves (`e2e/article-pages.spec.ts` uses `https://is.gd/3a9eIm`, made once through is.gd's API, to `https://httpbin.org/drip?duration=10&numbytes=5&code=200`); the Item is then stored and queued like any other Paste with the final URL as the job's address, so its content comes from the same fetch job and a short link to an article gets the article's text. A short link that fails to resolve is saved under the short URL with that failure and no job. Any other redirect only decides where the title comes from, so a redirect to a Reddit or X link leaves the pasted URL as the identity and the answer is `redirect-stopped`. A hop that is not an `http` or `https` URL answers `unsupported`, and a hop to an address that is not globally reachable answers `refused`. The 21st redirect answers `redirect-limit` even when it points to Reddit or X. A link whose Source allows no request (an X post, a Reddit link that is not a post or a comment) answers `not-requested`. A final dot on a host (`x.com.`) is dropped before any of these rules and before the Item's identity is built.
  - **Meta refresh.** A page from a short link host that ends the chain as HTML and holds a `<meta http-equiv="refresh">` with a delay of 0 counts as one more redirect (`src/core/meta-refresh.ts`, the HTML standard's [shared declarative refresh steps](https://html.spec.whatwg.org/multipage/document-lifecycle.html#shared-declarative-refresh-steps), read 2026-11-05): the URL resolves against the page's URL, goes through the same address, Reddit and X, `http(s)` and 20-redirect checks, and a page on any other host is never followed this way. tinyurl.com needs it: on 2026-11-04 and 2026-11-05 it answered an old link sometimes with a 301 to the target and sometimes with a 302 to `/preview/deprecated/<id>`, a 200 HTML page whose head holds the refresh (`curl` and a probe through `nodeNetwork.get`).

## AI tasks and Providers

Every model call is an AI task with a kind, inputs, an input revision and a Zod result schema. The kinds are `digest`, `topic_overview`, `related_pick` and `proposals`. The core creates the task row, an executor runs it, and the core checks the result against the schema and the rules before it applies it. A result whose input revision is no longer current is not applied; instead the core queues the same step again over the current inputs, so no Item's Digest is left out of a Topic overview.

| Executor | Provider rows it serves | Targets | How it runs a task |
|---|---|---|---|
| HTTP | OpenRouter (key or Connect), Anthropic, OpenAI and xAI keys, an OpenAI-compatible URL | both | AI SDK `generateText` with `output: Output.object({ schema })`; the vendor's own AI SDK package (`@ai-sdk/anthropic`, `@ai-sdk/openai`, `@ai-sdk/xai`) maps the schema to that vendor's structured-output dialect, and `@ai-sdk/openai-compatible` serves OpenRouter and the URL row |
| Workers AI | Workers AI | Cloudflare | `env.AI.run(model, { messages, stream: false, max_tokens: 2048, response_format: { type: "json_schema", json_schema } }, { signal })` in `src/targets/worker/ai-binding.ts`; the model list is the JSON-mode list on Cloudflare's Workers AI docs |
| CLI | Claude Code, Codex, Grok on the server | container | `claude -p --output-format json --json-schema`, `codex exec --output-schema`, `grok --json-schema --output-format json`, in an empty folder with tools off; reads `structured_output`, the last message or `structuredOutput` |
| Grok Bot | Grok Bot | both | asynchronous, below |

- **Grok Bot runs every AI task when it is the Provider** (owner's decision, 2026-11-04). Threadsift posts `{task id, kind, inputs, input revision, result schema}` to the bot's webhook with the stored key; the bot wakes, writes the result and posts it to `POST /api/ai-tasks/:id/result`. The bot's skill files in `bot/` hold the same contract. Whether the bot writes good wiki results is unverified until a live run.
  - **Who may answer.** Only the agent token the owner connected as Grok Bot may post a result; any other token gets 403.
  - **X links.** A `digest` task for an X link closes through `POST /api/items`, which carries the content the bot fetched, its Digest and the task id, as `docs/spec.md` (Grok Bot, flow C) describes. Either route closes the task by its id.
  - **Duplicates and late answers.** A result for a task that is already closed gets 409 and changes nothing. A result for an open task whose input revision has moved is handled like any stale result: the step is queued again.
  - **Deadline.** A Grok Bot task gets one hour (a chosen value, because the bot wakes in seconds to tens of seconds by its own estimate). At the deadline the task is sent again, up to 3 attempts; after that it fails, the Item or Topic shows the failure with Try again, and the Log records it. There is no silent fallback to another Provider, because the owner picks one.
- **Without Grok Bot,** every task runs on the Provider the owner picked, on that target's executor. Nothing in the core knows which executor ran a task.
- **OpenAI-compatible URL on Cloudflare** must be a public HTTPS address, because the Worker runs on Cloudflare's network, not in the owner's home. Ollama on the owner's machine works from the container.
- **Workers AI is called through the binding, not through a package.** Cloudflare deprecated `workers-ai-provider` for `createAI` from its `agents` package (npm deprecation notice), and `agents` 0.33.0 is 10.8 MB unpacked with 11 dependencies, Babel and Rolldown plugins among them. The trade-off is one structured-output dialect we write and test ourselves.
- **OpenRouter Connect** is OpenRouter's PKCE flow; the returned key is stored like any other key.
- **Built HTTP path.** `src/targets/shared/ai-executor.ts` implements the lazy AI runtime adapter and uses `ai` 7.0.161 with `@ai-sdk/openai-compatible` 3.0.83, `@ai-sdk/anthropic` 4.0.95, `@ai-sdk/openai` 4.0.107 and `@ai-sdk/xai` 5.0.37, with structured output, retries off, telemetry off and the attempt's abort signal. The three vendor versions are the ones whose `@ai-sdk/provider` (4.0.35) and `@ai-sdk/provider-utils` (5.0.73) are the ones `ai` and the compatible package already use, so the lockfile keeps one copy of each (`npm view @ai-sdk/<package>@<version> dependencies`, 2026-11-07). `languageModel` in `src/targets/shared/ai-executor.ts` picks the factory by Provider and gives every one the same `aiTransport` fetch and the row's fixed base URL: Anthropic's Messages API (`createAnthropic(...).languageModel`, which uses native structured output through `output_config.format` for models that support it and a JSON-tool fallback otherwise, in `structuredOutputMode: "auto"`), OpenAI's Responses API (`createOpenAI(...).responses`, the SDK's default factory, named so a later SDK default does not change the endpoint) and xAI's Responses API (`createXai(...).responses`; the package has no Chat factory). Sources: [Anthropic](https://ai-sdk.dev/providers/ai-sdk-providers/anthropic), [OpenAI](https://ai-sdk.dev/providers/ai-sdk-providers/openai), [xAI](https://ai-sdk.dev/providers/ai-sdk-providers/xai), and the installed type files. `runAiTask` in `src/core/ai-tasks.ts` loads the saved config, creates the task, applies its 10-minute deadline and records failures. It returns successful output with the Provider and model actually used; Verify stores its success directly, while the Digest job stores it atomically with the Digest. `src/targets/shared/ai-runtime.ts` imports the HTTP adapter inside `run`, so an isolate serving other routes does not initialize either SDK package. The `ports.ai` runtime owns the sealer, URL policy and execution seam; its HTTP adapter owns transport. Task definitions own input preparation, and callers supply input revision and attempt count. A saved connection is HTTP, with a URL and a key, or a binding, with a Provider and a model only, so the binding executor and the future CLI executors need no invented URL or key. Each task row stores the Provider, model and executor (`http`, `binding` or `caller`) of the connection it loaded, a failed Verify included; rows from before the columns existed, and caller-sent Digest tasks, keep them null. The adapter names its SDK imports statically so the bundler can remove unused exports. `src/core/ai-contract.ts` owns the Digest schema; Kept-comment ids wait for the comment filter. Verify writes no Item, Topic or Tag.
- **Task owner.** `ai_tasks.item_id` names the Item a task works for. A Digest task, model or caller, carries its Item; the Verify task carries null. The key is `ON DELETE CASCADE` like every other child of `items`: `inputs` holds up to 14,000 bytes of the Item's text, so `SET NULL` would leave that text behind after the Item is gone, and `NO ACTION` would make every delete of an Item list its tasks first. SQLite checks a `NO ACTION` key at the end of a statement ([SQLite docs, Foreign keys](https://www.sqlite.org/foreignkeys.html)), so one `DELETE FROM items` removes the Digest and the task it names together, while a delete of that task alone is refused. Both were run on `node:sqlite` and on local D1 (wrangler 4.156.0, 2026-11-07), with the same results. Foreign keys are on in both targets, and a task for an Item that is gone is refused by the key. `startTask` in `src/core/ai-tasks.ts` creates an Item's task only while its job still holds its claim, in one `INSERT ... SELECT ... WHERE` on `holding` (`src/core/job-rows.ts`, the condition the finishing guard checks), never after a separate read. When the insert writes no row, `runAiTask` and `startCallerTask` report the lost claim and the Digest attempt returns `lostClaim`, a write batch whose guard never passes. `finish` then rejects the batch because the claim is gone, logs one `job-claim-lost` line, and the attempt makes no Provider call. If the claim were still held, the same guard makes the attempt fail and retry instead of finishing with no Digest. Migration `0015` sets `item_id` from `digests.task_id` with `UPDATE ... FROM digests` (SQLite 3.33 or later, which D1 must run because the code already uses `RETURNING`, added in 3.35; D1 does not document its version), which scans `digests` once and finds each task by primary key; the earlier correlated subquery took 17.5 s for 10,000 Digests on `node:sqlite` (slice review) against D1's 30 s query limit; tasks made before it that no stored Digest names (failed attempts, replaced Digests, Verify tasks) keep null, and nothing sets their owner later. `e2e/ai-task-owner.spec.ts` deletes the job at its claim, for a model and a caller Digest, and `e2e/task-owner-migration.spec.ts` seeds the previous schema.
- **Sealed settings.** `src/core/sealed-secret.ts` uses Web Crypto AES-GCM with a fresh 96-bit IV; the ports build its sealer once at start-up. `loadAiConfig` in `src/core/ai-settings.ts` owns the read and decrypt path. `THREADSIFT_SECRET_KEY` is 32 random bytes encoded as 64 hex characters, supplied as an environment variable in the container or a Worker secret. A missing or malformed key, or a stored key that cannot be decrypted, blocks Save and Verify of an HTTP Provider until the original key is restored. Workers AI seals nothing, so its Save and Verify work without the key. `src/http/ai-routes.ts` exposes owner-only settings and Verify; responses reveal only whether a key is set. The executor returns selected refusal categories and an HTTP status, never an SDK error object, because those objects may contain credentials.
- **HTTP transport.** `src/targets/shared/ai-transport.ts` is the SDK's custom fetch. It refuses redirects on both targets. On the Worker, `src/core/ai-url.ts` applies the fetch guard's public-address rules from `src/core/addresses.ts` and requires HTTPS on Save and Verify. The Worker passes `workerFetch` from `src/targets/worker/network.ts`, which also serves the fetcher and turns Cloudflare’s 530 error page into a network failure. The local Worker's name-check gap below still applies. The container permits a private HTTP endpoint for Ollama. The Provider fields and fixed URLs come from `PROVIDERS` in `src/core/ai-contract.ts`; the Cloudflare form explains its HTTPS requirement.
- **Refusal mapping.** `executionRefusal` in `src/targets/shared/ai-executor.ts` turns every SDK error into one category. An HTTP 401 or 403 is `wrong-key`, 404 `model-not-found`, 429 and 5xx `provider-busy`, 400 and 422 `no-json`, a redirect or a refused address `refused`. xAI answers a wrong key with HTTP 400 and `{"code":"invalid-argument","error":"Incorrect API key provided..."}` (`curl` to `https://api.x.ai/v1/responses` with an invented key, 2026-11-07), so an xAI 400 whose message holds `Incorrect API key provided` is `wrong-key` too; Anthropic (`authentication_error`) and OpenAI (`invalid_api_key`) answer 401. The executor reads the finish reason before the output: `content-filter` is `declined` and `length` (the 2,048-token output cap) is `cut-off`, even when the text parsed, and a `NoObjectGeneratedError` is classified by the same finish reason. When a non-`stop` finish carries no text, the SDK's `output` getter throws `NoOutputGeneratedError`; the finish reason is read first, so that error only remains for the finish reasons `error` and `other`, and it is `no-json`. Anthropic's `refusal` stop reason reaches the SDK as `content-filter` (provider page, Finish reason mapping). `@ai-sdk/openai` 4.0.107 does not do this for the Responses API: its response schema accepts only `output_text` content parts (`openai-responses-api.ts` in the package), so a refusal part (`{"type":"refusal"}`, OpenAI's structured-output refusal shape) fails decoding as an `APICallError` with status 200 and a `TypeValidationError` whose `value` is the response. `holdsRefusalPart` recognises that shape with a Zod schema (an `output[].content[]` part of type `refusal`) and returns `declined`. `@ai-sdk/openai` 4.0.110 decodes refusal parts (its changelog, entry 6b97088), but it needs `@ai-sdk/provider` 4.0.36 and `@ai-sdk/provider-utils` 5.0.75, which would add a second copy of each, and it was published 2026-11-06, inside the repository's 3-day `minimumReleaseAge` (`pnpm-workspace.yaml`); when `ai` and the other packages move to those versions, drop `holdsRefusalPart`. A local server that sent the SDK a refusal part, an empty `incomplete` response and a schema-valid `incomplete` response got `declined`, `cut-off` and `cut-off` from `runHttp`; no vendor sent one, so a real refusal stays unverified. `declined` and `cut-off` are deterministic for the same model and input, so `retriesAi` does not retry them: the Digest job marks the Item failed with Try again, and Verify shows the recovery text. A `no-json` without an HTTP status is still retried, because a model can return valid JSON on the next call.
- **Measured Digest input budget.** `digestPrompt` and `cutDigestInput` in `src/core/ai-contract.ts` share a selected cap of 14,000 UTF-8 bytes between the catalog and Item input, omitting an incomplete final code point. The catalog gets up to 4,500 bytes, split equally between Topics and Tags with JSON overhead reserved; each list retains its names with the most Items first, breaking ties by id. `CATALOG_NAME_LIMIT` bounds each `readCatalog` query from the per-list byte budget and the shortest valid encoded name, so no name that could fit is excluded by the row limit. These are chosen limits for the proof model, not a guarantee for other models. On 2026-11-06, `direnv exec . node tools/measure-ai-input.ts Hex` through the Workers AI credentials measured a hexadecimal Item with 200 Topics and 500 Tags against `@cf/meta/llama-3.3-70b-instruct-fp8-fast`, whose documented context is 24,000 tokens. The input was 14,000 bytes, and the whole prompt with instructions and schema was 14,915 bytes. The Provider reported 6,668 input tokens; adding the reserved 2,048 output tokens gives 8,716 tokens. The lists leave room for Item text. Re-measure when the prompt, schema or budget changes.
- **SDK bundle cost.** Keeping `generateText` and `Output.object` also keeps the unused gateway dependency. A minified HTTP-executor measurement attributed 187,606 bytes to `ai`, `@ai-sdk/gateway` and `@vercel/oidc` together. In the 2026-11-06 Wrangler 4.156.0 dry-run comparison (`pnpm exec wrangler deploy --dry-run --outdir <dir> --metafile <file>`), importing the SDK package namespace dynamically kept its unused exports and grew the bundle from 5,328,151 to 6,026,602 bytes; `ai` accounted for 598,048 of the extra bytes. Loading the local adapter lazily instead preserves named-import tree shaking and produces 5,436,407 bytes, about 5.18 MiB. The remaining 108,256 bytes are additional retained code in the same packages, principally Zod (67,946 bytes), the gateway (13,213), `ai` (10,755) and provider-utils (7,555); the metafiles show no additional CommonJS dependency files. Lazy initialization changes when this code runs, not the remaining package cost. `pnpm build:worker` checks the current upload size. ## Access: owner login, agent tokens, MCP

- **Setup.** A new Instance shows a setup page that asks for the one-time `SETUP_CODE` first (unless the Instance has none usable, below), then for a new password and, optionally, an export zip to restore (see Export, backup and restore). On Cloudflare the deploy button prompts for `SETUP_CODE` and `THREADSIFT_SECRET_KEY` as secrets; in the container both are environment variables, and a missing `SETUP_CODE` makes the container print a generated one as one `Setup code:` log line at each start while no owner exists. Without the code, anyone who finds a fresh public Instance could claim it. A code shorter than 16 characters is refused with 503 on both setup calls, and so is a Worker with no code. Every refusal of the setup and login calls carries one `code` in the error body (the closed list `REFUSAL_CODES` in `src/http/schemas.ts`: `wrong`, `owner-exists`, `locked`, `setup-missing`, `setup-short`, `password-short`, `password-long`), and the web client reads that field instead of guessing from the status. While no owner exists, `GET /api/session` also answers `code` (`set`, `missing` or `short`, from `checkConfiguredCode` in `src/core/setup-code.ts`), so the setup page opens on the block that names the fix instead of asking for a code first. The field reveals only what the 503 already reveals, and it is absent once an owner exists. The single `owner` row (a `CHECK` on `id = 1`, inserted with `ON CONFLICT DO NOTHING`) makes a second setup a 409.
- **The guard.** One middleware on `/api/*` runs before every handler and answers closed by default. The only routes it lets through unauthenticated are `GET /api/session`, `POST /api/setup/code`, `POST /api/setup`, `POST /api/login` and `POST /api/password/reset`, matched by exact method and path in `src/http/access-rules.ts`. It checks, in order: an owner session cookie or an agent token (`bearer-auth`: 400 for a malformed header, an empty one included, 401 for an unknown or revoked token), then that `/api/tokens`, `/api/logout`, `/api/settings`, `/api/password` and `/api/items/:id/read-state` are not reached with a token (403), because Read state is the owner's, then Hono's `csrf` (403) for requests without an `Authorization` header only, because a bearer token is no ambient credential a foreign page could make the browser send, then `body-limit` (413). A route added later is therefore closed until someone lists it.
- **Owner login.** The password is counted in code points after NFKC normalization, must be 15 to 1,024 long (NIST SP 800-63B-4 sets 15 as the minimum for a password alone), and is hashed with scrypt from `node:crypto`, which both targets have, at N=2^15, r=8, p=3, one of OWASP's Password Storage settings, with `maxmem: 64 MiB`. Node's default `maxmem` of 32 MiB rejects those settings (`ERR_CRYPTO_INVALID_SCRYPT_PARAMS`, Node 26.11.1, run on 2026-11-04). The OWASP default N=2^17 needs 128 MiB, the whole memory of one Worker. The stored string is `scrypt$N=…$r=…$p=…$salt$key`, so a later cost change still verifies old hashes. A session is a 32-byte random id in the `__Host-threadsift_session` cookie (`HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, Max-Age 30 days), stored in `sessions` as a SHA-256 digest with its expiry. A use renews the session once less than 29 days remain, so a session lives 30 days from its last use, and an expired one is deleted and refused. A login commits its session in a guarded batch (see Database and search) that holds only while the password hash it verified is still the stored one, so a login that raced a password change or a reset gets 409 `password-changed` and starts no session. Setup does the same: it inserts the owner, then commits its session in a guarded batch on the hash it wrote, so a reset that lands between the two leaves no session and setup answers 409 `password-changed`. Chromium keeps the `Secure` `__Host-` cookie over `http://127.0.0.1`, so the local suite runs the real cookie.
- **Throttle.** The `throttles` table holds one row for each of `setup`, `login` and `reset`. One atomic upsert counts each attempt before its code or password is checked, so parallel guesses each count and only ten of them are checked; the tenth counted attempt locks the kind for 60 seconds. A locked kind answers 429 with `Retry-After` without checking anything, even for the right code or password, so an attempt during a lock is not counted and does not extend it. Each attempt counted after a lock ends, before a success, doubles the next lock, up to 1 hour. A success deletes the row only when it is the latest counted attempt, so a success that finishes late cannot clear a lock that newer attempts set. The lock is in the database, so a restart keeps it. It is global, not per address, because behind a proxy the app has no address it can trust; the cost is that anyone who can reach the login can lock the owner out of signing in for up to an hour, while sessions already open and agent tokens keep working.
- **Change and reset the password.** `src/core/owner-password.ts` holds both. They end every session and keep the agent tokens, which the signed-in owner revokes on their own.
  - **Change.** `POST /api/password` is owner-only and closed to tokens. It refuses a new password outside 15 to 1,024 characters (400) before it counts an attempt, then verifies the current password under the `login` throttle kind, so a guess through the login or through the change draws on one budget (OWASP Authentication Cheat Sheet: ask for the current password to change it, and count lockout per account). A wrong current password answers 403 `wrong`, never 401, because the web client treats a 401 as signed out. One guarded batch sets the new hash, deletes every session and inserts the caller's new session, and it holds only while the stored hash is still the one that was verified and the calling session still exists. The new session is prepared without writes, and its cookie is sent only after the commit, replacing the guard's renewal cookie if both are set (OWASP Session Management Cheat Sheet: renew the session id on a password change). A call that loses the race gets 409 `password-changed` and changes nothing. A change runs two scrypt hashes in one request.
  - **Reset.** `POST /api/password/reset` is public and works only while the server holds `PASSWORD_RESET_CODE`: a container environment variable read at start, or a Worker secret read from each request's `env` (`src/targets/worker/index.ts` keeps one app per code value and never reads the code from the cached ports). It is an operator credential on the owner's own server, like `SETUP_CODE`, so it has no expiry. That departs on purpose from the Forgot Password Cheat Sheet's expiry advice, and its single use, the 32-character minimum and the removal after use make up for it. The code is compared by SHA-256 digests with `crypto.equal`, under its own `reset` throttle kind that counts each attempt before the check. The reset reads the stored hash before it hashes the new password. One guarded batch, which holds only while that hash is still the stored one and the code is unspent, inserts the code's digest into `spent_reset_codes`, sets the hash, deletes every session and clears the `login` throttle row, because that lock protected the old password. A spent digest stays refused after later codes are used, so setting an old code again does nothing. When the batch fails, the reset answers `reset-used` if the code is spent and `password-changed` otherwise, so a reset never overwrites a change that committed after it read the hash. The reset starts no session and sets no cookie (Forgot Password Cheat Sheet: do not log the user in automatically).
  - **States the routes reveal.** Wrong current password 403 `wrong`; wrong reset code 403 `wrong`; no reset code 503 `reset-missing`; a code under 32 characters 503 `reset-short`; a spent code 409 `reset-used`; no owner 409 `no-owner`; a lost race 409 `password-changed` (also from setup and reset); a change without a live session 401; locked 429 with `Retry-After`; a new password outside 15 to 1,024 characters 400. Every refusal leaves the password, the sessions and the spent codes as they were. The 503 reveals only whether a code exists, as the setup 503 does.
  - **Rules from outside.** NIST SP 800-63B-4 3.1.1.2 and 3.2.2 are cited as selected guidance (15 characters, no composition rules, no forced rotation, an attempt limit), not as full conformance; its section 4 on recovery was not read. Cloudflare's `wrangler secret put` deploys a secret at once and `wrangler secret delete` removes it (Workers docs, Secrets). A run on a throwaway pull request copy (wrangler 4.156.0, 2026-11-07) agreed: after `put` of a code, a reset with it answered 204; after `put` of a second code, the first answered 403 `wrong` and the second 204; after `delete`, a code never used answered 503 `reset-missing`.
- **Agent tokens.** One random token per connected agent, `tsa_` and 32 random bytes in base64url, shown once, stored as a SHA-256 hash (the token is high-entropy, so a fast hash is enough), revocable in settings. `last_used_at` updates at most once an hour through a conditional `UPDATE`, so a busy agent does not write on every request. The Extension, Grok Bot and MCP clients use them as bearer tokens. The token the owner connects in the Grok Bot settings is marked as Grok Bot's, and only it may post AI task results.
- **Secrets at rest.** Provider keys, the Grok Bot webhook key, the vault token and the owner's Reddit session cookie are sealed with AES-GCM (WebCrypto, on both targets) under `THREADSIFT_SECRET_KEY`, which the app reads from its environment and never shows.
- **The share route.** `/share` (`src/http/share-routes.ts`) is the manifest's `share_target` action. It sits outside `/api/*`, so the guard never sees it and an agent token never reaches it. It takes the form `POST` that the manifest declares and a `GET` with the same fields, and it writes only for a `POST` that has all three: an owner session cookie, `Sec-Fetch-Site: same-origin` and an `Origin` whose host equals the request's host (`src/http/share-trust.ts`). Missing metadata, `Origin: null` and a token never authorize a write. The session cookie is `SameSite=Lax`, so a cross-site `POST` carries no cookie, and the two header checks stop a same-site page on another port, whose `POST` does carry it. The pattern is the `csrf()` default of the installed Hono 4.13.16 (`node_modules/hono/dist/middleware/csrf/index.js`), made stricter: Hono lets a request pass on either header, this route needs both. It compares the host of the `Origin` and not its scheme, because the container sees plain HTTP behind the owner's TLS proxy while the browser's `Origin` says `https`, and `Sec-Fetch-Site: same-origin` already covers the scheme. The 64 KiB body limit applies, and a body that cannot be decoded, such as `multipart/form-data` with no boundary, answers the same `no-store` `303` with `notice=invalid` (`src/http/share-fields.ts`). A trusted share calls `saveItem`, the core function that `POST /api/items` calls, and answers `303` to `/?saved=<id>`, or `/?refreshed=<id>` for a known Item that had been fetched. Every other arrival writes nothing and answers `303` to `/?link=<link>`, with `notice=invalid`, `private` or `empty` when the trusted share had nothing valid to save (`src/core/share-address.ts` owns the address in both directions). The link is the first `http:` or `https:` address in `url`, then `text`, then `title`, without trailing `.,;:!?)]}'"` (`src/core/shared-link.ts`); an address that ends in `)`, such as a Wikipedia title with a bracket, loses it, which is the cost of the rule. The address carries at most 1,000 UTF-16 code units, so the redirect stays under Node's default header limit of 16 KiB even when every unit percent-encodes to 9 bytes, the worst case for a three-byte UTF-8 character (Node docs, `--max-http-header-size`); a longer link is cut to that and carries `notice=invalid`.
- **Request limits.** Hono's `body-limit` middleware caps request bodies on both targets, because Node has no cap of its own and Cloudflare's cap depends on the zone's plan (100 MB on Free and Pro, Workers docs, Limits). Every route takes 64 KiB, except `POST /api/items`, which takes 8 MiB (413) because it carries a thread; its `content` field is then limited to 4 MiB (413) and must parse as a Reddit thread of the link (400, with the reason). `GET /api/items/:id` returns the published `comments` view: the reported and received counts, the Kept count and the nodes in tree order.
- **MCP.** `createMcpHandler` from `@modelcontextprotocol/server` serves Streamable HTTP at `/mcp` on both targets; its SDK documents that web-standard handler for Workers. The handler checks no token itself (MCP SDK reference, `createMcpHandler`), so a Hono middleware hashes the bearer token, rejects a miss, checks Host and Origin, and passes the caller as `authInfo` to `handler.fetch`. Each tool calls the same core function as the matching HTTP route. OAuth for Grok Bot's catalog comes later (`docs/spec.md`, Grok Bot).

## Web app

- A React 19 single-page app built by Vite (owner's decision, 2026-11-04). One static build serves Workers static assets and Hono's `serveStatic` on Node, and it is the shape Tauri and Capacitor take for a later desktop or mobile app. No server rendering: one owner behind a login gains nothing from it.
- React-specific libraries stay few, so the app can try Preact 11 through `preact/compat` after the first release if page weight matters: in a small comparable build, React's framework JavaScript was 68.0 KB gzip and Preact's 7.7 KB (measured 2026-11-04 in a scratch build, not on this app).
- The prototype is Claude Design's own template format on React 18 classes, so the app rewrites it. Its behaviour (reader bar fitting, folding by measured height, reading-place restore, the keys) is plain DOM code and becomes plain TypeScript modules that take an element. Highlights are drawn with the CSS Custom Highlight API.
- `design/system/tokens.css`, `components.css` and `settings-table.ts` are the one source of values and settings. `settings-table.ts` owns the rows that `web/` and `e2e/` import; `settings.ts` builds the defaults, stored-settings reader and root attributes from those rows. The table has the Style row (attribute `data-style`, default Library, a Look setting that Reset look covers) and the Text size row (attribute `data-size`, Small, Medium and Large, default Medium, a Look setting in the Reading group), with one `[data-size]` block per option in `tokens.css` that sets only a factor, and its Theme default follows the spec's "with no setting stored, the app draws Light". The Style row offers Library and the 10 Styles in `docs/design/styles.md`. Their `[data-style]` blocks follow the Theme and derived-token rules, with nested `[data-theme]` selectors. Style supplies the fonts and accent; the panel keeps Plex text and inherits the Style accent. Font and Accent keep their stored values while disabled, and Library restores them. The settings table lives in `settings-table.ts`; storage operations and derived values live in `settings.ts`. `checkDefaults()` in `e2e/default-tokens.ts` confirms that the default option of every setting draws the same tokens as an element with no attribute.
- **Settings storage and the root.** All twelve settings are one JSON object in `localStorage` under `STORAGE_KEY` (`design/system/settings.ts`). `readStored` checks each key on its own against the table's option ids with plain code (the settings module imports no Zod), so one bad value falls back alone and a payload that is not an object gives the defaults. Every read and write of `localStorage` is guarded, and a failed write leaves the change applied for the session. The app root carries every attribute the table builds, and `html` carries the same `data-theme`, so the page background and `color-scheme` follow the theme; while Theme is Match system, a `change` event of `matchMedia("(prefers-color-scheme: dark)")` redraws both without a reload, and a `storage` event for `STORAGE_KEY` from another tab applies that tab's object. Before the first paint, a blocking inline script that the plugin in `tools/theme-script.ts` injects into the built `index.html`, after `<meta charset>`, sets `html`'s `data-theme` from the stored object, so a stored Dark never draws a Light frame; the plugin builds the script from the settings table (key, Theme option ids, the Match system pair) at build time, and an unreadable store leaves Light.
- **Settings panel.** The panel is a `<dialog>` inside the app root, never a portal to `body`, so the `data-*` rules of the root reach it and its own `data-font` keeps it in the default type pair. Each single-choice group (Theme, Text size, Text width, Density, Accent) is a `radiogroup` of native `<input type="radio">` elements, one `name` per setting, each inside a `<label>` that is drawn as the segment or the swatch; the input is transparent and covers its label, so it stays focusable and the label shows the focus ring through `:has(:focus-visible)`. The browser gives each group one Tab stop and moves and chooses with the arrow keys; a swatch's accessible name is the `aria-label` on its input. The panel is a container (`container-type: inline-size`), and under `24rem` of its own width each label sits above its control; its width is `--pop-w` in `rem`, so it grows with the browser's text size. At 760px and wider it is a non-modal popover (`show()`) that closes on Escape, when focus leaves it or when a press lands outside. Under 760px it is a modal sheet (`showModal()`): the browser makes the rest of the page inert, puts the panel in the top layer and draws `::backdrop`, which `components.css` fills with `--scrim`; Escape arrives as the `cancel` event, a tap on the backdrop closes it, and a Tab handler wraps from the last control to the first and back. The panel is closed and shown again when the width crosses 760px; if the focused element is gone, as Close is, focus goes to the first checked radio in the panel body (`FIRST_CHOICE` in `web/src/use-panel.ts`). Closing returns focus to the gear.
- Fonts: `tokens.css` imports no font host. `web/src/main.tsx` imports every face from Fontsource, so a self-hosted Instance makes no third-party request. Fontsource's variable packages name their family with a `Variable` suffix (Fontsource docs, Variable fonts), so each font token in `tokens.css` names `'<Family> Variable'` first and the plain family as the fallback. Instrument Serif, Cal Sans, Spectral, DM Mono, Fira Mono and Space Mono have static Fontsource packages. They register the plain family name and load per-weight files; the catalogue offers no variable face for them. The other Style faces use variable packages. Imports keep all package subsets, as the existing font imports do, so saved text can use the supported scripts. Weights and italics follow the Google Fonts list in `design/prototype/tokens.css`: `opsz.css` for Newsreader, Bricolage Grotesque, Source Serif 4 and DM Sans, which have an optical-size axis in that list, `wght.css` for the rest, and the italic files of Newsreader, Instrument Serif, Spectral and EB Garamond. The document-head script and `use-settings.ts` both apply Theme and Style to `html`, so the page canvas matches the app before and after React mounts. `--acc` is derived only where its inputs change, so the panel inherits the Style accent and each Accent swatch draws its own hue.
- Static files answer the same on both targets: `index.html` for a path whose last segment has no `.`, `404` for any other path that matches no file, so `/favicon.ico` and a missing `/assets/x.js` are not HTML. Workers' `single-page-application` mode cannot do this: it answers every unmatched path with `index.html` and `200` (Workers docs, Static Assets, Single Page Application, Configuration; `wrangler dev` 4.156.0 answered `/favicon.ico` and `/assets/nope.js` with `200 text/html`). The Worker therefore leaves `not_found_handling` unset, gets the `ASSETS` binding, and serves `/` itself for a `GET` or `HEAD` of a path without an extension (`src/targets/worker/index.ts`). `run_worker_first: ["/api/*", "/share"]` makes the Worker answer those paths before any static asset (Workers docs, Static Assets, Routing, Worker script); the setting only decides when the Worker runs, so `isServerPath` (`src/http/document-path.ts`) also sends `/api`, `/api/*` and `/share` to the Hono app, because `serveDocument` answers a `POST` with 404. The Node entry mounts the Hono app before static files, so `/share` reaches it there without a rule, and serves the page with `isDocumentPath` (`src/http/document-path.ts`).
- Caching: hashed `/assets/*` are `public, max-age=31536000, immutable` and `index.html` is `no-cache`. The Node entry sets them in `src/targets/node/index.ts` and compresses with Hono's `compress` middleware. On Workers the platform compresses, and `web/public/_headers` carries the same two rules (Workers docs, Static Assets, Headers); that file also reaches `dist/web`, so the Node entry answers `/_headers` with the page and never serves the file. `/index.html` redirects to `/` on both targets (`307`).
- The library, not the paste card, reads `GET /api/items/:id/status` (the list's columns, without the post text) once a second for each Item's first 10 polls, then once every 5 seconds while it stays `processing` (`web/src/item-polling.ts`). The card shows the state of its Item from those reads, so a dismissed card, a card that a newer Paste replaced and a page load that found a `processing` Item all update their row. A read changes the list only when it succeeded and the Item differs, so an unchanged poll renders nothing, and an Item's next read starts after the last answered, so reads never stack. A hidden tab (`document.hidden`) makes no reads, and the first read after it becomes visible runs at once. No websocket, so both targets serve it the same way.
- The paste box mounts two live regions before any status arrives: a polite `<output>` and an empty `role="alert"` element. Every status, from the card or from a row, is written into one of them as `<title>: <Item name>` plus its note: Reading the link, Added, Already saved, refreshed and a note go to the polite one, and `timeout`, `network`, `gave-up` and the input errors go to the alert one. The card itself has no live role. A row's Try again is a Paste through the same path, so it shows the card and makes the same announcements. The Added, refreshed and failure cards close themselves 6 s after they show, held while the pointer or focus is inside; only Dismiss and Escape move focus to the paste field.
- **The Reader in List.** Choosing an Item navigates to `/items/:id`, and the Reader is the third pane (`ReaderPane`), reading `GET /api/items/:id` for the post text and the Digest's Summary, Key points and Tags (`digest` is null before the first Digest). Under 760 px (`narrow`) the Reader covers the screen as a page: the list column is `inert`, focus moves to the Reader's title, and the back control returns focus to the row. `PUT /api/items/:id/read-state` takes `{readState}`, answers the Item as the list shows it and changes no other column; only the owner session may call it, a Paste refresh and the Digest job never write the column. The client adjusts the counts itself while no filter is on. With a filter on, the marked row stays and one counts-only read follows, so the row leaves at the next list read (`web/src/library.ts`).
- **The Reader in Grid.** `data-reader` on the app root is `pane`, `page` or `sheet`, worked out in `web/src/reader-place.ts` from Layout, Open items as and the width; under 760 px it is always `page`. Page is the Reader over the whole app, as in List under 760 px. Sheet is a modal `<dialog>` that fills the window and holds the Reader's slot and the Previous and Next buttons, because only a descendant of the dialog sits in the top layer above its `::backdrop`; a click that starts and ends on the dialog itself, outside the sheet, closes it. Closing goes through the address like every other close, so Escape, the back gesture (`cancel`) and Close all end in `/`. Opening an Item pushes a history entry that records the path it came from (`web/src/routing.ts`); closing goes back one entry when that path was the library, and replaces the address with `/` for an Item reached directly, so browser Back never reopens a closed Item. ## Vault mirror

- **Git mode, both targets:** commits through GitHub's REST API (create blobs, a tree and a commit, then move the branch ref), with a fine-grained token that can write the contents of one repository. Workers has no `git` binary, and one code path keeps both targets the same. The owner chose this on 2026-11-04; v1 mirrors only to a vault repository on GitHub.
- **Folder mode, container only:** writes the same files into a mounted vault folder.
- **What triggers it.** Every change to a mirrored file's content adds its vault paths to `mirror_paths` with a new sequence number, in the same batch as the change: a new, refreshed or deleted Item; a new Digest; a Read state change; a Highlight or a Note; a Topic page; a Related Item; a Log entry; the Index, whenever a Topic's count or overview line changes; and an accepted Proposal, which rewrites every note whose Topic or Tags it renames or merges. One mirror job drains the table and writes the latest state of each path, so later wiki changes reach the vault too. When it is done it deletes only the rows up to the sequence number it read for each path, so a change that arrived while it ran stays queued.
- **One writer.** The mirror job holds the single `vault` lease and checks its generation again right before it moves the ref or writes the folder; a job that lost the lease stops without writing. It moves the ref without `force`; when GitHub rejects the update because the branch moved, it rebuilds the commit on the new tip. A writer that loses its lease between that check and GitHub's answer can still land one stale commit; the next drain rewrites those paths from current state, so the vault converges.
- **GitHub's limits.** Text files go inline as `content` in the tree; only images become blobs. One commit holds at most 500 paths (a chosen value), so a large Import mirrors in several commits. On 403 or 429 the job waits for `Retry-After` and resumes, because GitHub's secondary rate limits restrict content creation (GitHub REST docs, Rate limits). A file over GitHub's 100 MiB file limit (GitHub docs, About large files) is left out of the vault with a line in the Log.

## Export, backup and restore

- The export zip holds one Markdown file per Item with its images, as the spec describes, plus `threadsift.json` with every library record: Items, comments, media (stored images and video URLs), Digests, Topics, Tags and their links to Items, Topic pages, Related Items, Log, Proposals, Pins, Highlights, Notes and the server settings. It leaves out secrets (Provider keys, the Grok Bot webhook key, the vault token), the owner's password hash, sessions, agent token hashes, and the working tables (`jobs`, `leases`, `ai_tasks`, `mirror_paths`), because a restored Instance gets a new password and new tokens and starts with no work in flight. A fresh Instance can restore from it. The same zip is the backup on both targets and moves a library between them. The owner chose this on 2026-11-04.
- **Export** is a chain of jobs. Each slice streams the next Items into a store-mode zip (no compression, so little CPU) as R2 multipart parts of at least 5 MiB, or appends to a file in the container, and saves its checkpoint (the multipart upload id, the parts written, the zip's central-directory entries so far and the last Item id) in `exports` in the same batch as its progress; the next slice resumes from it, so an interrupted export continues instead of restarting. Each Item's records and files are read in the same slice, and while an export runs, file deletions from deleted or refreshed Items wait until it ends, so the zip never lists a file it does not hold. Nothing holds the whole library in memory.
- **Restore** uploads the zip into the file store in parts under 100 MB (an R2 multipart upload on Cloudflare, a plain file in the container), then a chain of restore jobs reads it with ranged reads and writes records in batches, each slice saving its offset and the last record written in `restores`.
- **Why the app writes its own backup:** D1's export does not support databases with virtual tables, and the FTS5 tables are virtual (D1 docs, Import and export data); since the search index, D1's own export no longer works on a Threadsift database, and the portable export that replaces it is planned and not built. D1 Time Travel restores a database to any minute of the last 30 days on the paid plan (7 on the free plan) and covers the database only, not R2 (D1 docs, Time Travel).
- A backup list names every table the backup includes; a test migrates a database and fails when a table is in neither that list nor its list of excluded tables.

## Lint and format

oxlint and oxfmt run directly, not through Vite+. Vite+ 1.5.0 bundles the same oxlint and oxfmt, but its docs advise against `oxlint.config.ts` and `.oxfmtrc.json` and document only `--fix`, `--type-aware` and `-c` for `vp lint` (viteplus.dev/guide/lint, read 2026-11-04). Direct use keeps every oxlint flag and lets oxlint update on its own schedule. `oxlint.config.ts` and `.oxfmtrc.json` hold the rules; what they cannot show:

- **No separate `tsc` step.** `options.typeCheck` makes `oxlint-tsgolint` report TypeScript errors with the lint, and it needs TypeScript 7.
- **Rule plugins in `tools/oxlint/`.** `anti-slop/` is dmmulroy/anti-slop, vendored (its `UPSTREAM.md`); `oxlint.config.ts` and `.oxfmtrc.json` ignore it and `tsconfig.json` excludes it, so the repository's strict options do not apply to upstream code. `threadsift/` holds `no-comments` (`docs/agents/changing-code.md`, No comments). Anti-slop's `require-safety-comment-for-type-assertion` and its two assertion rules are off, because `typescript/consistent-type-assertions` set to `never` bans the assertion itself, and the safety rule would ask for a comment.
- **Only safe fixes run unattended.** The commit hook and the agent hook (`.claude/hooks/lint-fix.sh`, after each edit to a file in the project or in one of its git worktrees, linted with that checkout's own `node_modules`) apply safe fixes; suggestion fixes run only through `pnpm lint:fix`, whose diff the agent reads.
- **Markdown is not formatted.** oxfmt pads every table column to its widest cell, so a one-cell change in a doc would rewrite the whole table.
- **`design/` is mostly outside the lint.** `design/prototype/` is reference code, and the CSS in `design/system/` keeps its one-line rule layout, so both stay out of oxlint and oxfmt. `design/system/settings.ts` is app code: oxlint, oxfmt and the TypeScript `include` cover it.

## Dependency updates

Renovate, the GitHub App, is the one update bot; `renovate.json` holds its rules.

- **Schedule.** Every minor and patch npm update arrives in one PR on Monday morning (Istanbul time); each major gets its own PR, except that `oxlint` and `@oxlint/plugins` always move together, because they must share one exact version. Lock file maintenance refreshes the indirect packages on the first day of each month. The Dependency Dashboard issue lists every pending and waiting update, so it is where an update is noticed. Renovate never merges on its own.
- **Release age.** Renovate proposes an npm version only once it is 3 days old, the same wait as pnpm's `minimumReleaseAge` in `pnpm-workspace.yaml`, so a PR never asks for a version pnpm refuses.
- **Security.** GitHub's Dependabot alerts and the OSV database feed Renovate's security PRs, which open at any time and skip the wait (Renovate docs, `vulnerabilityAlerts`, read 2026-11-04). A fix younger than 3 days still fails pnpm's install, so that PR also adds the package to `minimumReleaseAgeExclude` in `pnpm-workspace.yaml`. Dependabot's own version and security PRs stay off, because both bots would open a PR for the same bump.
- **Local check.** `pnpm outdated` lists the npm updates before Renovate's next run. `devenv.lock` moves through `.github/workflows/update-devenv-lock.yml`, weekly or by hand, because Renovate's `nix` manager reads only `flake.nix` and is still in beta (Renovate docs, Nix manager, read 2026-11-04). The workflow runs `devenv update`, opens a pull request and approves the `pull_request` run of `gate` on its head through the REST endpoint for approving a workflow run, because a pull request that `GITHUB_TOKEN` opens holds its `pull_request` runs for approval (GitHub docs, Triggering a workflow from a workflow, read 2026-11-04). A `gate` started with `workflow_dispatch` instead passed but left the pull request blocked on `main`'s required check while the held run waited (a throwaway pull request, 2026-11-04). The approve endpoint needs the Actions write permission, which the job's `actions: write` gives its `GITHUB_TOKEN` (GitHub REST docs, Permissions required for GitHub Apps, read 2026-11-04). It needs the repository setting that lets Actions create pull requests.

## CI, releases and rollback

- **Gate.** `.github/workflows/gate.yml` runs the devenv checks, build, audit, design checks, and 3 end-to-end shards per target on separate runners and Instances with one Playwright worker each. Fail-fast is off so a failed shard leaves the others running, and every shard uploads reports and scenario attachments for 14 days. Compare full job times with devenv shell setup separated from test execution, following the local commands and count-selection procedure in `docs/testing.md`.
- **Shell setup and package cache.** Unmodified `pkgs.corepack` is available from `cache.nixos.org`, so cold runners avoid its build and install checks. pnpm 12 reads `pnpm_config_store_dir` for the cached store and ignores `npm_config_store_dir`.
- **Docs-only changes.** When every changed path matches `docs/**` or a root `*.md` file, the end-to-end jobs skip themselves with a job-level `if:`; `ci:check` and the build still run. A path outside that list runs every job, so a file missing from the list costs a longer run, never a skipped check.
- **Merging.** `main` requires one aggregate `gate` job that needs every other job and passes when each passed or skipped itself; a workflow-level `paths` filter is not used, because a workflow it skips leaves its required checks pending. Renovate opens dependency updates after a 3-day wait.
- **Secrets and forks.** No pull request run gets an AI credential: the Workers AI token, its account id and the Claude Code token live only in the GitHub environment `ai-proof`, whose deployment branch rule allows only `main`, because a dependency's install script in a pull request job can read a repository secret (the same reason the deploy token sits in `preview` and `live`). The gate's end-to-end jobs use `ai-proof` only on a push to `main`, so when those jobs run (a docs-only change skips them, as above), the real-AI cases run after each merge and skip with a notice on every pull request; a regression in them shows as a red run on `main`. Each run on `main` has its own concurrency group, so a later merge never replaces a pending run and every merge gets its AI proof; pull request runs keep one group per branch and cancel the older run. A pull request from a fork gets no secrets either, and a rerun does not change that (GitHub Actions docs). No job that runs pull request code uses `pull_request_target`, because it would run the fork's code with the secrets; the copy cleanup below uses it and checks out `main` only.
- **Pull request copies.** Each pull request from a branch of this repository against `main` gets its own Worker on Cloudflare with a demo owner and demo data, and its pull request page links it through a GitHub deployment. Worker Previews are not used, because they consume no Queue and run no Cron Trigger (Workers docs, Previews, Resources and isolation, read 2026-11-06), so every Paste would stay `processing`. `tools/pr-copy/cli.ts` does the work and `.github/workflows/pr-copy.yml` runs it; run with no arguments, it prints how to run it from a maintainer's machine.
  - **The token boundary.** The Cloudflare token can write every Worker, D1 database, Queue and R2 bucket in an account that also runs other production Workers, so no job that runs pull request code sees it. It needs the Workers R2 Storage Write permission in both environments. The token, the account id and the demo password exist only in the GitHub environments `preview` and `live`, whose deployment branch rule allows only `main`. The gate's `build` job holds no secret and uploads the pull request's build, migrations and `wrangler.jsonc` as an artifact. The deploy runs on `workflow_run` of a successful gate, from `main`'s workflow file and `main`'s checkout, and reads the artifact as data: it copies only named regular files that stay inside the artifact. The pull request number and head SHA come from the event, never from the artifact, and the deploy checks them against the pull request before it changes anything. The copy itself runs the pull request's code, so it receives the shared demo password and holds only demo data.
  - **Whose config.** The copy runs the pull request's `wrangler.jsonc`, so a change to the compatibility date, a flag, a limit or the cron shows on its copy. The deploy parses that file against a fixed list of keys and bindings and writes every name itself, so no command can reach the live database, Queue or bucket. `r2_buckets` may be absent or hold one entry with the binding `FILES`; the copy gets its own bucket name whatever the entry says. `ai` may be absent or hold the binding `AI`, and the copy keeps it as written, because a Workers AI binding names no resource of its own. A new key or binding fails the deploy, before any Cloudflare call, until `tools/pr-copy/stage.ts` maps it to a copy name. A file that holds `__proto__` or a `\u` escape fails too, because Wrangler's JSONC parser turns a `__proto__` key into the object's prototype, where the strict schema cannot see it (wrangler 4.156.0, 2026-11-07). Cleanup needs no config from the pull request, so such a change never stops a cleanup.
  - **Names.** A copy is the Worker and D1 database `threadsift-pr-<n>` and the Queue `threadsift-pr-<n>-jobs`, at `https://threadsift-pr-<n>.<subdomain>.workers.dev`. The R2 bucket for `FILES` is `threadsift-pr-<n>-files` (`threadsift-live-files` on the live copy). `wrangler deploy` makes it on the first deploy and reuses it on later ones; no explicit creation is needed (a first deploy on a new name made it, a second one found it and kept a file put there by hand, 2026-11-07). Each write refuses names outside that pull request’s exact Worker, database, Queue and bucket names before it runs; the live command has a separate set of allowed names. `threadsift-live-files` and `threadsift-files` (the name in `wrangler.jsonc`) are refused by every command, whatever the target.
  - **Migrations and resets.** Migrations run before the Worker deploys, so a failed migration never publishes code that needs the new schema; a later push keeps the data. `wrangler d1 migrations apply` skips a file whose name is applied even when its SQL changed, so each successful deploy records the database id and a hash of every migration file in its GitHub deployment. When the record no longer matches, a resource is missing while the Worker exists, or a database, Queue or bucket exists without its Worker (the left-over of a teardown that failed half way), the deploy deletes the whole copy, bucket included, and builds it again, because files left behind would belong to rows that no longer exist. It deletes the Worker too, because after `wrangler deploy` returned, the previous Worker version answered requests for some seconds and failed on its deleted database (2026-11-06). The Queue must lose its consumer before the Worker can go, and the Worker before the Queue. The Queues list API returns `consumers[].script`, although its API docs name `script_name` (2026-11-06, `GET /accounts/{account_id}/queues?per_page=100`). Matching copy and live Queue rows require `script`; a missing field fails their inventory before any write. Unrelated Queue consumers are not parsed. `wrangler delete` is not used, because it also lists KV namespaces, which the token may not read (wrangler 4.156.0, 2026-11-06).
  - **Sealing key.** `tools/pr-copy/copy.ts` reads the Worker’s secret names through the account API before a deploy. It uploads a random `THREADSIFT_SECRET_KEY` only when the binding is absent; later deploys omit it from `--secrets-file`, which preserves the existing secret in wrangler 4.156.0 (`pnpm exec wrangler deploy --help`). The setup code is refreshed for the demo setup path, and a random `PASSWORD_RESET_CODE` is uploaded beside it on every deploy, copy or live. A recreated sealing key cannot open settings encrypted under a deleted key; those still need the original key.
  - **Demo owner and data.** The deploy claims an unclaimed copy, or signs in to a claimed one, through the real API with the demo password. When the login answers `wrong` or `locked` (the password was changed on that copy, or its login lock is set), the deploy posts the reset with the code it uploaded, which sets the demo password and clears the lock, and signs in again; a reset that is itself locked fails the deploy with that reason. A reset or a change on the live copy ends Impeccable's saved session there. The deploy then pastes a fixed list of links and waits for each Item's end state. A page that changed fails that deploy only, with the Item's answer in the log. Right after a deploy, workers.dev answered Cloudflare's own 404 or `error code: 1042` instead of the app, even after a run of good answers from the app (2026-11-06). So the deploy waits for the app first and repeats a call that got such an answer; that call never reached the app, and a Paste of a known link only refreshes it. A call that got no answer at all, a network error such as `fetch failed`, is repeated the same way (2 of 10 fresh deploys failed that way right after publish, 2026-11-07). Every repeat ends at the earlier of the 120 s sign-in budget and the call's own deadline: no repeat starts when less than one poll (1 s) of it remains, the pause and the repeated request are cut to it, and a call with a zero budget makes one attempt. Only a transport failure from `fetch` is repeated; a malformed address or request fails at once. A request that reached the copy before its answer was lost is handled where a repeat would otherwise fail: a second setup answers 409 and the deploy signs in, a second reset answers 409 `reset-used` and the deploy then signs in with the demo password and fails if that login is refused, and a Paste of a known link refreshes the Item. Any other HTTP answer from the app still fails the deploy at once, and the log names a repeated request by its route, never its body.
  - **One run at a time.** Deploy and cleanup for one pull request share one concurrency group with `queue: max`, so runs queue and none is cancelled (the default keeps only the newest pending run). A run for an older head or a closed pull request stops without changes, so two quick pushes end on the newer head, and a close during a deploy is cleaned up after it. The number of copies has a cap, a guess against Cloudflare's 500 Workers and 250 Cron Triggers on Paid (the account had 2 Workers on 2026-11-06); a deploy past it fails and names the open copies.
  - **Cleanup.** The `delete` job runs on `pull_request_target` `closed`, or a dispatch with a pull request number, and checks out `main` only. It reads the pull request after it acquires its concurrency group and deletes only on `state: closed`; an API error keeps its resources and fails the run. A dispatched cleanup fails for an open pull request; a close-event cleanup that finds a reopened pull request ends without changes. It tries every deletion and treats a resource already gone as deleted. The bucket is emptied only when the Worker is gone: its delete succeeded, or answered 404 with code 10007, or the Worker was not listed. When the Worker stays, the bucket stays and the run fails, while the Queue and database deletions still run. The command starts one `prefixDelete` job with an empty prefix (`POST /accounts/{id}/r2/buckets/{bucket}/jobs`), polls it every 2 s for up to 10 minutes (a chosen bound, under the job timeout of 30 minutes), and deletes the bucket, which R2 refuses while it holds objects (409, code 10008). A bucket delete that an incomplete multipart upload still blocks fails and leaves the bucket for the weekly sweep; R2's default rule expires such uploads after seven days ([R2 docs, Object lifecycles](https://developers.cloudflare.com/r2/buckets/object-lifecycles/)), and the empty-prefix job cleared one in the 2026-11-07 run. A job that fails, is cancelled or times out fails the deletion, and the job is not started again in the same run; the next sweep or dispatched delete finds the bucket and starts a new job. A 404 counts as deleted only when a read of that exact bucket then answers 404 too; a 404 from the job endpoint with the bucket still listed fails the deletion. It fails with all deletion errors; only a successful cleanup marks the pull request’s GitHub deployments inactive. A reopened pull request gets a new copy from its next gate run.
  - **Copy checks.** Playwright's two targets run no real Cloudflare scrypt limit, Queue, Cron or invocation log, so `.github/workflows/copy-checks.yml` measures a copy on Cloudflare. A maintainer dispatches it with the pull request number and its head (`gh workflow run copy-checks.yml -f pr=<n> -f head=<sha>`; `docs/agents/reviewing-code.md` says when). It runs from `main` in the `preview` environment, joins the copy's concurrency group so a deploy or cleanup cannot replace the Worker mid-check, downloads the build of the gate run named in the copy's deployment record as data, and executes no pull request code. Because `main`'s code reads a pull request's copy, whose answers may carry fields or values `main` does not know yet, the checks decode each answer with their own schemas in `tools/pr-copy/copy-answers.ts`, which hold only the fields a check reads, never with the app's response schemas. `pr-copy.yml` writes that run's id and a digest of the artifact into the record's payload, and `cli.ts gate-run` checks that the run is a successful `pull_request` gate of this pull request at the dispatched head. A record without a run id stops the check and asks for a redeploy. `check` and `rebuild` also compare the digest of their `--artifact` with the recorded one (`artifactDigest` in `tools/pr-copy/stage.ts` hashes `dist/web`, `dist/worker/index.js`, the migrations and `wrangler.jsonc`, and an entry of `migrations/` ending in `.sql` that is not a regular file fails it) and refuse a different build, or a record without a digest, before any Cloudflare call. Two gate builds of different heads gave different digests, and one changed byte or one extra file changes the digest; the full path through a record could not run before a copy was deployed with the digest. The Cloudflare token reaches only the check step and the resume step, never the install step. `tools/pr-copy/checks.ts` drives the copy over HTTP and the account API; its scenarios are in `tools/pr-copy/check-*.ts` and its pass conditions in the run's step summary and `manifest.json`.
    - **Stops.** Before any Cloudflare write the run stops with a message when the pull request is closed or not at the dispatched head, when the copy's newest deployment is missing, failed or at another commit, when the Worker lacks Workers Logs with invocation logs at sampling 1, or when a real telemetry query fails. `stage.ts` writes that setting into every copy and the live copy, so a pull request cannot set it and a copy deployed before it needs one redeploy. The run reads the pull request and the deployment again just before its first write, and it stops when the copy is not idle: unfinished jobs, a pending Digest or a Provider would change the measurements. Every wait ends at an absolute deadline, and every request and sleep is cut to the time left. A run starts no new measurement when less than 15 minutes remain of its 240-minute budget and ends the check as inconclusive, so the step timeout of 300 minutes (the budget, one Cron wait of 21 minutes in flight, and the preflight) and the job timeout of 330 minutes (checkout, install, the download, the upload and the 10-minute resume step) hold whatever the copy does.
    - **Evidence.** The token needs the Workers Observability Write permission to query invocation records (`POST /accounts/{id}/workers/observability/telemetry/query`, view `invocations`). `tools/pr-copy/telemetry.ts` filters by Worker, script version, invocation type and the scenario's window, pages through the answer, and dedupes by request id. After each action the run makes one request to `/api/session` and waits until its record appears. That record shows the expected invocations arrived. It does not show the data is complete, because Cloudflare documents no ingestion watermark. So each query must report a `COMPLETED` run, `abr_level` 1 and no truncated record, and a `count` calculation over the same filters and window must report `sampleInterval` 1 (the telemetry query reference, read 2026-11-07); otherwise the check is inconclusive. The absence of a Cron sweep inside a Paste's window is read from the `scheduled_runs` row in the copy's D1 database before and after the Paste, because a sweep changes it, rather than from the telemetry. A sweep inside the window of a Paste makes that attempt unusable; after two unusable attempts the check is inconclusive. Each Paste uses a link the copy has not seen (its tag holds the scenario, the measurement index and the attempt, and the answer must be 201), the copy must be idle before it, and consecutive measurements are 20 s apart so their query windows (each widened by 10 s for clock skew) never overlap. A consumer invocation counts for a measurement only inside that Paste's own interval and when the Item has exactly one fetch job, finished; otherwise the check is inconclusive. A page whose decoded size differs from its declared size by more than 1 %, or that is not HTML, is fixture drift and makes the check inconclusive before any product assertion (the two requests for Beer differed by 307 bytes, 0.03 %, on 2026-11-07). Records hold full request headers, cookies and addresses, so the artifact keeps only the time, trigger, queue or cron name, route template, outcome, CPU and wall milliseconds, script version and status, and every string from the copy is dropped unless a closed enum or a validated id carries it. A route outside the app's list in `tools/pr-copy/routes.ts` is recorded as `other` (the list is written by hand, because the app builds its OpenAPI routes only with its ports; `e2e/contract.spec.ts` fails the gate on both targets when the served OpenAPI document lists a path that `routeTemplate` does not know, which found `/api/items/:id/read-state` missing; a stale line for a removed route is not caught and does no harm; routes outside the document, such as `/share`, stay `other`, and an unlisted route fails safe). Errors from the copy carry the route template and status only, and one function (`publicMessage`) formats every error the CLI, the scenarios and the rebuild print. Every decode of a copy's JSON goes through `decodeAnswer` in `tools/pr-copy/copy-calls.ts`, which turns a body that is not JSON into a fixed message with the route template and status, so a parser message that quotes the body never reaches the note, the manifest or the summary; `publicMessage` also replaces any `SyntaxError` message with a fixed one. The artifact is kept for 14 days; Workers Logs keep records for 7 days on Paid, and the 20 million events a month the plan includes cover a run of about 1,500 (Workers docs, Workers Logs, read 2026-11-06).
    - **Cron recovery.** The check pauses delivery on the copy's Queue, pastes a link, purges the Queue, and waits until the purge status reports a new purge complete. The Item must still be `processing` with an unclaimed job. It then resumes delivery. Passing needs a scheduled invocation after the purge and before the first consumer invocation after it. An Item that is no longer `processing` after the purge, a consumer invocation first, or a scheduled invocation before the purge completed means the message may not have been removed. The attempt is repeated once with a new link, and the check is inconclusive when the second attempt is unusable too. Resume runs when the check ends, in a separate workflow step with its own deadline that reads back `delivery_paused`, and in the next run's preflight.
    - **Workers AI.** The `workers-ai` scenario (`tools/pr-copy/check-workers-ai.ts`) is opt-in, because it spends Workers AI allocation: the `workers_ai` input of the dispatch (`-f workers_ai=true`) or `--workers-ai` on the CLI adds it to the default scenarios, and `--scenario workers-ai` runs it alone. The manifest's `rerun` command carries `-f workers_ai=true` when the run included it. It runs last, because it sets a Provider on the copy. Before any write it ends inconclusive when less than 15 minutes of the run budget remain, when the copy's settings answer lists no `workers-ai` (or has no `providers` list), or when the deployed version's bindings (`GET workers/scripts/{name}/versions/{id}`) hold no `AI` binding, so a pull request that predates the binding is not failed by it. The scenario saves Workers AI with a model and no key; runs Verify; waits for the jobs that the save opened for older Items; pastes a long Article (Gutenberg 1342) and expects a Digest; and reads the executor, Provider and model of the Verify and Digest task rows (the `ai_tasks` row, not only the `digests` row) from D1. It then waits for the copy to be idle, records the newest `ai_tasks` id, saves a model that does not exist, and expects exactly two newer tasks, Verify and the one Digest attempt, both bound to that model, failed as `model-not-found` and with one attempt, while the Digest job is done with no retry (`jobs.attempts` 0) and the Item ends ready with a failed Digest. Counting only tasks newer than that id keeps a second run on the same copy from seeing the first run's rows. Every request, query, poll and sleep ends at the earlier of its own deadline and the run deadline minus a 60-second allowance for cleanup, and the scenario calls `run.pace.settle()` before each phase that opens more work. Cleanup always runs: the scenario waits for the copy's jobs, then deletes the `settings` row in D1 and reads it back, and a drain timeout or a failed delete is recorded without skipping the other step. The workflow's resume step (`check --pr <n> --resume --workers-ai`) deletes the `settings` row too, so a cancelled run leaves the copy idle. Both paths reach D1 only through the exact-target guard. The binding works on a deployed Worker with no token, which a local `wrangler dev` does not give. The scenario calls real models, so each run spends the account's Workers AI allocation on the Items the save queues.
    - **Rebuilds.** The workflow's `rebuild` input deletes a throwaway draft pull request's D1 database and deploys its copy again that many times, to find the app 500 seen once during a demo seed. Before the first delete, and again before each one, it checks that the pull request is an open draft at the dispatched head, that the copy is at that head, that the artifact passes `copyConfig` and that the telemetry answers. Before all of that, `rebuildCommand` refuses an artifact that is not the copy's gate build. An app 500 anywhere in an attempt (the readiness polls, sign-in, a Paste) ends the attempt as `app-500`, so it is never `clean`. A 500 is classified as the app's JSON 500 or an edge or runtime failure. The run then polls for the invocation with the same route, status and time and records its request id and whether the Worker logged an exception, or records that the evidence is missing; the copy gives no request id, so the match is by route, status and time. The exception text stays in Cloudflare's logs. Close the throwaway pull request afterwards, which deletes the copy.
- **Weekly sweep.** `.github/workflows/sweep-copies.yml` runs `tools/pr-copy/cli.ts sweep` from `main` with the `preview` environment. The command joins pull request numbers from the Worker, D1, Queue and R2 bucket inventories and dispatches the copy workflow’s delete for each closed pull request. A closed pull request whose bucket is its only leftover is found too. The bucket list is cursor-paged, 1,000 a page. `sweep --dry-run` prints those resources without dispatching. Each deletion shares the pull request’s deploy concurrency group and checks its state again. The sweep attempts every lookup and closed-copy dispatch, collects failures by pull request number, then fails its Actions run if any failed; there is no automatic retry. A maintainer running it sets `GITHUB_REPOSITORY` and `GITHUB_TOKEN`; `GITHUB_API_URL` defaults to `https://api.github.com`.
- **Live copy.** `.github/workflows/live-copy.yml` accepts only a successful `push` gate on `main` in this repository. Its first job compares the gate SHA with `main` without secrets. The live job builds that exact SHA and checks `main` again just before its first Cloudflare write. The `threadsift-live` concurrency group queues runs without cancellation. The secret environment is `live`; the persistent GitHub deployment is `live-copy` with task `deploy:live`.
  - `tools/pr-copy/live.ts` deploys only the Worker and D1 database `threadsift-live`, the Queue `threadsift-live-jobs` and the bucket `threadsift-live-files`, using `stage.ts`; `wrangler deploy` makes the bucket when it is missing. It never deletes or resets them, and the bucket keeps its files across deploys. An initial deploy has no migration record; an existing record must match the database id and every recorded migration hash. `tools/pr-copy/live-migrations.ts` queries D1’s applied migrations and records their hashes immediately after application, including a partial failure, before publishing. If recording fails too, the log names both failures and preserves the migration error. Wrangler 4.156.0 rolls back the failing migration and keeps earlier successful migrations (`pnpm exec wrangler d1 migrations apply --help`). A failed deploy fails its workflow and is not retried.
  - **Recovery.** For `Live applied migration is absent from this build`, restore that applied migration file from the deployed revision, then add a new migration for any correction. For a missing Worker, restore `threadsift-live` with its original `THREADSIFT_SECRET_KEY` before deploying; do not replace that key against existing encrypted data. For a migration hash mismatch, restore the recorded migration file and add a new migration for the correction. For a database id mismatch, restore the recorded database binding and data before redeploying; if replacement was deliberate, verify its applied schema and data, then create a corrected `deploy:live` deployment payload through the GitHub deployments API before rerunning. For a missing D1 database, restore its data from backup and reconcile the record to its verified id; for a missing Queue, recreate `threadsift-live-jobs` and restore its consumer binding before rerunning. These are manual operations because a deploy cannot decide which lost data or queued work is recoverable.
  - **Demo data.** `tools/pr-copy/demo.ts`’s `ensureDemo` claims the owner or signs in with the live environment’s password. It pastes each demo link when the owner was created, or when that link has no Item yet, so a partial first seed completes next time. Existing Items are kept; live waits only until demo Items are no longer `processing`, then ends with a signed-in `GET /api/session`. Changed demo pages do not fail the live deploy. Pull request copies retain their stricter end-state checks.
- **Design review.** `tools/impeccable-wait.sh` reads a head’s `pr-copy` deployment and Impeccable check without posting comments; its usage text names the exit codes and timeout setting. When the review needs a request or approval, it prints the caller’s comment command and exits 3; once a `/impeccable` comment newer than the copy exists, it waits for that review's run instead. The copy workflow’s run name identifies the pull request and original head, since a `workflow_run` run itself reports main’s SHA. A draft exits immediately. `docs/agents/reviewing-code.md` owns the review procedure. Impeccable’s live address is the live copy; it signs in there with a saved browser session, because the live copy’s demo password differs from the copies’ and Impeccable’s form check found no sign-in form (`docs/spec.md`, Decisions: Design review).
- **Releases.** Not built: no release workflow exists. The plan is that a release tag builds and publishes the image with that tag and moves the `release` branch to it.
- **Rollback.** Planned with the releases. The container rolls back by running the previous image tag. Cloudflare rolls back with `wrangler rollback` to the previous Worker version. Both work because a migration only adds and the previous release still runs on the new schema.

## Testing

`docs/testing.md` is the project's testing policy: no fakes and no replayed recordings; each claim is proven through the real app the way the owner or an agent reaches it.

- **One suite, two targets.** Playwright runs the same `e2e/` suite against the container image (built and started with Podman, real `node:sqlite` and a real folder) and against the Worker under `wrangler dev`, which runs Cloudflare's own workerd with local D1, R2 and Queues. The target's script (`tools/e2e/container.sh`, `tools/e2e/worker.sh`) gives the suite its base URL in `THREADSIFT_BASE_URL`, and a spec restarts the target through the script, so the app has no restart route. A script also takes `launch`, `restart`, `logs`, `sql`, `query` and `stop` for one instance folder, so a spec can start a second Instance with its own `SETUP_CODE`, restart it, read its log, change a row (`sql`, for example to end a throttle lock) and read rows (`query`; the container runs `node:sqlite` inside the image, which has no `sqlite3` binary). `THREADSIFT_INSTANCE_SCRIPT` names the script, `THREADSIFT_E2E_DIR` the folder of the main Instance and `THREADSIFT_SETUP_CODE` its code. With `THREADSIFT_ARTIFACTS` set to a folder, each target run writes into its own `<target>-<UTC time>` folder there, so a later run does not overwrite it: the HTML report in `html/`, the app's own log of every Instance in `logs/` (the container's stdout, the `wrangler dev` output, with generated setup codes redacted), and under `results/` the access scenario's screenshots and `api-statuses.json` and the ingest scenario's screenshots and `statuses-<step>.json` (each Item's status, reason, fetch result and the attempts of each job), and the article scenario's `item-<step>.json` (each Item's API answer after the step, post text included). Global setup completes the main Instance's setup through `POST /api/setup` and saves the owner's session and an agent token for every spec. Tests reach the app through the UI, `POST /api/items`, `GET /api/items` and `/mcp`, each with the owner's session or an agent token, and check what the owner sees: Source, Kept comments and Context stubs, Digest fields, search and filters, Read state, Highlights and Notes, and what survives a restart.
- **Checkout images.** `devenv.nix` owns the checkout path and `THREADSIFT_E2E_IMAGE`, which `image:build` and `tools/e2e/container.sh` share. The tag identifies the checkout path so builds in separate worktrees cannot replace each other. Before building, `tools/e2e/build-image.sh` removes labelled images whose checkout folder is gone and this checkout's own untagged images. Cleanup is best effort; an image a container still uses stays. Images without the checkout label and images of other existing checkouts stay untouched.
- **Instance ports.** `tools/e2e/worker.sh` passes port 0 for HTTP and the inspector on launch with `--ip 127.0.0.1` and reads the bound HTTP address from Wrangler's readiness output. `tools/e2e/container.sh` omits the published host port and reads the mapping with `podman port`. Both keep the assigned HTTP port on restart, because open browser pages and Playwright request contexts keep their original base URL. The Worker's inspector uses port 0 on every start.
- **Hard cases the suite owns,** each brought about through a real route:
  - an export and a restore of a library larger than 100 MB on both targets, each stopped mid-run (the container restarted, the local Worker restarted) and resumed from its checkpoint;
  - a client that disconnects in the middle of a file download and of an MCP stream on the container (Hono's Node adapter has open streaming issues 407, 411 and 388);
  - two `POST /api/items` calls at once, each carrying a ready Digest that names the same new Tag, which must leave one Tag;
  - a Grok Bot result posted for a task whose input revision has moved, which must not be applied and must queue the step again, and a second result for a closed task, which must get 409;
  - many Item changes while a mirror job runs, after which the vault matches the library.
  - a share from the installed app: `e2e/share-target.spec.ts` posts a same-origin form with no `url` field and a `text` that holds a link with a query, a fragment and a trailing full stop, then shares it again and reloads and goes back and forward, and counts the `POST /share` and `POST /api/items` requests the server received and the fetch jobs it opened (the owner's browser goes through a recording proxy that `e2e/share.ts` starts in the test process, because neither target keeps an access log), expecting 2 and 0, and 0 and 0 for a forged `/?saved=` or `/?link=` address; it also sends arrivals from pages that `e2e/share.ts` serves from the test process (a link, a no-referrer link, a `GET` form, a `POST` form and a sandboxed `POST` form, from the same host on another port and from the other loopback name), a header matrix with the owner's cookie, and an agent token alone. `e2e/share-signed-out.spec.ts` covers sign-in with a wrong password first and a session that ends before Add.

  Lease expiry itself has no real route that a test can time. The guarded batch it relies on was run in the spike (Database and search, Guarded batches); expiry inside the app stays listed under Open items.
- **Jobs on the Worker.** Local Queues run no consumer concurrency (Cloudflare docs, Queues local development), so on the Worker suite jobs run one after another, and on the container up to 4 run at once. `e2e/ingest-scenario.spec.ts` asserts that a fast link ends before a stalled one on the container, and after it on the Worker. Local Cron Triggers do not run on their own. `wrangler dev` 4.156.0 serves `/cdn-cgi/local/scheduled`, which calls the Worker's `scheduled` handler; `/__scheduled` answers the app's page unless the dev server starts with `--test-scheduled`. A call to the endpoint answers 200 whatever the handler did, so `e2e/ingest.ts` (`sweepNow`) clears `scheduled_runs` first and the specs assert the job row's effect.
- **Real sources.** Fetcher tests call the live GitHub API, live article pages, Reddit's oEmbed and Arctic Shift, and assert on the shape of the result (title present, Markdown text of some length, the repository's stars as a number), not on text that changes, except for the article tests below. The link tests use pages that do not change: example.com, is.gd short links created once through is.gd's API (to a documentation page, a page that answers after 6 s, a page that sends its headers and then drips its body for 10 s, a Reddit post, an X post and the essay `https://stephango.com/saw`; two tinyurl.com links made the day before already answered with tinyurl's `/preview/deprecated/` page), one old Reddit post with two of its comments, and the `KyaniteHQ/commonplace` repository, which GitHub redirects to `KyaniteHQ/threadsift`. The article tests read real public pages and assert on sentences from them: `https://en.wikipedia.org/wiki/Bread` (619,662 bytes; the live page, because the owner named this URL), Bird vocalization through a permanent revision URL (`/w/index.php?title=Bird_vocalization&oldid=1380253618`, its footnote from past byte 524,288), the essay `https://stephango.com/saw` (author, title and posted date), `matklad.github.io` and `jvns.ca` posts (a date without a time, and a time without an offset), MDN's `<video>` page (iframes and code samples that mention the tags) and `https://httpbin.org/html` (a page with no `<title>`). An edit to the live pages (Bread, the essay, MDN, the two blog posts) fails those tests until their constants in `e2e/articles.ts` follow it. httpbin cannot serve a page of our choosing as `text/html` (its `/base64/` route answers `text/plain`, and `httpbin.org/response-headers` refuses `text/html`), so no test depends on a made-up HTML page except the `text/plain` case.
  - **Reddit's rate limit.** `e2e/reddit.ts` spaces the pastes that send an oEmbed request by 2 s. One run of the suite made 23 such requests before slice 12a (the `reddit-oembed` annotations of the Playwright report); the Reddit thread specs add 2 by count, not yet measured. The oEmbed endpoint sends no rate-limit header; 25 requests at one a second all answered 200 on 2026-11-04.
  - **GitHub's rate limit.** GitHub allows 60 unauthenticated requests per hour per address, shared by every program on it ([rate limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api#primary-rate-limit-for-unauthenticated-users)). `e2e/github.spec.ts` sends 10 requests per run per target, measured as the change of `used` in `GET https://api.github.com/rate_limit`, which does not count against the limit: 2 for `kepano/defuddle`, 3 for `KyaniteHQ/commonplace` (the 301, the repository, the README), 2 for `KyaniteHQ/homebrew-linctl`, which has no README, 1 for a repository that does not exist, and 2 for the run whose claim is taken over. `requireGithubBudget` reads the same endpoint before each test. When fewer requests remain, it skips the test on a development machine and fails it in GitHub Actions (`GITHUB_ACTIONS` is `true`, [default variables](https://docs.github.com/en/actions/reference/workflows-and-actions/variables#default-environment-variables)); either message names the remaining count and the reset time, so a rate-limited run never shows as passed. `CI` cannot tell the two apart, because `tools/e2e/worker.sh` sets it on every Worker run. The trade-off is that a runner whose shared address has used its 60 requests fails the gate until GitHub's reset, and the fix is to rerun the failed shard after the reset time in the message. `e2e/normalization.spec.ts` and `e2e/scenario.spec.ts` paste 6 links to repositories that do not exist, each answered 404 after one request (`used` went from 1 to 7 for the two files on the Worker, 2026-11-07), so one run of the whole suite sends 16 requests per target; their outcome does not depend on the answer, so a rate-limited answer leaves them passing.
  - **The listener.** The refusal tests start an HTTP listener in the network the app runs in, through `THREADSIFT_APP_EXEC` (empty for the Worker, `podman exec -i <container>` for the container), and send it a control request from the same network first, so its later silence means a refusal and not a wrong address.
  - **The redirectors.** httpbin.org's `/redirect-to` answers 403 to a target on an internal address (`Forbidden redirect target: redirect target is an internal address`, 2026-11-04), so the refusal tests redirect through httpbin.dev, which redirects anywhere, and httpbin.org serves the redirect chains, the stalled body and the encodings.

A revocation between a check and the insert needs a write between the two statements, and the attempt makes none: SQLite fires triggers on writes, never on a read, so no trigger can order it. The atomicity rests on the task being one statement.
