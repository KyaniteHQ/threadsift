# Testing

The testing policy for this repository; it overrides broader testing instructions. Read it before writing, changing or deleting a test. `docs/architecture/testing.md` says how the suites are built.

- Tests run the real code on a real database and real runtimes. The app has no mocks, stubs, fakes, replayed recordings or test-only seams. A vendor's own local runtime (`wrangler dev` with local D1, R2 and Queues, Podman, Chromium) counts as real.
- Core tests in `test/*.test.ts` start the real app in process on a temp database with the real `migrations/` and call it through `app.request`. They reach no network beyond a refused local port (a test that saves a Provider points it at `http://127.0.0.1:9`) and no working Provider, and each file states the requirement it proves. Two of them, through `test/own-host-name.ts`, need the machine's own host name to resolve only to private addresses, as it does on a GitHub runner and on a host whose `/etc/hosts` maps the name to a loopback address; on a machine where it resolves to a public address they fail, and so do `pnpm test`, the pre-push hook and the `check` job, until an `/etc/hosts` line maps the name to `127.0.0.1`. Run them with `pnpm test`; the `check` job and the pre-push hook run them too. A parser that takes literal input, such as `readArticle` and `catalogKey` in `test/parsers.test.ts`, is also tested by calling it directly, because its input and output are values and no request reaches it; any rule that a request can meet, such as the refusal of a host, is tested through `POST /api/items`.
- The gate without the browser smoke is `devenv tasks run ci:gate`, and the `check` job runs the same command. `devenv test` is not the gate, because it starts the dev `processes`.
- One browser smoke spec, `smoke/smoke.spec.ts`, runs on both install targets on every pull request. Run it with `devenv tasks run smoke:worker` and `devenv tasks run smoke:container`. Each checkout builds and runs its own image, `localhost/threadsift:smoke-<slot>`, on its own port, so two worktrees can run it at once (`docs/architecture/testing.md`, Smoke).
- The start check, `tools/start-check.sh <image>`, runs an image with a fresh volume and `PORT=8080` and asks `GET /api/session` until it answers 200, for at most 60 s after the container starts. The `image` and `image-publish` jobs run it on every image they publish before `:main` moves. Run it by hand on a local build with `devenv tasks run image:build`, which tags the build `localhost/threadsift:publish` (one tag for every checkout), then `tools/start-check.sh localhost/threadsift:publish`. A `workflow_dispatch` run with `publish: false` runs it on both architectures and pushes nothing (`docs/architecture/ci-releases-and-rollback.md`, Image).
- The live check, `smoke/live.spec.ts`, reaches the internet daily on `main` and blocks neither a pull request nor the deploy. On the container it also calls a real model, the owner's Claude subscription through the Provider "Claude Code on this server". The Worker run calls no model: its Pastes carry a caller-sent Digest. Run them with `devenv tasks run live:worker` and `devenv tasks run live:container`. `live:container` needs `CLAUDE_CODE_OAUTH_TOKEN` from `claude setup-token` and fails at once without it; it installs Claude Code in the container, so it needs the network.
- Checks against a deployed copy run on the owner's machine, never in CI. Run `tools/check-deployment.ts` as [Check an Instance](deployment-check.md) describes; Provider mode and caller-supplied publication mode prove different contracts. Preview provisioning creates the demo owner, the demo Items and, when the database has a `proposals` table, the demo Proposals (Tag pairs, Topic pairs when the database has the column `from_topic_id`, lost-Highlight rows on demo Highlights when it has the column `highlight_id`, overview-gap rows on three demo Topics when it has the column `topic_id`, and items-disagree rows on three demo pairs of Items when it has the column `from_item_id`; one `wrangler d1 execute` insert), and saves no Provider; it runs no deployed check suite.
- Only the `deploy` job in `.github/workflows/gate.yml` targets `--env live`. The separate PR preview workflow runs remote commands only against its PR manifest (`docs/pr-previews.md`). A machine signed in to Wrangler reaches the live account, and `CI=true` skips Wrangler's confirmation prompt, so a local check uses `--local`.
- A change is proven by running the real program the way its caller does, and the command and its output are kept as the artifact. A bug fix is proven by one reproduction that fails before the fix and passes after it.
- A flaky run is rerun, and its cause is fixed in the test, not hidden behind a retry or a sleep.
