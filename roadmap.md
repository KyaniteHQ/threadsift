# Roadmap to v1 and after

This file is the one ordered list of the work left for Threadsift v1 and for the two parents that follow it. It is temporary: the owner deletes it at the release of the hosted product, or earlier. It lists issue numbers because it is a working list, not a doc of the product.

Status: the list is running. The plan for running it is in "How the list is run".

## How to use this file

- Work from the top. `- [ ]` is left, `- [x]` is done. An item is ticked when its own **Check** ran and passed, and for no other reason.
- The next item starts when the one before it is ticked, or when the one before it waits or failed as "How the list is run" describes.
- An item marked **WAITING** does not block the list. It names who has to act. Skip it, go on, and come back when the answer arrives. An item that needs a WAITING item says so in its "Needs".
- **Issues.** Before an item that names an issue is built, read that issue in full: its body, its comments and its acceptance criteria. The pull request names the issue. An item whose Check names an issue's criteria works on that issue; an item that only mentions an issue in its text does not. An issue is closed after the last item that works on it is ticked, once its own acceptance criteria are met and its comments, relations and state are read back. So a tick never waits for an issue to close, and no issue is closed by a tick alone. The issue of a Part (items 2.0 to 6.0) closes when the last item of its Part is ticked. A parent issue (#1, #704, #705) is closed by its own item (7.25, 8.6, 9.13), when its sub-issues are closed and the owner says yes.
- When an issue's body and an item of this file disagree, the owner decides which one changes. The open cases are listed under "Issues and this file" below.
- An item that changes a screen follows the screen rules of [Changing code](docs/agents/changing-code.md): the `impeccable` skill, the `modern-web-guidance` skill, tokens only, and the browser target Baseline Widely available.
- **Needs.** An item needs every earlier item of its own Part that is not marked WAITING, and every item its "Needs" names. Parts 0 and 1, and items 7.1 and 7.2, are the exception: their items do not need each other. Items 4.17 and 6.11 need only the items they name: 4.13 and 4.14 need 4.17, and the owner decided on 2026-11-27 that 6.11 is built at once. Items 4.13, 7.10, 7.11 and 7.12 change no screen and also need only the items they name; for 4.13 the Extension's final look is needed by the upload of 4.14, not by the package command. Parts 8 and 9 need the release (7.19).
- **Words used below.** "The smoke library" is the set of Items the browser smoke spec creates; an item that needs a kind of Item it lacks adds one. The docs are named by what they hold: the product context doc is [PRODUCT.md](PRODUCT.md), the design system doc is [DESIGN.md](DESIGN.md), the spec is [the spec](docs/spec.md), the decisions doc is [Decisions and evidence](docs/architecture/decisions-and-evidence.md), the styles doc is [Styles](docs/design/styles.md), the fetchers doc is [Fetchers](docs/architecture/fetchers.md), the web app doc is [Web app](docs/architecture/web-app.md), the testing doc is [Testing](docs/testing.md), the bot docs are [Extension and Threadsift bot](docs/architecture/extension-and-threadsift-bot.md), and the open claims are in [Open items and unverified claims](docs/architecture/open-items-and-unverified-claims.md).
- The research behind this file is in the gitignored private docs folder of the owner's main checkout, `docs/private/`, which a worktree does not hold; a brief gives its full path. Its folders: `research/` (similar products, release schemes), `design/` (the Gemini 4 Neon answer and the mood boards), `refero/` (60 style references from refero.design), `extension-stores/` (the stores' API and review docs), `terms/` (Reddit's, GitHub's and X's terms), `x-api/` (the X docs, the OpenAPI document and `design-notes.md`), `grok-bot/` (xAI's Grok Bot docs and `NOTES.md`) and `requests/` (the questions behind 0.3 with their answers and checks, and the texts the owner sends to X, Reddit and a payment company).

## How the list is run

This is the plan for running the whole list after the owner says go. One session, the orchestrator, runs it. Lines marked "decided" are the owner's answers to the plan; the others follow from the rules the repository and the owner's agents already have, and the orchestrator may change them when a run shows a better way.

For one item:

- **Who starts the agent (decided).** The owner says go once. The orchestrator then starts one agent for each item, Opus 5.5 at high effort, in its own herdr tab, with `claude-tools agent start`. The owner can open any tab and read or stop the agent.
- **What the agent gets.** A brief file outside the repository. It names the item's text and its Check, the issues to read in full first (body, comments, criteria), the worktree the orchestrator made for the item, the docs the routing table of `AGENTS.md` names for the paths, the full path of the private research folder, the limits (the spending rule, the data rule, no landing, no issue closed), the commands that prove the item, the stop conditions, and the report path.
- **What the agent returns.** One commit or more on the item's branch, and a report file: the commit, the files changed, each part of the Check with the command and its output, each acceptance criterion of each issue with its evidence, and every open point with its blocker. It then tells the orchestrator it is done.
- **How the orchestrator verifies.** It does not take the report as proof. It runs the item's Check itself, reads each named issue's criteria against the evidence (a Check that cannot be repeated, such as a tag, an upload or a deletion, is verified by reading its result back), and starts the one review of the change by a reviewer that did not write it. The agent fixes every finding, and the orchestrator compares the fixed change with the reviewed one. Then the pull request lands by squash merge once the required checks pass, the item is ticked in this file, and an issue is closed as the Issues rule above says.
- **What waits for the owner's yes (decided).** Ordinary code, doc and design items land and close their issues without the owner. Six kinds of action wait, each with one line that says what will happen: a pull request that holds a migration; the release candidate tag and the `v1.0.0` tag; an upload to a store or a post in the owner's name; deleting a cloud resource or a repository; a run that would take the X API spend of the whole list above 20 USD (a guess for the probes and live checks); and closing a parent issue (#1, #704, #705). An action that waits is handled like a WAITING item: the list goes on with what does not depend on it. Items 2.11, 4.9, 6.5, 6.7 and 6.8 probably hold a migration, so their pull requests wait in this way.
- **Screens wait for the owner's look (decided).** No item that changes a screen lands before the owner approves its screenshots. The agent builds it, the orchestrator verifies and reviews it, and the pull request stays open. The orchestrator then reports the pull request and the folder of screenshots, taken on synthetic Items in every Theme at 360 px and at 1680 px. What the owner wants changed goes back to the same agent, and the owner looks again. While a screen item waits, the orchestrator starts no other item that changes a screen, so nothing is built on a look the owner may refuse; it goes on with items that change no screen and do not need the waiting one.
- **When verification fails (decided).** The findings go back to the same agent. After two fix rounds that fail for the same cause, the item gets a line `FAILED` under it in this file, with the error and where the evidence is, and its branch and worktree stay in place. The orchestrator goes on with the items that do not need it and reports the failure at its next stop. It stops at once only when the failure is in something every item uses: the gate, a broken `main`, or the live copy being down. A check that cannot run at all (a missing login, a service that is down) is marked "not run" with the error; the item is not ticked, and the list goes on in the same way.

For the whole list:

- **Order.** From the top, one item at a time, one agent for each item. The orchestrator picks the first open item that is not waiting, has not failed, and whose "Needs" are ticked.
- **WAITING items.** The orchestrator does the part an agent or a session can do (the draft, the request text, the dry run) when it reaches the item in the order, and then leaves the item open with what the owner or the other party has to do. It asks the owner at once when the owner is present. An item that has a WAITING part inside it is built up to that part and is ticked when the part is done.
- **A question from an agent.** When an agent needs a product decision that the spec, the decisions doc, the glossary and the issue do not settle, the orchestrator asks the owner, and the item waits like a WAITING item.
- **The states of an item, and the way out of each.** The order always starts again from the top, so an item whose wait has ended is picked before a later one.
  - Open: it starts when its Needs are ticked.
  - Building: one agent works on it.
  - Waiting for the owner or another party (a WAITING item, an agent's question, the owner's look at a screen, the owner's yes to one of the six actions): a line `WAITS:` under the item says for what and since when, with the pull request when one is open. It leaves this state when the answer arrives.
  - Not run (a Check that cannot run): a line `NOT RUN:` under the item names the error. It is tried again when the cause is gone, and it counts as waiting until then.
  - Failed: a line `FAILED:` under the item. It is tried again only after the owner or a later change removes the cause.
  - Ticked.
- **When the orchestrator stops and reports.** At a screen item that is ready for the owner's look; at an action from the list of six that is ready for the owner's yes; when a failure blocks everything; when no open item can start, because each one left waits on someone or needs a waiting or failed item; and when the list is done. Each report says how many items are ticked and how many are open, names every open item that waits with what ends the wait, every failed item with its error, and every check that did not run. Between stops, a reply to a finished agent gives only the counts.
- **State.** This file is the record of what is done. The orchestrator's own checklist, outside the repository, holds each running agent's name, worktree, brief and report path, so that the run continues after the session's context is summarized.

## Part 2. The brand first, then the Styles and the Settings menu

The owner's decision: the 10 borrowed Styles are removed. Styles of our own replace them, 3 or more, with Library as the default. Font and Accent work under every Style. The redesign covers layouts, buttons and components, not only colours and faces.

What the review found (each line names its source):

- **The panel today.** One popover holds 12 settings and the app's navigation. Highlights, Import, Index, Log, Proposals and Instance settings are links inside it, so the library wiki is two clicks behind a gear (seen on a local Instance at `origin/main`, 2026-11-25). - **How similar products offer settings.** None of the 13 studied offers whole looks, except Linkit with 12 colour themes. The others offer Light, Dark and System, a few reading controls (face, size, line width; Readwise Reader adds 6 reading colours) and nothing else. They keep view options (layout, columns, what a card shows) in a menu beside the list, apart from reading options (Karakeep's View options, Raindrop's View menu, Readwise Reader's "Aa" popover).
- **What a brand looks like in the 60 refero references** (`docs/private/refero/`). Each describes one look, and 54 of the 60 name a signature element that may not change ("the 60px pill is non-negotiable", Fable). Only 15 mention themes at all.
- **What is common, and so not ours.** 27 of the 60 references are warm paper or cream, and 57 of the 60 use pill shapes. A warm cream page with a rust accent and pill buttons is the look of the moment.
- **Gemini 4 Neon (High)** proposed three directions, a catalogue strip with the kept count as the signature, navigation in the masthead and fewer settings. Its own pick, "Index Room", is warm paper with a red-orange accent, which the count above argues against. The owner chose another of the three, Quarto (item 2.3).

The recommendation: set up one brand first, and let the settings sit inside it.

- **The brand is what never changes:** the wordmark and icon, the signature element (the mono strip with the kept count, and the covers of Part 3), the anatomy of every component, the layouts, the motion and the voice. A screenshot in any Style, Theme or Accent is still Threadsift.
- **The redesign of layouts, buttons and components happens once, in the brand.** It is not repeated per Style.
- **A Style is a material, not another product.** It changes token values only: the neutral world (paper and ink), the faces, the default Accent, the corners, the weight of hairlines, shadow or no shadow, how a button is filled and how a Tag is drawn. It never changes where things are or what a component is made of. The trade-off: Styles differ less than the borrowed ten did. In return each combination of Style, Theme, Accent and Font is one of 135 token sets (3 Styles; 3 Themes, because System only picks one of them; 5 Accents; 3 Font pairs; 180 once 2.12 adds a fourth pair) that one contrast check covers, and the product is recognisable.
- **Three Styles at v1:** Library (the brand's default), a print one (working name Broadsheet: sharp corners, hairline rules, no shadows, a serif reading face) and a technical one (working name Workbench: a mono-forward face for a library of repositories and code). A fourth is added only when it has a use the three do not cover. Dark is a Theme, so no Style is "the dark one".
- **Choosing a Style writes its Font and Accent into the settings,** and the owner can then change either. No control is ever disabled.

## Part 6. X through the X API, with the owner's own key

What the X docs say (every claim has its file in `docs/private/x-api/design-notes.md`):

- **Price.** Credits are prepaid, with no tier to choose. A post read costs 0.005 USD, a search bills each post it returns at the same price, and one of the owner's own bookmarks costs 0.001 USD. The console has a spending limit per billing cycle, and `GET /2/usage/credits` returns the balance.
- **Keys.** Reading posts and searching needs only the app's read-only Bearer token. Bookmarks need OAuth 2.0 with PKCE and the scopes `tweet.read users.read bookmark.read offline.access`; a refresh token works once.
- **One app per owner.** X's Restricted Use Cases page says "requiring your end users to register applications for the purpose of using your tool or service could result in enforcement actions", and X staff answered on the developer forum on 2026-08-18 that a free kit which each person runs with their own developer app "isn't permitted". X's own xurl and xmcp, n8n and Postiz ask each user for their own app all the same, and a search of 2026-11-27 found no user and no tool punished for it. The owner's decision of 2026-11-27: the reader is built, it stays optional, and the guide for the key names this risk (6.9).
- **Duties.** Stored posts must follow X: a post deleted, protected or changed on X must be deleted or changed in the store. A displayed post must show the author's picture, name and handle with links, a linked timestamp and the X logo. These reach a self-hosted Instance too, and they change the Reader for X Items.
- **Hosted.** A hosted product may not take its customers' X keys, and pay-per-use is for "a limited number of end-users". X publishes no number for it (0.8), so a hosted Instance stores an X Item as a Link-only Item (item 0.3).
- **X's MCP server.** The docs MCP is free and useful for the agents here. The X MCP spends credit on every call (one full search page of 500 posts is 2.50 USD), so no agent and no part of the product gets it with the paid key.

It works on Cloudflare, where the grok CLI does not. One Item costs about 0.70 USD for a post with 45 replies (a guess from the price table), because probe S2 measured that X bills the users and the quoted posts in `includes`.

## Release and version scheme

The survey read the tags of 47 repositories on 2026-11-25 (the release schemes file in the private research folder).

| Approach | Format | Example repository and tags | For Threadsift |
|---|---|---|---|
| SemVer, strict | `v1.4.2` | immich `v3.4.2`; paperless-ngx `v3.5.1`; linkwarden `v2.17.0` | Fits. Both extension stores and image tags accept it, and each part can carry a meaning (below). |
| SemVer with a long 0.x | `v0.35.0` | karakeep `v0.35.0`; ollama `v0.40.18` | No. The project already calls its first release v1, and a 0.x that never ends says "not ready". |
| CalVer, year and month | `2026.11.3` | home-assistant `2026.11.3`; bitwarden `v2026.11.1`; actual `v26.11.0` | The runner-up. It shows a copy's age, but cannot say "this release needs you to act", and it fits a fixed monthly release, which Threadsift does not have. |
| CalVer, date | `2026.11.23` | yt-dlp `2026.11.23` | No. It suits daily fixes with no migrations. |
| Hybrid or named | `v66.13.0`, "Krypton" | unocss; node's LTS codenames; tailscale's odd and even minors | No. Each adds a rule a reader must learn. A headline phrase in the release title gives the same warmth for free. |
| Rolling | `:main`, a date and a commit | searxng; minio's timestamps | Stays as the edge channel (`:main`). It cannot be the release: the stores need rising numbers and the bot needs a pin. |
| One prefix per artifact | `bot-v12`, `browser-v2026.11.0` | bitwarden/clients; tauri; the bot today | No. "Which Extension works with which Instance" then needs a table. |
| One version for all artifacts | server and app share `3.4.0` | immich | Chosen. Every artifact carries the release's version, and the gate refuses a difference. |

**The format, the owner's decision.** SemVer, first release `v1.0.0`, one version for every artifact.

- **Major:** the owner must act to update, or an Extension or bot of the last major stops working.
- **Minor:** new behaviour; it may carry a migration, and its notes say how far back a rollback can go.
- **Patch:** fixes only, and never a migration. So the image tag `:1.4` is always safe to follow.
- **Before a release:** `v1.5.0-rc.1`. It gets its own image tag and moves nothing else.
- **Image tags:** `:1.4.2`, `:1.4`, `:1`, `:latest` for the newest stable release, and `:main` for the edge.
- **Titles:** the product and the version, with a headline on a minor.

| Tag | Release title |
|---|---|
| `v1.0.0` | Threadsift 1.0 |
| `v1.1.0` | Threadsift 1.1: (one headline phrase) |
| `v1.1.2` | Threadsift 1.1.2 |

**Notes.** A release's notes open with two or three plain sentences, then "Before you update" (migrations, the rollback floor, manual steps, the Extension and bot versions this Instance expects), then Added, Changed, Fixed and Security, then the image line, then GitHub's generated list of pull requests. They are written by hand in the changelog as the work lands.

**The `github-release` skill of awesome-copilot.** Its checklist (a tag, generated notes, a verified tag) fits. Its release branch name `release/vX.Y.Z` does not: Git refuses it beside the existing `release` branch.
